FHIR-37791: Clarify interface behavior across conformance definitions

Issue request:
FHIR-37791 was Published / Persuasive with Modification for R5. It asked the specification to define where interface StructureDefinitions may be referenced: allowed in StructureDefinition.context, SearchParameter.base, ElementDefinition.type.profile, and ElementDefinition.type.targetProfile; not allowed in Reference.type or ElementDefinition.type.code; and to explain inherited interface constraints in snapshots.

Initial application:
The original source application appears to be git ee6ec073, "37791 - interface documentation", which added StructureDefinition examples for abstract resources and interfaces. Related later commits covered parts of the same behavior indirectly: FHIR-32069 split concrete ResourceType from all resource types for bindings, FHIR-28411 clarified Reference.type as a concrete resource type, and FHIR-46620 clarified extension context specialization and interface contexts. Current source still lacked explicit guidance for several surfaces named in the resolution.

Additional context:
FHIR-I minutes on 2022-08-15 record the 15-0-0 Persuasive with Modification vote for this issue, and the Jira comments record the detailed FHIR-I discussion. FHIR-51035 later clarified that interfaces are not valid baseDefinition targets for additional resources, which is consistent with using profile/targetProfile or implements-style interface references rather than treating interfaces as concrete types. No Zulip thread directly mentioning FHIR-37791 was found.

AutoFHIR reconciliation:
This commit updates active build source for extension context, SearchParameter.base, Reference.type, ElementDefinition.type.code/profile/targetProfile, and StructureDefinition notes. The edits state how interface paths apply to implementing resources, how search parameters based on abstract/interface types are associated with implementers, that Reference.type and ElementDefinition.type.code cannot name interfaces, that ElementDefinition profile/targetProfile can name interfaces, and how constraints declared on interfaces propagate into snapshots with ElementDefinition.constraint.source.

Recommendation:
Keep this commit. It completes the clarification requested by FHIR-37791 without changing conformance bindings or adding new artifacts. If future tooling creates enforceable filters for "FHIR types except interfaces", the ElementDefinition.type.code value set could be tightened, but the current source text now states the intended rule.
