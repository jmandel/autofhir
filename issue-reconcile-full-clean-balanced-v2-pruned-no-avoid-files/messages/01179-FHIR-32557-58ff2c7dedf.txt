FHIR-32557: Clarify Device availability status source

Issue request:
FHIR-32557 was Published with a Persuasive with Modification resolution for R5. It asked whether disposed, destroyed, or otherwise unavailable devices required inactivating Device records; the resolution clarified that Device.status is the record status, removed Device.statusReason, and added Device.availabilityStatus for device availability states such as lost, damaged, destroyed, and available.

Initial application:
The R5 application is visible in git commit 0cd35c3c18, which updated Device.status to record-status wording, removed Device.statusReason, added Device.availabilityStatus, and created the device availability terminology. That same application left two stale descriptions: the Device.availabilityStatus binding called the codes a status reason, and the device-availability-status CodeSystem described itself as record status.

Additional context:
Device is active in source/fhir.ini, so source/device/structuredefinition-Device.xml and the referenced device terminology feed the current build. Related R5 Device changes FHIR-36195 and FHIR-36214 refactored operational and association status into newer Device structures, and later Applied issue FHIR-53243 intentionally re-added unknown to Device.status for R6; this reconciliation therefore does not remove unknown. FHIR-54324 is Resolved - change required but not yet Applied/Published and proposes broader future availability terminology changes, so it is context rather than current source-edit authority for this default run.

AutoFHIR reconciliation:
This commit corrects the stale Device.availabilityStatus binding description and the device-availability-status CodeSystem description to say they describe the availability status of the device. It leaves the current Device.status record-status wording, Device.availabilityStatus element, and later re-added unknown Device.status code unchanged.

Recommendation:
Keep this focused source fix. Future work on the broader availability-status value set, binding strength, or THO migration should be handled under the later ready-to-apply issues rather than expanding FHIR-32557.
