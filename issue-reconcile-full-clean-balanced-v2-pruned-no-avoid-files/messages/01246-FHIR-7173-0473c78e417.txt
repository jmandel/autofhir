FHIR-7173: Clarify NutritionOrder identifier V2 signpost

Issue request:
FHIR-7173 was Published with resolution Persuasive with Modification. The issue asked that NutritionOrder.identifier relate to HL7 V2 filler and placer orders as signposts for readers, and the recorded resolution said to use the existing V2 mappings and add a note that Identifier.type can indicate filler vs. placer if needed.

Initial application:
The issue was initially applied in commit 534862556c ([#7177],[#7173]), which added a NutritionOrder.identifier comment saying Identifier.type could indicate filler vs placer and pointing to the then-current DiagnosticOrder notes. Later source refactors carried the comment into source/nutritionorder/structuredefinition-NutritionOrder.xml and updated the old DiagnosticOrder link to ServiceRequest, and commit 086649a235 added the matching Request pattern mapping exception.

Additional context:
NutritionOrder is an active current-build resource in source/fhir.ini, while the old NutritionRequest name now appears only in the deleted-resource list. The current source preserved the intended filler/placer note, but the sentence was grammatically defective and pointed to servicerequest.html#notes for further detail even though the ServiceRequest notes section does not contain the promised identifier discussion. The Request pattern still provides the general requester/placer and performer/filler context, and no direct Zulip or Confluence record was found that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This commit updates the authoritative NutritionOrder StructureDefinition comment and the matching Request mapping exception to state directly that Identifier.type can be used to indicate the HL7 V2 placer or filler order identifier if needed. It removes the stale ServiceRequest notes pointer without broadening the resolved issue beyond the requested identifier signpost.

Recommendation:
Keep this source fix as-is. It preserves the applied non-substantive clarification, removes a misleading cross-reference, and keeps the mapping-exception source synchronized with the resource definition; no further work is needed for FHIR-7173 unless OO wants a broader cross-resource identifier policy change.
