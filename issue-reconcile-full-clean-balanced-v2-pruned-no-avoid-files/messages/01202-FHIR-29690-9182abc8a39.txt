FHIR-29690: Align MessageHeader response search description

Issue request:
FHIR-29690 was Published with a Persuasive with Modification resolution for R5. It asked whether MessageHeader.response.identifier should target an id or an Identifier, and resolved to change the element type from id to Identifier and update the element short and definition to say it carries the Bundle.identifier of the original message.

Initial application:
The data type was changed from id to Identifier in dd765a96beb1acc58f2276f9d6f6c3fa9e89b2fc while applying broader MessageHeader work, and bce22083f1b66e65552b1bddcbcb812506c29e3b changed the MessageHeader.response.identifier short and definition to Bundle.identifier wording. Current messaging narrative also uses Bundle.identifier for message identity and for the value quoted in MessageHeader.response.identifier.

Additional context:
The implementers Zulip thread that led to the tracker concluded that Bundle.id was unsafe across routing hops and that MessageHeader.response.identifier should point to Bundle.identifier. FHIR-I January 2021 minutes record the Persuasive with Mod vote and explicitly note that both short and long descriptions should be updated. Later August 2022 FHIR-I minutes and the related FHIR-25460/FHIR-25461 messaging-identifier discussion confirm that the current messaging identity model uses Bundle.identifier, with FHIR-25461 ultimately resolved no-change because other trackers had addressed the topic.

AutoFHIR reconciliation:
This commit updates the active MessageHeader response-id SearchParameter description from the stale old short text, "Id of original message", to "Bundle.identifier of original message". The MessageHeader resource is active in source/fhir.ini, the SearchParameter expression already points at MessageHeader.response.identifier, and the stable search parameter code remains unchanged.

Recommendation:
Keep this source fix. It closes the remaining active source wording that could preserve the id-vs-Identifier ambiguity from FHIR-29690 without changing wire-level search parameter names or broadening the resolved issue.
