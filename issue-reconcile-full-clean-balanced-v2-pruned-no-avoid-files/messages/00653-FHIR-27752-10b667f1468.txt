FHIR-27752: Allow multiple related action data references

Issue request:
FHIR-27752 was Published/Persuasive with Modification for R5. It asked whether DataRequirement should gain an optional name, but the accepted resolution instead made PlanDefinition.action.input and PlanDefinition.action.output complex structures with title, requirement, and a repeatable relatedRequirementId-style reference plus an invariant requiring either requirement or related references, but not both.

Initial application:
The issue was initially applied by git commit 2101fd4e46 (J#27752), which changed the active PlanDefinition StructureDefinition source from direct DataRequirement input/output arrays to BackboneElement input/output arrays with title, requirement, relatedData, and exclusive-or constraints. That implementation used relatedData rather than the proposed relatedRequirementId name, but it left each relatedData at max 1 even though the final Jira resolution called for 0..*. Later cleanup removed XPath constraints, and FHIR-40218 changed PlanDefinition.action.input.relatedData from id to string because it references an Element.id value.

Additional context:
PlanDefinition is active in the current build through source/fhir.ini, and source/plandefinition/structuredefinition-PlanDefinition.xml is the authoritative resource definition. The current source already has no DataRequirement.name and correctly has title, requirement, relatedData, and the xor constraints. CDS WGM minutes record the 29-0-3 approval, Workflow minutes record the proposal rewrite, and later Zulip discussions confirm relatedData is the intended PlanDefinition mechanism for passing data between actions. FHIR-34265 later copied definitional action aspects into RequestGroup/RequestOrchestration, but that is a separate tracker and is not changed here.

AutoFHIR reconciliation:
This commit changes only PlanDefinition.action.input.relatedData and PlanDefinition.action.output.relatedData from max 1 to max * so the active source matches the final FHIR-27752 cardinality while preserving the later FHIR-40218 string type and the existing xor constraints.

Recommendation:
Keep this source fix as-is for FHIR-27752. If the work group wants matching RequestOrchestration.action relatedData cardinality changes, handle that as a separate review under the RequestOrchestration/FHIR-34265 change family rather than broadening this PlanDefinition reconciliation.
