FHIR-26540: Restore ClinicalUseDefinition category cardinality

Issue request:
FHIR-26540 is a Published/Persuasive BR&R change request for R5 that added ClinicalUseIssue.category as CodeableConcept 0..1 to categorize warning types such as pregnancy, overdose, and effects on driving, with the approved friendly modification to rename the former ClinicalUseIssue.type code "other" to "warning".

Initial application:
The issue was initially applied in git commit 307373127e6e5c1dc9725d59691ab045de71bdb6, which added ClinicalUseIssue.category as 0..1 in the then-authoritative spreadsheet and changed the type value set code/display from other/Other to warning/Warning. The later source rework preserved the category as 0..1 in structuredefinition-ClinicalUseIssue.xml before the resource rename.

Additional context:
ClinicalUseIssue was later renamed to ClinicalUseDefinition for FHIR-31847, and the current build uses ClinicalUseDefinition as an active BR&R resource. During that rename, commit 13b7d768e64d35ebbd4089299e3ceff30978acc8 changed the copied category max from 1 to * even though the FHIR-31847 Jira resolution only approved the resource name change. Later warning work in FHIR-32064 added explicit warning details but did not approve changing ClinicalUseDefinition.category to repeat.

AutoFHIR reconciliation:
This commit restores the active ClinicalUseDefinition.category cardinality from 0..* to the approved 0..1 in source/clinicalusedefinition/structuredefinition-ClinicalUseDefinition.xml. The file is in current build scope through the active ClinicalUseDefinition entries in source/fhir.ini, and no generated diagram/SVG artifacts were edited.

Recommendation:
Keep this source fix. If BR&R now wants multiple categories on a single ClinicalUseDefinition, that should be handled as a new explicit tracker because it would intentionally reverse the cardinality approved and applied for FHIR-26540.
