FHIR-34434: Align ElementDefinition mapping replacement note

Issue request:
FHIR-34434 was Published as Persuasive with Modification for R5. It asked FHIR-I to clarify how duplicate ElementDefinition mappings are handled; the adopted resolution required a warning invariant for duplicate mapping identities and profiling guidance that a profile mapping with the same identity replaces the corresponding parent mapping.

Initial application:
The warning invariant is already present in the active ElementDefinition datatype source as a warning on ElementDefinition using mapping.select(identity).isDistinct(). Git history shows that invariant was inserted by 08d840fb48809b6e69bfd75e45073818aab41498 on the same day as the FHIR-34434 work, and the explicit FHIR-34434 commit d94012a93904193b692562a5f43a08b3e0327934 added the profiling-page replacement rule. That application did not update the ElementDefinition narrative table note, which still said mappings never replace base mappings.

Additional context:
source/fhir.ini lists ElementDefinition as an active normative datatype, so source/elementdefinition.html is in current build scope. FHIR-I minutes from 2022-04-04 record the same duplicate-mapping question and the Persuasive with Modification vote. The linked Zulip thread shows the motivating US Core example where a differential mapping with the same identity produced duplicate snapshot mappings. A related Jira text search found no separate final issue to decide.

AutoFHIR reconciliation:
Updated the ElementDefinition narrative note for the delta marker so it still says additional constraints do not replace base constraints, but now states that an additional mapping with the same identity replaces the base mapping with that identity. The existing invariant and profiling-page text were left unchanged because they already express the adopted rule.

Recommendation:
Keep this source fix. It removes an active-page contradiction with the FHIR-34434 resolution while preserving the existing invariant and profiling guidance; no related source changes or opportunistic Jira decisions are needed.
