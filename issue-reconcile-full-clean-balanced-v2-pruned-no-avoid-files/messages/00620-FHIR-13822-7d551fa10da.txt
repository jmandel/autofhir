FHIR-13822: Correct revinclude example spelling

Issue request:
FHIR-13822 was a Published/Persuasive with Modification STU3 Security issue asking to add a "Query Parameters Considerations" subsection under Authorization and Access Control. The requested guidance says that when a restricted user submits unauthorized query parameters, local policy should determine whether the result is an error, zero results, or the results after removing unauthorized parameters, with _include/_revinclude as the motivating example.

Initial application:
Commit 7b2b64512052c9a800a59b0ac3cd2cd013659b1b added the requested subsection to source/secpriv-module.html and explicitly listed GF#13822 in the commit message. That application carried forward the Jira text's misspelled reverse-include parameter as `_revinc`. Later edits, including 710e0055136423fc77ec9bf54a194d3f5468d855 and 87b00c9c0de977f8559e0f99694e8664e03a06cd, updated nearby approach and conformance-language wording but left the example's invalid parameter spelling unchanged.

Additional context:
The current Security and Privacy module is in the build hierarchy at source/hierarchy.xml and still contains the FHIR-13822 subsection. The canonical FHIR search parameter is `_revinclude`, as defined and repeatedly used on source/search.html; `_revinc` is not a valid FHIR search result parameter and appears only in the FHIR-13822 subsection. FHIR-34362 later clarified access-control guidance in the same area but did not supersede this query-parameter example.

AutoFHIR reconciliation:
This commit changes the FHIR-13822 example in source/secpriv-module.html from `_revinc` to `_revinclude`, preserving the applied policy guidance while correcting the only stale invalid search-parameter spelling introduced by the original application.

Recommendation:
Keep this source fix. It is in a current build-scoped narrative page, aligns the example with the canonical Search page, and avoids misleading implementers while leaving the work-group's policy-choice guidance unchanged.
