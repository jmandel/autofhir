FHIR-20849: Clarify optional mapping rule names

Issue request:
FHIR-20849 was a Published/Persuasive FHIR-I change request for StructureMap and the FHIR mapping language. It asked to make StructureMap.group.rule.name optional and to stop implying that every mapping rule needs a persisted or parser-generated name.

Initial application:
The issue was initially applied in f7e617e576302162ba6b96f6ddfede11a02e820a, merged by 7c6b62dae230fa69a9a5cb9559de751244e4b036, which changed the StructureMap spreadsheet cardinality for StructureMap.group.rule.name from 1..1 to 0..1. The current StructureDefinition source now has min=0, but source/mapping-language.html still retained the Jira-quoted wording about rule names usually being inferred/generated by the parser or engine.

Additional context:
StructureMap is active in source/fhir.ini, and source/mapping-language.html is part of the current build hierarchy. The formal grammar already treats ruleName as optional, and the only discovered community evidence was implementation/coordination discussion; no Zulip or Confluence evidence contradicted the Jira request.

AutoFHIR reconciliation:
Updated the mapping-language transform-rule format to mark the trailing quoted rule name as optional, and replaced the ambiguous generated-name prose with explicit guidance that rule names are optional, author-supplied names must be unique, and engines may assign internal generated names only when they need to identify an unnamed rule.

Recommendation:
Keep this source fix. It completes the narrative half of the Published FHIR-20849 decision without taking on other StructureMap mapping-language issues from the same general backlog.
