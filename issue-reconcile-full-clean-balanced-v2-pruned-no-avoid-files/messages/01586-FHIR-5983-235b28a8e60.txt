FHIR-5983: Remove stale Extensible binding columns

Issue request:
FHIR-5983 was Published/Persuasive for DSTU1 and asked that spreadsheet binding authoring expose only the four binding-strength choices. The important decision was to stop combining a Conformance value with a separate Extensible boolean column because that could silently turn Preferred+Extensible into an Extensible binding.

Initial application:
The issue appears to have been applied in git commit 986a9f2b89d4299a8dd76b9acfae0ad3b65c2cab, imported from svn revision 5450, which was explicitly titled "#5983 - clean up binding strength in spreadsheets" and removed Extensible columns from many then-current spreadsheets. Later source layout history introduced the current profile-extension spreadsheet files with the obsolete Binding-sheet header still present.

Additional context:
source/fhir.ini actively includes source/profiles/pharmacy-extensions-spreadsheet.xml, source/profiles/element-extensions-spreadsheet.xml, and source/profiles/rendering-extensions-spreadsheet.xml under [profiles]. Those three current build inputs still had empty Binding sheets with both Conformance and Extensible columns. Other Extensible headers found under source/request, source/devicedispense, source/entrydefinition, and source/iteminstance were not edited because they are not active fhir.ini profile/resource inputs for the current build. A 2020 Zulip spreadsheet-authoring discussion confirmed that "extensible" is an allowed Conformance value and that the separate Extensible column should be removed.

AutoFHIR reconciliation:
Removed the obsolete Extensible column from the active pharmacy, element, and rendering extension spreadsheets. The reconciliation adjusted the Binding-sheet filter range, expanded column count, trailing column index, and empty row cell counts so each active Binding sheet now has the 13-column layout with Conformance as the single binding-strength column. No binding rows or value set semantics were changed because these Binding sheets contained no binding data rows.

Recommendation:
Keep this source fix as-is. If future cleanup wants to remove the same obsolete header from dormant legacy spreadsheets, first confirm those files are still intended build inputs; this reconciliation intentionally stayed limited to the current active fhir.ini profile sources.
