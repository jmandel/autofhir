FHIR-41633: Add datatype context example

Issue request:
FHIR-41633 was Applied/Persuasive with Modification for R6 and asked FHIR-I to clarify the ExtensionContextType element concept. The reporter noted that the existing definition said context.type=element matched ElementDefinition.id, which left datatype expressions such as string ambiguous for elements like Device.lotNumber. The approved resolution added that an element's assigned type is also an assigned id usable in this context, and said to provide an example somewhere in the spec.

Initial application:
The upstream application commit 5f55dff751f3b41656e969f1ba37d8160958d683 changed source/structuredefinition/codesystem-extension-context-type.xml to add the assigned-type rule to the ExtensionContextType CodeSystem definition. Later context-family edits preserved that rule, but the build-scoped Defining Extensions narrative still described the element context format only as formal Element ids and did not include the approved datatype example.

Additional context:
The originating Zulip thread confirms the intended interpretation: Grahame Grieve explained that an element with a type has more than one id, including the id of the root type, so it can be used there. FHIR-I WGM minutes record the FHIR-41633 Persuasive with Modification motion at 24-0-0. Related applied issues FHIR-43364 and FHIR-46620 refined adjacent Extension Context guidance for resource roots and Resource specialization without reversing the assigned-type rule; both are already represented on the combined branch.

AutoFHIR reconciliation:
This commit updates source/defining-extensions.html#context, the Defining Extensions guidance linked from the active StructureDefinition.context definition, to state that an assigned type is also treated as an element id for context matching and to give the requested string/Device.lotNumber example. The existing CodeSystem definition is left unchanged because it already carries the approved assigned-type semantics.

Recommendation:
Keep this focused source fix. It completes the applied clarification by aligning the narrative guidance with the normative ExtensionContextType definition and adding the promised example, without changing validator behavior or broadening the later Resource-context decisions.
