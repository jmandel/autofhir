FHIR-5653: Clarify decimal primitive source row

Issue request:
FHIR-5653 was Published with a Persuasive with Modification resolution for the FHIR-core datatypes page. It asked to clarify decimal's value domain so it was not described as all rational numbers, to explain FHIR's precision-aware decimal handling relative to XSD decimal/precisionDecimal, and to clarify exponent handling.

Initial application:
The issue was initially applied in the 2015 primitive datatype rewrite: commit 7b5ff8e introduced the datatype table wording "Rational numbers that have a decimal representation" and precision guidance on source/datatypes.html shortly after the Jira was filed. The current narrative still carries that finite-decimal-domain wording. However, the active primitive datatype spreadsheet row that feeds generated primitive type definitions still used the older overbroad "A rational number with implicit precision" wording and named Java BigInteger as an example implementation class.

Additional context:
FHIR-8175 later confirmed the same precision-aware decimal design and left the schema arrangement in place with explanatory text. FHIR-16874 later allowed exponential form in all formats, so FHIR-5653's original exponent-prohibition concern should not be restored in current source; the existing xs:decimal/xs:double union and exponent-capable regex reflect the later decision.

AutoFHIR reconciliation:
This commit updates source/datatypes/primitives.xml, an authoritative primitive datatype spreadsheet source used for generated primitive type definitions, so the decimal row now matches the active datatypes narrative: decimal is a rational value that has a decimal representation and carries implicit precision. It also changes the misleading Java BigInteger example to Java BigDecimal, consistent with the current narrative's decimal implementation guidance.

Recommendation:
Keep this commit. It is a narrow source correction for a stale active datatype source row and avoids changing the later-approved exponent behavior.
