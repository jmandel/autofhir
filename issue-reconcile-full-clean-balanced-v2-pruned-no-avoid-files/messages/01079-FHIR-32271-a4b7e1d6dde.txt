FHIR-32271: Clarify DeviceDefinition hierarchy

Issue request:
FHIR-32271 was Published as Persuasive with Modification for OO. It asked to avoid modeling the same DeviceDefinition composition relationship with both DeviceDefinition.parentDevice and DeviceDefinition.hasPart. The final resolution required removing DeviceDefinition.parentDevice, leaving the DeviceDefinition.hasPart backbone unchanged, explaining the DeviceDefinition/Device hierarchy direction with examples in DeviceDefinition Notes, making no Device resource change, and updating search parameters appropriately.

Initial application:
No commit was found whose message explicitly mentions FHIR-32271. The apparent application was git commit 2cfdd9c837592f22e50fa54e7d6635d5746c0397, which commented out DeviceDefinition.parentDevice in the DeviceDefinition StructureDefinition and commented out the DeviceDefinition-parent search parameter. Current source/fhir.ini also records DeviceDefinition.parentDevice as removed in favor of hasPart. However, source/devicedefinition/devicedefinition-notes.xml was still empty, and the build-visible FHIR ModelInfo example still exposed DeviceDefinition.parentDevice while omitting DeviceDefinition.hasPart.

Additional context:
The OO/Devices Confluence project page for Device - Device Definition Parent/HasPart records accepted Option 4: keep Device.parent for particular device instances, keep DeviceDefinition.hasPart for reusable component definitions, remove DeviceDefinition.parentDevice, add explanatory hierarchy text and examples, and add hasPart search support. FHIR-30505 is the earlier Published issue that introduced DeviceDefinition.hasPart and explains why a parentDevice-only direction does not answer the main model-definition question. FHIR-39332 was discovered in the same search path but is Resolved - No Change/Retracted for DeviceMetric and does not require a separate source decision here. DeviceDefinition is active in source/fhir.ini, and publish.ini plus the Library example list expose the FHIR model-info XML as build-visible CQL model-definition content.

AutoFHIR reconciliation:
This commit adds the missing DeviceDefinition Notes guidance explaining why DeviceDefinition uses hasPart from a defined device to reusable component definitions while Device uses parent from a component instance to its current single parent instance. It also updates the FHIR ModelInfo example by replacing the stale parentDevice element with a DeviceDefinition.HasPart backbone and hasPart list element, and refreshes the embedded Library.data payload so the Library/FHIR-ModelInfo resource matches the edited model-info content. No active StructureDefinition or search-parameter source change was needed because those surfaces already remove parentDevice and provide hasPart search parameters.

Recommendation:
Keep this source fix. It completes the published FHIR-32271 resolution in current build-visible source without reopening Device or independently deciding the background FHIR-30505 and retracted FHIR-39332 issues. The remaining parentDevice strings are limited to non-active XML comments or migration notes and should be left unless a broader cleanup issue decides to remove disabled source comments.
