FHIR-2840: Clarify Location contact addresses

Issue request:
FHIR-2840 was a Published/Persuasive with Modification FHIR-core datatypes issue raised against the early Location model. It noted that a Location had only one Address even when a specific location might need both a physical address and a mailing address such as a PO box; the recorded disposition rejected adding a physical/postal code to Address at that time and proposed a Location-level element or extension.

Initial application:
No git commit explicitly mentioning FHIR-2840 was found in the source history. The current Location source already has a single Location.address defined as the physical location, while later Location.contact support provides location-level contact addresses. However, Location.address still said additional addresses should be represented only by another Location resource or by the Organization, which obscured the current location-specific mailing/billing-address path.

Additional context:
FHIR-6088 later revisited the same physical-vs-postal address family and added Address.type with postal, physical, and both values for general Address use; that issue is already represented on the combined branch. FHIR-25375 and FHIR-29035 later added Location.contact 0..* ExtendedContactDetail, whose datatype includes purpose and address; FHIR-25375 is also already represented on the combined branch. PA Zulip and Confluence evidence for FHIR-25375 confirms the need for role/purpose-specific contact details at both organization and location level. The Location resource is active in source/fhir.ini, so source/location/structuredefinition-Location.xml is current build source.

AutoFHIR reconciliation:
Updated the Location.address comment to distinguish additional physical addresses from location-specific mailing, billing, or other contact addresses. The comment now points physical-address alternatives to another Location resource, points contact addresses to Location.contact.address, and keeps the Organization-contact fallback only for addresses that are not location-specific.

Recommendation:
Keep this source fix. It makes the current Location guidance match the applied issue family without adding a new element or duplicating the already-audited FHIR-6088 Address.type and FHIR-25375 Location.contact decisions.
