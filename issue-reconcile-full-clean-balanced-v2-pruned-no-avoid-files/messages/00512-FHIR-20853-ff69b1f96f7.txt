FHIR-20853: Clarify datatype subtype substitution

Issue request:
FHIR-20853 was a Published/Persuasive MnM clarification request for the FHIR-core datatypes page. It asked whether primitive datatype subtypes such as markdown/string or url/uri can be substituted for one another, and the resolution was to clarify that data types cannot be substituted with subtypes.

Initial application:
The issue appears to have been initially applied in the R5 MnM non-substantive batch: git commit ec83d5b505 added a datatypes.html note saying "Subtypes cannot be substitued for datatypes". That commit did not name FHIR-20853 in its subject/body and the line was removed the next day by the unrelated RatioRange datatype commit b9fd58139d. Current source retained only the older uri/url/canonical-specific substitution note, leaving the general primitive clarification absent.

Additional context:
FHIR-9168 is background evidence that datatype specialization/profile presentation had already created a false impression that specialized datatypes could be substituted. FHIR-40555 later clarified the string-to-markdown compatibility discussion by distinguishing single-type elements from choice elements where the datatype name appears in the wire element name. source/fhir.ini confirms datatypes default to the active datatypes page, so source/datatypes.html is in current build scope.

AutoFHIR reconciliation:
Restored the missing clarification in source/datatypes.html with corrected, more precise wording: datatype specialization does not imply substitutability, instances are valid against explicitly allowed datatypes, and a choice element allowing string does not also allow markdown unless markdown is explicitly listed.

Recommendation:
Keep this source fix. It directly implements the Published clarification in the active datatype source without changing diagrams or unrelated datatype semantics; no further FHIR-core work is needed unless MnM wants additional examples beyond the string/markdown choice case.
