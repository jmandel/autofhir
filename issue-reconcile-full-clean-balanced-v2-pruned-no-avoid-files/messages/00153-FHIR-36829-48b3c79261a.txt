FHIR-36829: Clarify Consent purpose matching as OR

Issue request:
FHIR-36829 was Published/Persuasive with Modification for FHIR-core Consent. It asked how repeated fields within a single Consent.provision should be interpreted, noting that actor, securityLabel, and action lacked explicit repeat semantics, class/code already implied OR, and the purpose binding text implied AND. The final Jira resolution closed the issue by the changes to FHIR-34322.

Initial application:
No source commit explicitly mentioning FHIR-36829 was found. FHIR-34322 was applied through the Consent provisions narrative added by PR #1882, including commits 045316834324696c30df57559a5d83b4b03e3b30 and 3ec287e360dfe910ef0697a2922d025bae81fdbe, which state that sibling provisions are OR-ed, different attributes within a provision are AND-ed, and repeated values within a multi-valued attribute are OR-ed. Current source already contained that narrative, but Consent.provision.purpose still retained the older binding description saying that when more than one label is specified, operations must have all specified labels.

Additional context:
Consent is an active current-build resource in source/fhir.ini, and source/consent/structuredefinition-Consent.xml is the authoritative StructureDefinition input for the element binding description. The later FHIR-39597 Consent model changes, including the existing combined-branch reconciliation commit 73953f4e6f096f0614960011d34b353282dd8f9d, updated base-decision/provision-zero wording but did not alter the repeated-value semantics from FHIR-34322. Older FHIR-11056 and FHIR-11057 snapshots explain earlier security-label wording, but they predate the later FHIR-36829/FHIR-34322 clarification. Zulip and Confluence searches found no directly relevant or conflicting discussion for FHIR-36829 or FHIR-34322.

AutoFHIR reconciliation:
This commit updates the Consent.provision.purpose binding description so it no longer contradicts the provisions narrative. The description now says that when more than one purpose is specified, matching any one purpose is sufficient for the purpose attribute to match, aligning the generated element definition with the published multi-valued-attribute OR rule.

Recommendation:
Keep this source fix as the bounded FHIR-36829 reconciliation. No broader Consent model change is needed for this issue; if CBCC later wants an element-specific AND interpretation for purpose or security-label combinations, that should be handled as a new work-group decision because it would contradict the current published provisions narrative.
