FHIR-7924: Remove stale vread Content-Location guidance

Issue request:
FHIR-7924 was Published/Not Persuasive with Modification for DSTU1. It asked how read responses should populate Content-Location when a server does not support full versioning; the accepted resolution was instead that the Content-Location header would be removed from the read guidance.

Initial application:
The issue was applied by git commit a3d92167cec3c317028c952cd87d533034ec6589, imported from SVN revision 6510, with the subject "#7924 - remove content-location header." That commit removed Content-Location from the REST metadata mapping, read, vread, update/create/conformance response prose, and interaction summary table. The older vread paragraph explaining how a client might discover a version id still retained a reference to a content location returned from read.

Additional context:
source/http.html is the active RESTful API page source, mapped by publish.ini as http.html = http. Later FHIR-38991 work added a Content-Location row to the HTTP headers table for the asynchronous request pattern only; that later change does not reintroduce Content-Location as read/vread version-discovery guidance. Jira, Zulip, and Confluence searches found no later decision requiring read to return Content-Location.

AutoFHIR reconciliation:
This commit edits the vread paragraph in source/http.html to say a version id may be recorded from the ETag returned from read, aligning it with the current metadata table and read interaction text while leaving the async Content-Location header table entry intact.

Recommendation:
Keep this commit as-is. It completes the narrow FHIR-7924 removal in current build-scope source without disturbing the later async-only Content-Location header documentation; any broader HTTP header modernization should be handled under a separate tracker.
