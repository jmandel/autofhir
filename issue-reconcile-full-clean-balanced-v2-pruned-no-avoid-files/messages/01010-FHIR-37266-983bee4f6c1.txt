FHIR-37266: Mark ServiceRequest focus as modifier

Issue request:
FHIR-37266 was Published/Persuasive for R5 and requested adding ServiceRequest.focus so a request can be associated with a patient record while the requested service is actually focused on another related person, thing, condition, fetus, tumor, home, or similar target. The request also identified focus as modifier-like because it changes how ServiceRequest.subject is interpreted.

Initial application:
The Jira comment points to PR commit 7be0569, a merge whose first parent includes 652af4826f. That implementation added ServiceRequest.focus to source/servicerequest/structuredefinition-ServiceRequest.xml, with cardinality 0..* and Reference(Resource), but it did not add isModifier or isModifierReason. The current build includes ServiceRequest as an active resource in source/fhir.ini, so the StructureDefinition source is in current build scope.

Additional context:
Observation.focus and Procedure.focus are already modifier elements because they change who or what is the target of the observation/procedure. The contemporaneous implementers Zulip discussion for the ServiceRequest change says the R5 element was intended to be a modifier because ServiceRequest.subject shifts from the entity acted on to the record the request is attached to. Later OO issue FHIR-54620 was Resolved - change required/Persuasive with a 6-0-2 vote and explicitly says ServiceRequest.focus will be marked as a modifier; FHIR-52916 separately declined adding a focus-role extension and does not change this modifier decision.

AutoFHIR reconciliation:
This commit completes the FHIR-37266 application by marking ServiceRequest.focus as a modifier and adding the modifier reason approved in the later same-change-family issue. The change is made in the authoritative ServiceRequest StructureDefinition source rather than generated diagram output.

Recommendation:
Keep this commit. It applies the missing modifier semantics from the original Published issue and is directly supported by later OO confirmation in FHIR-54620; a future FHIR-54620 reconciliation should see the source already corrected rather than reapply the same hunk.
