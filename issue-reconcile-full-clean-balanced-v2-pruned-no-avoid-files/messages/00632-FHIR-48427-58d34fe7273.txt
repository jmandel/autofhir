FHIR-48427: Align vital signs base result requirements

Issue request:
FHIR-48427 is an Applied/Persuasive with Modification OO change request for R6. It reported that the Vital Signs Base Profile used Must Support inconsistently: FHIR-47136 removed base component Must Support, but base Observation.value[x] Must Support and text implying a valueQuantity result still remained. The requested outcome was to keep Must Support expectations in the specific vital signs profiles rather than the base profile, and not make the base narrative require valueQuantity as the only result shape.

Initial application:
No prior source commit explicitly named FHIR-48427. The March 2025 FHIR-47136 vital signs commits, especially 983b8c8cd0 and follow-ups, removed Must Support from base Observation.value[x], Observation.dataAbsentReason, Observation.component, and component sub-elements while leaving Must Support on the common base metadata elements. FHIR-30934 added a top-level Vital Signs Must Support expectations section. The already-published FHIR-49736 reconciliation removed stale component-specific summary text from the base StructureDefinition, but the build-scope vital signs introduction still said every base-profile Observation required a numeric result value and UCUM unit.

Additional context:
The 2025-03-21 OO minutes list FHIR-48427 under the base-profile Must Support Jira discussion and record the decision as Persuasive with Modification because the concern should have been covered by other vital signs tickets, followed by marking it Applied. Current source/observation/implementationguide-Observation-vitalsigns.xml includes observation-vitalsigns-profile-introduction.xml in the active Vital Signs IG, and StructureDefinition/vitalsigns has vsp-2 allowing value[x], component, hasMember, or dataAbsentReason rather than always requiring a numeric value. No directly relevant Zulip discussion was found for FHIR-48427 or conflicting vital-signs Must Support guidance.

AutoFHIR reconciliation:
This commit updates the mandatory-data bullet in source/observation/observation-vitalsigns-profile-introduction.xml so the human-readable Vital Signs Base narrative matches the current differential: a vital signs Observation can satisfy the base requirement with Observation.value[x], populated Observation.component elements, an Observation.hasMember relationship, or Observation.dataAbsentReason when none of those are present. It preserves the UCUM-unit guidance for numeric vital sign profiles without saying every base-profile Observation must carry a numeric valueQuantity result.

Recommendation:
Keep this source-changing commit. The formal base and specific-profile differentials already reflect the applied Must Support decisions, so no further structural changes are needed for FHIR-48427; this patch removes the remaining misleading narrative requirement in current build scope.
