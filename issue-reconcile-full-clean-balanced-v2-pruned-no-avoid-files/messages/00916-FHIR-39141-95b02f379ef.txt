FHIR-39141: Allow multiple Transport reasons

Issue request:
FHIR-39141 was a Published/Persuasive-with-Modification OO change request for R5 asking to replace Transport.reasonCode and Transport.reasonReference with a single Transport.reason CodeableReference and to give that replacement element cardinality 0..*.

Initial application:
The Jira-tagged implementation commit 69b0fca978 removed the old Transport.reasonCode/reasonReference material and introduced Transport.reason as a CodeableReference, but it retained the old 0..1 maximum from the prior element. Later Transport refactoring changed mappings and removed request-oriented elements, but no discovered later Jira or source-history event superseded the 0..* cardinality part of FHIR-39141.

Additional context:
Transport is an active core resource in source/fhir.ini. The current resource is now Event-aligned, Event.reason is repeatable, and source/transport/transport-event-mapping-exceptions.xml still recorded the only cardinality divergence as Event.reason * versus Transport.reason 1. FHIR-40310 later reaffirmed that the reasonCode conflict was gone and that the remaining Transport.reason work was terminology binding, not a new cardinality restriction.

AutoFHIR reconciliation:
This commit changes Transport.reason from 0..1 to 0..* and removes the obsolete Event.reason upper-cardinality mapping exception. It deliberately leaves the stale reasonCode prose for the separate FHIR-40310 reconciliation commit, because that seed specifically records the later no-rename/TransportReason decision.

Recommendation:
Keep this source fix. It completes the explicit FHIR-39141 cardinality requirement and aligns Transport.reason with the Event pattern without reintroducing removed reasonCode or reasonReference elements.
