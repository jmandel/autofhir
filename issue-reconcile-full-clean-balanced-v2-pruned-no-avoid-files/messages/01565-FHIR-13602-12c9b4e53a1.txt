FHIR-13602: Use iterate for include examples

Issue request:
FHIR-13602 was Published with a Persuasive with Modification resolution for the STU3 search page. It asked to correct the include examples to use search parameter names, clarify that the process loops over inclusions rather than requiring a recursive relationship, make clear that iterative inclusion is not the default for performance reasons, and rename the modifier from "recurse" to "iterate".

Initial application:
The issue appears to have been applied by git commit d113f6694513dede9ec8faa4fe208a8743e4d5be, "GF#13602 - fix search recursion", which changed source/search.html from :recurse to :iterate, corrected the MedicationDispense include example, clarified direct-match-only default behavior, and added performance/default guidance. Later search-page refactors preserved that interpretation, and FHIR-31951 corrected the same MedicationDispense example to the current search parameter/resource names.

Additional context:
Current source/search.html is in build scope through publish.ini and source/hierarchy.xml and already defines the official modifier as iterate. The Clinical Reasoning knowledge-artifact distribution page is also in build scope through publish.ini and source/hierarchy.xml, but still contained a current built example using _revinclude:recurse. Community searches for FHIR-13602 and the key recurse/iterate example terms found no Zulip or Confluence evidence that changes the Jira/source conclusion.

These are narrow source changes to align current built pages with the applied FHIR-13602 decision and the current official modifier name.

Recommendation:
Keep this commit as-is. The authoritative search guidance and the active Clinical Reasoning example now consistently use iterate; no additional work-group review is needed unless a future issue reopens iterative include behavior.
