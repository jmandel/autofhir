FHIR-12057: Align ElementDefinition example narrative

Issue request:
FHIR-12057 was a Published FHIR-core StructureDefinition change request for DSTU2. It asked to change ElementDefinition.example from 0..1 to 0..* so profiles can carry multiple examples, and the final Persuasive with Modification resolution was to use a repeating example component with label and value[x].

Initial application:
The issue was applied in svn/git commit 16760763e2fe435ccdb9dc8ae77e0a7442c2d9fd, which changed source/datatypes/elementdefinition.xml from ElementDefinition.example[x] 0..1 to ElementDefinition.example 0..*, adding ElementDefinition.example.label and ElementDefinition.example.value[x]. Current source still has those authoritative datatype rows. The manually maintained ElementDefinition interpretation page, however, still listed the legacy ElementDefinition field as example[x].

Additional context:
source/fhir.ini actively lists ElementDefinition as a datatype and maps elementdefinition to the elementdefinition page, so source/datatypes/elementdefinition.xml and source/elementdefinition.html both feed the current build. Jira search found no later final issue reversing FHIR-12057. A 2022 Zulip conformance discussion questioned why ElementDefinition.example.label is mandatory, and Grahame Grieve replied that keeping label mandatory is simpler than adding a conditional rule, supporting the current label 1..1 shape rather than changing it here.

AutoFHIR reconciliation:
This commit updates source/elementdefinition.html so the interpretation table names the current ElementDefinition.example field instead of the removed example[x] choice element. It leaves the already-correct 0..* cardinality and label/value[x] structure in source/datatypes/elementdefinition.xml unchanged.

Recommendation:
Keep this commit as-is. It is a narrow current-build documentation/source consistency fix that completes the applied FHIR-12057 model change without reopening the label cardinality question or adding redundant explanatory prose.
