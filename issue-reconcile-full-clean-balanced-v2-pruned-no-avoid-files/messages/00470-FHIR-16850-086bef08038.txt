FHIR-16850: Clarify evaluate-measure state effects

Issue request:
FHIR-16850 was Published/Persuasive for the STU3 Measure $evaluate-measure documentation. The Jira identified contradictory idempotency wording and resolved that the operation should not be described as idempotent because measure evaluation creates a MeasureReport result.

Initial application:
The issue was initially applied in SVN 14857, imported as git commit 3f103525db9991ead6654bc36bc502faab62b022, by changing the Measure operation source to say state impact depends on whether the server persists the generated MeasureReport and that GET is allowed when it is not persisted. That applied guidance is still present in the current OperationDefinition source, but the clinical reasoning quality-reporting narrative still said the operation was idempotent and that GET was used because of idempotency.

Additional context:
The Measure resource is active in source/fhir.ini, and source/clinicalreasoning-quality-reporting.html is the current narrative page for invoking measures. Later FHIR-37571 deprecated $evaluate-measure and introduced $evaluate with the same persistence-dependent GET guidance, so the safe reconciliation is to align the stale narrative with the existing operation definition rather than change the operation model more broadly. Focused Zulip and Confluence searches found no directly relevant conflicting community record.

AutoFHIR reconciliation:
Updated source/clinicalreasoning-quality-reporting.html to replace the unconditional Idempotent property with persistence-dependent state-effect guidance and to explain that the GET examples assume the server does not persist generated MeasureReport resources.

Recommendation:
Keep this source correction. It resolves the stale narrative contradiction while preserving the later OperationDefinition guidance; any future decision to model persisted-report behavior differently across $evaluate-measure and $evaluate should be handled as a separate work-group change.
