FHIR-14384: Fix VisionPrescription prism rename mapping

Issue request:
FHIR-14384 was a Published/Persuasive FHIR-core VisionPrescription change request asking to support two prisms by changing Prism to repeat, with prism.amount 1..1 decimal and prism.base 1..1 code constrained to up, down, in, or out.

Initial application:
The issue was initially applied in git commit 498018ea62207aa6271adc10e8c5ce9339ee5e54 ("Tracker #14384"), which changed the then-authoritative VisionPrescription spreadsheet from a single decimal prism and sibling base into a repeating prism backbone with mandatory amount and base children. Later commit 9c9403324df70351bf59981a05828a59d6b2b723 carried that model through the dispense-to-lensSpecification refactor. The current StructureDefinition source already preserves the requested cardinalities and child elements.

Additional context:
VisionPrescription is active in the current build through source/fhir.ini and source/hierarchy.xml. A later related no-change issue, FHIR-55283, considered whether VisionPrescription.lensSpecification.prism.base needed an escape value and decided it did not, so no base value set expansion is part of this reconciliation. Community searches found no relevant Zulip or Confluence evidence that changes the Jira/source conclusion. The remaining current-source inconsistency was in source/fhir.ini [r3-renames], where the old VisionPrescription.dispense.base element still pointed at nonexistent VisionPrescription.lensSpecification.base instead of the current VisionPrescription.lensSpecification.prism.base path.

AutoFHIR reconciliation:
This commit corrects the active R3 rename metadata in source/fhir.ini so the old base element maps to VisionPrescription.lensSpecification.prism.base, matching the source element introduced by the FHIR-14384 prism backbone change and preserved in the current StructureDefinition.

Recommendation:
Keep this commit as-is. The current VisionPrescription definition already allows multiple prism repetitions with mandatory amount and base children; the only needed source fix was the stale rename target corrected here.
