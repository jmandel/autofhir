FHIR-55315: Include unknown in AdverseEvent actuality search

Issue request:
FHIR-55315 was Applied/Persuasive with Modification for R6. Patient Care voted to add an "unknown" code to the AdverseEvent.actuality code system and value set with the definition "The source system does not specify which of the values currently applies for this event," and to add a comment that unknown is present for legacy data and strongly discouraged.

Initial application:
The issue was initially applied by HL7/fhir commits 78171f260c82d2a9f4db6b4074ca3bd791f368b2 and eb5350e6f879455be0ebe678bedf3d2014f8186c. Those commits added the unknown concept, updated AdverseEvent.actuality committee notes, comment, and short display, and the value set composes the full AdverseEvent.actuality code system. The AdverseEvent actuality search parameter source was left with the stale description "actual | potential".

Additional context:
BRR input favored a boolean/two-value model, but the later Patient Care resolution in Jira chose the compatible unknown-code escape valve for legacy data instead of changing the datatype. source/fhir.ini keeps AdverseEvent active in the current build, and the search parameter bundle lives under the active AdverseEvent source folder. Zulip and high-signal Confluence searches found no later community evidence that reverses the Jira/source conclusion.

AutoFHIR reconciliation:
Updated source/adverseevent/bundle-AdverseEvent-search-params.xml so the build-scoped AdverseEvent-actuality SearchParameter description includes "unknown" alongside "actual" and "potential".

Recommendation:
Keep this commit as a narrow completion of the applied Jira change. Further work is only needed if Patient Care later reopens the semantic question and chooses a breaking datatype or value-set change.
