FHIR-27761: Mark StructureMap sourceMap as type-scoped

Issue request:
FHIR-27761 was Published/Persuasive with Modification for R5. It asked to support operation parameters that apply only at system, type, or instance invocation levels by adding OperationDefinition.parameter.scope 0..* with codes system/type/instance, a missing-meaning rule, and updated existing operations where level-specific prose was being used instead.

Initial application:
The issue was initially applied in d46f7ac by adding the operation-parameter-scope CodeSystem/ValueSet and OperationDefinition.parameter.scope, then in e981c42 by adding scope markers to operation parameters that were level-specific at the time. The current OperationDefinition source has the requested 0..* element, required binding, and meaningWhenMissing text.

Additional context:
FHIR-23851 later added StructureMap.$transform sourceMap as a direct StructureMap input. That new parameter repeats the type-level-only semantics of the existing source URI parameter, but it was added after the FHIR-27761 sweep and did not receive the matching structured scope. The StructureMap resource and OperationDefinition resource are active in source/fhir.ini, so the edited operation definition is in current build scope. A residual Resource.$validate mention of instance-level invocation was inspected but not changed because the validate notes show the resource input can still apply at instance level for update validation, so omitting a scope remains correct there.

AutoFHIR reconciliation:
Added <scope value="type"/> to StructureMap.$transform sourceMap so tooling can distinguish that parameter from instance-level invocations consistently with the existing source URI parameter and the FHIR-27761 model.

Recommendation:
Keep this source fix. It is a narrow completion of the published FHIR-27761 decision for a later-added parameter, and no further core source changes were found for the same issue during the targeted operation audit.
