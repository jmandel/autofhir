FHIR-19465: Require Coverage cost category

Issue request:
FHIR-19465 was a Published/Persuasive FHIR-core Coverage change request, raised in STU3 and applied for STU3. It asked for Coverage.status, Coverage.beneficiary, and Coverage.costToBeneficiary.type to be 1..1, and for Coverage.payor to be 1..*.

Initial application:
Commit 7fbe7046270ff6857644a6af63207642576dc7ef explicitly included GF/FHIR #19465 and updated the old Coverage spreadsheet so Coverage.status and Coverage.beneficiary became 1..1 and Coverage.payor became 1..*. The same applied spreadsheet still showed Coverage.costToBeneficiary.type as 0..1, and the later StructureDefinition conversion preserved that missed cardinality in the current source.

Additional context:
Coverage is active in the current build through source/fhir.ini. The current StructureDefinition already has Coverage.status and Coverage.beneficiary as 1..1. The historical Coverage.payor element was later split for R5 into Coverage.insurer 0..1 and Coverage.paymentBy 0..*, and FHIR-37702 records the FM no-change decision explaining that R5 split rather than restoring payor. Later Coverage.costToBeneficiary decisions, including FHIR-32966 adding category/network/unit/term and FHIR-27024 making value[x] optional when exceptions are present, did not reverse the accepted requirement that each costToBeneficiary entry identify its cost category type.

AutoFHIR reconciliation:
Changed source/coverage/structuredefinition-Coverage.xml so Coverage.costToBeneficiary.type has min=1. No example changes were needed because the only Coverage example with costToBeneficiary already includes type, valueMoney, and exception.

Recommendation:
Keep this commit as the missing portion of the Published STU3 cardinality fix. Do not reintroduce Coverage.payor in current R6+ source; if FM wants Coverage.costToBeneficiary.type to become optional after the later cost-qualifier additions, that should be handled by a new reversing Jira decision.
