FHIR-27802: Clarify user identity resource linkage

Issue request:
FHIR-27802 was Published with a Persuasive with Modification resolution for the Security and Privacy module #user section. It asked to add FAQ guidance distinguishing application users and roles from Practitioner/PractitionerRole, including that PractitionerRole can be relevant for practitioner users but is not the only FHIR linkage because users can also be Patient or RelatedPerson.

Initial application:
The issue was applied by b1ab4dabb8bd626b70ea00d24b50e4eec9431b5f, which added guidance to source/secpriv-module.html that user role assignment is generally managed outside FHIR and that practitioner users may have functional or structural roles through PractitionerRole. That initial application left PractitionerRole misspelled as PractionerRole and did not include the Patient/RelatedPerson clarification from the Jira resolution. The page is in current build scope through source/hierarchy.xml as the Security and Privacy module page.

Additional context:
The originating Zulip thread records Lloyd McKenzie's guidance that generic user, role, and permission management belongs outside FHIR, that Practitioner is for people acting in a professional capacity, and that using Practitioner to represent a Patient or RelatedPerson is undesirable. A later security-page spelling issue, FHIR-55342, corrected an unrelated contraction and did not address this FHIR-27802 wording. The combined branch did not already contain an Issue-Reconcile-Key commit for FHIR-27802.

AutoFHIR reconciliation:
This commit corrects the resource name to PractitionerRole and adds the missing clarification that Practitioner/PractitionerRole are not the only possible FHIR linkages for user identity; patient and related-person users should instead link to the appropriate Patient or RelatedPerson resource.

Recommendation:
Keep this source change as the completed reconciliation for FHIR-27802. It is narrow, keeps the existing general-IT/SCIM guidance, and completes the published Jira resolution without expanding into unrelated access-control policy.
