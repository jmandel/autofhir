FHIR-31491: Align named-query parameter scope notes

Issue request:
FHIR-31491 was Published with a Persuasive with Modification resolution for R5. It asked to clarify the Search section statement that all standard search parameters are automatically in scope for named queries, including whether resource-specific search parameters are also available, when servers must support inherited parameters, what clients can assume from CapabilityStatement, and why named-query definitions should enumerate relevant allowed parameters.

Initial application:
The issue was applied in git commit ddecc63591d23dab5767aa2888c985a7c75964b6, which added the requested clarification to source/search.html. The current Search page still carries the FHIR-31491 rule: standard all-resource and search-result parameters are potentially available, resource-specific parameters are potentially available when the query operation has a resource scope, inherited parameters need not be supported unless documented, clients should not assume parameters absent from CapabilityStatement support, and authors should include relevant parameters in the OperationDefinition.

Additional context:
source/search.html is in build scope via publish.ini and source/hierarchy.xml, and source/fhir.ini actively lists operationdefinition=OperationDefinition, so source/operationdefinition/operationdefinition-notes.xml feeds the current OperationDefinition resource page. A later named-query issue, FHIR-39318, added OperationDefinition-page narrative, but the resulting paragraph still used the older "automatically in scope" wording, tied resource-specific parameters to resources returned by the operation rather than the query operation's resource context, and said servers must list supported parameters in OperationDefinition. Related FHIR-39318 and FHIR-39316 reconciliation commits are already on the combined branch, so this commit only decides FHIR-31491 and avoids duplicate related-issue commits.

AutoFHIR reconciliation:
This commit updates the OperationDefinition notes paragraph to align with the current Search-page semantics for FHIR-31491. It links to the named-query and standard-search-parameter sections, uses "potentially available" rather than "automatically in scope," clarifies resource-specific parameter availability for query operations defined in one or more resource-type contexts, distinguishes definition from server support, points clients to CapabilityStatement support for general searches, and recommends documenting relevant parameters in the named query OperationDefinition or a constrained OperationDefinition.

Recommendation:
Keep this source fix. It removes a parallel-page inconsistency that could otherwise lead implementers to a different understanding from the Search page. No further source change is recommended for FHIR-31491 unless the work group later wants to revisit the stricter FHIR-39318 wording about how servers document per-query parameter support.
