FHIR-40503: Align Device search parameter names

Issue request:
FHIR-40503 was Applied as Persuasive with Modification for OO to review Device and DeviceDefinition search parameters. The accepted change was to add Device version-type, rename Device udi-carrier to udi-carrier-hrf, and add DeviceDefinition search coverage for device identifiers, model-number, version, version-type, and has-part.

Initial application:
The issue was partially applied in the current branch by FHIR-40503-tagged commits 55843e1232, c09b7267b8, cae8422ef9, and f187893e6a. Those commits added the search parameters and later adjusted the Device version code and DeviceDefinition model-number code, but three source-level mismatches remained: DeviceDefinition identifier indexed the udiDeviceIdentifier backbone rather than the deviceIdentifier child, DeviceDefinition model-number kept the old DeviceDefinition-model id/url, and the Device and DeviceDefinition version-type parameters used type-version canonical URLs.

Additional context:
Device and DeviceDefinition are active current-build resources in source/fhir.ini, and their bundle-*-search-params.xml files feed the search parameter registry. Later Applied issue FHIR-53301 intentionally superseded the original DeviceDefinition has-part parameter by replacing it with has-part-canonical and has-part-code after hasPart.reference became hasPart.definition[x], so this reconciliation did not restore the old has-part source. FHIR-53212 later referenced the normative DeviceDefinition model-number and version-type search parameters, supporting the corrected names, and no Zulip hits were found for FHIR-40503 that changed the Jira/OO minutes conclusion.

AutoFHIR reconciliation:
This commit corrects the active source by narrowing DeviceDefinition identifier to DeviceDefinition.udiDeviceIdentifier.deviceIdentifier, renaming the DeviceDefinition model-number SearchParameter id/url to match its code and later normative naming, and aligning the Device and DeviceDefinition version-type canonical URLs with their id/code values.

Recommendation:
Keep this source fix. It completes the already-applied FHIR-40503 search parameter work without reversing later hasPart changes; no additional core change is recommended for this issue family unless a future OO decision wants a separate DeviceDefinition device-identifier code instead of the existing identifier parameter coverage.
