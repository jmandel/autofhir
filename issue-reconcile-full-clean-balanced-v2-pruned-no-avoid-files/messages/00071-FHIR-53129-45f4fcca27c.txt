FHIR-53129: Clarify Consent authorization tracing

Issue request:
FHIR-53129 was Applied/Persuasive for R6 by Security. It asked for the Access Control material to mention AuditEvent and Provenance as ways to record or trace authorization decisions founded on Consent, including the existing AuditEvent consent authorization example and new Provenance examples for the same use case.

Initial application:
PR #3952 was merged as 14ab71d33601002555732d7e1269b814512d6ae2 after implementation commit 88a96446a80bf3e43352eb8aac8ddd5db8cf54ee. That application added the AuditEvent access-control bullets, a Consent Used subsection, and Provenance/example5 and Provenance/example6. The active fhir.ini resource entries confirm AuditEvent, Provenance, Consent, and the Security module are in current build scope. The application left the Access Control narrative describing only AuditEvent and left the new Provenance examples with copied comments from a different Procedure follow-up-note example.

Additional context:
Security WG minutes on 2025-10-13 and 2025-10-27 record the intended explanation as an access control decision recorded or memorialized by AuditEvent and/or Provenance, and the 2025-10-27 vote approved FHIR-53129 6-0-0. The 2025-11-10 minutes and FHIR-23739 comments record that Patient Care was satisfied and that the ticket was complete after Security's AuditEvent and Provenance update. Later FHIR-54833 kept Provenance.authorization as a CodeableConcept reason/purpose element, so the Consent/AuditEvent references for this use case still belong in Provenance.entity.what, not Provenance.authorization.

AutoFHIR reconciliation:
This commit adds the missing Provenance explanation to the Access Control consideration list, updates the Security module Consent Used subsection so it covers AuditEvent and Provenance for create/update/delete tracing, links the two Provenance examples, and replaces misleading copied comments in those examples with comments describing the Consent-authorization use case.

Recommendation:
Keep this commit as-is. It completes the applied FHIR-53129 intent without reopening FHIR-23739 or changing the Provenance.authorization semantics addressed by FHIR-54833.
