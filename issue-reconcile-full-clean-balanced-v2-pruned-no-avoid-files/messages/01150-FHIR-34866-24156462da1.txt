FHIR-34866: Add authored aliases to legacy search parameters

Issue request:
FHIR-34866 was Applied/Persuasive with Modification for FHIR-I and raised that equivalent authored-date SearchParameters used inconsistent codes including authored, authored-on, and authoredon. The approved R6 resolution added SearchParameter.aliasCode, examples, registry/table visibility, formal HL7 search-parameter naming guidance, and preferred-code cleanup while preserving backward compatibility; it explicitly noted that normative SearchParameters may need to keep their normative code.

Initial application:
The issue was partially applied before this reconciliation. Git commit 188ed0d92982a31f00ed9093844f90544b613a11 added SearchParameter.aliasCode to the SearchParameter StructureDefinition, and commit 216f001194d17327f7b2ffdf9150b89b2303e5ae, later merged through HL7/fhir#3967, added naming guidance and alias examples. Those commits did not add aliases to the actual DeviceRequest, MedicationRequest, or Task authoredOn search parameters; the current source still had normative primary codes authored-on or authoredon with no authored alias.

Additional context:
SearchParameter, DeviceRequest, MedicationRequest, and Task are active current-build resources in source/fhir.ini. The current SearchParameter notes say HL7-defined parameters should be consistent across resources and give authored as the example authoring-date code, while aliasCode is documented as the compatibility mechanism for renamed parameters. Because the affected entries are normative, this reconciliation preserves their published primary codes and uses aliasCode rather than renaming them. Related reconciliation for FHIR-25037 already used the same aliasCode mechanism for a compatibility-sensitive search-code cleanup.

AutoFHIR reconciliation:
This commit adds aliasCode="authored" to the DeviceRequest authored-on, MedicationRequest authoredon, and Task authored-on SearchParameter definitions. It does not rename their normative primary codes and does not attempt a broad cleanup of unrelated Request.authoredOn-like names without a source list of approved preferred codes.

Recommendation:
Keep this fix. It completes the seed issue's concrete authored/authored-on/authoredon compatibility case in current build-scope source while avoiding a risky normative code rename or an unbounded search-parameter naming sweep. Any broader preferred-code inventory from the Jira attachment should be handled through focused follow-up review.
