FHIR-20400: Clarify fractional seconds for time primitives

Issue request:
FHIR-20400 was a Published/Persuasive FHIR-core datatypes change request. It reported that the time datatype prose only described hh:mm:ss while the regex permitted fractional seconds without a finite upper bound, and the resolution said to update the text for time and dateTime to allow milliseconds.

Initial application:
Historical commit 0ed3302de365979d3eee6f8c96cd9570acb542d8 explicitly referenced FHIR-20400 and changed the then-inline time regex in source/datatypes.html from an unbounded fractional-second pattern to a 1-to-3 digit fractional pattern. It did not update the time prose and did not independently reconcile the dateTime prose with the primitive regex source. Earlier commit d621ab0bda61832d87d16ee8fa98261bf403a9da had added "Milliseconds are optionally allowed" to the dateTime row, but current primitive regex source later moved beyond millisecond-only wording.

Additional context:
The current build renders datatype regexes from source/datatypes/primitives.xml through the [%regex ...%] placeholders on source/datatypes.html. Later dateTime regex decisions, including FHIR-38735 and FHIR-52878, left the current dateTime regex with optional 1-to-9 digit fractional seconds, and the time regex uses the same 1-to-9 digit fractional-second limit. The original Zulip thread linked from the Jira records Grahame saying fractions are allowed and that he supports up to 9 digits. FHIR-42984 separately clarified the same precision family for instant by saying sub-millisecond precision is optionally allowed.

AutoFHIR reconciliation:
Updated the active datatype page and primitive datatype spreadsheet definitions so dateTime and time both state that fractional seconds are optionally allowed. The regexes were intentionally left unchanged because later applied decisions already settled the current 1-to-9 digit precision behavior.

Recommendation:
Keep this commit. It completes the FHIR-20400 textual reconciliation without narrowing the later-approved regex behavior; no additional core source work is recommended unless the work group separately decides to change the 1-to-9 digit precision policy.
