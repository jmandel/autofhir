FHIR-37966: Clarify Request groupIdentifier definitions

Issue request:
FHIR-37966 was Published/Persuasive for R5. It asked to replace the ambiguous groupIdentifier definition, which said the element represented the identifier of a requisition or prescription, with wording explaining that the same Identifier appears on multiple independent Request instances activated or authorized together and can affect reporting, billing, and similar business processes.

Initial application:
The original source application was git commit b5f0dcdffd, which updated CommunicationRequest.groupIdentifier, DeviceRequest.groupIdentifier, MedicationRequest.groupIdentifier, RequestOrchestration.groupIdentifier, and Task.groupIdentifier. The active Request logical pattern in source/request/request-spreadsheet.xml still kept the old definition, and later active Request-pattern resources such as NutritionOrder.groupIdentifier and VisionPrescription.groupIdentifier were added with similarly ambiguous resource-specific definitions.

Additional context:
source/fhir.ini includes request as an active logical pattern and includes ServiceRequest, NutritionOrder, and VisionPrescription as active resources. FHIR-38868 already cleaned up Request pattern narrative references from requisitionId to groupIdentifier, but it did not change the Request.groupIdentifier element definition. FHIR-50429 later kept ServiceRequest.requisition as the ServiceRequest element name while retaining its workflow mapping to Request.groupIdentifier, so this reconciliation clarifies its definition without renaming it. SupplyRequest still contains related legacy wording only in out-of-build source artifacts because SupplyRequest has moved outside the active core build.

AutoFHIR reconciliation:
Updated the active Request.groupIdentifier definition and the active ServiceRequest.requisition, NutritionOrder.groupIdentifier, and VisionPrescription.groupIdentifier definitions to the approved FHIR-37966 wording. Removed obsolete active request-mapping exception definition differences that no longer exist after the Request pattern and resource definitions now match; kept remaining short, comment, requirements, and Task-specific definition exceptions.

Recommendation:
Keep this source fix as-is. The remaining old wording found after reconciliation is limited to generated-looking SVG titles and out-of-build SupplyRequest mapping metadata, so it should not drive a core source edit unless those artifacts are regenerated or SupplyRequest is reconciled in its current external home.
