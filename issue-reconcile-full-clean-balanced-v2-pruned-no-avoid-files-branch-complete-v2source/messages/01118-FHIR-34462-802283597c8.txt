FHIR-34462: Align eld-17 targetProfile summary

Issue request:
FHIR-34462 was a Published/Persuasive R4B technical correction asking for ElementDefinition eld-17 to allow targetProfile when the type code is CodeableReference, matching the R5 draft behavior instead of limiting targetProfile to Reference or canonical.

Initial application:
The executable portions of the issue were already applied before this reconciliation: the current source FHIRPath and XPath for eld-17 both include CodeableReference, and Jira comments point to R5/R4B pull requests plus commits 68716c13e5 and 32d07acd91 that fixed the stale XPath in the R4B/R4 lines. The current source still had one leftover human-readable invariant sentence saying targetProfile was only allowed for Reference or canonical.

Additional context:
ElementDefinition is an active normative datatype in source/fhir.ini, so source/datatypes/elementdefinition.xml feeds the current build. The remaining stale human sentence conflicted with the adjacent FHIRPath and XPath constraints and could mislead readers even though validators using the expressions would permit CodeableReference. Direct Zulip and Confluence searches for FHIR-34462 found no conflicting community decision; the only broader CodeableReference/targetProfile minutes hit was about a different child-placement rule family.

AutoFHIR reconciliation:
Updated the eld-17 human-readable constraint text in source/datatypes/elementdefinition.xml to say targetProfile is allowed for Reference, canonical, or CodeableReference. No expression or XPath change was needed because both were already correct.

Recommendation:
Keep this source fix. It completes the published tracker by aligning the displayed invariant summary with the existing executable constraint and does not require further work unless a future work group decision changes eld-17 semantics.
