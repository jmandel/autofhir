FHIR-39024: Remove stale data-type target wording

Issue request:
FHIR-39024 was Published/Persuasive with Modification for R5 SubscriptionTopic. It asked to constrain SubscriptionTopic.resourceTrigger.resource, eventTrigger.resource, canFilterBy.resource, and notificationShape.resource away from all FHIR data types and toward resource-type choices plus an any/cross-version option; the resolution said to use the new cross-version resource-type value set and remove data type as a possible target from short and long descriptions where needed.

Initial application:
Git commit 23bc6d672392d659a2ad57ef61377032588f7943 explicitly applied FHIR-39024 by changing the four R5 SubscriptionTopic resource bindings from all-resource-types to the SubscriptionTypes value set with an all-resource-types UI additional binding. That commit left the resourceTrigger.resource and eventTrigger.resource short descriptions saying "Data Type or Resource"; after the R6 FHIR-46492 refactor collapsed those elements into SubscriptionTopic.trigger, the current source still had data-type wording on trigger.resource and notificationShape.resource.

Additional context:
FHIR-38800 created the version-independent resource-type terminology used by the SubscriptionTypes value set. Later Applied R6 issues FHIR-46492 and FHIR-47365 intentionally broadened SubscriptionTopic guidance for event triggers and non-FHIR focuses, including logical models, Basic, Binary, and Parameters examples; those later decisions mean the current source should not be narrowed to only concrete FHIR resources. Existing combined-branch reconcile commits already represent FHIR-46492 and FHIR-47365, so this commit only reconciles the residual FHIR-39024 wording.

AutoFHIR reconciliation:
This commit updates the active SubscriptionTopic StructureDefinition so trigger.resource no longer advertises a data type target and notificationShape.resource describes a resource type or other definition, such as a logical model, rather than a data type. The binding to ValueSet/subscription-types and the later R6 non-FHIR/logical-model guidance are left unchanged.

Recommendation:
Keep this commit. It removes the stale implementer-facing data-type target wording required by FHIR-39024 while preserving later FHIR-I decisions that allow non-FHIR definitions where appropriate.
