FHIR-6343: Remove stale mailbox source references

Issue request:
FHIR-6343 was Published as Persuasive with Modification for FHIR-core messaging. It asked to remove the DSTU1 /Mailbox endpoint now that FHIR operations can cover that role, with the final resolution removing mailbox from the document paradigm and defining $process-message for synchronous message processing.

Initial application:
The issue was explicitly applied in svn revision 5657, mirrored as git commit 8b801ae887a7ed1c4e58cb57c30a8379b50cf157 with subject "#7976, #6343 - rework operations and messages". That commit replaced the main messaging mailbox section with $process-message, but later current source still retained mailbox wording in REST/use-case narrative, CapabilityStatement source, and the $process-message operation's security bullet.

Additional context:
MessageHeader and CapabilityStatement are active resources in source/fhir.ini, source/messageheader/list-MessageHeader-operations.xml includes OperationDefinition/MessageHeader-process-message, and source/messaging.html now delegates $process-message details to that operation definition. FHIR-7976 is the same svn-r5657 change family for asynchronous $process-message response handling and is already represented on the combined branch; its current audit confirms the operation definition is the right home for process-message transport details. A 2016 Zulip implementer thread also describes DSTU2 as having redefined the messaging interface to use $process-message instead of the DSTU1 mailbox.

AutoFHIR reconciliation:
This commit removes current-build source references that could still direct readers to the removed mailbox model. It changes the REST overview and decision-support use-case page to link to $process-message, changes CapabilityStatement.implementation.url so it no longer describes mailbox interfaces, removes the obsolete CapabilityStatement narrative hook for rest/documentMailbox, and changes the operation's security bullet from "mailbox endpoint" to "$process-message endpoint". It intentionally does not hand-edit the generated CapabilityStatement SVG or the old QUICK model/spelling-dictionary occurrences that do not drive current normative mailbox behavior.

Recommendation:
Keep this source fix. Future generated builds can refresh generated diagram artifacts such as capabilitystatement.svg from the updated StructureDefinition; no separate work is needed for FHIR-6343 unless a work group wants broader editorial changes to historical or out-of-build model files.
