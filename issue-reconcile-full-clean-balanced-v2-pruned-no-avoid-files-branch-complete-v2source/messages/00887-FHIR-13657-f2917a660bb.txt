FHIR-13657: Clarify string and uri value set bindings

Issue request:
FHIR-13657 was Published as Persuasive with Modification for STU3. It asked that the string and uri datatype entries make ValueSet binding visible, and that the specification clarify that value sets bound to string or uri should not contain the same code string from different code systems because the instance value carries no system to distinguish them.

Initial application:
The issue was applied in SVN revision 12452, represented in git as b9c26b467566c3f04bc2545c614e6005680a6c63, which added datatype-page binding notes for string, uri, code, Coding, CodeableConcept, and Quantity and expanded terminologies.html. Earlier FHIR-12445/r11209 had already added a datatypes note and terminology-page references for string/uri bindings. In the current source, the string, uri, and Quantity datatype rows still state that they can be bound, but the uri row linked to the string terminology anchor and the active terminology page no longer carried FHIR-13657's ambiguity warning.

Additional context:
FHIR-22670 later removed the dedicated terminologies.html#strings section for R5 and folded string/uri extensible-binding behavior into the general binding-strength language, so restoring the old section would conflict with that later decision. The current source/terminologies.html page still had an active "See below" link to the removed #strings section, while source/datatypes.html and source/terminologies.html are active core source pages for the datatype and terminology guidance in this build.

AutoFHIR reconciliation:
This commit updates the active terminology notes to preserve the string/uri duplicate-code guidance from FHIR-13657 without resurrecting the removed #strings section, and points readers to the current Extensible Binding Strength rules. It also fixes the uri datatype row so its binding note links to the uri terminology anchor rather than the string anchor.

Recommendation:
Keep this source fix. It is a narrow reconciliation of FHIR-13657 with the later FHIR-22670 refactor; FHIR-12445, FHIR-22670, and FHIR-13303 should remain separate historical/context issues rather than additional decisions in this seed.
