FHIR-17172: Require host segment in RESTful reference regex

Issue request:
FHIR-17172 was Published/Persuasive for STU3 and reported that http://Patient/1 was invalid but passed the RESTful reference regex on the References page. The accepted resolution said the regex should be fixed because a URL with a scheme must have a host, while http://example.com////////Patient/1 remains valid.

Initial application:
The issue was initially applied in svn revision 14232, represented in git by 075cd55564e68888a3325e4c90f920d74aa5fe53, which changed the optional absolute URL prefix from zero-or-more slash-delimited segments to one-or-more segments. The same-day FHIR-14079 follow-up added '-' to the host/path character class. That application rejected http://Patient/1 in a full-string match, but the current source still allowed an empty first segment after the scheme, such as http:///Patient/1, because each repeated segment could be empty.

Additional context:
source/references.html is the active References page source and is linked by current Bundle source when explaining URLs that look like RESTful server URLs. Later Published issue FHIR-34405 only appended an optional fragment suffix and added cautionary prose; it did not change the scheme/host rule. Searches for FHIR-17172 and the reported URL/regex terms in Zulip and Confluence found no conflicting community decision.

AutoFHIR reconciliation:
This commit changes the optional absolute RESTful prefix so the first segment after http:// or https:// must contain at least one allowed character before its slash, while subsequent segments may still be empty. This preserves the accepted repeated-slash example after a host and prevents the regex from accepting an empty-host absolute URL.

Recommendation:
Keep this source fix. It completes the host requirement from FHIR-17172 without broadening the regex or revisiting separate historical questions about anchoring and other URL grammar details.
