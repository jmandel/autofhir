FHIR-23859: Allow notification entry responses in profile

Issue request:
FHIR-23859 was Published/Persuasive with Modification for R5. It asked how Bundle should represent subscription notifications, especially full-resource payloads with request/response details and id-only payloads, with final Jira text saying to use history bundles and relax constraints after the original disposition was lost and reconstructed from minutes.

Initial application:
The original minutes and later subscription work show that the issue was ultimately applied through the R5 subscription redesign rather than by keeping history as the notification type. Commit a8762c404cabbf352bfaa710016d436b85b757b9 added the subscription-notification Bundle type and Bundle constraints allowing request and response for that type in the then-authoritative Bundle spreadsheet, and commit a0abf4b1705a30f48541089896d3335ae9b6bd5b added the Bundle narrative section. Later Bundle profile commits added a subscription-notification-bundle profile, but that profile accidentally prohibited Bundle.entry.response on non-first entries.

Additional context:
FHIR-23738 documents the Argonaut/R5 subscription branch application of FHIR-23859: add Bundle.type = subscription-notification, allow entry.request and entry.response for subscription-notification, and require a SubscriptionStatus first entry. Current core source is in build scope through the active Bundle resource and Bundle-core implementation guide. Current Subscription narrative and examples still allow or use entry.response in subscription-notification payload entries, so the profile restriction was inconsistent with the applied design.

AutoFHIR reconciliation:
Removed the max=0 restriction for Bundle.entry:other.response from source/bundle/structuredefinition-profile-subscription-notification-bundle.xml. The first SubscriptionStatus entry remains constrained to omit response, while additional notification entries now inherit the base Bundle response cardinality and match the accepted subscription-notification design and examples.

Recommendation:
Keep this source fix. It is a narrow profile correction for the current build and avoids changing base Bundle invariants or reopening the older history-vs-new-type decision. Separate editorial cleanup, such as the pre-existing "NessageHeader" typo in the profile slicing description, should be handled by a distinct tracker if desired.
