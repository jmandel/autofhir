FHIR-46193: Align patch format binding text

Issue request:
FHIR-46193 was Applied with a Persuasive with Modification resolution for FHIR-core Conformance. It asked that CapabilityStatement.patchFormat stop using the all-MIME-types binding and instead constrain to the five legal patch MIME types: application/fhir+xml, application/fhir+json, application/fhir+turtle, application/json-patch+json, and application/xml-patch+xml. The resolution also required updating the element comment so it no longer implied that only the JSON Patch and XML Patch MIME types are legal.

Initial application:
The issue was partially applied by upstream commit d42017f27269949479aca292f2365ab8c804f560, which changed CapabilityStatement.patchFormat from ValueSet/mimetypes to ValueSet/patchmimetypes and added the PatchMimeType binding row and valueset-patchmimetypes.xml. That commit left the element comment saying only application/json-patch+json and application/xml-patch+xml are legal, and left the binding name/definition as the generic MimeType text saying any valid MIME type is allowed.

Additional context:
CapabilityStatement is an active resource in source/fhir.ini, so source/capabilitystatement/structuredefinition-CapabilityStatement.xml feeds the current build. source/terminologies/bindings.xml is the standard binding source that now contains PatchMimeType, and the checked-in capabilitystatement.svg displayed the stale generic binding tooltip. FHIR-I minutes from 2024-06-24 confirm the 8-0-0 decision that creating a value set for the five suggested values was reasonable. No directly relevant Zulip discussion was found.

AutoFHIR reconciliation:
This commit updates CapabilityStatement.patchFormat to use the PatchMimeType binding name, replaces the generic all-MIME-types binding definition with patch-specific text, updates the comment to list all five legal patch MIME types, and keeps the checked-in SVG tooltip and bindings.xml row synchronized with the authoritative source.

Recommendation:
Keep this source-changing reconciliation. It completes the Applied issue without broadening the change beyond CapabilityStatement.patchFormat; future patch formats should be added by updating ValueSet/patchmimetypes and the element comment together.
