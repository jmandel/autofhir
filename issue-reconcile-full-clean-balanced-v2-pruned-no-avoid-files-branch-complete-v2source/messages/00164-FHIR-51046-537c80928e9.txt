FHIR-51046: Align operation GET criteria

Issue request:
FHIR-51046 was Applied/Persuasive for the FHIR-core Operations page. It asked to make the GET invocation rule a conformance MAY, remove the duplicate "and", and replace the old "simple input parameters" restriction with a rule allowing parameters whose data type has a corresponding search type.

Initial application:
Commit d542f8a98c (from HL7/fhir#3967) applied the main list item in source/operations.html by changing "may" to "MAY", removing the duplicate "and", and allowing Identifier/Reference-like datatypes with corresponding search types. That commit left two other GET-invocation paragraphs on the same built Operations page describing the older primitive-only condition.

Additional context:
The implementers Zulip thread that prompted the issue discussed whether token-style URL formatting should be available for complex operation parameters. FHIR-I WGM minutes recorded a 7-0-0 Persuasive with Mod vote for FHIR-51046 about what can be mapped as HTTP parameters. Later source commits for FHIR-45251 and FHIR-41220 touched adjacent Operations request text but did not remove the remaining primitive-only GET criteria.

AutoFHIR reconciliation:
This commit updates the remaining Operations page GET-invocation criteria to use the FHIR-51046 search-type rule instead of the old primitive-only rule. source/operations.html is in build scope through source/hierarchy.xml, and each hunk removes a contradictory local statement that would otherwise lead implementers to believe GET is limited to primitive parameters.

Recommendation:
Keep this source fix. It completes the applied FHIR-51046 semantics on the current built Operations page without changing unrelated operation behavior.
