FHIR-25460 + FHIR-39096: Clarify reliable messaging protocol wording

Attribution note: surfaced while reviewing FHIR-25460, but direct Jira backing for this change is FHIR-25460 + FHIR-39096.

Issue request:
FHIR-25460 was Published with a Persuasive with Modification resolution for R5. It asked to clarify the Absence of Reliable Messaging section by replacing the vague statement that "FHIR messaging describes" a reliability approach with wording that says the remainder of the section describes a protocol for infrastructure that does not guarantee reliable messaging, changing sender/receiver references to "this protocol", changing Bundle.id table/example references to Bundle.identifier, and adding an STU feedback note.

Initial application:
The explicit FHIR-25460 source application was git 5e623b7da8, merged by a30b9f6df8, which updated the opening paragraph and sender wording in source/messaging.html but did not apply the receiver wording change. A later commit, 6f083998e3, added a different STU ballot note about the Bundle.id/MessageHeader.id identifier debate, not the requested "protocol has not been widely tested" note. Subsequent FHIR-39096 messaging commits replaced the Bundle.id/MessageHeader.id retry tables and examples with Bundle.identifier wording.

Additional context:
FHIR-25461 was the related identifier question and ultimately resolved no-change because other trackers addressed the topic. FHIR-39096, already represented on the combined branch, is the later Published decision that message identity is driven by Bundle.identifier, with MessageHeader.response.identifier aligned by FHIR-29690. That later context confirms the current Bundle.identifier model and makes reintroducing an age-sensitive STU warning about untested protocol status unsafe without fresh work-group review, but it does not justify leaving current source text that still names the wrong protocol concept.

AutoFHIR reconciliation:
This commit completes the durable source corrections still needed for FHIR-25460 in current build inputs. In source/messaging.html, the receiver rule now says "When a receiver implements this protocol". In the active MessageHeader $process-message OperationDefinition, the duplicated footer/comment link text no longer tells implementers to follow rules for "Bundle.id and message id" and instead points to the reliable-messaging rules for message Bundle.identifier values. source/documentation.html links messaging.html from the current documentation navigation, source/fhir.ini actively lists messageheader=MessageHeader, and source/messageheader/list-MessageHeader-operations.xml references OperationDefinition/MessageHeader-process-message, so both edited files are in build scope.

Recommendation:
Keep this source fix. It removes the remaining misleading current-spec wording without adding speculative feedback-note text whose historical request was never applied and whose accuracy after later R5/R6 identifier rewrites needs human/work-group confirmation if someone still wants it.
