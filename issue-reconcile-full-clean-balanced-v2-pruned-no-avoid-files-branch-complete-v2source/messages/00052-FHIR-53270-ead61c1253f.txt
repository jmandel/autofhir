FHIR-53270: Correct Requirements category change metadata

Issue request:
FHIR-53270 was Applied/Persuasive with Modification for R6. It asked to allow requirement statements to have a 0..* category for grouping/filtering, originally suggesting CodeableConcept with a preferred binding; the approved modification was to do this using Coding.

Initial application:
The Jira comments point to HL7/fhir#3948 and merge commit 74e0a6db71bffd6530d3c6cc6a030c1d6d556d26, whose branch first added a Requirements.category element. Later source history, especially 46c288728a5c11247ef2f8d0b71ebfe15eab3799, corrected that application by moving the element to Requirements.statement.category with Coding type and an example binding.

Additional context:
The Requirements resource is active in source/fhir.ini, and the authoritative StructureDefinition now has Requirements.statement.category 0..* Coding. A later ballot issue, FHIR-54023, asks for an explicit THO code system and preferred binding; that work is not Applied/Published in this default run and is tied to unresolved UTG proposal UP-783. The checked-in requirements.svg still references Requirements.category, but it is a generated-looking diagram artifact and is not the authoritative source to edit by itself.

AutoFHIR reconciliation:
This commit corrects the active R5-to-R6 change metadata in source/fhir.ini from Requirements.category=+ to Requirements.statement.category=+, aligning the release-change surface with the current authoritative Requirements StructureDefinition and the applied Jira decision.

Recommendation:
Keep this source fix. Handle FHIR-54023/UP-783 separately when the terminology value set and preferred binding are final and in scope; do not infer that work from FHIR-53270 alone.
