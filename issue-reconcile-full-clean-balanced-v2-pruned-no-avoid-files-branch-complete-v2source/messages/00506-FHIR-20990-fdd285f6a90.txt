FHIR-20990: Correct address line extension example

Issue request:
FHIR-20990 was a Published FHIR-core datatypes change request asking for a standard Address.line qualifier extension bound to v3 AddressPartType. The final Not Persuasive with Modification resolution rejected a new qualifier extension, confirmed that the existing ISO 21090 address-part extensions are intended for this purpose, and promised an example showing the complete address-part extension use.

Initial application:
The issue appears to have been initially applied by git commit 3fe108e91dc94537ac937263f428e8f9245410fa, which added an Address example to source/datatypes-examples.html. A later datatype-examples JSON conversion in e9e4e5f34c8d0b40d680c26f92acfa19b5f714a6 added a JSON rendering for the same example. The current example was present in the active datatype examples page, but it incorrectly used streetNameBase for the street type and direction values and placed all JSON primitive extensions on the first Address.line entry.

Additional context:
The ISO 21090 address-part StructureDefinitions now live in the FHIR Extension Pack, and their definitions distinguish streetNameBase from streetNameType and direction. The datatype pages link to datatypes-examples.html#Address, so this source is part of the current build surface. A contemporaneous Zulip thread from the same reporter shows the address-line modeling concern and Grahame's response that existing line-level extensions were intended to support such use cases. No Confluence or direct FHIR-20990 Zulip evidence was found that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This commit corrects only the active Address example: the XML and JSON now use iso21090-ADXP-streetNameType for "Street" and iso21090-ADXP-direction for "NW", and the JSON _line array now has one primitive-extension object per address line so careOf is attached to the first line while the street parts are attached to the second line.

Recommendation:
Keep this source fix. It completes the published resolution without adding the rejected qualifier extension or changing the extension definitions; no related Jira issue needs a separate reconciliation commit from this investigation.
