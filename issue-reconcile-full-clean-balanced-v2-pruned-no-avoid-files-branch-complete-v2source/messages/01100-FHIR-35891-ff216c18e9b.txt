FHIR-35891: Restore multi-type binding guidance

Issue request:
FHIR-35891 was Published with a Persuasive with Modification resolution for R5. It asked the terminology page to document that a binding on an element with multiple data types applies to all bindable types, and that type-specific binding needs an explicit mechanism rather than an implicit datatype exception.

Initial application:
The issue was initially applied in commit d7b4a4ab88, which added the requested paragraph to source/terminologies.html. That paragraph was then removed the next day by ab0ada5222 while applying unrelated terminology-page edits, leaving the current source without the approved clarification. The current page is in build scope through source/fhir.ini resourceType=terminologies.

Additional context:
The originating Zulip thread and the 2022-07-18 FHIR-I minutes confirm the intended rule: bindings on choice-type elements apply to all bindable types. FHIR-48480 later added an ElementDefinition warning for bindings with more than one bindable type and recommends slicing by type when the binding is not intended for every bindable type. Since additional bindings are now part of ElementDefinition and do not replace the main binding, the restored text uses current terminology and points to type slicing for type-specific conformance bindings.

AutoFHIR reconciliation:
Added a paragraph to source/terminologies.html in the binding overview explaining that a binding on an element with multiple allowed types applies to all allowed bindable types: code, Coding, CodeableConcept, CodeableReference, Quantity, string, and uri. The paragraph also directs authors to slice a choice element by type when the binding should apply only to a specific type.

Recommendation:
Keep this source-changing commit. It restores an approved clarification that was accidentally lost and aligns the terminology page with the later FHIR-48480 warning invariant. Future work should only revisit the paragraph if the work group wants to define a distinct additional-binding usage pattern for type-scoped supplementary bindings.
