FHIR-39431: Align DeviceMetric unit binding text

Issue request:
FHIR-39431 was Published with a Persuasive resolution for R5. It reported that DeviceMetric.unit was bound to the broad Device Metric and Component Types value set and resolved to change the preferred binding to all of UCUM.

Initial application:
The issue was initially applied by commit 471e546700387be46eaef1cbd2218cdb9275706f from HL7/fhir#2820, which changed source/devicemetric/structuredefinition-DeviceMetric.xml so DeviceMetric.unit points to http://hl7.org/fhir/ValueSet/ucum-units instead of http://hl7.org/fhir/ValueSet/devicemetric-type. That application left the adjacent binding description as "IEEE 11073-10101" and left the element comment saying RTMMS was preferred; a later FHIR-51404 formatting cleanup added Markdown links but retained the same preference wording.

Additional context:
source/fhir.ini keeps devicemetric=DeviceMetric active in the current build, so structuredefinition-DeviceMetric.xml is authoritative source. Earlier DeviceMetric unit trackers such as FHIR-7141 and FHIR-7596 show the long-standing UCUM preference discussion, and later FHIR-50161 chose not to narrow DeviceMetric.unit from CodeableConcept to Coding because implementers may represent a unit in both UCUM and MDC. Those decisions support keeping both coding-system mentions while removing the stale RTMMS preference and IEEE binding description that conflict with the UCUM preferred binding.

AutoFHIR reconciliation:
This commit keeps the already-correct preferred UCUM value set and CodeableConcept type, but aligns the surrounding source text. The DeviceMetric.unit comment now says UCUM or RTMMS can be used without stating that RTMMS is preferred, and the binding description now identifies UCUM rather than IEEE 11073-10101.

Recommendation:
Keep this commit as-is. It completes the published FHIR-39431 binding correction in the active DeviceMetric StructureDefinition without changing the allowed CodeableConcept representation; future terminology policy changes should be handled by their own DEV decisions.
