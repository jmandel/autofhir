FHIR-27024: Require Coverage cost value or exception

Issue request:
FHIR-27024 was a Published/Persuasive FHIR-core Coverage change request, raised in R4 and applied for R5. It asked to change Coverage.costToBeneficiary.value[x] from 1..1 to 0..1 because costToBeneficiary.exception can represent copayment exception cases where a fixed amount or percentage is irrelevant, and it also asked for an invariant requiring value[x] or exception or both.

Initial application:
Coverage is an active current-build resource through source/fhir.ini, and source history shows commit 720258c80a99566e1259c4c1a1dcacd8fbc5abbf changed Coverage.costToBeneficiary.value[x] from min 1 to min 0 in source/coverage/structuredefinition-Coverage.xml. No Jira-tagged FHIR-27024 source commit was found, and the current source/build surface lacked the requested value-or-exception invariant, so the prior application was partial.

Additional context:
FHIR-18122 introduced Coverage.costToBeneficiary.exception as the supporting element for copayment exceptions. Targeted Jira, Zulip, and Confluence searches found no later core decision reversing FHIR-27024's invariant request. The current build profile surface already exposed value[x] as 0..1 but had no Coverage.costToBeneficiary constraint beyond the generic ele-1 invariant.

AutoFHIR reconciliation:
Added cov-ctb-1 to Coverage.costToBeneficiary with FHIRPath expression value.exists() or exception.exists(), and linked that condition from the value[x] and exception child elements. Existing Coverage examples with costToBeneficiary already include value[x], exception, or both, so no example source changes were needed.

Recommendation:
Keep this commit as the completion of the Published R5 application. If the Financial Management work group later wants to allow costToBeneficiary entries that contain only categorization details without a value or exception, that should be handled by a new reversing Jira decision.
