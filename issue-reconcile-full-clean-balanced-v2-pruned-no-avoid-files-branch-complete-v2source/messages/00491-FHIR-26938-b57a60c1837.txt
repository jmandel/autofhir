FHIR-26938: Fix AuditEvent search description path

Issue request:
FHIR-26938 was a Published/Persuasive Security WG clarification for R5 asking the AuditEvent page to explain how a FHIR search, especially a POST search, should be recorded. The accepted resolution added a "Recording Search Events" note saying that the search request belongs in AuditEvent.entity.query as the whole HTTP request encoded as base64Binary, with the harmonized search parameter string optionally recorded as descriptive text.

Initial application:
The issue was initially applied by commit 9284053de1b13444a6cb249d31fcd6e0838e3e7c, which added the Recording Search Events note to source/auditevent/auditevent-notes.xml. The note remained in the active AuditEvent resource source, but it carried forward the resolution text's typo naming AuditEvent.entry.description, an element that does not exist in AuditEvent.

Additional context:
Current source/fhir.ini has AuditEvent as an active resource, and source/auditevent/auditevent-notes.xml feeds the active AuditEvent page. The current StructureDefinition defines AuditEvent.entity.description and AuditEvent.entity.query, the AuditEvent search example places the harmonized URL in entity.description and the raw query payload in entity.query, and the AuditEvent search parameter bundle also indexes AuditEvent.entity.description. The cited Zulip thread supports the same model: capture the full HTTP request in entity.query without sanitization while allowing a more usable description for what was processed.

AutoFHIR reconciliation:
This commit changes only the broken path in the FHIR-26938 note from AuditEvent.entry.description to AuditEvent.entity.description. That makes the clarification point at the actual element available for the harmonized search parameter string and aligns the narrative with the resource definition and existing example.

Recommendation:
Keep this commit as-is. The rest of the FHIR-26938 note and existing search example already convey the approved GET/POST search audit pattern; adding a new example now would go beyond the final resolution, but leaving the invalid element path would mislead implementers.
