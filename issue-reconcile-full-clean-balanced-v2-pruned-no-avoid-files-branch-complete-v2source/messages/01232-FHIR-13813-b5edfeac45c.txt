FHIR-13813: Align expansion identifier prose with optional cardinality

Issue request:
FHIR-13813 was Published/Persuasive for FHIR-core ValueSet after the Vocabulary WG accepted changing ValueSet.expansion.identifier from mandatory to 0..1 because terminology servers are not required to persist expansions and should not be forced to generate an identifier for transient $expand results.

Initial application:
The issue was applied in SVN revision 13317, represented in git as a1e1588a06e0b0faae02480aa5f109274ffb67fb, which changed source/valueset/valueset-spreadsheet.xml from 1..1 to 0..1. The current refactored active StructureDefinition source already carries min 0/max 1, but older ValueSet narrative still said every expansion has or SHALL have ValueSet.expansion.identifier.

Additional context:
source/fhir.ini has valueset=ValueSet in the active [resources] section and assigns ValueSet to vocab, so source/valueset narrative and StructureDefinition sources are in the current build scope. Related FHIR-5795 explains the earlier 1..1 rule, FHIR-16442 explains the current business-identifier short text, and later FHIR-55363 rejected repeating the identifier because the server performing the expansion assigns a single value. A 2021 terminology Zulip thread independently identified the same contradiction between the SHALL prose and the 0..1 cardinality from FHIR-13813.

AutoFHIR reconciliation:
Updated the active ValueSet introduction and expansion identifier notes to say that ValueSet.expansion.identifier can be included and is optional for transient expansions, while retaining the requirement that a populated identifier uniquely identifies the expansion and that reused identified expansions keep the same identifier.

Recommendation:
Keep this source change. It completes the original cardinality decision across the active narrative without changing the already-correct StructureDefinition cardinality or unrelated generated artifacts.
