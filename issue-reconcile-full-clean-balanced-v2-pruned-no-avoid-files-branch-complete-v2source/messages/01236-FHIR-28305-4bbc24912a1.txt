FHIR-28305: Clarify Questionnaire item type mapping

Issue request:
FHIR-28305 was Published with a Persuasive with Modification resolution for R5. It asked to remove Questionnaire.item.type from the properties that can be deferred to Questionnaire.item.definition/ElementDefinition because Questionnaire.item.type is 1..1, while adding item.text as the ElementDefinition.label mapping, warning clients about definition-based questionnaires, and preserving an alignment note for ElementDefinition.type.

Initial application:
The Jira-linked commit 3f2444c74d added the definition-based Questionnaire narrative, added item.text to the derived-property list, removed item.type from that list, and created the questionnaire-definitionBased extension. A same-day FHIR-23128 commit, f7d53f8a45, removed the obsolete derived-property list from the Questionnaire.item.definition element definition and pointed readers to the detailed notes. However, the FHIR-28305 narrative accidentally said QuestionnaireResponse.item.type, and the Questionnaire.item.type element comment still used the old "value may come from ElementDefinition" phrasing.

Additional context:
FHIR SDC minutes for 2020-10-01 record the approved 9-0-0 direction: keep Questionnaire.item.type mandatory, remove item.type from the ElementDefinition mapping list, add item.text to the mapping list, and add notes that ElementDefinition.type must match item.type. The related definitionBased extension now lives in the FHIR Extension Pack, while the core Questionnaire resource and its notes remain active in source/fhir.ini.

AutoFHIR reconciliation:
This commit corrects the active Questionnaire notes to refer to Questionnaire.item.type, not the nonexistent QuestionnaireResponse.item.type, and updates the active Questionnaire.item.type comment so it says the value must be present in the Questionnaire and should align with ElementDefinition.type when a definition is referenced.

Recommendation:
Keep this source-changing commit. It completes the core-source reconciliation for FHIR-28305 without reopening the external SDC profile work; any future SDC-specific mustSupport/profile expectations should be handled in the SDC IG rather than this core FHIR checkout.
