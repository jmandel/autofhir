FHIR-24827: Clarify Coverage boundaries

Attribution note: surfaced while reviewing FHIR-17950, but direct Jira backing for this change is FHIR-24827.

Issue request:
FHIR-17950 was a Published/Persuasive Financial Management change request from the STU3 cycle asking Coverage to add a Boundaries and Relationships section that distinguished Coverage from Contract and InsurancePlan.

Initial application:
The requested section was initially applied by git commit 288d1e5047c9743642f053c3b5099e6bfd882d60, whose message references GF #17944, #17950, and #17951. That commit added the Coverage boundaries table to source/coverage/coverage-introduction.xml, and source/fhir.ini keeps Coverage as an active core resource, so the page remains in current build scope.

Additional context:
Later FHIR-24827 split the old InsurancePlan model into InsuranceProduct and InsurancePlan, while explicitly keeping Coverage.insurancePlan pointed at InsurancePlan. Current Coverage source also defines Coverage.contract as Reference(Contract) and Coverage.insurancePlan as Reference(InsurancePlan). FHIR-47649 and FHIR-47650 then updated the InsurancePlan and InsuranceProduct boundaries pages to say Coverage links an InsurancePlan to a beneficiary/subscriber. No Zulip or Confluence search result for FHIR-17950 or the Coverage/Contract/InsurancePlan boundary terms conflicted with the Jira/source history.

AutoFHIR reconciliation:
This commit keeps the already-applied Coverage boundaries section and updates only its InsurancePlan row. It removes the stale TODO introduced during the InsuranceProduct split and aligns the Coverage page with the current InsurancePlan/InsuranceProduct distinction, without changing Coverage's Contract row or adding unrelated guidance.

Recommendation:
Keep this source fix. The seed request remains satisfied, and the Coverage boundaries page no longer leaves implementers with an unresolved question about whether Coverage should point directly to InsuranceProduct. FHIR-24827, FHIR-47649, and FHIR-47650 were used as bounded context only and should be reconciled separately if needed.
