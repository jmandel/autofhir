FHIR-37403: Add modified Composition status

Issue request:
FHIR-37403 was Published/Persuasive for R5 and asked Structured Documents to align Composition.status with DiagnosticReport.status because both resources have similar document/report lifecycles and Composition needed the DiagnosticReport statuses that distinguish initial, preliminary, and changed pre-final content.

Initial application:
The issue was initially applied in commit 6bfc6989a5 (FHIR-37403), linked from the Jira comments as PR 1953. That commit expanded composition-status with registered, partial/preliminary, corrected/appended, cancelled, deprecated, and unknown, and updated Composition/DocumentReference summaries, but it missed DiagnosticReport's pre-final modified code.

Additional context:
SDWG minutes for 2022-05-12 record a 17-0-0 Persuasive vote to update Composition Status to incorporate missing concepts present in Diagnostic Report Status. FHIR-37404 asked the same question for DocumentReference.docStatus, then was retracted by the submitter because FHIR-37403 resolved it as well; DocumentReference.docStatus is bound to the shared Composition Status value set. Composition, DiagnosticReport, and DocumentReference are active resources in source/fhir.ini, and source/sc.html includes the checked-in status-codes spreadsheet in the build. No directly relevant Zulip discussion was found.

AutoFHIR reconciliation:
Added the missing modified concept to source/composition/codesystem-composition-status.xml and updated the Composition.status and DocumentReference.docStatus short descriptions, search parameter descriptions, mapping-exception status list, status-codes spreadsheet rows, and Composition narrative lifecycle text. The change makes Composition Status contain every DiagnosticReport Status code while preserving the existing Composition-only deprecated code rather than making a breaking removal.

Recommendation:
Keep this source fix. Do not publish a separate FHIR-37404 commit from this seed: that issue is Resolved - No Change/Retracted and is useful context showing why DocumentReference-bound summaries were updated with the shared value set. If a future work group wants exact equality between the two code systems, review the existing Composition-only deprecated code as a separate compatibility decision.
