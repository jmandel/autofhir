FHIR-26944: Complete position discriminator guidance

Issue request:
FHIR-26944 was Published/Persuasive for R5 and requested support for slicing based on element order by introducing ElementDefinition.slicing.discriminator.type = "position" and explaining the constraints recorded in the FHIR-I discussion: path $this, fixed cardinality for all but the last slice, and no combined discriminator array.

Initial application:
The issue was initially applied by git commit 1740aadf7cdadffaaaf4c8ffc4726d9005fd202f, which added the position discriminator code to source/datatypes/elementdefinition.xml and added profiling prose in source/profiling.html describing index-based matching and the fixed-cardinality rule. That application did not carry forward the approved path $this guidance or the prohibition on combining position with other discriminator entries.

Additional context:
FHIR-I minutes from 2020-04-27 mirror the Jira comment and explicitly record that position slicing uses $this and should prohibit discriminator.type = position in combination with other discriminators. The current build includes ElementDefinition as an active datatype source via source/fhir.ini, and publish.ini lists profiling.html as a built page. Later Zulip discussion in 2026 confirms implementers understand position as an R5 discriminator and quotes the existing cardinality rule, with no conflicting work-group decision found.

AutoFHIR reconciliation:
This commit completes the partial R5 application by updating the authoritative ElementDefinition spreadsheet code-list definition and the profiling narrative to state that position uses discriminator path $this and must be the only slicing.discriminator entry, while preserving the existing fixed-cardinality rule.

Recommendation:
Keep this commit as a source fix. It narrows the current R5/R6 guidance to the exact constraints approved for FHIR-26944 and avoids broader changes such as adding a formal invariant, which would need a separate work-group/tooling decision.
