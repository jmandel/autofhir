FHIR-17447: Restore search response expectations

Issue request:
FHIR-17447 was a Published/Persuasive FHIR-I change request for the FHIR-core search page. It asked the specification to make explicit that a query response cannot be subdivided into separate sub-Bundles and that search responses can include resources that are not hosted/readable through the responding server.

Initial application:
The issue was initially applied by svn r14257 in git commit 5d9f0714c67b0b73079017756ca207f3d36411f9, which added paragraphs to source/search.html saying returned search Bundle resources could include non-read/vread resources and that a search result Bundle contains only one set of results. The later 2022 search page rewrite in commit 36e9fd596f144835ac237e7f8ef619656091f29f6 removed those explicit paragraphs while reorganizing the page.

Additional context:
The original Zulip thread confirms the two decisions: nested search result Bundles were rejected, and FHIR resources generated from non-FHIR/non-readable back-end data were allowed. The current build includes source/search.html through the active Search=search.html entry in source/fhir.ini, and no Confluence reference or later conflicting Jira decision was found during this bounded check.

AutoFHIR reconciliation:
This commit restores the missing current-build clarification in the Search Responses section. It states that servers MAY include resources not available through read or vread interactions, and that a search response is one result set in a single searchset Bundle rather than nested searchset Bundles representing alternatives. It also clarifies that a returned Bundle resource remains an ordinary match or include entry in the same result set.

Recommendation:
Keep this commit as-is. It is a focused restoration of the accepted FHIR-17447 guidance after a later page rewrite dropped the explicit wording, and it avoids reviving the obsolete malformed markdown link from the original 2018 paragraph.
