FHIR-52968: Align Composition invariant fixtures with CodeableConcept relatesTo.type

Issue request:
FHIR-52968 was Applied/Persuasive for R6 by Structured Documents. It requested changing Composition.relatesTo.type from code with a required binding to CodeableConcept with an extensible binding to http://terminology.hl7.org/ValueSet/artifact-relationship-type.

Initial application:
The main StructureDefinition was updated by 7c0eccb7ae to make Composition.relatesTo.type CodeableConcept and extensible, and 2644684f6c/d1aeb68743 updated the main Composition example. Later invariant-test fixture commits 0cb437f657, 2abb9267b5, and 061a508e39 added or copied Composition invariant examples that still serialized relatesTo.type as a primitive code, so part of the active Composition source folder still reflected the pre-FHIR-52968 shape.

Additional context:
FHIR-49759 is the same Composition.relatesTo change family: it changed relatesTo from RelatedArtifact to a BackboneElement with type and target children, initially using code/required before FHIR-52968 revised that type and binding. Structured Documents minutes from 2025-09-25 record the rationale for using CodeableConcept/extensible after moving the artifact relationship terminology to THO. source/fhir.ini lists composition=Composition in the active [resources] section, and the invariant fixtures live under that active Composition source folder rather than in generated output.

AutoFHIR reconciliation:
This commit updates all eight source/composition/invariant-tests Composition fixtures so their relatesTo.type values are CodeableConcepts containing artifact-relationship-type codings for replaces and appends. It does not modify the already-correct StructureDefinition, main example, or generated-looking SVG.

Recommendation:
Keep this commit as-is. It completes the FHIR-52968 application for Composition source fixtures and avoids invariant examples failing or passing for the wrong datatype reason after the R6 type change.
