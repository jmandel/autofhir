FHIR-5498: Correct Attachment empty-content wording

Issue request:
FHIR-5498 was a Published/Persuasive DSTU1 MnM ballot issue for the Attachment datatype. It objected that the empty Attachment guidance referred to content being unavailable "for the reason stated" even though Attachment had no reason property, and the approved resolution was to fix the language so the assertion depends on the language and MIME/content type combination rather than a reason.

Initial application:
The Jira comments cite SVN revision 4533. In the git-svn history, commit d8c3b09240e38503a709e6540aea5782e76cc4f7 corresponds to build@4533 and changed the Attachment paragraph from "for the reason stated" to a language/content-type combination. A later datatype documentation update, 5ae1eebfcac2835ff22fdbbc1cdfb452b33ab838, converted the surrounding narrative to the current Attachment.contentType terminology but left this sentence with the obsolete coded name mimeType.

Additional context:
source/fhir.ini routes datatypes through datatypes.html, so source/datatypes.html is active source for the current build. FHIR-5499 reviewed the same empty Attachment behavior and was resolved no-change, so this reconciliation preserves the assertion that an empty Attachment can indicate unavailable content rather than removing the paragraph.

AutoFHIR reconciliation:
Updated the active Attachment constraints paragraph to say that, when neither data nor URL is provided, no content is available for the specified contentType, language, or the combination of both. This removes the obsolete mimeType element reference and keeps the FHIR-5498-approved semantics without reintroducing a non-existent reason property.

Recommendation:
Keep this commit as-is. It is a narrow source correction in the active datatype narrative and does not require a broader change to Attachment cardinalities or empty Attachment behavior.
