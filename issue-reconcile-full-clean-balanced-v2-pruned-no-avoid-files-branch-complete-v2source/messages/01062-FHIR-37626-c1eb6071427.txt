FHIR-37626: Clarify validate resource-type endpoints

Issue request:
FHIR-37626 is a Published/Persuasive FHIR-I technical correction for R5 asking the Resource $validate operation page to stop implying that type- and instance-level invocations use literal /Resource endpoints. The issue requested examples like [base]/[resourceType]/$validate and [base]/[resourceType]/[id]/$validate instead of [base]/Resource/$validate and [base]/Resource/[id]/$validate.

Initial application:
No source commit explicitly mentioning FHIR-37626 was found. The current generated formal OperationDefinition narrative still renders URL lines with Resource in the path, and the current source did not include local Resource.$validate prose explaining that those type and instance paths require a concrete resource type. Later validate-operation work added system-level support and a summary table, but did not remove the ambiguity on the formal operation page.

Additional context:
The original Zulip thread confirms the intended interpretation: Resource was meant as a resource type placeholder, not the literal endpoint. Later FHIR-41356 added valid system-level [base]/$validate support, so the reconciliation must not say that every $validate invocation requires a resource type. FHIR-41357 added the current system/type/instance matrix and is already represented on the combined branch. The edited file is build-scope source because Resource is an active infrastructure resource in source/fhir.ini and source/resource/list-Resource-operations.xml references OperationDefinition/Resource-validate.

AutoFHIR reconciliation:
This commit adds a targeted clarification to source/resource/operationdefinition-Resource-validate.xml in both the generated footer markdown and the OperationDefinition comment. The new text states that type- and instance-level invocations use a concrete resource type such as [base]/Patient/$validate or [base]/Patient/[id]/$validate, and that abstract Resource does not define literal /Resource/$validate or /Resource/[id]/$validate endpoints. This preserves later system-level [base]/$validate support while fixing the ambiguity raised by the issue.

Recommendation:
Keep this source fix. A future publisher-level improvement could render abstract Resource operations directly as [ResourceType] in the generated URL list, but the current source clarification is necessary and safe for the present build.
