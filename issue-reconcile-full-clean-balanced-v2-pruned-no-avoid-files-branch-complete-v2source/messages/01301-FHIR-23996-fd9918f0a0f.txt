FHIR-23996: Clarify deleted-resource 410 guidance

Issue request:
FHIR-23996 was Published with a Persuasive with Modification resolution for the FHIR-core HTTP page. It asked that deleted-resource read guidance stop implying that a deleted resource always returns 410, because policy or security requirements may require treating it like a resource that never existed, and the resolution called for pointing to Access Denied guidance.

Initial application:
The issue appears to have been partially applied by git commit 639dbcd2848776be444488fe66b23438c581256d, which changed the delete interaction to say 410 is returned when the server wishes to indicate deletion and linked to Access Denied handling. That commit also touched the read and vread text, but left the read note saying a deleted resource returns 410 and the vread paragraph saying the server should return 410.

Additional context:
source/http.html is the active RESTful API (HTTP) source page linked from source/documentation.html. The current delete, delete-history, and delete-history-version sections already use the weaker "when the server wishes" / Access Denied framing, and source/security.html explains that Access Denied response choices are policy- and context-controlled, including returning 404 to avoid data leakage. Direct Zulip and Confluence searches for FHIR-23996 found no community record that changed the Jira/source conclusion.

AutoFHIR reconciliation:
This commit updates the read note and vread deleted-version guidance in source/http.html to state that 410 Gone is used when the server wishes to indicate deletion, while allowing policy/security-driven treatment as unknown or another Access Denied response. The status-code summary table was not changed because it correctly lists 410 as a possible read/vread response rather than a mandatory one.

Recommendation:
Keep this source fix as-is. It completes the published Jira decision in the current build without changing the broader delete semantics or requiring further work-group review.
