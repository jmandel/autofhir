FHIR-28193: Correct PlanDefinition apply intent wording

Issue request:
FHIR-28193 was Published/Persuasive for R5 and asked that PlanDefinition and ActivityDefinition $apply documentation say to set request intent to option, not status to option, because request status value sets do not contain option.

Initial application:
The Jira-tagged commit 7eea3aced6 added the ActivityDefinition $apply step to set target resource intent to option. The PlanDefinition narrative had already been reworked by FHIR-33169 to use intent for the target resource and RequestOrchestration, but it left the explanatory note saying the ActivityDefinition/$apply operation might not produce the resource with "this status."

Additional context:
PlanDefinition and ActivityDefinition are active current-build resources in source/fhir.ini. FHIR-33169 later replaced the old RequestGroup/CarePlan-oriented PlanDefinition $apply flow with RequestOrchestration/Bundle semantics, so the current reconciliation should preserve that later model while removing the leftover status-vs-intent ambiguity. Quoted Zulip and Confluence searches for FHIR-28193 found no conflicting community evidence.

AutoFHIR reconciliation:
Changed source/plandefinition/plandefinition-notes.xml so the note says ActivityDefinition/$apply might not produce the resource with this intent, matching the immediately preceding intent=option requirement and the published FHIR-28193 decision.

Recommendation:
Keep this source fix. It is a narrow correction in build-scoped PlanDefinition narrative that completes the status-to-intent cleanup without reopening the later FHIR-33169 $apply semantics.
