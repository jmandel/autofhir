FHIR-30515: Align $translate dependsOn value types

Issue request:
FHIR-30515 was Published/Persuasive for R5 and asked ConceptMap/$translate to expose the ConceptMap target.dependsOn information in each output match, alongside the related match.product corrections from FHIR-28284. The final resolution added match.dependsOn with property/value sub-parts, required the value to support the same polymorphic choices used for ConceptMap dependsOn/product values, and noted that OperationDefinition needed allowed-type support.

Initial application:
Commit 3a8665b9c2 added match.dependsOn and changed match.product for the original R5 ConceptMap work, and later ConceptMap2-to-ConceptMap and OperationDefinition refactors converted the value choices to allowedType. The source therefore already exposed match.dependsOn, but later model changes left the match.dependsOn.value allowedType list stale while match.product.value and dependency.value had been updated.

Additional context:
ConceptMap is active in source/fhir.ini and source/conceptmap/list-ConceptMap-operations.xml includes OperationDefinition/ConceptMap-translate, so the operation definition is in current build scope. FHIR-40504 split mapping properties from source/target additional attributes and made the current ConceptMap additional-attribute value set code, Coding, string, boolean, Quantity; the already-published FHIR-33032 reconciliation added id. In current source, ConceptMap.group.element.target.product inherits the dependsOn backbone by contentReference, and match.product.value already matched that active model, but match.dependsOn.value still listed integer, dateTime, decimal, and uri and omitted Quantity.

AutoFHIR reconciliation:
Updated source/conceptmap/operationdefinition-ConceptMap-translate.xml so match.dependsOn.value allows code, Coding, string, boolean, Quantity, and id, matching ConceptMap.group.element.target.dependsOn.value[x], ConceptMap.group.element.target.product, dependency.value, and match.product.value.

Recommendation:
Keep this source fix. It completes the already-applied FHIR-30515 output parameter by aligning the active $translate dependsOn response surface with the current ConceptMap additional-attribute model and does not reopen related ConceptMap policy decisions already represented by FHIR-40504 and FHIR-33032 commits.
