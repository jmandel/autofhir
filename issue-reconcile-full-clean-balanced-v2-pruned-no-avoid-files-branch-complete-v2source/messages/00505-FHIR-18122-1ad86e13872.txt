FHIR-18122: Add Coverage exception authorizer

Issue request:
FHIR-18122 was a Published/Persuasive with Modification FHIR-core Coverage change request, raised and applied for STU3. It requested support for copayment exceptions by adding Coverage.costToBeneficiary.exception 0..* with a required type CodeableConcept, an optional validity period, and an optional reference to the authorizer/source of the exception.

Initial application:
Coverage is an active current-build resource through source/fhir.ini. Commit 7fbe7046270ff6857644a6af63207642576dc7ef explicitly included #18122 and added Coverage.costToBeneficiary.exception, its type and period children, example financial-exception terminology, and an example instance. The source migration commits preserved type and period, but no source or git-history evidence showed the requested authorizer child ever being added.

Additional context:
Later terminology cleanup moved the example financial-exception code system out of core while retaining the active value set reference. FHIR-27024, already represented on the combined branch, relies on Coverage.costToBeneficiary.exception and adds the value-or-exception invariant without changing the exception child list. Targeted Jira, Zulip, and Confluence searches found no later decision reversing the FHIR-18122 authorizer/source requirement. The Jira text used ProviderRole, which is not an active current-build resource; PractitionerRole is the current available role resource alongside Organization.

AutoFHIR reconciliation:
Added Coverage.costToBeneficiary.exception.authorized as an optional Reference(PractitionerRole|Organization) in source/coverage/structuredefinition-Coverage.xml. This completes the missing authorizer/source part of the published resolution in the authoritative current Coverage StructureDefinition source.

Recommendation:
Keep this commit as the completion of the applied FHIR-18122 change. If Financial Management wants a different element name or target-resource set than the historical authorizer/source request, handle that as a new forward-looking Jira decision.
