FHIR-13399: Clarify profile discriminator example

Issue request:
FHIR-13399 was Published with a Persuasive with Modification resolution for FHIR-core ElementDefinition/StructureDefinition. It asked for targetProfile slicing by profile and for profile slicing to be clarified as validation against the relevant profile, not merely checking Resource.meta.profile.

Initial application:
The issue was applied in svn revision 13385, represented in git as d4d7fd1550c21ef9786b82d8f86b40fff78ae1b9. That commit updated the DiscriminatorType.profile definition in source/datatypes/elementdefinition.xml to say that a .resolve() path uses the reference targetProfile and requires validation by the possible profiles, but the active profiling example still described the profile discriminator as a "profile tag" on the target reference.

Additional context:
source/datatypes/elementdefinition.xml is active normative ElementDefinition source through source/fhir.ini, and source/profiling.html is an active built narrative page through source/hierarchy.xml. Later FHIR-23035 work on the same profiling page clarified resolve()/targetProfile behavior without reversing FHIR-13399. Zulip discussion around slicing by target profile quoted the old "profile tag" wording and separately discussed meta.profile as only a workaround, confirming that the remaining example wording could mislead readers.

AutoFHIR reconciliation:
This commit updates the List.entry profile-discriminator example in source/profiling.html to say entries are differentiated by whether the target resource conforms to the profile declared for the slice's item reference. It leaves the DiscriminatorType.profile code definition unchanged because it already contains the requested targetProfile and validation language.

Recommendation:
Keep this source change. It removes a stale meta.profile/tag implication from an active narrative example while preserving the already-applied ElementDefinition code semantics; no broader discriminator model change is needed for this issue.
