FHIR-41688: Fix Range composite POST example

Issue request:
FHIR-41688 was Applied/Persuasive with Modification for R6 by FHIR-I. It asked the specification to define search behavior for Range-typed data, with the final decision to use composite search parameters rather than introduce a new range search type, modifier, or delimiter. The resolution specifically called for object-level joining when a composite parameter references the same underlying Range search parameter more than once, and for examples that distinguish explicit Range boundaries from ordinary repeated-parameter set joins.

Initial application:
The current combined branch already contains source commit 10af8c0a5aff3957b36d6c901af64f0d577e1877, "FHIR-41688 - Document composite search for Range datatypes", which added the generic Range/composite guidance to source/search.html but did not include an Issue-Reconcile-Key trailer. That source change correctly added the special Range-search section and same-Range-instance semantics, but its POST form of the new example used the reversed value-range-values=le20$ge30 body while the GET form and explanation used ge20$le30.

Additional context:
The linked Zulip thread shows the original Group.characteristic valueRange use case and implementer feedback preferring, or at least tolerating, the composite-parameter approach instead of a new search syntax. FHIR-I minutes on 2025-03-24 record the 13-0-0 motion that FHIR-41688 can be handled with composite parameters and that the Zulip discussion showed no interest in a new search parameter type. A later 2025-04-14 FHIR-I discussion of FHIR-40341 is related but distinct: it concerns resource-specific Group search parameters and quantity/type-mapping details, so it is not decided by this FHIR-41688 commit.

AutoFHIR reconciliation:
Updated source/search.html so the POST body for the Range composite example matches the GET query and the accompanying explanation: value-range-values=ge20$le30. This is a source-changing reconciliation because the mismatched POST example would otherwise teach the opposite boundary order from the surrounding normative-style guidance. No broader edits were made because the current search page already contains the approved composite-parameter behavior for Range searches.

Recommendation:
Keep this commit as-is. It completes the FHIR-41688 reconciliation by preserving the applied composite Range guidance while fixing the contradictory example. Handle any Group-specific or additional resource-specific Range search parameters under their own Jira issues, such as FHIR-40341, rather than broadening this seed.
