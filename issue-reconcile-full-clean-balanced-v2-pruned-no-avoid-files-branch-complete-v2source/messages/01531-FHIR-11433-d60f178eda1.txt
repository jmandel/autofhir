FHIR-11433: Clarify direct REST workflow requests

Issue request:
FHIR-11433 was a Published/Persuasive FHIR-core workflow clarification asking why workflow communication options were focused on fulfillment rather than also recognizing status changes. The approved resolution said to revamp the wording to reflect that status changes are possible too.

Initial application:
The issue was initially applied in git commit 839bf586d6c1cf9a322e122852f0cc49bcfed263, which added the communication-pattern convention saying most patterns also apply to status changes and information requests, while limitations should identify narrower patterns. After the later workflow-page split, that wording lives in source/workflow-communications.html, and Task-based options in source/workflow-management.html already say they can request status changes or other updates.

Additional context:
The ad-hoc workflow pages are active build inputs through source/hierarchy.xml and publish.ini. A remaining Option A limitation in source/workflow-ad-hoc.html still said simple RESTful POST or PUT only worked for fulfillment requests and could not handle state changes or information, despite the same option allowing create, update, or operation invocation and despite the FHIR-11433 convention. Generic Zulip and Confluence searches found no community evidence that narrows or reverses the Jira decision.

AutoFHIR reconciliation:
This commit changes the Option A limitation to say fulfillment, status changes, information requests, or other actions fit the simple REST pattern only when they can be expressed as the direct create, update, or operation invocation. This keeps the limitation on synchronous/direct REST interactions while removing the stale fulfillment-only statement.

Recommendation:
Keep this source fix. It is a narrow correction to an active workflow page and aligns the remaining Option A wording with the already-applied FHIR-11433 clarification without reopening broader workflow-pattern design questions.
