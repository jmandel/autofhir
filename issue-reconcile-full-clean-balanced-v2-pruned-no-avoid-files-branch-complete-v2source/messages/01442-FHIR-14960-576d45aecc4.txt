FHIR-14960 + FHIR-51046: Clarify operation HTTP method support

Attribution note: surfaced while reviewing FHIR-14960, but direct Jira backing for this change is FHIR-14960 + FHIR-51046.

Issue request:
FHIR-14960 was Published/Persuasive with Modification for FHIR-core OperationDefinition in STU3. It asked the OperationDefinition.affectsState definition and the Operations execution page to clarify supported HTTP methods: servers SHALL support POST for all operations, and servers SHALL support GET for non-state-affecting operations when the parameters can be represented in the URL, while rejecting a separate hybrid CapabilityStatement variance rule.

Initial application:
The Jira application comment records svn revision 14052. Git commit 4522f03c9617ba7df0907489136e0e449432c8dc, "GF#14960 - clarification of OperationDefintion.affectsState", applied the issue to the then-authoritative OperationDefinition spreadsheet by adding the POST/GET bullets, and that content was later migrated into source/operationdefinition/structuredefinition-OperationDefinition.xml. The same commit did not update source/operations.html, leaving the Operations request section with weaker POST wording.

Additional context:
The linked 2018 Zulip thread records the implementation question that led to the tracker: Grahame stated servers SHALL support POST for all operations and SHALL support GET for affectsState=false, while Eric identified the mismatch between OperationDefinition and the Operations page. Later FHIR-18197 removed the misleading idempotent reference from affectsState, FHIR-36265 clarified that the affectsState=false condition applies to the GET rule, and FHIR-51046 updated the built Operations page from a primitive-only GET criterion to the current search-type criterion. FHIR-36265 and FHIR-51046 are already represented on the combined branch, so this commit does not publish duplicate decisions for them.

AutoFHIR reconciliation:
This commit completes the seed across the current build-scope sources. It makes source/operations.html explicitly say that servers SHALL support POST invocation for all operations, and it aligns the OperationDefinition.affectsState comment with the later Operations-page search-type criterion while preserving the FHIR-36265 affectsState=false disambiguation. source/hierarchy.xml includes operations.html, and source/fhir.ini actively lists operationdefinition=OperationDefinition, so both edited files feed the current build.

Recommendation:
Keep this source fix. It resolves the seed's missing Operations-page POST mandate and removes a stale primitive-only OperationDefinition criterion that would otherwise contradict later applied Operations-page guidance. Do not create additional commits for FHIR-36265 or FHIR-51046 in this run because both already have reconcile commits on the combined branch.
