FHIR-12719: Clarify ConceptMap priority mapping

Issue request:
FHIR-12719 was Published/Persuasive for R5 and asked ConceptMap to address priority when one source concept maps to multiple targets. The approved resolution called for an example and explicit ConceptMap text, using a priority property with an integer value rather than implying priority from ordering.

Initial application:
No source commit explicitly mentioning FHIR-12719 was found. The change appears to have been partially applied by a8814f0161, which added a ConceptMap priority example using product.property="priority" and valueInteger rankings, after Vocab minutes recorded that an example was needed. Later R5 ConceptMap property work in cebd9afb99 and 0de5092965 refactored the model so this use case belongs on ConceptMap.group.element.target.property, but the example's priority values had been converted to strings and the grouping notes still said duplicate groups might maintain a fixed order.

Additional context:
FHIR-25935 is a duplicate of FHIR-12719 for target ranking. FHIR-28284 made dependsOn/product values choice-typed, and FHIR-39151/FHIR-40504 later distinguished additional attributes from mapping properties; FHIR-40504 specifically identified priority as a property of the mapping itself, not a product of the translation. ConceptMap is in the active build via source/fhir.ini, and list-ConceptMap-examples.xml includes the priority example.

AutoFHIR reconciliation:
Updated the ConceptMap notes to state that group, element, and target order does not indicate priority and to direct readers to an integer priority mapping property. Updated conceptmap-example-priority.xml so the priority property declares type integer and uses valueInteger values, matching the original FHIR-12719 intent through the current FHIR-40504 ConceptMap.property model.

Recommendation:
Keep this source fix. It corrects a misleading ordering hint and restores integer priority values in the active ConceptMap example without changing the later mapping-property model.
