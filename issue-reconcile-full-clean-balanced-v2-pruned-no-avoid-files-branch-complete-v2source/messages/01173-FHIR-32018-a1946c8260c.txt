FHIR-32018: Clarify _id search support discretion

Issue request:
FHIR-32018 was a Published/Persuasive with Modification FHIR-core search-page issue for R5. It asked to remove ambiguity from the search parameters section that had said servers need not implement standard search parameters "except" `_id`, replacing that apparent requirement with guidance that servers SHOULD support `_id`.

Initial application:
The issue was applied through PR 1799 and commit 82418ca8e77ceefa65a24270427f91e0a7d64f6e, which changed the main `source/search.html` parameters paragraph from the old exception wording to a SHOULD-support statement for `_id`. Later conformance-language cleanup in a3766ac36c61fa3448d53aca0519dcbd874cfc93 preserved the SHOULD guidance and wrapped it as conformance text. A legacy summary bullet in the same active search page still said servers can choose supported parameters "other than `_id` above," leaving the original ambiguity partially present.

Additional context:
The originating Zulip thread shows the ambiguity: participants disagreed whether `_id` was mandatory, and Lloyd McKenzie asked for a change request to clarify. FHIR-I WGM minutes for 2021-09 record the approved direction as clarifying "SHOULD support search by _id" and explicitly state this was not a change of standard requirement. Current `source/search.html` already contains the approved SHOULD sentence in the authoritative parameters section, so only the stale nearby discretion summary needed correction.

AutoFHIR reconciliation:
Updated `source/search.html` so the server-discretion bullet says servers can choose which parameters to support and points to the `_id` recommendation above, rather than carving `_id` out as if it were mandatory. No other search behavior or conformance expectation was changed.

Recommendation:
Keep this commit as-is. It completes the approved clarification on the active search page by removing the remaining misleading exception-style wording while preserving the SHOULD-level `_id` recommendation.
