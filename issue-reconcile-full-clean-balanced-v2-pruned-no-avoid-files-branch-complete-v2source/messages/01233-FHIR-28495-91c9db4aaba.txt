FHIR-28495: Correct If-None-Match update guidance

Issue request:
FHIR-28495 was Published with a Persuasive with Modification resolution. It asked the HTTP page to support `If-None-Match: *` on `PUT [type]/[id]` so a client can create a resource with a client-specified id while ensuring an existing resource is not replaced. The approved resolution also noted that servers may support only the wildcard form for this use case; later Jira/meeting notes deferred the separate discovery mechanism to CapabilityStatement2 work.

Initial application:
The issue was initially applied by git commit 22e27816418f62634685e937808236683070c101, which added `If-None-Match` prose to `source/http.html`. That application placed the rule under the conditional update interaction and described an ETag-specific `W/"[ETag]"` example before the wildcard case. Later source edits corrected nearby wording but left the guidance attached to conditional update instead of the approved `PUT [type]/[id]` update-as-create use case.

Additional context:
The original Zulip thread and FHIR-I minutes both frame the change as an idempotent client-assigned-id create using `PUT Patient/123` with `If-None-Match: *`. `source/http.html` is in the current build through `publish.ini`. A 2022 FHIR-I note and the Jira comment say CapabilityStatement discovery should be handled by a new CapabilityStatement2 tracker rather than by reopening FHIR-28495. Later transaction-Bundle questions about `Bundle.entry.request.ifNoneMatch` did not surface a final Jira decision, so this reconciliation keeps the source change bounded to the approved HTTP interaction text.

AutoFHIR reconciliation:
This commit moves the substantive guidance to the Update as Create section of `source/http.html`, states the `If-None-Match: *` precondition and 412 failure behavior when the resource already exists, records that servers may support only the wildcard variant for update-as-create, removes the misplaced conditional-update ETag paragraph, and updates the HTTP header and request summary tables to point to and list the update usage.

Recommendation:
Keep this commit as the core FHIR reconciliation for FHIR-28495. If the work group wants transaction Bundle `ifNoneMatch` behavior or explicit CapabilityStatement2 discovery for wildcard-only update support, handle that as a separate scoped tracker because the available evidence does not show a final decision for those surfaces under FHIR-28495.
