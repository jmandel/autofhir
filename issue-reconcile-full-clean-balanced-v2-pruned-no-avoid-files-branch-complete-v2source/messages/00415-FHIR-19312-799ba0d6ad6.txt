FHIR-19312: Document X-Consent header on Consent page

Issue request:
FHIR-19312 was an Applied FHIR-core change request for the Security/CBCP area, resolved Persuasive with Modification, asking the Consent page to document an optional X-Consent HTTP header. The final request defined the header value as a URI to consent material and called out client assertion responsibility, server authorization responsibility, applicability across REST verbs, optional server support, retrieval/rejection behavior, short-lived caching or freshness handling, possible use of async responses, and no discovery or CapabilityStatement mechanism.

Initial application:
No prior source application was found in the current repository history. Searches for FHIR-19312 and X-Consent in git history and current source found no Jira-tagged commit or existing source text, and spot checks of R4, R5, and current published Consent/Security pages also found no X-Consent wording. The active fhir.ini entries show Consent is part of the current build and belongs to the security work group.

Additional context:
The linked Zulip discussions immediately after the vote clarified that X-Consent is an optional request mechanism, not a mandate, for communicating consent material a requester believes applies to the transaction. They also narrowed the request use case, rejected using the response direction for this header, and favored cache validation/freshness such as ETag rather than inventing broad authorization behavior. Confluence minutes list the San Antonio WGM session where GF#19312 was discussed, and no later final Jira issue was found that supersedes this applied decision.

AutoFHIR reconciliation:
Added an X-Consent Header section to source/consent/consent-notes.xml, an authoritative Consent resource note that is in build scope. The text defines the header as a URI-valued request header, gives Consent/Binary/PDF examples, states client and server responsibilities, documents optional server support and rejection when the material cannot be retrieved or verified, notes applicability to all RESTful interactions with primary usefulness for query/retrieve, points to the async request pattern, and captures cautious short-lived/validated caching with revocation awareness. No generated artifacts or unrelated HTTP header tables were changed.

Recommendation:
Keep this source change as the missing application of FHIR-19312. If the work group later wants a precise header-parameter grammar for cache TTL or a CapabilityStatement discovery surface, that should be handled as a separate change request because FHIR-19312 explicitly left discovery unresolved and the post-vote discussion did not establish a stable syntax.
