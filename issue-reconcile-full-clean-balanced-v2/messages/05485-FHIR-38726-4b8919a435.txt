FHIR-38726: Audit uncertain date extension disposition

Issue request:
FHIR-38726 is a Published/Persuasive with Modification FHIR-core change request asking for support for imprecise dates on resources such as Condition, AdverseEvent, MedicationStatement, and Procedure. The final resolution said to define uncertain extensions for the date, dateTime, and time data types with upper/lower bounds when an exact value is not known.

Initial application:
Commit 5436c013 added an uncertainPeriod row to the active core element-extensions spreadsheet, with contexts date and dateTime and value type Period. That captured the date/dateTime range idea but did not add a primitive time context or separate uncertainDate/uncertainDateTime/uncertainTime definitions. Commit dd468d4 later removed extension definitions from the R5 core source as part of moving standard extensions out of this checkout.

Additional context:
The current core build still includes source/profiles/element-extensions-spreadsheet.xml from source/fhir.ini, but that active spreadsheet no longer contains uncertainPeriod or uncertainTime rows; core only retains OID registry lines for uncertainPeriod and the older timing-uncertainDate. The surviving definitions are in the FHIR Extension Pack: uncertainPeriod is scoped to date and dateTime and uses valuePeriod, and FHIR-41649 later deprecated timing-uncertainDate in favor of uncertainPeriod. Zulip and FHIR-I minutes after the initial application record that the issue did not cover the full intended scope, raised the descriptive-versus-prescriptive uncertainty distinction, and said to pull the work out of R5 for later discussion. The tightly related FHIR-39336 time-bound issue is already represented on the combined branch with a human-review audit commit.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Reintroducing extension definitions in core would edit an artifact family that now belongs in the Extension Pack, and adding the missing time semantics would require a work-group design decision that the later community evidence shows was unresolved.

Recommendation:
Keep this audit commit as a human-review marker. FHIR-I should decide in the Extension Pack whether uncertainPeriod remains the intended date/dateTime solution and whether a separate time-only or Timing-specific extension is needed; core should only be changed later if the work group asks for current-spec narrative guidance or registry updates in this checkout.
