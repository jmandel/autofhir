FHIR-19422: Correct specimen container type value set

Issue request:
FHIR-19422 was a Published/Persuasive with Modification OO change request for R5 asking that SpecimenDefinition.typeTested.container.type use a specimen-container value set based on SNOMED CT descendants of 706041008 |Device for body fluid and tissue collection/transfer/processing (physical object)|, with title/name/definition corrected away from the old LOINC cholesterol example.

Initial application:
No explicit FHIR-19422-tagged source commit was found. Git history shows commit 0fe60a4236d65f04316982ed97e7c352497bbc57 replaced the original LOINC cholesterol example value set under source/specimendefinition with a SNOMED CT include rooted at 706041008, but it left the title/name generic and the definition partly copied from a patient-preparation value set. Later source also contained a second source/specimen copy of the same canonical ValueSet/specimen-container-type rooted at 434711009, and the current CI build was publishing that stale copy.

Additional context:
Specimen and SpecimenDefinition are both active resources in source/fhir.ini. The current SpecimenDefinition structure definition binds SpecimenDefinition.typeTested.container.type to http://hl7.org/fhir/ValueSet/specimen-container-type and describes the intended 706041008 descendants. OO minutes from 2021-04-12 record that the value set had already moved to SNOMED CT but needed its definition updated to the Jira-listed root, and the 2021-04-29 OO block vote accepted FHIR-19422 as persuasive with modification/pre-applied. The later FHIR-49741 R6 Specimen.container remodel removes Specimen.container.type from the active Specimen structure, but it does not change the SpecimenDefinition binding or the canonical value set definition.

AutoFHIR reconciliation:
This commit updates both build-scoped source copies of ValueSet/specimen-container-type so their name, title, description, and SNOMED CT filter agree with the FHIR-19422 decision. Updating both copies is necessary because build.fhir.org was selecting the source/specimen copy for the canonical page even though SpecimenDefinition binds to the same canonical URL.

Recommendation:
Keep this source fix as-is. A future cleanup may remove or consolidate the duplicate source/specimen value-set file if the publisher no longer needs it, but the current reconciliation should preserve both files and align their canonical content so the built specification is not dependent on source selection order.
