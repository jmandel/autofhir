FHIR-22105: Allow preferred NamingSystem ids by period

Issue request:
FHIR-22105 was Published as Persuasive with Modification for R5. It asked to change NamingSystem invariant nsd-2 so that multiple preferred identifiers of the same type can be distinguished by their validity period, and to make $preferred-id date-aware.

Initial application:
Commit 25159ea161eaed360cf05d040c52d38e80cdcbac listed FHIR-22105 among broad NamingSystem R5 updates, but it only moved the existing nsd-2 expression and kept uniqueId.where(preferred = true).select(type).isDistinct(), so the constraint still rejected the reported period-based use case. Later commits b709f1aec3008d932753b1a0ac53f60235208aa0 and c7583c6f60f457f2a14238a80e83113fa2e7c3cc made $preferred-id date-aware under follow-up Jira issues.

Additional context:
NamingSystem is active in source/fhir.ini, so source/namingsystem/structuredefinition-NamingSystem.xml and its invariant fixtures feed the current build. FHIR-37673 superseded the originally proposed input name by choosing the operation parameter name date and added the SHOULD NOT overlap by period note; FHIR-43169 confirmed the current nsd-3 type/start/end period-combination FHIRPath pattern. Confluence minutes and the archived deprecated-identifier policy both confirm that the intended rule is one preferred identifier per type for a given period, not one preferred identifier per type across all time.

AutoFHIR reconciliation:
Updated nsd-2 to compare preferred identifiers by type plus period.start plus period.end, updated the human-readable invariant text, added nsd-2 as a condition on NamingSystem.uniqueId.period, and added a passing invariant fixture with two preferred identifiers of the same type in distinct periods.

Recommendation:
Keep this source fix. It removes the stale over-restrictive invariant while preserving the current date-aware $preferred-id behavior and the later guidance that preferred identifiers for the same type should not overlap by period.
