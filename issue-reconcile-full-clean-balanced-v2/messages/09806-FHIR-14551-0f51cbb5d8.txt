FHIR-14551: Audit batch transaction wording

Issue request:
FHIR-14551 was a Published/Persuasive STU3 FHIR-I change request for the RESTful API batch/transaction section. It asked the paragraph describing the submitted Bundle to state request optionality unequivocally in light of FHIR-14550 and to avoid implying that transaction entries are processed independently like batch entries.

Initial application:
The issue appears to have been applied by git-svn commit ffbcccb1db3608f46cc6d70fb5982c45144f5814, which records svn revision 14049 and mentions GF#14551. That commit changed source/http.html to say each entry SHALL carry Bundle.entry.request details, removed the optional-request note, and added the distinction that batch entries are individual interactions while transaction interactions either succeed or fail together.

Additional context:
The current build includes source/http.html as the RESTful API page through source/hierarchy.xml. The current batch/transaction text still contains the applied SHALL request-details language and now also introduces batch as independent actions versus transaction as a single atomic set before reiterating the batch/transaction distinction in the submitted-Bundle paragraph. FHIR-14550 is the supporting published decision that made request mandatory for transaction and batch bundles; current batch and transaction Bundle profiles require Bundle.entry.request for the method slices. Direct Zulip and Confluence searches for FHIR-14551 found no contrary community discussion.

AutoFHIR reconciliation:
This audit commit makes no source changes. The current RESTful API source already conveys the issue's required behavior: request details are mandatory for batch/transaction entries, PUT and POST entries carry a resource body, batch entries are treated like individual interactions or operations, and transaction interactions succeed or fail together.

Recommendation:
Keep this no-change audit commit as-is for FHIR-14551. No follow-up source edit is needed for this issue; FHIR-14550 remains a closely related request-mandatory decision but is not separately decided here.
