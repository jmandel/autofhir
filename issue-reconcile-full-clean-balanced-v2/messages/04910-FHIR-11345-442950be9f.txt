FHIR-11345: Audit CarePlan prohibited reason wording

Issue request:
FHIR-11345 was a Published/Not Persuasive with Modification CarePlan change request asking to add CarePlan.activity.detail.prohibited.reason. The accepted resolution rejected a separate element and instead required the CarePlan.activity.detail.reasonCode description to explain that the same rationale element also carries the reason an activity was prohibited.

Initial application:
The wording was applied in historical commit bd9f60dbffee762fd2b3e49ee2e07e232b9685a9, which explicitly listed #11345 and changed CarePlan.activity.detail.reasonCode from only "Why activity should be done" to "Why activity should be done or why activity was prohibited," with the matching definition sentence. Later source rebuild/refactor commits carried that applied wording into the current StructureDefinition source.

Additional context:
CarePlan is active in the current build through source/fhir.ini. The current source no longer uses the exact DSTU2 element names: CarePlan.activity.detail.reasonCode is now CarePlan.activity.plannedActivityDetail.reason, represented as a CodeableReference, and CarePlan.activity.detail.prohibited is now plannedActivityDetail.doNotPerform. The current reason element still explicitly covers why an activity was prohibited and maps to Request.reason. Later Jira FHIR-14818 considered whether the same reasonCode element was redundant and was Resolved - No Change, reinforcing that the element has a distinct rationale role.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scoped CarePlan StructureDefinition already implements the approved FHIR-11345 outcome through the current equivalent element, and adding a separate prohibited.reason element would contradict the accepted resolution.

Recommendation:
Keep this no-change audit commit as-is. No follow-up source work is needed for FHIR-11345 unless a future PC decision changes how CarePlan doNotPerform/prohibited rationale should be modeled.
