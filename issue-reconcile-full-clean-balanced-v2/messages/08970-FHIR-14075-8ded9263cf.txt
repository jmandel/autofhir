FHIR-14075: Audit operation GET criteria clarification

Issue request:
FHIR-14075 was a Published/Persuasive with Modification FHIR-I change request for the FHIR-core Operations page. It asked to clarify that operation GET invocation depends on URL-expressible input parameters and on whether the operation affects server state, not on also having a single output parameter named return; the approved modification replaced idempotent wording with the OperationDefinition.affectsState concept and a link to its definition.

Initial application:
The Jira comment records svn revision 14270, which corresponds to git commit c208aebcec645ec8dc393a60cd798908ba57f63c. That commit removed the confusing sentence tying primitive inputs and a single Resource return together, added a separate GET eligibility list, and moved the single-return response statement into its own paragraph. Later commit 1e03edb85ba9a6148f1aab515bd3bd6713029b34 removed an idempotent/HTTP-spec parenthetical from adjacent Operation Request guidance and linked affectsState directly.

Additional context:
source/hierarchy.xml actively includes source/operations.html in the current build, and source/fhir.ini plus source/hierarchy.xml keep OperationDefinition in scope. The current Operations page separates direct return-resource response handling from GET invocation criteria and links to OperationDefinition.affectsState. Later FHIR-51046 changed the older simple/primitive-parameter boundary to the current rule for datatypes with corresponding search types and is already represented on the combined branch, so FHIR-14075 should be read through that later clarification. Later response issues, including FHIR-28292 and FHIR-24869, refined the return-parameter paragraph without re-coupling it to GET eligibility. Zulip searches found historical discussion quoting the old confusing sentence and discussing affectsState, but no community evidence that conflicts with the current source.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The current active source already implements the FHIR-14075 clarification: GET eligibility is stated independently from the single-return response rule, uses affectsState, and has been consistently updated by the later FHIR-51046 search-type clarification.

Recommendation:
Keep this audit commit as-is. No FHIR-14075 source follow-up is needed in core; future work on operation GET behavior should use later issues such as FHIR-51046 rather than restoring the older primitive-only wording.
