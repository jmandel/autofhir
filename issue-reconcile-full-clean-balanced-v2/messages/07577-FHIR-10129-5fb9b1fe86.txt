FHIR-10129: Audit ValueSet filter clarification

Issue request:
FHIR-10129 was a Published/Persuasive with Modification vocab change request for the ValueSet $expand filter parameter. It asked whether the filter definition could be tightened around case sensitivity, punctuation, wildcards, prefix/contains matching, and word order. The final resolution deferred strict standardization to TerminologyCapabilities and said servers can declare their behavior in TerminologyCapabilities.expansion.textFilter while adding documentation around the kinds of text-filter behavior a server may support.

Initial application:
TerminologyCapabilities was added before final publication with an expansion.textFilter element for documenting text-search behavior. The explicit FHIR-10129 application was svn revision 14613, preserved as git commit 4cfb0f493e59259e757035f0908761dfbb470cd2, which added explanatory $expand filter documentation and pointed readers to TerminologyCapabilities.expansion.textFilter. Later source restructuring moved the spreadsheet content into source/valueset/operationdefinition-ValueSet-expand.xml and source/terminologycapabilities/structuredefinition-TerminologyCapabilities.xml while preserving the applied guidance.

Additional context:
source/fhir.ini lists both ValueSet and TerminologyCapabilities as active resources in the current build. The current $expand filter parameter still states that interpretation is server-defined, points to TerminologyCapabilities.expansion.textFilter, and lists typical behaviors such as left matching, wildcard support, searched fields, and search conditions. TerminologyCapabilities.expansion.textFilter also says implementations should document case sensitivity, punctuation handling, wildcards, starts-with versus contains behavior, and word-order handling. Jira, Zulip, and Confluence searches found no later directly relevant decision reversing this approach.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current source already implements the accepted resolution at the active operation-definition and TerminologyCapabilities surfaces. Minor surviving editorial roughness in the $expand prose does not change implementer understanding of the FHIR-10129 decision and is below the source-edit threshold for this reconciliation.

Recommendation:
Keep this no-change audit. If the work group wants to standardize exact text-filter matching semantics rather than document server-specific behavior, open a new terminology issue because that would go beyond FHIR-10129's published resolution.
