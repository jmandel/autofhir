FHIR-18993: Audit subscription subscriber security guidance

Issue request:
FHIR-18993 was Published/Persuasive, applied for R5, and asked the Subscription resource to explicitly address subscriber-side security: using headers or secrets for notification trust, avoiding insecure handling of those values, limiting who can see sensitive Subscription data such as endpoints, and defending subscribers and FHIR servers from fake notifications.

Initial application:
The issue appears to have been initially applied by dbeb5e6a7a, which moved the Subscription safety guidance into source/subscriptions.html while mentioning FHIR#18993, and then by 3a6fa70bed, explicitly titled "FHIR-18994, FHIR-18993, FHIR-19621 - Additional security considerations." That later Jira-tagged commit added HTTPS/rest-hook guidance, sensitivity of Subscription data such as privileged endpoints, and fake-notification denial-of-service guidance. FHIR-39034 later renamed the header mechanism to Subscription.parameter without changing the subscriber-security intent.

Additional context:
FHIR-18994 is a Published companion issue whose resolution says to handle broader Subscription security considerations as part of FHIR-18993. FHIR-19621 is a Duplicate whose resolution says the rest-hook HTTPS warning will be addressed as part of FHIR-18993; the linked Zulip thread discusses REST-hook payload, endpoint trust, TLS/SNI validation, payload minimization, and authorization risk. Subscription, SubscriptionStatus, and SubscriptionTopic are active current resources in source/fhir.ini, and the Subscription resource notes link their Safety and Security section to the Subscriptions Framework page.

AutoFHIR reconciliation:
No source change was needed. The current active Subscriptions Framework page already contains security guidance for authorization at creation and notification time, payload minimization, HTTPS/rest-hook channel security, sensitive Subscription data and privileged endpoints, secrets via Subscription.parameter, validating incoming messages, and fake-notification denial-of-service defenses.

Recommendation:
Keep this empty audit commit as-is. Future changes should only revisit this if the work group wants more specific normative TLS/BCP195 requirements; the current source already covers the Jira's R5 subscriber-side security concerns without duplicating guidance elsewhere.
