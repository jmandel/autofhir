FHIR-5691: Audit delete behavior for non-versioned servers

Issue request:
FHIR-5691 was a Published/Persuasive FHIR-core HTTP change request asking the specification to clarify what a server that does not support versioning is responsible for when it receives a delete request, including whether such a server may actually delete the resource.

Initial application:
The issue was applied by git-svn commit e87ca6573175c7049611dd195ebebef8edb2c4b7, corresponding to svn 4487, which added server-discretion wording to the delete interaction and changed the version-history sentence to apply only to servers that maintain a version history.

Additional context:
The current source/http.html remains an in-build top-level HTTP narrative page. It still says versioning is optional, defines no-version capability behavior, states delete support is at server discretion, limits the version-history retention rule to servers that maintain history, and separately says servers may completely delete a resource and its history when policy or business rules make that appropriate. Later commit 6e6160af87f2dd0c2643631e27b95156ee4c93e8 strengthened the delete-policy caveat; no directly relevant Zulip or Confluence record was found that conflicts with this reading.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current HTTP delete wording already conveys the requested clarification for non-version-capable servers, and adding another note would be redundant rather than corrective.

Recommendation:
Keep this audit commit as-is. No FHIR core follow-up is needed for FHIR-5691 unless the work group later wants a broader policy change to RESTful delete semantics.
