FHIR-3730: Audit operation compatibility guidance

Issue request:
FHIR-3730 was a Published/Persuasive with Modification FHIR-core FHIR-I change request for OperationDefinition and the operations page. It asked how clients and servers should handle optional, required, and later-added operation parameters, and the final decision was to document the safe compatibility rule: after an operation definition becomes stable/normative, operation signatures must not be changed in incompatible ways; new operation variants should be defined instead.

Initial application:
The issue was applied by SVN-derived git commit e2c9447cca757714ea04d871e5355a3943144692, "#3730 note on operation compatibility", with git-svn-id build@5035 matching the Jira comment. That commit updated source/compatibility.html to add that additional optional parameters may be introduced but operation signatures cannot change and additional operation variants will be defined. The old compatibility page was later reorganized into the active version-management source.

Additional context:
The current build no longer has source/compatibility.html; the active compatibility guidance is in source/versions.html, which is listed in publish.ini. A later Published/Persuasive with Modification issue, FHIR-13089, explicitly requested changing the FHIR-3730 sentence from "Operation signatures cannot change; instead..." to the current wording about defining new operations and potentially deprecating old ones. FHIR-13089 already has an Issue-Reconcile-Key commit on the combined branch, so it is not decided again here. Later OperationDefinition guidance from FHIR-38034 also explains compatible derived OperationDefinitions and unexpected parameters, without contradicting the FHIR-3730 rule.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/versions.html states that the compatibility rules apply once a core or HL7 International IG artifact becomes normative, then its Operations row says new operations may be defined, operations and existing parameters will not be removed or renamed, parameter type and lower cardinality will not change, upper cardinality may only be widened from 1 to *, additional optional parameters may be introduced, and incompatible operation changes will be handled by defining new operations and potentially deprecating old operations. Current operations and OperationDefinition pages also point implementers to derived OperationDefinitions for extensions and say unexpected parameters should generally be ignored.

Recommendation:
Keep this audit commit as-is. No core source edit is recommended because the original compatibility rule is already present in active source, and the wording difference is explained by the later approved FHIR-13089 refinement.
