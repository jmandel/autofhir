FHIR-19745: Audit ElementDefinition path length enforcement

Issue request:
FHIR-19745 was a Published FHIR-core change request resolved Persuasive with Modification for R5. It reported that ElementDefinition path/name characters were constrained computably, but the declared 64-character component limit was not reliably enforced because eld-19's regular expression was not anchored; the resolution asked to anchor eld-19, mention that eld-19 enforces the 64-character limit, and remove the implication that eld-20 is the hard length rule.

Initial application:
The anchoring part appears to have been applied through the later FHIR-26306 technical-correction commit 6c40cfa8f4, which added ^/$ anchors and fixed the XPath namespace/escaping for eld-19 and eld-20. The FHIR-19745-tagged commit 913853e2d9 then updated source/datatypes/elementdefinition.xml so eld-19 mentioned the 64-character maximum and eld-20 used a bounded naming regex. Later wording commits refined the human descriptions without removing eld-19's hard length enforcement.

Additional context:
ElementDefinition is active in source/fhir.ini as a current datatype/page and normative artifact, so source/datatypes/elementdefinition.xml is in build scope. Related Published issues FHIR-25627, FHIR-38795, and FHIR-38796 confirm the current split: eld-19 is the hard SHALL enforcing each path component's 64-character limit, while eld-20 remains a warning about UpperCamelCase/lowerCamelCase naming with a logical-model caveat. Those related issues already have reconciliation commits on the combined branch and should not be re-decided here.

AutoFHIR reconciliation:
No source change was made. The current active source has eld-19 as an error rule whose human text says each '.'-separated component is restricted to a maximum of 64 characters and whose FHIRPath/XPath regular expressions are anchored and use {1,64}; eld-20 no longer carries the stale hard-length description and instead describes naming convention expectations.

Recommendation:
Keep this empty audit commit as-is. The current specification already implements the FHIR-19745 decision when read with the later published eld-19/eld-20 clarification issues; any future change to eld-20's warning expression or logical-model behavior should be handled as a separate work-group decision.
