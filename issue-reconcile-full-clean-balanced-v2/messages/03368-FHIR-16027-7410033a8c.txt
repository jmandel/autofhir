FHIR-16027: Audit AdverseEvent detection dates

Issue request:
FHIR-16027 was a Published Patient Care change request for STU3 asking AdverseEvent to capture the date when the adverse event was detected, which may or may not be the same date as when it occurred. The final Persuasive with Modification resolution requested AdverseEvent.detected dateTime 0..1, AdverseEvent.assertedDate dateTime 0..1 for first recording, and recognized existing AdverseEvent.date for occurrence.

Initial application:
The issue was applied in historical commit 722ed5c93f4bc9828e96f0f5b476bedc3486fb92, whose subject explicitly says GF#16027 added AdverseEvent.detected and AdverseEvent.recordedDate. That patch added AdverseEvent.detected 0..1 dateTime and AdverseEvent.recordedDate 0..1 dateTime to the AdverseEvent spreadsheet source, with committee notes tying recordedDate to GF#16027 and GF#17285.

Additional context:
FHIR-17285 explains the broader Patient Care decision to distinguish assertedDate from recordedDate across related clinical resources, which accounts for the current source using recordedDate instead of the seed resolution's assertedDate wording. Later AdverseEvent issues reorganized and refined the resource: FHIR-22737 placed detected between the occurrence/date element and recordedDate in the approved element order, and FHIR-24684 explicitly decided not to rename detected to assertedDate. Current source/fhir.ini includes AdverseEvent in the active build, so source/adverseevent/structuredefinition-AdverseEvent.xml is authoritative current-build input.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current StructureDefinition already contains AdverseEvent.detected as 0..1 dateTime with short text "When the event was detected" and the requested reporter-opinion definition, and contains AdverseEvent.recordedDate as 0..1 dateTime with first-recorded definition/comment text and committee notes citing GF#16027 and GF#17285. Community and Confluence searches found no direct contrary FHIR-16027 decision; broader Patient Care minutes discuss later AdverseEvent date questions without invalidating these elements.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-16027 unless the work group opens a new issue to revisit AdverseEvent's broader clinical-research date model; related issues such as FHIR-16028, FHIR-22737, FHIR-24681, and FHIR-24684 are separate applied/published AdverseEvent changes and were not decided by this seed audit.
