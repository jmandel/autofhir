FHIR-17433: Confirm canonical targetProfile support

Issue request:
FHIR-17433 was a Published/Persuasive FHIR-core ElementDefinition change request raised for STU3. It asked the specification to make clear that ElementDefinition.type.targetProfile can constrain canonical targets as well as Reference targets, enabling forms such as canonical(ValueSet), canonical(StructureDefinition), and canonical(CodeSystem).

Initial application:
The issue was applied before this reconciliation by svn revision 14218, represented in git as commit 30f92b7806dc9e99c6553a0607eb4ead2265cef4, which changed source/datatypes/elementdefinition.xml so ElementDefinition.type.targetProfile referred to the Reference/canonical target instead of Reference only. Current history and source inspection did not find a later reversal of canonical support.

Additional context:
ElementDefinition is an active normative datatype in source/fhir.ini, so source/datatypes/elementdefinition.xml feeds the current build. The July 2018 committers Zulip thread records the same rule: targetProfile is the mechanism for qualifying canonical allowed target types, just as for Reference. FHIR-I minutes for 2018-07-30 record FHIR-17433 as Persuasive in the block vote. Related FHIR-17438 addressed display/documentation for canonical target types separately, and later FHIR-34462 broadened eld-17 to CodeableReference while preserving canonical.

AutoFHIR reconciliation:
No source change was made. The current ElementDefinition source defines ElementDefinition.type.targetProfile as canonical(StructureDefinition|ImplementationGuide), describes it as applying to the Reference/canonical target, and says it is used when the type is "Reference" or "canonical". The adjacent eld-17 invariant also allows targetProfile for canonical. The references page's canonical resource section points canonical(Any) readers back to targetProfile and does not conflict with this rule.

Recommendation:
Keep this empty audit commit as-is. No further FHIR core source work is needed for FHIR-17433; nearby rendering/display questions such as FHIR-17438 and later CodeableReference changes such as FHIR-34462 should remain separate issue decisions.
