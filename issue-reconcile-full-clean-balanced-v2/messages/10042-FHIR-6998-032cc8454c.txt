FHIR-6998: Audit update response Location header

Issue request:
FHIR-6998 was a Published/Persuasive FHIR-core overview issue from the DSTU1 ballot asking that an update response return an HTTP Location header with the updated resource's new location on the service. The recorded resolution was "ok add it" with svn revision 6417.

Initial application:
The issue was initially applied in git commit 251260b22659fe5a0501368ecb95f1d1164c9c61, the svn build@6417 import commit named "#6998 - add content-location to example". That commit changed the active Developer Introduction update response example in source/overview-dev.html by adding a Content-Location header and noting that the ETag version was also available in that fixed URL.

Additional context:
The originally-applied Content-Location wording was intentionally superseded by FHIR-7924, whose Published/Not Persuasive with Modification resolution removed the Content-Location header. Later related Published issues refined the same REST response behavior: FHIR-13915 clarified that Location should be as specific as the server can supply, and FHIR-26358 made the Location header mandatory for successful create/update outcomes, including conditional update. Current source/overview-dev.html is in build scope through source/hierarchy.xml as the Developer Introduction, and current source/http.html is in build scope as the RESTful API page.

AutoFHIR reconciliation:
This audit made no source change. The current Developer Introduction update response example now uses a Location header pointing to the updated version URL, and the RESTful API update interaction states that successful updates and creates SHALL return a Location header containing the logical id and version id for the resource version, with fallback to [base]/[type]/[id] when the server does not track versions. This preserves the substance of FHIR-6998 while reflecting later published decisions that removed Content-Location.

Recommendation:
Keep this no-change audit as-is. The current built specification already conveys the requested Location-header behavior in the active overview example and the authoritative REST API page; reverting to Content-Location or adding duplicate prose would conflict with later FHIR-I decisions and risk maintenance drift.
