FHIR-38882: Audit Patient merge cardinality ownership

Issue request:
FHIR-38882 was Published/Persuasive with Modification for R5 and asked PA to clarify the Patient $merge post-parameter-table cardinality rule so the operation requires at least one source patient identity and at least one target patient identity, allowing either reference or identifier parameters and originally allowing both when they identify the same patient.

Initial application:
No source commit explicitly tagged FHIR-38882 was found. The Jira comments, PA minutes, and Zulip discussion show the issue was applied by using the later FHIR-38881 resolution instead; the R5 published Patient $merge page therefore says exactly one source and exactly one target patient may be identified by reference or identifiers, but not both.

Additional context:
FHIR-38881 superseded the conflicting last sentence of FHIR-38882. The current core build no longer owns OperationDefinition/Patient-merge: source/patient/list-Patient-operations.xml lists Patient-match and Patient-purge only, source/patient/patient-notes.xml links to HL7/admin-incubator for $merge, and git commit b487fdda4b deleted source/patient/operationdefinition-Patient-merge.xml. The current HL7/admin-incubator rendered page/source still shows the older at-least-one comment in its generated OperationDefinition narrative, so any current correction belongs in that external IG repository, not this FHIR core checkout.

AutoFHIR reconciliation:
Published this empty external-repo audit commit. No core source files were changed because the Patient $merge OperationDefinition is outside the current core build scope.

Recommendation:
Keep this audit commit as-is for FHIR core. If PA wants current CI/R6 $merge wording aligned with the applied R5 decision, update HL7/admin-incubator input/resources/patient/OperationDefinition-Patient-merge.xml and related page content so the rendered operation uses the FHIR-38881 controlling text rather than the stale at-least-one wording.
