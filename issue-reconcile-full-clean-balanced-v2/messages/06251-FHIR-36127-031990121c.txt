FHIR-36127: Audit guarded name regex constraints

Issue request:
FHIR-36127 was a Published/Persuasive FHIR-core technical correction, raised in R4B and applied for R5, reporting that many root-level cnl-0 constraints used `name.matches('[A-Z]([A-Za-z0-9_]){0,254}')`. Because `name` is optional, the unguarded expression evaluates to `{}` rather than `true` when `name` is absent. The requested correction was to avoid warning/failing resources with no `name`, either by moving the constraint to `name` or otherwise guarding the root expression.

Initial application:
The Jira comment records R4B commit `cada1a356c` and R5 commit `9ea5ca6fcc`. Git history confirms both commits changed the affected StructureDefinition expressions, including `source/plandefinition/structuredefinition-PlanDefinition.xml`, from bare `name.matches(...)` to `name.exists() implies name.matches(...)`.

Additional context:
Later issue FHIR-34147 deliberately changed the same machine-friendly-name regexes from `{0,254}` to `{1,254}`, and commit `5fbb239871` later anchored the expressions for QA. Those later changes explain the current `name.exists() implies name.matches('^[A-Z]([A-Za-z0-9_]){1,254}$')` text and should not be reverted while auditing FHIR-36127. Zulip discussion shows the original optional-field report that led to FHIR-36127; a later `implies` thread briefly questioned this guarded form, but the concern was retracted after confirming `name.exists()` is false when `name` is absent.

AutoFHIR reconciliation:
No source change was made. The current build-scope PlanDefinition source, and the other current StructureDefinition sources with this name regex, already use the guarded `name.exists() implies ...` form. A source search found no remaining root-level `<expression value="name.matches(` constraints in current `source/`, and the active current resources are driven by `source/fhir.ini`; retired R4 resources from the Jira description do not require current-build edits.

Recommendation:
Keep this empty audit commit as-is for FHIR-36127. Any future discussion about SearchParameter naming policy or the later `{1,254}` minimum-length rule should be handled under those separate Jira issues, not as a FHIR-36127 follow-up.
