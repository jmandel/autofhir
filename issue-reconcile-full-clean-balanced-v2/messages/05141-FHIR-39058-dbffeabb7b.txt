FHIR-39058: Audit Requirements conditionality element

Issue request:
FHIR-39058 is Published/Persuasive for R5 and asked for a boolean on Requirements.statement to indicate that a requirements statement is conditional. The resolution proposed statement.conditional with short text "Statement includes conditionality," longer guidance that the statement includes applicability logic such as SHALL only in some circumstances, and a rendering-focused comment.

Initial application:
The issue was applied by 9529fd0680d464a377f07cbd49144bcf02190036, titled "FHIR-39058 How to do \"IF\" conditional statements?" That commit added the active Requirements.statement.conditionality 0..1 boolean to source/requirements/structuredefinition-Requirements.xml with text describing requirements that include "if x then y" conditionality. Later Requirements cleanup preserved the element and corrected a spelling typo in its definition.

Additional context:
Requirements is an active current-build resource in source/fhir.ini and is assigned to FHIR-I/normative, so source/requirements/structuredefinition-Requirements.xml is the authoritative core source for this check. FHIR-I minutes on 2022-12-05 record the FHIR-39058 persuasive vote as 15-0-2, after the 2022-10-31 minutes had requested submitter input. A later public Zulip thread from the original reporter describes EHR family rendering that uses statement.conditionality as a "conditional" pill, confirming downstream use of the applied element name. No later core tracker or community evidence found during this reconciliation requires renaming the shipped element to statement.conditional.

AutoFHIR reconciliation:
This audit commit makes no source change. The current source already provides the requested boolean and conveys the approved semantics. Renaming the element from the historically applied and used Requirements.statement.conditionality to the exact Jira proposal statement.conditional would be a breaking conformance change and is not justified by this applied issue.

Recommendation:
Keep this no-change audit commit as-is. If the work group wants a different element name or clearer wording for the existing element, handle that as a new substantive tracker because R5/R6-era source and downstream usage already use Requirements.statement.conditionality.
