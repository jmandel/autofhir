FHIR-5825: Audit FamilyMemberHistory single-relative model

Issue request:
FHIR-5825 was a Published/Persuasive with Modification Patient Care change request from DSTU1 asking to stop modeling FamilyHistory as one resource with multiple relation entries, rename the resource to FamilyMemberHistory, collapse relation-level content to the resource level, and use List when a full family history needs to point at multiple family-member records.

Initial application:
The issue was applied by db4ace37c6, a 2015-03-28 source commit tagged with {#5825}, whose message says it turned FamilyHistory into a List of FamilyMemberHistory and whose diff removed the old source/familyhistory examples with repeated relation elements, added source/familymemberhistory examples, updated the FamilyMemberHistory spreadsheets/profiles, and adjusted List examples.

Additional context:
The current build-scope authority source/fhir.ini actively lists familymemberhistory=FamilyMemberHistory and records only a deleted-resource note that FamilyHistory became FamilyMemberHistory. The current StructureDefinition describes significant health conditions for a person related to the patient, has relationship/name/sex/born/age/deceased/note/condition at FamilyMemberHistory scope rather than under a repeating FamilyHistory.relation backbone, and the resource introduction explicitly says the entire family history can be represented by combining FamilyMemberHistory instances in a List. Later FHIR-16146 considered an alternate Condition-profile model and was resolved No Change, supporting retention of FamilyMemberHistory as the current model. No relevant Zulip or Confluence evidence was found that changes this conclusion.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current authoritative source already reflects the FHIR-5825 decision, including the rename, single-family-member granularity, resource-level relationship/content, and List aggregation guidance.

Recommendation:
Keep this no-change audit commit as-is. Future work on FamilyMemberHistory should be driven by later targeted Jira issues rather than reopening the DSTU1 FamilyHistory-to-FamilyMemberHistory restructuring.
