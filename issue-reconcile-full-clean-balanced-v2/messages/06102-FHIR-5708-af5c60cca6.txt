FHIR-5708: Audit Condition status rename

Issue request:
FHIR-5708 was a Published/Persuasive with Modification DSTU1 Patient Care issue asking that Condition.status be renamed because its provisional/working/confirmed/refuted values did not match the usual lifecycle meaning of status. The recorded resolution directs readers to GForge change #3976.

Initial application:
The direct application is git commit 1f32e2833bae9fb8cc45636c39142020e353b5c6, whose subject is "#3976 - rename Condition.status to Condition.clinicalStatus". That commit changed the Condition source and related examples/profiles shortly after the PC WG decision recorded in FHIR-3976, which FHIR-5708 cites as its outcome.

Additional context:
FHIR-3976 records the 2015-03-19 PC WG motion to rename status to clinical status and remove certainty. FHIR-5734 is related but was Resolved - No Change and also points to #3976. Later Published Condition issues, especially FHIR-7581 and duplicate-family FHIR-7864, split the post-rename concepts into clinicalStatus and verificationStatus, so the current wording no longer literally preserves the original provisional/working/confirmed/refuted clinicalStatus proposal but does preserve the final specification direction that the ambiguous Condition.status element is gone.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Condition is active in source/fhir.ini, and the current active Condition StructureDefinition defines Condition.clinicalStatus and Condition.verificationStatus, while a current source search under source/condition finds no Condition.status element or path. The current search parameters likewise target clinical-status and verification-status, so the seed issue is already correctly reflected in the build source after later approved refinements.

Recommendation:
Keep this audit commit as-is. No current core source edit is needed for FHIR-5708; future changes to Condition status semantics should be handled through the later clinicalStatus/verificationStatus issue family rather than by resurrecting or renaming Condition.status.
