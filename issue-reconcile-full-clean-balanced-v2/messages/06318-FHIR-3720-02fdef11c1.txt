FHIR-3720: Align NutritionOrder status comment with request intent

Issue request:
FHIR-3720 was a Published/Persuasive with Modification DSTU1 Patient Care issue asking order/request resources, including CarePlan, DiagnosticRequest, MedicationPrescription, ReferralRequest, and related request classes, to represent planned and proposed activities. The recorded resolution endorsed using status values at the time, with OO and Pharmacy comments supporting planned/proposed status handling.

Initial application:
The explicit historical application was git d6259fa8e3beda8fd5e58ad54d85001f1efb9d42, whose message included "[#3720] add 'planned' and 'proposed' to DiagnosticOrder and NutritionOrder". That patch added proposed/planned values to then-current DiagnosticOrder and NutritionOrder status lists, while some originally mentioned artifacts were later renamed, subsumed, or handled through the FHIR workflow/request pattern rather than by preserving proposed/planned as status codes.

Additional context:
Current build scope has CarePlan, MedicationRequest, NutritionOrder, and ServiceRequest active; fhir.ini records DiagnosticOrder as subsumed into ServiceRequest, MedicationPrescription as MedicationRequest, and ReferralRequest as ServiceRequest. Later workflow decisions split lifecycle state from planned/proposed/order authority: Request.status is lifecycle-oriented, while Request.intent carries proposal, plan, and order semantics. FHIR-9266 later resolved Not Persuasive/No Change for adding proposed/planned to MedicationOrder status because the resource follows the Request workflow pattern, and FHIR-14414 added NutritionOrder.intent/status alignment to that pattern. The current CarePlan, ServiceRequest, MedicationRequest, and NutritionOrder definitions already expose proposal/plan/order through required intent bindings, but NutritionOrder.status still contained stale prose saying the status was set to "requested" and then maintained by the receiver, contradicting both the current code set and the request-pattern fulfillment model.

AutoFHIR reconciliation:
This commit changes only the stale NutritionOrder.status comment and the matching NutritionOrder request-pattern mapping exception. The new text removes the invalid requested status reference, makes the requester-controlled lifecycle meaning explicit, and points performer fulfillment state to event resources or Task. No proposed/planned status codes were added because the current and later-approved representation is through intent, not lifecycle status.

Recommendation:
Keep this source fix as-is. It preserves the current Request pattern while removing a real stale contradiction from one of the original FHIR-3720 artifacts; future changes should not reintroduce proposed/planned status codes unless the workflow pattern is reopened by a new work-group decision.
