FHIR-33170: Audit summary ancestor tooling handoff

Issue request:
FHIR-33170 is Applied/Persuasive with Modification. It asked that when a BackboneElement descendant is marked _summary, the BackboneElement ancestors also be marked _summary; the approved resolution was to change tooling so ancestors are marked automatically and tooling errors if a summary BackboneElement has no summary children.

Initial application:
The Security examples were partially applied in core source by commit 2c7d674ebe5bfdd04b2239cbb6d5990931b20aad, which added isSummary=true to Provenance.agent, Provenance.entity, AuditEvent.agent, AuditEvent.source, and AuditEvent.entity. That commit did not implement the approved tooling behavior, and the FHIR source checkout does not contain Kindling source; it consumes org.hl7.fhir:kindling as an external Gradle dependency.

Additional context:
FHIR-I minutes on 2021-11-29 record the formal 17-0-0 decision that if a descendant is _summary, the backbone element needs to be _summary and the change belongs to FHIR-Tooling-Core. Zulip follow-up in 2022-2023 records that only Provenance/AuditEvent had been fixed manually and the problem persisted, specifically CareTeam.participant. Current source and build checks still show active build-scope examples such as CareTeam.participant and Goal.target lacking isSummary while their descendants have it, and HL7/kindling#173 is open/reopened for the approved tooling work.

AutoFHIR reconciliation:
This empty audit commit makes no core source change. A broad manual sweep of active resource StructureDefinitions would paper over current examples but would not implement the approved automatic ancestor propagation or validation rule, and it would overlap unresolved follow-up issues such as FHIR-34180. The remaining actionable change is in the external Kindling tooling repository.

Recommendation:
Keep this audit commit as an external-repo decision for core. Complete HL7/kindling#173 so the publisher propagates summary flags to BackboneElement ancestors and validates the inverse rule; only consider manual core source cleanup as a separate editor/work-group decision if tooling cannot land in time.
