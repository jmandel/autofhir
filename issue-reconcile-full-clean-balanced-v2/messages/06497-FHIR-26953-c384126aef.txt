FHIR-26953: Audit DeviceRequest performer reconciliation

Issue request:
FHIR-26953 was Published with resolution Persuasive with Modification. The request started from applying the standard request-performerOrder extension to DeviceRequest for ordered alternate performers, but the accepted resolution was to change DeviceRequest.performer to a CodeableReference and drop DeviceRequest.performerType.

Initial application:
The source history contains two explicit FHIR-26953 commits. Commit 25cc0f276f changed DeviceRequest.performer from Reference to CodeableReference. Commit f8644c49e8 removed DeviceRequest.performerType from the live element list by commenting it out; later cleanup commit f8afeaa14a removed that commented block entirely. There was no separate application that added request-performerOrder to DeviceRequest.

Additional context:
DeviceRequest is in the active current build according to source/fhir.ini. The current DeviceRequest source keeps performer at 0..1, so there is no current list of DeviceRequest performers for request-performerOrder to order. The old R5 migration map records DeviceRequest.performerType as mapped to performer.concept, which is consistent with using CodeableReference rather than keeping a separate performerType element. The Extension Pack definition for request-performerOrder applies to ServiceRequest.performer and Task.requestedPerformer, not DeviceRequest.performer; this is consistent with the final FHIR-26953 resolution and does not require a core source edit. Confluence agenda/minutes references tracked the PAO impact check for changing DeviceRequest.performer to CodeableReference, and no relevant Zulip conflict was found.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active DeviceRequest StructureDefinition already has DeviceRequest.performer as CodeableReference and no live DeviceRequest.performerType element, which satisfies the published Jira disposition. Adding request-performerOrder to DeviceRequest now would go beyond the final resolution because DeviceRequest.performer remains singular.

Recommendation:
Keep this no-change audit commit. Revisit only if OO decides in a new tracker to make DeviceRequest.performer repeatable or to add request-performerOrder support despite the current singular cardinality.
