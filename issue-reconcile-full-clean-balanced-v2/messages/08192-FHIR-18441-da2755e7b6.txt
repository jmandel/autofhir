FHIR-18441: Audit XML canonicalization whitespace guidance

Issue request:
FHIR-18441 was Published/Persuasive for FHIR-core XML after STU3. It asked whether the XML digital-signature canonicalization rule limiting whitespace to single spaces could subtly change meaning, especially for markdown serialized in XML attributes, and the final resolution was to warn that XML normalization can assign the same normalized text to resources with different meanings.

Initial application:
The issue was applied by git commit 543388f9fe1aa2f08a988c3cc888ddd622085376, which added warning notes to the then-current source/datatypes.html Signature section and source/xml.html canonical XML section. Jira also records that the change was committed to both the R4 technical correction and current build.

Additional context:
The current build now has an active source/signatures.html page under Security and Privacy, while source/xml.html#digsig only links to that page and source/datatypes.html#Signature points readers to the same signature guidance. Later signature-page refactors removed the original warning text but replaced the risky behavior with an explicit XML canonicalization rule that whitespace in non-XHTML primitive values SHALL not be altered, including multiple spaces in markdown. The Zulip thread linked from the issue confirms the original concern and the alternative guidance that JSON avoids XML attribute-normalization risk; no Confluence reference or later final Jira decision was found that requires reintroducing the old note in addition to the current rule.

AutoFHIR reconciliation:
No source change was made. The active current-build signature guidance already preserves primitive whitespace, directly addressing the semantic risk raised by FHIR-18441, and adding a second warning on xml.html or datatypes.html would duplicate a rule now centralized on signatures.html.

Recommendation:
Keep this audit commit as-is. If the work group later decides that XML canonicalization cannot safely guarantee primitive-value whitespace preservation, that should be handled through the unresolved R6 signature rewrite/canonicalization trackers rather than by restoring the obsolete 2019 warning text here.
