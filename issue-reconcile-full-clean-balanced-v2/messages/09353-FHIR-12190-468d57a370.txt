FHIR-12190: Audit create Location header requirement

Issue request:
FHIR-12190 was Published/Persuasive for FHIR-core and asked that the RESTful create response requirement be strengthened from a SHOULD to a SHALL for the HTTP Location header, because clients should not need to look at both Location and Content-Location to discover a newly created resource.

Initial application:
The change appears to have been applied in source/http.html by commit 3d7763fc7d0a1a1921562cf73de46c53197d669e, corresponding to the Jira comment "svn @10126". That commit explicitly mentions #12190 and changed the create response text from "SHOULD also return a Location header" to "SHALL also return a Location header".

Additional context:
The current RESTful API source still requires Location for a successful create, and the current HTTP header table separately documents Content-Location only for the async pattern. FHIR-26358 later extended mandatory Location-header behavior to conditional create/update cases, which reinforces rather than reverses the seed decision. Zulip discussions in 2017 and 2021 questioned Location versus Content-Location, but the responses found during reconciliation confirmed that Location is the intended header for newly created resources.

AutoFHIR reconciliation:
This is an empty no-change audit commit. The current source/http.html create section already says a 201 Created response SHALL also return a Location header, and a bounded source search found no competing create-response SHOULD that would undermine that requirement.

Recommendation:
Keep this audit commit as-is. No source follow-up is needed in core for FHIR-12190 unless a future work group decision intentionally changes the HTTP create response header rule.
