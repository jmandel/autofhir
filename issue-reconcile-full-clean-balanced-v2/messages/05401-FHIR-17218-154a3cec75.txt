FHIR-17218: Audit validate-code display status guidance

Issue request:
FHIR-17218 was a Published/Persuasive with Modification STU3 Vocabulary issue asking ValueSet $validate-code to clarify whether a supplied display value must match the value set display or another designation, and whether an invalid display makes the result output false. The accepted resolution was to say this was at implementer discretion while Vocabulary continued work on display validation expectations.

Initial application:
No current git commit explicitly mentions FHIR-17218. The Jira comment says the change was already done, and the R4B/current OperationDefinition source carries the applied note that validation behavior for language on Coding.display is currently undefined and may receive later requirements or recommendations. That source was imported into the current build-era git history in c69d71aa21 and later spelling-only edited in 60e98c41f6.

Additional context:
The ValueSet resource is active in source/fhir.ini, so source/valueset/operationdefinition-ValueSet-validate-code.xml is in current build scope. Later applied issue FHIR-41229 directly revisited the broader wrong-display true/false ambiguity and added lenient-display-validation: absent or false means an invalid display fails validation; true permits treating display problems as non-fatal. The current source also has displayLanguage guidance for language-specific display validation. A new source edit restoring open-ended implementer discretion would conflict with the later, more specific R6 decision.

AutoFHIR reconciliation:
This audit commit intentionally makes no source changes. The current ValueSet $validate-code source preserves the FHIR-17218 language-validation caveat and now includes the later lenient-display-validation parameter that supplies the current result-status rule for invalid displays.

Recommendation:
Keep this no-change audit. Future work on display/designation matching should proceed through a new Vocabulary decision if the remaining language/designation details need additional normative precision, rather than reapplying the older STU3 discretionary wording over the later R6 parameter semantics.
