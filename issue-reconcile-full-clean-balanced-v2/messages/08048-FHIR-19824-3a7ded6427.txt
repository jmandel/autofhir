FHIR-19824: Audit batch response wording

Issue request:
FHIR-19824 is a Published/Persuasive FHIR-I change request for the FHIR-core HTTP Batch/Transaction Response section. It asked to clarify that each response entry includes the HTTP status code and, where applicable, Location and ETag header values, rather than implying Location or ETag are always required.

Initial application:
The issue was applied by a1efcc18b1f95aac0fa4f5f6246e69e9b59469b6, which changed source/http.html to add "where applicable" for Location and ETag and to capitalize/mark up those HTTP header names. Current source/http.html still contains that clarification in the Batch/Transaction Response section.

Additional context:
FHIR-I minutes from 2019-07-01 record agreement to reword the item to clarify ETag and Location header requirements with a 6-0-0 Persuasive vote. The current Bundle source remains consistent: Bundle.entry.response.location is 0..1 and populated if the operation returns a location, while Bundle.entry.response.etag is 0..1 and relevant when processing produced a versioned resource. No Zulip or additional Confluence search result was found that changes this interpretation.

AutoFHIR reconciliation:
This audit intentionally makes no source change. The important requirement clarity from the Jira resolution is already present in source/http.html, and the retained "which are used for identifying and versioning" clause is explanatory wording rather than a conflicting conformance rule. Removing it would be editorial cleanup, not a necessary current-spec correction under the reconciliation threshold.

Recommendation:
Keep this no-change audit commit as-is. No follow-up source work is recommended for FHIR-19824 unless the work group separately chooses to do editorial cleanup of the HTTP narrative.
