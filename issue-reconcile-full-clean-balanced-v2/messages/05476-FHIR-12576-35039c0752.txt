FHIR-12576: Audit CodeSystem compose cardinality

Issue request:
FHIR-12576 is a Published/Persuasive Vocabulary change request for the DSTU2 CodeSystem $compose operation. It reported that the out parameter compose.match.unmatched was 1..1 even though a complete match should have no unmatched properties, and asked for the cardinality to be loosened.

Initial application:
The issue was applied in the historical spreadsheet source by Grahame's 2017-01-17 commit 5df4188d5c9db25ee14a0c11e94ce44a1176197c, which changed compose.match.unmatched from 1..1 to 0..*. That matches the contemporaneous Zulip direction from Grahame that unmatched should be 0..*, even though the Jira description suggested 0..1.

Additional context:
FHIR-15956 later renamed CodeSystem $compose to $find-matches and adjusted its maturity, and FHIR-17563 cleaned remaining $compose references after that rename. Both related issues are already represented on the combined branch. For the current R6 ballot source, source/fhir.ini actively includes CodeSystem, but source/codesystem/list-CodeSystem-operations.xml lists only $lookup, $validate-code, and $subsumes. The later 2025 terminology-curation commit 40306e5cd9c1b1e3eb6f115de16a8da3aa13a351 removed the CodeSystem $find-matches OperationDefinition from the current build.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The cardinality problem was applied historically, the operation was subsequently renamed, and the renamed operation is no longer active in the current CodeSystem operation list. Reintroducing or editing orphaned example fragments would not improve the current built specification.

Recommendation:
Keep this audit commit as-is. No FHIR core source follow-up is needed for FHIR-12576 unless the Vocabulary work group reintroduces a CodeSystem matching operation; if that happens, the output shape should preserve the historically applied 0..* unmatched cardinality.
