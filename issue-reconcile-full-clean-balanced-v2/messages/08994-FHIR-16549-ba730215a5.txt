FHIR-16549: Audit conditional update no-match upsert wording

Issue request:
FHIR-16549 was a Published FHIR-I change request for the core HTTP conditional update section, resolved Persuasive for STU3. It asked to clarify that a conditional update with no matches behaves like normal update/create-as-update behavior rather than implying unconditional server creation, and to add an "Update as Create" subheader tied to the same CapabilityStatement support.

Initial application:
The issue was explicitly applied by 098f965b5694f683ba3d593564f698c031777ef2, "GF#16549 - note about conditional update and create," which added the source/http.html upsert anchor and changed the conditional-update no-match wording from a direct create interaction to an Update as Create reference. That application was later refined by d69dfafe26d9ad9151c011ef743568a3ab2158fc for FHIR-17906 to distinguish no Resource.id from Resource.id-provided no-match behavior.

Additional context:
The current build-scope HTTP narrative is source/http.html, listed in publish.ini as http.html. Later finalized same-section decisions explain the current wording without reversing FHIR-16549: FHIR-17906 split the no-match and one-match conditional-update cases, FHIR-20390 clarified that "id provided" means Resource.id, FHIR-26688 removed the contradictory sentence saying a supplied id is ignored, and FHIR-36859 split the Resource.id-provided/no-match case when that id already exists. The Zulip thread opened after GF#16549 confirms the initial wording could be misread as disallowing server-assigned conditional upserts and led to FHIR-17906 rather than undoing the FHIR-16549 Update as Create linkage.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active HTTP source already has an "Update as Create" subsection, declares CapabilityStatement.rest.resource.updateCreate as the support flag, and the conditional-update no-match table now creates directly only when no Resource.id is provided while treating the Resource.id-provided/no-existing-resource case as Update as Create or rejection if unsupported. That preserves the seed clarification after later applied refinements.

Recommendation:
Keep this no-change audit commit as-is. No core source follow-up is needed for FHIR-16549; future changes to conditional update should be handled under separate finalized trackers because the seed behavior is already present and later family issues are already represented on the combined branch.
