FHIR-5909: Audit primitive value rendering

Issue request:
FHIR-5909 was a Published / Persuasive DSTU1 FHIR-core issue on the profiles page. It asked that when a simple type is profiled only to define extensions, the rendered definition should not expose the unchanged primitive "value" property in a way that adds noise or implies the value was specially constrained.

Initial application:
No migrated commit explicitly mentions FHIR-5909. The Jira comments record Grahame's concern that hiding value entirely could make the inlined primitive datatype ambiguous, then state "already done elsewhere." The closest historical source trail is old profile/rendering tooling work: b90a9b36e98cd84889f821e579d69824391c1f30 fixed primitive datatype profile definitions, and b1640e6611a7d2b99e6c31bd31ad7205dcb5dbb5 / FHIR-8171 improved differential rendering by showing inherited base cardinality, type, and definition information greyed out instead of making readers switch to the snapshot. Those legacy Java generator files are not current build-scope source in this checkout.

Additional context:
Current build-scope profiling guidance says differentials are sparse and describe only differences, while snapshots are complete and retain inherited constraints. The current profile presentation table says the Differential Table is the differential view and that additional context not in the differential is shown partially transparent. Current primitive-value guidance also provides explicit mustHaveValue and valueAlternatives shortcuts for the modern case where a primitive's value is actually constrained or replaced by allowed extensions.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already preserves the issue's implementer-facing intent: unchanged inherited primitive value structure is not treated as a new constraint in the differential, but enough inherited context may be displayed transparently to avoid ambiguity. Adding a new local warning would duplicate existing differential/snapshot and primitive-value guidance rather than correct current spec behavior.

Recommendation:
Keep this audit commit as-is. Revisit only if the current renderer regresses by making unchanged inherited primitive value elements appear as profile-authored constraints instead of transparent context, or if a new work-group decision changes how primitive extension differentials should be rendered.
