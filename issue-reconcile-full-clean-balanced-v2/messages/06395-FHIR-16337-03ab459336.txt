FHIR-16337: Audit ValueSet expansion safeguards

Issue request:
FHIR-16337 was a Published/Persuasive with Modification Vocab change request for STU3 ValueSet. It asked that ValueSet $expand parameters such as filter, activeOnly, profile-derived behavior, excludeNested, excludeNotForUI, excludePostCoordinated, and limited expansion not silently change the apparent content of a stored/base expansion. The accepted resolution required documentation that an expansion-only ValueSet requested with inconsistent parameters is an error, matching parameters may reuse the existing expansion, additional parameters may be applied only when the server validates that the result is the same as a direct expansion, persisted expansions SHALL record the relevant $expand parameters, and ExpansionProfile would be removed/redrafted out of the current design.

Initial application:
The Jira application comment cites svn revision 13900. In git history this is commit 0cf4c0c96d333dbe2a5b7a5d158f7e59db4c4b5b, titled "GF#16337 & GF#16490 - remove ExpansionProfile + various notes about how expansions work". That commit updated source/valueset/valueset-notes.xml so existing expansions are checked against requested parameters, inconsistent requests without compose return an error, safe additional parameters may be applied only when the result is validated as equivalent to direct expansion, and expansion.parameter SHOULD include all parameters affecting $expand with a SHALL for persisted expansions. The same commit removed ExpansionProfile from active source/build inputs and moved version-override behavior into explicit $expand parameters.

Additional context:
ValueSet is an active current-build resource in source/fhir.ini, and source/valueset/list-ValueSet-operations.xml includes OperationDefinition/ValueSet-expand. Later final Vocab decisions refined the same parameter-accounting area: FHIR-16443 audited ValueSet.expansion.parameter source/name behavior after ExpansionProfile removal, FHIR-17558 removed stale ValueSet ExpansionProfile references, and FHIR-41589/FHIR-41639 refined current R6 guidance so expansion.parameter SHOULD include used client inputs, server-defaulted inputs, and terminology artifacts used. FHIR-16069 separately resolved that ValueSet operations should remain normative, so FHIR-16337's maturity concern does not justify demoting the current $expand operation.
