FHIR-5982: Audit lockedDate context guidance

Issue request:
FHIR-5982 was a Published/Persuasive DSTU1 vocab change request about ValueSet.lockedDate/stableDate mixing dates with version semantics. The accepted resolution was to document that lockedDate must be interpreted in context, specifically the context expressed by ValueSet.useContext.

Initial application:
The issue was applied in git-svn commit 3b87aca875 (#5982), which added the lockedDate comment that its interpretation is often context-dependent, with a SNOMED CT example expanding differently in the USA than in the UK. No later source history shows the FHIR-5982 guidance being removed.

Additional context:
ValueSet is active in the current build through source/fhir.ini. Later lockedDate work preserved and refined the same source area: FHIR-7043 added the note that explicitly versioned includes must be available at the locked date, FHIR-9535 moved lockedDate under ValueSet.compose, and FHIR-10490 corrected the definition so lockedDate applies to references not already tied to a specific version. Current ValueSet metadata also defines jurisdiction as generally found in useContext, so the current lockedDate comment's jurisdiction/context example still conveys the accepted rule without requiring duplicate wording.

AutoFHIR reconciliation:
This audit intentionally makes no source change. The active current source for ValueSet.compose.lockedDate already says that lockedDate interpretation is context-dependent and gives the same jurisdictional SNOMED CT example introduced by the original FHIR-5982 application.

Recommendation:
Keep this no-change audit commit. Further edits should only be made if the vocab work group wants a new, more explicit normative requirement tying lockedDate evaluation to a particular useContext coding; the existing source already satisfies FHIR-5982 as applied and preserved through later refactors.
