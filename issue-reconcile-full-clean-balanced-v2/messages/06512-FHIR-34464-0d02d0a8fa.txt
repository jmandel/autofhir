FHIR-34464: Audit sdf-10 extension bindings

Issue request:
FHIR-34464 was Published/Persuasive with Modification for R5 after reporting that R4B extension StructureDefinitions for event-statusReason, iso21090-SC-coding, and request-statusReason could contain an ElementDefinition.binding with neither valueSet nor description, violating StructureDefinition sdf-10. The accepted resolution was to change Kindling/publisher behavior so a binding-definition extension is promoted to binding.description, and to fail the build when neither source exists.

Initial application:
The Jira application comment records Kindling b3431a0. No FHIR core git commit explicitly names FHIR-34464, which is consistent with the approved fix being in the build tooling rather than a direct hand edit to these extension definitions. Current core inputs still include active event and request extension spreadsheets whose StatusReason binding rows carry the formal binding definition text; the exact R4B iso21090-SC-coding extension is no longer an active core source definition.

Additional context:
The current StructureDefinition source still contains sdf-10, so the issue remains semantically meaningful. Current Extension Pack definitions for event-statusReason, request-statusReason, and the restored deprecated iso21090-SC-coding definition all include binding.description where needed. Later FHIR-48957 explains the iso21090-SC-coding Extension Pack restoration/deprecation path and does not require a core source change for this issue.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build inputs and maintained extension definitions already convey the required binding description/valueSet information, and the original Jira resolution was a tooling behavior change that has already been applied outside this core source reconciliation.

Recommendation:
Keep this audit commit as-is. No current FHIR core source edit is needed for FHIR-34464; any future concern about historical R4B generated packages or Extension Pack packaging should be handled in the corresponding tooling or Extension Pack repository, not by changing unrelated current core source.
