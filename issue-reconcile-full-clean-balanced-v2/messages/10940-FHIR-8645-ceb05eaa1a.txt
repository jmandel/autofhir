FHIR-8645: Audit code-system binding enforcement

Issue request:
FHIR-8645 was Published/Persuasive for FHIR-core after FHIR-I accepted that value sets bound to elements whose data type is code should draw only from FHIR-defined code systems, aside from allowed mappings to v2, v3, or other systems. The requested change was to enforce that policy in the build tool.

Initial application:
The issue was applied in the historical in-repository Java publisher. Commit 0627be72fd128ab2fc79bc304e8dc143338976f8 added the ResourceValidator hint at svn revision 11401; commit c670df73aa60592935da71f718bb45ef0d06d112 immediately commented it out because of FMM-level impact; commit a30914f3e0a0628813eb2f730b25d901a4fc54f3 re-enabled the warning for STU4 at svn revision 14117.

Additional context:
The old tools/java publisher source was removed when HL7/fhir switched to the Gradle build with an org.hl7.fhir:kindling dependency. The current build.gradle.kts invokes org.hl7.fhir.tools.publisher.Publisher from Kindling, and current HL7/kindling ResourceValidator still checks simple code bindings with noExternals and emits the FHIR-8645-style message. The current core suppressed-messages.txt includes that message for CapabilityStatement.format, showing that the current build pipeline is receiving the validation output. Later Jira issues such as FHIR-24096 and FHIR-24097 used this QA message to fix resource-specific terminology, while FHIR-28285 is a separate later code-binding tooling rule already audited on the combined branch.

AutoFHIR reconciliation:
This is an empty external-repo audit commit. No HL7/fhir source file was changed because the requested enforcement now lives in the external HL7/kindling build tooling, and the current core checkout already delegates publishing and validation to Kindling.

Recommendation:
Keep this audit commit as-is for core source reconciliation. If this policy regresses, fix or version the Kindling/Publisher tooling rather than adding redundant core prose or editing generated artifacts; resource-specific QA warnings should be handled under their own Jira issues.
