FHIR-13192: Audit capability statement kind metadata wording

Issue request:
FHIR-13192 was a Published FHIR-I change request, resolved Persuasive, asking STU3 to remove the deprecated HTTP OPTIONS wording from the capability-statement-kind value set's instance code definition. The requested replacement was to describe the kind as returned by the metadata endpoint of a FHIR server.

Initial application:
The change appears to have been applied before this reconciliation. Jira's only comment, on 2017-12-18, says "already fxied", and commit ec09ca8c8d7e1dc670d74f0270defce4f76da409c, "#13773 - fix typo", changed the active CapabilityStatement spreadsheet definition from "returned by OPTIONS" to "returned by /metadata" on the same date. Later source refactoring kept that wording when the terminology moved from the spreadsheet into source/capabilitystatement/codesystem-capability-statement-kind.xml.

Additional context:
The current value set source is a compose-only ValueSet that includes all codes from http://hl7.org/fhir/capability-statement-kind, so the code definition lives in the paired CodeSystem source. source/fhir.ini actively lists CapabilityStatement as a build resource, and the CapabilityStatement StructureDefinition binds kind to ValueSet/capability-statement-kind. The related OPTIONS-removal HTTP-page issue FHIR-17322 is already represented on the combined branch; it supports the same current behavior, but it is a separate issue and is not re-decided here. Current source/http.html likewise describes the capabilities interaction as GET [base]/metadata.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current build-scope CodeSystem definition for the instance code says it is returned by /metadata, the ValueSet includes that CodeSystem, and a current source grep found no remaining "returned by OPTIONS" wording to remove.

Recommendation:
Keep this no-change audit commit. No FHIR core source follow-up is needed for FHIR-13192 unless FHIR-I later wants an editorial refinement from "/metadata" to a linked phrase such as "metadata endpoint"; that would be optional wording polish rather than a missing application of this issue.
