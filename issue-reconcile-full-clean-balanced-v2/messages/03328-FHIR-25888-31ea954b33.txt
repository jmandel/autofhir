FHIR-25888: Audit ValueSet expansion subproperty support

Issue request:
FHIR-25888 was a Published FHIR-core ValueSet change request resolved Persuasive with Modification. It asked for ValueSet.expansion.contains.property to be able to carry sub-properties by adding a non-recursive subProperty backbone with required code and value[x], and by updating the ValueSet/$expand property input documentation to say returned properties may include subproperties and that '*' requests all properties and sub-properties.

Initial application:
The issue was applied by git commit ff7b414909e963e85d7204f5dde7f3b4aa1f03a5, which added ValueSet.expansion.contains.property.subProperty, subProperty.code, and subProperty.value[x] to source/valueset/structuredefinition-ValueSet.xml and updated source/valueset/operationdefinition-ValueSet-expand.xml. Later formatting/OID-related history preserved the substance of those changes.

Additional context:
The final Jira comments and 2022-02-21 Vocabulary minutes say the solution was revised to make subproperty not nested and that changing ValueSet.expansion.contains.property.code to 0..1 was considered but not recommended for this ticket. A follow-up Zulip thread discussed that cardinality concern and did not surface a final later Jira decision requiring a different ValueSet model. The active source/fhir.ini resources list includes valueset=ValueSet, so the inspected ValueSet source is in current build scope.

AutoFHIR reconciliation:
No source change was made. The current source already contains the required single-level subProperty backbone with code 1..1 and value[x] 1..1 using the same datatype set as property.value[x], and the $expand property parameter documentation already states that returned properties may include subproperties and that '*' includes all properties and sub-properties.

Recommendation:
Keep this audit commit as-is. Any future editorial cleanup of the pre-existing "a the formal URI" wording can be handled separately; it does not change the implemented FHIR-25888 semantics and does not justify a source-changing reconciliation commit for this issue.
