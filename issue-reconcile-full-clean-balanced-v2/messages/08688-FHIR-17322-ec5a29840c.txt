FHIR-17322: Audit OPTIONS capability retrieval removal

Issue request:
FHIR-17322 was a Published FHIR-I change request, resolved Persuasive, asking the R4 HTTP page to actually remove the deprecated STU3 use of the HTTP OPTIONS command for retrieving the server CapabilityStatement because that use was not conformant with HTTP and complicated CORS support.

Initial application:
The issue appears to have been applied in svn revision 13874, mirrored as commit 996a1f3590fd9b32e1883f47b977b26a3e98234b, "GF#1732 - finish removing options". That commit removed the remaining commented hData section from source/http.html, including the statement that FHIR supported the hData RESTful Transport OPTIONS command on the service URL. Earlier commit f74048dde73667db9350d52f87f4e55bff46dcd6 had only deprecated OPTIONS for the conformance/CapabilityStatement interaction; FHIR-17322 completed the removal.

Additional context:
The current source/http.html page is the active RESTful API HTTP narrative linked from source/documentation.html. Its capabilities interaction explicitly says the interaction is performed by HTTP GET and shows only GET [base]/metadata, and the summary table likewise lists capabilities as /metadata with GET. The remaining current OPTIONS mentions are not the removed CapabilityStatement retrieval mechanism: one is the later FHIR-17831 generic HTTP-capabilities note already audited on the combined branch, several are DICOM Endpoint examples, and two are historical release notes saying STU3 deprecated OPTIONS. Jira search found the related FHIR-17831 note and FHIR-13192 valueset cleanup, but no later final decision requiring restoration of OPTIONS for CapabilityStatement retrieval. Zulip and Confluence searches for FHIR-17322 and the OPTIONS/CapabilityStatement/CORS terms found no directly relevant or conflicting community record.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current build-scope source already implements the approved removal: clients get the server CapabilityStatement through GET /metadata, not OPTIONS [base]. Removing the later generic FHIR-17831 OPTIONS note or historical release-note entries would be broader than FHIR-17322 and would make the current spec less accurate.

Recommendation:
Keep this no-change audit commit. No FHIR core source follow-up is needed for FHIR-17322 unless FHIR-I later decides to change the generic treatment of unspecified HTTP OPTIONS behavior, which is separately covered by FHIR-17831.
