Issue request:
FHIR-37001 was an Applied/Persuasive FHIR-core Task change request from OO asking to change the Task.code binding from example to extensible. The rationale was that FHIR-31900 added a Task.restriction invariant driven by the standard task-code value 'fulfill', so Task.code needed stronger alignment with the existing Task Codes value set.

Initial application:
The issue appears to have been applied before this reconciliation. Git history includes two FHIR-37001 commits on 2025-03-09 that changed source/task/structuredefinition-Task.xml so Task.code binding strength became extensible; current blame attributes the binding-strength line to 50d02c76bd866915254d40e1203e6939514cd234. The second touched hunk in those commits only normalized spacing in the Task output-parameter binding text and is unrelated to this issue's semantic request.

Additional context:
source/fhir.ini actively lists task=Task under [resources], so source/task/structuredefinition-Task.xml is in the current build. The current Task source also still carries the Task.restriction invariant requiring the 'fulfill' code from http://hl7.org/fhir/CodeSystem/task-code when restriction is present. FHIR-31900 and OO meeting minutes explain why the Task.code binding strength mattered, while Jira and source searches found no later FHIR-core decision reversing the extensible binding.

AutoFHIR reconciliation:
This audit commit intentionally makes no source changes because the current build source already has Task.code bound extensibly to http://hl7.org/fhir/ValueSet/task-code and the supporting value set still includes the standard task-code code system, including 'fulfill'.

Recommendation:
Keep this empty audit commit as-is. No follow-up is needed for FHIR-37001 unless a future OO decision changes the Task.code binding policy or the Task.restriction invariant.
