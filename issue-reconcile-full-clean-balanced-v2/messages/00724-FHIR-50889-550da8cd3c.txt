FHIR-50889: Audit symptom observation category external terminology

Issue request:
FHIR-50889 is Applied/Persuasive for R6 and asks to add symptoms to Observation.category because symptoms are patient observations, visual observations, or sensations not clearly represented by the existing Observation category codes.

Initial application:
No core source commit mentioning FHIR-50889 was found. The issue resolution points to the same fix as FHIR-34408, and a later Jira comment says the work is covered by UP-738. Current core source already delegates Observation Category code content to external terminology: `source/observation/valueset-observation-category.xml` includes all codes from `http://terminology.hl7.org/CodeSystem/observation-category`, and active `Observation.category` source binds to `http://hl7.org/fhir/ValueSet/observation-category`.

Additional context:
FHIR-34408, FHIR-37560, and FHIR-52872 are the same symptom Observation category change family. UP-738 is Proposal Implemented and updated the UTG/THO source-of-truth object `input/sourceOfTruth/fhir/codeSystems/CodeSystem-observation-category.xml`; its rationale explicitly includes FHIR-50889 and related symptom tickets. OO minutes record that the group had already decided to add symptom and had created a UTG ticket, while Zulip announcements confirm UP-738 was intended to make the observation-category updates available for related R6 work. The combined branch already contains an external-repo audit commit for FHIR-52872, but not for this seed issue.

AutoFHIR reconciliation:
This commit intentionally makes no source change in the FHIR core checkout. The requested `symptom` code belongs to the external THO/UTG Observation Category CodeSystem, while core already imports that CodeSystem wholesale and binds Observation.category to the importing ValueSet. Current THO exposes `symptom` and the current FHIR build expansion includes it.

Recommendation:
Keep this audit commit as-is for FHIR core. No duplicate local CodeSystem concept should be added to core; any remaining follow-up belongs to THO/UTG release management if the external terminology publication or package version needs coordination.
