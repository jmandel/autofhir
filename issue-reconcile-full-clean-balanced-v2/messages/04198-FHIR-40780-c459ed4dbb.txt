FHIR-40780: Correct answerValueSet invariant text

Issue request:
FHIR-40780 was Applied with a Persuasive with Modification resolution for Questionnaire.item.answerOption/answerValueSet inconsistencies. The final decision aligned answerOption item types with answerOption.value[x], added a separate answerValueSet invariant limited to coding, string, and uri items, documented answerValueSet interpretation, and required answerOption.value[x] to match item.type.

Initial application:
The issue was initially applied in commit 463dec9a70a3ff9d42135f14e29d07924f1a0e19, which added que-5b, expanded answerOption value types, added que-18a/que-18b, and added invariant tests. Follow-up QA cleanup in 7ad13b103ce corrected the que-5 and que-5b expressions to their current union form, but the human text for que-5b still described the old broad answerOption rule rather than the new answerValueSet rule.

Additional context:
Questionnaire is an active approved resource in source/fhir.ini, so source/questionnaire/structuredefinition-Questionnaire.xml is in build scope. Current source already applies the substantive FHIR-40780 constraints: answerValueSet carries condition que-5b, the que-5b expression allows only coding/string/uri item types, answerOption.value[x] includes the requested choices, and que-18a enforces value/type alignment. Zulip discussion and FHIR SDC minutes support that the tighter restriction was for answerValueSet while answerOption broadened.

AutoFHIR reconciliation:
Updated the que-5b human-readable invariant from the stale answerOption wording to "Only coding, string, or uri items can have answerValueSet" so generated constraint prose matches the normative expression and the applied resolution.

Recommendation:
Keep this source fix. No further core change is needed for FHIR-40780 unless the work group wants to revisit the broader answerValueSet design in a new tracker.
