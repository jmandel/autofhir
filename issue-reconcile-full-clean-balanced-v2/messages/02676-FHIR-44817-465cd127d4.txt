FHIR-44817: Audit Resource.id FHIRPath typing

Issue request:
FHIR-44817 was an Applied FHIR-I clarification request asking whether Resource.id/Patient.id should be treated in FHIRPath as System.String or FHIR.id. The Jira resolution text records the concern that Resource.id is intended to be constrained by the FHIR id datatype while lacking id/extension children, and the issue was applied for R6.

Initial application:
The current branch already contains explicit Jira-tagged application commit 415c4e014b, which added Resource.id examples to source/fhirpath.html. Those examples state that Patient.id is System.String and that Patient.id is not FHIR.id. The underlying Resource StructureDefinition source also defines Resource.id with type code http://hl7.org/fhirpath/System.String and a structuredefinition-fhir-type extension value of id.

Additional context:
FHIR-25274 previously published the System.String-plus-fhir-type documentation pattern for simple elements that should not inherit primitive id/extension children. Later final issue FHIR-45989 resolved no-change and states that Resource.id is defined as System.String with FHIR type id: it behaves as a string with no extensions on the wire, while its wire value remains limited by id datatype character and length rules. The Zulip thread linked from FHIR-44817 confirms the original ambiguity; related FHIR-37861 proposes further case/comment cleanup for the same FHIRPath examples, but its workflow status is not Applied/Published, so it is context rather than source-edit scope for this seed.

AutoFHIR reconciliation:
No source change was made. The current FHIRPath page and Resource StructureDefinition already express the current reconciled rule: Resource.id is represented as a FHIRPath System.String value constrained by FHIR id rules, not as a full FHIR.id primitive with id/extension children.

Recommendation:
Keep this audit commit as-is for FHIR-44817. Do not change Resource.id to FHIR.id as part of this seed; if the work group later applies FHIR-37861 or another issue, handle the case annotations and explanatory comments under that issue's own workflow decision.
