FHIR-30799: Audit maxDecimalPlaces questionnaire context

Issue request:
FHIR-30799 was a Published/Persuasive FHIR-core technical correction asking whether the maxDecimalPlaces extension should explicitly list Questionnaire.item.item because the R4 extension page listed Questionnaire.item but not the nested item path.

Initial application:
The Jira application comment explained that a context of Questionnaire.item already supports Questionnaire.item.item and deeper recursive items, so explicit Questionnaire.item.item contexts were unnecessary. Lloyd McKenzie cited core commit d9dcf0b2aca077ad85aaa237838a28f3608671f5, which removed redundant Questionnaire.item.item contexts from questionnaire-specific extension definitions; the maxDecimalPlaces row was already represented with Questionnaire.item and ElementDefinition in the active element extensions spreadsheet at that point.

Additional context:
The current core build no longer contains the authoritative maxDecimalPlaces StructureDefinition source; commit dd468d4f1799dd79819315b211588ef1cf4586e0 removed these extension definitions from the R5 core source. The extension now lives in the FHIR Extension Pack, whose current StructureDefinition-maxDecimalPlaces.xml and published build page list Questionnaire.item and ElementDefinition contexts and do not list Questionnaire.item.item. The original Zulip thread confirms the intended behavior: maxDecimalPlaces should be usable at any questionnaire item layer. No Confluence evidence was found that changes that conclusion.

AutoFHIR reconciliation:
This is an empty no-change audit commit. No core source file was changed because the current core checkout has no active maxDecimalPlaces definition to edit, and the current authoritative extension-pack definition already preserves the Jira decision by using Questionnaire.item without the redundant nested path.

Recommendation:
Keep this audit commit as-is. If future validation tooling treats Questionnaire.item as excluding nested Questionnaire.item.item instances, that should be handled as a validator/context-interpretation defect or in the Extension Pack, not by adding duplicate Questionnaire.item.item context rows back to core.
