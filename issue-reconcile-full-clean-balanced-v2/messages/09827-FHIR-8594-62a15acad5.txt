FHIR-8594: Audit ElementDefinition type-code binding

Issue request:
FHIR-8594 was Published/Persuasive for DSTU1 and reported that ElementDefinition.type.code was bound to the data-types value set even though core StructureDefinitions used resource names plus the special xhtml and * type-code cases.

Initial application:
The issue was applied in git-svn revision 6371 by commit 0c3f6c7312134abd6957687e714ffcdab61a9f2e, which changed ElementDefinition.type.code from the old DataType binding to FHIRDefinedType and fixed validation/tooling fallout from stricter code validation.

Additional context:
Later ElementDefinition decisions changed the shape of the same area. FHIR-12245 made ElementDefinition.type.code a uri for logical-model support. FHIR-35853 then introduced FHIRPathTypes and an ElementDefinition-specific value set so the binding would include the FHIRPath system codes used in core definitions. FHIR-32069 later renamed/reorganized the terminology sources, leaving the current active source bound to ElementDefinitionTypes. source/fhir.ini keeps ElementDefinition active and normative, so source/datatypes/elementdefinition.xml and source/terminologies/bindings.xml are in the current build scope.

AutoFHIR reconciliation:
No source change was made. The current ElementDefinition.type.code row is a uri with the ElementDefinitionTypes binding, that binding is extensible, source/terminologies/valueset-elementdefinition-types.xml imports FHIRPath types and all FHIR types, and the current generated/published fhir-types code system includes resource types and xhtml. The remaining * value is the documented open-type wildcard on source/datatypes.html rather than a normal FHIR type code, so adding it to the generated FHIR type code system would be a semantic change not supported by this old issue.

Recommendation:
Keep this audit commit as-is. Any future desire to make the wildcard a formal terminology concept should be raised as a new FHIR-I terminology/design issue rather than inferred from FHIR-8594, because the current spec already covers the original data-types binding mismatch and documents the wildcard special case.
