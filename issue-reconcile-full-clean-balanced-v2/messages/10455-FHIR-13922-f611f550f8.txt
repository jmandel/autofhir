FHIR-13922: Audit async API support

Issue request:
FHIR-13922 was a Published/Persuasive FHIR-core change request raised for STU3 to add asynchronous access pattern support to the base FHIR API and consider what CapabilityStatement should say about it. The recorded resolution was that the then-external Bulk Data specification would be integrated into the FHIR specification and maintained through the usual process.

Initial application:
No source-history commit found during this reconciliation explicitly names FHIR-13922. The apparent initial application was commit aa08450fd95f3590fa11c94cc74f2e1a5d9b4a2b, which created source/async.html and moved the bulk-data asynchronous API material out of source/http.html. The current RESTful API and documentation pages still link to source/async.html, so the async page is part of the current core build surface.

Additional context:
Later final decisions refined the original application rather than leaving a missing seed change. FHIR-35936 split and aligned the async page with community Bulk Data work. FHIR-24882 clarified async interaction outcomes for non-GET interactions. FHIR-47271 clarified how _outputFormat disambiguates the Bulk Data and Interaction patterns. FHIR-41202 added OperationDefinition.synchronicity and points the async page to synchronicity extensions for CapabilityStatement declarations. Those related issues are already represented on the combined branch and are not republished here. FHIR-I 2019 WGM minutes also show the work group did not want a one-off async export discovery protocol in CapabilityStatement, preferring Bulk Data conformance declaration through CapabilityStatement.instantiates and later/generic Prefer-header mechanisms.

AutoFHIR reconciliation:
This audit commit makes no source change. Current source/async.html defines the asynchronous request-pattern landing page, references RFC 7240 respond-async behavior, covers FHIR defined interactions and operations, distinguishes Bulk Data and Interaction patterns, and documents the current conformance hooks. Reintroducing the old detailed Bulk Data prose into core would conflict with later decisions that keep detailed pattern text in the Bulk Data/API Incubator materials.

Recommendation:
Keep this no-change audit as-is. Future detailed async-pattern changes should be handled under their specific Jira issues and, when the detailed page lives outside core, in the API Incubator, Bulk Data IG, or FHIR Extension Pack rather than by reopening the STU3 seed request.
