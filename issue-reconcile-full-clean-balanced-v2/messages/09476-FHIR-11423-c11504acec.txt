FHIR-11423: Audit Request priority application

Issue request:
FHIR-11423 was Published/Persuasive with Modification for the DSTU2 Request pattern. The ballot comment asked to add Coding to Request.occurrence[x] to express STAT/high/low priority; the accepted resolution said coded timings were already supported in Timing and that a separate Request.priority element would be added.

Initial application:
The historical workflow commit 839bf586d6 explicitly included #11423 and added Request.priority 0..1 as a coded RequestPriority element with routine, urgent, asap, and stat codes, while leaving Request.occurrence[x] as dateTime|Period|Timing. That matches the implemented intent of separating priority from timing, even though the Jira resolution text used the broader word CodeableConcept.

Additional context:
The current build configuration lists request as an active logical pattern, and the current Request spreadsheet still carries Request.priority with the request-priority code system/value set and leaves occurrence limited to date/time/timing datatypes. A later same-element issue, FHIR-55655, discusses the binding strictness for Request.priority and is only Resolved - change required in the current default run scope; it does not justify changing this seed issue's already-applied priority element.

AutoFHIR reconciliation:
