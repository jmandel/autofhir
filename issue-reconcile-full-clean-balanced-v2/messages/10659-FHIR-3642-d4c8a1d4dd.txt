FHIR-3642: Audit profile fixed value handling

Issue request:
FHIR-3642 was a Published/Persuasive DSTU1 FHIR-core tooling correction asking that fixed values entered in profile spreadsheets, including primitive and complex values in the Value column, appear in the displayed differential/delta view and in the published XML.

Initial application:
The Jira comment says the issue was applied in SVN revisions 3106-3108. Imported git history matches that exactly: commits 07350c04a9cbd9911f0e65b9d8ecaec300eda5c9, 811e87592ebc2425a53b8053850c9547952bb4ce, and 1a8d67cffc77fa49beabe685f0c2445c5ca6cb98 are all titled "{#3642}: put fixed values into profiles" and carry git-svn ids build@3106, build@3107, and build@3108. Those patches parsed spreadsheet Value, Pattern, and Example cells into typed values, copied them into profile ElementDefinition output, and rendered fixed values instead of omitting them or showing a placeholder.

Additional context:
The original DSTU1 Java tooling paths and profile template files touched by the application commits no longer exist in the current FHIR checkout. Current build-scope source still has active spreadsheet profile inputs in source/fhir.ini, current narrative documents ElementDefinition.fixed[x], and current authoritative StructureDefinition XML can contain fixed values such as the active Parameters FHIRPath Patch profile's fixedString slice names. No relevant Zulip or Confluence record was found that reverses or narrows the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The historical request was already applied to the old tooling, the current source surface already supports and documents fixed[x] values, and the removed historical tooling paths leave no current in-repository correction to make for this old DSTU1 issue.

Recommendation:

If a future build shows fixed values from current spreadsheet profiles missing from rendered differentials or generated XML, handle that as a current publisher/tooling defect in the responsible tooling repository rather than reopening this already-applied DSTU1 source issue.
