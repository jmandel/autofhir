FHIR-16428: Point CORS note to security guidance

Issue request:
FHIR-16428 was a Published FHIR-I change request, resolved Persuasive, asking that the HTTP page stop recommending CORS as a gross security recommendation because CORS is appropriate only under specific conditions and can be dangerous if configured permissively.

Initial application:
The issue was partially applied in commit b294d647ed, following related commit 6f65400358 for FHIR-17307. Those commits moved the ongoing CORS security-holes note to source/security.html and added a security-page reference from source/http.html, but the current HTTP page still said servers SHOULD implement CORS and linked the CORS phrase to Enable-CORS rather than to the security guidance.

Additional context:
FHIR-13827 later softened the security page wording to say servers should consider CORS when browser-based JavaScript clients are desirable and should consult W3C, Enable-CORS, and Moesif guidance. The HTTP page remained inconsistent with that applied security-page decision.

AutoFHIR reconciliation:
Rewrote the HTTP-page note so it no longer recommends that servers SHOULD implement CORS. It now states that browser-based client applications may require CORS support and directs readers to security.html#http for CORS considerations and related security guidance. The edited root source/http.html page is part of the current built RESTful API narrative.

Recommendation:
Keep this commit. It completes the FHIR-16428 HTTP-page portion of the same CORS guidance family without changing the more detailed security-page wording.
