FHIR-20398: Audit canonical server policy guidance

Issue request:
FHIR-20398 was Published/Persuasive with Modification for R5. It asked for best-practice guidance around server handling of duplicate or versioned canonical URLs, especially when StructureDefinitions or SearchParameters have the same canonical URL in different server deployment contexts. The accepted resolution was to add guidance in the canonical section of the references page explaining that url+version and unversioned canonical URLs might not resolve to a single record and that resolution is a matter of server policy.

Initial application:
The issue was applied in commit 1c4a35dbe293f96f5b95682b627ef541a838ea92, which added the "Choosing the right Canonical Reference" section to source/references.html. That section directly covered no-version, partial-version, and full-version duplicate matches, described duplicate same-version resources as generally an editorial error, and explained that servers choose a default based on version, publication date, status, and local policy knowledge.

Additional context:
The original Zulip thread supports avoiding a universal uniqueness rule because different repository, validation, terminology, and archive use cases have different needs. Vocab minutes moved the issue to FHIR-I as an implementation issue, and FHIR-I minutes record the Persuasive with Modification vote. Later source changes, including FHIR-52895 and FHIR-39270, refined the same references.html canonical matching area by adding package/version matching detail and a narrow same-canonical-version multiple-form exception, but they did not remove the core FHIR-20398 server-policy guidance.

AutoFHIR reconciliation:
Made no source change. The current build-scope references page still contains the requested canonical guidance: it flags multiple matches as policy-dependent, explains no-version, partial-version, and full-version duplicate cases, says the spec does not define the server algorithm, and names the information a server can use to select the default canonical resource.

Recommendation:
Keep this empty audit commit. FHIR-20398 is represented in the current source, and adding separate server-type uniqueness rules or CapabilityStatement extensions would go beyond the published resolution and re-open the policy choice that the work group intentionally left to server deployments.
