FHIR-9853: Audit Resource-level _list search

Issue request:
FHIR-9853 was a Published/Persuasive FHIR-I change request, raised against DSTU2 and applied for R5, asking to allow the standard _list search parameter at the Resource level. The requested behavior was that a server-root search such as GET [base]/?_list=101 can return all resource types referenced by the nominated List, instead of only type-scoped searches such as Observation?_list=.

Initial application:
The Jira comments show Richard Ettema confirmed in May 2021 that the change had not yet been applied and asked whether the now-normative search page made it a technical correction. The Jira-tagged commit 0ad8347015dc36b2f56cb96aeaad8fee2352c541 then added a Resource-_list SearchParameter to source/resource/bundle-Resource-search-params.xml and clarified source/search.html. Current source still contains that Resource-level SearchParameter and the server-root _list example.

Additional context:
The Resource source is in current build scope through source/fhir.ini's active type-page and resource-infrastructure entries. Later search work did not reverse the seed decision: FHIR-31387 handled the structured _list SearchParameter and its summary row, FHIR-37846 retained _list for backward compatibility and List-specific functional-list behavior while adding _in for broader membership searches, and FHIR-39342 linked the functional-list wording. FHIR-9816 is related background for List, Group, and CareTeam membership searching but is not needed to decide this seed.

AutoFHIR reconciliation:
No source change was made. Current build-scope source already permits Resource-level _list: source/resource/bundle-Resource-search-params.xml defines Resource-_list as a common special SearchParameter, source/search.html documents _list and gives GET [base]/?_list=101 as the example for any resource referenced by a List, and the common-parameters summary row points to Resource-list.

Recommendation:
Keep this audit commit as-is. The current source satisfies the FHIR-9853 request, and further membership-search evolution should remain with the later _in/_list issue family rather than reopening this applied Resource-level _list decision.
