FHIR-31377: Clarify Consent status code scope

Issue request:
FHIR-31377 was a Published FHIR-core Consent change request asking to add a reason associated with Consent status, such as a reason for declining consent. The final Not Persuasive with Modification resolution did not add Consent.statusReason; it directed the status code descriptions to state that Consent.status is the status of the resource, not of the patient's consent, and added Scope guidance pointing to Provenance, DocumentReference, and Contract for ceremony/status-change tracking.

Initial application:
The Jira-tagged source commit ec8ea03fab4 added the requested Scope paragraph to source/consent/consent-introduction.xml. Later cleanup left Consent.status itself saying "current state of this Consent resource," but the active ConsentState CodeSystem description, ValueSet description, required binding description, and individual code definitions still described "the consent" rather than the Consent resource.

Additional context:
source/fhir.ini actively includes consent=Consent and codesystem=CodeSystem, so the Consent resource folder and terminology XML are in current build scope. FHIR-31769 is a same-status-family no-change decision stating that ConsentState is the state of the Consent resource and that the state of the consent itself belongs in the source document. FHIR-48997 later asks the FHIR Extension Pack to allow event-statusReason on Consent, but it remains Triaged and unresolved, so it does not supersede the core R5 decision.

AutoFHIR reconciliation:
This commit updates the active ConsentState CodeSystem description and concept definitions, the ConsentState ValueSet description, and the Consent.status binding description to consistently say Consent resource. It leaves the already-applied Scope paragraph intact and does not add a Consent.statusReason element.

Recommendation:
Keep this source fix. If FHIR-48997 or a future CBCP/Security decision approves a statusReason extension or core element for Consent, handle that as a separate extension-pack or future-core change rather than reopening this R5 clarification.
