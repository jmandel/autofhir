FHIR-7932: Audit optional capabilities ETag

Issue request:
FHIR-7932 was a Published/Persuasive DSTU1 RESTful API issue asking to make ETag support for the Conformance resource optional. The requested semantic change was to replace the requirement that an ETag header SHALL be returned with the conformance resource with SHOULD, because other resources did not require ETags and Conformance should not need special mandatory handling.

Initial application:
The Jira comments record svn revision #5342. The git-svn history contains faf642834768d4564aa59e6488b2750d0ee74351, "#7932 - change conformance from SHALL to SHOULD", from build@5342. That commit changed source/http.html from "An ETag header SHALL be returned with the conformance resource" to "An ETag header SHOULD be returned with the conformance resource" while retaining the separate consistency rule for the value when an ETag is returned.

Additional context:
The Conformance resource has since been renamed to CapabilityStatement, and the REST interaction is now the capabilities interaction. FHIR-40496 and commit 08e2ca9544ccdc4e19a042aa50bc35239a927da0 later clarified the capabilities section while preserving "An ETag header SHOULD be returned with the response" and linking to the general versioning and HTTP header guidance. The current source/http.html page is the active RESTful API page linked from source/documentation.html.

AutoFHIR reconciliation:
Published an empty audit commit. No source change is needed because current source/http.html already implements the FHIR-7932 semantic change: a capabilities-response ETag is recommended, not mandatory. The remaining SHALL only requires the value to change if a returned ETag is used for a changed returned resource; it does not make ETag support mandatory.

Recommendation:
Keep this no-change audit commit as-is. No FHIR-7932 follow-up source edit is recommended unless the work group separately wants to revisit the generic rule that a returned ETag must remain consistent with the returned resource version.
