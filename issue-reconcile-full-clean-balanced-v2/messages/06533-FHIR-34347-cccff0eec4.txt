FHIR-34347: Audit root mustSupport best-practice invariant

Issue request:
FHIR-34347 was a Published FHIR-core StructureDefinition issue, resolved as Not Persuasive with Modification for R5. It asked to address confusing mustSupport semantics on the root element of profiles and extensions, and the approved disposition was to add a StructureDefinition best-practice invariant warning that the root element of a profile should not have mustSupport=true because mustSupport is determined by the referencing element/type context.

Initial application:
The issue was applied before this reconciliation by git commit a9fc52f30b8e64be902b7bc30186f6a3cd9179c2, which added constraint sdf-26 to source/structuredefinition/structuredefinition-StructureDefinition.xml with the approved best-practice wording and FHIRPath/XPath check. The current source retains that invariant in the active StructureDefinition resource source, with the detailed rationale carried by the best-practice explanation extension and the concise human text/expression attached to StructureDefinition.snapshot.

Additional context:
source/fhir.ini lists structuredefinition=StructureDefinition as an active build resource, so the checked XML is in current build scope. The originating Zulip thread asked how to interpret mustSupport on resource/profile roots, and Lloyd McKenzie advised filing the tracker against StructureDefinition. Patient Care IPS minutes later referenced FHIR-34347 while removing root-level mustSupport from IPS profiles, which is consistent with the core invariant. Later FHIR-50391 clarified mustSupport and obligations for repeating elements and slices; it does not reverse or narrow the root-profile best-practice rule.

AutoFHIR reconciliation:
This is an empty audit commit. No source edit was needed because the current active StructureDefinition source already contains sdf-26, including the best-practice marker, explanation, human text, and expression preventing element[0].mustSupport=true in the snapshot.

Recommendation:
Keep this audit commit as-is. No follow-up is needed in FHIR core unless a future work-group decision intentionally changes root-level mustSupport semantics.
