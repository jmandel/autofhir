FHIR-3857: Audit ConceptMap batch translate handling

Issue request:
FHIR-3857 was a Published/Persuasive DSTU1 request to add batch mode for ConceptMap translation so clients could submit multiple source codings/codeable concepts with per-item target systems/value sets and receive corresponding concept-translation outcomes.

Initial application:
The request was initially applied in svn revision 4526, imported as git commit f16595324f39903eda2d89de8c2e30744b13e8ff, by adding a separate batch/batch-translate operation to the old ConceptMap spreadsheet source. That source form is no longer part of the current build.

Additional context:
FHIR-8416 is the later Published/Persuasive decision that explicitly removed the dedicated batch validation and translation operations because the generic FHIR batch interaction could execute operations in one request. Its implementation commit 42d6bcd1e0f35bb81ca063f979a852748e5db198 removed the batch-translate rows from the ConceptMap spreadsheet. The current HTTP source still says batch/transaction can perform multiple extended operations and processes each entry as an individual operation. The current ConceptMap $translate OperationDefinition remains a single-concept operation with repeatable match output, which is consistent with the later removal rather than an unapplied FHIR-3857 gap.

AutoFHIR reconciliation:
This commit makes no source change. Reintroducing a ConceptMap batch-translate operation or changing the current normative $translate input cardinalities would reverse FHIR-8416 and would need a new work-group decision, especially because later informal terminology discussion shows renewed interest in operation batching but no final Jira disposition for changing core $translate.

Recommendation:
Keep this audit commit as-is. If implementers want a shared-parameter batch $translate beyond ordinary Bundle batch entries, open and resolve a new terminology/FHIR-I proposal rather than restoring the obsolete DSTU1 batch operation from FHIR-3857.
