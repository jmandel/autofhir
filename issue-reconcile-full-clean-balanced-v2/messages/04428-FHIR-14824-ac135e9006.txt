FHIR-14824: Audit Encounter.class cardinality

Issue request:
FHIR-14824 was Published/Persuasive for STU3 and asked that Encounter.class be mandatory 1..1 because the Encounter notes described class as required and classHistory.class was already 1..1.

Initial application:
The issue was applied in the historical spreadsheet by d9eb43b4d33236a32920636c5450e52ea95e3851 (GF#14824: Make Encounter.class mandatory (1..1)). The Jira comments also state that Encounter.class was already 1..1 in the then-current build.

Additional context:
Later R5 work intentionally changed the same element. FHIR-32341 was Published/Persuasive with Modification and resolved Encounter.class to 0..* CodeableConcept with a preferred binding. FHIR-32342 made the datatype CodeableConcept. FHIR-39014 then challenged the 1..1 to 0..* change and was Resolved - No Change, explaining that legacy and jurisdictional variation make a base 1..1 requirement inappropriate and that profiles can require class. FHIR-42918 corrected the leftover notes text from "required" to "should be provided." The current source/fhir.ini actively includes Encounter in the build.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active source/encounter/structuredefinition-Encounter.xml now has Encounter.class as 0..* CodeableConcept with a preferred EncounterClass binding, and source/encounter/encounter-notes.xml says class should be provided, so restoring 1..1 would contradict later final PA decisions.

Recommendation:
Keep this audit as-is. Do not reapply FHIR-14824 to the current core build; use profiles for use cases that need Encounter.class 1..1, consistent with FHIR-39014.
