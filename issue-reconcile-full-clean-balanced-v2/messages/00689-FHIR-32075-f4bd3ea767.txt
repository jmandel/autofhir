FHIR-32075: Clarify process note references

Issue request:
FHIR-32075 was Published/Persuasive for R5 and asked FM to clarify the relationship between ClaimResponse item/detail/subDetail/addItem noteNumber values and ClaimResponse.processNote, with matching clarification for ExplanationOfBenefit. The issue specifically noted that the former note wording had become processNote and asked for the definitions/comments and resource pages to explain that noteNumber values point to processNote.number.

Initial application:
The only Jira-tagged application found was d0f1565c05, which added narrative Additional Information paragraphs to source/claimresponse/claimresponse-notes.xml and source/explanationofbenefit/explanationofbenefit-notes.xml. Those paragraphs explain that noteNumber values match processNote.number values, but the StructureDefinition definitions for noteNumber, processNote, and processNote.number remained the older generic wording.

Additional context:
ClaimResponse and ExplanationOfBenefit are active resources in source/fhir.ini, so their StructureDefinition XML files are in current build scope. Searches found no FHIR-32075 Zulip or Confluence discussion and no conflicting later core Jira decision. FHIR-32776 was applied in the same historical commit but concerns separate adjudication/supportingInfo and sequence-number guidance, so it is background rather than a separate decision here.

AutoFHIR reconciliation:
This commit updates the active ClaimResponse and ExplanationOfBenefit StructureDefinition definitions so every noteNumber element explicitly identifies the corresponding processNote.number values, and so processNote/processNote.number state that items, details, sub-details, and added items can reference those notes. It leaves the already-applied narrative pages unchanged.

Recommendation:
Keep this source fix as-is. It completes the missed conformance-definition part of the published clarification without changing cardinalities or adding a new invariant; any stronger machine-checkable constraint should be a separate FM decision.
