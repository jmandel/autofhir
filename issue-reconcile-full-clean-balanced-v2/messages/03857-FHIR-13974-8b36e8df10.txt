FHIR-13974: Audit Procedure reason usage guidance

Issue request:
FHIR-13974 was Published/Persuasive with Modification for STU3 Patient Care Procedure. It asked to clarify when Procedure.reasonCode versus Procedure.reasonReference should be used, add a usage comment that a Procedure can itself justify another Procedure, and allow Procedure.reasonReference to reference Procedure as well as Condition and Observation.

Initial application:
The issue was applied in the 2017-11-13 commit 52ac1cc0e7, which updated the Procedure spreadsheet so reasonReference allowed Procedure, Condition, Observation, DiagnosticReport, and DocumentReference and added the generic reason wording family. A later 2018-07-20 commit 2abadfb0e6 explicitly mentioned GF#13974 and GF#16346 and added the reasonCode/reasonReference usage comments.

Additional context:
FHIR-16346 later clarified the same Procedure reason guidance and is already represented on the combined branch. Current source has since refactored Procedure.reasonCode and Procedure.reasonReference into the active Procedure.reason CodeableReference element, so the old split-element text is preserved through Procedure.reason.concept/reference guidance rather than as separate STU3 element comments.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active Procedure resource is in source/fhir.ini, and source/procedure/structuredefinition-Procedure.xml already defines Procedure.reason with the requested Procedure target profile plus Condition, Observation, DiagnosticReport, and DocumentReference, and explains when to use the concept versus reference form.

Recommendation:
Keep this audit as-is. Do not reintroduce the old separate reasonCode/reasonReference prose unless a future work-group decision reverses the CodeableReference model or asks for additional Procedure-specific examples.
