FHIR-33945: Clarify JSON Patch transaction Binary example

Issue request:
FHIR-33945 was Published/Persuasive for R5 and asked FHIR-I to document support for using a Binary resource to carry a JSON Patch body in batch/transaction Bundles. The recorded FHIR-I discussion accepted the Binary pattern and specifically called out that the example should not use a relative Bundle.entry.fullUrl such as Patient/1, and should explain that fullUrl identifies the resource acting as the patch input/output rather than the patch metadata itself.

Initial application:
The issue was initially applied in f656fee32c8a7c9edb711e84c5046da777a1ab55, merged by 77022fe0d3a8434ac49063cdca14882268a2da12, which added the JSON Patch batch/transaction subsection to source/http.html. That application preserved the core Binary mechanism but left the example with "JSON Path" wording, a relative fullUrl of Patient/1, and no note explaining what fullUrl identifies.

Additional context:
The current source still contains the FHIR-33945 subsection on the active RESTful API page. Later R6 normative cleanup removed the trial-use wrapper but did not change the example semantics. Zulip implementer discussion shows the original Binary-in-Bundle JSON Patch pattern and confusion caused by using Binary as the entry resource while the request URL targets another resource. Confluence minutes show FHIR-I revisited the issue for vendor input and then voted FHIR-33945 Persuasive 12-0-2 on 2022-03-14.

AutoFHIR reconciliation:
This commit keeps the accepted Binary mechanism and corrects only the missed application details: the prose now says JSON Patch rather than JSON Path, the example uses an absolute fullUrl, and a short note explains that fullUrl identifies the patched resource, not the Binary patch document.

Recommendation:
Keep this source correction as-is. It aligns the current active HTTP page with the published FHIR-I decision without broadening the patch mechanism or deciding any separate conditional-patch behavior.
