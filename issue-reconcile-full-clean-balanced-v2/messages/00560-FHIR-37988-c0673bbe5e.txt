FHIR-37988: Audit Measure evaluate return cardinality

Issue request:
FHIR-37988 was Published/Persuasive for R5 and asked CQI to fix Measure $evaluate-measure because the return parameter was constrained to a single MeasureReport even though provider/subject evaluation can produce multiple results. The final resolution changed the return parameter to 0..* Bundle, with one Bundle per input subject and MeasureReport content plus evaluated/created resources in each Bundle.

Initial application:
The issue was applied before this reconciliation by PR 2305 in commit 804ded2ef07b29df6025e1a19c572d334c226219, followed by cleanup commit 060b160cb531b79f1eea1a1b04bf759bd809fc2a. The historical patch changed source/measure/operationdefinition-Measure-evaluate-measure.xml from return 1..1 MeasureReport to return 0..* Bundle and updated the operation-level wording. The Measure resource is active in source/fhir.ini, and source/measure/list-Measure-operations.xml still lists both the current Measure-evaluate operation and the retired Measure-evaluate-measure operation.

Additional context:
The current build now has a newer Measure-evaluate operation and retains Measure-evaluate-measure as retired/deprecated. Both operation definitions now use return min 0, max *, type Bundle. Later CQI work, including FHIR-51487 already represented on the combined branch, clarified the return documentation to state that Bundles contain 1..* MeasureReport resources and that the multi-cardinality return is represented using a Parameters response. FHIR-40422 also refined group-level Measure subject support and current Measure evaluate wording. Searches found no directly relevant Zulip or Confluence record for FHIR-37988 that conflicts with the Jira/source history.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The authoritative current operation sources already satisfy FHIR-37988: the returned value is 0..* Bundle rather than 1..1 MeasureReport, examples show a Parameters response containing a Bundle return resource, and the linked quality-reporting guidance discusses Bundle organization by subject. The note in the original issue about possible OperationOutcome output was not adopted by the final resolution, and operation failures are handled by the general operations/REST framework rather than by adding OperationOutcome as an explicit success return parameter here.

Recommendation:
Keep this no-change audit commit as-is. No FHIR-core source follow-up is needed for FHIR-37988 unless CQI opens a separate issue to add operation-specific error-response guidance.
