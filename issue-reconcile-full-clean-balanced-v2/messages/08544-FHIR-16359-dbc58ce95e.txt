FHIR-16359: Audit CapabilityStatement searchParam definition guidance

Issue request:
FHIR-16359 was a Published/Persuasive with Modification FHIR-core change request asking that CapabilityStatement.rest.resource.searchParam.definition be required when a computable search parameter is declared. The accepted resolution did not change the cardinality to 1..1; it required a usage note saying the element SHALL be populated when the search parameter refers to a SearchParameter defined by core FHIR or an external IG.

Initial application:
The issue was applied by git-svn commit a4513eabdaf4c85c13820b36cc9216261c71caa4, which references GF#16359 and svn revision 13887 and added the accepted SHALL-populate note to the CapabilityStatement spreadsheet source. The same note is now present in the current generated StructureDefinition source for CapabilityStatement.rest.resource.searchParam.definition.

Additional context:
CapabilityStatement is in current build scope through source/fhir.ini. The current source keeps CapabilityStatement.rest.resource.searchParam.definition at 0..1, which matches the modified resolution rather than the original 1..1 request. A later same-area change, FHIR-46110 / commit 4bf721b04fa1d03d77120c37f1b206c594dea3f6, added guidance that non-true search parameters such as _format and _count SHALL omit .definition and use type special, which further supports not forcing the element to 1..1 in all cases.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active source already includes the FHIR-16359 usage note in both the element definition and comment, while the optional cardinality remains necessary for the later-documented non-SearchParameter cases.

Recommendation:
Keep this no-change audit commit as-is. Do not change the cardinality to 1..1 unless the work group reopens the question and supersedes both the FHIR-16359 modified resolution and the current non-true SearchParameter guidance.
