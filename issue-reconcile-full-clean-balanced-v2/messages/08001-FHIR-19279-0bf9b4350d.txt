FHIR-19279: Audit Coding display validation warning

Issue request:
FHIR-19279 was a Published/Persuasive FHIR-I issue for R5 asking that the validator not warn, when validating an instance against a profile, merely because an instance Coding.display differs from a ValueSet concept display. The decisive Jira comments say display/designation handling cannot be determined from the ValueSet alone, and the final 2021 comment marked the issue fixed because the remaining warning case was base-resource validation without the profile value set binding, where a warning was appropriate and unavoidable.

Initial application:
No current git history entry in this FHIR source checkout explicitly mentions FHIR-19279. The issue appears to have been applied as validator/tooling behavior rather than as a source edit: Jira records it as fixed, while current build-scope source has no rule requiring validators to warn on ValueSet.include.concept.display mismatches. Current source instead carries the related $validate-code display-language caveat and later display-validation controls.

Additional context:
Later and more specific terminology decisions govern the current source. FHIR-37603 clarified Coding.display in datatypes.html: populated Coding.display SHALL be one of the code-system display strings, including CodeSystem.concept.display or CodeSystem.concept.designation.value, and displays defined in value sets are not allowed in Coding.display. FHIR-17218 preserved a caveat that ValueSet $validate-code language behavior for Coding.display was undefined at that time. FHIR-40770 and FHIR-41229 later added displayLanguage and lenient-display-validation semantics for CodeSystem/ValueSet $validate-code. ValueSet and CodeSystem are active resources in source/fhir.ini, and their operation lists include the validate-code OperationDefinitions, so those current-source checks are in build scope.

AutoFHIR reconciliation:
This audit commit intentionally makes no source changes. Adding new prose to suppress warnings against ValueSet concept displays would be redundant at best and could conflict with the later current rule that Coding.display is based on code-system displays/designations, not ValueSet include displays. The current source already separates profile/terminology validation caveats from $validate-code display severity controls.

Recommendation:
Keep this no-change audit. If validator users still see unwanted warnings when a profile-specific binding is available, that should be handled as validator/tooling behavior with a concrete reproduction; the current FHIR core source should not be changed to re-open the older ValueSet-display matching ambiguity.
