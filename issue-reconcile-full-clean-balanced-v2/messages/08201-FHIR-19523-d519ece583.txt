FHIR-19523: Audit no-filter resource search behavior

Issue request:
FHIR-19523 was Published with a Persuasive resolution. It asked the FHIR-core HTTP/search documentation to state explicitly that a search with no search parameters, such as GET [base]/Practitioner, returns all instances of that resource, while recognizing that servers may prohibit queries without or with insufficient parameters.

Initial application:
The issue appears to have been initially applied by 142ad7624ca77d81a9463a6ddbd278f521a109da (Fix FHIR-19523,22702,23809) on 2021-05-30, which added a paragraph to source/search.html saying that in the absence of search filters, GET [base]/Patient or POST [base]/Patient/_search with an empty body should return all records and that servers may prohibit queries without or with insufficient parameters. That commit also made unrelated edits for the other issue keys named in its subject.

Additional context:
FHIR-20392 is the same no-filter search behavior family and was already represented on the combined branch by 9019dd5cfad9c32eafac78bddfe26fe6e720541b. Its implementation commit 6600a9d1738b011230210afa99d7dbc7ea1cef89 revised the FHIR-19523 paragraph to cover both system and type search contexts, to say records are returned in scope of the search context, and to direct servers that reject overly broad searches to return an appropriate error instead of silently applying an implicit default filter. Later commits only wrapped the paragraph in conformance markup and adjusted punctuation. The Jira-linked Zulip thread for FHIR-19523 confirms the original clarification request: Lloyd McKenzie said it was implicit that omitting filters returns everything and invited a tracker to add an explicit sentence.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative source/search.html paragraph already says that, in the absence of any search filters, GET [base], GET [base]/Patient, POST [base]/_search, and POST [base]/Patient/_search with no body SHOULD return all records in scope of the search context, and that servers MAY reject overly broad searches with an appropriate error. That fully covers the seed request after considering the later FHIR-20392 refinement.

Recommendation:
Keep this empty audit commit as-is. Do not add duplicate wording to source/http.html or elsewhere unless the work group wants a navigation-only editorial restructure, because the current Search Inputs section already carries the normative behavior and duplicating it would increase maintenance drift.
