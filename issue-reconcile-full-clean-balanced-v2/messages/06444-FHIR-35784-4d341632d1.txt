FHIR-35784: Audit valuesets.xml ConceptMap generation

Issue request:
FHIR-35784 was Published/Persuasive for R4B and asked that contained ConceptMaps in the generated valuesets.xml download use the R4/R4B ConceptMap target element <equivalence> and R4 equivalence codes such as wider and narrower, instead of the R5 <relationship> element and source-is-* relationship codes. The accepted resolution was to correct the tooling so contained ConceptMaps are generated correctly.

Initial application:
No FHIR core source commit explicitly tagged FHIR-35784 was found. The Jira comment links HL7/kindling#69, merged 2022-04-07, whose body says generated instances should use the correct base-standard version when generating R4B and explicitly lists FHIR-35783 and FHIR-35784. In this checkout, tools/history/release4b/valuesets.xml was last introduced/updated by core commit cdc3309868 as part of the R4/R5 conversion framework and already contains the R4/R4B form.

Additional context:
FHIR-35783 is the direct sibling for conceptmaps.xml and cites the same Kindling PR. FHIR-32816 reports the same invalid contained ConceptMap pattern for the nhin-purposeofuse ValueSet in valuesets.xml. The current active source/valueset/valueset-nhin-purposeofuse.xml uses <relationship> and source-is-* codes because the current R5/R6 ConceptMap structure uses those names; changing the active source to <equivalence> would regress the current specification. The checked release5 valuesets.xml likewise uses the R5 relationship form, while the checked release4b valuesets.xml uses equivalence/wider/narrower. No Zulip or Confluence evidence was found that changes this conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current FHIR source is correct for the current build, and the checked R4B history valuesets.xml no longer contains the invalid R5 relationship element/codes that FHIR-35784 identified.

Recommendation:
Keep this audit commit as-is. Do not edit the active current ValueSet source for this issue; any future concern about regenerating historical R4B download artifacts should be handled in the generation tooling path, which HL7/kindling#69 already addressed for this issue family.
