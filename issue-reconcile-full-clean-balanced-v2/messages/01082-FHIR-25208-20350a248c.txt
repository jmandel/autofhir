FHIR-25208: Audit integer64 datatype coverage

Issue request:
FHIR-25208 was Published/Persuasive for FHIR core datatypes. It asked to add a signed long integer datatype, described in the resolution as int64, for event/count values that can exceed 32-bit integer range, and to note that JSON serialization is as a string.

Initial application:
No source commit explicitly tagged FHIR-25208 was found. The apparent initial application was the December 2019 datatype/subscription work after the vote: cbdf7d1e55dc4bfa1dc30fc526edee0491e05782 added the integer64 primitive row with xs:long and JSON string representation, and 38a923bf7f4ede5a598e29324da81895750a75fa changed subscription event-count source and examples to integer64.

Additional context:
The 2019 Zulip thread linked from Jira records the original subscriptions/event-count use case, the need to avoid decimal as a workaround, and discussion of string JSON serialization. FHIR Infrastructure minutes for 2019-11-25 record the motion to add int64. Later Published issues use the established FHIR name integer64: FHIR-26937 clarified JSON serialization for newer integer types and left integer64 as a string, and FHIR-26389 mapped FHIR.integer64 to System.Long in the FHIRPath table. The active source/fhir.ini type-page and type-characteristics settings keep datatypes.html and integer64 in current build scope.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/datatypes.html defines integer64 as a signed 64-bit integer with xs:long mapping and JSON String representation; source/datatypes/primitives.xml defines integer64 with schema type long and JSON type string; source/json.html explicitly says all other primitive types, including integer64, serialize as JSON strings; current SubscriptionStatus and Subscription operation source use integer64 where event counters need the larger range. The difference between the Jira shorthand int64 and current integer64 spelling is not a defect because later applied/published source and Jira context consistently establish integer64 as the FHIR datatype name.

Recommendation:
Keep this no-change audit commit. Do not rename integer64 to int64 or add duplicate prose; future changes to FHIRPath, RDF/ShEx, or package-specific support should remain with their separate trackers.
