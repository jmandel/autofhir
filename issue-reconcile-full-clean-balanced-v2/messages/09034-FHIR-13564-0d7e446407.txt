FHIR-13564: Clarify ambiguous may-not wording

Issue request:
FHIR-13564 was Published/Persuasive for STU3 as a non-substantive clarification. It asked that uses of "may not" be reviewed and changed to "might not" when they state possibility, or "shall not" when they state prohibition, because "may not" can be misread as a conformance prohibition.

Initial application:
The issue was originally applied in svn revision 12802, represented in git as d33191d634a51afc60193ac498c314a9fd2a6c7f, which changed 170 source files under the subject "#13564 - hunt and destroy all uses of 'may not'". That historical cleanup included the ValueSet example named in the Jira, which now says "might not" in source/valueset/structuredefinition-ValueSet.xml.

Additional context:
Later R5/R6 edits reintroduced the ambiguous wording in active core source: resource StructureDefinition XML, resource narrative snippets, search/subscription narrative pages, examples, terminology source, and fhir.ini migration text. source/fhir.ini lists the changed resources as active resources and includes the template lifecycle CodeSystem source. The remaining matches after this reconciliation are imported DICOM text in source/dicom/partD.html and an unreferenced StructureMap working note; those were left unchanged because they are not appropriate current FHIR-core source fixes for this issue. FHIR-48870 is a later Applied RelatedPerson boundaries issue that introduced one of the current phrases and is cited only as background, not independently reconciled here.

AutoFHIR reconciliation:
This commit replaces non-prohibitive "may not", "MAY not", and "MAY or MAY NOT" uses in current build-relevant FHIR source with "might not" or "might or might not". It changes the single apparent prohibitive "may NOT" narrative use to "SHALL NOT". No conformance expectation is changed; the edits only remove the ambiguity identified by FHIR-13564.

Recommendation:
Keep this source cleanup. If the project wants to prevent recurrence, a separate human-approved publisher/style validation rule could enforce the same wording policy while excluding imported external standards and non-built working notes.
