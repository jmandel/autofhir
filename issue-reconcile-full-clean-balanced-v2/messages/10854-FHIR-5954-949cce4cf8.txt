FHIR-5954: Audit OperationDefinition affectsState flag

Issue request:
FHIR-5954 was a Published/Persuasive FHIR-core OperationDefinition change request from DSTU1 asking for OperationDefinition to include an idempotent flag so clients and servers could determine whether HTTP GET invocation is allowed.

Initial application:
The issue was applied in SVN revision 5054, preserved in git as ed58e45af1f531ad118f3a35313f75ad16091101, which added OperationDefinition.idempotent as a 0..1 boolean with GET/idempotence guidance to the then-authoritative OperationDefinition spreadsheet source.

Additional context:
The current build-scoped OperationDefinition source is active through source/fhir.ini and contains OperationDefinition.affectsState, a 0..1 boolean carrying the same operational safety decision. Later Published issues refined that original element rather than removing it: FHIR-13018 renamed idempotent to affectsState, FHIR-14960 clarified POST/GET method support, and FHIR-18197 removed the misleading HTTP idempotent reference from the definition. source/fhir.ini also records the historical rename as OperationDefinition.idempotent=OperationDefinition.affectsState.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already satisfies the seed request through OperationDefinition.affectsState and its HTTP method comment, while preserving the historical rename mapping and later clarifications.

Recommendation:
Keep this audit commit as-is. No FHIR core source follow-up is needed for FHIR-5954; any future changes to operation HTTP method obligations should be handled under the later, already separate OperationDefinition method-support issues.
