FHIR-14848: Audit SearchParameter AND/OR support

Issue request:
FHIR-14848 was a Published/Persuasive with Modification FHIR-I change request from the STU3 ballot asking for a way to indicate whether logical AND and/or OR combinations are supported for search parameters, originally raised against CapabilityStatement.rest.resource.searchParam. The accepted resolution was to add the ability to indicate support for OR and/or AND to SearchParameter.

Initial application:
The Jira comments identify svn revision 13220. In the current git history, git-svn commit f0ec862a5f986e3a82bb9ef1a4fa32619c65d6e1 maps to build@13220 and is titled "GF#15646 - CapabilityStatement.security changes + GF#14647 - remove CapabilityStatement.acceptUnknown + GF#14848 - SearchParameter and/or"; its patch added SearchParameter.multipleOr and SearchParameter.multipleAnd rows to the then-authoritative SearchParameter source.

Additional context:
SearchParameter and CapabilityStatement are both active current build resources in source/fhir.ini. The current SearchParameter StructureDefinition includes SearchParameter.multipleOr and SearchParameter.multipleAnd boolean elements with meaningWhenMissing text saying omitted values leave AND/OR repetition support to server discretion. CapabilityStatement.rest.resource.searchParam still names supported parameters and references SearchParameter definitions; its comments explicitly direct systems that want to document modifiers, comparators, target types, and chained parameters to use SearchParameter. Later FHIR-40328 clarified missing-value semantics, FHIR-42931 audited the rendered multiples text and is already represented on the combined branch, and FHIR-20471 covered conformance expectation extension context for SearchParameter and is also already represented on the combined branch.

AutoFHIR reconciliation:

The current authoritative source already implements the accepted FHIR-14848 model by carrying OR/AND support on SearchParameter, and adding parallel multipleOr/multipleAnd fields to CapabilityStatement.rest.resource.searchParam would diverge from the accepted resolution and current design.

Recommendation:
