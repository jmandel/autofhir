FHIR-18850: Audit FamilyMemberHistory sex binding

Issue request:
FHIR-18850 was Published with a Persuasive with Modification resolution for the STU3 FamilyMemberHistory ballot item asking that the old FamilyMemberHistory.gender binding use AdministrativeGender rather than the BirthSex value set. The accepted resolution kept a single sex/birthSex concept for family history but required it to be bound to AdministrativeGender.

Initial application:
The issue was applied in historical commit 04c4d675c5f4, which grouped GF#18850 with GF#17780 and GF#18848 work on FamilyMemberHistory gender/sex naming and binding. A later Published technical-correction issue, FHIR-20393, was applied by 0b584258d4 to replace the temporary build.fhir.org AdministrativeGender link with the canonical http://hl7.org/fhir/ValueSet/administrative-gender URL.

Additional context:
FHIR-17780 explains why the element is now named FamilyMemberHistory.sex instead of gender, and FHIR-18848/FHIR-19716/FHIR-43360 confirm Patient Care's intent to keep the element as sex while using the AdministrativeGender code system/value set family rather than creating a separate XX/XY-style code system. A later R6 issue, FHIR-55021, proposes a different definition and preferred SPCU binding, but it is only Resolved - change required and has not reached Applied or Published workflow status in this default run scope.

AutoFHIR reconciliation:
This commit intentionally makes no source change. FamilyMemberHistory is active in source/fhir.ini, and the authoritative current StructureDefinition source has FamilyMemberHistory.sex bound extensibly to http://hl7.org/fhir/ValueSet/administrative-gender, so the published FHIR-18850 request is already represented in the current build inputs.

Recommendation:
Keep this audit commit as-is for FHIR-18850. Revisit FamilyMemberHistory.sex separately when FHIR-55021 is applied/published, or in a separately scoped review of the old BirthSex value set artifact if needed; neither is required to satisfy this seed issue.
