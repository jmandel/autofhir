FHIR-17321: Audit ValueSet expand contextDirection

Issue request:
FHIR-17321 was a Published/Persuasive Vocab change request from STU3 asking ValueSet.$expand to support selecting different value sets for incoming versus outgoing use. The approved resolution was to use the existing $expand context parameter and add an additional contextDirection parameter with incoming and outgoing values.

Initial application:
The Jira comment records svn revision 14031. In git history, c2bc0211921c8f7bbac3abeb6645aba6788402e2 is the matching git-svn build@14031 commit and explicitly says GF#17321 defined ValueSet.$expand.contextDirection; its patch added expand.contextDirection to the ValueSet operation spreadsheet with the incoming/outgoing semantics. Later terminology ballot reconciliation commit 66ae1e40f1bc02283363c872db14035fc795f8f7, for FHIR-18047 and related $expand guidance, reformatted the same valid values as a bullet list. Subsequent source refactoring moved the operation into the standalone OperationDefinition XML, preserving the applied parameter.

Additional context:
The active source/fhir.ini resources list includes ValueSet, and source/valueset/list-ValueSet-operations.xml references OperationDefinition/ValueSet-expand, so the inspected operation definition is in current build scope. The original Zulip discussion linked from Jira records the Clinical Notes use case, agreement that incoming/outgoing were sufficient, and Brett Marquard creating GF#17321. A later terminology Zulip thread confirms context/contextDirection implementation discussion and clarifies that context mapping is handled through bindings in StructureDefinition and CapabilityStatement. FHIR-18047 has already been represented on the combined branch as a no-change audit, and FHIR-24834 later proposed but retracted adding contextDirection=existing.

AutoFHIR reconciliation:
No source change was made. source/valueset/operationdefinition-ValueSet-expand.xml already defines a 0..1 input parameter named contextDirection of type code, immediately after context, and its documentation says the valid values are incoming for codes a client can use for PUT/POST operations and outgoing for codes a client might receive from the server. This fully carries the FHIR-17321 resolution in the current authoritative source.

Recommendation:
Keep this no-change audit commit as-is. If Vocab wants a formal binding value set for contextDirection or additional direction modes, that should be handled by a new or explicitly confirmed tracker because FHIR-17321's published request is already satisfied and later FHIR-24834 did not approve another value.
