FHIR-15839: Audit Timing repeat count constraint

Issue request:
FHIR-15839 is a Published/Persuasive MnM change request from STU3 asking to prevent negative Timing.repeat.count values, originally suggesting a tim-3 invariant and resolving to change count and the other integer repeat elements to a non-negative integer type.

Initial application:
The issue was applied in git-svn commit 17de59e0e5ef39865240142162841d9f36030ca0 (svn 14509), matching the Jira application comment. That commit changed Timing.repeat.count, Timing.repeat.countMax, Timing.repeat.frequency, and Timing.repeat.frequencyMax in source/datatypes/timing.xml from integer to positiveInt rather than adding a separate invariant.

Additional context:
Timing is an active normative datatype in source/fhir.ini. The current source still types the four Timing.repeat integer elements as positiveInt, which is a stricter primitive than the requested non-negative guard and therefore continues to prohibit negative values. Earlier FHIR-12881 context clarifies Timing.repeat.count as a total desired repetition count, and the FHIR-15839 Zulip origin only establishes that negative repetitions should be prohibited. Searches found no later Jira, Zulip, or Confluence evidence requiring zero to be allowed.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scope Timing source already enforces the applied issue's negative-value prohibition, and switching to a zero-allowing type would be a separate normative relaxation not justified by this Published tracker alone.

Recommendation:
Keep this audit commit as-is. If MnM wants Timing.repeat.count or the parallel integer repeat elements to allow zero, open or apply a separate work-group decision because that would change the longstanding positiveInt conformance rule.
