FHIR-32500: Correct availability rendering example times

Issue request:
FHIR-32500 was a Published/Persuasive with Modification PA change request for R5 asking that PractitionerRole availability guidance explain that systems may render availability differently than it is exchanged on the wire. The approved resolution placed the usage note in PractitionerRole.availableTime detailed descriptions and also applied it to HealthcareService.availableTime and Location.hoursOfOperation.

Initial application:
The issue was initially applied by commit 77446ad94209db50fb0712364dbc2bff0e6e488a and merged through PR #2011 by 496b7c217c8b72487d236e709cd22e3ece4a1112. That application added the requested comments to the three resource definitions, but the example changed the intended morning interval into `9am-12am` and rendered the compact form as `9-12am`, making noon look like midnight.

Additional context:
The current build scope includes Location, PractitionerRole, and HealthcareService as active resources in source/fhir.ini. Later FHIR-25381/FHIR-26641 refactoring changed the R5 availability structures to the shared Availability datatype while preserving the FHIR-32500 rendering guidance on the corresponding active resource elements. FHIR-41311 recently adjusted Availability.availableTime.period but does not change the rendering-note decision. PA WGM minutes confirm the persuasive-with-modification vote and the three target artifacts, and no conflicting Zulip evidence was found.

AutoFHIR reconciliation:
This commit corrects only the misleading time examples in the active PractitionerRole.availability, HealthcareService.availability, and Location.hoursOfOperation comments: the split interval now says `9am-12pm` and the compact display says `Mon-Fri 9am-12pm and 1pm-5pm`. It leaves the approved rendering guidance, resource placement, and later Availability datatype changes otherwise unchanged.

Recommendation:
Keep this source fix. It completes the FHIR-32500 application by preserving the WG-approved rendering clarification while removing a semantic typo that could be read as midnight instead of noon; no separate datatype-level wording change is needed for this issue.
