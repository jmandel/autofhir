FHIR-24897: Audit Consent agreement date clarification

Issue request:
FHIR-24897 was Published/Persuasive for FHIR-core Consent. It asked to clarify that the then-current Consent.dateTime element is the date and time the consent instance was agreed to, not the resource creation time, and to note that Consent.provision.period represented the bound effective time of the consent in the base provision.

Initial application:
The issue was applied in commit 2da480ca699986fa93ba5f234dc5b055146d8144, which updated the old Consent spreadsheet so the dateTime row changed from creation/indexing wording to "When consent was agreed to" with definition "Date and time the consent instance was agreed to", and added the requested Consent.provision.period comment and V2 mapping.

Additional context:
Consent is an active current-build resource in source/fhir.ini. The source was later converted from the spreadsheet to StructureDefinition XML. Commit 89587cb0d9612f16695f4451d6653a53e300d846 changed Consent.dateTime to Consent.date with type date and definition "Date the consent instance was agreed to." Commit d4aba66bf49bed3c8b5ccfc888c4d313c91913f3 added top-level Consent.period for the consent-wide effective period. Later FHIR-39597 removed the provision-zero/base-provision model, and its reconciliation updated Consent.provision.period to point to Consent.period for consent-wide effective time while keeping provision.period provision-specific. No relevant Zulip or Confluence evidence was found that changes this interpretation.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source preserves the substantive FHIR-24897 clarification: Consent.date captures when the consent was agreed to, separate from resource creation, and Consent.period now carries the consent-wide effective period that the old resolution described via the base provision. Re-adding dateTime wording or a base-provision note would contradict later current-build model decisions.

Recommendation:
Keep this no-change audit commit. Any desire to restore time-level precision or revise consent effective-time modeling should be handled by a new work-group decision because the current source is internally consistent after later Consent model changes.
