FHIR-18064: Audit DICOM UID identifier handling

Issue request:
FHIR-18064 was Published/Persuasive with Modification for STU3. It asked for a way to distinguish DICOM UID identifiers from other OID identifiers, originally suggesting a new Identifier.type code, and the final resolution called for a DICOM namespace/codeset plus a representative DICOM UID value and ImagingStudy.identifier guidance/examples.

Initial application:
The original application is commit 131af0770aa6467c6907c7f556dfd51b8519f05d, which explicitly includes GF#18064 and changed ImagingStudy source to document the DICOM Study Instance UID in ImagingStudy.identifier with Identifier.system urn:dicom:uid. The same evidence trail shows FHIR-19455 sharing that application branch for additional Study UID guidance. There was no source history showing a required core v2-0203 IdentifierType code that remains missing from the current build.

Additional context:
FHIR-19602 and its Zulip discussion clarified the broader Identifier.system rule: OID-like values can use a specific assigned identifier system, such as urn:dicom:uid, instead of relying solely on urn:ietf:rfc:3986 plus Identifier.type. FHIR-19765 corrected the ImagingStudy example to keep the urn:oid: value prefix. Current HL7 Terminology publishes NamingSystem dui as an active identifier system with preferred URI urn:dicom:uid. Later FHIR-56212 added an optional DCM#110180 Study Instance UID type coding to an ImagingStudy example and explicitly said this type code should not be required. UP-767 concerns the separate DICOM UID Registry code-system URI DCMUID and does not replace the FHIR identifier system.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/fhir.ini includes ImagingStudy as an active resource; source/imagingstudy/structuredefinition-ImagingStudy.xml constrains studies with series to have one urn:dicom:uid identifier and points readers to the implementation notes; source/imagingstudy/imagingstudy-notes.xml tells implementers to use Identifier.system urn:dicom:uid and urn:oid: values; source/imagingstudy/imagingstudy-example-xr.xml demonstrates both urn:dicom:uid and the optional DCM#110180 type coding. The IdentifierType binding remains extensible, so adding a redundant or mandatory core identifier-type value would conflict with the later clarified approach.

Recommendation:
Keep this no-change audit commit as-is. If the work group later wants DICOM UID type coding to be required rather than optional, that should be a new Imaging Integration/Terminology decision because current applied guidance treats urn:dicom:uid as the distinguishing mechanism and DCM#110180 as an example-level optional type code.
