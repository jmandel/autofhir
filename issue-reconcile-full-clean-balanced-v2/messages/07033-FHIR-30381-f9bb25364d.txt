FHIR-30381: Audit Subscription $status status filter

Issue request:
FHIR-30381 is Published/Persuasive for FHIR core R5. It asked for Subscription/$status to allow an optional list of Subscription.status values on the type-level /Subscription/$status operation, with the final resolution saying to add a code parameter bound to http://hl7.org/fhir/subscription-status and to match the R4 backport issue FHIR-30382.

Initial application:
The filter was already present before this reconciliation. Commit 17740f61cd added the R4B-derived type-level status input parameter to source/subscription/operationdefinition-Subscription-status.xml, commit 26b1acc56b explicitly applied FHIR-30381 by adding the required subscription-status ValueSet binding, commit e981c42de8 limited the id and status inputs to type scope, and commit f1da78150b clarified the status parameter documentation under FHIR-30379.

Additional context:
The current source and the published R5 and subscriptions-backport operation definitions all use the parameter name status rather than the currentStatus name in the Jira resolution prose. That is consistent with the issue title's request to filter by Subscription.status and the already-published API surface. The Subscription and SubscriptionStatus resources are active in source/fhir.ini, so the operation definition in the active Subscription resource folder is in build scope. The January 2021 Subscriptions Track page records FHIR-30381 and sibling backport issue FHIR-30382, and targeted Zulip searches found no conflicting discussion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. source/subscription/operationdefinition-Subscription-status.xml already defines a type-scoped, repeating input parameter named status of type code, with a required binding to http://hl7.org/fhir/ValueSet/subscription-status and documentation explaining Resource-level filtering and OR semantics.

Recommendation:
Keep this no-change audit commit. Renaming the already-published status parameter to currentStatus would be a compatibility-affecting API change and is not supported by the applied source history, published R5 surface, or sibling backport surface.
