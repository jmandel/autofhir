FHIR-24695: Audit Observation valueAttachment guidance

Issue request:
FHIR-24695 was an Applied/Persuasive OO change request raised against STU3 and applied for R6. It asked to define an Observation valueAttachment extension for R4 use and to document when to use Observation.valueAttachment, Observation.derivedFrom, and DiagnosticReport.presentedForm in the Observation introduction and element definitions.

Initial application:
No git commit explicitly mentioning FHIR-24695 was found. The tightly related FHIR-24693 change was applied by commit 0acff97ca003816dc9ddb57f84c591cffbd84666, which added Observation.valueAttachment to the Observation notes and added the Attachment-vs-derivedFrom-vs-presentedForm guidance. Later source rework carried Attachment into the active Observation.value[x] StructureDefinition type list and comment, and subsequent Observation cleanup preserved the same guidance.

Additional context:
Observation is an active current-build resource in source/fhir.ini. The current source already lists valueAttachment in the Observation notes, includes Attachment as a type for Observation.value[x], and explains that Attachment is for the actual binary observation value, derivedFrom is for a DocumentReference from which the value was derived, and DiagnosticReport.presentedForm is for an entire binary report. The current versions page defines cross-version extension packages and URL patterns for elements from other major FHIR versions, which matches Lloyd McKenzie's Jira comment that inter-version extensions should already work for valueAttachment and that only usage guidance was needed here. The local FHIR Extension Pack checkout does not contain a bespoke Observation.valueAttachment extension, so there is no core source or extension-pack source file to edit for this reconciliation.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The active R6 core Observation source already satisfies the required guidance, and adding duplicate local prose or a bespoke extension definition in core would conflict with the existing cross-version extension approach.

Recommendation:
Keep this audit commit as-is for core. If a future review finds that a specific cross-version package fails to publish the expected valueAttachment extension for R4 use, handle that as follow-up in the cross-version/extension packaging workflow rather than by changing the current core Observation source.
