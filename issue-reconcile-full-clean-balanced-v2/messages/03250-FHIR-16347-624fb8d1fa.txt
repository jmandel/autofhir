FHIR-16347: Audit instant purpose clarification

Issue request:
FHIR-16347 was Published/Persuasive with Modification for the STU3 datatype page. It asked whether instant is only for server/system timestamps such as Resource.meta.lastUpdated or can also be used by other resources, noting confusion about Appointment.start/end using instant while Observation.effective did not. The resolution was to clarify that instant is suitable anywhere a work group decides a full instant of time is required, as opposed to merely allowed by dateTime.

Initial application:
The issue was applied by SVN-backed commit 077b0ff042befbd4c6611c1f3969cccaea79b5a3, which has message "GF#16347 - note about use of instant" and git-svn revision 14163. That commit changed source/datatypes.html to say instant is intended for when precisely observed times are required and that date/dateTime should be used for human-reported times. The current source still preserves that guidance, with later editorial refinements.

Additional context:
The current build-source datatype page maps primitive datatypes to datatypes.html through source/fhir.ini, and source/datatypes/primitives.xml carries matching primitive-source comments for instant. Related FHIR-16274 resolved no-change for Appointment.start/end, clarifying that Appointment intentionally uses instant when exact appointment times are needed. Related FHIR-16944 made grammar/text fixes in the same instant row, and later FHIR-42984 and FHIR-24564 updated sub-millisecond and UTC-offset wording while preserving the FHIR-16347 clarification. Current Observation.effective[x] also includes instant as one of its choices, so the specific Appointment-vs-Observation example no longer indicates a missing datatype-page clarification.

AutoFHIR reconciliation:
No source change was made. The active datatype source already tells implementers that instant is for precisely observed times when full instant precision is required, not a server-only datatype, and the primitive spreadsheet/source and checked resource definitions are consistent with that interpretation.

Recommendation:
Keep this empty audit commit as-is. No follow-up core source change is needed for FHIR-16347; separate related issues such as FHIR-16944 or FHIR-42984 should be reconciled under their own keys if selected as seeds.
