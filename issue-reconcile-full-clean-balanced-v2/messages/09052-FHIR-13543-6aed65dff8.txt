FHIR-13543: Audit Reference.type support

Issue request:
FHIR-13543 was Published/Persuasive with Modification for STU3. It asked for a way to convey the target resource type when a Reference uses a business identifier/logical reference; FHIR-I chose to add Reference.type [0..1] rather than only a standard extension, with consistency required when Reference.reference also identifies a FHIR URL and a legacy extension requested for prior versions.

Initial application:
The issue was applied in git-svn revision 13214, commit 2319e45e41, which added Reference.type to source/datatypes/reference.xml and a Target Type section to source/references.html. The active [types] entry in source/fhir.ini includes Reference and [type-pages] maps reference to references, so these are current build inputs. Current source has Reference.type 0..1 uri bound to FHIRResourceTypeExt and describes canonical/resource-type semantics plus consistency with Reference.reference.

Additional context:
Later FHIR-28411 clarified that Reference.type in resources must be a valid non-abstract FHIR resource while logical models may use non-resource content; FHIR-39290 removed an over-strong comment implying references must resolve when type is present; and FHIR-50574 updated narrative on when type is useful. FHIR-18059 was later resolved no-change because R4 already had Reference.type. No relevant Zulip or Confluence evidence was found for the seed. The Extension Pack search did not reveal a separate legacy Reference.type extension, and any missing historical-version extension is outside the current core build being reconciled.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active Reference datatype and references page already implement the substantive current-spec effect of the issue: Reference has target type information, logical references can carry the target type, and later accepted clarifications are present.

Recommendation:
Keep this audit commit as-is. Do not add redundant prose or a current-core extension for older releases. If HL7 wants to recover the historical extension promised for pre-R4 versions, handle that as Extension Pack or historical publication maintenance rather than a current FHIR core source change.
