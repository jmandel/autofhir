FHIR-3197: Clarify conditional read 304 handling

Issue request:
FHIR-3197 was Published/Persuasive for DSTU1 and asked the RESTful API page to give explicit guidance for conditional reads using If-Modified-Since, including that clients must accept 304 Not Modified or full content and that servers may support this cache optimization. The applied Jira comment also incorporated If-None-Match/ETag handling.

Initial application:
The issue was initially applied in svn revision 3229, represented in git as 51f55e6a8f, which added conditional read prose to source/http.html. Later REST page refactoring kept the conditional read section, and later header-table work added If-Modified-Since and If-None-Match rows, but the response summary table still omitted the 304 response and a QA edit changed the server condition from the approved unchanged-since wording to a less precise because-the-header-was-specified wording.

Additional context:
FHIR-9930 later corrected the same conditional-read sentence from "content has not changed" to "content has changed" for the full-content alternative, and current source already retains that correction. source/hierarchy.xml includes source/http.html in the active RESTful API page hierarchy, so the edited file is in current build scope. Jira, Zulip, and Confluence searches found no later conflicting decision for FHIR-3197.

AutoFHIR reconciliation:
This commit updates source/http.html to restore the intended conditional-read condition: servers can return 304 when content is unchanged since If-Modified-Since or when the current ETag matches If-None-Match. It also adds 304 to the read interaction's response status-code summary so the summary table no longer omits the response code explicitly described by the conditional read guidance.

Recommendation:
Keep this source fix. It is a narrow build-scope correction to the RESTful API page and no further core-source follow-up is needed for FHIR-3197.
