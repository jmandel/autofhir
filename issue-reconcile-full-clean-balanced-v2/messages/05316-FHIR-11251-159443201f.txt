FHIR-11251: Audit Endpoint payload MIME type naming

Issue request:
FHIR-11251 is a Published, Persuasive with Modification PA change request for FHIR-core Endpoint. It asked to replace the confusing Endpoint.payloadFormat name and adjust cardinality; the final resolution chose Endpoint.payloadMimeType with 0..* cardinality so endpoints can advertise multiple MIME types or omit the list for open-ended/no-content cases.

Initial application:
No git commit explicitly names FHIR-11251. The historical Endpoint ballot-feedback commit 3e7c097adea104fa3f766d892afffaaf65f6f0db applied the substantive change by replacing payloadFormat example output with payloadMimeType and changing the Endpoint spreadsheet row from Endpoint.payloadFormat 1..1 string to Endpoint.payloadMimeType 0..* code. This matches the Jira resolution even though the commit message used only a general ballot-feedback summary.

Additional context:
Later Published issue FHIR-40247 intentionally moved payloadType and payloadMimeType under a repeatable Endpoint.payload backbone so supported type/MIME combinations can be represented. The current build-scope source therefore uses Endpoint.payload.mimeType, and source/fhir.ini keeps a legacy conversion mapping from Endpoint.payloadMimeType to Endpoint.payload.mimeType. FHIR-39617 subsequently added current narrative guidance for Endpoint.payload.type, Endpoint.payload.mimeType, and profile elements. The only remaining payloadFormat text found in Endpoint source is an internal CSV/template placeholder name that emits <mimeType>; it is not a current conformance element or rendered resource property.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The active Endpoint StructureDefinition already defines Endpoint.payload.mimeType as 0..* code, examples use <payload><mimeType>, and no current Endpoint element named payloadFormat remains.

Recommendation:
Keep this audit commit as-is. No current FHIR core correction is needed for FHIR-11251; any future cleanup of the internal example-template placeholder name should be treated as non-normative maintenance rather than a required reconciliation fix.
