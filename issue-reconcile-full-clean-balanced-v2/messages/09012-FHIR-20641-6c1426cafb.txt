FHIR-20641: Audit stacked modifier guidance

Issue request:
FHIR-20641 was a Published/Not Persuasive with Modification FHIR-I search issue raised against STU3 and applied for R5. It requested allowing :missing to stack with modifiers such as reference type, token :text, and token :of-type; the approved resolution rejected broad stacked-modifier semantics, clarified that stacked modifiers are prohibited, and directed layered behavior to explicit search parameters or operations when needed.

Initial application:
The issue was applied by commit 1e3b7571675379e59420a5ceaba188bd20bb1012, which updated the active Search page source to advise defining a new search parameter or operation when multiple layers of modification are necessary. The adjacent source-history cluster includes fd19eba3ff735b49eb917ed3b722ce8511f8011f for FHIR-37373, which added the current explicit sentence that only a single modifier is allowed on a single search parameter.

Additional context:
The original Zulip discussion shows the same request pattern, including reference:type:missing examples and broader :missing stacking concerns, and participants pointed to existing tracker history saying stacked modifiers were not valid. FHIR-I minutes from 2022-05-23 confirm that the related FHIR-37373 issue was resolved by pointing to FHIR-20641 because modifier chaining is prohibited; FHIR-37373 already has an audit commit on the combined branch. Later FHIR-51598 is Resolved - change required for a narrower wording issue around chaining before versus after :identifier, but it does not reverse the published FHIR-20641 rule and is outside this default applied/published seed decision.

AutoFHIR reconciliation:

The :missing section remains a single-modifier definition with true/false values, so the current source implements the approved FHIR-20641 disposition without needing redundant wording.

Recommendation:
Keep this no-change audit as-is for FHIR-20641. Handle FHIR-51598 separately if that resolved-change-required clarification is later applied, because it concerns precise placement of chaining around :identifier rather than the already-published prohibition on stacked modifiers.
