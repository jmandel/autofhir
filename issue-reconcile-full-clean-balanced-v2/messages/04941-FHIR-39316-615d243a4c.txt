FHIR-39316: Correct named-query examples

Issue request:
FHIR-39316 was a Published/Persuasive FHIR-I clarification for R5 asking for examples of invoking a named query with _query=current-high-risk, including GET and POST forms, a ward parameter, a birthdate search parameter that may be accepted or rejected if not enumerated in the OperationDefinition, and a variation where a non-_query parameter appears before _query to show that parameter order does not control named-query processing.

Initial application:
The issue was applied by git commits 7399925f104938ec96ee55b81f92a2e6e5810fcc and 8379376575fc965f7d3d6bb4d228804f296e2a87, which added a current-high-risk OperationDefinition example and request table to source/search.html. The current source still had the intended example section, but one GET birthdate value was mistyped as ge1970-01-1, the added order example still placed _query first, and the inline OperationDefinition output parameter remained named return instead of the current named-query result parameter.

Additional context:
source/search.html is a build-scope Search page source: publish.ini lists search.html and source/hierarchy.xml includes it under the RESTful API page. The originating Zulip thread shows the examples came from an implementer question about invoking named queries and explicitly asked whether Patient?param1=foo&_query=myquery is valid; the same thread also led to FHIR-39318, whose Published/Persuasive with Modification resolution clarified that named queries have a single output parameter named result of type Bundle and that a _query parameter anywhere in the query means the entire query is handled according to the named query OperationDefinition. The combined branch already contains an FHIR-39318 reconciliation commit, so this commit only decides FHIR-39316 while keeping the examples consistent with that later clarification.

AutoFHIR reconciliation:
This commit corrects the named-query example on source/search.html by changing the inline OperationDefinition output parameter from return to result, fixing the malformed birthdate GET example, clarifying that the birthdate example uses no additional named-query-specific parameter, and changing the final request example so birthdate appears before _query in both GET and POST forms.

Recommendation:
Keep this source fix. It preserves the already-applied example section while closing the remaining FHIR-39316 gaps that could mislead implementers about the exact birthdate example and whether _query may appear after another query parameter.
