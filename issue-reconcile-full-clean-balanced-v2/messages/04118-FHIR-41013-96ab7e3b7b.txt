FHIR-41013: Correct filter composite example

Issue request:
FHIR-41013 was an Applied/Persuasive FHIR-I technical correction for R5 search.html section 3.2.1.5.16. It reported that the first Composite Search Parameters example used the invalid value form code$loinc|12907-2,value$ge150|http://unitsofmeasure.org|mmol/L and should use the normal composite value loinc|12907-2$ge150|http://unitsofmeasure.org|mmol/L.

Initial application:
The issue was applied by c013542438a3f239bdfb88f4cdfe55f307c4ef6d and then 9aa15f6fe91fe4bfbd0803406e9eda74d21e2441, which corrected the GET and POST examples in source/search.html. The combined branch already contains that correction and had no prior Issue-Reconcile-Key commit for FHIR-41013, but source/search_filter.html still carried the same invalid named-and-comma composite value in an active _filter example.

Additional context:
The #implementers Zulip thread linked from the tracker discussion confirmed that the old value looked like a new composite syntax and was a documentation error. FHIR-I minutes on 2023-05-01 recorded FHIR-41013 as a technical correction that was auto approved. source/search.html links to source/search_filter.html as the _filter page, and source/search_filter.html states that token values use the same format as existing search parameters while warning that composite search parameter evaluation is complex.

AutoFHIR reconciliation:
This commit updates the active source/search_filter.html example to use the same normal composite value syntax as the already-corrected Composite Search Parameters example, removing the last current-source occurrence of the invalid code$...,value$... form for this Observation code-value-quantity example.

Recommendation:
Keep this source fix. It is a bounded parallel-location correction for the same erroneous example syntax and avoids leaving _filter documentation that contradicts the applied FHIR-41013 correction and the page's own token-format guidance.
