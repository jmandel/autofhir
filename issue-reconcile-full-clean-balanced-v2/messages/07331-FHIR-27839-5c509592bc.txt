FHIR-27839: Audit interface inheritance application

Issue request:
FHIR-27839 was Published / Persuasive with Modification for R5 by FHIR-I. It asked that StructureDefinition.baseDefinition remain a strict parent-resource hierarchy rather than pointing to CanonicalResource or MetadataResource interfaces, and that interface conformance be represented by a 0..* structuredefinition-implements extension instead.

Initial application:
No local git commit message explicitly mentions FHIR-27839, but the published R5 artifacts and current CI build show the request applied at the generated StructureDefinition surface. ConceptMap and StructureDefinition publish with baseDefinition = http://hl7.org/fhir/StructureDefinition/DomainResource and with structuredefinition-implements values of MetadataResource and CanonicalResource respectively. The checked-in source XML uses build template markers such as http://hl7.org/fhir/build/StructureDefinition/template with interface-valued pre-template baseDefinition inputs, which explains why direct source inspection does not match the generated conformance artifacts.

Additional context:
The original Zulip thread documents the code-generation problem caused by treating interface baseDefinitions as ordinary inheritance, and FHIR-I minutes on 2022-07-18 record the approved FHIR-27839 motion. Later FHIR-39191 was closed Not Persuasive after the commenter confirmed they had been looking at the wrong version and that the R5 generated StructureDefinition baseDefinition was DomainResource. FHIR-37791 and FHIR-51035 later clarified related interface-reference behavior and additional-resource baseDefinition guidance; both are already represented on the combined branch and do not require a duplicate FHIR-27839 source change.

AutoFHIR reconciliation:
This is an empty audit commit. No source change is needed because the current generated specification already exposes the requested strict baseDefinition hierarchy plus structuredefinition-implements extension, while the source template inputs are part of the build mechanism that produces those artifacts.

Recommendation:
Keep this audit commit as-is. Follow-up would only be needed if the work group wants to change the internal source template representation, but that would be a tooling/source-model decision separate from the current published conformance surface for FHIR-27839.
