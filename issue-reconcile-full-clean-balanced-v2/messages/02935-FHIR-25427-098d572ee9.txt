FHIR-25427: Clarify PractitionerRole contact addresses

Issue request:
FHIR-25427 was Published/Persuasive for R5 and asked for PractitionerRole to support role-specific administrative addresses that differ by role or organization and are not necessarily tied to a practicing Location. The approved resolution replaced the prior telecom-only representation with contact 0..* carrying purpose, name, telecom, and address, with a note that this could later use the new contact datatype from FHIR-29035.

Initial application:
The structural part was applied before this reconciliation: commit 6c6927cc55 added PractitionerRole.contact as ExtendedContactDetail, e1320848bd removed the deprecated PractitionerRole.telecom element while explicitly referencing FHIR-25427, and eb428f546b updated PractitionerRole search parameter source in the same PA contact-change family. Current source/fhir.ini actively includes PractitionerRole, and source/practitionerrole/structuredefinition-PractitionerRole.xml defines PractitionerRole.contact 0..* ExtendedContactDetail with a definition that includes addresses.

Additional context:
FHIR-29035 was Published/Persuasive and created ExtendedContactDetail with address 0..1, matching the caveat in the FHIR-25427 resolution. FHIR-14415 and related PA contact trackers show that the same datatype was applied consistently across provider-directory resources. PA January 2021 minutes repeat the FHIR-25427 use case and approved contact backbone shape. No Zulip mention of FHIR-25427 was found, and the Confluence references located agendas plus the PA minutes without conflicting guidance.

AutoFHIR reconciliation:
This commit fixes the remaining stale PractitionerRole notes text. The old note said there was no address on PractitionerRole because Location contained the address, which could contradict the new PractitionerRole.contact.address support for administrative or purpose-specific addresses. The updated note preserves the intended distinction: physical service-location addresses still come from Location, while role-specific administrative addresses can be represented in PractitionerRole.contact.address.

Recommendation:
Keep this source fix. The resource definition and datatype already implement the approved element model; this commit only removes a contradictory narrative statement from the active PractitionerRole page so implementers are not steered away from the approved contact.address mechanism.
