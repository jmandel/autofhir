FHIR-6195: Audit referral fulfillment links

Issue request:
FHIR-6195 was a Published DSTU1 Patient Care change request asking for a reference from ReferralRequest to the fulfillment of the referral request, including when the request was fulfilled or when the requested service occurred. The accepted Not Persuasive with Modification resolution kept the normal FHIR direction: fulfillment resources should point back to the request, and the related-resource documentation should explain that referral requests may be fulfilled by Encounter, Procedure, DiagnosticReport, or other assessment-related resources.

Initial application:
The issue was applied in SVN/git commit a7344a39, which added ReferralRequest introduction prose saying that a ReferralRequest might be fulfilled by DiagnosticReport, Encounter, Procedure, or other assessment-related resources. A separate nearby DiagnosticReport change, d543702d, widened DiagnosticReport.request to include ReferralRequest. Those historical ReferralRequest sources are no longer active current-build resources.

Additional context:
FHIR-13196 later merged ReferralRequest and ProcedureRequest into the current ServiceRequest resource, and source/fhir.ini records ReferralRequest as a deleted/renamed resource while ServiceRequest is active. The current ServiceRequest page says referral/transfer-of-care requests are represented by ServiceRequest and that generated resources link back to ServiceRequest through basedOn. The current Request pattern gives the general rule that requests do not track their own fulfillment; corresponding Event resources and Tasks track execution, with Events using basedOn. Encounter.basedOn explicitly covers incoming referrals and targets ServiceRequest; DiagnosticReport.basedOn, Procedure.basedOn, and Observation.basedOn also target ServiceRequest. No relevant Zulip or Confluence discussion was found that changes this interpretation.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build already preserves the FHIR-6195 directionality and implementer guidance through the active ServiceRequest and Request-pattern source plus the relevant event-resource basedOn definitions. Adding another ServiceRequest paragraph would duplicate existing guidance without changing conformance or implementer understanding.

Recommendation:
Keep this audit commit as-is. Future work should address any new request/event linkage issue through the current ServiceRequest and workflow/Event pattern, not by reviving ReferralRequest-specific wording.
