FHIR-5850: Audit Communication sender and recipient targets

Issue request:
FHIR-5850 was Published with a Persuasive with Modification resolution for DSTU1 Communication. It asked that the Communication sender and receiver resource reference lists be made identical, including order, by adding Organization to receiver and making the lists alphabetical.

Initial application:
The issue was applied in historical SVN revision 4977, represented in git as a47e7d33aa1bc0c16baec2397ef964e6f8975053. That commit changed source/communication/communication-spreadsheet.xml so Communication.sender and Communication.receiver/recipient both used Reference(Device|Organization|Patient|Practitioner|RelatedPerson), and it updated the Communication introduction to include organizations among possible senders and receivers.

Additional context:
Communication is still in the current build through the active source/fhir.ini resource entry, and the current source/communication/structuredefinition-Communication.xml includes Organization in both Communication.recipient and Communication.sender. The current target lists are no longer identical because later published/applied Patient Care decisions changed the model: FHIR-8466 added Group as recipient, FHIR-12817 added CareTeam as recipient, FHIR-17448 added HealthcareService and explicitly recorded that Group/CareTeam differences between sender and recipient were warranted, FHIR-22630 added Endpoint to both sides, FHIR-26619 later added CareTeam to sender, and FHIR-40760 records current recipient examples that include Location. Those later decisions supersede the original DSTU1 expectation of identical lists.

AutoFHIR reconciliation:
This empty audit commit makes no source change. Re-sorting or forcing the current lists to be identical would either be editorial-only ordering churn or would undo later work-group decisions about which entities can act as Communication senders versus recipients.

Recommendation:
Keep this audit as-is. If Patient Care wants current Communication.sender and Communication.recipient to have exactly identical, alphabetized targetProfile lists again, that should be a new work-group decision because it would alter or reinterpret later published/applied tracker outcomes.
