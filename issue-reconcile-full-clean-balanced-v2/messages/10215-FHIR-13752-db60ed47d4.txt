FHIR-13752: Audit _type search parameter guidance

Issue request:
FHIR-13752 was a Published/Persuasive STU3 FHIR-core issue asking that the Search page's "Specifying the type of Resource"/_type language be fixed to match the REST Variant Searches guidance. The problem was that the Search page text could be read as allowing only parameters that apply to all resources even when _type named multiple resource types, while the REST page allowed parameters common to the named types.

Initial application:
The Jira comment records svn revision 12719. In the converted git history, commit 13705e55a3fd555a4167d7814f373e0f588e26fe (#13752 - clarify about search all parameters) changed source/http.html in the Variant Searches area. A later search-clarification commit, c6fb216ed04cdc382687bf2cd72c5f0861ff76f5, changed source/search.html so the no-type case is limited to all-resource base parameters while the multiple-type case can use search parameters shared across the specified resources.

Additional context:
The original implementers Zulip thread confirms the intended distinction: Grahame explained that the quoted all-resource-only sentence was from before parameters common across multiple types existed. FHIR-36347 later revisited the same HTTP/Search-page consistency problem for R5, and its already-published audit commit on the combined branch confirms that current source/http.html delegates parameter availability to source/search.html while source/search.html now states separate no-type, single-type, and multiple-type rules using CapabilityStatement names, SearchParameter.code, and SearchParameter.alias. No Confluence reference to FHIR-13752 was found.

AutoFHIR reconciliation:
This is an empty audit commit. No source change is needed because the current active Search page already says that no _type permits only all-resource base parameters, a single _type permits that type's parameters, and multiple _type values permit parameters commonly referenced between the resources. The current HTTP Variant Searches section links readers to the Search page rather than maintaining conflicting local rules.

Recommendation:
Keep this audit commit as-is. The current build-scope source already conveys the FHIR-13752 rule, as refined by later published search guidance, so another wording edit would duplicate or risk destabilizing the existing guidance.
