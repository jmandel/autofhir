FHIR-45285: Audit MedicationKnowledge interface fixes

Issue request:
FHIR-45285 was an Applied/Persuasive Pharmacy change request for MedicationKnowledge's declared interface compatibility. It asked that MedicationKnowledge.name become 0..1, MedicationKnowledge.status use http://hl7.org/fhir/ValueSet/publication-status, and MedicationKnowledge.author change from Reference to ContactDetail so the resource remains compatible with CanonicalResource and MetadataResource.

Initial application:
The source was already changed by git commit 2f67957cf6aea72ba830e0c93aebbf70cb712807, whose patch changed exactly those three MedicationKnowledge elements in source/medicationknowledge/structuredefinition-MedicationKnowledge.xml. Related commit a9c1983ca83b4825332d8ffef14df71477472b27 for FHIR-42901 notes that author/status were handled by FHIR-45285 and only changed intendedJurisdiction to jurisdiction.

Additional context:
MedicationKnowledge is an active current-build resource in source/fhir.ini. The current StructureDefinition declares MetadataResource as its template/base, MetadataResource templates CanonicalResource, and the current interface definitions require CanonicalResource.name 0..1, CanonicalResource.status bound to publication-status, and MetadataResource.author as ContactDetail. FHIR-45284 provided the FHIR-I background/tooling clarification and later added the MetadataResource template marker. The checked-in medicationknowledge.svg still depicts the old status binding, author Reference, intendedJurisdiction, and name 0..*, but that is a generated-looking diagram artifact rather than the authoritative resource definition source.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The authoritative MedicationKnowledge XML already satisfies the three requested interface-compatibility corrections, and editing only the stale SVG would violate the generated-diagram guardrail.

Recommendation:
Keep this audit commit as-is for FHIR-45285. If the checked-in SVG is still used by the publisher instead of being regenerated from StructureDefinition source, handle that as a diagram regeneration/build hygiene follow-up rather than a new semantic source correction for this issue.
