FHIR-26067: Audit FHIR version hierarchy application

Issue request:
FHIR-26067 was Published/Persuasive with Modification for R5. It asked to replace the old publication.major.minor/revision terminology with major.minor.patch-label wording, update the fhirVersion MIME parameter text, and add major.minor FHIR-version codes as parents for the corresponding longer version codes.

Initial application:
The issue was applied in git commit 6f6a888188, which explicitly mentions FHIR-26067 and FHIR-35168 and states that it added the major.minor hierarchy to the FHIRVersion CodeSystem while updating the version terminology pages. The current authoritative FHIR-version worksheet already contains the requested major.minor parents and the versioning/http pages use the requested major/minor/patch terminology.

Additional context:
FHIR-35168 was applied in the same commit and explains the terminology cleanup that FHIR-26067 depends on. FHIR-35169 was later Resolved - No Change because FHIR-26067 already addressed the fhirVersion value-set concern. A Zulip committers thread for FHIR-26067 records Grahame Grieve explaining that the master for this CodeSystem is still the Excel-style source/terminologies/bindings.xml file. The checked-in source/capabilitystatement/codesystem-FHIR-version.xml copy is stale and still shows 6.0.0 under 4.6, but it is not the active source of truth for the built CodeSystem; the current build output from build.fhir.org follows the terminology worksheet and includes 4.6.0, 5.0/5.0.0, and 6.0/6.0.0 in hierarchy.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The build-scope source for the FHIR-version list already satisfies the Jira request, the narrative pages already use major.minor.patch-label and major/minor wording, and changing only the stale capabilitystatement XML copy would not be the authoritative correction.

Recommendation:
Keep this audit commit as-is. No FHIR core source fix is needed for FHIR-26067; if maintainers want the stale checked-in XML copy refreshed, handle that as generated-artifact/tooling cleanup rather than as this issue's normative source fix.
