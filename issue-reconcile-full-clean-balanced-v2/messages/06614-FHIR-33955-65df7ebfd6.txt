FHIR-33955: Audit CapabilityStatement rest-mode invariant

Issue request:
FHIR-33955 was a Published/Persuasive R5 FHIR-core Conformance change request asking to add an invariant to CapabilityStatement.rest so there can be only one rest repetition per mode. The Jira resolution says to do this.

Initial application:
The issue was applied by Grahame Grieve in commit 071000dbe268d8a21cd01b391af8613807371d67, which added cpb-4 to source/capabilitystatement/structuredefinition-CapabilityStatement.xml with expression rest.mode.isDistinct(). A later canonical-resource refactor in commit 49b86f8a6978650d8f8a6d36d27dee0433e455bc preserved the cpb-4 invariant while removing the obsolete XPath representation used by older source.

Additional context:
CapabilityStatement is an active resource in source/fhir.ini, so source/capabilitystatement/structuredefinition-CapabilityStatement.xml is in current build scope. Current source still has cpb-4 as an error-level constraint on CapabilityStatement and marks CapabilityStatement.rest and CapabilityStatement.rest.mode with condition cpb-4. The Zulip thread linked from the Jira records the originating implementer question and confirms the intended rule of one client and one server rest entry. A later issue, FHIR-54050, asks whether the cpb-4 explanatory text should say SHALL/must rather than should, but that issue is Triaged and unresolved, so it is background only and not a final decision to change source here.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative CapabilityStatement source already contains the requested invariant and the build-scoped resource wiring needed for the current specification to enforce one CapabilityStatement.rest per mode.

Recommendation:
Keep this audit commit as-is for FHIR-33955. Handle the wording concern raised in FHIR-54050 only after the work group reaches a final disposition, because the existing error-level invariant already satisfies this Published issue.
