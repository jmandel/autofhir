FHIR-22825: Audit external OpenAPI schema-version fix

Issue request:
FHIR-22825 is a Published/Persuasive FHIR-core tracker asking that IG Publisher OpenAPI generation stop producing STU3 JSON schema references when processing an R4 CapabilityStatement. The Jira comment records Grahame Grieve's "fixed" response and the issue was applied for R5.

Initial application:
No current FHIR source commit was found with the FHIR-22825 key. The OpenAPI generator had already been moved out of this specification checkout before the issue was filed: local commit 74a27559 moved the OpenAPI code to org.hl7.fhir.core, and later local commit 6a5793 removed the stale igtools Java sources from this checkout. In the external org.hl7.fhir.core repository, commit cc837365 "fix version issue in openAPI?" changed OpenApiGenerator.specRef() from a hard-coded STU3 schema base to context-version logic that maps 4.0.x contexts to the R4 schema base.

Additional context:
The current FHIR checkout has no active OpenAPI generator source; the only active OpenAPI text found here is an OperationDefinition narrative mention. Current HL7/fhir-ig-publisher code invokes org.hl7.fhir.r5.openapi.OpenApiGenerator from the external core library, and the current external OpenApiGenerator still maps a 4.0 context to https://hl7.org/fhir/R4. Zulip discussion in #IG creation > Exception generating OpenAPI confirms that the reported problem was specifically R4 IG/CapabilityStatement output referencing STU3 schemas and that Grahame confirmed it was fixed.

AutoFHIR reconciliation:
This commit intentionally makes no source change in HL7/fhir because the relevant implementation is no longer part of this checkout or the current FHIR build. The historical external fix and current external code address the reported R4/STU3 behavior; any future generator change belongs in org.hl7.fhir.core or the IG Publisher repository rather than this spec source tree.

Recommendation:
Keep this empty external-repo audit commit as-is for the FHIR-source reconciliation. Revisit only if there is a new reproducer in the current IG Publisher/core tooling, in which case the follow-up should target the external tooling repository.
