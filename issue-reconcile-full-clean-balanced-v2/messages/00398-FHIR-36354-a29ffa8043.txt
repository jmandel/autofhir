FHIR-36354: Clarify Consent security-label decisions

Issue request:
FHIR-36354 was Published/Persuasive for FHIR-core Consent. It asked the spec to clarify how Consent.provision.securityLabel should be interpreted when the label code comes from a hierarchical code system such as v3 Confidentiality, including whether permit and deny provisions include less-restrictive or more-restrictive confidentiality codes.

Initial application:
The approved narrative text was applied in PR #2132 by commit da6cefb31d234cd244fc01b0fd93da66ec4d9726 and merged by 991c8c5a5e9431e2f612ab039ce3ebc6c6e1c896. Current source/consent/consent-notes.xml already states that hierarchical code subsumption must be considered, that permit provisions include subsumed lower-protection codes, and that deny provisions include higher-protection codes such as Very Restricted when Restricted is denied.

Additional context:
Consent is an active current-build resource in source/fhir.ini, and source/consent/structuredefinition-Consent.xml is the authoritative StructureDefinition input for generated element definitions. The older Consent.provision.securityLabel element comment still said that an R security label applies to R or lower without distinguishing permit from deny, which preserved only the permit-side high-water behavior and could mislead implementers reading the generated definitions. Older FHIR-11056 identified high-water wording as confusing but left possible ConfidentialityCode special handling for later clarification; later Consent restructuring such as FHIR-39597 did not supersede the FHIR-36354 permit/deny rule.

AutoFHIR reconciliation:
This commit updates only the Consent.provision.securityLabel comment in source/consent/structuredefinition-Consent.xml. The new comment points readers to the matched provision decision: a permit decision for R includes R or lower, while a deny decision for R also denies higher-protection codes such as V. This aligns the element definition with the already-applied Consent narrative and leaves unrelated security-label and purpose-of-use wording unchanged.

Recommendation:
Keep this source fix as the bounded FHIR-36354 reconciliation. No broader Consent model or terminology change is needed; future changes to hierarchical security-label interpretation should be handled by a new CBCC/Security work-group decision.
