FHIR-7345: Audit Patient merge behavior guidance

Issue request:
FHIR-7345 was a Published Patient Administration change request from the DSTU1 ballot asking the Patient section to require server behavior when a client uses a merged-off patient id, specifically suggesting redirect-like behavior. The final resolution was Not Persuasive with Modification: PA did not define a required redirect/merge behavior, and instead asked for notes in the Merging Patients section requesting implementer feedback because search, GET, and other post-merge behavior needed more experimentation.

Initial application:
The issue was explicitly applied by git commit bbed5fd4fc ("Tracker# 7345 - Patient Merge notes"), which added a DSTU note to source/patient/patient-notes.xml asking for implementer input on the effect of linking, merging, and unlinking on GET, searching, reverse includes, and related behavior. Duplicate issue FHIR-7938 contains the same request and points back to FHIR-7345.

Additional context:
Later PA work addressed the experimentation requested by FHIR-7345. FHIR-19687 and associated PA Confluence minutes recorded that merge behavior would re-wire references so search is consistent, while linking remained more client-side/cross-system. FHIR-38183 then updated the Patient narrative to remove the old announcement/feedback text and point readers to the Patient $merge operation. A later core refactor moved Patient $merge out of the core operation list and retargeted Patient narrative links to the Administration incubator operation, so the remaining core build scope is the Patient page guidance and external operation link rather than a core Patient-merge OperationDefinition.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active Patient source already distinguishes merging from linking and points implementers to the current $merge operation page; source/fhir.ini keeps Patient in the active build, while source/patient/list-Patient-operations.xml no longer lists Patient-merge as a core operation. Reintroducing the old feedback note or defining a new mandatory redirect behavior in core would conflict with the later PA decisions and current operation move.

Recommendation:
Keep this no-change audit. If the external Administration incubator Patient $merge operation needs further changes, handle that in the owning external IG/repository rather than by editing inactive core operation remnants or adding redundant core prose.
