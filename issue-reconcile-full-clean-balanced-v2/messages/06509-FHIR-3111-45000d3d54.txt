FHIR-3111: Audit Condition relationship split

Issue request:
FHIR-3111 was a Published FHIR-core Patient Care change request for Condition from the Initial Draft, resolved Persuasive with Modification for DSTU1. It asked to replace Condition.relatedItem, whose type code distinguished due-to from following relationships, with two separate associations: dueTo and occurredFollowing. The recorded decision was to drop the ConditionRelationshipType attribute, create two associations instead of one, and use extensions for any future relationship types.

Initial application:
The relevant historical source change appears in commit a7d4372eee6bc082995cfca0a3028c8f3afc48c9, which changed the Condition spreadsheet and examples from Condition.relatedItem to Condition.dueTo and Condition.occurredFollowing. The commit subject cross-labels two old tracker numbers, but its patch directly implements the relationship split requested by FHIR-3111 by removing Condition.relatedItem and ConditionRelationshipType rows and adding dueTo/occurredFollowing rows and search parameters.

Additional context:
Later published Patient Care decisions FHIR-7620 and FHIR-7621 refined the same relationship family: Condition.stage and Condition.evidence stayed in core, while dueTo and occurredFollowing moved from core Condition elements to standard extensions, with their target/detail representation normalized. Commit d9e60bf0bbf8924afe37bac0b3187b05d498573c applied that later decision. The current build actively includes Condition, no current core Condition source contains Condition.relatedItem, dueTo, or occurredFollowing elements, and the maintained Extension Pack contains active condition-dueTo and condition-occurredFollowing definitions for use on Condition.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current core Condition source already reflects the FHIR-3111 semantic outcome when later decisions are considered: the original combined relatedItem/type model is gone, the core resource is not supposed to carry dueTo/occurredFollowing as native elements anymore, and the relationship concepts remain available as standard extensions outside the core checkout.

Recommendation:
Keep this audit commit as-is. Reintroducing core Condition.dueTo or Condition.occurredFollowing would reverse later published Patient Care decisions, and adding redundant core narrative would not materially improve implementer understanding because the current Condition.evidence comment links causality to the condition-dueTo extension and the extension definitions are maintained in the Extension Pack.
