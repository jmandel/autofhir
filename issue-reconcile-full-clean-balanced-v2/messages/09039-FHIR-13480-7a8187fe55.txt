FHIR-13480: Audit Reference type profile rendering

Issue request:
FHIR-13480 was a Published/Persuasive FHIR-core tracker, raised for STU3 and applied for R5, asking to fix IG Publisher rendering for an ElementDefinition.type where code is Reference and both profile and targetProfile are present. The example rendered only Reference(US Core Patient Profile) instead of showing the Reference datatype profile, "Identifier Free Reference Data Type", together with the target profile.

Initial application:
No Jira-keyed commit was found in the current HL7/fhir source history, and the issue text plus contemporaneous Zulip discussion identify this as an IG Publisher rendering/tooling defect. Grahame's 2022 Jira comment says the issue already looked fixed, and the current external HL7/fhir-ig-publisher renderer has explicit handling for both type.hasProfile() and type.hasTargetProfile().

Additional context:
FHIR-I minutes from 2018-08-06 approved FHIR-13480 as Persuasive in a block vote. The current core specification source remains semantically correct: ElementDefinition.type.profile and ElementDefinition.type.targetProfile are distinct active definitions, and source/fhir.ini routes ElementDefinition and Reference pages into the current build. The implementation surface for the reported rendering behavior is the IG Publisher repository, not this FHIR source checkout.

AutoFHIR reconciliation:
This commit intentionally makes no source change in HL7/fhir. The current FHIR source does not contain the reported IG-specific example or a stale renderer implementation to edit, and the external renderer already distinguishes the datatype profile from the reference target profile.

Recommendation:
