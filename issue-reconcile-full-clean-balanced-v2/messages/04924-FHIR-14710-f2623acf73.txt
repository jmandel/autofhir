FHIR-14710: Audit ConceptMap source and target cardinalities

Issue request:
FHIR-14710 was a Published/Persuasive with Modification STU3 ConceptMap request to make ConceptMap.group.source and ConceptMap.group.target mandatory so that source and target code systems would always be known. The final resolution did not require unconditional 1..1 cardinalities: group.source and group.target may be omitted when the corresponding source or target value set identifies only one code system, and the root source/target scope elements remain optional for empty $closure initiation.

Initial application:
The issue appears to have been applied in svn r14010, preserved as git commit 7a03cbd98d, which updated the old ConceptMap spreadsheet comments to say group.source and group.target are not needed when the corresponding value set is specified and contains concepts from only a single system. The related earlier closure decision FHIR-12314 had already relaxed the old root ConceptMap.source[x] and ConceptMap.target[x] cardinalities from 1..1 to 0..1.

Additional context:
ConceptMap is active in the current build through source/fhir.ini, and the authoritative current source is source/conceptmap/structuredefinition-ConceptMap.xml rather than the old spreadsheet. Later R5/R6 work renamed ConceptMap.source[x] and ConceptMap.target[x] to sourceScope[x] and targetScope[x] and added value-set mapping usage notes, but did not reverse the 2018 cardinality decision. The referenced Zulip thread records implementer input, the $closure use case, and the conclusion to document the rule rather than tighten the cardinalities.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current ConceptMap source keeps sourceScope[x], targetScope[x], group.source, and group.target at 0..1, and the group.source/group.target comments already express the FHIR-14710 resolution that the group code-system elements are unnecessary when the corresponding value set contains concepts from only a single system.

Recommendation:
Keep this no-change audit. Future work should only revisit this area if the Terminology Infrastructure WG wants a new enforceable invariant for the cases where sourceScope/targetScope do not imply a single system; FHIR-14710 itself is already reflected in the active source.
