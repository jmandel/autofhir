FHIR-18659: Audit CodeSystem subsumes parameter co-occurrence

Issue request:
FHIR-18659 was a Published vocab change request for STU3 asking whether CodeSystem $subsumes input parameters codeA, codeB, and system could ever be null and suggesting 1..1 cardinalities. The final Persuasive with Modification resolution was to note co-occurrence with codingA/codingB more explicitly, not to make those individual parameters mandatory.

Initial application:
Jira records Grahame Grieve's application commit 4907f9bcb0b710cb2837a93a20c4b23210a37249. That commit updated the CodeSystem $subsumes source spreadsheet to add operation-level wording that a client SHALL provide both A and B codes, either as code or Coding parameters, and that system is required unless the operation is invoked on a CodeSystem instance. The source kept codeA, codeB, system, codingA, and codingB at 0..1 so the alternative parameter forms could be represented.

Additional context:
The current build-scoped source is no longer the spreadsheet row but source/codesystem/operationdefinition-CodeSystem-subsumes.xml, with CodeSystem and OperationDefinition active in source/fhir.ini and the CodeSystem operation list referencing OperationDefinition/CodeSystem-subsumes. Later source history fixed a typo in the added sentence and performed canonical-name/formatting maintenance without changing the FHIR-18659 rule. A bounded related Jira search found FHIR-24698 because its terminology capability statement mentioned CodeSystem-subsumes required input parameters; that issue is a separate capability-statement change already represented on the combined branch and does not override the operation definition's code-or-Coding alternatives. Direct Zulip and Confluence searches found no FHIR-18659 discussion or conflicting later work-group record.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The authoritative OperationDefinition already says clients SHALL provide both A and B as code or Coding parameters, codeA/codeB each say a system must be provided when a code is used, system says it is required unless invoking on an instance, and codingA/codingB remain explicit alternatives. Changing the individual min cardinalities to 1 would incorrectly forbid the Coding form and instance invocation case that the resolution preserved.

Recommendation:
Keep this audit commit as-is. No follow-up source edit is needed for FHIR-18659 unless a future terminology work-group decision changes $subsumes parameter co-occurrence rules across both the OperationDefinition and terminology-service narrative.
