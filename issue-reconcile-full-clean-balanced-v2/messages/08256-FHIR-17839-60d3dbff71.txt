FHIR-17839: Audit open type list sorting

Issue request:
FHIR-17839 was a Published/Persuasive FHIR-I change request for the STU3 datatypes page. It asked to sort the list of open types and add sub-labels because the metadata-types portion was not sorted and readers expected the whole list to be sorted.

Initial application:
The Jira comment points to GH#bb3cf76b52. Commit bb3cf76b52e925cfec03721272b075521bcdc8cf, "GF#17839 - sort open data types list", changed source/datatypes.html by removing the outer <ul> wrapper around [%wildcard-type-list%]. That followed commit dcd3ffda9020726ce3628f04603b19e4bf289c52, which had replaced the old hand-maintained open-type list with the single source [%wildcard-type-list%] token.

Additional context:
The current build-scoped source/datatypes.html still uses [%wildcard-type-list%] unwrapped at the Open Type Element section, and source/fhir.ini maps wildcard "*" to the datatypes page. The Kindling publisher's PageProcessor renders the token by opening a new <b> classification label and <ul class="dense"> whenever TypesUtilities.wildcards changes classification, so the current CI page renders Primitive Types, Datatypes, MetaDataTypes, and Special Types sub-labels. The current CI MetaDataTypes subgroup includes newer metadata types whose hard-coded Kindling order is not strictly alphabetic, but that residual ordering is a publisher/dependency ordering detail and not an in-scope core source change needed to preserve implementer understanding for this old applied issue. FHIR-26935 is a later open-types usage-list issue already represented on the combined branch and does not change the seed decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current core source retains the Jira-linked application and delegates the open-type list to the categorized generator; a manual core-source list would reintroduce drift from the single source. If strict alphabetic ordering of newer metadata-type additions is desired, it should be handled in the Kindling/TypesUtilities source or by a fresh human-reviewed tracker rather than by this reconciliation.

Recommendation:
Keep this audit commit as-is. No core FHIR source edit is needed for FHIR-17839; optional follow-up would be an external publisher cleanup to sort the hard-coded metadata-type order for newly added types.
