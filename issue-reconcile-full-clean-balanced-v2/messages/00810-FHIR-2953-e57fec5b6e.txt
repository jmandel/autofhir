FHIR-2953: Audit GET/POST operation guidance

Issue request:
FHIR-2953 was a Published, Persuasive with Modification FHIR-core Query change request. It asked the specification to be explicit that non-safe or non-idempotent behavior should not be exposed through GET, to account for search POST usage when query strings would expose sensitive data, and to document the distinction between search/query and service-style operations.

Initial application:
The Jira comment records "idempotency: Svn revision 3074" and git history contains 5bc50dd2f1a6b653246dd7c11912d3a739178e22, "{#2953}: add note about idempotency", which added the original operations-page rule that GET invocation was only for idempotent operations. The remaining service-operation work was applied as the operations framework evolved, rather than as a single later FHIR-2953-tagged source change.

Additional context:
The current build includes the relevant source pages through source/hierarchy.xml and the OperationDefinition resource through source/fhir.ini. Later operations work renamed OperationDefinition.idempotent to affectsState, and FHIR-14960 plus its Zulip discussion clarified that servers support POST for all operations and GET for operations with affectsState=false when the parameters can be represented in the URL. Later search protocol work, including FHIR-35859 and FHIR-39137 commits, moved HTTP search method guidance into source/http.html and explains why GET or POST can be undesirable in production, including PHI exposure in query parameters. The Confluence search found no relevant conflicting decision; the only FHIR-2953 reference was an unrelated Orders and Observations WGM issue list.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Current source already expresses the required semantics: operations may use GET only when they do not affect server state, no-parameter state-changing operations must use POST, OperationDefinition.affectsState says audit-trail side effects do not count as state changes, and the RESTful search section documents both GET and POST with method-selection/security considerations. Restoring the old RFC idempotency wording would be redundant and less aligned with the current affectsState model.

Recommendation:
Keep this no-change audit as-is for FHIR-2953. If future work revisits finer points of operation method conformance or POST search support, handle those under their later tracker issues rather than reopening this DSTU1 query/operations reconciliation.
