FHIR-5353: Audit Identifier.type application

Issue request:
FHIR-5353 was a Published FHIR-core/MnM Jan 2015 ballot comment resolved Persuasive with Modification. It requested a clear coded identifier type on Identifier as a 0..1 CodeableConcept with an extensible binding, plus guidance that the type is not a substitute for Identifier.system and should not define codes that are 1..1 with systems.

Initial application:
The issue was applied in svn/git history. Commit 0c9b5378687bfa0a80cbf386bbda371a0becc39e (svn r5063, cited from Jira) replaced Identifier.label with Identifier.type as 0..1 CodeableConcept and bound it to IdentifierType. The immediately following build-fix commit f976eec819da795c0bc81e9bef74077506a5a5c2 added the identifier-type value set; later terminology maintenance moved/refined the value set without removing the requested datatype element or guidance.

Additional context:
Identifier is an active datatype in source/fhir.ini and is marked normative. Current source/datatypes/identifier.xml still defines Identifier.type as 0..1 CodeableConcept with the IdentifierType binding and usage notes saying the element is for general identifier categories and should not correspond 1..1 with Identifier.system. Current source/terminologies/bindings.xml keeps IdentifierType as an extensible binding, and source/terminologies/valueset-identifier-type.xml includes the current identifier-type value set. Later FHIR-20466 resolved no-change on the same type-vs-system boundary, confirming that Identifier.type is not intended for identifier universality mechanisms or single namespaces.

AutoFHIR reconciliation:
This audit makes no source change because the current build-scope datatype, binding, value set, and narrative guidance already preserve the substance of FHIR-5353. Renaming the requested historical "code" concept to Identifier.type and moving the value set to current terminology sources are historical/refactoring differences, not current specification defects.

Recommendation:
Keep this no-change audit commit. No core source follow-up is needed for FHIR-5353; future requests for additional identifier-type codes or jurisdiction-specific identifier systems should be handled as separate terminology or registry work rather than by changing this datatype audit.
