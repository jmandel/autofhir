FHIR-19725: Audit Location boundary handling

Issue request:
FHIR-19725 was a Published Patient Administration change request asking whether Location.position should become an array to represent irregular areas. The final Not Persuasive with Modification decision kept Location.position as the single WGS84 point/centroid and instead required the comments to point to the location-boundary-geojson extension, add examples with contentType application/geo+json, and include the VhDir contains search parameter in core for R5.

Initial application:
The issue was explicitly applied by git commit 1eb8e7072a5c7457d14017061f9a1dfac3fc7a81, which added the Location.position comment, a boundary search narrative section, the Washington DC boundary example, the example-list entry, and the imported contains search parameter. Later link/refactor commits adjusted the extension link but did not reverse the applied semantics.

Additional context:
Location is an active current-build resource in source/fhir.ini, so source/location files are in build scope. The location-boundary-geojson definition now lives in the FHIR Extension Pack with the same canonical URL and an Attachment value whose comment requires application/geo+json, so its absence from core extension definitions is expected. No directly relevant Zulip or Confluence evidence was found that conflicts with the Jira and git-history conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/location/structuredefinition-Location.xml points from Location.position to the standard location-boundary-geojson extension and the contains search parameter; source/location/location-notes.xml documents the contains search; source/location/location-wash-dc-metro.xml provides an example using application/geo+json; and source/location/bundle-Location-search-params.xml includes the contains search parameter over the boundary extension value.

Recommendation:
Keep this audit commit as-is. The current specification already implements the Published Jira decision; changing Location.position cardinality or duplicating extension details in core would contradict or over-apply the final resolution.
