FHIR-27544: Align process-message response wording

Issue request:
FHIR-27544 was Applied as Not Persuasive with Modification for the InM MessageHeader/$process-message concern that the operation text appeared to conflict with messaging rules about whether every request needs a response message. The final disposition accepted that the operative modification was the messaging-page change making response messages zero-or-more, rather than tightening $process-message return cardinality to 1..1.

Initial application:
No source commit explicitly tagged FHIR-27544 was found. The relevant prior application appears through the same messaging evidence trail: commit 87b1af3c09 for FHIR-40518/FHIR-40519 changed the opening messaging description from one-or-more to zero-or-more response messages, while earlier FHIR-25465 and FHIR-25252 commits clarified that some message and $process-message exchanges can be satisfied by an HTTP response with no message Bundle.

Additional context:
MessageHeader is an active current-build resource in source/fhir.ini, and source/messaging.html is the current messaging narrative. The current source already had the applied zero-or-more rule in the messaging introduction, but the $process-message narrative summary and OperationDefinition description still said the operation returns one-or-more response messages, and the return parameter still called synchronous message returns mandatory. Those stale built-source locations preserved the contradiction that FHIR-27544 and the related response-message decisions intended to remove.

AutoFHIR reconciliation:
This commit aligns the $process-message summary in source/messaging.html and the MessageHeader process-message OperationDefinition description with the applied zero-or-more response-message rule. It also narrows the return parameter documentation so a synchronous response Bundle is described as present when a response payload is needed, preserving the existing 0..1 cardinality and asynchronous no-return rule.

Recommendation:
Keep this commit as a source fix. It is a narrow consistency update to active source and does not reopen the rejected proposal to require a $process-message return; no separate source decision is needed here for the related FHIR-25252, FHIR-25465, or FHIR-40518 issues.
