FHIR-12216: Audit delete response code alignment

Issue request:
FHIR-12216 was a Published/Persuasive FHIR-I change request for the FHIR-core HTTP page. It reported that the delete interaction first said successful deletion, or a resource that does not exist, should return only 204 No Content, while the already-deleted-resource paragraph allowed 204 or 200. The accepted resolution was to align both statements so 200 OK is used when a response body is returned and 204 No Content is used when there is no response body.

Initial application:
The issue was applied in git-svn commit 3d7763fc7d0a1a1921562cf73de46c53197d669e, corresponding to svn @10126 cited in Jira. That commit changed source/http.html so both the general successful-deletion/nonexistent-resource sentence and the already-deleted-resource sentence say the server returns either 200 OK if the response contains a payload, or 204 No Content with no response payload.

Additional context:
The current HTTP page source is in build scope through publish.ini [pages], where http.html is listed as the HTTP page. The latest combined branch still has the aligned wording in source/http.html:1071-1086. A later Zulip discussion about DELETE and ETag questioned what a 200 OK delete payload would contain, but did not reverse the Jira decision; the discussion noted that 200 may be useful mostly for servers that always return 200. Direct FHIR-12216 Zulip and Confluence searches found no conflicting community record.

AutoFHIR reconciliation:
This commit intentionally makes no source change because the current source already satisfies the published resolution for FHIR-12216.

Recommendation:
Keep this audit commit as-is. No FHIR core follow-up is needed for FHIR-12216 unless FHIR-I separately decides to revisit whether DELETE should continue allowing 200 OK responses with payloads.
