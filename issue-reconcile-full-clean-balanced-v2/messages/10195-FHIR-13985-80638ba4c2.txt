FHIR-13985: Audit chained no-result search guidance

Issue request:
FHIR-13985 was a Published/Persuasive FHIR-I clarification for the FHIR-core Search page, raised against STU3. It asked how to handle a chained query such as AllergyIntolerance?patient.identifier=http://mysys|100 when no Patient has that identifier. The accepted resolution was to add more words to the search error safety guidance for parameters that have no matching values.

Initial application:
The issue was applied by svn r13431, preserved in git commit f341085fbec8cabb1d80347a17544919dd816297 with the message "GF#13985 - more narrative about unmatched chain searches". That commit added the patient.identifier no-match example and explanatory text to source/search.html. Later search-page rewrites and cleanup commits changed formatting and wording but preserved the substance in the current Handling Errors section.

Additional context:
The linked Zulip thread #implementers > Search issues records the exact question and rationale: ordinary searches with no matching rows return an empty set, while a server may still choose an error in narrow circumstances where it recognizes the identifier system and knows exactly one match should exist. The current source/search.html is in build scope through publish.ini, and bounded Jira/Confluence/community searches found no later conflicting decision.

AutoFHIR reconciliation:
This commit makes no source change. Current source/search.html already says an empty search result is not an error, that logical no-match conditions SHOULD be processed by returning an empty search set, and that the search set may include an OperationOutcome warning. It also includes the patient.identifier no-MRN example and links to a warning bundle example, satisfying the Jira request without adding duplicate prose.

Recommendation:
Keep this empty audit commit as-is. The current build already carries the accepted FHIR-13985 guidance, and further edits would be redundant rather than corrective.
