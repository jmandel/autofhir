FHIR-36859: Audit conditional update Resource.id clarification

Issue request:
FHIR-36859 was a Published FHIR-core HTTP change request, resolved Persuasive with Modification for R5, asking what a conditional update should do when the search finds no matches, the submitted resource has an id, and a resource with that id already exists. The approved resolution split the old "No matches, id provided" case into a non-existing-id Update as Create case and an already-existing-id 409 Conflict case.

Initial application:
The issue was explicitly applied by git commit e76c0dd6aa055fe1ad4d07c56cee8784707220b0, which changed source/http.html to add the two no-match/id cases. Later HTTP status-code formatting commits 9db1c10f97bbd396ea035531fec1e53dc12b22cd and ee761ef4bd5a52057846f25556c859510db5375c preserved that behavior while normalizing the 409 Conflict wording.

Additional context:
Earlier Published issues FHIR-17906 and FHIR-20390 explain the conditional-update decision table and the intended meaning of "id provided" as Resource.id. FHIR-I WGM minutes for 2022-05 record the FHIR-36859 Persuasive with Modification motion. Targeted Zulip searches found no later or conflicting community discussion. The current build source is the core HTTP page at source/http.html and already contains the two required bullets.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current HTTP page already says that when no search matches are found and the provided id does not already exist, the server treats the request as Update as Create or rejects it if unsupported, and when no search matches are found and the provided id already exists, the server rejects the update with 409 Conflict. A minor grammatical wording difference from the Jira resolution does not change implementer understanding.

Recommendation:
Keep this audit commit as-is. No further core source work is needed for FHIR-36859 unless the work group wants a separate editorial cleanup unrelated to the resolved semantic clarification.
