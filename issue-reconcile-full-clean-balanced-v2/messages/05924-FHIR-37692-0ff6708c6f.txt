FHIR-37692: Audit constraint key uniqueness wording

Issue request:
FHIR-37692 was Published as Persuasive with Modification for R5. It asked that ElementDefinition.constraint identifiers be unique within a StructureDefinition after duplicate sdf-24 constraint keys were found in the StructureDefinition source, with the final resolution calling for explicit specification language and tooling/test enforcement while allowing repeated appearances in derived sliced models.

Initial application:
The issue was applied in two Jira-tagged commits. d12d91aa97 renamed the duplicate StructureDefinition constraint key from sdf-24 to sdf-28, and 39122085c8 added conformance-rules.html language saying constraint keys identify constraints, are required to be unique when declared, and will be validated for meaningful uniqueness where validators can do so.

Additional context:
The FHIR-I Zulip thread for FHIR-37692 explains why a formal StructureDefinition invariant was not added: slicing and snapshots repeat inherited constraints, so uniqueness cannot be checked by a simple invariant over all repeated constraint elements. The 2022-08-22 FHIR-I minutes record the reopen and final persuasive-with-modification vote. The active StructureDefinition resource source remains in the build, and the current conformance rules source still carries the applied policy language.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already reflects the approved outcome: the original duplicate key was corrected, and the spec now declares the unique-when-declared rule in conformance guidance without adding the over-broad invariant that the follow-up discussion rejected.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-37692 unless a separate tooling review finds that validator/build enforcement is missing outside this source checkout.
