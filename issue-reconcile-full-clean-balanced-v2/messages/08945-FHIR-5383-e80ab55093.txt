FHIR-5383: Audit ValueSet definition and expansion clarification

Issue request:
FHIR-5383 was a Published/Persuasive DSTU1 vocabulary ballot comment for FHIR-core ValueSet. It asked that the specification make clear whether a requested ValueSet resource represents the definition, an expansion of codes, or validation behavior, with Grahame's resolution to clarify the ValueSet scope, refer to terminology service behavior, and make the terminology service API clearer.

Initial application:
No source commit explicitly mentioning FHIR-5383 was found. The Jira comments record that the issue was applied as part of terminology connectathon tasks, and 2015 ValueSet/terminology-service history shows a cluster of terminology connectathon-era commits clarifying ValueSet definitions, $expand behavior, and terminology service operations.

Additional context:
The active ValueSet resource is in build scope through source/fhir.ini's [resources] entry valueset=ValueSet and its vocab workgroup/FMM entries. Later published ValueSet ballot work, especially FHIR-14790 and FHIR-14791, refined the same compose-versus-expansion explanation by linking to element definitions and adding the current combinations-of-compose-and-expansion guidance. Searches found no direct Zulip or Confluence references for FHIR-5383 that would change the Jira/source conclusion.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Current source/valueset/valueset-introduction.xml states that ValueSet has compose and expansion aspects, that a ValueSet resource can carry either, both, or neither, and that $expand and $validate-code are the operations for generating expansions and checking membership. source/valueset/valueset-notes.xml describes expansion processing and the use cases for compose-only, expansion-only, both, and neither. source/terminology-service.html and the active ValueSet operation definitions describe the terminology service API for expansion and validation.

Recommendation:
Keep this no-change audit. The current specification addresses the original ambiguity without splitting definition, expansion, and validation into separate resources, and additional prose would duplicate existing active guidance rather than change implementer understanding.
