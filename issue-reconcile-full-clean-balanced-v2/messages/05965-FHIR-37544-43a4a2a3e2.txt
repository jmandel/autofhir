FHIR-37544: Audit Resource.id rendered type

Issue request:
FHIR-37544 was a Published/Persuasive with Modification FHIR-I change request raised against R4B because the HTML presentation for Resource.id on the Resource page rendered the type as string even though the underlying definition carried the id constraints. The resolution treated this as a rendering issue: Resource.id is a simple FHIRPath System.String with structuredefinition-fhir-type=id, and HL7/kindling#78 was filed so the renderer would display the constrained FHIR type.

Initial application:
No FHIR core source commit mentioning FHIR-37544 was found. The current core Resource source was already in the expected shape for this issue: the active Resource definition uses code http://hl7.org/fhirpath/System.String with structuredefinition-fhir-type valueUrl id. Related prior source work for FHIR-25274 added ElementDefinition documentation explaining how these simple FHIRPath string types and fhir-type constraints are meant to be interpreted.

Additional context:
The R4B published HTML still demonstrates the historic rendering problem by linking Resource.id to datatypes.html#string, while the R4B conformance JSON has structuredefinition-fhir-type=id. The current CI build now renders Resource.id as id in both resource-definitions.html and resource.html. The FHIR-I 2022-07-25 minutes record the vote for FHIR-37544, and the Zulip thread linked from Jira records Grahame's clarification that R4B's underlying structures were correct while the presentation was wrong. HL7/kindling#78 remains the external tooling issue for the renderer behavior.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current FHIR source and generated CI presentation already convey the correct Resource.id type to implementers, and a source edit would either duplicate the existing fhir-type mechanism or misrepresent why the underlying code remains FHIRPath System.String.

Recommendation:
Keep this no-change audit for the current FHIR core branch. If HL7 still wants a historical R4B technical correction, handle that through the publication/rendering tooling path rather than by changing the current Resource StructureDefinition source.
