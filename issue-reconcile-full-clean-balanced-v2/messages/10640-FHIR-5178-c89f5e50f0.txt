FHIR-5178: Audit workflow state guidance

Issue request:
FHIR-5178 was a Published/Persuasive with Modification DSTU1 ballot comment asking for clearer rules on when a stateful healthcare concept should be modeled as a separate resource versus as a lifecycle/status value on an existing resource. The recorded resolution said that, in STU3, workflow states would live on Task rather than Order/Request resources.

Initial application:
No Jira-keyed source commit for FHIR-5178 was found. The STU3-era workflow work appears to have been applied through broader workflow-pattern commits, especially git commit 5064224bd079b7f4ef4023d3ead9111b57bd8bff, which aligned resources with Request/Event/Definition patterns and updated the Workflow module without naming this Jira key.

Additional context:
The current build includes the Workflow module, Request pattern, and Task resource sources through active source/fhir.ini entries. Current source no longer supports the literal 2015 shorthand that every workflow state belongs only on Task: Request and Event resources have status/intent or status semantics for their own domain lifecycle, while Task is the workflow-management record for assignment, ownership, progress, and fulfillment. Related Jira discussion in FHIR-5707 supports this more nuanced model by recognizing that request and event resources can have separate lifecycle states when the workflow section clarifies their boundaries. Zulip and Confluence searches found no direct FHIR-5178 community record or conflicting later work-group decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active source already explains the implementer-relevant boundary: Request status/intent represents proposal/plan/order/authorization state, Event status represents activity/outcome state, and Task is used when separate workflow management of assignment, progress, or fulfillment is needed.

Recommendation:
Keep this audit commit as-is. Do not add a literal statement that all workflow states live on Task; that would conflict with the current Request/Event pattern model and with later status guidance. Future work should be driven by a current workflow issue if the work group wants stronger conformance rules around duplicated state across Task, request resources, and event resources.
