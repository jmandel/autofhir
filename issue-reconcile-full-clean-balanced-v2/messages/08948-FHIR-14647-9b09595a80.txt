FHIR-14647: Audit acceptUnknown removal

Issue request:
FHIR-14647 was a Published FHIR-core Conformance change request with resolution Persuasive with Modification. It asked to remove CapabilityStatement.acceptUnknown because the negative element name, vocabulary, and semantics were awkward and confusing, especially for requirements-based CapabilityStatements.

Initial application:
The Jira comment records svn revision 13220. In git history, f0ec862a5f986e3a82bb9ef1a4fa32619c65d6e1 corresponds to build@13220 and removed CapabilityStatement.acceptUnknown from the CapabilityStatement source/examples while also hiding the JSON/XML representation-page links to the removed element. The current CapabilityStatement StructureDefinition does not define CapabilityStatement.acceptUnknown.

Additional context:
source/fhir.ini actively includes capabilitystatement=CapabilityStatement and assigns CapabilityStatement to the conformance work group with normative version 4.0.0, so the current CapabilityStatement source is in build scope. Remaining acceptUnknown grep hits are not a current CapabilityStatement element: two are inside HTML comments on the JSON/XML pages, one is an HTML-comment TODO in the CapabilityStatement introduction, one is inert CapabilityStatement narrative XSLT handling with no current source instances, release2/release3 hits are historical, and the Library QUICK model hit is QUICK.Conformance example content rather than the current CapabilityStatement definition. A Zulip thread in 2020 explicitly points implementers asking about R4 acceptUnknown back to FHIR-14647 and notes no replacement had been defined.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current build-scope CapabilityStatement source already reflects the issue by omitting CapabilityStatement.acceptUnknown, and the remaining references do not create a current conformance element or rendered instruction.

Recommendation:
Keep this no-change audit as-is. Future work should be separate from FHIR-14647 unless the work group decides to define a replacement declaration mechanism for unknown extension/element handling or to clean non-rendered comments and historical/example artifacts as editorial maintenance.
