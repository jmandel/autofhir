FHIR-41186: Audit DocumentReference related context support

Issue request:
FHIR-41186 was an Applied OO change request raised against R5 because DocumentReference.context.related in R4 allowed links to arbitrary contextual resources, while R5 subject and basedOn did not cover those use cases. The issue was resolved as Persuasive with Modification with an 8-0-0 vote on 2024-05-20; the resolution text said to modify .context to allow Reference(Any).

Initial application:
No current git commit message explicitly mentions FHIR-41186. History shows FHIR-32585 commit 1211a3b963 removed the earlier DocumentReference.related Reference(Any) before R5. After FHIR-41186 was resolved, commit d63adb6a17, "DocumentReference updates June 20204", restored a DocumentReference.related element as Reference(Resource) and added the related search parameter, matching the implementer's Jira comment that related was brought back instead of changing .context.

Additional context:
The current build includes DocumentReference as an active resource. Current source keeps DocumentReference.context limited to Appointment, Encounter, and EpisodeOfCare because it supports encounter-like context and associated constraints, while DocumentReference.related.target is now Reference(Resource). Later Applied R6 issues FHIR-53824 and FHIR-53550, already represented on the combined branch, retained the arbitrary-resource target but made related a coded backbone and added guidance so related does not duplicate subject, context, or lifecycle relatesTo.

AutoFHIR reconciliation:
No source change was made. The current source already provides the requested arbitrary-resource linkage through DocumentReference.related.target Reference(Resource), has the search parameter wired to DocumentReference.related.target, and has implementation guidance explaining appropriate use. Changing .context itself to Reference(Any) now would conflict with the implementer's Jira note and later R6 decisions.

Recommendation:
Keep this audit commit as-is. If OO wants Account or another specific resource added to DocumentReference.context, or wants .context itself widened despite the later related-backbone decision, that should be handled by a new tracker because the current issue has been applied through the related element.
