FHIR-12259: Audit implicit type slicing guidance

Issue request:
FHIR-12259 was a Published/Persuasive FHIR-core change request from DSTU2 asking the profiling and ElementDefinition guidance to clarify implicit type slicing for choice elements. The approved change required the base [x] element to stay in snapshots, type-list constraints to be made on the original [x] element, type-specific constraints to apply only to the relevant type slice, and the obsolete @type discriminator wording to be removed in favor of slice/id handling such as Patient.deceased[x]:deceasedBoolean.

Initial application:
The issue was directly applied by c7c93dc81ec97baf811ceabb97ab0e5ba80b90a2, which removed the old statement that a 0..1 choice element sliced by type used discriminator "@type" and added the current "Constraining elements with a choice of Type" rules to source/elementdefinition.html. A later same-family issue, FHIR-16312, added the ElementDefinition.id note explaining that type-choice ids reflect the type slice.

Additional context:
Later Published/Persuasive R5 issues FHIR-39180 and FHIR-39182 changed the examples away from choice type renamed paths such as Patient.deceasedBoolean and toward the current full slice form Patient.deceased[x]:deceasedBoolean. Zulip discussion confirms FHIR-12259 as the original policy source and later records the community/tooling move to the full slice syntax while preserving the rule that a type-specific element does not by itself constrain the allowed type list.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-source text in source/elementdefinition.html already states that choice-element ids reflect type slices, that allowed-type constraints belong on the original [x] element, that a type-specific element constrains only that type, and that the original element always appears in snapshots. The active build configuration also maps ElementDefinition to the elementdefinition page, and source/hierarchy.xml includes the profiling page in the built navigation, so the relevant current source is in build scope.

Recommendation:
Keep this audit commit as-is. No FHIR-12259 source edit is needed unless the work group later chooses to reopen the broader tooling question about implicit differential shorthand versus explicit snapshot slicing.
