FHIR-6850: Audit modifier-extension rejection response note

Issue request:
FHIR-6850 was a Published/Not Persuasive with Modification FHIR-core extensibility issue from the DSTU1 ballot asking what HTTP response should be returned on create or update when an unknown modifier extension is detected, and whether server validation should check for those extensions. The resolution was to add a note about possible server return values to the modifier-extension section, with no other change.

Initial application:
Git commit b58cc25916bd7787982d82331cb5654a4b7bc305, corresponding to svn revision 6392 cited in the Jira comments, added the current note that a server could return HTTP 422 with an OperationOutcome when a client PUTs or POSTs a modifier extension it does not know.

Additional context:
FHIR-7259 asked the adjacent OperationOutcome error-code/recommendation question for the same modifier-extension wording and was marked "already done" the day after the #6850 source change. Later FHIR-18353 narrowed the meaning of "process the data" so that rejection remains one option without implying that all storage or pass-through handling is prohibited. source/fhir.ini maps the Extension type page to extensibility, so source/extensibility.html is in current build scope.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Current source/extensibility.html retains the possible server response note requested by FHIR-6850, and the later processing-scope edits do not invalidate it.

Recommendation:
Keep this no-change audit. The source already reflects the approved note; any stronger server validation rule or mandatory OperationOutcome.issue coding would require a separate work-group decision.
