FHIR-13915: Audit create Location version fallback

Issue request:
FHIR-13915 was a Published/Persuasive STU3 FHIR-core HTTP issue asking what Location header a create response should use when a server does not support version-specific retrieval. The resolution was to document that Location should be as specific as the server can supply: include the version when the server understands versioning, and allow [base]/[type]/[id] when it does not.

Initial application:
The Jira comment records svn revision 14043, and git commit fa063a9991eb8c08d9ca71ed51016822812eb338 is the corresponding git-svn application. It changed source/http.html to add the current rule that the Location header should be as specific as possible and that non-version-tracking servers return [base]/[type]/[id].

Additional context:
The current RESTful API source is still source/http.html, the Jira-related FHIR-core HTTP page. Later FHIR-17746 added that the Location MAY be absolute or relative in the same paragraph, and FHIR-26358 reused the same version-aware Location pattern for create-via-update and conditional interactions. A related 2022 Zulip discussion quoted the current text as the operative rule and did not identify a versioning problem. Direct FHIR-13915 Zulip and Confluence searches found no conflicting community evidence.

AutoFHIR reconciliation:
This audit makes no source change. Current source/http.html already says create returns Location: [base]/[type]/[id]/_history/[vid] when versioning is available, then explicitly says servers that do not track versions use [base]/[type]/[id]. The neighboring update and conditional-create text points back to the same behavior and does not require a separate FHIR-13915 correction.

Recommendation:
Keep this empty audit commit as-is. The issue's requested clarification is present in the active RESTful API source, and editing the current wording would be redundant unless a future work-group issue reopens the broader HTTP Location header rules.
