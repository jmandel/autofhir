FHIR-32581: Audit DocumentReference security label explanation

Issue request:
FHIR-32581 was a Published/Persuasive with Modification OO change request for DocumentReference.securityLabel. It asked the specification to explain why DocumentReference.securityLabel and DocumentReference.meta.security can both exist, when they can differ, and how each should be used.

Initial application:
The older DocumentReference.securityLabel definition already distinguished the referenced document's labels from DocumentReference.meta.security, but Jira comments asked for a clearer explanation. Git commit 1e542148c2d27a0394c2798fa8a1a78014db1b4d expanded the active StructureDefinition definition to mention the content at DocumentReference.content.attachment.url, explain that meta.security labels the data elements in DocumentReference while securityLabel labels the referenced document, and add the sensitive-document/less-sensitive-metadata example. Git commit 314c3b3a9f56c4480808c133aec77d1078f3bf6f later changed only "may" to "might" in that sentence.

Additional context:
DocumentReference is active in source/fhir.ini, so source/documentreference/structuredefinition-DocumentReference.xml is current build source. OO Confluence minutes show the issue moving from a request for John Moehrke to write a better description, to Persuasive with Modification and block vote approval. Later FHIR-39687 asked to remove DocumentReference.securityLabel as duplicative, but was resolved Not Persuasive because FHIR-32581 had already clarified the distinction; the related Zulip thread states the same distinction.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active source already contains the clarification requested by FHIR-32581, including when the labels differ and why DocumentReference metadata may be less sensitive than the referenced document. Adding more prose would be redundant and risks drifting from the authoritative element definition.

Recommendation:
Keep this audit commit as-is. Future work should be limited to a new tracker if implementers still find the element definition unclear; the current FHIR-32581 requirement is already represented in build-scope source and supported by the later FHIR-39687 no-change decision.
