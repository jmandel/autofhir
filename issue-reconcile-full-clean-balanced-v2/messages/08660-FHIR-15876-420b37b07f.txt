FHIR-15876: Correct FHIRPath System.String examples

Issue request:
FHIR-15876 is a Published/Persuasive FHIR-core issue for the FHIRPath page. It asked to clarify that FHIR is the namespace for FHIR types, that FHIR primitive types differ from FHIRPath system types including case, how implicit primitive conversion works, that is() remains type-explicit while the then-current as() behavior was different, and to clarify the getValue() helper.

Initial application:
The issue was applied by git-svn commit 340c69711cee6353255046839edc4d5589876755, matching the Jira comment for svn revision 14058, which added the FHIR type namespace prose, the FHIR-to-System mapping table, the is()/getValue() examples, and the as()/later ofType() example block to source/fhirpath.html. Later FHIRPath refactors preserved the section and changed the old as() example terminology to ofType(), but the current examples still used System.string in three places even though the same section and the FHIRPath type code system use System.String.

Additional context:
source/hierarchy.xml lists fhirpath.html as the active FHIRPath page, so source/fhirpath.html feeds the current build. source/terminologies/codesystem-fhirpath-types.xml declares the FHIRPath type code system as case-sensitive and defines http://hl7.org/fhirpath/System.String. Later related trackers FHIR-37861 and FHIR-55495 specifically call out the remaining System.string casing, but they are still Triaged rather than Applied or Published and are not separately decided here; FHIR-53948 is a broader unresolved follow-up about primitive conversion semantics and should remain outside this narrow reconciliation.

AutoFHIR reconciliation:
Updated the three remaining System.string examples in source/fhirpath.html to System.String so the examples match the surrounding case-sensitive type mapping and the FHIRPath type code system.

Recommendation:
Keep this narrow source fix as-is for FHIR-15876. Do not treat this commit as deciding FHIR-37861, FHIR-55495, or FHIR-53948; those later trackers should be handled separately if the work group wants broader changes to ofType(), getValue(), hasValue(), or primitive conversion wording.
