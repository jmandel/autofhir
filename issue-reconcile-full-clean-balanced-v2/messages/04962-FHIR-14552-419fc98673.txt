FHIR-14552: Audit TerminologyCapabilities server identity

Issue request:
FHIR-14552 was Published with resolution Persuasive with Modification. It asked for TerminologyCapabilities to identify the server it describes, for example by reference to CapabilityStatement.url and CapabilityStatement.version, and the resolution said to add server .url, .version, and .description based on CapabilityStatement.

Initial application:
The issue appears to have been applied in svn revision 14629, represented in git as ecf37e5e12a995d95d0e549e90a8aa32e6d83a2a (#GF14552 - add to TerminologyCapabilities). That commit added the CapabilityStatement-style kind, software.name/version, and implementation.description/url structure to the TerminologyCapabilities spreadsheet and example. The current source preserves the same model in the active TerminologyCapabilities StructureDefinition: software.version identifies the covered software version, while implementation.description and implementation.url identify the specific installation/base URL.

Additional context:
TerminologyCapabilities is an active current-build resource in source/fhir.ini and is marked normative. Later source migration retained the applied elements in structuredefinition-TerminologyCapabilities.xml, and CapabilityStatement itself uses the same software.version plus implementation.description/url separation rather than an implementation.version element. Later related issue FHIR-24698 updated the terminology service CapabilityStatement/TerminologyCapabilities examples and required a mode=terminology TerminologyCapabilities to include url, name, title, status, date, codeSystem, kind, and codeSystem version details, but it did not require a distinct server or implementation version element. Jira, Zulip, and Confluence searches found no later final decision requiring such an element for TerminologyCapabilities.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Adding TerminologyCapabilities.server.version or TerminologyCapabilities.implementation.version now would introduce new normative content not supported by the applied source history or by later related requirements. The current source already satisfies the issue's durable intent by allowing an instance-specific server description/base URL and a software version.

Recommendation:
Keep this audit commit as-is. Revisit only if the Vocabulary/Terminology Infrastructure work group opens a new final issue to add a distinct server-version element beyond the existing CapabilityStatement-style model.
