FHIR-6332: Audit history bundle rationale

Issue request:
FHIR-6332 was a Published/Persuasive with Modification DSTU1 FHIR-core Feed issue asking to clarify why history bundle entries were required to carry transaction details. The approved resolution was to explain that this lets receivers distinguish creates from updates and allows a history bundle to be treated as a transaction, while noting limitations around lost transaction boundaries.

Initial application:
The issue was applied in SVN revision 6411, represented in git as 696b360575967d922958bf43deb51be8af31541c, which changed source/http.html to say history Bundles can be treated as transactions for pub/sub-style replication, noted original transaction-boundary limitations, and added that request details let subscriber systems differentiate create and update interactions.

Additional context:
The current specification has renamed the old Bundle entry transaction element to request and has later Bundle rules requiring history entries to contain request and response details. A recent FHIR-7933 reconciliation commit updated the same active source/http.html history paragraph so it aligns with those current rules while preserving the FHIR-6332 rationale.

AutoFHIR reconciliation:
Made no source change. The active HTTP history text already explains both parts of the FHIR-6332 resolution: history Bundles can be processed as transaction or batch-like input for replication with transaction-boundary caveats, and entry.request information lets subscriber systems distinguish newly created resources from updates.

Recommendation:
Keep this empty audit commit as-is. Reopening the source would be redundant and risks drifting from later request/response terminology and Bundle invariants that already preserve the approved rationale.
