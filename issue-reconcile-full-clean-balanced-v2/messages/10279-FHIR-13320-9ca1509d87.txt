FHIR-13320: Audit _id search case sensitivity

Issue request:
FHIR-13320 was a Published FHIR-core search change request resolved as Persuasive. It reported that the all-resource _id search parameter is type token while Resource.id is a case-sensitive id primitive, and asked the search specification to clarify that _id searches are case-sensitive, token case sensitivity depends on the underlying data semantics, exact-match language should not imply generic case-insensitive token behavior, common Resource search parameters should appear in the search summary table, token searches over string data are not case-sensitive, and the safety tradeoff should be documented.

Initial application:
The issue was applied in git-svn commit 2d2371c75b043e4332188b63d93cdc5fc7667767, whose subject is "#13320 notes about case sensitivity on token searches" and whose git-svn metadata records build revision 12779, matching the Jira application comment. That commit added the _id case-sensitive note, changed token search from an unqualified exact-match description to a closer-to-exact description, added context-dependent token case-sensitivity wording, added the string-backed-token note, and added the safety note.

Additional context:
The current build-scope search page is listed in publish.ini and still carries the intended rule: token matches are literal and case-sensitive unless the relevant context indicates otherwise, _id matches are always case-sensitive, and string-backed token searches are not case-sensitive. The dedicated _id section explains that _id uses token search with only the code segment and exact matching rather than case-insensitive string starts-with behavior, and the search summary table includes the Resource-level _id row. Later search-page refactoring in ddecc63591d23dab5767aa2888c985a7c75964b6 moved this material into the current structure without reversing it. Related FHIR-6123, FHIR-13655, and FHIR-19673 audit commits are already present on the combined branch and support the same current interpretation.
