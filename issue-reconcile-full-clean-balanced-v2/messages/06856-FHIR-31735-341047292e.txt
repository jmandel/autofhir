FHIR-31735: Audit validation tools handoff

Issue request:
FHIR-31735 was Published with a Persuasive with Modification resolution for R5. The original request asked to stop describing the Java validator as the only full FHIR validator and to account for the Firely .NET SDK validator; the accepted modification was to move mutable tool-specific documentation out of the core spec by linking implementation tools, reference implementations, and validator information to Confluence pages.

Initial application:
The issue was applied in PR HL7/fhir#2396 through commits 472abf78c495c2ae44924d499be7434ed50788d0 and e404ccd07129409bf907b904ae62ded6c82d28bf, merged as f4d043fc5f79889b21e1a4f09281534b89deea2a. Those commits changed source/validation.html from a Java-validator-specific section to a generic FHIR validators section linked to the FHIR Tools Registry, changed Java-validator caveats to refer to validators/common validators, moved downloads tool listings to the FHIR Tools Registry, and moved implementation support reference implementation lists to Confluence. Related commit f575ef6b27e6bc5fc01db942c9cf8d00f50099f2 had already moved downloads-page reference implementation rows to Confluence for FHIR-30088.

Additional context:
FHIR-I minutes for the January 2022 WGM record agreement that other tools should be listed and likely maintained on a Confluence page so the list can be updated independently from the spec. Current source/hierarchy.xml and publish.ini confirm that source/downloads.html, source/validation.html, and source/implsupport-module.html are active build pages. A related combined-branch audit for FHIR-33980 already records the same reference-implementation handoff pattern for Android SDK listings, so this commit does not attempt to decide that related issue again.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source no longer says the Java validator is the only full validator, points implementers from validation.html and downloads.html to the Confluence FHIR Tools Registry, and points reference implementation/library information from implsupport-module.html to the Confluence Open Source Implementations page. Adding Firely .NET SDK details directly to core source now would reverse the accepted Confluence handoff and create a stale mutable tools inventory in the specification.

Recommendation:
Keep this no-change audit commit as-is for the core specification. If Firely .NET validator details or official-tool status need updates, maintain them on the relevant Confluence tools/validation registry page rather than in the FHIR core source checkout.
