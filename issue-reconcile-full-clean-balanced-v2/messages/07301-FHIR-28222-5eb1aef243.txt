FHIR-28222: Audit OperationDefinition operation-code naming guidance

Issue request:
FHIR-28222 was a Published/Persuasive with Modification FHIR-I change request asking that OperationDefinition document the naming/casing rules for custom operation codes and suggesting warning invariants for non-conforming OperationDefinition.code values. The approved resolution was to link from the OperationDefinition page, specifically the code element or other applicable locations, to the HL7 Guide to Designing Resources naming rules and not to implement invariants at this point.

Initial application:
The issue was applied by historical commit f66495934d6e14f49960225f34dad67af323c298, which added an OperationDefinition Code narrative section and updated the OperationDefinition.code element comment with the Confluence Naming Rules & Guidelines link. Current source/fhir.ini actively includes OperationDefinition as a built resource, so the checked source locations feed the current core build.

Additional context:
The FHIR-I 2020-11-09 minutes record the 9-0-1 Persuasive with Modification motion to create a link to the Confluence naming guidelines and not update invariants. The linked Zulip thread shows the original question and later rationale: the group preferred awareness/documentation over brittle constraints that could create spurious errors, and clarified that the Confluence rules are internal HL7 authoring guidance rather than binding rules for all implementers.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current OperationDefinition.code already includes the requested naming-guidelines link, the OperationDefinition narrative also points to the same guidance, and no OperationDefinition.code casing invariant has been added.

Recommendation:
Keep this audit commit as-is. No current-spec source fix is needed for FHIR-28222 unless the work group later decides to replace the external methodology link with ballot-controlled normative text or validator warnings.
