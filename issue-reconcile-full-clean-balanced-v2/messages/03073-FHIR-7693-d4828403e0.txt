FHIR-7693: Audit Bundle.signature guidance

Issue request:
FHIR-7693 was Published with resolution Persuasive with Modification. It asked who or what should sign a Bundle, how Bundle signatures are used, what happens when a transaction is unsigned, and required three concrete changes: add rationale for document/message/transaction/search-response signatures, add a usage note that signing and verification requirements are implementation-environment specific, and revise Bundle.signature from base64Binary to Signature.

Initial application:
The issue was applied in svn revision 5820, now git commit 2e87ff782b75b5c2f1945c9e475fc1057a4056d1, which added the requested rationale and usage note to source/bundle/bundle-spreadsheet.xml. That spreadsheet-era source was later converted into source/bundle/structuredefinition-Bundle.xml during the current source refactor, preserving Bundle.signature as type Signature with the FHIR-7693 rationale and comment until the later digital-signature rewrite.

Additional context:
Current source/fhir.ini has Bundle as an active resource, so source/bundle/structuredefinition-Bundle.xml is in build scope. Later work made Signature and Bundle.signature normative in FHIR-44637, then FHIR-51099 and FHIR-I minutes explicitly chose not to relax Bundle.signature cardinality because Bundle signing should move to Provenance resources; source commit 9fe4e8ba2ec241ab35dc18046c102c38872e1d50 implemented that direction by deprecating Bundle.signature and moving the substantive signing guidance to source/signatures.html. FHIR-52810, already represented on the combined branch, further updated the Provenance-based embedded Bundle signature target rule.

AutoFHIR reconciliation:
This commit makes no source change. The current source still satisfies the durable parts of FHIR-7693: Bundle.signature is typed as Signature, the signature guidance explains authenticity, integrity, non-repudiation, local-policy-dependent signing and verification requirements, and the current Bundle-specific guidance points implementers to Provenance-based signatures rather than reviving the old Bundle.signature rationale on a deprecated element.

Recommendation:
Keep this audit commit as-is. Do not re-add the 2015 Bundle.signature rationale to the element definition unless the work group reverses the later Provenance/deprecation direction, because doing so would make the deprecated element look more current than the normative signing guidance now intends.
