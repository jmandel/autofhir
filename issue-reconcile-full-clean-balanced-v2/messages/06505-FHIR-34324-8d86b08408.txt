FHIR-34324: Align validate status guidance

Issue request:
FHIR-34324 is a Published/Not Persuasive with Modification FHIR-I issue for R5 asking whether the Resource $validate operation should always return 200 OK when the resource is invalid. The accepted clarification says the operation returns 200 provided validation could be performed, regardless of whether validation issues were found, while malformed or otherwise unprocessable validated content can cause the overall operation to fail with a 4xx or 5xx response.

Initial application:
The issue was applied in commit 6da05ac1f1fe5ad00535a873c3dfa112ab64e0fd from PR #1804, but that source commit updated only the build footer markdown in source/resource/operationdefinition-Resource-validate.xml. The formal OperationDefinition comment field still needed to carry the same clarified status-code rule so generated conformance content does not preserve the older unconditional 200 OK wording.

Additional context:
Resource is active build-scope infrastructure content in source/fhir.ini, and source/resource/list-Resource-operations.xml references OperationDefinition/Resource-validate. A later FHIR-37626 reconciliation commit added concrete-resource-type endpoint clarification to both the footer and the comment, but its comment text retained the old FHIR-34324 status-code sentence while the footer kept the corrected sentence. FHIR-I minutes for 2022-03-21 record the Not Persuasive with Modification vote, and no Zulip or Confluence search found conflicting rationale.

AutoFHIR reconciliation:
This commit updates only the Resource $validate OperationDefinition comment to use the same clarified 200 response guidance already present in the build footer: 200 applies when validation was possible regardless of validation issues, while invalid character sets, broken JSON, or similar content errors may fail the overall operation with a 4xx or 5xx response.

Recommendation:
Keep this source fix. It completes the already-approved FHIR-34324 clarification in the active OperationDefinition source without changing the later endpoint-path clarification or adding new policy.
