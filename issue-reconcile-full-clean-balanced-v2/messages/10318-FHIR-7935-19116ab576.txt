FHIR-7935: Audit search error handling guidance

Issue request:
FHIR-7935 was a Published FHIR-core change request, resolved Persuasive with Modification, asking for clearer resource integrity/lifecycle guidance for reads and searches when resource identifiers have been merged, deleted, redirected, or otherwise modified. The final disposition narrowed the applied change to adding a section about handling errors with searches.

Initial application:
The issue appears to have been applied in svn revision 5666. The corresponding git-svn commit 20dc2f7c4a605bfe418bb4ed6144164271989ea2 was headed for FHIR-7285, but it also added the search Handling Errors section that FHIR-7935's Jira comment identifies as revision 5666. A later typo fix, bf1ce05118d8bd16a2bf66b7ac35f69eeb272cd8, corrected the syntactic/logical error sentence.

Additional context:
Current source/search.html contains explicit search error guidance: failed searches use 4xx/5xx with OperationOutcome when appropriate, syntactically invalid parameters should error, logical misses such as unknown subjects/codes should return an empty search set, and OperationOutcome entries may provide hints. The _id/logical identifier text now also explains that searching by id returns a Bundle and may include OperationOutcome information when the id does not exist or cannot be returned. Current source/http.html still has a Transactional Integrity section, while the detailed search behavior is centralized on the Search page. Later FHIR-9263 clarified that OperationOutcome entries are not counted in Bundle.total. Later FHIR-19687 and Patient merge material address the broader patient merge/linking use case separately and do not reverse the generic search error guidance.

AutoFHIR reconciliation:
No source change was made. The current build source already satisfies the final FHIR-7935 disposition, and adding duplicate HTTP-page prose would risk diverging from the active Search page guidance and later patient-specific merge guidance.

Recommendation:
Keep this audit commit as-is. If further patient merge behavior is revisited, handle it under patient/merge-specific issues rather than reopening FHIR-7935's already-applied generic search error handling.
