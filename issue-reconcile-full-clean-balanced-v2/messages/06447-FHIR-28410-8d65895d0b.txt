FHIR-28410: Audit ServiceRequest instantiates clarification

Issue request:
FHIR-28410 was a Published/Persuasive OO change request for R5. It reported that ServiceRequest.instantiatesCanonical was ambiguous because a ServiceRequest might either result from applying an ActivityDefinition/PlanDefinition or state that it should be performed according to one. The approved disposition asked to update the ServiceRequest.instantiatesCanonical comment with the PlanDefinition-vs-ActivityDefinition boundary text and link to PlanDefinition Boundaries and Relationships; replacing instantiates[x] with more precise relationships was explicitly left to separate Jira work.

Initial application:
The requested R5 wording was applied in commit 393306ab233c610059b90f85a380266c366634fb, which replaced the ServiceRequest.instantiatesCanonical comment with the approved PlanDefinition/ActivityDefinition clarification and PlanDefinition boundary link. No additional current-source application is needed for that element because it is no longer present in the active ServiceRequest StructureDefinition.

Additional context:
The 2023-02-03 OO minutes for FHIR-28410 recorded both the immediate clarification and the expectation that ServiceRequest.instantiatesCanonical and instantiatesUri should be removed in the future. Later workflow-alignment issues FHIR-40499 and FHIR-43441 did that R6 work: ServiceRequest.instantiatesCanonical, instantiatesUri, and their search parameters were removed in favor of the more precise workflow instantiation extensions. The current active ServiceRequest source is registered in source/fhir.ini, has no instantiatesCanonical or instantiatesUri elements, and uses ServiceRequest.code as the remaining ActivityDefinition/PlanDefinition reference surface. FHIR-47249 later clarified that PlanDefinition may be used for grouped activities such as order sets. The PlanDefinition Boundaries and Relationships page still contains the FHIR-28410 boundary wording.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The ambiguity FHIR-28410 fixed was applied for R5 and is not present in the current authoritative ServiceRequest element set after the later R6 removal decisions. The only discovered leftover old wording is in source/servicerequest/servicerequest.svg, a generated-looking diagram/title artifact; editing that alone would not change the authoritative specification source and is out of scope for this reconciliation.

Recommendation:
Keep this audit commit as-is. If reviewers want more local guidance on choosing ActivityDefinition versus PlanDefinition for ServiceRequest.code, handle that through FHIR-47249 follow-up or a new tracker rather than reviving the removed instantiatesCanonical comment.
