FHIR-13796: Audit vital signs supporting values

Issue request:
FHIR-13796 is a Published/Persuasive OO change request from STU3. It reported that the Vital Signs Base profile constrained Observation.value[x] and Observation.component.value[x] to Quantity and pointed supporting related observations back to a Vital Signs profile, making supporting observations such as blood pressure cuff size as a CodeableConcept impossible. The recorded resolution was to loosen the value constraint so permitted value datatypes could be used.

Initial application:
No source commit explicitly named FHIR-13796. The linked 2017 implementers Zulip thread records that GF#13796 was filed from the cuff-size/supporting-observation discussion and that OO approved relaxing the constraint for supporting observations. Source history shows the old cuff-size/CodeableConcept wording entered the vital-signs profile family in the 2018 vitals slicing work around GF#13897/GF#13964/GF#14037, and the related FHIR-14037 decision moved the old Observation.related restriction out of the base Vital Signs profile.

Additional context:
Later applied R6 vital-signs decisions refine how the original concern should be interpreted now. FHIR-31382 removed the confusing statement that cuff size could be an Observation.value[x] CodeableConcept and replaced the base Observation.value[x] definition with "The quantity for the vital sign being observed." while leaving Observation.component.value[x] generic. FHIR-27800, FHIR-43353, FHIR-47136, FHIR-48427, and existing combined-branch reconciliations moved unit bindings and Must Support requirements so supporting data can be carried in components or related observations without forcing all components to be Quantity. Current source/fhir.ini lists Observation as an active resource, and source/observation/implementationguide-Observation-vitalsigns.xml includes StructureDefinition/vitalsigns in the active Vital Signs IG.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current combined-branch source still keeps the actual vital-sign Observation.value[x] as Quantity, consistent with later FHIR-31382 wording, but it no longer blocks the seed issue's practical supporting-observation use case: Observation.component.value[x] has no datatype restriction or unit binding on the unsliced element, the Quantity unit binding is limited to the valueQuantity slice, and Observation.hasMember targets generic Observation rather than only the Vital Signs profile.

Recommendation:
Keep this no-change audit. Reopening Observation.value[x] to all datatypes now would contradict later applied OO clarification that cuff size is not the BP Observation.value[x]; if OO wants non-Quantity top-level vital-sign values again, that should be handled by a new tracker that explicitly supersedes FHIR-31382 and the R6 vital-signs profile cleanup.
