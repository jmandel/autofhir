FHIR-7800: Audit profile cardinality warning

Issue request:
FHIR-7800 is a Published/Persuasive FHIR-core profiling issue from DSTU1 asking the publishing tools to warn when a derived profile uses cardinalities that are not allowed by the base definition, such as changing a base 0..1 element to 0..*.

Initial application:
The Jira application comment says "svn revision 5954 - add warnings." Git history contains that SVN import as commit f50c21837c0d37e53da00f4d29fd0594d3c5f24e, "#7800 - detect illegal cardinalities in profiles," which added min/max derivation warning checks to the old tools/java ProfileUtilities implementation.

Additional context:
The current profiling source still states that a profile can only restrict cardinality within the limits of the base structure and includes a base-vs-derived cardinality table showing that 0..1 cannot become 0..n and 1..1 cannot become optional or repeating. The current Gradle build depends on the external kindling publisher artifact and the historical tools/java source tree changed by r5954 is absent from this checkout, so there is no current in-repository publisher hunk to restore. Related FHIR-7799 added the cardinality documentation table in SVN r6465, and adjacent FHIR-7801/FHIR-7802 audit commits on the combined branch already cover the neighboring binding-strength documentation and tooling-warning issues.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current built profiling guidance already conveys the cardinality restriction that the historical warning protected, the historical warning was applied in repository history, and editing current core source would either duplicate existing prose or target obsolete/absent tooling files rather than the current publisher implementation.

Recommendation:
Keep this empty audit commit as-is for FHIR-7800. If future validation shows the current external kindling/validator publisher no longer enforces this rule, track that as a tooling issue in the publisher/validator codebase; no current core spec source change is indicated by this reconciliation.
