FHIR-20925: Audit maxLength complex-type restriction

Issue request:
FHIR-20925 was Published/Persuasive with Modification for FHIR-core ElementDefinition. It asked that ElementDefinition.maxLength be prohibited for non-simple/complex types such as CodeableConcept or Reference; the final resolution was to clarify the long description rather than add an invariant, with the 2019 wording initially narrowed toward strings because the then-normative short description said "strings".

Initial application:
Commit fce5daa6e5be65acdae0d73ed5aa36503e75b532 applied the seed by changing source/datatypes/elementdefinition.xml from "Max length for strings" to "Max length for string type data" and adding that maxLength SHOULD only be used on primitive data types with a string representation. That applied the core non-complex-type direction, but later decisions revisited the exact primitive/string scope.

Additional context:
FHIR-22128 is the same maxLength type-scope family and is already represented on the combined branch by commit b4e0f63158d8b5dfb2dc06497a562c836002c49f. It reconciled the current source to say maxLength SHALL only be used on primitive data types where character length has meaning, not complex types such as Coding. FHIR-49226 later clarified date/dateTime/time support and removed boolean from Questionnaire's maxLength constraint. source/fhir.ini lists ElementDefinition as an active normative datatype, so source/datatypes/elementdefinition.xml is current build-scoped source.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current ElementDefinition.maxLength source already prohibits complex/non-simple use and its broader primitive wording is required by later applied decisions, so reverting to the seed's original string-only phrasing would be wrong for the current build.

Recommendation:
Keep this audit commit as-is for FHIR-20925. No further FHIR-core source change is recommended for the seed; any future tightening should be handled through a new work-group decision because later issues intentionally broadened support beyond string-only data.
