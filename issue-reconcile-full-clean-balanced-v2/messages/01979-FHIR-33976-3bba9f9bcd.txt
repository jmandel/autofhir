FHIR-33976: Audit Location near sort guidance

Issue request:
FHIR-33976 was a Published/Persuasive PA change request asking whether Location searches using the near parameter are implicitly sorted by distance and how a client can request the closest matches, especially when the calculated distance is returned in Bundle.entry.search rather than on the Location resource.

Initial application:
The issue was applied before this reconciliation by commit ecb4dd444f3c065bac2460eb9df26b4f66b2af4a, which added the Location Positional Searching guidance and updated the Location-near SearchParameter description. Commit 98ea87dae0a4e9ad4ad4c780ae3322607f099ba1 later adjusted SearchParameter description line breaks. Current source still contains the applied guidance.

Additional context:
PA minutes show the January 2022 decision to add guidance and the April 2022 refinement that coordinated FHIR-33976 with FHIR-27157's Location-near unit/algorithm clarification. A later source commit for FHIR-40693 corrected the example from _sortby=near to the current _sort=near syntax, so the current example no longer carries that stale wording.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Location is active in source/fhir.ini, and the active Location notes already say that sorting by near may be treated as an ordered set, that the order may not be dependable, that near MUST also be supplied when sorting by near, and that a Bad Request is returned if _sort=near is requested without near. The active Location-near SearchParameter description already contains the algorithm-undefined caveat requested by the final resolution.

Recommendation:
Keep this no-change audit commit as-is. No follow-up core source work is needed for FHIR-33976 unless PA later chooses to strengthen the guidance from permissive/clarifying text into stricter conformance language.
