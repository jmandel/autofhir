FHIR-13271: Audit digital signature update guidance

Issue request:
FHIR-13271 was a Published/Persuasive Security work group change request for STU3. It asked that the Digital Signatures text reference the storage/retrieval variation discussion at updates.html, with the resolution to add text to the Security and Privacy Module page and the Signature datatype as prescribed.

Initial application:
The issue appears to have been applied by the 2017-08-14 security batch commit 84f8086d21facb3551bfb28481156250510ae48b, whose message explicitly lists GF#13271 under Security and Privacy Module updates. That commit added a Digital Signatures use-case section to source/secpriv-module.html explaining that create/update managed elements can invalidate prior digital signatures and linking to updates.html for ramifications of storage/retrieval variations; the same security batch also touched source/datatypes/signature.xml for signature wording.

Additional context:
Later source history moved the detailed signature guidance from the Security and Privacy Module page to the dedicated, active source/signatures.html page. Commit 9f942f4729bcb5a897c7ca47794151db8ffd3317 (FHIR-44617) removed the old inline secpriv-module signature section and linked the module to signatures.html; commit dcf53a8af6d730f886918f45af2510e990a986eb rewrote the Signatures page while preserving the create/update invalidation warning and updates.html cross-reference. FHIR-53855 was later Applied/Persuasive with Modification and specifically removed Digital and Electronic Signatures from the secpriv-module use-case list because signature material is covered elsewhere on the page/site. Current source/hierarchy.xml places signatures.html under Security and Privacy, current source/secpriv-module.html links to Signature Use, and current datatype narrative links Signature to signatures.html.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scope sources already convey the requested warning and updates.html cross-reference in the canonical Signatures page, and restoring the older inline secpriv-module use-case would duplicate active guidance and conflict with the later FHIR-53855 cleanup.

Recommendation:
Keep this no-change audit commit as-is. No core source follow-up is needed for FHIR-13271 unless the Security work group makes a new decision to duplicate signature guidance on the module page, which would need to consider FHIR-53855 and the current dedicated Signatures page.
