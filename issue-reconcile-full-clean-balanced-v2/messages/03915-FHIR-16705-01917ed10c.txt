FHIR-16705: Audit Clinical Reasoning dynamicValue language

Issue request:
FHIR-16705 was a Published, Persuasive with Modification CDS change request from the STU3 ballot. It noted that a Clinical Reasoning dynamicValue example showed only a description and was missing an expression language, suggesting defaulting to FHIRPath when no library is present and using the library language when exactly one library is present. The final resolution was narrower: update documentation based on the move to the new Expression datatype.

Initial application:
No source commit explicitly mentioning FHIR-16705 was found. The issue comments state that the concern had been applied by changing examples to use the Expression datatype. The relevant 2018 implementation history is commit 3dc81b908557be64248363dc4e5bbf5ed5213965, which removed direct dynamicValue description/language children from ActivityDefinition and PlanDefinition spreadsheet definitions, changed dynamicValue.expression to type Expression, and updated examples to nest description, language, and expression under an Expression element.

Additional context:
The current build-scope source has ActivityDefinition and PlanDefinition listed as active resources, assigns them to CDS, and includes the Clinical Reasoning Using Expressions page through hierarchy.xml. Current ActivityDefinition.dynamicValue.expression and PlanDefinition.action.dynamicValue.expression are both type Expression. The Using Expressions topic now explains the Expression pattern, names Language as one of the expression elements, gives dynamicValue examples with expression.language, and states how named expressions are resolved when the containing resource references one or multiple libraries. Related STU3 CDS ballot issues FHIR-16776 and FHIR-16780 were implemented in the same 2018 Expression-datatype commit, and FHIR-16711 has already been audited separately on the combined branch.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source no longer has the missing-language shape from the ballot example, and the applied Jira resolution did not approve adding implicit default-language semantics beyond the Expression datatype migration and current library-scoping guidance. Adding a new FHIRPath default rule now would be broader than the published resolution and could conflict with the current Expression.language model.

Recommendation:
Keep this audit commit as-is. No FHIR core source change is recommended for FHIR-16705 unless the CDS work group separately decides to introduce new default-language semantics for Expression, which would be a new substantive change rather than completion of this applied ballot issue.
