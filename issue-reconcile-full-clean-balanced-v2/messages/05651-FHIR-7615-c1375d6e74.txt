FHIR-7615: Audit Condition recordedDate usage note

Issue request:
FHIR-7615 was a Published Patient Care DSTU1 issue, resolved Not Persuasive with Modification. It objected that if Condition.dateAsserted was meant to capture the first asserted date, a sibling dateFirstAsserted should be added instead; the approved resolution was to add a usage note explaining that the element represented when this particular record was created, not when later severity, abatement, or other updates were made, and that the last record change could be found from resource metadata.

Initial application:
The issue was initially applied in git commit c6b154ca1b, which explicitly cited #7615 together with #7855 and #7859. That commit renamed Condition.dateAsserted to Condition.dateRecorded in the then-current Condition spreadsheet and examples, changed the short/definition toward documented/recorded semantics, and added the requested usage note saying the date was when the particular Condition record was created in the EHR rather than the most recent update, with last modification available from resource metadata. Later source migrations and resource evolution changed the current element/source representation to Condition.recordedDate in source/condition/structuredefinition-Condition.xml.

Additional context:
Condition is an active current-build resource in source/fhir.ini. The current StructureDefinition source says Condition.recordedDate is the date the condition was first recorded and defines it as when this particular Condition record was created in the system. Later Published Patient Care issues FHIR-27808, FHIR-34392, and FHIR-34394 refined the same element by explaining how recordedDate can serve as an onset boundary, when a sending system's value should be preserved, when a receipt timestamp may be used, and how recordedDate contrasts with recorder as the most recent author. FHIR-35113 later requested more recordedDate/assertedDate changes and was Resolved - No Change because the element had already been reviewed. No direct Zulip or Confluence evidence for FHIR-7615 was found.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The active Condition source already conveys the substance of FHIR-7615 after later decisions: recordedDate is about the first/created record timestamp, not subsequent clinical updates or most-recent authorship. Adding a new local sentence about metadata.lastUpdated would restate general Resource metadata behavior and would not change implementer understanding of the current specification.

Recommendation:
Keep this no-change audit commit as-is. If Patient Care wants a local Condition-specific pointer to meta.lastUpdated, that should be handled as a new clarification request rather than as unfinished work for this already-applied DSTU1 issue.
