FHIR-14394: Audit trigger cardinality application

Issue request:
FHIR-14394 was Published with a Persuasive with Modification decision for STU3. It asked for triggers to support more than one resource type by changing TriggerDefinition.dataRequirement, now TriggerDefinition.data, to 0..* and explaining that multiple data requirements are combined as "and"; changing EventDefinition.triggerDefinition, now EventDefinition.trigger, to 1..* and explaining that multiple triggers are combined as "or"; and adding a request for comment about statements still not expressible in core.

Initial application:
The issue was explicitly applied by git commit 478a62a85ba492b64db444f330043aed7d432843, "GF#14394 - event definition cardinality adjustments", which changed the TriggerDefinition datatype spreadsheet and the EventDefinition spreadsheet source. Later source refactors moved the EventDefinition element into source/eventdefinition/structuredefinition-EventDefinition.xml, but the cardinality and OR semantics remain present.

Additional context:
TriggerDefinition and EventDefinition are active current-build artifacts in source/fhir.ini. Later decisions touching the same area, including FHIR-21232, FHIR-53316, and FHIR-53414, changed SubscriptionTopic support, EventDefinition status, examples, and condition guidance without reversing the FHIR-14394 AND/OR model. Community searches found no Confluence references and no substantive Zulip discussion that conflicts with the source and Jira evidence. The request-for-comment portion of the 2018 resolution appears to have been a ballot-era solicitation rather than a current normative requirement to add stale RFC text to the R6 build.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current TriggerDefinition.data row is 0..* DataRequirement and says multiple data requirements are "and" / all must be true. The current EventDefinition.trigger element is 1..* and says multiple triggers are "or" / the event fires whenever any trigger condition is met.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-14394 unless a work group wants to file a new issue for event statements that remain outside the expressivity of TriggerDefinition/EventDefinition.
