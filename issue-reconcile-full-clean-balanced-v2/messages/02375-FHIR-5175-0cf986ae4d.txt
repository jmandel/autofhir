FHIR-5175: Audit entered-in-error lifecycle guidance

Issue request:
FHIR-5175 was a Published/Persuasive DSTU1 MnM change request asking for a consistent rationale for resources that can be nullified with an entered-in-error-like status versus resources where deletion or other handling is sufficient. Its accepted resolution pointed to FHIR-5171, called for domain-by-domain consideration, requested guidance explaining entered-in-error and the difference from deleting, and rejected a universal nullifier element.

Initial application:
No current git commit was found that names FHIR-5175 directly. The Jira comments say the work was applied under another task; FHIR-5171's Jira comment names SVN revision 4531, mirrored as git commit 07e5ff1f68a745c7d2a3c0a6acf98b8d26a92619, which created source/lifecycle.html with an Entered In Error Summary and generated table. The status-codes workbook also carries the canonical entered-in-error definition that the record was created in error and, for record integrity, often cannot be removed.

Additional context:
source/lifecycle.html is an active built narrative page through publish.ini, and the current page explains that entered-in-error means a resource was created accidentally and should be ignored, describes the relevant life-cycle families, and includes the entered-in-error summary table. source/conformance-rules.html explains why entered-in-error statuses are modifiers. Later Published issue FHIR-32165 and FHIR-I minutes clarified that erroneous-data handling is business-process-specific, that IGs should document additional actions such as redaction or notifications, and that no generic rule should be added.

AutoFHIR reconciliation:
Made no source change. The current specification already conveys the FHIR-5175 decision without adding a universal nullifier or redundant generic delete-vs-flag rule, and later accepted guidance argues against broadening the core text beyond the current lifecycle summary and per-resource table.

Recommendation:
Keep this audit commit as-is. Future work should be resource-specific or IG-specific if a particular resource lacks needed entered-in-error semantics; no additional core-wide lifecycle wording is indicated by the current issue family.
