FHIR-11349: Audit CarePlan doNotPerform cardinality

Issue request:
FHIR-11349 was a Published/Persuasive Patient Care change request for DSTU2 asking that CarePlan.activity.detail.prohibited not be required. The accepted resolution was to make the modifier 0..1 with a default meaning of false.

Initial application:
The historical source application is commit f39dde8e17, which changed CarePlan.activity.detail.prohibited from 1..1 to 0..1 and added Default Value = False in the then-authoritative CarePlan spreadsheet. Later workflow-alignment history renamed the element to doNotPerform while keeping the same negation semantics.

Additional context:
Current CarePlan is active in source/fhir.ini and the current StructureDefinition expresses the same approved behavior on CarePlan.activity.plannedActivityDetail.doNotPerform: min 0, max 1, a definition saying false or missing means the activity should be engaged in, and meaningWhenMissing carrying the false/missing interpretation. FHIR-12171 is the same element family and clarified the false wording. A leftover source/careplan/PFM.xml still contains the old prohibited element name, but it is not referenced by the active CarePlan example or pack lists and is not the current build-scope conformance source.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change because the current build-scope CarePlan definition already implements the cardinality and false/missing semantics requested by FHIR-11349.

Recommendation:
Keep this no-change audit as-is. If the unlisted PFM.xml file is ever brought back into build scope, it should be reviewed separately as stale historical example content, not as a required FHIR-11349 source fix.
