FHIR-35811: Audit MIME type clarification

Issue request:
FHIR-35811 was Published/Persuasive for the FHIR-core HTTP page. It asked to clarify that the old wording about UTF-8 for the mime type application/fhir was generic wording for FHIR MIME types, not a statement that application/fhir is itself a valid MIME type. The accepted resolution was to change the sentence to: "UTF-8 encoding SHALL be used for FHIR instances."

Initial application:
Commit 4ccbcfe84ecfa7e9fffc20efa054d198c72e4df5 applied FHIR-35811 in source/http.html by replacing the invalid standalone application/fhir wording with "UTF-8 encoding SHALL be used for FHIR instances." It kept the separate note that UTF-8 may be specified as a MIME type parameter, without attaching that note to the invalid application/fhir media type.

Additional context:
The current HTTP page is active spec narrative: source/documentation.html links to http.html, and source/http.html's Content Types and encodings section lists the formal resource MIME types as application/fhir+xml, application/fhir+json, and application/fhir+turtle before the UTF-8 sentence. The originating Zulip discussion confirms the problem was the apparent standalone application/fhir type and that the intended meaning was a generic reference to the valid FHIR variants. FHIR-13409 is relevant background for keeping charset parameters optional; it does not require additional FHIR-35811 source edits. Confluence searches found no FHIR-35811 minutes or conflicting later context.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source no longer says application/fhir is a valid MIME type, preserves the accepted "FHIR instances" wording, and keeps a separate optional MIME-parameter sentence that is not misleading in context.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed unless the work group separately decides to change the charset-parameter guidance.
