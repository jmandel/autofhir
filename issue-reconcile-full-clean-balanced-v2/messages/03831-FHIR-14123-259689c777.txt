FHIR-14123: Audit Attachment hash signature warning

Issue request:
FHIR-14123 was a Published/Persuasive FHIR-core datatypes change request raised for STU3. It asked that Attachment.hash clarify that changing the hash algorithm does not address malicious threats and that protection against malicious changes should use a digital signature, pointing readers to Provenance.signature.

Initial application:
The issue was applied in git-svn commit c4d708b33f435bffb8b22d81c7cd1db1579a5ce0, "GF#14123 - clarify hash is not a signature", which matches the Jira comment citing svn revision 13063. That commit extended source/datatypes/attachment.xml so Attachment.hash says the hash is not intended to support digital signatures and directs malicious-threat protection to Provenance.signature.

Additional context:
Attachment remains in active build scope: source/fhir.ini routes datatypes through the datatypes page and marks Attachment normative. The current Attachment source and the current datatypes narrative both still contain the warning and Provenance.signature link. Later source history reformatted or regenerated the spreadsheet but preserved the substantive FHIR-14123 wording. Searches of Zulip and Confluence found no issue-key or concept evidence that reverses or narrows the Jira decision; the only Zulip concept hit quoted the current Attachment hash text without conflict.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current specification already conveys the required rule: Attachment.hash is for detecting technical failures/content changes, is SHA-1/base64, is not a digital signature, and points to Provenance.signature for protection against malicious alteration. The remaining awkward wording is editorial rather than a semantic failure of the published issue.

Recommendation:
Keep this audit commit as-is. No FHIR-14123 follow-up is required in core unless a work group wants a separate editorial cleanup of the Attachment.hash grammar.
