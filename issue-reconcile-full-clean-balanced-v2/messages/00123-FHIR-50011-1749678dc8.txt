FHIR-50011: Correct terminology relatedArtifact constraint sources

Issue request:
FHIR-50011 was Applied/Persuasive for R6 and asked Vocabulary to apply the RelatedArtifact usage guidance from FHIR-50010 to CodeSystem, ConceptMap, NamingSystem, and ValueSet by prohibiting depends-on and composed-of relatedArtifact types and by constraining successor/predecessor targets to the same terminology resource kind.

Initial application:
The issue was initially applied in source commit 50b0f2cf34b6642c1e9ea57b827d69eb3647331d. That commit added the depends-on/composed-of invariants and successor/predecessor explanatory text to all four terminology StructureDefinitions. Per the Jira follow-up comment, it intentionally did not add resolve() constraints after PR review discussion. The implementation left the new CodeSystem, ConceptMap, and NamingSystem invariant source canonicals pointing at ValueSet.

Additional context:
FHIR-50010 is the broader Applied/Persuasive RelatedArtifact datatype and guidance issue that required work groups to decide relevant relationship types for each resource. The implementer Zulip discussion records the rationale for resource-specific RelatedArtifact restrictions, and the 2025-04-10 Vocabulary minutes approved the FHIR-50011 disposition 6-0-0. The four terminology StructureDefinition XML files are in active resource directories listed in source/fhir.ini, so their constraint metadata feeds the current build.

AutoFHIR reconciliation:
This commit preserves the applied FHIR-50011 behavior and the later decision not to add resolve() constraints. It corrects only the constraint source metadata for the three non-ValueSet resources so csd-8 points to CodeSystem, cmd-14 points to ConceptMap, and nsd-4 points to NamingSystem, matching the existing pattern used by neighboring constraints.

Recommendation:
Keep this commit as-is. It is a narrow metadata correction directly tied to the FHIR-50011 application; further changes to add executable successor/predecessor resolve() constraints should not be made without renewed work-group review because Jira records that they were deliberately omitted.
