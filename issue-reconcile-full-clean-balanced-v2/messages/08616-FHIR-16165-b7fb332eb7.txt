FHIR-16165: Audit FHIR version identification guidance

Issue request:
FHIR-16165 is a Published/Persuasive FHIR-I change request against FHIR-core BaseResource. It asked to add a fhirVersion data element to Resource so implementers could identify the FHIR version for resources exchanged as attachments or data objects outside the REST API. The accepted resolution did not add Resource.fhirVersion; it directed the specification to document the MIME-type fhirVersion parameter, the use of a version-specific profile in Resource.meta.profile, and resolvability of those version-specific profile URLs.

Initial application:
The Jira application note cites svn revision 13842. In the git mirror, commit 6c524e959315a07f484862bbcd627c2ce90a3057, "GF#16165 - clarify how versioning works", added source/versioning.html, expanded source/resource/resource-notes.xml so Meta.profile links to version-specific profile guidance, and updated source/versions.html versioning guidance. Current source also retains the MIME-type fhirVersion parameter on source/http.html and lists the R4 change in source/history.html.

Additional context:
The 2018 Zulip discussion and FHIR-I Cologne WGM minutes show the work group considered resource-specific version attributes, a Meta.fhirVersion-style element, MIME metadata, and Resource.meta.profile. The recorded decision favored metadata/context mechanisms rather than adding a new Resource element. Later issues FHIR-35779, FHIR-35780, and FHIR-41622 revisited the version-specific profile table and package-resolvability wording; each already has a separate combined-branch audit commit and none supersedes the FHIR-16165 mechanism.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Current build-scope source/versioning.html says there are three ways to determine the FHIR version: CapabilityStatement.fhirVersion, the fhirVersion MIME-type parameter, and a version-specific profile on the resource. source/http.html documents the MIME-type parameter, source/versions.html points readers to the same three methods, source/resource/resource-notes.xml says Meta.profile can indicate which FHIR versions a resource conforms to, and source/resource/structuredefinition-Resource.xml has only the established Resource children id, meta, implicitRules, and language rather than a Resource.fhirVersion element.

Recommendation:
Keep this no-change audit as-is. Future updates should be handled under a new or existing versioning-page tracker if FHIR-I wants to revise the version-specific profile URL table or add release-specific rows, but FHIR-16165 itself is already correctly reflected in current source.
