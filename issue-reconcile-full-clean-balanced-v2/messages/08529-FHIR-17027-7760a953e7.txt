FHIR-17027: Audit Binary FHIR content types

Issue request:
FHIR-17027 was a Published/Persuasive STU3 technical correction for the Binary REST note. It asked that the wording not imply that only application/fhir+xml and application/fhir+json are FHIR content types, because other FHIR content types exist.

Initial application:
The issue was applied by svn revision 14345, represented in git as b460ed645c6342e838cc9178950807b4cb0d06a1, which changed the Binary REST text to list application/fhir+xml and application/fhir+json followed by an explicit non-exhaustive "etc". Later the same day, the FHIR-13507/FHIR-16886 Binary REST rewrite in 4c0d34042c3e8742eda89fdb336da09c622aa009 recast the rule as a request made with a FHIR type in the Accept header, using application/fhir+xml and application/fhir+json only as examples. The later FHIR-37381 duplicate-bullet cleanup in e1ca41ce941ff6f9dc4c06c63da22483cc620720 removed the duplicate wording but preserved that current non-exhaustive bullet.

Additional context:
Binary is an active current-build resource in source/fhir.ini and is listed in the infrastructure normative package. The current Binary source says that a request with a FHIR type in the Accept header returns the Binary resource in the requested FHIR format, with XML and JSON shown as examples, and the adjacent _format bullet refers to the standard FHIR mime types. The HTTP page defines the broader current FHIR MIME-type context, including RDF/Turtle. Jira neighborhood checks found related Binary REST issues, but no later decision requiring this seed wording to enumerate every FHIR content type. Zulip and Confluence searches for FHIR-17027 found no directly relevant or conflicting community record.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current Binary narrative already conveys the seed decision: XML and JSON are examples of a broader class of FHIR types, not an exhaustive pair. Adding "etc" or enumerating other formats here would be redundant with the current HTTP content-type guidance and would not change implementer understanding.

Recommendation:
Keep this no-change audit commit as-is for FHIR-17027. If a future work group wants the Binary page to enumerate RDF/Turtle or other FHIR MIME types explicitly, treat that as a new broader editorial/content-type consistency issue rather than as an unapplied part of this STU3 Binary tracker.
