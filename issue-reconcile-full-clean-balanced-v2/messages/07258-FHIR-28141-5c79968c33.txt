FHIR-28141: Audit ElementDefinition markdown datatype resolution

Issue request:
FHIR-28141 is Published/Persuasive with Modification. The Jira description asked for ElementDefinition.constraint.requirements to render as rich text, the reporter immediately clarified that they meant constraint.human, and the recorded resolution named ElementDefinition.constraint.human, ElementDefinition.binding.description, and ElementDefinition.mapping.comment as string-to-markdown changes.

Initial application:
The Jira-tagged implementation commit a74d790b4480099fb9d8b68ad2df3bef4844d99b changed source/datatypes/elementdefinition.xml so ElementDefinition.constraint.requirements, ElementDefinition.binding.description, and ElementDefinition.mapping.comment are markdown. It intentionally did not change ElementDefinition.constraint.human, leaving that element as string.

Additional context:
FHIR-25392 had previously rejected changing ElementDefinition.constraint.human to markdown and recommended the rendering-markdown extension instead. FHIR-I minutes from 2022-08-29 record the explicit FHIR-25392/FHIR-28141 conflict and conclude that FHIR-28141 had a typo in the resolution and that both tickets were already applied correctly. The matching Zulip thread records the same interpretation: the FHIR-28141 text should say constraint.requirements rather than constraint.human.

AutoFHIR reconciliation:
No source change was made. The active ElementDefinition datatype source is in the current build, and the current rows already match the later clarified interpretation: constraint.requirements, binding.description, and mapping.comment are markdown, while constraint.human remains string.

Recommendation:
Keep this audit commit as-is. Do not change ElementDefinition.constraint.human to markdown unless FHIR-I reopens the prior no-core-change decision; use the rendering-markdown extension for marked-up constraint messages.
