FHIR-31964: Audit CanonicalResource interface paths

Issue request:
FHIR-31964 was Published / Persuasive with Modification for R5. It reported that generated ElementDefinition.path values for CanonicalResource fields on resources such as CapabilityStatement.copyright appeared as resource-local paths, e.g. CapabilityStatement.copyright rather than CanonicalResource.copyright, and requested clearer differentiation between CanonicalResource as an interface, DomainResource as an abstract class, and the rendered inheritance/interface indicators.

Initial application:
No git commit explicitly mentioning FHIR-31964 was found. The relevant source state already defines CanonicalResource as an active interface and DomainResource as an active abstract resource in fhir.ini, and CanonicalResource carries the structuredefinition-interface marker. CapabilityStatement is an active build resource that implements/redeclares CanonicalResource content; its copyright element remains CapabilityStatement.copyright, which is consistent with interface redeclaration rather than class inheritance.

Additional context:
The Jira comment explains the key interpretation: CanonicalResource is an interface, not a class, and not every canonical resource exposes every canonical element in the same way. The current UML/interface documentation says implementing classes redeclare interface attributes and associations and that same-named elements are redeclarations of the interface element, not independent elements. The related FHIR-37791 reconciliation, already present on the combined branch, further clarifies where interfaces may be referenced and how interface constraints propagate.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active source already conveys that CanonicalResource is an interface, DomainResource is abstract, and resource-specific paths such as CapabilityStatement.copyright are expected redeclarations of interface elements rather than erroneous inherited class paths.

Recommendation:
Keep this empty audit commit. If a future rendered build still fails to visually distinguish interfaces from abstract classes in a particular generated view, that should be handled as publisher/rendering follow-up; the current FHIR source does not need a semantic correction for FHIR-31964.
