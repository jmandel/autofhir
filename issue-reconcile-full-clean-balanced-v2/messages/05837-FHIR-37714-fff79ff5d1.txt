FHIR-37714: Audit complex search parameter guidance

Issue request:
FHIR-37714 was a Published FHIR-core Change Request raised against R4 and applied for R5. It reported that the search parameter registry lists parameters such as Patient.name, Person.name, Practitioner.name, RelatedPerson.name, address, and other complex-element parameters by search parameter type rather than by the underlying complex datatype fields. The accepted Persuasive with Modification resolution was to add Search page guidance that a string search parameter pointing at a complex or backbone element is interpreted as a search against one or more string-valued sub-elements selected by the implementation, that expressions may point directly to sub-elements when an explicit subset is intended, and that SearchParameter.processingMode should be other when narrative adds additional indexing considerations.

Initial application:
The issue was applied before R5 publication by ee10be816c, which added the requested string-search prose, Patient.name/HumanName example, and an xpathUsage/processingMode note to source/search.html. Commit 28782409d0 cleaned the R5 TODO and changed that note to SearchParameter.processingMode. Later search-page work kept and refined the same guidance: 6941dfafeb added a general Matching and Sub-Elements section, and a3766ac36c tagged the normative MAY/SHOULD sentences as conformance language.

Additional context:
The current source/search.html top-level Search page is the authoritative normative narrative linked from source/searchparameter-registry.html. It now contains both the general Matching and Sub-Elements rule and the string-specific section requested by FHIR-37714. Spot checks of the named registry examples show the core SearchParameter definitions still use type string with expressions such as Patient.name and descriptions that explain a server-defined match across HumanName string fields, which is consistent with the accepted clarification rather than a requirement to change the formal search parameter type. Confluence minutes record FHIR-I running out of time on 2022-07-25 and approving FHIR-37714 as Persuasive with Mod 13-0-0 on 2022-08-01. Zulip search found only a later sort-behavior thread that cites FHIR-37714 as related background, not a conflicting decision. A later SearchParameter derivation issue, FHIR-48481, is already represented on the combined branch and does not change the FHIR-37714 rule.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current built source already carries the accepted R5 clarification, including the complex/backbone string-search default, the explicit sub-element expression option, the Patient.name example, and the SearchParameter.processingMode guidance. Changing search parameter datatypes or rewriting the registry would go beyond the accepted resolution and would not better convey implementer expectations.

Recommendation:
Keep this audit commit as-is. No FHIR core follow-up is needed for FHIR-37714 unless a future work group decision reopens whether particular standard SearchParameter definitions should use processingMode=other for non-default indexing behavior.
