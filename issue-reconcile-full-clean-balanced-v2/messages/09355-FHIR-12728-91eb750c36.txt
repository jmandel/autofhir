FHIR-12728: Add missing workflow encounter search parameters

Issue request:
FHIR-12728 was Published/Persuasive for DSTU2 by FHIR-I and asked that all Event and Request pattern resources have an `encounter` search parameter, in addition to the historical `context` parameter, because implementers naturally search by encounter when the pattern context points to Encounter or EpisodeOfCare.

Initial application:
The request was applied in two historical git-svn commits: 0565e3795f added `encounter` as a standard search criterion to both the Event and Request pattern spreadsheets, and df6f87077f (svn build@11224, named in Jira) added a build-validator warning for Event/Request resources. Later FHIR-17901 work renamed the pattern element itself from `context` to `encounter`, and that related reconciliation is already on the combined branch.

Additional context:
Current source/fhir.ini keeps Event and Request as active logical patterns and keeps AdverseEvent, ClaimResponse, DetectedIssue, and GuidanceResponse as active resources. Current source search showed these active Event-family resources have Encounter-bearing `encounter` elements or Event.encounter mappings but lacked authored `encounter` SearchParameter resources. DocumentReference was intentionally not changed because later FHIR-29801 renamed its encounter search surface to `context` while broadening targets to Appointment and EpisodeOfCare, and FHIR-54170 later clarified that broadened context wording. The historical Java ResourceValidator source that contained the original build warning is no longer present in this checkout, so this reconciliation fixes the concrete current conformance surface rather than reviving retired tooling.

AutoFHIR reconciliation:
This commit adds resource-specific `encounter` SearchParameter entries for AdverseEvent, ClaimResponse, DetectedIssue, and GuidanceResponse, using the existing resource encounter elements as expressions. It does not add an AllergyIntolerance search parameter because that resource is not an Event/Request pattern resource in the checked workflow evidence, and it does not add DocumentReference-encounter because the later approved search code is `context`.

Recommendation:
Keep this source fix. If the work group wants a generalized future build-time warning for missing Event/Request encounter search parameters, handle that in the current publisher/tooling repository separately; the active core search-parameter sources inspected here now satisfy the issue's current-spec requirement.
