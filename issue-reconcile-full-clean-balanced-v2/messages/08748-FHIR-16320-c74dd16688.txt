The approved resolution was to check whether other documentation work exposed the correct explanation and to clarify only if it did not.

Additional context:

The old standalone backboneelement.html page was later folded into the current type framework. The combined branch already contains no-change audit commits for FHIR-17017 and FHIR-16877, so this seed should not duplicate those related decisions.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source/types.html BackboneElement section now explains that BackboneElement is for complex elements defined as part of a resource definition, distinguishes it from datatype elements, gives Patient.contact as an example, and notes that descendant BackboneElement types are declared implicitly as part of resource definitions. The generated-definition source in source/datatypes/backboneelement.xml is consistent, defining BackboneElement as elements inside a resource but not those in a datatype.

Recommendation:
Keep this audit commit as-is. No follow-up source change is needed for FHIR-16320 unless a future work group decision changes the BackboneElement/DataType boundary or the generated page loses the current explanatory text.
