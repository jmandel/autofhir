FHIR-47371: Audit SubscriptionTopic non-blocking processing

Issue request:
FHIR-47371 was Applied/Persuasive for R6 and asked whether SubscriptionTopic filter timing requires subscriptions, includes, or revincludes to be evaluated before server state changes complete. The accepted resolution was to add text clarifying that Subscription processing is independent of server processing/state changes, with lightweight processing such as a separate filtering/inclusion system allowed.

Initial application:
The issue appears to have been applied by source commit f486594368f07012d3a5af1b6f6958cb98856588, linked from the Jira comment as PR 3967. That commit added the current paragraph under the SubscriptionTopic "Filter Timing and Interactions" section stating that filter evaluation, content collection, and notification dispatch are independent of the request that changes system state, that create/update/delete commits need not block while subscriptions are evaluated, that asynchronous queues or background tasks are appropriate, and that temporary subscription-processing delays or failures should not roll back or affect the originating interaction.

Additional context:
SubscriptionTopic is an active current-build resource in source/fhir.ini, so source/subscriptiontopic/subscriptiontopic-notes.xml is build-scope resource narrative. FHIR-I minutes for 2025-03-31 approved the Subscriptions block vote including FHIR-47371 at 17-0-0, and the Zulip block-vote announcement found no separate contradictory discussion. The older FHIR-39028 timing clarification established the surrounding create/delete/update filter-timing section; FHIR-47371 adds the later non-blocking clarification without reversing those rules.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active SubscriptionTopic source already conveys the accepted resolution and addresses the concern that subscription filtering, inclusion collection, and notification dispatch could otherwise be read as blocking the originating server interaction.

Recommendation:
Keep this audit commit as-is. Revisit only if the work group wants to refine the exact consistency expectation for included resources; no current source correction is needed for FHIR-47371.
