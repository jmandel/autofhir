FHIR-31721: Audit cross-version extension guidance

Issue request:
FHIR-31721 was a Published FHIR-core change request, resolved Persuasive with Modification for R5, asking the versions page to clarify practical rules for cross-version/implied extensions: renamed or unavailable reference targets, complex datatype representation, choice datatypes, propagation of source extensions, cardinality handling, and creation of the referenced cross-version packages.

Initial application:
The issue was directly applied in core by commit 254ea0c87356baddf7f1da9c0a8fdbc91ca6a27f, which expanded source/versions.html with the requested guidance for alternate reference/canonical handling, _datatype use for unsupported choice datatypes, cardinality limitations, primitive mappings, and complex-extension examples. The R5 published versions page still contains that detailed text.

Additional context:
The current build later changed ownership of these details. Commit f45505e5b3aa0d87effb991938750e627b782d2d intentionally removed the long core guidance under the subject "R6 - pulling cross-version content that moves to guides" and replaced it with a concise core overview plus links to the individual cross-version definition packages. The active source/versions.html page remains in build scope through publish.ini, now points to the package matrix, and says further details are in the individual cross-version definition packages. The standard alternate-reference, alternate-canonical, and _datatype extensions now live in the FHIR Extension Pack, while published xver packages and their FAQ/lookup pages carry the package-specific guidance.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Reintroducing the detailed FHIR-31721 prose into core would duplicate guidance that was deliberately moved to xver guide/package artifacts and would risk future divergence. The current core page still gives the canonical URL pattern and links to the package family, so core is not misleading for the current build.

Recommendation:
Keep this audit commit as-is. If implementers find remaining gaps in package-specific rules or examples, handle that work in the cross-version package/source process (and, for standard extension definitions, the FHIR Extension Pack), not by restoring duplicate detailed guidance in core versions.html.
