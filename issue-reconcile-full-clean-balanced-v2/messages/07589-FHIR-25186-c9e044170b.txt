FHIR-25186: Audit QuestionnaireResponse attester extension

Issue request:
FHIR-25186 was Published / Not Persuasive with Modification for R5. It asked not to add a native QuestionnaireResponse.attester element, but to define a standard QuestionnaireResponse extension that captures attestation information mirroring Composition.attester structures, data types, cardinalities, and value sets, then expose it in SDC as optional.

Initial application:
The issue was applied in core by 53bb3c4c23, which added source/questionnaireresponse/structuredefinition-extension-questionnaireresponse-attester.xml and referenced it from the QuestionnaireResponse core implementation guide. The Jira comment also records 53bb3c4c23 as the core application.

Additional context:
Core commit dd468d4f17 later removed standard extension definitions from the R5 core source as part of the Extension Pack split. The current FHIR core checkout no longer has a questionnaireresponse-attester StructureDefinition source; a source search finds only the retained OID mapping. The active definition is now in the FHIR Extension Pack at input/definitions/QuestionnaireResponse/StructureDefinition-questionnaireresponse-attester.xml and in the Extension Pack CI build. Later related issues do not require a core edit: FHIR-55803 is a Resolved - No Change decision to keep Device as an allowed QuestionnaireResponse attester party because Questionnaire attestation rules are not identical to document attestation, while FHIR-55801 is still Triaged and unresolved for possible broader DocumentReference/generic attester work.

AutoFHIR reconciliation:
This is an empty external-repo audit commit. No FHIR core source was changed because the requested artifact has already been applied and then intentionally moved out of the core checkout; current maintenance belongs in HL7/fhir-extensions, not this core branch.

Recommendation:
Keep this audit commit as-is for core. Do not reintroduce the extension definition into core. Any future change to the QuestionnaireResponse attester extension, including a generic/broader context or alignment with later Composition attester modeling, should be handled through a final work-group decision and an HL7/fhir-extensions change.
