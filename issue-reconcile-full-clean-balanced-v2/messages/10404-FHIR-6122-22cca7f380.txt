FHIR-6122: Audit batch transaction support

Issue request:
FHIR-6122 was Published/Persuasive with Modification for DSTU1 and asked to support non-atomic transactions/batches in the RESTful API: add Bundle.type batch and batch-response, document that batch entries have no interdependencies, rename transaction/transactionResponse details to request/response, expose batch/transaction support in Conformance, and clean up operation/interaction wording.

Initial application:
The Jira comments cite svn revision 5798, which is git commit 5a81d5df0fb8db27e0b88b6077ccde5171ba8645. That commit changed source/http.html to introduce batch/transaction text, batch processing rules, batch-response, request/response terms, and operation/interaction cleanup. The current Bundle and CapabilityStatement source has since been refactored, but the same model remains.

Additional context:
FHIR-9681 later clarified the batch rule because the original server-validation SHALL was intentionally loose and hard to test. Its Published/Persuasive application narrowed interdependencies to entries causing server changes, changed per-change independence and validation obligations to SHOULD, and marked references to resources being created in a batch as non-conformant. Current combined-branch source/fhir.ini actively includes Bundle and CapabilityStatement, and current source/http.html, Bundle type terminology, Bundle request/response elements, and system RESTful interaction codes reflect the combined effect.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current combined branch already supports independent batch processing and distinct batch responses, while preserving the later FHIR-9681 clarification rather than reverting to FHIR-6122's original stricter validation wording.

Recommendation:
Keep this commit as-is. Reintroducing a stricter server SHALL reject/validate rule would conflict with FHIR-9681's later clarification; any further tightening should be handled as a new work-group decision.
