FHIR-13559: Audit search paging guidance

Issue request:
FHIR-13559 is a Published/Persuasive FHIR-core Search-page issue raised for STU3. It reported that paging was mentioned without explicitly identifying the Bundle links used for paging or explaining how those links work, and its recorded resolution was to make this point to the HTTP paging section.

Initial application:
The Jira comment says "svn 12837". In the Git history, that SVN revision is commit d799b4e939f192a781e79887a956e6cbee5bd0b8, "#13559 - note about paging support", which edited source/http.html. The commit made HTTP paging a SHOULD-supported search/history behavior when available, preserved the RFC 5005 Bundle-link paging model, and added the key guidance that paging links are opaque, server-understood URLs that clients must use rather than parse. The Search page also contains a current _count section that points readers to http.html#paging for the returned Bundle links.

Additional context:
Current source/search.html now also has an "Other Links - Paging" subsection that explicitly names common link relations: first, last, next, prev, and previous, with prev/previous described as interchangeable. Related Applied issue FHIR-42892 about previous versus prev has already been represented on the combined branch by commit 1ee6826f19686f42042534450f8004b70d77fe74, so this reconciliation must not publish a duplicate FHIR-42892 decision. Later Applied issue FHIR-51428 added paging best-practice guidance and a Search-page cross-link to the HTTP paging best-practices section, which is consistent with leaving the seed issue as already satisfied. A 2017 Zulip implementers thread asked the same practical question about how paging should be performed; responses pointed to http.html#paging and explained that clients cannot parse paging URLs and must use the server-supplied links.
