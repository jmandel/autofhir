FHIR-38940: Audit Bundle constraint FHIRPath consistency

Issue request:
FHIR-38940 was a Published/Persuasive FHIR-I change request raised against R4 and applied for R5. It asked that Bundle constraint FHIRPath use a consistent local element form, changing expressions that referred to Bundle.[element] or %resource.[element] to just [element] where that is the correct context.

Initial application:
The Jira comment points to HL7/fhir#2428. Commit 9d62b7791f99105778f23844e42d13f7ae60eec9 initially changed source/bundle/structuredefinition-Bundle.xml by replacing %resource.type with type in the then-current bdl-3/bdl-4 constraints and replacing Bundle.issues with issues in bdl-16/bdl-17. The PR was merged by 0bf45b6fab56d2e4958f3852b7fc0f529472a2c6. A follow-up commit, 1b2d9f9e248c7fc83375414cd62617e2c3500c50, reverted the bdl-3/bdl-4 %resource.type changes because those expressions evaluated inside entry.all(), where the unqualified type path was not in context.

Additional context:
FHIR-38942 later split the old bdl-3/bdl-4 rules into bdl-3a through bdl-3d. In the current active Bundle StructureDefinition, those constraints and the surrounding Bundle constraints use unqualified root element names such as type, entry, identifier, timestamp, link, and issues. source/fhir.ini actively registers Bundle, so source/bundle/structuredefinition-Bundle.xml is in build scope. A search of the Bundle directory found remaining Bundle.* expressions only in Bundle search-parameter definitions, not in Bundle constraints, so they are outside the requested constraint cleanup.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current active Bundle constraints already reflect the FHIR-38940 consistency goal while preserving the later technical correction that unqualified paths must only be used in the correct FHIRPath context.

Recommendation:
Keep this audit commit as-is. No FHIR core source follow-up is needed for FHIR-38940; do not rewrite Bundle search-parameter expressions as part of this issue because they are not the constraint expressions covered by the Jira decision.
