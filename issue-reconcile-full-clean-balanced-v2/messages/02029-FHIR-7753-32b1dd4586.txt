FHIR-7753: Audit DocumentReference securityLabel rename

Issue request:
FHIR-7753 was Published with a Persuasive with Modification resolution for the DSTU1 DocumentReference confidentiality element. The final disposition was to rename DocumentReference.confidentiality to DocumentReference.securityLabel, keep it consistent with the SecurityLabels binding, and clarify in the definition how those labels differ from DocumentReference.meta.security.

Initial application:
The Jira comment records svn revision 6201, and git commit b2a4538039611f2ed8fe57b8b440027edc28abe6 is that converted svn change. It renamed the DocumentReference element and examples from confidentiality to securityLabel, renamed the binding from HCS to SecurityLabels, removed the local valueset-security-labels.xml source, and added initial definition text distinguishing DocumentReference.meta.security from the document-level security labels.

Additional context:
DocumentReference remains active in the current build through source/fhir.ini. The current StructureDefinition source has only DocumentReference.securityLabel, no remaining DocumentReference.confidentiality element, and the definition now explains that meta.security labels the data elements in the DocumentReference while securityLabel labels the referenced document. Later FHIR-32581 expanded that explanation for R5, FHIR-39687 rejected removing securityLabel because the distinction had been clarified, and FHIR-32586 changed the binding strength to example, so the current example binding is intentional rather than an un-applied part of FHIR-7753.

AutoFHIR reconciliation:
This is an empty audit commit. No source change is needed because the active current source already carries the renamed element and the requested meta.security distinction, with later related decisions preserving and clarifying that interpretation.

Recommendation:
Keep this audit commit as-is. Reopening the original HCS wording or renaming would conflict with the Published disposition and later OO decisions; any future work should be handled through a new tracker if the field's usage guidance needs additional clarification.
