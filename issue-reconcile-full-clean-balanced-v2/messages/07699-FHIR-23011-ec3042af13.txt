FHIR-23011: Audit canonical version hash guidance

Issue request:
FHIR-23011 was a Published/Persuasive FHIR-I change request asking that canonical reference URL parsing be made unambiguous when a canonical resource version contains '#'. The accepted resolution for R5 was to add guidance that conformance/canonical resource versions SHOULD NOT contain '#', that an unescaped hash is presumed to start a fragment id, and that embedded hashes in versions create parsing failure.

Initial application:
The issue was previously applied by git commit 6052da613c ("FHIR-23011 Parsing of canonical reference urls is ambiguous"), which added a shared Business Version note to source/resource/resource-notes.xml and appended '#'-avoidance comments to canonical-resource version elements. Current source still carries that guidance, including the CanonicalResource.version comment linking to resource.html#bv-format.

Additional context:
The linked Zulip discussion confirms the original ambiguity: the example canonical http://fhir.acme.com/Questionnaire/example|1.0#vs1 is parsed as URL/version/fragment, so http://fhir.acme.com/Questionnaire/example|2019#1 would be ambiguous unless the version hash is avoided or escaped. A later related Requirements issue, FHIR-47736, concerned another use of '#' with canonical URLs but resolved by changing Requirements statement references rather than revising the general FHIR-23011 guidance. No Confluence reference for FHIR-23011 was found.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scope source already states that business versions in canonical resources SHOULD NOT contain '#', explains that '#' has special URL meaning, requires escaping if it is used in a version inside a URL, and carries the linked warning on CanonicalResource.version and derived canonical resource version comments.

Recommendation:
Keep this audit commit as-is. Do not add duplicate text to references.html unless the work group later decides it wants a separate parser algorithm statement there; the current source already conveys the implementer rule needed to avoid the ambiguity raised by FHIR-23011.
