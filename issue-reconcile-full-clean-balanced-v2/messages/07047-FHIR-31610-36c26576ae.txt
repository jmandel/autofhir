FHIR-31610: Audit conditional PATCH wording

Issue request:
FHIR-31610 was a Published/Persuasive FHIR Infrastructure technical correction for the RESTful API HTTP page. It reported that the PATCH paragraph incorrectly described the If-Match/version-aware resource contention process as "conditional PATCH" and requested wording that points to the same Concurrency Management process defined for UPDATE instead.

Initial application:
The issue appears to have been applied before this reconciliation by commit 639dbcd2848776be444488fe66b23438c581256d, which explicitly lists FHIR-31610 and changed source/http.html from "servers SHALL support conditional PATCH" for the PATCH paragraph to language requiring the same Concurrency Management process for UPDATE. No prior Issue-Reconcile-Key commit for FHIR-31610 was present on the combined branch.

Additional context:
The HTTP page is in the active build scope through publish.ini's [pages] entry for http.html. Later edits kept the same semantic split: the resource contention section still carries the versionaware anchor and explains ETag/If-Match optimistic locking, while the PATCH paragraph now says servers that support PATCH SHALL support Resource Contention on the PATCH interaction. The separate Conditional patch section remains search-based and was later clarified by FHIR-49646 to include the PATCH [base]/[type]?[search parameters] URL. FHIR-17256 and FHIR-34278 are related same-paragraph/history decisions that support the current distinction and scope.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source no longer calls version-aware PATCH or If-Match support "conditional PATCH", and the actual conditional patch interaction is separately defined as resolving a logical id through search.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-31610 unless a future work group decision changes the resource contention or conditional patch semantics.
