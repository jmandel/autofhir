FHIR-2856: Audit ElementDefinition type disjunction representation

Issue request:
FHIR-2856 was a Published/Persuasive DSTU1 FHIR-core StructureDefinition change request asking whether old Profile.structure.element.definition.type examples that encoded disjunctions as Resource(Patient|Group|Device|Location) were equivalent to repeated type entries, and expecting the profile type representation to use repeats for disjunctions.

Initial application:
No current git commit explicitly mentions FHIR-2856. The Jira comments record that the ProfileGenerator and validators were adjusted in 2014 and that the issue was fixed before being marked applied. Git history in the same window shows untagged Profile/profile-generation work, including the snapshot/profile display changes and the Resource()/ResourceReference-to-Reference rename that preserved the then-current guidance that each allowed target resource had a separate type/code pair.

Additional context:
The current build no longer uses the DSTU1 Profile.structure.element.definition.type model. The active ElementDefinition datatype is in build scope through source/fhir.ini, has ElementDefinition.type as 0..*, and separately models profile and targetProfile as repeatable canonical constraints with "one must apply" semantics. Checked-in generated StructureDefinition XML uses repeated type entries for distinct data type choices and repeated targetProfile entries for Reference target choices; compact Resource(A|B) syntax is absent from current source and compact Reference(A|B) syntax is absent from generated StructureDefinition XML.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current specification already conveys the corrected disjunction model through ElementDefinition.type, ElementDefinition.type.profile, ElementDefinition.type.targetProfile, and generated StructureDefinition source examples.

Recommendation:
Keep this audit commit as-is. No follow-up source edit is recommended in core unless a future work group decision changes how authoring-spreadsheet shorthand should be represented; the built conformance source already avoids the ambiguous old Profile.structure encoding.
