FHIR-22628: Audit websocket subscription payload support

Issue request:
FHIR-22628 was a Published/Persuasive FHIR-core Subscription issue asking to align websocket subscriptions with REST hooks by allowing notification payloads over the socket instead of documenting only the websocket PING mechanism. The resolution agreed to add that support while considering the broader R5 Subscription overhaul.

Initial application:
The Jira application comment names commits 03a9bc2af6584c50cfe2a38a0545649ee907bdc0 and 70355f13b223012ee7f9f70eb5a999219cfe7fb1. Commit 03a9bc2af658 changed the websocket notes so websocket event notifications are subscription-notification Bundles whose format is determined by Subscription.contentType and Subscription.content. Commit 70355f13b223 expanded the websocket workflow and stated that websocket notifications SHALL use the format specified by the Subscription contentType and content fields. Both commits are contained in the v5.0.0 tag.

Additional context:
Subscription remains an active current-build resource in source/fhir.ini. The current Subscription source defines channelType, endpoint, contentType, and content as general Subscription configuration; the introduction lists websocket as a core channel and says Subscription.content can request full resource content, id-only content, or an empty notification body. Later R6 cleanup commit e07a4ebf3485b02e47e981f2d2f1488e9d2f1cac intentionally moved detailed websocket content to external sources, and the current core text points to the FHIR Subscriptions Backport IG for current websocket details. That IG says websocket notifications use the Subscription channel payload and conform to the configured payload-content level. FHIR-21281 independently resolved a websocket ping/logical-id request as already supported by payload.content=id-only across all delivery mechanisms.

AutoFHIR reconciliation:
This audit commit makes no source change. The current source no longer contains the old PING-only websocket limitation, and the combination of current core Subscription payload elements, core websocket channel recognition, and the external websocket channel details preserves the accepted FHIR-22628 behavior without adding redundant core prose.

Recommendation:
Keep this no-change audit. Do not reintroduce detailed websocket protocol wording into core unless FHIR-I decides to move those mechanics back from the external Subscription guidance; the current core source is already sufficient to show websocket subscriptions can carry configured payloads.
