FHIR-16966: Audit markdown/string guidance

Issue request:
FHIR-16966 was a Published/Persuasive with Modification MnM change request for the FHIR-core datatypes page. It asked for consistent use of string, markdown, and xhtml; the final decision was to use string unless there is a markdown use case, limit xhtml to Narrative, and document that string-to-markdown changes are non-breaking for non-choice elements and that adding markdown as an allowed choice is non-breaking.

Initial application:
The Jira comment records svn revision 14160. The corresponding git-svn commit a5c90c3db3 applied a datatype documentation batch that explicitly named GF#16966, updated source/datatypes.html to say markdown is a FHIR string subject to string rules and to document string-to-markdown compatibility, and updated source/versions.html to carve out string-to-markdown as an allowed datatype compatibility change.

Additional context:
The current active datatype source still carries the decision, refined by later final issues: FHIR-38714 corrected markdown's no-inline-HTML processing rules, FHIR-40555 clarified that string-to-markdown is non-breaking for single-type elements but breaking for existing choice wire names, FHIR-51051 generalized the compatibility rule while retaining string-to-markdown as an example, and the already-published FHIR-20853 reconciliation clarified that markdown cannot substitute for string unless explicitly allowed. source/fhir.ini maps default datatype pages to datatypes.html and maps xhtml to the Narrative page; current source has no StructureDefinition type code of xhtml outside Narrative. MnM minutes for 2018-07-10 also list FHIR-16966 as Persuasive with Mod, matching Jira.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already conveys the durable implementer-facing rule: markdown is a constrained string-like datatype, safe string-to-markdown evolution is documented in both datatype notes and compatibility policy, choice-element wire-name caveats are present, and xhtml remains presented through Narrative rather than as a generally substitutable datatype. Adding more prose about the internal authoring guideline would be redundant and could drift from the later refined wording.

Recommendation:
Keep this empty audit commit as-is. No FHIR-core follow-up is needed for FHIR-16966 unless the work group wants a separate contributor-facing authoring policy for when new elements should choose markdown instead of string.
