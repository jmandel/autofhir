FHIR-12700: Audit CodeSystem validate-code example

Issue request:
FHIR-12700 was a Published/Persuasive vocab change request asking for an example that validates a code directly against a known code system without specifying a value set. The final resolution changed the requested application from a ValueSet example to adding the operation to the CodeSystem resource for STU4.

Initial application:
The issue was applied by svn revision 12757, imported as git commit aa22ace2ba333228a87b6fcbbf0c4f8db71de7ad, which added CodeSystem $validate-code request/response example files and operation source content. Later CodeSystem $validate-code commits corrected example wording and JSON shape, but the operation and known-code-system example remained present.

Additional context:
The current build includes CodeSystem and ValueSet as active resources in source/fhir.ini. The CodeSystem OperationDefinition is active through the CodeSystem operations list, terminology module/service pages, and terminology server CapabilityStatement. Zulip discussion in January and February 2017 shows the WG rationale: validating code-system membership was distinct from validating value-set membership, and the voted FHIR-12700 outcome was to add $validate-code to CodeSystem. A September 2017 terminology thread confirmed this was scheduled for STU4. Later related issues fixed wording and example defects rather than reversing the CodeSystem operation decision.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Current source already has OperationDefinition/CodeSystem-validate-code with example extensions pointing to $validate-code-request.txt and $validate-code-response.txt, and the request example begins with instance-level validation against a known CodeSystem: GET [base]/CodeSystem/loinc/$validate-code?code=1963-8&display=test.

Recommendation:
Keep this no-change audit. Do not add a parallel ValueSet example for this historical issue because the accepted resolution intentionally moved the use case to CodeSystem; any future parameter-table or terminology-service refinements should be handled through their own current Jira decisions.
