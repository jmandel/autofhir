FHIR-44748: Audit Permission logic outside core

Issue request:
FHIR-44748 was an Applied/Persuasive Security issue for R6 asking to clarify Permission rule processing: repeated Permission.rule.data and Permission.rule.activity instances are OR alternatives, elements and repetitions within each data/activity repetition are AND conditions, Permission.rule.data.period should be 0..1 because multiple periods cannot express a distinct AND relationship, and examples should be placed into element comments.

Initial application:
The issue was applied while Permission was an active core resource. Jira's application comment points to merge commit 2268c17c01881bb6256b9c2a61c98afd75396e98 / HL7/fhir#3054, which added the Rules Processing Logic narrative, added StructureDefinition comments for Permission.rule, Permission.rule.data, Permission.rule.activity, and Permission.rule.limit, and changed Permission.rule.data.period from 0..* to 0..1.

Additional context:
Permission is no longer in the current core build. Commit 0e2a8a7f839d5e1a43787523daccf07d958362f3 removed source/permission and the active Permission entries from source/fhir.ini, while current Security and history pages link Permission to the HL7 Data Access Policies IG. Security WG minutes and the FMG Zulip thread record the later decision to keep Permission out of R6 core as a non-core/additional resource so it can evolve. HL7/data-access-policies PR #57 moved the Permission source into that IG, and current Data Access Policies source still contains the FHIR-44748 AND/OR comments and the 0..1 data.period cardinality.

AutoFHIR reconciliation:
This empty commit intentionally makes no core source change. Reintroducing or editing source/permission in core would conflict with the later approved move out of core; the authoritative current Permission source is now in HL7/data-access-policies and already preserves the FHIR-44748 clarification.

Recommendation:
Keep this external-repo audit as-is for core. Future Permission rule-logic changes should be made in HL7/data-access-policies unless a later final work group decision moves Permission back into the active core build.
