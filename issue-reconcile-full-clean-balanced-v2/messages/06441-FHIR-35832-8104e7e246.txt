Issue request:
FHIR-35832 was a Published/Persuasive with Modification FHIR-I change request asking for guidance on how resource.category should be used for methodology, workflow, and implementation. The accepted resolution defined a 0..* unbound CodeableConcept category element for the Request, Event, and Definition workflow patterns with short/definition/comment guidance about filtering, access control, system behavior, automatic or manual categorization, multi-axis categorization, and avoiding strong overall bindings; it also asked for Definition guidance distinguishing category from usageContext and jurisdiction.

Initial application:
The issue was applied in git commit 193d552d630fe22578c31b120f6db85fefd90a6d, which updated the request, event, and definition workflow pattern spreadsheets and explicitly named FHIR-35832. The current source still contains the requested Request.category and Event.category rows and comments in active logical-pattern spreadsheets.

A later Published/Persuasive FHIR-I issue, FHIR-40406, aligned the Definition pattern documentation with CanonicalResource. Its application commit 1e7ed5c7a6146f8bd69ebfb2169cd9c687d9e34d removed Definition.category and its FHIR-35832 text while retaining/aligning Definition useContext and jurisdiction semantics with CanonicalResource. The active build configuration includes request, event, definition, canonicalresource, and metadataresource inputs, so these source checks are in current build scope. FHIR-I minutes confirm the original FHIR-35832 persuasive decision and the later FHIR-40406 persuasive alignment decision. Zulip and broader Confluence searches found no conflicting community discussion.
