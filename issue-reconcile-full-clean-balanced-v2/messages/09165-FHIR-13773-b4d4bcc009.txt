FHIR-13773: Audit capability statement kind metadata wording

Issue request:
FHIR-13773 was a Published FHIR-I change request for STU3, resolved Persuasive, asking that the CapabilityStatementKind value set's instance code definition remove the deprecated HTTP OPTIONS reference because STU3's capabilities interaction used /metadata instead.

Initial application:
The change appears to have been applied before this reconciliation. Jira records Grahame Grieve's comment "svn revision 12816", and commit ec09ca8c8dd94301b64e64a8f86cd2b9042fccd6, "#13773 - fix typo", changed the CapabilityStatement spreadsheet definition from "returned by OPTIONS" to "returned by /metadata" on 2017-12-18.

Additional context:
The current source no longer uses the old spreadsheet as the authoritative terminology input. A 2021 source refactor created source/capabilitystatement/codesystem-capability-statement-kind.xml and source/capabilitystatement/valueset-capability-statement-kind.xml with the /metadata wording preserved. CapabilityStatement is actively listed as a build resource in source/fhir.ini, and CapabilityStatement.kind has a required binding to ValueSet/capability-statement-kind. The same-change-family issue FHIR-13192 is already represented on the combined branch and is not re-decided here. Current source/http.html describes the capabilities interaction as GET [base]/metadata; its remaining OPTIONS mention is only a generic note that unspecified HTTP capabilities cannot be expected to be consistent beyond HTTP itself.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The active CodeSystem definition for the instance code already says it is returned by /metadata, the ValueSet includes that CodeSystem, and current source grep found no remaining "returned by OPTIONS" stale wording to remove.

Recommendation:
Keep this no-change audit commit. No FHIR core source follow-up is needed for FHIR-13773 unless FHIR-I later wants a purely editorial refinement of the existing /metadata phrase.
