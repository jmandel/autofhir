FHIR-16153: Audit ServiceRequest quantity element

Issue request:
FHIR-16153 was Published with a Persuasive resolution for FHIR-core ServiceRequest. It requested structured service quantity/amount support for LTSS service plans, with a 0..1 choice able to carry Quantity, Ratio, or Range and with quantity kept distinct from service schedule/timing details.

Initial application:
The issue appears to have been applied by commit b1dc88787aabb8826e7ca5b5661a308df6f57bf0, whose message references GF#15692 and GF#16153. That commit added the old ServiceRequest spreadsheet row as ServiceRequest.quantity[x], cardinality 0..1, type Quantity|Ratio|Range, short "Service amount", and the requested amount-of-service definition. Later source refactors preserved that row in the current StructureDefinition XML.

Additional context:
Zulip and OO Confluence minutes show the work group discussed the real-world LTSS need, the difference between authorized quantity and detailed timing, and then approved GF#16153 in a 2018-07-31 OO block vote. FHIR-20510 later clarified ServiceRequest.quantity[x] by moving type examples from the definition into a comment and adding a ratio example; that later same-change-family issue is already represented on the combined branch by an AutoFHIR no-change audit commit.

AutoFHIR reconciliation:
No source files were changed. ServiceRequest is active in source/fhir.ini, and the authoritative current source already has ServiceRequest.quantity[x] as a 0..1 Quantity|Ratio|Range choice with the accepted "Service amount" semantics. Renaming it to amount[x] would conflict with the original applied source history and later accepted references to ServiceRequest.quantity[x].

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-16153; any future generated diagram refresh or FHIR-20510 example wording follow-up should be handled under that later issue family, not by changing the original quantity element decision.
