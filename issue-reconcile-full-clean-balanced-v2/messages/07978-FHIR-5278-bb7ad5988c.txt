FHIR-5278: Audit DiagnosticReport document clarification

Issue request:
FHIR-5278 was a Published/Persuasive OO DSTU1 ballot comment asking what distinguishes a DiagnosticReport resource from a FHIR document bundle that represents a diagnostic report. The disposition agreed that the term "report" was confusing and should clarify that a diagnostic report can be conveyed in documents, REST, or messages, but a document conveyance would still include the DiagnosticReport resource as a section/resource within that document.

Initial application:
The current active DiagnosticReport source already contains the requested clarification. A February 2015 git-svn commit, d6259fa8e3, added the core sentence that a diagnostic report can be conveyed as a Document, RESTful API, or Messaging framework and that each includes the DiagnosticReport resource itself; a September 2015 QA commit, 3a53283fae, corrected the grammar of that sentence. Neither commit explicitly mentions FHIR-5278, but the text matches the FHIR-5278 disposition.

Additional context:
DiagnosticReport is an active resource in source/fhir.ini. Later DiagnosticReport/Composition work in FHIR-29258 added DiagnosticReport.composition for structured report organization, reinforcing that DiagnosticReport carries the report's diagnostic data while Composition/document structures can organize or convey it. FHIR-54513 is a later R6 documents-page clarification request mentioning DiagnosticReport, but it is only Resolved - change required and belongs to the documents page rather than the DiagnosticReport page audited for this published DSTU1 issue.

AutoFHIR reconciliation:
This empty audit commit makes no source change because source/diagnosticreport/diagnosticreport-introduction.xml already tells implementers that the report can be conveyed as a FHIR Document, RESTful API, or Messaging framework, and that the DiagnosticReport resource itself is included within those conveyances. Nearby Boundary and Relationships text also distinguishes DiagnosticReport from Observation, Composition, and DocumentReference, so adding more prose for this old ballot issue would be redundant.

Recommendation:
Keep this audit commit as-is for FHIR-5278. Treat any future documents-page mention of DiagnosticReport as separate work under the later documents-page tracker rather than as a missing application of this DiagnosticReport ballot comment.
