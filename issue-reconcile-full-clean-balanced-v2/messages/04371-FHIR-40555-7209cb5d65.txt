FHIR-40555: Audit string-to-markdown guidance

Issue request:
FHIR-40555 was a Published/Persuasive FHIR-core datatype clarification for R5. It asked to change the markdown datatype note so converting an element from string to markdown is recognized as breaking when the element is a choice datatype because the wire-format element name changes, and to add caution about how existing string values may be interpreted when treated as markdown.

Initial application:
The issue appears to have been applied before this reconciliation by Lloyd McKenzie's Jira-referenced master commit e161279945db540d091fb3ab145294a235d3e60f on 2023-03-20. That commit edited source/datatypes.html, replacing the older blanket non-breaking statement with the current single-type versus multi-type/choice distinction and adding the safe-rendering/escaping caution.

Additional context:
Earlier final issue FHIR-16966 introduced the original string-to-markdown compatibility guidance, while FHIR-20853 clarified that datatype specialization does not allow substituting markdown where only string is declared. The Zulip Orders and Observation discussion that led to FHIR-40555 shows the concrete concern: replacing Observation.valueString with valueMarkdown changes the wire name and existing strings can render differently as markdown. Later Applied issue FHIR-51051 generalized source/versions.html from the special string-to-markdown exception to same-domain type changes while retaining string-to-markdown as an example, so the broader versioning page is later context rather than a stale contradiction to the datatype-page choice-element caveat.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current active source/datatypes.html already says string-to-markdown is non-breaking for single-type elements, breaking for multi-type/choice elements because the type name is reflected in the element name, adding markdown as an additional choice is non-breaking, and the lack of escaping on existing string data should be considered before rendering as markdown. The immediately following warning and implementation note explain the escaping risk and mitigation.

Recommendation:
Keep this audit commit as-is. No FHIR-core source follow-up is needed for FHIR-40555; any future changes to the broader Version Management Policy should be handled under a separate compatibility-page decision rather than by re-opening this applied datatype clarification.
