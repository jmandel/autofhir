FHIR-10711: Audit Consent purpose clarity

Issue request:
FHIR-10711 was Published/Persuasive with Modification for FHIR-core Consent. It asked whether DSTU2 Consent.except.purpose represented user access context, an obligation to attach a purpose-of-use tag, or a data tag, and suggested organizing exception elements into user-context, data-qualifier, and action groups. The final Jira resolution was "Solved by 11055."

Initial application:
No source commit was found that names FHIR-10711 directly. The linked resolution issue, FHIR-11055, was explicitly applied by historical commit 0f594b3938a50781639ecd7fa5930288595d9bfe, "Definition and comment changes for CR 11055 and CR 11056." That commit replaced the old Consent purpose comment with the approved purpose-of-use conflict sentence and appended the same sentence to the adjacent securityLabel comment. Later source refactors carried the guidance into the current StructureDefinition source as Consent.provision.purpose and Consent.provision.securityLabel.

Additional context:
Consent is an active current-build resource in source/fhir.ini, and source/consent/structuredefinition-Consent.xml is the authoritative current StructureDefinition input. The old DSTU2 Consent.except family is now represented by Consent.provision, and no current Consent.except element remains in the Consent source. FHIR-11055 already has a no-change audit commit on the combined branch, FHIR-11056 already audits the same historical commit's securityLabel definition change, and later FHIR-36354 refined hierarchical security-label wording while preserving the FHIR-11055 purpose-of-use sentence. A later Zulip thread discussed PurposeOfUse value-set semantics for Consent.provision.purpose but did not contradict the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already distinguishes Consent.provision.purpose as the user's access/request context and Consent.provision.securityLabel as data labels, with the approved shared comment that data purpose-of-use tags and access-request purpose-of-use shall not conflict. Adding new grouping prose would duplicate existing guidance and is not required by the final FHIR-10711/FHIR-11055 disposition.

Recommendation:
Keep this empty audit commit as-is. No further core FHIR source work is needed for FHIR-10711 unless CBCC later makes a new decision to restructure Consent provisions or change the purpose/securityLabel interaction.
