FHIR-17776: Audit batch entry failure wording

Issue request:
FHIR-17776 was a Published/Persuasive STU3 FHIR-I change request for the RESTful API Batch Processing Rules. It objected that the text said a non-200 response meant the batch itself failed and none of the operations succeeded, and the accepted resolution was to state that a response code on an entry indicates whether processing that entry's request failed.

Initial application:
The Jira comment records GH#c78b3c2ffa. Commit c78b3c2ffa8f233d54df948e98c11dcebb0d5f3d updated source/http.html by replacing the whole-batch-failed sentence with per-entry wording: a response code on an entry other than 2xx indicates that processing the request in the entry failed.

Additional context:
source/http.html is the active RESTful API page in the current build via source/hierarchy.xml. The current Batch Processing Rules still say the overall batch HTTP response is 200 OK when the batch was processed correctly, regardless of individual entry outcomes, and direct readers to the returned Bundle entry status for interaction-specific results. Later source history only normalized HTTP status-code markup/terminology and changed "operations" to "interactions"; it did not restore the erroneous whole-batch failure rule. The current 2xx wording is also consistent with nearby RESTful API success codes such as 201 Created, 202 Accepted, and 204 No Content.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active source already conveys the accepted FHIR-17776 rule, and changing the sentence to the literal Jira-resolution phrase "other than 200" would incorrectly classify valid non-200 2xx entry statuses as failures.

Recommendation:
Keep this audit commit as-is. No further core source work is needed for FHIR-17776 unless the work group later wants to reopen the separate policy question of exactly which entry status classes count as successful.
