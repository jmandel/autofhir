FHIR-32455: Remove stale AuditEvent altId from model definition

Issue request:
FHIR-32455 was a Published Security WG change request for R5 asking why AuditEvent.agent.altId was named altId when agent.who already represented the user identity. The approved Persuasive with Modification resolution removed the altId element and preserved the DICOM AlternativeUserID concept as an AuditEvent agent extension with an Identifier value.

Initial application:
The issue was explicitly applied by git commit 11dbeb346100ba0d9089f63b88f99bd28348ad84, which removed AuditEvent.agent.altId from source/auditevent/structuredefinition-AuditEvent.xml and added an auditevent-AlternativeUserID extension definition. A later extension migration commit removed the core extension definitions from the FHIR checkout, and the current Extension Pack now contains the auditevent-AlternativeUserID definition. The active current FHIR model-definition Library content still retained AuditEvent.Agent.altId, so the original application missed this parallel source artifact.

Additional context:
source/fhir.ini marks AuditEvent and Library active/approved, and source/library/list-Library-examples.xml lists the FHIR Model Definition Library as a built example. Current AuditEvent source no longer has an altId element; agent.who carries the userId alias and DICOM UserName/UserId mapping. Current core AuditEvent examples reference the external auditevent-AlternativeUserID extension, which is present in the Extension Pack. The separate QUICK model-definition example is a legacy QUICK 1.0 model, not the current FHIR model definition, so it was not changed.

AutoFHIR reconciliation:
Removed the stale AuditEvent.Agent altId element from source/library/library-fhir-model-definition-content.xml and refreshed the embedded base64 attachment in source/library/library-fhir-model-definition.xml so the Library resource and linked readable content stay identical.

Recommendation:
Keep this commit as-is for FHIR core. If the WG wants to revisit whether the moved Extension Pack definition should be renamed to alternativeIdentifier or constrained to 0..1 exactly as the Jira resolution text said, that should be handled as follow-up work in the Extension Pack, not by adding new core source for this issue.
