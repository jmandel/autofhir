FHIR-11138: Audit double cousin relationship handling

Issue request:
FHIR-11138 was a Published/Persuasive Clinical Genomics change request asking whether the v3 FamilyMember relationship terminology should include a "double cousin" relationship. The accepted resolution was not to add a separate double-cousin code; it said the relationship should be represented through pedigree information while using the existing cousin relationship semantics, with the genetics sibling extension and an example demonstrating the pedigree links.

Initial application:
The issue was applied by git commit e3493bf5ac23399d1e3a8102b6ada656126cc97e, which explicitly referenced #11138 and added the double-cousin List example, a sibling relationship value set, and the genetics sibling extension/profile wiring. The current core source still has the double-cousin example under the active List source and links it from the active FamilyMemberHistory examples page.

Additional context:
FamilyMemberHistory and List are active resources in source/fhir.ini. Later R5 source cleanup removed the concrete genetics extension definitions from core, while the same canonical sibling extension and sibling relationship value set are present in the FHIR Extension Pack source. The current core source therefore should not re-add a double-cousin terminology code or duplicate extension-pack definitions. Zulip and Confluence searches found bot/usage mentions but no conflicting WG decision or later reversal for this issue.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current core source preserves the applied double-cousin pedigree example and the current extension definition belongs to the Extension Pack, so a core source edit would either duplicate external source of truth or add a relationship code contrary to the published resolution.

Recommendation:
Keep this audit commit as-is. If future work wants to modernize the old genetics profile/example presentation or repair non-semantic typos in the example metadata, handle that separately from FHIR-11138; no current core terminology change is required for this issue.
