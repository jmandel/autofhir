FHIR-13827: Align CapabilityStatement CORS guidance

Issue request:
FHIR-13827 was a Published security WG change request, resolved Persuasive with Modification, asking for stronger guidance than a blanket "SHOULD use CORS" or permissive Access-Control-Allow-Origin approach for Internet-facing FHIR APIs.

Initial application:
The issue was initially applied in git commit 9071f6d0d1 under the historical GF#13827 identifier by softening the CORS sentence in source/security.html and adding W3C, Enable-CORS, and Moesif references. Later cleanup in 3baee24231 corrected spelling and modal wording, and the current security page now carries the intended conditional guidance.

Additional context:
FHIR-13828 is a duplicate of this issue. FHIR-16428 and FHIR-17307 are the same CORS/http/security page change family. Source review found that the active CapabilityStatement resource still had a parallel CORS comment recommending Access-Control-Allow-Origin: * and stating that all servers SHOULD support CORS, which preserved the same security ambiguity in generated conformance definitions even though the security page itself had been corrected.

AutoFHIR reconciliation:
Updated CapabilityStatement.rest.security.cors to remove the permissive wildcard-header example and blanket SHOULD, and to say that CORS support is appropriate when a server chooses to support browser-based JavaScript clients and should be configured according to security policy. The edited source is in build scope because source/fhir.ini lists capabilitystatement as an active resource.

Recommendation:
Keep this commit. It completes the seed issue by aligning the current conformance definition with the already-applied security page guidance; the duplicate FHIR-13828 needs no independent source change.
