FHIR-16449: Audit ValueSet expand limitedExpansion removal

Issue request:
FHIR-16449 was a Published Vocab change request for STU3, resolved Persuasive with Modification, asking to remove the ValueSet $expand input parameter limitedExpansion. The accepted resolution was to remove that client parameter and update the documentation on count because the server, not the client, decides when an expansion is too expensive while clients can still request partial results with count.

Initial application:
The Jira comments point to svn revision 14008. In git, af02669d4245739a4c4ea146117faca6ad0fb4c9 is the git-svn import of that revision with subject "GF#16449 - Remove ValueSet.$expand.limitedExpansion parameter". It changed the then-authoritative source/valueset/valueset-spreadsheet.xml by removing the expand.limitedExpansion operation row and adding operation prose that clients can use count to request a subset of the expansion for limited purposes. It also added the R4 history/ballot row for this breaking change.

Additional context:
The current build no longer uses the old ValueSet spreadsheet as the active source for this operation; source/fhir.ini lists ValueSet as an active resource, and source/valueset/list-ValueSet-operations.xml references OperationDefinition/ValueSet-expand. The active source/valueset/operationdefinition-ValueSet-expand.xml has no parameter named limitedExpansion, keeps offset/count as the paging inputs, and includes operation-level text saying clients can use offset/count for partial pages or use count to request a subset for limited purposes. Later issue FHIR-55914 confirms that references to a limitedExpansion input parameter in CRMI were stale because the parameter was removed in STU3; FHIR-40717 separately handled later valueset-toocostly/valueset-unclosed clarification and is already represented on the combined branch.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current core source already implements the FHIR-16449 decision: limitedExpansion is not an input to ValueSet $expand, and the operation documentation explains the count-based alternative. Adding duplicate wording to the count parameter itself would not change implementer understanding and would create avoidable maintenance drift.

Recommendation:
Keep this no-change audit commit as-is for FHIR core. No further core source work is needed for FHIR-16449; stale references in non-core IGs should continue to be handled in those external repositories, as FHIR-55914 did for CRMI.
