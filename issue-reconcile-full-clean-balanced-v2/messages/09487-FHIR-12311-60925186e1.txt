FHIR-12311: Audit ElementDefinition orderMeaning

Issue request:
FHIR-12311 was a Published/Persuasive FHIR-core change request asking ElementDefinition to distinguish repeating elements whose order carries semantic meaning. The accepted resolution was to add ElementDefinition.orderMeaning as a string with text saying absence means order has no meaning, and that profiles cannot introduce ordering meaning unless the base resource or datatype did so.

Initial application:
The issue was applied in svn revision 11203, now git commit 8c3813303ed3c8d0e5efe695af4639ec6a9ecf9a, which added ElementDefinition.orderMeaning to source/datatypes/elementdefinition.xml with the requested cardinality, type, definition, and comments. That same historical commit also carried FHIR-12331 ordering-note work, but the orderMeaning element itself directly implements FHIR-12311.

Additional context:
ElementDefinition is an active datatype in source/fhir.ini and is marked normative in the current build. Current source still contains ElementDefinition.orderMeaning as 0..1 string, retains the requested definition and profile/base-type restriction text, and the FHIR model definition includes orderMeaning as FHIR.string. Searches for directly relevant Zulip and Confluence discussion found no conflicting later community evidence.

AutoFHIR reconciliation:
No source change was made. The current source already implements the requested ElementDefinition.orderMeaning element and preserves the accepted semantics, so adding or changing wording would be redundant and risk needless drift.

Recommendation:
Keep this audit commit as-is. No follow-up is needed for FHIR-12311 unless a future work-group decision changes the policy for semantic ordering in profiles.
