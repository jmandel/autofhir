FHIR-18992: Audit subscription text/plain email guidance

Issue request:
FHIR-18992 was a Published / Persuasive with Modification STU3 Subscription issue asking that SMS and email subscriptions work better than raw XML/JSON by ensuring text/plain is usable and by explaining intended SMS/email use. The accepted resolution explicitly did not add a core element; it said to ensure text/plain is part of the value set, add narrative for SMS/email use, and rely on extension experimentation before standardizing a default-message element.

Initial application:
The Jira comment points to commit f6ab808915, which applied GF#18992 to the then-current Subscription source by adding narrative that text/plain can be useful for email and SMS together with an extension describing conversion of resources to a text representation. The immediately preceding related commit 80086b8f22 applied FHIR-18991 by changing Subscription.channel.payload from string toward a MIME-type code binding and revising the SMS payload note.

Additional context:
FHIR-18991 is the same 2018 Subscription channel/payload change family and supplied the payload datatype/value-set prerequisite assumed by FHIR-18992. Current Subscription source has since been refactored into R5/R6 topic-based Subscription resources, but Subscription remains active in source/fhir.ini. The current core-defined channel list includes rest-hook, websocket, email, and message, with no SMS-specific core narrative. The current Subscription.contentType element is a code with a required binding to ValueSet/mimetypes (BCP 13) and explicitly notes that the Email channel defines additional MIME types such as text/plain and text/html. The current Email channel narrative explains that the body is human-readable, gives text/plain examples, describes attachment MIME parameters, and explains how a standard non-PHI body can be used while respecting Subscription.content.

AutoFHIR reconciliation:
This is an empty audit commit. No source edit is needed because the current active source preserves the implementer-visible outcome of the accepted issue: text/plain is valid through the MIME type binding and is explicitly documented for Email channel bodies, while the previously mentioned default-message element was intentionally not added and SMS is no longer a current core-defined channel section to update.

Recommendation:
Keep this no-change audit as-is. Do not add redundant Subscription prose or a core default-message element for FHIR-18992 without a new work-group decision; any future SMS channel or standardized default-message extension should be handled as a separate current-scope proposal.
