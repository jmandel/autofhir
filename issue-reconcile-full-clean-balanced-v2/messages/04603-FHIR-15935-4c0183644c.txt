Issue request:

The recorded resolution was to move both Patient operations from normative status to STU/trial-use because the committee had not intended them to be normative.

Initial application:
No current git commit explicitly mentions FHIR-15935, but Jira records an application comment that the operations were tagged trial-use. The R4B source import, and the later v5.0.0 source, carried both source/patient/operationdefinition-Patient-match.xml and source/patient/operationdefinition-Patient-everything.xml with structuredefinition-standards-status value "trial-use", which is consistent with the applied R4 decision.

Additional context:
The current build has source/fhir.ini actively listing Patient, and source/patient/list-Patient-operations.xml now lists Patient-match and Patient-purge only; Patient-everything was removed from the current Patient operation list and source by a later R6 commit. A broad 2025 status-code cleanup changed Patient-match and Patient-everything from trial-use to normative before the later removal of Patient-everything. Later R5 Patient/$match issues clarified parameters and return bundle behavior but did not reopen the R4 normative-status decision. Zulip FMG NIB discussion confirms the 2018 ballot scope was marking Patient $match as not normative for R4.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. FHIR-15935 was applied to the R4/R4B/R5 lineage as trial-use, and the remaining current R6 Patient-match normative marker is a later standards-status change outside the R4-specific request. Reverting the current R6 status under this old tracker would be a new maturity decision rather than reconciliation of FHIR-15935.

Recommendation:
Keep this audit commit as-is for FHIR-15935. If PA or FMG wants Patient $match to remain trial-use in R6, open or resolve a current-scope Jira issue that explicitly supersedes the later R6 standards-status cleanup; do not use this R4-scoped tracker to silently change the current R6 maturity marker.
