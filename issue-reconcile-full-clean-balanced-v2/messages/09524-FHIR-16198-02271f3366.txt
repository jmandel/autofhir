FHIR-16198: Complete purge operation definitions

Issue request:
FHIR-16198 was Applied as Persuasive with Modification for FHIR-core REST. The final request was to define DELETE [base]/[type]/[id]/_history, DELETE [base]/[type]/[id]/_history/[vid], corresponding delete-history and delete-history-version CapabilityStatement interaction codes, and Patient/Group $purge operations suitable for asynchronous behavior, with links from the HTTP delete section.

Initial application:
The issue was partially applied by 582318c880c and c1b29d509424, then 79f7e6eb3ee added the Patient $purge OperationDefinition and a Delete-section link, and c2724e8a568 added the delete-history HTTP sections/table rows. FHIR-42728 and b4ae65a387 completed the RESTful interaction code and CapabilityStatement code surfaces. Later, 992dff4a2fa split the $purge operation into Patient and Group files to fix a build issue, but left the Patient definition scoped to both Patient and Group, left the Group definition with id/url metadata that did not match OperationDefinition/Group-purge, omitted the Group resource scope, and left both purge operations marked as not affecting state.

Additional context:
FHIR-I minutes and Zulip discussion confirm the intended split: DELETE handles historical versions of a single resource while $purge handles broader Patient-compartment deletion, including POST /Patient/[id]/$purge and POST /Group/[id]/$purge for all Patient compartments of Group members. The later FHIR-42728 decision is a supporting same-change-family issue for the interaction codes, but it is not decided here because the current code system and value set already contain delete-history and delete-history-version.

AutoFHIR reconciliation:
This commit updates the current build-scope REST source and OperationDefinition sources. The HTTP delete section now links both Patient $purge and Group $purge and states that delete-history-version is an error for the current version, matching the Jira resolution. The Patient $purge OperationDefinition now applies only to Patient and correctly marks the operation as state-changing. The Group $purge OperationDefinition now has the Group-purge id/canonical metadata expected by the active Group operations list, declares Group as its resource scope, describes Patient compartments of Group members, includes standard OperationDefinition publication metadata, and marks the operation as state-changing.

Recommendation:
Keep this commit. It completes the applied FHIR-16198 semantics in the authoritative current source without expanding into future policy details; any additional questions about SMART scopes, exact purge side effects, or 404-vs-410 behavior should remain separate work-group decisions.
