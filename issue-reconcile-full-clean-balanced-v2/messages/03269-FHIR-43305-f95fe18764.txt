FHIR-43305: Audit nested composite search parameter rule

Issue request:
FHIR-43305 was an Applied/Persuasive with Modification FHIR-core SearchParameter clarification asking whether composite search parameters may reference another composite search parameter as a component. The final resolution required the core specification to say composites cannot reference other composites and that authors should construct the composite from the desired composite's leaf-level search parameters instead.

Initial application:
The issue was applied by PR HL7/fhir#3967, whose Jira comment was added after merge, and by commit 34a98858304e6298f0393956c4e91c50e78d9939, "FHIR-43305 - clarify that composite parameters cannot be nested." That commit changed active source/search.html only, adding the no-nesting conformance sentence, non-composite component guidance, and a leaf-component example. The current combined branch already contains that source commit.

Additional context:
FHIR-I WGM minutes for January 2024 record the same decision: explicit disallowance of a composite search parameter referencing another composite search parameter, with a 15-0-1 Persuasive with Modification vote. The SearchParameter resource is active in source/fhir.ini, and the active Search page currently contains the normative rule. SearchParameter.component.definition remains a generic canonical reference to SearchParameter, but the page-level conformance rule supplies the runtime restriction without conflicting with the structure definition. Direct Zulip searches found no relevant counter-discussion, and Jira neighborhood searches found no later core issue changing the rule.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already states that composite search parameters SHALL NOT declare components referencing other composite search parameters, requires components to be non-composite, and explains flattening to leaf component search parameters with an example.

Recommendation:
Keep this no-change audit as-is. Any future desire to add validator/tooling enforcement should be handled as a separate tooling or implementation task because the Applied FHIR-core source clarification is already present and consistent with the recorded FHIR-I decision.
