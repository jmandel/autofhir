FHIR-22770: Audit duplicate-create response guidance

Issue request:
FHIR-22770 was a Published/Persuasive FHIR-core issue, raised against STU3 and applied for R5, asking for create-interaction language that would let a server detect a duplicate patient or other existing record and return 201 with the existing resource as though a new resource had been created.

Initial application:
The Jira-tagged commit 5de04e66970292a21c6f7393527c115fef02fe4d added the requested create-section note to source/http.html in May 2022, stating that a server MAY return 201 when a create request matches an existing record with high confidence and reminding clients to review returned data.

Additional context:
FHIR-32757 was a later Published/Persuasive with Modification FHIR-I decision for the same duplicate-create behavior. Its resolution says returning 201 when no new record was created is non-conformant and instead allows 303 See Other with Location pointing to the existing unchanged record. The combined branch already contains Issue-Reconcile-Key: FHIR-32757 in commit 984dc7f24002d09b308b2e3710f51dfa1dacca3a, which moved that later rule into the active create section and removed the stale FHIR-22770 201 allowance. FHIR-53546 was inspected as nearby conditional-create duplicate/race-condition context, but it concerns If-None-Exist concurrency rather than the standard create response requested here.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Current source/http.html already reflects the later controlling FHIR-32757 decision: 201 applies when the create request creates a new resource, duplicate POSTs MAY return 303 See Other with Location, and a server SHALL NOT return 201 Created if it did not create a new resource.

Recommendation:
Keep this no-change audit. Do not restore the older FHIR-22770 201-for-existing-record note unless FHIR-I makes a new explicit decision reversing FHIR-32757; the current source is the correct reconciled state for duplicate create responses.
