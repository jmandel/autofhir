FHIR-6066: Audit ElementDefinition choice snapshot base metadata

Issue request:
FHIR-6066 was a Published FHIR-core profiles change request, resolved Persuasive with Modification, about derived profiles that constrain a type-specific choice element such as MedicationStatement.effectivePeriod without intending to remove the other allowed [x] types from the generated snapshot. The approved resolution was to add basePath, baseMin, and baseMax to ElementDefinition as a 0..1 base component whose path, min, and max children are required when base is present.

Initial application:
The Jira comment records svn revision 5924. Git-svn history shows ddb1f8c4e0916fada828b645a84c2c90f59329e2 (#6066, svn r5923) adding ElementDefinition.base and initial population, followed by 74950f48e21290a8d95baa474e74c2d2d3034e11 (#6066, svn r5924) adding the ElementDefinition.base invariants. Current source no longer uses the flat basePath/baseMin/baseMax names, but represents the approved concept as ElementDefinition.base.path, ElementDefinition.base.min, and ElementDefinition.base.max.

Additional context:
FHIR-6093 and FHIR-6340 are the same Published/Persuasive with Modification StructureDefinition [x] path family and are already represented on the combined branch by audit commits. FHIR-8310 is another same-family issue about retaining base cardinality information after max is constrained to 1, and is audited separately by this reconciliation. ElementDefinition is an active normative datatype in the current build, StructureDefinition snapshots require base information on all elements, and current choice-element narrative says the original [x] element is always represented in snapshots while type-specific elements only constrain that specific type use. Direct Zulip and Confluence searches found no FHIR-6066-specific community record that changes the Jira/source conclusion.

AutoFHIR reconciliation:
No source change was made. The current authoritative ElementDefinition and StructureDefinition source already carries the base metadata needed for tools to distinguish the original [x] element from type-specific constraints without treating omitted type-specific rows as removed types.

Recommendation:
Keep this audit commit as-is. No FHIR core follow-up is needed for FHIR-6066 unless the work group separately decides to change current ElementDefinition.base semantics or snapshot generation rules for choice elements.
