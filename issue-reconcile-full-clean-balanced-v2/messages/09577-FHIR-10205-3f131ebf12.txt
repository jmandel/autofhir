FHIR-10205: Audit CapabilityStatement.rest cardinality

Issue request:
FHIR-10205 was a Published/Persuasive FHIR-core Conformance change request for DSTU2 asking to change Conformance.rest from 0..* to 0..2 because the then cnf-8 invariant allowed only one REST declaration per mode.

Initial application:
The Jira application note says svn revision 14121 revoked the one-rest-per-mode constraint after Zulip discussion, rather than tightening cardinality, because the rest element definition allowed both client/server behavior and possibly different configuration settings. In the current build, Conformance has become the active CapabilityStatement resource; CapabilityStatement.rest remains 0..* and still carries the multiple-repetitions comment.

Additional context:
FHIR-33955 is a later Published/Persuasive R5 issue for the same artifact that explicitly decided to add an invariant limiting CapabilityStatement.rest to one repetition per mode. The linked Zulip thread records Lloyd McKenzie's guidance that only one client and one server repetition should exist and that an invariant was appropriate because the resource design could not express cardinality 0..2. Commit 071000dbe2 added cpb-4 to the active CapabilityStatement StructureDefinition. FHIR-54050 later questions the cpb-4 explanatory wording but is still Triaged/Unresolved, so it is not a final contrary decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active source currently reflects the later FHIR-33955 decision by keeping CapabilityStatement.rest at 0..* while enforcing rest.mode.isDistinct() through cpb-4; changing max to 0..2 or removing cpb-4 for FHIR-10205 would conflict with the later published work-group decision.

Recommendation:
Keep this audit commit as-is for FHIR-10205. If FHIR-I later resolves FHIR-54050 or another follow-up about cpb-4 wording or semantics, handle that as a separate issue rather than reopening the DSTU2 FHIR-10205 cardinality request.
