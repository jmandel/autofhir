FHIR-12465: Audit ElementDefinition type profile cardinalities

Issue request:
FHIR-12465 was a Published/Persuasive FHIR-core ElementDefinition change request raised for DSTU2. It asked to change ElementDefinition typeRef.profile and typeRef.targetProfile to 0..* and to add an invariant requiring typeRef.code to be unique, because multiple target profiles can be legitimate alternatives for a single Reference/canonical type while repeated type codes would make validation and code generation ambiguous.

Initial application:
The historical application is visible in git commit 292398314311cb4026b7620e7b6d7ce00a3c356a, whose subject is "#12465 - make ElementDefinition.type.profile and targetProfile 0..*  and #13065 - add ElementDefinition.isModifierReason" and whose git-svn-id is build@13068. Comparing that commit with its parent shows ElementDefinition.type.profile and ElementDefinition.type.targetProfile changed from 0..1 to 0..*, and the ElementDefinition invariant "Types must be unique by code" / type.select(code).isDistinct() was added.

Additional context:
ElementDefinition is an active datatype/page in source/fhir.ini, so source/datatypes/elementdefinition.xml is in current build scope. The current source now uses ElementDefinition.type.profile and ElementDefinition.type.targetProfile rather than the older typeRef wording, keeps both cardinalities at 0..*, and keeps the unique-by-code invariant. Later FHIR-44761 added warning-level uniqueness checks for duplicate profile and targetProfile repetitions, which is compatible with FHIR-12465 and does not narrow the allowed 0..* alternatives.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current authoritative source already implements the requested 0..* profile and targetProfile cardinalities and the type-code uniqueness invariant, and no conflicting Zulip or Confluence evidence was found.

Recommendation:
Keep this audit commit as-is. No follow-up source change is needed for FHIR-12465 unless a future work-group decision changes the current multiple-profile semantics.
