FHIR-10121: Remove stale CapabilityStatement messaging event references

Issue request:
FHIR-10121 was a Published FHIR-core Conformance change request with a Persuasive with Modification resolution. The comments clarified that the actual problem was Conformance/CapabilityStatement.messaging.event.response being 1..1 even though some messages have no application-level response and others allow multiple response message definitions; the final resolution was to remove CapabilityStatement.messaging.event after community comment.

Initial application:
Jira records svn revision 12734. In git history, 3046b26fdb1d6820bce26924803583dbbc0b0330 (#12829 & #10121 CapabilityStatement tasks) removed the CapabilityStatement.messaging.event subtree, including the 1..1 request and response elements, from the source spreadsheet and changed the example to use CapabilityStatement.messaging.supportedMessage. Current active source has no CapabilityStatement.messaging.event element and MessageDefinition.allowedResponse is 0..*, but some current narrative and element comments still pointed at the removed event mechanism.

Additional context:
source/fhir.ini shows CapabilityStatement and MessageDefinition are active current-build resources. MessageDefinition carries the message category and the 0..* allowedResponse list that supersede the removed CapabilityStatement.messaging.event.category/response fields. A 2017 Zulip implementers thread independently raised the same response cardinality mismatch, and Lloyd McKenzie replied that CapabilityStatement.messaging.event was going away and being replaced by MessageDefinition. Direct FHIR-10121 Zulip/Confluence searches and Confluence Jira-reference searches found no conflicting guidance. FHIR-12829 shared the same svn application commit but was a separate CapabilityStatement profile-placement issue already represented on the combined branch.

AutoFHIR reconciliation:
Updated current source so CapabilityStatement messaging notes describe supportedMessage/MessageDefinition instead of the removed event/request/response mechanism, the supportedMessage element comment no longer calls it a proposed alternative to a removed structure, and the reliable-messaging guidance now points to MessageDefinition.category instead of nonexistent CapabilityStatement.messaging.event.category. No generated SVG or build output was edited.

Recommendation:
Keep this source fix as-is. It completes the FHIR-10121 removal by eliminating stale current-spec references to removed CapabilityStatement.messaging.event fields while preserving the intended MessageDefinition-based capability model.
