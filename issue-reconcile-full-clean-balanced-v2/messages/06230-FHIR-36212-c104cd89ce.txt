FHIR-36212: Audit Reference.identifier cardinality duplicate

Issue request:
FHIR-36212 was a Published/Persuasive with Modification FHIR-core References issue asking to change Reference.identifier cardinality from 0..1 to 0..* so logical references could carry multiple known business identifiers. The Jira resolution explicitly made it a duplicate of FHIR-30878 and directed readers to that resolution.

Initial application:
No FHIR-36212-specific source-changing commit was found. The duplicate target, FHIR-30878, appears to have been applied by git commit 0bdbd05b41b1a83334cde1e26cfb7d30a59b6e72, which updated the active Reference datatype spreadsheet source to keep Reference.identifier single-valued and add usage-note guidance for additional identifiers. The current source still has Reference.identifier max 0..1 and the additionalIdentifier extension guidance.

Additional context:
FHIR-30878 resolved that the normative Reference.identifier max cardinality could not be widened and that the right R5-compatible path was a standard extension. The originating Zulip thread confirms the implementer use case was multiple logical-reference identifiers, while FHIR-I minutes show the work group considered the normative-break concern, approved FHIR-30878 as Persuasive with Modification, and later voted FHIR-36212 as a duplicate of FHIR-30878. The additionalIdentifier extension now lives in the FHIR Extension Pack with Reference context, max *, and Identifier value type, and the current CI build links Reference.identifier comments to that extension. A later FHIR-13694 reconciliation changed adjacent Reference.identifier scope wording but preserved the single-identifier/additionalIdentifier rule.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current core source is correct for FHIR-36212 because the final decision was not to make Reference.identifier 0..*, but to retain the normative 0..1 cardinality and direct additional identifiers to http://hl7.org/fhir/StructureDefinition/additionalIdentifier.

Recommendation:
Keep this empty audit commit as-is. Do not widen Reference.identifier in core for this issue; any future change to multiple identifiers would need a new normative-change decision rather than reopening this duplicate.
