FHIR-38999: Audit shared interface search parameters

Issue request:
FHIR-38999 was a Published FHIR-core R5 change request resolved Persuasive with Modification. It asked that SearchParameters inherited from interfaces such as CanonicalResource be represented as shared/common definitions rather than separate resource-specific definitions such as ActivityDefinition-status, that MetadataResource-derived resources also receive CanonicalResource search parameters, and that the search parameter registry make the shared parameters clear.

Initial application:
The issue was explicitly applied in git commit 6c4526c5e03f2ec90cc8d0a5f62d89e3812e76dc, which removed the old manually duplicated conformance-* common SearchParameter definitions from source/searchparameter/common-search-parameters.xml. Current source keeps CanonicalResource and MetadataResource as active interface resources and defines interface search parameter bundles that the publisher expands to the applicable concrete resources.

Additional context:
MetadataResource currently declares CanonicalResource as its template/baseDefinition, so resources based on MetadataResource inherit the CanonicalResource search parameter family. The generated CI search-parameters.xml contains shared CanonicalResource-* and MetadataResource-* SearchParameters and no ActivityDefinition-status, ActorDefinition-status, or conformance-status definitions. The generated registry lists CanonicalResource and MetadataResource shared sections at the top and concrete resource sections refer to those shared ids. Jira searches found no later issue overriding this decision, Zulip searches found no conflicting discussion, and Confluence only confirmed the FHIR-I approval motion.

AutoFHIR reconciliation:
This is an empty audit commit. No source change is needed because the current built specification already publishes interface search parameters as shared SearchParameter definitions and points concrete resource search support at those definitions. The remaining registry presentation does not create separate resource-specific definitions; it is a generated rendering choice rather than a core source defect that changes implementer understanding.

Recommendation:
Keep this audit commit as-is. If the work group wants the generated registry's per-resource sections further compressed to a single inherited-parameters row, that should be treated as a publisher/rendering enhancement, not as a correction to the current core SearchParameter definitions.
