FHIR-12438: Audit UCUM expansion tooling locus

Issue request:
FHIR-12438 was a Published/Persuasive FHIR-core change request from DSTU2 asking that UCUM, being intensional, not display a misleading finite expansion made from common UCUM table codes.

Initial application:
The Jira comments say the issue was fixed as part of the R3 marathon. The linked 2016 Zulip discussion shows the requested application was for the spec/publisher terminology expansion to refuse full UCUM expansion or clearly point to common UCUM instead. No current source commit tagged FHIR-12438 was found, and the current build-scope ucum-units ValueSet source remains a compose-only include of http://unitsofmeasure.org with no embedded expansion to remove.

Additional context:
FHIR-12464 removed the duplicate US Core UCUM value set in favor of the core ucum-units ValueSet. Later FHIR-36010 explicitly notes that ucum-units has no explicitly defined expansion and that fixes to its expansion behavior are tooling or tx.fhir.org work. Current ValueSet.$expand source guidance says unbounded value sets such as UCUM should return an error or use the valueset-unclosed extension for incomplete expansions, while the current build.fhir.org HTML still shows a tx.fhir.org-generated UCUM expansion without such a marker.

AutoFHIR reconciliation:
This empty audit commit makes no source change because the authoritative FHIR source already lacks an embedded UCUM expansion and the remaining expansion display behavior is generated outside this source checkout by terminology/publisher tooling. Editing the ValueSet definition would not directly implement the requested display behavior.

Recommendation:
Keep this audit as an external-repo decision. If the current rendered UCUM page is still considered misleading, follow up in the FHIR publisher or tx.fhir.org terminology service so all-code UCUM expansions are refused or marked unclosed/incomplete consistently with the current $expand guidance.
