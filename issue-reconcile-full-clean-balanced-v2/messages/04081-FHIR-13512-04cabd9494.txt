FHIR-13512: Audit RequestOrchestration reason alignment

Issue request:
FHIR-13512 was a Published/Persuasive CDS change request for STU3 asking that RequestGroup.reasonCodeableConcept and RequestGroup.reasonReference be moved out from a nested/choice structure to top-level reasonCode and reasonReference elements, aligned with the then-current Request pattern.

Initial application:
The Jira comment records SVN 12255. The converted git commit 571fea972c605378a443f9fa8c2bace66e61a178 is that application and changed the RequestGroup spreadsheet and example from RequestGroup.reason[x]/reasonCodeableConcept to top-level RequestGroup.reasonCode and RequestGroup.reasonReference.

Additional context:
RequestGroup was later renamed to RequestOrchestration by FHIR-24619, and source/fhir.ini now has requestorchestration as the active resource with RequestGroup mapped to RequestOrchestration for R4-to-R6 migration. The current Request pattern represents code-or-reference reasons as a single top-level CodeableReference Request.reason, with Request.reasonReference retained only as a migration entry. RequestOrchestration follows that pattern with a top-level RequestOrchestration.reason CodeableReference mapped to Request.reason, and no nested action reason or legacy reasonCodeableConcept/reasonReference remains in the RequestOrchestration definition.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The original STU3 request was applied, and the later CodeableReference refactor preserves the intended top-level reason semantics for the current build.

Recommendation:
Keep this no-change audit commit. Reintroducing separate reasonCode/reasonReference elements would undo the current Request pattern rather than fix FHIR-13512; no follow-up is needed unless the work group separately decides to change the shared Request.reason pattern.
