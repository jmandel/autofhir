FHIR-5406: Audit _count paging-link guidance

Issue request:
FHIR-5406 was a Published/Persuasive DSTU1 FHIR-core-search ballot comment asking the search page to say that servers should repeat the original _count parameter in returned page links so subsequent paging requests honor the original _count.

Initial application:
The request was applied in git-svn commit 354ab48017ef928149f648f6c2e7e77f697afd69, corresponding to SVN revision 4496 cited in Jira, which added the proposed _count page-link sentence to source/search.html.

Additional context:
The active search source remains in source/search.html. Later Published issue FHIR-28589 revisited the same sentence for cases where the requested _count exceeds a server maximum page size and changed the exact implementation guidance from repeating the parameter literally to ensuring linked pages respect the original requested _count expectations or a server-overridden max page size. Zulip discussion in 2020 supports that later clarification, and no FHIR-5406-specific Zulip or Confluence evidence was found that conflicts with the source/history conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current normative search page still tells servers not to exceed the requested per-page count and says linked pages should respect the original _count expectation or server max page size, which preserves FHIR-5406's implementer-facing rule after the later FHIR-28589 refinement.

Recommendation:
Keep this audit commit as-is. Do not restore the older literal "repeat the original _count parameter" wording for FHIR-5406 because FHIR-28589 deliberately replaced it with the current behavior-focused wording.
