FHIR-7929: Make REST create version metadata conditional

Issue request:
FHIR-7929 was Published/Persuasive with Modification for the DSTU1 HTTP page. It asked that create-time version metadata wording be conditional on server versioning support; the accepted note kept the requirement as SHALL but only when the server supports versioning.

Initial application:
The Jira comment records svn revision 5341. Git commit 97095030bb8d07af7c80ef6c0c7f7b76f460bc85, imported from that revision, changed the update interaction wording in source/http.html from an unconditional meta.versionId/meta.lastUpdated population requirement to a conditional "If the server supports versions" sentence. That application did not update the parallel create/update-as-create Location and metadata text, which still implied that all servers populate or return a version id.

Additional context:
Current source/http.html is the active HTTP narrative page named by the Jira related page. The current Support for Versions section says no-version servers must omit Resource.meta.versionId while updating Resource.meta.lastUpdated correctly. Later FHIR-14222 Resource Metadata table text, already represented on the combined branch, likewise distinguishes server-updated lastUpdated from versionId that can be updated or removed when versions are unsupported. FHIR-11259 is also already represented on the combined branch and supports the same no-version/meta.versionId interpretation.

AutoFHIR reconciliation:
This commit updates source/http.html so update/create processing always says the server updates meta.lastUpdated, while meta.versionId is populated only when the server supports versions. It also makes the Location-header descriptions for update-created resources, conditional updates, create, and conditional create say Version Id is included only when versioning is supported, matching the existing explanatory sentence that no-version servers return [base]/[type]/[id].

Recommendation:
Keep this source-changing commit. It completes the FHIR-7929 reconciliation in the current HTTP page without republishing the already-audited related Meta/versioning issues.
