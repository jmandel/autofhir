FHIR-17102: Audit profiling cardinality guidance

Issue request:
FHIR-17102 was Published/Persuasive with Modification for STU3 and asked for profiling documentation notes that constraining a repeating element's upper cardinality does not change JSON array representation, and that profile authors should be careful not to over-constrain upper cardinality when slicing or lower-cardinality expectations can express the need.

Initial application:
The issue was applied in svn 14332, imported as git commit f1c3bd7e5c2fc58bafcc4a68333464daf8e33264, titled "GF#17102 - cardinality clarifications". That commit added a Changing Cardinality paragraph explaining that narrowing Patient.name from x..* to x..1 still leaves JSON array representation unchanged, plus a Slice Cardinality section warning about slice minimum and maximum cardinality totals.

Additional context:
The current build includes profiling.html as an active published page through publish.ini. The cited Zulip thread confirms the issue's rationale: JSON shape is determined by the base resource rather than the profile, and profile authors should avoid unnecessary upper-cardinality narrowing. Later profiling work, notably FHIR-31054, refined one slice-cardinality bullet but preserved the substance of the FHIR-17102 guidance.

No source change was made. Current source/profiling.html still contains the JSON array-format warning and the active Slice Cardinality section, so the current specification already implements the published FHIR-17102 decision.
