FHIR-39616: Add Endpoint payload profile ModelInfo

Issue request:
FHIR-39616 was Applied with a Persuasive resolution for R5. It asked to support FHIR profile identifiers on Endpoint payloads by adding Endpoint.payload.profile as 0..* Canonical(StructureDefinition) | URI, so Endpoint can advertise expected resource/profile content without overloading payload.type.

Initial application:
The issue was initially applied in core by 63638211f47be5c334babed5e0d868891e177695, which added Endpoint.payload.profile[x]. Follow-up commit d58d7f95864558e6c61aa74084d91599e96874ff made an editorial punctuation correction, and 776045a35d350696534e4448b84c40d3f7ea4938 split the choice into current Endpoint.payload.profileCanonical and Endpoint.payload.profileUri elements.

Additional context:
FHIR-40247 had already introduced the Endpoint.payload backbone, and the immediately preceding reconciliation commit aligned the active FHIR ModelInfo Library with that backbone for payload.type and payload.mimeType. Current Endpoint source includes profileCanonical/profileUri and a payload-profile search parameter over both fields, but the active ModelInfo Library still lacked those nested payload profile elements.

AutoFHIR reconciliation:
This commit adds profileCanonical as List<FHIR.canonical> and profileUri as List<FHIR.uri> to FHIR.Endpoint.Payload in source/library/library-fhir-model-definition-content.xml, then regenerates the Library.data attachment in source/library/library-fhir-model-definition.xml so the built Library remains synchronized.

Recommendation:
Keep this source fix as-is. It reconciles the current split profileCanonical/profileUri representation on the active core ModelInfo surface and does not alter the already-correct Endpoint StructureDefinition or search parameter sources.
