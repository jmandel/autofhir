FHIR-25275: Audit canonical fhir-type generator fix

Issue request:
FHIR-25275 was a Published/Persuasive FHIR-I technical correction raised against R4 for the canonical primitive StructureDefinition. The Jira report observed that canonical.value carried structuredefinition-fhir-type valueUrl "string" in the snapshot but "canonical" in the differential, and FHIR-I minutes recorded it as an auto-approved technical correction that would also be fixed in R4.

Initial application:
No FHIR core source commit mentioning FHIR-25275 was found. The application trail is the external Kindling generator work cited from Jira: HL7/kindling commit 1b0392b0, later included in the HL7/kindling#69 commit 962c1c66, changed primitive profile generation from a hard-coded fhir-type "string" to the primitive type code and explicitly named FHIR-25275.

Additional context:
The active current FHIR source defines canonical as a primitive based on uri with JSON string representation, and the ElementDefinition guidance explains that FHIRPath System.String values use structuredefinition-fhir-type to carry the FHIR primitive constraint. Although the original Jira wording called the snapshot "string" value correct, the accepted implementation and current primitive profile pattern align snapshot and differential to the primitive type code: string uses string, uri uses uri, uuid uses uuid, and canonical now uses canonical. The historical R4 canonical.profile.json still shows the old snapshot/differential mismatch, but R5 and the current CI build are consistent. The closely related Kindling fhir-type correction for FHIR-36036 is already represented on the combined branch.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current build-scope source does not contain a missing canonical.value fhir-type hunk, and current generated R5/CI canonical.profile.json already emits structuredefinition-fhir-type valueUrl "canonical" in both snapshot and differential. Changing the current source to force "string" would conflict with the generator fix and with the adjacent primitive profile pattern; editing historical R4 publication artifacts is outside this current-source reconciliation.

Recommendation:
Keep this no-change audit for the current FHIR core branch. If HL7 still wants the old R4 publication artifact corrected, handle that through the historical publication/generator path rather than by changing the current core source.
