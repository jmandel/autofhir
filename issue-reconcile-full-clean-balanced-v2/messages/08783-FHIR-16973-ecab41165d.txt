FHIR-16973: Audit Attachment.url wording

Issue request:
FHIR-16973 was a Published FHIR-core change request resolved Persuasive with Modification. It asked why Attachment.url was defined as "An alternative location where the data can be accessed," because that implied Attachment.data was primary and Attachment.url was secondary; the accepted resolution was to remove "alternative" and check whether additional data/location wording was needed.

Initial application:
The issue was applied by SVN/Git commit 17920b99794ce85c84f69b0fb5e338e71f9f01c6 (svn revision 14301), which changed source/datatypes/attachment.xml from "An alternative location where the data can be accessed" to "A location where the data can be accessed." That matches the Jira comment recording svn revision #14301.

Additional context:
source/fhir.ini lists Attachment as an active datatype and normative artifact, so source/datatypes/attachment.xml is in current build scope. The current Attachment.url row retains the corrected definition and includes additional comments about same-content requirements when both data and url are provided, relative/transient URLs, bundle-local URIs, resolution to actual data, and later security validation guidance. FHIR Infrastructure Confluence minutes for 2018-07-09 list the block-vote item for tracker 16973 as Persuasive with Mod and record the block vote as approved 9-0-0.

AutoFHIR reconciliation:
No source change was made. The current active Attachment.url source already says "A location where the data can be accessed," and a current-source search found no remaining "alternative location where the data can be accessed" wording to correct.
