FHIR-34261: Audit Endpoint cardinality application

Issue request:
FHIR-34261 was Published/Persuasive for R5. It requested changing Endpoint.connectionType from 1..1 to 1..* so one Endpoint can support more than one connection type, changing Endpoint.payloadType from 1..* to 0..* so payload types can be fully described by connection types, and adding a connectionType comment explaining that payload types, mime types, and status apply across all listed connection types.

Initial application:
The issue was applied before this reconciliation. Commit 445d4741d1559c197decca8343f60d1cad753d36 changed source/endpoint/structuredefinition-Endpoint.xml by making Endpoint.connectionType max="*", adding the requested comment to Endpoint.connectionType, and making the then-current Endpoint.payloadType min="0". Merge commit 29c32a3f611f298e0601cd090b441155fed47286 brought that Endpoint cardinality work into the main history.

Additional context:
Endpoint is active in source/fhir.ini, so source/endpoint feeds the current build. The current source has Endpoint.connectionType as 1..* and has the requested all-connection-types comment. The old Endpoint.payloadType compatibility name maps to Endpoint.payload.type in source/fhir.ini, and the current Endpoint.payload.type is 0..*. FHIR-12342 approved the same connectionType 1..* direction, FHIR-25393 approved the payloadType 0..* direction, and FHIR-36074 was closed as a duplicate after PA explicitly declined to make connectionType optional without a separate, better documented tracker. Later FHIR-36589 changed Endpoint.connectionType to CodeableConcept/example binding while preserving the 1..* cardinality, and later FHIR-39617 clarified payload advertising without reversing the FHIR-34261 cardinalities.

AutoFHIR reconciliation:
No source change was made. The active current Endpoint source already contains the requested connectionType cardinality, payloadType/payload.type cardinality, and connectionType explanatory comment, and later related decisions do not require a different cardinality for this seed issue.

Recommendation:
Keep this audit commit as-is. Do not add redundant narrative for FHIR-34261; future Endpoint changes should be handled under the later payload-advertising or connectionType terminology trackers if they change implementer behavior.
