FHIR-39010: Audit resource-specific search package

Issue request:
FHIR-39010 was a Published FHIR-I change request, resolved Persuasive with Modification for R5, asking that generated output artifacts include individual/resource-specific SearchParameter definitions in addition to the combined search parameters used in the rendered registry.

Initial application:
The Jira-tagged source application is git a4ed0ed8, which added an hl7.fhir.r5.search package entry to source/downloads.html describing a package where combined search parameters are uncombined into a set of search parameters for each resource. The current source also contains per-resource bundle-<Resource>-search-params.xml files, including Patient-specific definitions derived from combined common search parameters.

Additional context:
FHIR-I minutes first asked Brian for clarification on 2023-01-09 and then approved Persuasive with Modification on 2023-01-30. The Jira resolution explicitly says these resource-specific instances should be in published packages for R5 and later, should not show up in the rendered spec, and should not be referenced by CapabilityStatements. A related Zulip implementers thread from November 2022 confirms that individual search parameters were expected to be package content rather than separate rendered pages.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The current build-scoped downloads page advertises the current hl7.fhir.r6.search package with uncombined/resource-specific search parameters, and active resource source folders contain the per-resource search-parameter bundles. Adding rendered registry links, CapabilityStatement references, or duplicate SearchParameter pages would conflict with the Jira resolution.

Recommendation:
Keep this audit as-is. If future package validation shows the hl7.fhir.r6.search package is missing these instances, investigate the publisher/package-generation tooling, but no core source edit is indicated by the current source and history.
