FHIR-17077: Clarify history bundle response invariant

Issue request:
FHIR-17077 was a Published/Persuasive FHIR-core Feed change request from the STU3 2018-May Core Norm Infrastructure ballot. It asked to allow Bundle.type = 'history' in the old bdl-4 entry.response invariant because history delete entries need response metadata such as timestamp and version id, and the issue comment says the change was already done.

Initial application:
The pre-refactor application appears in git commit c613b68f9b76a6d4f114766f447107ba47643a62, which changed the Bundle spreadsheet from only allowing entry.response for batch-response and transaction-response to making response mandatory for batch-response, transaction-response, and history. Later invariant cleanup replaced the old bdl-4 shape with bdl-3a through bdl-3d constraints.

Additional context:
Bundle is in the active current build scope through source/fhir.ini, and the current authoritative source already has bdl-3b enforcing request.exists() and response.exists() for every history entry. However, the bdl-3b human-readable text said "request or response elements", which contradicted the expression and weakened the exact response requirement FHIR-17077 was meant to preserve after the invariant refactor.

AutoFHIR reconciliation:
This commit changes only source/bundle/structuredefinition-Bundle.xml so the bdl-3b human text says history entries must contain request and response elements. No FHIRPath behavior changes were needed because the existing expression already required both.

Recommendation:
Keep this commit as-is. It is a narrow source fix in the active Bundle StructureDefinition that removes a misleading human-readable invariant summary while preserving the existing validation rule.
