FHIR-38860: Normalize HTTP status code formatting

Issue request:
FHIR-38860 was a Published/Persuasive FHIR-core-http clarification for R5. It asked that HTTP status codes on the HTTP page consistently use <code> markup, include the human-readable text when present and on first use of each code, and use the status text and capitalization from RFC 9110.

Initial application:
The Jira comments point to HL7/fhir#2425 and merge commit 7e91cbf62229789daece22e45563bbe92563fc0a, which reformatted many status-code references in source/http.html. The included commit ee761ef4bd5a52057846f25556c859510db5375c normalized many status names, and current source retained the original application, but later edits and the remaining 422 wording left the page inconsistent with the issue request.

Additional context:
FHIR-I WGM minutes on 2023-01-19 record FHIR-38860 as Persuasive with an 11-0-5 vote. Source history showed later edits to the same HTTP page, including FHIR-39137 search-method wording and FHIR-42728 conditional-delete wording, introduced or preserved additional status-code formatting slips. RFC 9110 defines status 422 as "Unprocessable Content", while the current source still used "Unprocessable Entity" in several HTTP status-code references.

AutoFHIR reconciliation:
This commit updates the current build source page source/http.html. It changes 422 reason phrases to <code>422 Unprocessable Content</code>, fixes <code>404 NotFound</code>, keeps 405 and 501 reason phrases inside the same <code> element as the numeric code, and gives the first 500 reference its RFC 9110 reason phrase. The edit is limited to the authoritative FHIR-core-http narrative source and does not change REST behavior.

Recommendation:
Keep this commit as a source fix for FHIR-38860. No related issue needs a separate reconcile decision; the related Jira-tagged history only explains why the current page had drifted after the original formatting PR.
