FHIR-11058: Audit Consent multiple policy support

Issue request:
FHIR-11058 was Published/Persuasive with Modification for FHIR-core Consent after the 2016 September ballot. It asked for Consent.policy to support multiple policies, with final resolution to change Consent.policy to 0..* uri, add Consent.policyRule as 0..1 uri for the computable policy, and require policy and/or policyRule.

Initial application:
The issue was applied in commit 612068c15886b6624c44de5d656417bcfa7d76d3 as part of the STU3 Consent resource updates. That commit changed the historical Consent.policy row from 1..1 uri to 0..* uri, added Consent.policyRule 0..1 uri for the specific computable policy, and added the corresponding policy/policyRule invariant. Later refactors removed the retired spreadsheet source and current R6 source no longer has active Consent.policy or Consent.policyRule elements.

Additional context:
Later final Consent decisions intentionally changed the model. FHIR-32817 replaced the old policy/policyRule pair with regulatoryBasis 0..*, policyBasis 0..1 Reference/URI, and policyText 0..* DocumentReference. FHIR-25387 removed the core invariant requiring discrete policy data while keeping guidance that policyBasis and/or policyText should be populated when practical. FHIR-39597 moved the default decision semantics to Consent.decision, FHIR-45450 changed policyBasis.url back to policyBasis.uri, and FHIR-55983 updated remaining old policy/policyRule wording. Consent is active in source/fhir.ini, which also records the R4/R5 mapping from old Consent.policy and Consent.policyRule names to current elements.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/consent/structuredefinition-Consent.xml already has the later approved structure: regulatoryBasis is repeatable, policyText is repeatable, policyBasis carries a single computable backing policy reference/URI, and the old required policy/policyRule invariant is not active. Changing policyBasis to repeat or reintroducing Consent.policy would reverse later work-group decisions rather than complete FHIR-11058.

Recommendation:
Keep this audit commit as-is. If implementers need multiple independent computable policy bases in one current Consent resource, that should be raised as a new work-group issue because the current single policyBasis cardinality is a later deliberate R5/R6 design decision, not an unapplied remainder of FHIR-11058.
