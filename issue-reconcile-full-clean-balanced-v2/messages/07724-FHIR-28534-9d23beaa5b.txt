FHIR-28534: Audit reverse chaining discovery note

Issue request:
FHIR-28534 was a Published FHIR-core change request with a Persuasive with Modification resolution. It asked how CapabilityStatement/SearchParameter can advertise support for reverse chaining (`_has`) and recorded that clients should not assume reverse chaining is supported wherever forward chaining is supported.

Initial application:
The issue appears to have been applied by HL7/fhir#2145, merged as f1d3052 after f7b26fb added a note to source/capabilitystatement/capabilitystatement-notes.xml. The application was not a new model element; it was a CapabilityStatement note documenting the reverse-chaining discovery gap, the non-assumption rule, and open questions about how much detail to declare.

Additional context:
FHIR-I minutes from 2020-12-14 accepted the request but recorded open design questions about whether SearchParameter could carry the information, whether CapabilityStatement2 might be needed, and how to express resource-pair-specific `_has` support. FHIR-I minutes from 2022-08-08 recorded the implementation path: add an STU paragraph in CapabilityStatement for readers to comment. Current active source still has that note, while SearchParameter.chain remains forward-chain-only and CapabilityStatement exposes searchInclude/searchRevInclude/searchParam but no field for supported `_has` combinations. Searches found no later final FHIR-core issue or community record that resolves the design and contradicts the STU-note application.

AutoFHIR reconciliation:
No source change was made. The current build-scoped CapabilityStatement source already contains the WG-approved application for this published issue, and adding a new machine-readable field now would require a new work-group design decision beyond the evidence for FHIR-28534.

Recommendation:
Keep this no-change audit commit. If FHIR-I wants machine-readable reverse-chain discovery in the current build, handle it with a current tracker or proposal that specifies the concrete CapabilityStatement/SearchParameter/extension semantics rather than inferring a new element from the R5 STU note.
