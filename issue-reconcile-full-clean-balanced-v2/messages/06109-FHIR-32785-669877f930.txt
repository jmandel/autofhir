FHIR-32785: Audit DeviceDefinition UDI type reuse

Issue request:
FHIR-32785 was a Published/Persuasive with Modification OO change request for R5. It asked to add structuredefinition-explicit-type-name to DeviceDefinition.packaging.udiDeviceIdentifier because two separately declared udiDeviceIdentifier BackboneElement types confused some code generators. The final resolution modified that request to reuse the already defined DeviceDefinition.udiDeviceIdentifier type, shown in the proposal as "see (udiDeviceIdentifier)".

Initial application:
The issue was applied before this reconciliation by git commit 48c1520a30dee406f5febe4f35fb614d6f1f0441, which changed source/devicedefinition/structuredefinition-DeviceDefinition.xml so DeviceDefinition.packaging.udiDeviceIdentifier uses contentReference="#DeviceDefinition.udiDeviceIdentifier" and removed the duplicate child element declarations. No prior AutoFHIR reconciliation commit with Issue-Reconcile-Key: FHIR-32785 was present on the combined branch.

Additional context:
DeviceDefinition is an active current-build resource in source/fhir.ini, so the structure definition source is in scope. OO HCP minutes on 2022-07-11 record the proposed "see (udiDeviceIdentifier)" approach after checking the content-reference solution with Lloyd and the submitter; OO HCP minutes on 2022-07-18 record the 6-0-0 motion adopting that proposal. The R5 published DeviceDefinition profile also has DeviceDefinition.packaging.udiDeviceIdentifier as a contentReference to #DeviceDefinition.udiDeviceIdentifier. Zulip searches for the issue key and DeviceDefinition UDI terms found no conflicting public discussion.

AutoFHIR reconciliation:
This audit commit makes no source change because the current in-scope source already implements the modified resolution: DeviceDefinition.packaging.udiDeviceIdentifier reuses DeviceDefinition.udiDeviceIdentifier through contentReference, and the duplicate packaging.udiDeviceIdentifier child definitions are absent. Adding the originally suggested explicit type-name extension now would be redundant at best and would not match the accepted modified resolution.

Recommendation:
Keep this audit commit as-is. No further FHIR-core source work is needed for FHIR-32785 unless OO later decides that generated code also needs an explicit type name in addition to the existing contentReference reuse.
