FHIR-13630: Restore ServiceRequest reason findings guidance

Issue request:
FHIR-13630 was a Published/Persuasive with Modification STU3 Orders and Observations issue asking Procedure and ProcedureRequest reasonReference to permit DiagnosticReport and DocumentReference, with ProcedureRequest.reasonReference comments clarifying that less-specific report or document references should contain findings that justify the follow-up request.

Initial application:
The issue was explicitly pre-applied in commit ab9c1bd7f48d954924628ca167dbc5a912901bcb, which changed ProcedureRequest.reasonReference to Reference(Condition | Observation | DiagnosticReport | DocumentReference) and added the requested DiagnosticReport/DocumentReference findings guidance. ProcedureRequest was later renamed/merged into ServiceRequest, and R4/R5 source history preserved the target types but the source rework that merged reasonCode and reasonReference into ServiceRequest.reason carried forward only the shorter reasonCode-style comment, losing the report/document-specific guidance.

Additional context:
source/fhir.ini lists servicerequest and procedure as active resources and records that ProcedureRequest was merged into ServiceRequest, so current reconciliation belongs in active ServiceRequest source rather than retired ProcedureRequest source. Current Procedure.reason already includes DiagnosticReport and DocumentReference and has a later FHIR-32510 comment decision specific to Procedure.reason consistency, so this commit does not alter Procedure. Later FHIR-47851 refined the same ServiceRequest.reason comment from referral to request and corrected the free-text path; this fix preserves that wording while restoring the FHIR-13630-specific guidance. FHIR-16681 renamed DiagnosticReport.codedDiagnosis to DiagnosticReport.conclusionCode, so the restored comment uses the current element name.

AutoFHIR reconciliation:
This commit updates source/servicerequest/structuredefinition-ServiceRequest.xml so ServiceRequest.reason again explains that DiagnosticReport references should contain findings in DiagnosticReport.conclusion and/or DiagnosticReport.conclusionCode, and that DocumentReference targets should contain clear findings language providing the relevant reason for the service request. It updates source/servicerequest/servicerequest-request-mapping-exceptions.xml with the matching Request mapping exception copy so the build-scope source remains synchronized.

Recommendation:
Keep this source fix. It restores substantive guidance approved by FHIR-13630 to the active ServiceRequest successor without changing later-approved target profiles or Procedure.reason wording.
