FHIR-7702: Mention PDF signature representations

Issue request:
FHIR-7702 was a Published/Persuasive with Modification Security WG change request for the Signature datatype. It asked whether Signature.blob could carry an image of an electronic signature, and resolved to add a MIME/content-type indicator, document XML DigSig and JWT usage, mention image/* and application/pdf for other signature reproductions, add XML and JWT examples, and update the documentation beyond XML DigSig only.

Initial application:
The issue was initially applied in git commit 3d8acf3aa0ccb15662c358df4bab917916002a4d, the SVN r5819 commit explicitly tagged #7702. That commit broadened Signature from XML-only to XML DigSig, JWT, and graphical signature forms and added a Signature.contentType MIME field. Later source history renamed Signature.blob to Signature.data, split Signature.contentType into Signature.targetFormat and Signature.sigFormat for FHIR-14175, and added current JWS examples on the active signatures page.

Additional context:
Signature is an active normative datatype in source/fhir.ini, and source/datatypes/signature.xml is the authoritative spreadsheet source for its element definitions. Current source already has Signature.sigFormat bound to MimeType, XML DigSig and JWS guidance, an XML Signature datatype example, and JWS examples on source/signatures.html. Later reconciliations for FHIR-14175, FHIR-47211, and FHIR-48679 keep the targetFormat/sigFormat split and valid MIME-type scoping, and do not supersede FHIR-7702's instruction that PDF reproductions of signatures should be mentioned.

AutoFHIR reconciliation:
Updated the active Signature.sigFormat definition to list application/pdf alongside image/* as an important MIME type for non-cryptographic signature representations, and fixed the adjacent XML DigSig spacing typo while touching the same sentence.

Recommendation:
Keep this source fix. It completes the remaining FHIR-7702 wording gap without changing the Signature model or MIME binding; no further core follow-up is needed for this issue unless the Security WG wants additional non-cryptographic signature examples.
