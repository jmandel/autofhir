FHIR-25252: Audit process-message response wording

Issue request:
FHIR-25252 was a Published/Persuasive R5 clarification request for $process-message. It asked the operation text to make clear that a message can be acknowledged with a simple HTTP status code, that a response Bundle rule applies only when a response payload is provided, and that synchronous use does not always require a response payload.

Initial application:
The explicit Jira-tagged application commit 6a94b0a3fdb24856076d09e0f991cf2ca11a3fc0 changed the MessageHeader $process-message OperationDefinition response content-type rule from always returning a message Bundle to returning one only "if not empty". That original commit did not remove the old "mandatory in this case" return-parameter wording, but later same-operation reconciliation on the combined branch, especially FHIR-27544, aligned the operation description and return documentation so the current source now states that zero or more response messages may be returned and that a synchronous response Bundle is present only when a response payload is needed.

Additional context:
MessageHeader is an active resource in source/fhir.ini, so source/messageheader/operationdefinition-MessageHeader-process-message.xml is in current build scope. The cited Zulip thread confirms the intended choices: bare HTTP success with no body, a message Bundle when a successful response payload is supplied, or an HTTP error with OperationOutcome detail. FHIR-I minutes for 2020-04-13 record the FHIR-25252 Persuasive vote. Later combined-branch commits FHIR-25465, FHIR-27544, and FHIR-34117 also touched nearby process-message/notification response wording and are already separately represented, so this seed should not duplicate their source changes.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current build-scoped source already says the $process-message response content type, if not empty, is a message Bundle; the return parameter is 0..1 and is documented as a response message only when synchronous messaging is used and a response payload is needed. No remaining source text says a synchronous response payload is mandatory.

Recommendation:
Keep this audit commit as-is. No further core source change is recommended for FHIR-25252 because the current OperationDefinition already conveys the approved clarification without adding redundant prose.
