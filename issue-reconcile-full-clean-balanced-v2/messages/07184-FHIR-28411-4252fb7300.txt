FHIR-28411: Audit Reference.type resource target rule

Issue request:
FHIR-28411 was Published / Persuasive for R5. It asked to clarify that when a Reference appears in a FHIR resource, Reference.type must identify a FHIR resource type from the ResourceType value set, while logical models may still use the extensible uri binding to refer to non-resource logical types.

Initial application:
The issue was applied by git 62a3b0888fa12f8761badaacbfa387daa2901324, "FHIR-28411 Clarify that Reference.type must be FHIR for references in FHIR instances." That commit updated source/references.html and source/datatypes/reference.xml to state the resource-only rule, but did not add an invariant. The contemporaneous Zulip thread records that an invariant was considered and rejected as too expensive for large resources, with validation expected to handle it instead.

Additional context:
source/fhir.ini lists Reference as an active datatype and normative artifact, so source/references.html and source/datatypes/reference.xml are in current build scope. Later related work kept the same interpretation: FHIR-32069 split concrete ResourceType from broader fhir-types/all-resource-type terminology, and the already-published FHIR-37791 reconciliation updated Reference.type to say it SHALL be a concrete, non-abstract resource type and that interfaces and abstract resources are invalid values.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/references.html already says that in resources, Reference SHALL point to another resource and Reference.type, if present, SHALL be a valid non-abstract resource, with non-resource content allowed only in logical models. Current source/datatypes/reference.xml also says Reference.type in resources SHALL be a concrete, non-abstract resource type and absolute URLs are only allowed for logical models.

Recommendation:
Keep this audit commit as-is. The current core source correctly reflects FHIR-28411; adding duplicative prose or a broad invariant would not improve the specification and would conflict with the recorded implementation concern about invariant evaluation cost.
