FHIR-39059: Audit Requirements hierarchy handling

Issue request:
FHIR-39059 was Published as Persuasive with Modification for FHIR-core Requirements. It asked for a parent relationship so Requirements content could be organized hierarchically, with final resolution text asking for a 0..1 Requirements.parent string and noting a canonical-plus-statement-key convention similar to statement.derivedFrom.

Initial application:
Core commit 9e8dc87830 applied the issue as Requirements.statement.parent, not as root Requirements.parent. Jira follow-up comments called out that mismatch, and the later extension-pack commit e38fb3c added the requirements-parent extension after Lloyd McKenzie noted the change could not be completed in core for R5.

Additional context:
Requirements is an active current-build core resource, but the current source does not define Requirements.parent. Instead, the current R6 Requirements source has the later statement-level relation model: Requirements.statement.partOf, with key/reference children and 0..* cardinality after the already-published FHIR-47739 and FHIR-47736 reconciliations. Those later decisions deliberately renamed statement.parent to partOf and clarified how statement-level hierarchy differs from derivedFrom. The extension-pack source remains the place where the FHIR-39059 parent extension lives outside this core checkout.

AutoFHIR reconciliation:
No core source files were changed. Adding a new root Requirements.parent in core now would go beyond the actual R5 application path, duplicate or conflict with the external extension solution, and ignore the later R6 statement-relation decisions already represented on the combined branch.

Recommendation:
Keep this external-repo audit commit as-is for core. If the requirements-parent extension needs correction or migration, handle that in HL7/fhir-extensions or through a new work-group decision; do not add an unapproved root Requirements.parent element to the current core source as part of this reconciliation.
