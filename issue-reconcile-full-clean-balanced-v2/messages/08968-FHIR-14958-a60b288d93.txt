FHIR-14958: Audit contentReference clarification

Issue request:
FHIR-14958 was a Published/Persuasive with Modification FHIR-I change request from STU3 asking to clarify how ElementDefinition.contentReference resolves, especially in derived profiles. The accepted resolution said contentReferences are defined only in specializations, cannot be changed by constrained profiles, always reference the non-constrained definition, and carry all ElementDefinition rules including bindings and invariants.

Initial application:
The issue appears to have been applied in git commit e06e2ce71eafaf039bc40297412622400a50b2d2, which added the current ElementDefinition.contentReference definition/comment text. The Jira comment cites an SVN application, and the git-svn history shows the FHIR-14958 application on the authoritative ElementDefinition datatype source.

Additional context:
ElementDefinition is in the active type hierarchy, and StructureDefinition is an active resource, so source/datatypes/elementdefinition.xml and source/structuredefinition/structuredefinition-StructureDefinition.xml are current-build inputs. FHIR-50509 later added the StructureDefinition constraint enforcing that contentReference appears only in specialization differentials, reinforcing the original FHIR-14958 rule. FHIR-39753 and later FHIR-57266/FHIR-57265 discuss recursive profiling behavior and possible contentReferenceProfile work; FHIR-39753 is already represented on the combined branch, while FHIR-57266/FHIR-57265 are later Resolved - change required work outside this seed's applied/published scope.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current ElementDefinition.contentReference text already says the target is an element defined elsewhere in the definition, that all referenced ElementDefinition rules carry across, and that contentReferences cannot be changed by constrained types. The current StructureDefinition source also contains the corresponding specialization-only constraint.

Recommendation:
Keep this audit commit as-is for FHIR-14958. Any future change to recursive contentReference profiling semantics should be handled under the later recursive-profiling/contentReferenceProfile issues rather than by re-opening this already-applied STU3 clarification.
