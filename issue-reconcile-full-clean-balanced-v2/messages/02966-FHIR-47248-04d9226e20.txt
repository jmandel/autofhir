FHIR-47248: Audit ServiceRequest.basedOn NutritionOrder support

Issue request:
FHIR-47248 was an Applied OO change request asking whether ServiceRequest.basedOn should also reference NutritionOrder, for example when a service request supports teaching a patient or family how to prepare foods for a specific diet. The persuasive-with-modification resolution was to try the whole Request pattern list, but if Reference(Request) did not work, to add NutritionOrder and handle other request resources through separate Jiras.

Initial application:
The issue was applied in ServiceRequest source history. Commit 8eed7c62a5 added NutritionOrder plus Request to ServiceRequest.basedOn, commit 91dcae7d0e then tried using only Reference(Request), and commit a910985a9b reverted to enumerated resource targets including NutritionOrder after build/CI evidence showed Reference(Request) was not valid for resource definitions.

Additional context:
FHIR-44992 records the broader tooling decision that Reference(Request) is not appropriate and that resource definitions should enumerate appropriate concrete request resources. The active source/fhir.ini includes ServiceRequest and NutritionOrder as current resources. The current ServiceRequest.basedOn target profile list includes NutritionOrder and several concrete request resources, and later same-family work such as FHIR-50001 and FHIR-54619 concerns additional concrete target alignment rather than reversing the FHIR-47248 NutritionOrder decision.

AutoFHIR reconciliation:
No source change was made. The current active ServiceRequest StructureDefinition already allows ServiceRequest.basedOn to reference NutritionOrder, and the separate mapping-exceptions file explicitly records the intentional divergence from the abstract Request pattern where ServiceRequest enumerates concrete targets instead of using Reference(Request).

Recommendation:
Keep this audit commit as-is. Do not replace the current enumerated targets with Reference(Request); future additions to ServiceRequest.basedOn should continue to be considered by separate Jira issues for the specific concrete resources.
