FHIR-23007: Audit mapping-language tree note

Issue request:
FHIR-23007 was a Published/Persuasive with Modification FHIR-I change request asking the mapping-language page to reduce confusion caused by describing FHIR mapping instances as DAGs. The accepted resolution was to add a note that FHIR resources are strict hierarchies, i.e., trees.

Initial application:
The issue was applied by commit 01e6c7f9a432144b5a8a7d4054feeacaad88284e, which inserted a note after the introductory DAG paragraph in source/mapping-language.html explaining that common contexts, including FHIR-defined types, do not use poly-hierarchies. Later same-day commit 0646c3096026cde98eca996d111806e36ed14572 corrected the wording to say that most contexts of use are strict mono-hierarchies (a.k.a trees), including FHIR specification types.

Additional context:
The referenced Zulip thread confirms the concern was that readers might infer FHIR resources were not trees; Grahame clarified that FHIR resources are trees while the mapping language can work with more general DAG-shaped data, and agreed that a parenthetical note about typical FHIR tree-shaped use would resolve the confusion. Current source/hierarchy.xml lists mapping-language.html as the Mapping Language page, so source/mapping-language.html is in build scope. Jira searches for nearby DAG/tree mapping-language issues found only FHIR-23007, and Confluence searches found no conflicting minutes.

AutoFHIR reconciliation:
This audit commit makes no source change because the current combined-branch source already preserves the approved clarification: it still describes the broader DAG capability, then immediately states that most contexts of use are strict mono-hierarchies (a.k.a trees), including FHIR specification types. Replacing the remaining DAG wording would conflict with the accepted modification and the Zulip clarification that the mapping language is broader than FHIR resource trees.

Recommendation:
Keep this audit commit as-is. No follow-up source work is recommended for FHIR-23007 unless the work group later decides to narrow the mapping language itself rather than clarify the typical FHIR use case.
