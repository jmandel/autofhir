FHIR-13177: Audit search parameter URL registry

Issue request:
FHIR-13177 was a Published/Persuasive FHIR-I change request raised against DSTU2 and applied for STU3. It asked the specification to list the URL for all SearchParameter definitions, with the search parameter registry suggested as the likely surface, because implementers needed the canonical SearchParameter URLs for IG CapabilityStatements.

Initial application:
The issue appears to have been applied directly by svn revision 12623, now git commit 504cee29eb827a96d411702c84b3059fa843cbc5, whose message says "#13177 - improve search parameter registry". That commit added the canonical URL pattern http://hl7.org/fhir/SearchParameter/[id] and added an Id column to source/searchparameter-registry.html, making each row's canonical URL derivable from the listed id.

Additional context:
source/hierarchy.xml includes searchparameter-registry.html under the RESTful API pages, so source/searchparameter-registry.html is a current build-scope narrative page. The current registry source still carries the canonical URL pattern, Id column, and links to generated XML/JSON downloads. The relevant Zulip thread confirms the request was specifically about canonical URLs such as http://hl7.org/fhir/SearchParameter/Organization-name. A later same-family issue, FHIR-34088, requested direct canonical URL exposure in resource/common search-parameter tables and is already represented on the combined branch by commit 3c1993a14883b739545e3fc24d50ce96464c82da, so this reconciliation should not duplicate that later source change.

AutoFHIR reconciliation:
No source change was made. The current registry still satisfies the FHIR-13177 request through the canonical URL rule plus per-row ids, and the generated search-parameters.json/XML downloads expose the full canonical URL field for each SearchParameter. Adding a redundant full URL column to the registry would be optional presentation polish rather than a necessary correction.

Recommendation:
Keep this no-change audit commit. Reviewers should preserve the existing registry URL pattern and download links; any future desire for literal full URLs in every registry row should be handled as a new presentation decision, not as unfinished FHIR-13177 work.
