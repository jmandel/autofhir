FHIR-36051: Audit recursive include guidance

Issue request:
FHIR-36051 was a Published/Persuasive with Modification R5 clarification for CapabilityStatement. It asked how a requirements CapabilityStatement should declare a recursive include when the recursive step belongs to a resource type that otherwise has no required interaction. The accepted outcome was that the first approach is allowed: list the include values, including those from the recursively reached resource, under the "root" resource type, while noting this level of detail is mostly useful for conformance expectations and may not be exposed by production servers or real-time clients.

Initial application:
The issue was applied in git commit 3b6e443e496f907801189a895636c924267804eb and merged by 137772c14c1208a817da97bc19068b3fab5d274f as HL7/fhir#2211. That application replaced the short searchInclude and searchRevInclude comments with explicit guidance and an example showing CarePlan searchInclude values that include both CarePlan:activity-reference:DeviceRequest and DeviceRequest:device under CarePlan. No prior Issue-Reconcile-Key audit commit for FHIR-36051 was present on the combined branch.

Additional context:
CapabilityStatement is an active current-build resource in source/fhir.ini, and source/capabilitystatement/structuredefinition-CapabilityStatement.xml is the authoritative source for its element definitions. Later maintenance updated the same comment to current search terminology, changing recursive/_include:recurse to iterative/_include:iterate, and a later wildcard clarification added text without changing the FHIR-36051 rule. The original Zulip thread and the 2022-04-25 FHIR-I minutes align with the Jira disposition.

AutoFHIR reconciliation:
This is an empty no-change audit commit. The current source already states that support for iterative (a.k.a. recursive) _include is communicated by listing the iterative include values supported by the server in CapabilityStatement.rest.resource.searchInclude for the "root" resource type, and the current example lists DeviceRequest:device as a CarePlan searchInclude. searchRevInclude points readers to the same comment. That satisfies the issue without adding redundant narrative or a separate DeviceRequest interaction requirement.

Keep this audit commit as-is for FHIR-36051. No source follow-up is needed for this issue; broader feature work such as CapabilityStatement2 include feature modeling or the later wildcard clarification should remain separate issue decisions.
