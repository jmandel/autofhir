FHIR-27808: Audit recordedDate clarification

Issue request:
FHIR-27808 was a Published/Persuasive R5 Patient Care clarification for Condition.recordedDate. It asked to add a comment saying that when a sending system provides recordedDate, the receiving system should preferably preserve it, and when the sending system does not provide it, the receiving system may assert its own system-generated date.

Initial application:
The issue was initially applied in git commit eef7e67022, which added J#27808 to the Condition.recordedDate committee notes and inserted the requested comment in source/condition/structuredefinition-Condition.xml. Later git commit 7fc5cd4fe9, for FHIR-34392 and FHIR-34394, retained the preservation/defaulting rule while adding the onset-proxy rationale, changing the fallback wording to the receiving system's receipt timestamp, and clarifying the contrast with Condition.recorder.

Additional context:
Condition is an active resource in source/fhir.ini, so source/condition/structuredefinition-Condition.xml is current build-scope source. Later Published Patient Care issues FHIR-34392 and FHIR-34394 explicitly built on FHIR-27808 and established the current recordedDate comment text. FHIR-34395 temporarily struck the recorder contrast when recorder was replaced by participant, but a later already-published combined-branch reconciliation for FHIR-34394 restored that contrast after recorder returned. FHIR-33180 is related background for the condition-assertedDate extension in the FHIR Extension Pack; it clarifies assertedDate versus recordedDate outside this core source checkout and does not require a core Condition.recordedDate change.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current Condition.recordedDate short text and comment already communicate the FHIR-27808 rule as later refined: recordedDate is the first recorded date, receivers should preserve a provided sending-system recordedDate, and if no sending-system recordedDate is provided the receiving-system receipt timestamp may be used as the recordedDate.

Recommendation:
Keep this audit commit as-is. No FHIR core source edit is needed for FHIR-27808; future work on assertedDate boundaries should be handled through the FHIR Extension Pack or the specific later Jira keys, not by rewording the current core Condition.recordedDate comment redundantly.
