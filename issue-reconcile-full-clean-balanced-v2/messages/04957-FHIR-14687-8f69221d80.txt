FHIR-14687: Audit ConceptMap unmapped clarification

Issue request:
FHIR-14687 was a Published/Not Persuasive with Modification Vocabulary issue raised against the STU3 ConceptMap resource. It questioned how ConceptMap.group.unmapped.url could be a canonical URL for another map and whether it was meant to be used when a source concept had an explicit target equivalence of unmatched. The approved resolution said the element references another ConceptMap to use when there is no mapping entry, clarified that unmapped processing does not include explicitly unmatched concepts, and requested a section explaining unmapped behavior.

Initial application:
The issue was applied by d75acd989aa64eb9de7ae6a439abe0b3377ecfdd, the git-svn commit for revision 14637, which added the Handling Unmapped Codes section to source/conceptmap/conceptmap-notes.xml and changed the then-active ConceptMap spreadsheet definitions for group.unmapped and group.unmapped.url. The historical application explained the other-map use case and stated that unmapped is not used when a matching code has an unmatched/disjoint relationship.

Additional context:
ConceptMap is an active current resource in source/fhir.ini, assigned to the Vocabulary work group. The old spreadsheet source is no longer the active current source, and later R5/R6 work renamed ConceptMap.group.unmapped.url to ConceptMap.group.unmapped.otherMap, replaced the old unmatched equivalence terminology with relationship/noMap semantics, and updated the unmapped-mode descriptions. FHIR-32545 is the directly related Published issue that renamed url to otherMap; FHIR-22100 is a later Published clarification of the same unmapped-mode family and is already represented on the combined branch. The Jira-linked April 2018 Zulip thread confirms the intended other-map fallback use case and revealed no conflicting decision; Confluence searches found no FHIR-14687 references.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active source already preserves the approved clarification: conceptmap-notes.xml has a Handling Unmapped Codes section, the other-map row says to use the map identified by the canonical URL in otherMap, structuredefinition-ConceptMap.xml defines ConceptMap.group.unmapped as default behavior when there is no mapping target and says it is ignored for relationship = not-related-to or noMap = true, and ConceptMap.group.unmapped.otherMap is a canonical reference to another ConceptMap.

Recommendation:
Keep this empty audit commit as-is. No follow-up core source edit is needed for FHIR-14687 because the current build-scope ConceptMap source conveys the requested behavior under the current R6 names and later related decisions.
