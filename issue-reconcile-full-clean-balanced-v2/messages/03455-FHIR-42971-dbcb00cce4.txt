FHIR-42971: Audit HTTP Date header correction

Issue request:
FHIR-42971 was Applied/Persuasive for FHIR-core HTTP after FHIR-I voted 9-0-0 on 2023-10-30. The issue reported that the HTTP page incorrectly said a server default timezone SHOULD be returned in the HTTP Date header, which conflicts with HTTP date syntax requiring UTC/GMT, and its resolution said to remove that text and document server timezone discovery through the timezone extension on CapabilityStatement.meta.

Initial application:
The issue was already applied in source history by Gino Canessa's FHIR-42971 commits, especially b811010c8b, which removed the Date-header timezone sentence from source/http.html and added a Timezone Discovery section to source/capabilitystatement/capabilitystatement-notes.xml, followed by 8e74a757dd, which only adjusted wording in the same HTTP replacement paragraph. Current source retains both substantive changes.

Additional context:
The triggering Zulip thread confirms the HTTP Date header cannot carry a local timezone and that FHIR did not intend to rely on forwarded non-HTTP date syntax. FHIR-I minutes for 2023-10-30 record the approved rationale that the timezone extension can be used on CapabilityStatement.meta for a server's time zone. The timezone extension is now maintained in the FHIR Extension Pack and explicitly includes Meta as an allowed context, so the core source's external extension link is appropriate. Historical FHIR-16434 explains why the invalid sentence had previously been moved to the return-content section, but FHIR-42971 superseded that guidance.

AutoFHIR reconciliation:
This commit intentionally makes no source change. source/http.html no longer contains the invalid default-timezone Date-header guidance, and source/capabilitystatement/capabilitystatement-notes.xml now tells implementers to indicate a server default timezone with the timezone code extension on CapabilityStatement.meta.

Recommendation:
Keep this audit commit as-is. No additional core FHIR source change is needed unless the work group later wants stronger or more detailed CapabilityStatement conformance language; that would be a new decision rather than a correction for FHIR-42971.
