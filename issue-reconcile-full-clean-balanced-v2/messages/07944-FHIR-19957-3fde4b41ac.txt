FHIR-19957: Audit Subscription REST-hook notification method

Issue request:
FHIR-19957 was a Published/Persuasive FHIR-I change request for FHIR-core Subscription, raised against STU3 and applied for R5. It asked to resolve confusing Subscription text that mixed generic "post/posting" language with REST-hook guidance suggesting payload-bearing notifications should be sent as an Update operation/HTTP PUT.

Initial application:
No commit explicitly names FHIR-19957, but the issue appears to have been applied during the R5 Subscription redesign. Commit 3be1bbb7 updated source/subscription/subscription-notes.xml after the July 2019 vote, replacing the old full-payload REST-hook sentence that told servers to forward matching resources as an Update operation (PUT) with wording that describes create, update, or delete operation metadata inside the notification bundle. FHIR-23738's R5 placeholder comment later explicitly listed FHIR-19957 as clarified at subscription.html#rest-hook, saying REST-Hook uses HTTP POST.

Additional context:
Subscription, SubscriptionStatus, and SubscriptionTopic are active current-build resources in source/fhir.ini. The current REST-hook source states that clients use rest-hook to receive notifications via HTTP/S POST and that the server POSTs a notification Bundle to the client's endpoint. The broader Subscriptions Framework separately says clients may request the Subscription resource via HTTP POST or HTTP PUT under normal FHIR create/update rules, so create/update of the Subscription resource is no longer conflated with outbound notification delivery. Zulip R5 Feedback discussion recorded the FHIR-19957 rest-hook clarification as part of the merged R5 Subscription work, and Confluence search found no contrary work-group record.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current source already conveys the reconciled R5 rule: REST-hook notification delivery is an HTTP POST of a subscription-notification Bundle, while any POST/PUT wording about a Subscription resource is confined to standard client create/update interactions.

Recommendation:
Keep this no-change audit. Do not reintroduce the older direct Update-operation/PUT framing for payload-bearing notifications; future edits should preserve the distinction between notification transport and Bundle.entry.request metadata or Subscription resource create/update interactions.
