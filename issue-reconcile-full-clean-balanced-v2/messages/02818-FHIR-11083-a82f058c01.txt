FHIR-11083: Clarify OAuth authorization wording

Issue request:
FHIR-11083 was a Published FHIR-core Security change request, resolved Persuasive with Modification, asking the security page to stop describing OAuth as an authentication protocol and to say that OpenID Connect may be used to authenticate users while OAuth 2.0 (or later) may be used to authorize access.

Initial application:
No git commit explicitly mentions FHIR-11083 or GF#11083. The closest historical application appears in security narrative work: commit 95ee245e72e4bd1ac09824738ae7b5f7519239ef added OpenID Connect authentication wording but still kept OAuth as something that could authenticate and/or authorize users, and commit d417c5d674a4a6b7e4af8d9ef15b7d55d3b4d3e8 later moved that stale OAuth authentication sentence into the Access Control section. A separate already-published AutoFHIR commit for FHIR-16532 fixed the top-level security checklist authentication bullet on the combined branch, but it did not remove the remaining OAuth-as-authentication wording elsewhere.

Additional context:
Current source/security.html is a root source page listed in source/hierarchy.xml and linked throughout the spec. The safety checklist is also a root source page, and source/fhir.ini actively includes source/codesystem/codesystem-safety-entries.xml as safety-entries. source/fhir.ini also lists CapabilityStatement and MessageHeader as active resources, so the PHR CapabilityStatement example and $process-message OperationDefinition are in current build scope. Later security issues, including FHIR-16532 and FHIR-34362, support keeping OpenID Connect/authentication guidance separate from OAuth-based authorization and access-token enforcement. Zulip and Confluence searches found no human discussion that reverses or narrows FHIR-11083.

AutoFHIR reconciliation:
This commit updates current source guidance that still implied OAuth authenticates users. It changes the Access Control OAuth recommendation to OAuth 2.0 (or later) authorization, updates the security summary's OAuth BCP wording, aligns the safety narrative and safety code-system checklist entry with OAuth 2.0 authorization and OpenID Connect authentication, changes the EHR-FM mapping to point authentication at OpenID Connect or another authentication protocol, and changes current CapabilityStatement and MessageHeader examples so OAuth 2.0 is described as authorization/security protection rather than an authentication service.

Recommendation:
Keep this source fix. It completes the published FHIR-11083 distinction in active current source without changing unrelated client-authentication mechanisms or out-of-build proposal notes.
