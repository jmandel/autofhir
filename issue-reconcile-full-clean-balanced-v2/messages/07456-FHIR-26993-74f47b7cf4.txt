FHIR-26993: Audit Questionnaire enableWhen clarification

Issue request:
FHIR-26993 was a Published/Persuasive FHIR-core Questionnaire clarification for R5. It asked that Questionnaire.item.enableWhen no longer read as if multiple enableWhen conditions are always ORed, and instead clearly distinguish multiple enableWhen clauses governed by enableBehavior from a single referenced question that has multiple answers.

Initial application:
The issue appears to have been applied in commit 1809c5dcba1f414b2beba75c38296e8c43857c5d, which the Jira comment records even though the commit subject says FHIR-26933. That patch replaced the old "treat enableWhens as OR" comment with explicit enableBehavior wording and the multiple-answer rule. A same-area Published clarification, FHIR-26312, later committed as 5665c38fcfbab7630b6f50f421947fcf41581117, also added the multiple-answer rule to Questionnaire.item.enableWhen.answer[x].

Additional context:
Questionnaire is active in the current build through source/fhir.ini. The originating Zulip thread shows the confusion was exactly between enableBehavior for multiple enableWhen clauses and matching any answer of a repeating question, and SDC minutes record the Persuasive vote for FHIR-26993. The same thread also discussed the separate que-12 threshold correction tracked by FHIR-26831, which already has its own combined-branch audit commit. The current comment still uses the legacy phrase "this extension", but the approved enableBehavior and multiple-answer semantics are present and that word does not change the conformance meaning requested by this tracker.

AutoFHIR reconciliation:
No source change was made. The active Questionnaire StructureDefinition already states that multiple enableWhen repetitions are interpreted by enableBehavior, that any matching answer satisfies an enableWhen against a multi-answer question, and that enableBehavior must be present when more than one enableWhen is supplied.

Recommendation:
Keep this audit commit as-is. The seed issue is already correctly applied in the current build; any desire to replace the legacy word "extension" with "element" should be handled as a small editorial cleanup rather than as a required reconciliation for FHIR-26993.
