FHIR-32883: Audit dateTime precision clarification

Issue request:
FHIR-32883 was a Published/Persuasive R4 clarification request for the primitive dateTime description after implementers read the listed formats as excluding fractional seconds. The approved resolution was to update the description to indicate that milliseconds are optionally allowed for the time part of dateTime.

Initial application:
Commit d621ab0bda61832d87d16ee8fa98261bf403a9da applied FHIR-32883 as part of an MnM batch by adding "Milliseconds are optionally allowed" to the dateTime row in source/datatypes.html. It also adjusted the primitive time example to include seconds, but the Jira-tagged source change for this issue was the dateTime precision sentence.

Additional context:
The datatype page is active in the current build through source/fhir.ini's type-page routing, and current source/datatypes.html still carries the FHIR-32883 dateTime sentence alongside later approved edits for ISO 8601 links and timezone-offset wording. The linked Zulip thread confirms the confusion was that the dateTime format examples looked complete and whole-second-only; MnM minutes record the Persuasive 4-0-0 vote. Later precision issue FHIR-42984 clarified sub-millisecond precision for instant, whose row says instant is a constrained dateTime, but it did not reopen or supersede the FHIR-32883 dateTime wording.

AutoFHIR reconciliation:
Made no source change. The current active dateTime narrative already includes the WG-approved optional-milliseconds clarification, so adding redundant or broader prose for dateTime or the separate time primitive would go beyond the FHIR-32883 final resolution.

Recommendation:
Keep this audit commit as-is. If the work group wants the time primitive row or dateTime row to explicitly say "fractional seconds" or "sub-millisecond precision," that should be handled as a separate clarification because FHIR-32883 was applied according to its final Published resolution.
