FHIR-34082: Audit Questionnaire item text string datatype

Issue request:
FHIR-34082 was a Published/Persuasive FHIR-core Questionnaire change request for R5 asking to change Questionnaire.item.text from markdown back to string. The resolution cited alignment with ElementDefinition.label, non-technical users, and the processing burden of markdown for every questionnaire item, and said the existing markdown extension should be used where markdown is needed.

Initial application:
The immediate prior state came from FHIR-20585, applied by commit 5399a4a442ddcd037451eaeceaf3b5a55ec7943b, which changed Questionnaire.item.text from string to markdown. FHIR-34082 was then applied by commit 680c4dae1c8438f0d9726a9ec952a1410b09c7e9, changing source/questionnaire/structuredefinition-Questionnaire.xml back to string. QuestionnaireResponse.item.text remained string, so the alternative propagation concern in the issue description did not require a source change once markdown was rejected.

Additional context:
The #questionnaire Markdown Zulip thread records the same rationale: Brian Postlethwaite identified FHIR-20585 as the original tracker, objected to markdown processing overhead on every item, and noted the QuestionnaireResponse.item.text mismatch. FHIR SDC minutes on 2021-10-07 record that FHIR-34082 would be discussed on Zulip; minutes on 2021-10-21 record the issue as Persuasive. fhir.ini confirms Questionnaire and QuestionnaireResponse are active resources in the current build.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current authoritative XML has Questionnaire.item.text type string and QuestionnaireResponse.item.text type string; the checked-in SVG diagrams also show string for both item.text rows. The current source therefore already satisfies FHIR-34082 in current build scope.

Recommendation:
Keep this audit commit as-is. No core FHIR follow-up is needed for FHIR-34082 unless a future work-group decision changes the rich-text strategy; such a future change should be tracked separately rather than reinterpreting this issue.
