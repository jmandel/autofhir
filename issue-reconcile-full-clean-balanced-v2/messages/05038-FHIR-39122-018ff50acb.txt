FHIR-39122: Audit _maxresults search limit

Issue request:
FHIR-39122 was Published/Persuasive for R5 and asked whether a client can tell a server it only needs the first few search results without requiring the server to prepare later pages. The accepted resolution was to add a search-result parameter, ultimately named _maxresults in the applied source.

Initial application:
The issue was applied in git commit 31975a04ec83f6394a0d5e542fb36069f782e9d6, which added _maxresults to source/search.html's contents navigation, search-result parameter table, Limiting Total Result Size section, and summary table. The current source retains those entries.

Additional context:
The Zulip thread linked from Jira distinguished _count as page size from a total-result limit and considered names and semantics. FHIR-I minutes on 2023-02-13 record the motion to add a parameter, with _maxResults suggested as the name, and Jira records a 16-0-1 Persuasive vote. The current source uses the lower-case _maxresults spelling that was implemented and published in R5/current CI; search parameter names are case-sensitive, but the spec's published parameter spelling is consistently lower-case. Later FHIR-46763 clarified the same section so _maxresults applies only to match entries, and that related reconciliation is already on the combined branch.

AutoFHIR reconciliation:
This commit makes no source change because the build-scoped search page already defines _maxresults as the total match-result limit and distinguishes it from _count page size. Adding more prose or renaming the parameter would conflict with the applied and published source rather than complete the seed request.

Recommendation:
Keep this empty audit commit as-is. No follow-up is needed for FHIR-39122 in core; any future changes to _maxresults should be handled by later tickets such as FHIR-46763 or new work-group decisions.
