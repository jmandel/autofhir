FHIR-26677: Audit Request.status alignment

Issue request:
FHIR-26677 was Published/Persuasive for R5 and reported that the Request Pattern's Request.status definition and state machine used status names that did not match the bound Request Status value set expansion, especially suspended/cancelled versus on-hold/revoked.

Initial application:
The issue was applied in git commit 2ed04c432f777fa8be8e47a7596c8c36dc0ac434, which Lloyd McKenzie cited in the Jira comment. That commit updated the active Request pattern spreadsheet and state-machine diagram source so the Request.status short list and diagram labels used on-hold and revoked rather than the stale suspended/cancelled names.

Additional context:
source/fhir.ini lists request as an active logical pattern, so source/request and the referenced Request state-machine image feed the current build. Later FHIR-48861 added the higher-level ended RequestStatus parent for completed/revoked, and the existing FHIR-48861 reconciliation on the combined branch completed that application in the current RequestStatus CodeSystem and Request.status short list. Existing FHIR-20563 reconciliation on the combined branch also cleaned up remaining active request-status prose that still referred to suspended/cancelled. The originating Zulip workflow thread identified the same value-set-versus-definition mismatch and did not add a conflicting requirement.

AutoFHIR reconciliation:
This is an empty no-change audit commit. Current source/request/codesystem-request-status.xml, source/request/valueset-request-status.xml, source/request/request-spreadsheet.xml, source/request/request-spreadsheet-notes.xml, and images/request-state-machine.svg are already aligned with the current RequestStatus value set and no longer expose suspended/cancelled as Request status names. The only remaining suspended text in the Request spreadsheet is a v3 ActStatus mapping for on-hold, not a FHIR RequestStatus code.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-26677; future RequestStatus changes should be handled under their own Jira keys so the value set, Request pattern short list/prose, and state-machine diagram remain aligned.
