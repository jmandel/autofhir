FHIR-34316: Align AdverseEvent effect ModelInfo

Issue request:
FHIR-34316 was a Published/Persuasive with Modification FHIR-core Patient Care change request for R5 AdverseEvent. It asked that AdverseEvent.resultingCondition cover consequences represented as Observation as well as Condition, and the final resolution renamed the element to resultingEffect and supported Reference(Condition | Observation).

Initial application:
The issue was initially applied by cd56c64aad2d9729209bf8268b4d6d9ee494714e, which renamed AdverseEvent.resultingCondition to resultingEffect in the resource StructureDefinition and added Observation as a target, and by 03c97a14f97d78ce86c5a466a31fa5e17037585f, which renamed the AdverseEvent search parameter. Current AdverseEvent source and search parameters already use resultingEffect, but the active FHIR ModelInfo Library still exposed the old resultingCondition property.

Additional context:
FHIR-48833 later made AdverseEvent.resultingEffect a CodeableReference with an example binding to clinical-findings, so current reconciliation must preserve the current CodeableConcept-or-Reference surface rather than reverting to a plain Reference. source/fhir.ini keeps AdverseEvent and Library active, and source/library/list-Library-examples.xml registers Library/library-fhir-model-definition as the FHIR Model Definition example. The fhir.ini R4-to-R6 resultingCondition alias is intentional historical mapping, not stale current element metadata.

AutoFHIR reconciliation:
This commit updates the active FHIR ModelInfo Library so AdverseEvent exposes resultingEffect as a list of CodeableConcept-or-Reference choices and no longer exposes resultingCondition. It also resynchronizes the embedded Library/library-fhir-model-definition attachment from the raw modelinfo content.

Recommendation:
Keep this source fix. It completes the remaining current-build computable metadata gap for FHIR-34316 while respecting the later FHIR-48833 CodeableReference decision. Broader cleanup of unrelated stale AdverseEvent ModelInfo fields should be tracked separately rather than expanded into this reconciliation.
