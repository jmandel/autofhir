FHIR-7543: Audit include iteration behavior

Issue request:
FHIR-7543 was Published/Persuasive for FHIR-core-search after the 2015 May ballot. It asked FHIR-I to decide the transitiveness of _include and _revinclude; the resolution was to define a :recurse modifier for _include/_reverseInclude, make non-recursive behavior the default, and allow servers to limit recursion depth.

Initial application:
The issue appears to have been applied by git-svn commit fbaf29fb043878886a33392fb9a1017135ef9fed, matching the Jira comment that cites svn revision 5813. That commit changed source/search.html to add _include:recurse examples, state that recursive inclusion only happens when :recurse is supplied, and state that servers may limit recursive evaluation.

Additional context:
Later final FHIR-core issue FHIR-13602 renamed the modifier from :recurse to :iterate, corrected the examples, clarified that default include processing applies only to the initial search matches, and reiterated that iterative search is resource-intensive and not the default. The current combined branch already contains an FHIR-13602 reconciliation commit, so this FHIR-7543 audit does not publish a second decision for that later issue. Later _include:iterate issues such as FHIR-31939, FHIR-46101, and FHIR-46944 further clarified wording without reversing the FHIR-7543 rule.

AutoFHIR reconciliation:
No source change is needed. The active FHIR-core search page source/search.html now expresses the required behavior using the later-approved :iterate terminology: _include and _revinclude are invoked only on the initial result set by default, :iterate repeats them on included resources, servers can choose how deeply to iterate, and iterative search is not the default behavior. Reintroducing :recurse would conflict with the later FHIR-13602 rename.

Recommendation:
Keep this no-change audit commit. The current specification already satisfies FHIR-7543 when read with the later rename and clarifications; no follow-up is needed for the core source.
