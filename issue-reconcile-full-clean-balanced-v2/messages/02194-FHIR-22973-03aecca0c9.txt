It asked why the then-current con-4 abatement invariant blocked abatement[x] when verificationStatus was entered-in-error and resolved to update the abatement invariant to allow clinicalStatus to be inactive, resolved, remission, or not valued; remove the old con-5 rule prohibiting clinicalStatus when verificationStatus is entered-in-error; and adjust the old con-3 guidance about clinicalStatus.

Initial application:

Additional context:
FHIR-29409 was a later Published / Persuasive with Modification Patient Care decision for R5 requiring Condition.clinicalStatus 1..1 and replacing the old conditional clinicalStatus invariant with guidance about the unknown clinicalStatus code. In the current source, Condition remains an active build resource in source/fhir.ini, clinicalStatus is 1..1, the abatement invariant is now keyed con-3, and con-4 is a later bodySite/bodyStructure rule from FHIR-39630. The old con-5 prohibition is absent from current Condition source. Community searches found no FHIR-22973-specific Zulip or Confluence evidence that changes the Jira/source conclusion.
