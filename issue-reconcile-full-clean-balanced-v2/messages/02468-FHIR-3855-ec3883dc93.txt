FHIR-3855: Audit search-parameter naming guidance

Issue request:
FHIR-3855 was a Published/Persuasive with Modification MNM DSTU1 change request asking for consistent search-parameter naming. The final decision was that search-parameter names should be lowercase and separated by dashes, with committee discretion for domain-recognized compound words, and that the convention should be documented with tool hinting.

Initial application:
The issue was applied before this reconciliation by git-svn commit 4d8804de58df42259a65c735bdb95f309174fc66, whose subject was "#3855 - check search params for style consistency". That commit added source/spelling dictionaries, passed the source folder into the historical ResourceValidator, and added a search-parameter style-guide hint that split names on hyphens and checked each word against the dictionaries. The current checkout no longer has that old Java validator path, but the spelling dictionaries remain in source/spelling.

Additional context:
SearchParameter is an active current resource in source/fhir.ini. Later R6 work refined the same naming family: FHIR-34866 added SearchParameter.aliasCode and formal SearchParameter naming conventions, and FHIR-45349 added enforceable constraints prohibiting '.', '$', '|', and whitespace in SearchParameter.code and aliasCode. The current source now states that HL7-defined search parameters use lowercase letters with hyphens for multi-word parameters and that SearchParameter.code/aliasCode should use only lowercase ASCII characters and hyphens for maximum compatibility. A current scan found no ordinary SearchParameter.code values with spaces, '.', '$', '|', or uppercase letters; the remaining underscore-style exceptions are special system parameters or later issue-specific search codes that should not be renamed under this DSTU1 audit without their own compatibility decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative source already documents the lower-hyphen convention and contains machine-readable constraints for invalid separator characters, while later aliasCode work provides the compatibility mechanism for any future preferred-code cleanups.

Recommendation:
Keep this no-change audit commit as-is. Do not use FHIR-3855 to rename current normative search parameter codes; any remaining code-specific naming cleanup should be handled through focused later tickets such as the FHIR-34866 family with aliasCode/backward-compatibility review.
