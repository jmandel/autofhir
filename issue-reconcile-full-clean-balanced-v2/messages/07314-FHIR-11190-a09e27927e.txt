FHIR-11190: Audit DiagnosticRequest stage rename

Issue request:
FHIR-11190 was Published/Persuasive for the OO DiagnosticRequest tracker raised in DSTU2. It said DiagnosticRequest.stage was a poor name and, by reference to duplicate target FHIR-12052, requested changing "stage" to required code element "intent" with proposal/plan/order semantics and a usage note allowing resource-specific codes to map back to proposal, plan, or order.

Initial application:
There is no discovered source commit explicitly naming FHIR-11190. FHIR-12052, the duplicate target cited by FHIR-11190, records implementation at svn @10160; git commit 6cab91a3e08dbbcd0ccdff56628ddcaef60dde30 is that imported commit and changed the Request logical model from Request.stage to Request.intent, code binding RequestIntent, and added the requested mapping usage note. Later commit e9a85998b0dbe25b03abd0045bfa30e67ce56b36 merged DiagnosticRequest into ProcedureRequest and shows the successor DiagnosticRequest element as DiagnosticRequest.intent rather than stage.

Additional context:
DiagnosticRequest is not an active current-build resource. The active successor source is ServiceRequest in source/fhir.ini, and current ServiceRequest.intent is 1..1 code, modifier, required-bound to ValueSet/request-intent. The Request pattern still carries the FHIR-12052 usage note, and the request-intent code system represents order subtypes such as original-order and reflex-order under order. Searches found no remaining current source path for DiagnosticRequest.stage, DiagnosticRequest.intent, ServiceRequest.stage, or Request.stage, and no Zulip or Confluence evidence that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current build already embodies the requested rename and mapping guidance through the active ServiceRequest successor, the Request pattern source, and the request-intent terminology.

Recommendation:
Keep this no-change audit. Any future cleanup of ServiceRequest.intent's local wording or newer request-intent code details should be handled under a current tracker, not by reopening this DSTU2 DiagnosticRequest.stage rename.
