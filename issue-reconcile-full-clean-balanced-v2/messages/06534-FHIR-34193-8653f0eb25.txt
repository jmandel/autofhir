FHIR-34193: Audit versioned-update clarification

Issue request:
FHIR-34193 was Published/Persuasive for R5 and asked to clarify the HTTP Support for Versions text and the versioning-policy terminology definition for versioned-update. The requested clarification replaced the ambiguous server-side phrase "Version ID must be correct for updates" with "supports version-aware updates (server) or will be specified (If-match header) for updates (client)".

Initial application:
The issue was applied by git commit c783e76c54e9e52068af62d0cf99e5c122763459, which changed both source/http.html and source/capabilitystatement/codesystem-versioning-policy.xml to the requested wording. The current source still has that wording, and the versioning-policy ValueSet composes the CodeSystem that contains the updated definition.

Additional context:
The linked Zulip thread confirms the reported ambiguity: a server that supports version-aware updates through If-Match should be able to declare versioned-update without separately checking client-supplied Resource.meta.versionId. FHIR-11259 is historical background because it introduced the three versioning support levels and the earlier explanatory wording that FHIR-34193 later clarified. Jira and Confluence searches found no later FHIR-core applied or published decision that reverses this clarification.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active HTTP page and the authoritative versioning-policy CodeSystem already express the Published FHIR-34193 clarification, and the ValueSet page is fed by that CodeSystem rather than a separate stale definition.

Recommendation:
Keep this audit commit as-is. If a future work group wants versioned-update to assert stricter server enforcement semantics, that should be handled by a new Jira because it would be a policy change beyond the FHIR-34193 clarification.
