FHIR-16447 was a Published/Persuasive FHIR-core HTTP change request for STU3. That original application did not add the AccessDenied cross-reference in the delete section.

Additional context:
source/http.html is the active RESTful API page in the current build through source/hierarchy.xml. Later FHIR-23996 work in git commit 639dbcd2848776be444488fe66b23438c581256d clarified deleted-resource 410 behavior and added the AccessDenied link in the delete interaction; the later FHIR-23996 reconciliation commit 39c41ba3da50ce9e29f75c44e72c7108032c5007 completed matching read/vread wording. FHIR-16460 separately fixed the HTTP status-code summary table note to point at AccessDenied. Direct Zulip and Confluence searches for FHIR-16447 found no conflicting community record.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current delete section already says that deleted resources disappear from search, that 410 is used when the server wishes to indicate deletion, that policy/security may require another AccessDenied response, that successful deletion may return 200/204 or 202 when the server is non-committal, and that delete support is discretionary based on policy and business rules.

Recommendation:
Keep this audit commit as-is. The current source satisfies the published seed decision when read with the later deleted-resource and AccessDenied clarifications, and adding more local prose would be redundant.
