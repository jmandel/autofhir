FHIR-13685: Audit leap-second datatype support

Issue request:
FHIR-13685 was a Published/Persuasive STU3 FHIR-core datatypes issue asking that time values support leap seconds by allowing a seconds field value of 60 rather than only 0-59. The accepted resolution was to revise the dateTime and timestamp regexes to permit "60" seconds and to add warning text about handling leap seconds.

Initial application:
The issue appears to have been applied in git-svn commit f2b3f28b2ff336fda895e176b2bdb2690ade688b, whose subject explicitly says "#13685 and #13684: validation improvements to date/time regex (leap seconds, year 0)" and whose patch changed the primitive regexes to allow `([0-5][0-9]|60)` in dateTime and time-related validation/generation code. The Jira comment records svn revision 12460, matching that commit.

Additional context:
The current build-scope primitive datatype source is source/datatypes/primitives.xml, with source/fhir.ini routing primitive datatype pages to datatypes and source/datatypes.html rendering the regex placeholders. The current source also includes later dateTime regex refinements and a related AutoFHIR FHIR-14094 audit commit on the combined branch, but those later decisions did not remove leap-second support.

AutoFHIR reconciliation:
Made no source change. The current primitive definitions already allow leap seconds for instant, dateTime, and time by including `|60` in the seconds component, and the datatype narrative says leap seconds are allowed while warning that many systems and libraries do not support them and should handle them gracefully.

Recommendation:
Keep this audit commit as-is. No core source edit is needed for FHIR-13685; future work should only revisit leap-second wording or validation if a new current-version issue changes the intended datatype behavior.
