FHIR-16940: Audit string and markdown datatype clarifications

Issue request:
FHIR-16940 was a Published/Persuasive MnM FHIR-core datatypes ballot issue asking to clarify string and markdown datatype definitions. The accepted resolution was to make clear that markdown follows the same rules as string, that the string size limit is one million characters, and that the string/markdown regex should be improved even if it cannot enforce every Unicode rule.

Initial application:
Jira records the issue as applied after a 2018-07-10 2-0-0 vote. The corresponding git-svn history is commit a5c90c3db3cc87902faf8b096c1fdc5f179853fc, which explicitly named GF#16940 and changed source/datatypes.html to state the character-count string limit, add string whitespace guidance, and define markdown as a FHIR string subject to string rules. Later datatype source changes preserved and refined those rules.

Additional context:
source/fhir.ini routes default datatype pages to datatypes.html, and the datatype page plus source/datatypes/primitives.xml are the current build-scope sources for primitive datatype narrative and regex values. Later final issues refined the same area without reversing the seed: FHIR-17639 kept empty strings invalid and added the whitespace-only warning; FHIR-40563 changed both string and markdown regexes to ^[\s\S]+$; FHIR-38714 corrected markdown's CommonMark/GFM no-inline-HTML guidance; FHIR-32800 and FHIR-48953 added additional string Unicode and newline clarification. MnM minutes corroborate the original FHIR-16940 disposition, and bounded Zulip/Confluence searches found no conflicting later community decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already tells implementers that markdown is a FHIR string and is subject to string rules, that strings are limited to 1,048,576 characters even though UTF-8 byte size may exceed 1MB, that strings should avoid disallowed control characters, how leading/trailing and whitespace-only strings behave across formats, and that both string and markdown use a non-empty regex that avoids the old useless \s*(\S|\s)* pattern.

Recommendation:
Keep this audit commit as-is. No FHIR-core source follow-up is needed for FHIR-16940; future work in this area should be handled only through a new work-group decision if the current string/markdown whitespace or regex policy is intentionally changed.
