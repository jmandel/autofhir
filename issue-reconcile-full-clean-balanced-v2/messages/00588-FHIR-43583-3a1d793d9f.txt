FHIR-43583: Audit Permission value rules outside core

Issue request:
FHIR-43583 was an Applied/Persuasive Security issue for R5 asking to clarify how multiple values under Permission.rule attributes, especially data and activity, are interpreted. The request asked for explicit documentation that repeated data and activity criteria in one permit or deny rule apply to any combination of those values, while noting a possible future any-of/all-of qualifier for rarer conjunctive security-label cases.

Initial application:
No historical source commit explicitly mentioning FHIR-43583 was found. While FHIR-43583 was being discussed, the same Permission AND/OR ambiguity was handled through FHIR-44748: Security WG minutes discuss FHIR-43583 and FHIR-44748 together, then approve FHIR-44748, and merge commit 2268c17c01881bb6256b9c2a61c98afd75396e98 added Permission Rules Processing Logic plus StructureDefinition comments saying repeated Permission.rule.data and Permission.rule.activity entries are OR alternatives and that elements/repetitions within each data or activity entry are AND conditions.

Additional context:
Permission is no longer an active resource in the current core build. Commit 0e2a8a7f839d5e1a43787523daccf07d958362f3 removed source/permission and active Permission entries from source/fhir.ini, and current core Security/history pages link Permission to the HL7 Data Access Policies IG. The current HL7/data-access-policies Permission StructureDefinition retains the rule, data, activity, and limit comments that convey the OR/AND rule-processing clarification. A prior combined-branch audit for FHIR-44748 already records this same Permission move-out-of-core context, but explicitly did not audit FHIR-43583.

AutoFHIR reconciliation:
This empty commit intentionally makes no core source change. Reintroducing or editing source/permission in core would conflict with the later core decision to remove Permission; the current external Permission source already contains the clarification needed for FHIR-43583.

Recommendation:
Keep this external-repo audit as-is for core. If future Permission rule-value semantics change, make the source change in HL7/data-access-policies unless a later final work-group decision moves Permission back into the active FHIR core build.
