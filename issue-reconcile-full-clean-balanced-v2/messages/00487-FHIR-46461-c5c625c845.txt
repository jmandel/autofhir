FHIR-46461: Audit Permission FMM outside core

Issue request:
FHIR-46461 was an Applied/Persuasive Security work group issue requesting that the R6 Permission resource be elevated to FMM 1. Jira's application comment also noted that an identifier needed to be added to satisfy FMM 1 requirements.

Initial application:
The issue was applied in core by commit 58a264be3617c318e637f060d5f9901eb17ddcbb and merged through HL7/fhir#3124 as c47a45a0c1ceceda1ecab8a4da2664a494f0323d. That implementation changed source/fhir.ini from permission=0 to permission=1, added Permission.identifier to source/permission/structuredefinition-Permission.xml, added the Permission identifier search parameter, and added FiveWs mapping exceptions needed for the promoted resource.

Additional context:
After that application, commit 0e2a8a7f839d5e1a43787523daccf07d958362f3 removed the Permission resource from the current core build, including source/permission and the active source/fhir.ini Permission entries. The current Security module links Permission to the HL7 Data Access Policies IG. The FMG Zulip thread on resource removal records that Security agreed Permission should move out of core and use the existing data-access-policies work. The current HL7/data-access-policies Permission source still carries structuredefinition-fmm value 1 and Permission.identifier.

AutoFHIR reconciliation:
This commit intentionally makes no core source change. Reintroducing source/permission or restoring source/fhir.ini Permission entries would conflict with the later move out of core. The FHIR-46461 FMM and identifier application has been preserved in the external Permission source of truth, so the correct core reconciliation is an external-repo audit.

Recommendation:
Keep this external-repo audit as-is. No core follow-up is indicated for FHIR-46461 unless a future final work group decision moves Permission back into core; ongoing Permission maturity and identifier changes should be handled in HL7/data-access-policies.
