FHIR-28284: Audit ConceptMap dependency value modelling

Issue request:
FHIR-28284 was Published/Persuasive for R5 and asked to remodel ConceptMap.group.element.target.dependsOn and the corresponding product backbone so their value is a value[x] choice rather than separate system/value/display fields. The approved resolution replaced the R4-style property/system/value/display shape with a property plus value[x] choices, and the Jira comments tied the request to $translate output behavior.

Initial application:
The change was applied in the R5 ConceptMap work. Commit fd2a87c248 changed ConceptMap.group.element.target.dependsOn.value to value[x] with primitive/code choices, and commit 8f39fd413c removed ConceptMap.group.element.target.dependsOn.display per FHIR-28284. The related March 2021 operation-definition work added product and dependsOn output parameters for $translate, while later R5 edits renamed and refined the model.

Additional context:
Related published issues FHIR-30515 and FHIR-34120 aligned $translate output and input parameters with the FHIR-28284 value model, and FHIR-33032 added id support. Later ConceptMap decisions, especially FHIR-39151 and FHIR-40504, separated mapping properties from source/target additional attributes and renamed the old dependsOn/product property references to attribute references. FHIR-40636 then clarified valueCode interpretation. The current source therefore differs from the original FHIR-28284 type list and names by design: current dependsOn/product values use the additional-attribute type set and the attribute naming introduced by later published decisions.

AutoFHIR reconciliation:
No source change was made. The active ConceptMap resource source already defines ConceptMap.group.element.target.dependsOn.value[x] and represents product with a contentReference to the same backbone. The current $translate OperationDefinition exposes dependency, match.product, and match.dependsOn values using the same allowed-type set. Changing the source back toward the literal 2021 wording would undo later published ConceptMap decisions rather than complete FHIR-28284.

Recommendation:
Keep this empty audit commit as-is. Further ConceptMap edits should be driven by a newer tracker if the work group wants to revisit the later attribute/property split or the current allowed-type set; FHIR-28284 itself is already satisfied in the current build.
