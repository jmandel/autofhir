FHIR-20499: Fix RequestIntent instance-order source hierarchy

Issue request:
FHIR-20499 was Published as Persuasive with Modification for R5. It asked to move Request.intent code instance-order out from under filler-order to be directly under order, because instance orders can be created by placing systems as well as filler systems, and to clarify the original-order, filler-order, and instance-order definitions.

Initial application:
Git 849d838231 applied the issue to source/request/codesystem-request-intent.xml by moving instance-order to be a direct child of order and by adding the approved definition clarifications. However, the active request logical-pattern spreadsheet still kept instance-order parented by filler-order and retained the old shorter definitions, so generated RequestIntent output could still reflect the pre-FHIR-20499 hierarchy.

Additional context:
source/fhir.ini lists request as an active logical pattern, and the current CI build request-intent CodeSystem showed solicit-offer/offer-response from the spreadsheet while still nesting instance-order under filler-order. That confirms the workbook remains build-driving for the rendered RequestIntent hierarchy. The 2019 FHIR-I Workflow minutes record the lab scenario that prompted the tracker: EHRs can create separate orders for each occurrence, motivating removal of instance-order from the filler-order specialization. FHIR-13999 is the same hierarchy family for MedicationRequest and has already been reconciled separately on the combined branch. FHIR-56142 is a later Resolved - change required escape-valve discussion and does not change this applied hierarchy decision.

AutoFHIR reconciliation:
Updated source/request/request-spreadsheet.xml so the request-intent worksheet makes instance-order a direct child of order and aligns the original-order, filler-order, and instance-order definitions with the already-correct RequestIntent CodeSystem XML. The edited spreadsheet is in build scope through the active request logical-pattern entry, and each hunk is necessary to prevent the generated RequestIntent hierarchy and definitions from diverging from the published Jira decision.

Recommendation:
Keep this source fix. It completes the partially applied FHIR-20499 change in the build-driving request worksheet; handle FHIR-56142 and any broader request-intent escape-valve guidance in that separate issue family.
