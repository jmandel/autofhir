FHIR-8310: Audit ElementDefinition base cardinality metadata

Issue request:
FHIR-8310 was a Published FHIR-core StructureDefinition change request, resolved Persuasive with Modification, about profiles that constrain an element's max cardinality to 1 and thereby lose information that the base element was repeating. The approved resolution was the same basePath/baseMin/baseMax addition to ElementDefinition, using a 0..1 base component whose path, min, and max children are required when base is present.

Initial application:
The Jira comment records svn revision 5924. No current git commit explicitly names FHIR-8310, but git-svn history for the same approved change family shows ddb1f8c4e0916fada828b645a84c2c90f59329e2 (#6066, svn r5923) adding ElementDefinition.base and initial population, followed by 74950f48e21290a8d95baa474e74c2d2d3034e11 (#6066, svn r5924) adding the ElementDefinition.base invariants. Current source represents the flat resolution names as ElementDefinition.base.path, ElementDefinition.base.min, and ElementDefinition.base.max.

Additional context:
FHIR-6066, FHIR-6093, and FHIR-6340 are the same Published/Persuasive with Modification ElementDefinition.base family. FHIR-6093 and FHIR-6340 are already represented on the combined branch, and FHIR-6066 is the seed audited by this reconciliation. ElementDefinition.base.max currently describes the base maximum cardinality and notes its importance for JSON serialization and code generation, directly covering the FHIR-8310 concern. Direct Zulip and Confluence searches found no FHIR-8310-specific community record that changes the Jira/source conclusion.

AutoFHIR reconciliation:
No source change was made. The current authoritative ElementDefinition source already includes required base path/min/max metadata and explanatory text preserving the base max cardinality, and current StructureDefinition snapshot constraints require snapshot elements to carry base definitions.
