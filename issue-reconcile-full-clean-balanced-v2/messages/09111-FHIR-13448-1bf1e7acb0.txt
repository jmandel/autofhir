FHIR-13448: Audit operation resource-body invocation wording

Issue request:
FHIR-13448 was Published/Not Persuasive with Modification for the FHIR-core Operations page and OperationDefinition artifact. It asked whether an operation with a single input parameter whose type is a FHIR resource could be invoked by POSTing that resource directly instead of wrapping it in Parameters; the accepted clarification was that this applies when a specific invocation has exactly one Resource input parameter, with the resource in the body.

Initial application:
The issue was applied by SVN revision 12843, now git commit 5a464a090fd6700ee82d13d4bfa30a46008cca2e, which changed source/operations.html from the older "only parameter to a specific invocation" wording to an explicit exactly-one Resource input parameter rule and included the then-current no-URL-parameters limitation. The current built source still contains the core exactly-one Resource input rule on source/operations.html.

Additional context:
Later Published issue FHIR-33385 deliberately revised the same paragraph for R5 after implementers noted that operations such as $validate legitimately POST a resource body while passing other parameters on the URL. Applied issues FHIR-51046 and FHIR-41220 then aligned the Operations page around parameters that have associated search types rather than the old primitive/simple-parameter wording. Those later decisions supersede the literal "no parameters on the url" part of the 2017 text while preserving the seed issue's clarification that there is a single Resource input parameter represented by the request body.

AutoFHIR reconciliation:
This commit makes no source change. source/operations.html is an active built page through source/hierarchy.xml, and its current Operation Request paragraph says that when an operation has exactly one input parameter whose type is a FHIR Resource, and any other submitted parameters have associated search types, the client may POST the input resource as the request body with those additional parameters as query parameters. That current wording is the correct result of FHIR-13448 plus later Operations-page decisions.

Recommendation:
Keep this audit commit as-is. Reverting the current paragraph to the original no-URL-parameters language would conflict with later FHIR-I decisions and examples; no further core source change is recommended for FHIR-13448.
