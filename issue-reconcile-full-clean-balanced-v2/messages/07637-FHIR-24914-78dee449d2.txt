FHIR-24914: Audit returned-resource transaction guidance

Issue request:
FHIR-24914 was Published/Persuasive with Modification for R5. It asked for create, update, and patch guidance saying that when a server stores changed content it SHOULD return the stored resource regardless of the Prefer response header or omit the ETag, and that a client receiving a returned resource SHOULD base later update or patch requests on that returned content; the resolution placed the text in the HTTP Transactional Integrity section and allowed out-of-band consistency agreements.

Initial application:
The issue was applied by git commit 52b757fe6c4dd79e5655b910dd5a43ba0702e980, which added the requested notes to source/http.html under Transactional Integrity. The current source also points the create and update sections to that Transactional Integrity note.

Additional context:
The originating Zulip thread confirms the rationale: stored content can differ from submitted content, and blindly patching from the submitted representation can corrupt data. Later HTTP-page editorial work, including FHIR-39135 commit e3d5959f90aee9e932edac1c9bc47ea8779e901c, corrected wording in the server bullet without changing the FHIR-24914 semantics. Confluence searches found no separate minutes or conflicting decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active HTTP source already includes the issue's two SHOULD expectations and the out-of-band-agreement note in the Transactional Integrity section, with create/update text linking readers to that section.

Recommendation:
Keep this audit commit as-is. No follow-up source work is needed for FHIR-24914 in core FHIR unless a future work-group decision changes the current create/update/patch transactional-integrity policy.
