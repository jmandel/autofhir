FHIR-20578: Audit Device type cardinality

Issue request:
FHIR-20578 was a Published/Persuasive with Modification OO change request for R5 asking to change Device.type from 0..1 to 0..* so a device instance can carry multiple distinct, non-synonymous type concepts such as GUDID/GMDN/SNOMED CT classifications. The accepted modification also asked the definition to say that the repeated types are those that apply to the specific device instance.

Initial application:
The issue appears to have been applied before this reconciliation. Commit a7f2575daae7bbacd9a22ea439c7ec35a4784f96, merged by f2409b3c69e13268c406a168498173bcd4677190, lists FHIR-20578 in its preapplied changes and changes the Device spreadsheet row for Device.type from 0..1 to 0..* while adding the specific-instance definition. The 2021 source refactor commit 33b409a4b6d544598262f2f074ebb4b6dc466157 preserved those semantics in source/device/structuredefinition-Device.xml.

Additional context:
Device is active in the current build through source/fhir.ini. The current Device.type source has max * and says a device instance may have more than one type when those types apply to the specific instance. FHIR-20579 was the parallel DeviceDefinition.type request, but it is a Duplicate and its comments say the DeviceDefinition side was resolved through FHIR-27798; that separate DeviceDefinition issue already has a no-change audit commit on the combined branch. Zulip and Confluence searches for FHIR-20578, Device type, and GUDID found no conflicting community record.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current authoritative Device source already implements the requested Device.type cardinality and definition, and nearby generated/diagram evidence agrees with the source rather than exposing a remaining source defect.

Recommendation:
Keep this no-change audit commit. No core source follow-up is needed for FHIR-20578 unless a future OO decision changes how multiple Device.type concepts should be represented.
