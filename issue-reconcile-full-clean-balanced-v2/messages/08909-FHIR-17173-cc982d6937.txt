FHIR-17173: Audit history bundle POST guidance

Issue request:
FHIR-17173 was a Published FHIR-core/fhir-i change request with a Persuasive with Modification resolution. It asked to clarify the apparent conflict between the create rule that a server ignores a submitted id and the guidance for applying history Bundles as transactions; the final resolution was that history-bundle entries with request.method POST must use Bundle.entry.resource.id for that resource, and that the HAPI-style POST-to-a-version URL looked incorrect.

Initial application:
The Jira comment records svn revision 14179. In git history this is commit 7f62d75b702eaf8411a2e9ee065322fe7f36482d, "GF#17173 - note about processing history as transaction", which added the three-line note under source/http.html#other-bundles saying that a history Bundle processed via transaction must use Bundle.entry.resource.id, matching Bundle.entry.response.location, so references are preserved. Current blame still attributes that note to the FHIR-17173 implementation commit.

Additional context:
The HTTP page is in current build scope through publish.ini's http.html = http entry. The current source still keeps the FHIR-17173 guidance in the "Accepting other Bundle types" section, immediately after the text that history Bundles may be treated as a transaction or batch. Later HTTP-page changes did not remove or contradict the note, and targeted Zulip/Confluence searches found no relevant community record that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The build-scope HTTP source already conveys the requested rule for history Bundle transaction processing, and adding duplicate wording to the create section would not change implementer expectations and could create maintenance drift.

Recommendation:
Keep this no-change audit commit as-is. Revisit only if the work group wants a broader normative-strength change, such as changing the lowercase "must" in the existing note to "SHALL" or adding a formal invariant, because that would go beyond the applied FHIR-17173 resolution.
