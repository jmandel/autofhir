FHIR-39398: Audit period sort clarification

Issue request:
FHIR-39398 was a Published/Persuasive with Modification FHIR-I R5 clarification asking how _sort should behave when a date search parameter targets Period-valued source data, such as Observation.effective[x]. The approved resolution was to state that when date sorting source data is not a single instance, behavior is server-defined, commonly using Period.start, and custom search parameters can define prescribed behavior.

Initial application:
The issue was applied by 6558a43936efbe4cea4c08cfd2102ce29dc686a5, which added the approved clarification to source/search.html in the _sort notes. Later edits rewrapped and conformance-tagged the same Search page but preserved the substantive date/Period sort guidance.

Additional context:
The linked Zulip discussion shows the implementation concern that Period.start versus Period.end and missing boundaries were not specified for sorting. FHIR-I minutes for 2022-12-05 record the Persuasive with Modification vote. The older FHIR-12205 sorting issue is related background for server discretion around complex and null sort values, but it was already represented in the surrounding general sort notes and does not require a separate decision here.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scoped top-level source/search.html Search page already says that date sorting over non-singleton source data such as Period is server-defined, that custom search parameters may assert specific behavior, and that most reference implementations use Period.start.

Recommendation:
Keep this audit commit as-is. No follow-up source change is needed for FHIR-39398 unless the work group later decides to prescribe exact Period boundary ordering or null-boundary behavior.
