FHIR-20487: Audit Meta open type correction

Issue request:
FHIR-20487 was a Published/Persuasive MnM change request raised against STU3/R4 because the Resource $meta operation required a Parameters.parameter.valueMeta value choice, while Meta was not listed as an allowed Parameters.parameter.value[x] type. The approved resolution was to add Meta to the Open Type Element list, allowing Meta anywhere the wildcard "*" type is used, including Parameters.parameter.value[x] and Extension.value[x].

Initial application:
The issue was applied by git commit 0dd70c3172 (GF#20487), which added Meta to the R4 wildcard type utility list and added R4 technical-correction release-note text. The Jira comment says it was applied in both master and R4Final. Later source rework commits carried the result into the checked-in Parameters StructureDefinition, where Meta appears in the Parameters.parameter.value[x] type list.

Additional context:
The current build scope includes the datatypes page and Parameters as an active infrastructure resource. The current datatypes page still owns the Open Type Element section via the generated wildcard-type-list include, and the current Parameters StructureDefinition explicitly permits Meta for Parameters.parameter.value[x]. Current core source no longer contains the old resource-operation-meta.html operation source; the ballot intro links the Resource $meta, $meta-add, and $meta-delete operations to the API incubator IG, so no additional core operation-definition edit is in scope. The original Zulip thread confirms the reported incompatibility and candidate R4 patch request, while Confluence and Jira neighborhood searches found no conflicting later decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current core source already implements the required semantic correction: valueMeta is available because Meta is in the Parameters.parameter.value[x] type choices, and the open-type narrative is generated from the active wildcard type list machinery.

Recommendation:
Keep this audit commit as-is. No core FHIR source follow-up is needed for FHIR-20487; any future review of the externally hosted API incubator $meta operation definitions should be handled in that IG rather than as a core-source reconciliation for this issue.
