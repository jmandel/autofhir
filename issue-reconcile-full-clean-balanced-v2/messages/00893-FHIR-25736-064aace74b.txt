FHIR-25736: Audit Range invariant application

Issue request:
FHIR-25736 was a Published/Persuasive MnM technical correction for R5 asking that Range constraint rng-2 not fail when a Range pattern constrains low/high coding information without low.value or high.value. The approved resolution proposed changing the invariant to `low.value.empty() or high.value.empty() or (low <= high)` and noted a separate FHIR-I follow-up for datatype-constraint validation on patterns.

Initial application:
The issue was applied in c4807a5165ee632872ef9f6289fee8e9e1abbb5f, a multi-issue R5 MnM commit that explicitly listed FHIR-25736 and changed source/datatypes/range.xml from `low.empty() or high.empty() or (low <= high)` to `low.value.empty() or high.value.empty() or (low <= high)`.

Additional context:
Range is active in the current build because source/fhir.ini lists Range under [types]. Current source/datatypes/range.xml retains the FHIR-25736 value-empty guards and later commit 8a6a54029fdef0c2811fe4ea4e0286f84c1de7e3 refined the comparison to use lowBoundary/highBoundary plus a comparability guard. The R5 historical generated profile also contains the value-empty expression. Jira and bounded community searches found the seed issue, the original Zulip reports, and MnM minutes confirming the approval, but no later conflicting decision.

AutoFHIR reconciliation:
No source file was changed. The current build-scope Range invariant already implements the approved semantic fix and the later comparison refinement does not reintroduce the pattern problem because absent low.value or high.value still satisfies rng-2.

Recommendation:
Keep this empty audit commit as-is. No FHIR core source follow-up is needed for FHIR-25736; any broader question about whether datatype invariants should be evaluated on pattern values belongs to the separate FHIR-I validation-policy work referenced by the resolution, which was not identified as a final applied issue in this bounded reconciliation.
