FHIR-17285: Audit Condition recorded date reconciliation

Issue request:
FHIR-17285 was a Published/Persuasive Patient Care change request for STU3 asking to clarify how Condition.clinicalStatus and assertedDate should be understood over time. The approved resolution applied to both AllergyIntolerance and Condition: move assertedDate from the core resources to an extension, define it as the date the allergy/intolerance/condition was first asserted or acknowledged, and add core recordedDate as the date this particular record was created in the EHR/system.

Initial application:
The issue appears to have been applied by git commit 722ed5c93f4bc9828e96f0f5b476bedc3486fb92 on 2018-06-19. That commit explicitly cites GF#14643, GF#15781, and GF#17285, moved AllergyIntolerance.assertedDate and Condition.assertedDate out to extension spreadsheets, renamed the core elements to AllergyIntolerance.recordedDate and Condition.recordedDate, and updated examples/search definitions. The current converted StructureDefinition sources preserve GF#17285 committee notes on the recordedDate elements.

Additional context:
FHIR-14643 and FHIR-15781 are same-family Published trackers for Condition.assertedDate and AllergyIntolerance.assertedDate ambiguity; their comments state that GF#17285 superseded them for the recorded-vs-asserted clarification. The original Zulip thread records the uncertainty around whether clinicalStatus was tied to assertedDate and the later Patient Care summary: move assertedDate to an extension and add recordedDate to core. The current core build actively includes AllergyIntolerance and Condition. Core no longer carries the assertedDate extension definitions after the R5 source cleanup; the FHIR Extension Pack now carries condition-assertedDate for both Condition and AllergyIntolerance, while allergyintolerance-assertedDate is retired/deprecated in favor of condition-assertedDate.

AutoFHIR reconciliation:
No source change was made. Current core source already has AllergyIntolerance.recordedDate and Condition.recordedDate with definitions/comments that distinguish first recording from the current recorder/asserter, has no core AllergyIntolerance.assertedDate or Condition.assertedDate element to continue the old ambiguity, and keeps R3 rename aliases from assertedDate to recordedDate for compatibility. The remaining asserted-date extension source belongs to the Extension Pack and already reflects the assertion-vs-recording distinction.

Recommendation:
Keep this audit commit as-is. No core follow-up is needed for FHIR-17285 unless a future Patient Care decision wants to change the external asserted-date extension text or the later extension-pack consolidation.
