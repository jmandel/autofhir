FHIR-18081: Audit GuidanceResponse request search expression

Issue request:
FHIR-18081 was a Published/Persuasive CDS change request for STU3. It reported that the GuidanceResponse-request SearchParameter was missing its FHIRPath and XPath expressions, and the reporter corrected the target element from GuidanceResponse.requestId to GuidanceResponse.requestIdentifier.

Initial application:
The issue was applied by commit 343c94cd77d956d3ea96e207cddb7e5f2e5a09d8, which changed the then-authoritative GuidanceResponse spreadsheet entry from GuidanceResponse.requestId to GuidanceResponse.requestIdentifier. The later source rework in 33b409a4b6d544598262f2f074ebb4b6dc466157 converted that spreadsheet data into source/guidanceresponse/bundle-GuidanceResponse-search-params.xml and carried both the FHIRPath expression and XPath for GuidanceResponse-request forward.

Additional context:
GuidanceResponse remains active in source/fhir.ini, so the current bundle search-parameter source is in build scope. Subsequent SearchParameter model changes renamed xpathUsage to processingMode and then removed XPath usage from the current SearchParameter structure and GuidanceResponse search-parameter bundle, so the absence of a current XPath element is intentional rather than a missed part of FHIR-18081. The originating Zulip thread only asked how to file the missing-expression trackers and did not add conflicting guidance; Confluence searches found no directly relevant minutes or references.

AutoFHIR reconciliation:
No source change was made. The current active GuidanceResponse-request SearchParameter has its path extension and expression set to GuidanceResponse.requestIdentifier, with processingMode normal, matching the current SearchParameter resource shape.

Recommendation:
Keep this audit commit as-is. Re-adding XPath to current GuidanceResponse search parameters would conflict with the current SearchParameter definition; no follow-up is needed in core for FHIR-18081.
