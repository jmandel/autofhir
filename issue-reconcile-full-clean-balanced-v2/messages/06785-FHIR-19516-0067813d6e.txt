FHIR-19516: Audit OO workflow changes

Issue request:
FHIR-19516 is an Applied OO change request for DiagnosticReport, NutritionRequest, ServiceRequest, and Task. It asked to apply two workflow-pattern changes from older GForge trackers: rename context to a 0..1 Encounter-based encounter element, and consider a reported[x] indicator/source element. The final resolution was Not Persuasive with Modification: acknowledge the context-to-encounter change was already applied in R4, do not update the resources for reported[x] because the requested definition was ambiguous and better handled after further implementation experience using an extension, and handle DiagnosticReport separately.

Initial application:
No current source commit explicitly names FHIR-19516. The encounter part traces to the workflow-family decision in FHIR-17901/GF#17794 and the October 2018 workflow-pattern commits that added workflow extensions and request/event pattern changes. Current migration metadata still maps DiagnosticReport.encounter and ServiceRequest.encounter from their former context elements, and the active source definitions for DiagnosticReport, NutritionOrder, ServiceRequest, and Task all use encounter rather than context. The reported[x] part was not applied to these OO request/task/report resources, matching the seed resolution rather than an implementation miss.

Additional context:
NutritionRequest is not an active current-build resource; current fhir.ini lists NutritionOrder as active and keeps NutritionRequest only as a legacy name. DiagnosticReport was called out in the seed as requiring separate resolution, and later Applied DiagnosticReport issues FHIR-48767 and FHIR-51687 revised the DiagnosticReport.encounter comment/requirements without re-opening the seed's reported[x] request. Related workflow-family issues such as FHIR-19511 and FHIR-19517 show other work groups made resource-specific reported[x] decisions instead of applying the pattern uniformly.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current source already reflects the encounter rename for the in-build OO artifacts, and adding reported[x] or new extension prose here would contradict the Applied seed resolution and risk creating redundant or ambiguous guidance.

Recommendation:
Keep this no-change audit as-is. Any future reported-record work for OO resources should be raised as a fresh, resource-specific Jira or extension-pack proposal with clarified semantics; DiagnosticReport.encounter should continue to be governed by its later DiagnosticReport-specific trackers.
