FHIR-19671: Audit passport identifier SID migration

Issue request:
FHIR-19671 is a Published, Persuasive with Modification FHIR-core datatypes issue asking for a defined way to encode passport identifiers, with the accepted resolution to define an SID pattern for passports and document it on the identifier registry page as http://hl7.org/fhir/sid/passport-xxx where xxx is the ISO three-character country code.

Initial application:
The issue was applied in core by commit 35313f6576, which added a Passport Numbers NamingSystem entry to source/namingsystem/namingsystem-registry.xml with type PPN, root OID 2.16.840.1.113883.4.330, and URI pattern http://hl7.org/fhir/sid/passport-[XXX]. That exact source content was later removed from core with the rest of the identifier NamingSystem registry content after the registry was migrated to HL7 Terminology.

Additional context:
FHIR-35932 changed source/identifier-registry.html so the current core build no longer owns the concrete identifier-system table and instead directs implementers to HL7 Terminology for actively curated Identifier.system values. UP-285 implemented that migration in THO and records that identifier systems from the FHIR identifier registry were created there; its comments specifically discuss replacing the passport pattern with separate country-code NamingSystems because THO cannot represent patterned URIs. FHIR-37889 then removed the duplicate core NamingSystem bundles to avoid stale or misleading copies. Current THO pages for country-specific passport NamingSystems, such as USA and IND, expose http://hl7.org/fhir/sid/passport-USA and http://hl7.org/fhir/sid/passport-IND as preferred URI identifiers.

AutoFHIR reconciliation:
This is an empty no-change audit commit. The current FHIR core source is correct for this issue: the active identifier registry page is in build scope and points to THO, while THO contains the migrated passport Identifier.system entries using the ISO alpha-3 country-code pattern requested by FHIR-19671. Reintroducing passport rows into core would contradict the later registry migration and duplicate authoritative THO content.

Recommendation:
Keep this audit as-is. Future passport identifier maintenance should happen through THO/TSMG rather than by editing the core FHIR identifier registry page, unless a later FHIR-core issue changes the policy that core delegates identifier-system registry content to THO.
