FHIR-17906: Audit conditional update behavior

Issue request:
FHIR-17906 was a Published FHIR-I change request for the core HTTP conditional update section, resolved Persuasive with Modification for STU3. It asked to replace the single no-match rule that always referenced optional Update as Create with separate no-id and id-provided behavior, and to clarify the one-match cases where a provided resource id matches or conflicts with the found resource.

Initial application:
The issue was explicitly applied by d69dfafe26d9ad9151c011ef743568a3ab2158fc, "GF#17906 = update notes about conditional create", which changed source/http.html from generic No matches/One Match bullets to the requested no-match/no-id, no-match/id, one-match/matching-id, one-match/mismatching-id, and multiple-match outcomes.

Additional context:
The current build-scope HTTP narrative is source/http.html, listed in publish.ini as http.html. Later finalized same-section decisions refined but did not reverse FHIR-17906: FHIR-20390 clarified that "id provided" means Resource.id and is already represented on the combined branch, FHIR-26688 removed the contradictory sentence saying a supplied id is ignored, FHIR-36859 split the no-match/Resource.id case when that id already exists, and FHIR-26358 added response Location guidance. The original Zulip thread records the same distinction between server-assigned creation when no id is supplied and Update as Create when an id is supplied. A later 2025 Zulip discussion questions response wording in the one-match row, but no finalized Jira decision was found for that separate response-code concern.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active HTTP source already says no-match/no Resource.id creates the resource, no-match/Resource.id with no existing id uses Update as Create or rejects if unsupported, no-match/Resource.id with an existing id returns 409 Conflict, one match updates when no Resource.id is supplied or when it matches the found resource, and one-match/mismatching Resource.id returns 400 Bad Request. That preserves FHIR-17906 while incorporating later applied clarifications.

Recommendation:
Keep this no-change audit commit as-is. No core source follow-up is needed for FHIR-17906 itself; any future cleanup of the one-match response-status wording should be handled under a separate finalized tracker because it comes from later Location-header guidance rather than the FHIR-17906 behavior decision.
