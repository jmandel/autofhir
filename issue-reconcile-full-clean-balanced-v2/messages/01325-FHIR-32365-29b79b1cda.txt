FHIR-32365: Audit MedicationRequest dose period support

Issue request:
FHIR-32365 was Published/Persuasive with Modification for R5. It asked MedicationRequest to support an overall medication dose period, including start and possible end, so implementations with multiple dosageInstruction periods would not need to derive the overall therapy span from each dosage line. The resolution called for effectiveDosePeriod 0..1 and a dosage-instruction grouping that included renderedDosageInstruction, effectiveDosePeriod, and dosageInstruction.

Initial application:
The request was applied by commit 4af0fbee92 ("FHIR-32488, FHIR-32365"), which added a MedicationRequest dose backbone with renderedDosageInstruction, effectiveDosePeriod, and dosageInstruction to source/medicationrequest/structuredefinition-MedicationRequest.xml. Later source history refactored the same area, so the original R5 element name is no longer present in the current model.

Additional context:
The current MedicationRequest resource is active in source/fhir.ini. Later Applied issue FHIR-52888 changed MedicationRequest.effectiveDosePeriod to MedicationRequest.effectiveTiming[x] with Duration, Range, and Period choices while preserving the definition that, where multiple dosageInstruction lines exist, the element represents the earliest date and latest end date. The R5-to-R6 change map in source/fhir.ini maps MedicationRequest.effectiveDosePeriod to MedicationRequest.effectiveTiming[x]. Later DosageDetails work moved the rendered dosage instruction representation into the active DosageDetails data type used by MedicationRequest.dosageInstruction.

AutoFHIR reconciliation:
No source change was made. The active current source already carries the requested overall dose-period semantics through MedicationRequest.effectiveTiming[x], keeps R5 compatibility history in fhir.ini, and uses DosageDetails for the consolidated rendered dosage instruction. The checked-in MedicationRequest SVG still contains older element names, but the authoritative XML and build configuration are correct and this reconciliation does not make a source-changing commit that edits only generated-looking diagram artifacts.

Recommendation:
Keep this no-change audit. Future work, if any, should address stale generated diagrams as a separate build/artifact-maintenance question, not as a semantic fix for FHIR-32365.
