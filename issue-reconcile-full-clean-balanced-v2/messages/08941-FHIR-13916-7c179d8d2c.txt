FHIR-13916: Audit Subscription creation rejection guidance

Issue request:
FHIR-13916 was a Published/Persuasive with Modification STU3 change request for Subscription error handling. It asked what a server should do when a posted Subscription cannot be honored at all, such as because the channel type or criteria are unsupported, and suggested not storing the Subscription and returning an error OperationOutcome; the approved resolution was to document this as a recommended option.

Initial application:
The issue was applied by commit 8efdf4db313c ("GF#13916 - note about subscription error handling", svn revision 14476), which added guidance to the Subscription notes saying the server SHOULD check whether it is prepared to accept/process the subscription and, if not, return an error with an OperationOutcome instead of processing the create. Later Subscription page refactors, including ef0558f0c600 and d51aae543ee9, moved and preserved this guidance in the active Subscriptions framework page while leaving the Subscription resource page linked back to that framework section.

Additional context:
Subscription and the Subscriptions framework are active in the current build: source/fhir.ini lists Subscription as an active resource, and source/hierarchy.xml lists subscriptions.html. Current source also lists the concrete checks a server should perform when processing a Subscription request, including supported topics, filters, channel type, endpoint, and payload. FHIR-47808 later asked a closely related R6 ballot question about failed Subscription creation HTTP codes; it was applied by bce7fd5987ae and is already represented on the combined branch by audit commit 952b52582d0e, so this reconciliation does not publish a duplicate FHIR-47808 commit. Its resolution and the current http.html#create text support using normal create error handling such as 400/422 plus OperationOutcome rather than hard-coding FHIR-13916's suggested 412 status.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build already conveys the approved FHIR-13916 behavior: unsupported or unprocessable Subscription requests can be rejected instead of created, and the server SHOULD return an OperationOutcome error. Adding another source edit would duplicate existing framework guidance and risk conflicting with the later standard HTTP create-error guidance.

Recommendation:
Keep this audit commit as-is. No FHIR core source change is needed for FHIR-13916 unless a future work-group decision explicitly requires a Subscription-specific HTTP status code beyond the existing standard create interaction rules.
