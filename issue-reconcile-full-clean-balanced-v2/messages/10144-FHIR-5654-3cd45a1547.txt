FHIR-5654: Audit integer constrained primitive types

Issue request:
FHIR-5654 was a Published/Persuasive with Modification FHIR-core datatype issue asking whether integer should disallow negative numbers. The final MnM/FHIR-I disposition retained the signed integer primitive, defined non-negative and positive integer constraints, and called for existing resource elements to use those constrained types as appropriate after WG consultation.

Initial application:
The primitive type work was applied in March 2015. Git commit a87257bf6bcf4f46ba484a2aa7683187d6bb1fbe added positiveInt and unsignedInt to the primitive spreadsheet, and the Jira-tagged commit 963f5d8fac89aa18784f4a33882d7c069fb6255d (#5654, SVN build@5050) changed many then-current spreadsheet elements from integer to unsignedInt or positiveInt, including Attachment.size, SampledData.dimensions, Bundle.total, OperationDefinition.parameter.min, claim sequence fields, and other counts.

Additional context:
Current active datatype source still defines integer separately from unsignedInt and positiveInt. source/datatypes.html clarifies integer as signed 32-bit, positiveInt as 1..2,147,483,647, and unsignedInt as 0..2,147,483,647; source/datatypes/primitives.xml carries the same primitive rows and regexes. Current source usage includes many constrained integer elements (42 unsignedInt and 95 positiveInt matches in source XML). Later final work also matters: FHIR-16950 clarified the size limits for integer, unsignedInt, and positiveInt; FHIR-19958/FHIR-25208 led Attachment.size to use integer64 rather than the old unsignedInt; and later Patient.multipleBirth issues FHIR-41244/FHIR-48399 updated the narrative while retaining valueInteger semantics. No direct Zulip or Confluence record was found that conflicts with the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scope datatype and resource sources already implement the final FHIR-5654 model: integer remains available for signed or WG-specific uses, while unsignedInt and positiveInt are defined and used for non-negative and positive counts. Reapplying the old issue literally would risk overriding later artifact-specific decisions and normative choice-element naming rather than fixing a current-source defect.

Recommendation:
Keep this audit commit as-is. Do not make a broad FHIR-5654 source edit in current core; if a specific current integer element is believed to need a non-negative or positive constraint, handle that through an artifact-specific Jira decision that accounts for current datatype, compatibility, and WG ownership.
