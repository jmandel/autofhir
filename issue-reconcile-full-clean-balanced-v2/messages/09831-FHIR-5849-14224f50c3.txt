FHIR-5849: Clarify Device UDI scope

Issue request:
FHIR-5849 was a Published/Persuasive with Modification OO change request for DSTU1 Device. It reported that earlier Device UDI guidance incorrectly treated UDI as a binary choice: either a unique instance identifier when serial-number production identifiers are present, or only a device type. The approved disposition restored a dedicated UDI element, removed guidance that told implementers to put full UDIs in Device.identifier or Device.type, and asked for unambiguous examples.

Initial application:
Commit 85cad2a017a228c70b358dab887c56b5bfccb18e pre-applied FHIR-5849 together with related Device UDI ballot comments FHIR-5503, FHIR-5505, and FHIR-5506. It removed the direct instruction to store full UDIs in Device.identifier or Device.type and pointed the full UDI string at Device.udi, but it also carried forward a shortened instance-or-type sentence in the Device notes.

Additional context:
Device is active in the current build through source/fhir.ini. Later Device UDI work superseded the original DSTU1 string element with the current Device.udiCarrier backbone, UDI examples, search parameters, and UDI mapping guidance. FHIR-8926 rewrote the Device notes to incorporate UDI components; later Applied/Published decisions such as FHIR-29312, FHIR-43063, FHIR-47419, and FHIR-48769 clarified Device identifier relationships, udiCarrier fields, and production-identifier descriptions. Those later decisions support keeping the current udiCarrier model, not reintroducing the old Device.udi string.

AutoFHIR reconciliation:
This commit updates the active Device.udiCarrier ElementDefinition comment and the Device UDI notes so they no longer describe UDI as only unique-instance-or-type. The text now explicitly allows the case raised by FHIR-5849: a UDI can carry production information such as lot number or expiration date without uniquely identifying an individual device instance. No examples were added because the current Device examples already include udiCarrier examples and the current notes point to the UDI mapping and examples.

Recommendation:
Keep this source fix. It is a narrow correction to current build inputs that preserves later R5/R6 udiCarrier decisions while removing the misleading binary wording that FHIR-5849 identified.
