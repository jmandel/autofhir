FHIR-3830: Clarify REST history deletion wording

Issue request:
FHIR-3830 was Published as Persuasive for FHIR-core-http after an implementer asked whether DELETE marks all versions as deleted or only affects the current resource, and whether a client can delete a specific version such as DELETE [base]/[type]/[id]/_history/1. The accepted resolution was to clarify delete operation behavior, applied in SVN revision 3607.

Initial application:
The issue was initially applied by fddb306c6756dbef9b6c3632c4fa7c513ed51133, the git-svn import of build@3607, which added text to source/http.html saying that deleting a resource does not delete its version history and instead creates a special deleted history entry. Later edits preserved that ordinary-delete rule while rewording the section.

Additional context:
The active RESTful API page is included from source/hierarchy.xml and now also includes the later FHIR-16198 delete-history and delete-history-version interactions. FHIR-16198 is already represented on the combined branch, and its applied semantics mean the older general history note that said past versions cannot be deleted was no longer accurate without a cross-reference to the dedicated interactions.

AutoFHIR reconciliation:
This commit updates the current build-scope source/http.html history notes so they continue to say past versions cannot be updated, but no longer say they cannot be deleted at all. The note now directs readers to the dedicated delete-history and delete-history-version interactions where supported, aligning the history guidance with the delete section, interaction table, and later applied FHIR-16198 behavior.

Recommendation:
Keep this commit. It is a narrow source correction that preserves FHIR-3830's ordinary-delete clarification while preventing the history section from contradicting the current REST interactions; no separate FHIR-16198 action is needed here because that issue already has a combined-branch reconciliation commit.
