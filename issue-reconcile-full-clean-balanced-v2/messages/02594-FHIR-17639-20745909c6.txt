FHIR-17639: Audit empty string handling

Issue request:
FHIR-17639 was Published with resolution Persuasive with Modification for STU3. It asked to resolve the mismatch where FHIR JSON/XML representations already prohibited empty string values while the string datatype regex and validator behavior appeared to allow them. The final decision kept empty strings unsupported, added the whitespace-only string warning to the string datatype, and required validator rejection of empty primitive values.

Initial application:
Commit f8e58880f9 explicitly applied GF#17639 by adding the string datatype note, keeping whitespace-only strings valid but warning that XML trimming can turn them into invalid empty values, and adding validator examples/tests including invalid empty valueString and valueMarkdown values. The current source retains that note and the broader primitive-value text that XML attributes are never length 0 and JSON primitive properties are never 0-length strings.

Additional context:
The datatype and primitive sources are in the current build scope through source/fhir.ini: the type-page fallback points datatypes to datatypes.html, and the infrastructure list includes PrimitiveType. The current JSON and XML representation pages still state that string properties and attributes cannot be empty. Later string-related decisions refined the same area without reversing FHIR-17639: FHIR-32800 clarified string Unicode/serialization behavior, while FHIR-40563 and commit b4c3af0a97 changed the string and markdown regexes to ^[\s\S]+$, preserving the non-empty rule while accepting all non-empty Unicode content. Zulip and Confluence searches found no FHIR-17639-specific conflicting discussion; a 2026 FHIR-I openEHR mapping minutes page describes current FHIR behavior as rejecting empty-string primitives.

AutoFHIR reconciliation:
No source change was made. The current source already conveys the FHIR-17639 decision: empty strings remain invalid, omitted elements represent missing values, whitespace-only strings are allowed but warned against, and the authoritative regex source requires at least one character.

Recommendation:
Keep this no-change audit commit as-is. Further source edits would be redundant and risk restating the same rule in more places; separate future work should only revisit this if FHIR-I intentionally changes the empty-string policy.
