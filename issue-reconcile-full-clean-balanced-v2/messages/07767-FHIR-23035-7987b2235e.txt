FHIR-23035: Clarify resolve discriminator targetProfiles

Issue request:
FHIR-23035 was Published with a Persuasive with Modification resolution for FHIR-core StructureDefinition profiling documentation. It asked the Discriminator section to explain that path elements after resolve() are interpreted in the referenced targetProfile and the approved resolution also said to explain how resolve() works when multiple targetProfile values are present.

Initial application:
The issue was initially applied by git commit 97dac7c066ececda81f3d3176017fb0f307e6ad4, which added the resolve() note to source/profiling.html for R5. That application covered the targetProfile location and fixed/pattern rule, but the current source still did not describe the multiple-targetProfile case approved in the Jira resolution and FHIR-I minutes.

Additional context:
source/profiling.html is an active built narrative page through source/hierarchy.xml. ElementDefinition.type.targetProfile is repeatable and its definition says that when profiles are specified, the content must conform to at least one of them. Later Zulip discussion confirms the intended validation model for resolve().property discriminators: validators use the applicable targetProfile to find the fixed value, pattern, or required value set for the post-resolve element, while slice authors remain responsible for distinguishable slices. No later Jira or community evidence was found that reverses the FHIR-23035 decision.

AutoFHIR reconciliation:
This commit updates the existing resolve() discriminator note in source/profiling.html to explain that, when a reference element lists multiple targetProfile values, the discriminator is evaluated against the targetProfile(s) that apply to the resolved resource. It also states that discriminator constraints may therefore live in different target profiles for different targets, while uniqueness and non-overlap across slices remain the profile author's responsibility, and fixes a nearby misspelling of discriminator.

Recommendation:
Keep this source change. It completes the published FHIR-23035 clarification in the active core profiling page without changing conformance rules or examples; any future machine-checkable invariant for resolve() targetProfile availability would need separate work-group review.
