FHIR-9107: Audit IG page kind binding removal

Issue request:
FHIR-9107 was a Published FHIR-core ImplementationGuide change request raised against DSTU2. It objected that ImplementationGuide.page.kind had a required GuidePageKind binding whose codes were useful to the FHIR publication tooling but too specific and incomplete for other tooling, and suggested making the value set extensible. The final resolution was Not Persuasive with Modification, with the resolution text "overtaken by other changes to IG".

Initial application:
No git commit explicitly mentions FHIR-9107. The relevant application appears to be indirect: b319b6a0dac9ca63360026abf48be963f7b143b9 reworked ImplementationGuide after extensive discussion and removed the old ImplementationGuide.page.kind element from the page structure, and 75410cdf57738f0d8d70655324aee865801f6aaf then added ImplementationGuide.definition.page.generation with a separate GuidePageGeneration binding.

Additional context:
ImplementationGuide is active in the current build through source/fhir.ini. The current source defines ImplementationGuide.definition.page with source, name, title, generation, and nested page children; it does not define ImplementationGuide.page.kind, GuidePageKind, or guide-page-kind. The remaining required page binding is GuidePageGeneration on ImplementationGuide.definition.page.generation, with only html, markdown, xml, and generated codes, so it is not the broad DSTU2 GuidePageKind taxonomy that FHIR-9107 challenged. FHIR-I minutes from 2018-07-09 record the issue as Not Persuasive with Modification, and a March 2018 Zulip thread shows the IG page model was being converted away from the R3 kind model toward generated-page behavior.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The requested DSTU2 concern is already resolved in the current active source because the old required GuidePageKind binding no longer exists; weakening the current required GuidePageGeneration binding would change a different, narrower tooling signal and is not supported by FHIR-9107.

Recommendation:
Keep this no-change audit as-is. No core follow-up is needed for FHIR-9107 unless a new work-group decision separately requests changes to the current ImplementationGuide.definition.page.generation codes or binding strength.
