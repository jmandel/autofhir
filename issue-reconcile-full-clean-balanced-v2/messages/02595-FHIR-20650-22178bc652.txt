The final decision added CareTeam.participant.timing as a Timing 0..1 element with the short/definition "When the member is generally available within this care team," plus the comment and requirement text about managing members with different timing.

Initial application:
The issue was initially applied by commit 8cb59593b22b3f33b6431c24a317587979e52128, which added CareTeam.participant.timing to the then-authoritative CareTeam spreadsheet source and added a Timing example in source/careteam/careteam-example.xml. That application matched the FHIR-20650 resolution at the time.

Additional context:
CareTeam is active and approved in source/fhir.ini. Soon after FHIR-20650, FHIR-23030 reworked the same participant timing/period area and merged CareTeam.participant.period plus CareTeam.participant.timing into CareTeam.participant.coverage[x] as a Period | Timing choice; the combined branch already has a FHIR-23030 reconciliation commit correcting that successor element to 0..*. FHIR-44834 later renamed coverage[x] to effective[x], and the combined branch already has a FHIR-44834 audit commit. Current source/fhir.ini maps the old CareTeam.participant.period name to CareTeam.participant.effective[x]. The Jira-linked Zulip thread and Confluence minutes explain the availability/scheduling discussion but do not create a later requirement to restore a standalone timing sibling.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative source already carries FHIR-20650's substantive Timing capability through CareTeam.participant.effective[x] with Period and Timing data types, the requested short/definition/comment/requirement semantics, and the later accepted name/cardinality changes from FHIR-23030 and FHIR-44834.

Recommendation:
Keep this audit commit as-is. Do not re-add CareTeam.participant.timing as a separate element; that would conflict with later published CareTeam decisions. If generated diagrams or examples need refresh, handle that through the normal generation workflow rather than changing this issue's source decision.
