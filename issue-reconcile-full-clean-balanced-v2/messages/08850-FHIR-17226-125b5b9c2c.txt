FHIR-17226: Audit POST search parameter handling

Issue request:
FHIR-17226 was a Published/Persuasive with Modification FHIR-core STU3 issue asking the RESTful search specification to define what happens when an HTTP POST search supplies search parameters in both the URL query string and the application/x-www-form-urlencoded body. The accepted resolution said parameters may appear in either place with the same meaning, and using both places is equivalent to repeating parameters.

Initial application:
The issue was applied in git-svn commit 0f3fd3eddea935b3926919a698d6f90a1ca1e49f, matching Jira's svn revision 13947 comment. That commit added HTTP-page prose saying POST search parameters may appear in both the URL and body, have the same meaning in either place, and are equivalent to repeated parameters. Later R5 search/http work moved and reshaped this content; commit e441170220c19e992f803667b245e63dcdd508cf moved transport-protocol content from source/search.html to source/http.html, and the current combined branch's FHIR-31944 reconciliation commit 147114dc2a42836ae64f0d31a75bbf998a094e2e restores the explicit accepted-parameter equivalence rule.

Additional context:
The active build navigation lists source/http.html as the RESTful API page with source/search.html beneath it. Current source/http.html says servers SHALL support POST body search parameters, MAY support query parameters on POST, and, when a server accepts a search parameter in the URL of a POST search, there is no semantic difference from supplying it in the body; accepted URL and body parameters SHALL be combined into a single set, with repeats treated as repeats. Current source/search.html also requires self links to disclose the parameters actually used. FHIR-31944 is a later Published issue in the same POST-search family and is already represented on the combined branch, so this seed should not duplicate that source-changing commit.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active REST/search source already states the FHIR-17226 rule in the necessary location, with later FHIR-31944 context explaining the optional support and self-link behavior for POST URL parameters.

Recommendation:
Keep this empty audit commit as-is. No further FHIR-core source work is needed for FHIR-17226 unless a future work group decision changes whether POST search URL parameters must be supported.
