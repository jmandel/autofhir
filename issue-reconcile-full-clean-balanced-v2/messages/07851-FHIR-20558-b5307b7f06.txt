FHIR-20558: Audit $convert Provenance disposition

Issue request:
FHIR-20558 was Published/Not Persuasive with Modification. It asked that the $convert operation recommend producing a Provenance record for the conversion, but the accepted disposition declined that base-server recommendation because a server returning a converted result is not storing the resource; the required change was to fix the invalid $convert example so version-specific requests could be shown.

Initial application:
The issue appears to have been applied in ec8600a67c8ee24a6a9d5239b46c916fd5e461cc, which split the $convert examples and added fhirVersion-specific request and response material. A same-day cleanup commit, 4dc8ff0339fccfecc8b1c06ead70812d9dc9cdb7, made the operation example formatting more readable.

Additional context:
The Resource abstract resource is active in source/fhir.ini, source/resource/list-Resource-operations.xml includes OperationDefinition/Resource-convert, and source/resource/operationdefinition-Resource-convert.xml references the request and response example files through build example extensions. Related Published issue FHIR-20912 concerns the same $convert/fhirVersion example family and is already represented on the combined branch by c6129f04ff6ca84bb49df29c81c06942338be21e, which fixed the remaining response-comment typo. The FHIR-20558 Zulip thread confirms the intended application was to make the version request example obvious, and Security community discussion treats provenance for simple syntax/version transforms as policy-dependent rather than a base-spec mandate.

AutoFHIR reconciliation:
This empty audit commit intentionally makes no source change. The current $convert examples show Content-Type with fhirVersion=3.0 on the input, Accept with fhirVersion=4.0 on the request, and a response Content-Type with fhirVersion=4.0, while the OperationDefinition still avoids adding the Provenance recommendation rejected by the Jira disposition.

Recommendation:
Keep this no-change audit commit. Further core edits would either duplicate the already-correct $convert example or reintroduce a Provenance recommendation that the published resolution explicitly did not adopt; any stronger provenance policy for conversions should be raised as new work-group guidance.
