FHIR-38904: Audit DeviceAssociation relocation

Issue request:
FHIR-38904 was Published with resolution Persuasive with Modification for R5. It asked to move patient association information out of Device to avoid reusable Device instances carrying patient-identifying history, add DeviceAssociation, remove Device.association and Device.operationStatus from Device while handling operation details, add boundary/notes guidance, and ensure the resulting association model could carry status, subject, body structure, period, and operator/use context.

Initial application:
The source history shows the issue was materially applied before this reconciliation. Commit 620b8fa10c746066887014813e72cf08475a42c0 added the DeviceAssociation resource to the active build. Commit 97e59d026d9311992199080e53a49ec78cf6aae5 for FHIR-38904 commented out the active Device.operation and Device.association structures, including Device.association.humanSubject/bodyStructure, and changed Device operation details during the R5 application. Commit 7a135eb3489ef36b8935e36d80d88b1729a2e8e8 added the DeviceAssociation operation/operator/period QA changes. The old Device subject/patient search parameters are also inside XML comments, so they no longer feed the build.

Additional context:
Related R4 tickets FHIR-39226 and FHIR-39243 explicitly defer to the FHIR-38904 disposition and are already represented on the combined branch. Later R6 Applied decisions changed the details of the DeviceAssociation model without reversing the patient-association move: FHIR-46968 clarified subject versus operator, FHIR-47604 removed the DeviceAssociation operation/operator backbone and added focus, and FHIR-53628 documents that the operation backbone was collapsed into other elements with DeviceAssociation.relationship carrying the operator role. Current source/fhir.ini keeps both Device and DeviceAssociation active. Current compartments put DeviceAssociation, not Device, in patient/related subject compartments. The checked-in DeviceAssociation SVG still contains old operation labels, but it is a generated-looking diagram artifact and the authoritative XML/narrative/search parameter sources already convey the current model.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative source has no active Device.patient, Device.subject, Device.association, or Device.operation paths; DeviceAssociation carries device, relationship, subject, focus, bodyStructure, and period; DeviceAssociation search parameters include subject, patient, focus, and date; and narrative guidance points implementers from Device to DeviceAssociation for ownership/custodianship and from DeviceAssociation to Observation for settings over time.

Recommendation:
Keep this audit commit as-is. Do not reintroduce Device patient association or the older DeviceAssociation operation backbone for FHIR-38904; those details have been superseded by later Applied R6 decisions. If diagram freshness matters, regenerate generated-looking SVG artifacts separately rather than hand-editing them as this issue's source reconciliation.
