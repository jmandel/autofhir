FHIR-7799: Audit derived profile override rules

Issue request:
FHIR-7799 is a Published/Persuasive FHIR-core profiling issue from DSTU1 asking the specification to list the rules for what a derived profile may and may not override, especially the full cardinality-override matrix rather than a single 1..1 example. The accepted motion was to list these rules and integrate the suggestions with the then-current constraints-and-rules guidance.

Initial application:
The Jira application comment says "svn revision 6465." Git history contains that SVN import as commit 9d4c8ad9d06cf81a4eb0dfa532c3b49244544646, "#7799 - add cardinality table," which added the Changing Cardinality section, the base-vs-derived allowed/disallowed cardinality table, and replaced the old single-example limitation with a reference to cardinality as described above.

Additional context:
The current profiling page still contains that cardinality matrix and now also gives broader profiling rules: StructureDefinitions constrain existing resources and datatypes, changed definitions must remain restrictions consistent with the base, type/reference/value-set restrictions are listed as allowed kinds of constraints, and binding-strength overrides have their own matrix. profiling.html is an active current-build page through publish.ini and source/hierarchy.xml and is linked from the conformance module. Adjacent same-family issues FHIR-7800, FHIR-7801, and FHIR-7802 are already represented on the combined branch, so they are cited only as context here.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current built source already implements the FHIR-7799 request by retaining the cardinality override table added for this issue and by surrounding it with the broader derived-profile constraint rules that later source evolution added. Adding another table or restating the same rule would be redundant and could create maintenance drift.

Recommendation:
Keep this empty audit commit as-is for FHIR-7799. If the work group later wants a new exhaustive, machine-verifiable catalog of every ElementDefinition property derivation rule, that should be handled as a new current-scope profiling/tooling issue rather than as a repair to this already-applied DSTU1 tracker.
