FHIR-32568: Audit Device property value cardinality

Issue request:
FHIR-32568 is a Published/Persuasive OO change request asking why Device.property.value was optional and resolving to make Device.property.value 1.. because a Device property should carry a value, not only a type.

Initial application:
The Jira application comment points to PR #1471 commit ff30e9f. The PR merge commit 79d69778f6662914640649ae32b8d03086c9bbbb, via implementation commit 20d37b330c8e08e98477dc607b2dcdedb368a60f, changed source/device/structuredefinition-Device.xml so Device.property.value[x] moved from min 0 to min 1. Later history shows 23d0f3c36f2244f7636e70edcfbd21cf074c49db again adjusted Device and DeviceDefinition property.value cardinality after intervening source refactors.

Additional context:
Device is an active resource in source/fhir.ini, so source/device/structuredefinition-Device.xml is current build input. Current source has Device.property.value[x] with min 1 and max 1, and the published R5/current build Device profiles expose the same 1..1 cardinality. R4 had separate optional valueQuantity/valueCode elements, confirming the Jira was an R5 application change. Zulip and Confluence searches found no later conflicting guidance; Confluence OO minutes only confirm the same block-vote handling reflected in Jira.

AutoFHIR reconciliation:
This is an empty no-change audit commit. No source edit is needed because the authoritative Device StructureDefinition already implements the requested mandatory value cardinality.

Recommendation:
Keep this audit commit as-is. No follow-up is needed for FHIR core unless a future OO decision changes the Device property model.
