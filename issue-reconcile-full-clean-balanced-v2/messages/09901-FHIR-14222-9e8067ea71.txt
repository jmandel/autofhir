FHIR-14222: Audit Resource meta server-handling notes

Issue request:
FHIR-14222 was a Published/Persuasive with Modification FHIR-core HTTP issue for STU3. It observed that REST create/update text requires servers to ignore client-supplied meta.versionId and meta.lastUpdated and populate correct server values, while other Meta fields can be changed by clients or servers. The accepted resolution asked to update the Resource metadata table to say what servers are allowed or required to do for each Meta field, and to add a note for balloters about versionId/lastUpdated handling by systems without versioning support.

Initial application:
The Jira comment records svn revision 14190. Git commit 08f6c3eb5eabae98782de609be417658de92172b, imported from that revision, added RESTful API handling notes to every row of source/resource/resource-notes.xml's Resource Metadata table and added an HTTP note about servers that do not support versioning. Git commit 5cc29abbe88aa6257c3af53138e73dfd9e478977 immediately fixed the HTTP note typo from "do support versioning" to "do not support versioning".

Additional context:
source/fhir.ini keeps Resource in the active resource infrastructure and FHIR resource listings, so source/resource/resource-notes.xml and source/datatypes/meta.xml are current build inputs. Later decisions refined the same area without reversing FHIR-14222: FHIR-17865 changed Meta.lastUpdated from "do not use" to "do not depend on" version-aware updates, FHIR-29685 replaced the old write-operation wording with explicit create/update/patch wording, FHIR-11259 clarified no-version server behavior for meta.versionId, and FHIR-45047 updated the generated Meta.lastUpdated comments. Those related decisions are already represented on the combined branch.

AutoFHIR reconciliation:
No source change was made. The current Resource Metadata table still says versionId and lastUpdated are server-updated for RESTful operations that impact meta, while source/profile/security/tag behavior is allowed or constrained per field. The Meta datatype spreadsheet and HTTP create/update/versioning text remain consistent with that rule, including the no-versioning case and the later lastUpdated clarifications.

Recommendation:
Keep this empty audit commit as-is. No follow-up is needed for FHIR-14222 unless a future work group decision changes RESTful Meta handling semantics.
