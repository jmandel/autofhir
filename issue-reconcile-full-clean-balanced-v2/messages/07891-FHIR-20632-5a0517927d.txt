FHIR-20632: Correct security label duplicate guidance

Issue request:
FHIR-20632 was Published with resolution Not Persuasive with Modification for the Resource security-label note. The requester asked to remove the old statement that security labels are unique by system+code; the accepted resolution instead said the spec should explicitly communicate that it is invalid to create two security labels with the same system+code but different .display or .version, because display and version are ignored when evaluating security labels.

Initial application:
The Jira-tagged source commit 7a0ddbd3129ca96c60aa283cac8b67bdfb21c9b1 replaced the old set sentence in source/resource/resource-notes.xml, which feeds the active Resource page. However, that application inverted the resolution by saying it is valid to create duplicate security labels with the same system+code but different display or version.

Additional context:
The active build configuration treats Resource as an active normative artifact, and the generated Resource notes still contain the security-label section. The parallel Meta.security datatype definition says security labels are a set and that uniqueness is based on system/code while version and display are ignored. A later related Jira, FHIR-53182, is still Triaged and unresolved, so it is useful background but not a final reversal of FHIR-20632. Zulip and Confluence searches found no final community record that overrides the published Jira resolution.

AutoFHIR reconciliation:
This commit changes the Resource security-label note from "valid" to "not valid" and changes the follow-up sentence to say .display and .version are not taken into account, aligning the current source with the published resolution and the Meta.security definition.

Recommendation:
Keep this source fix. It corrects a semantic inversion in active core Resource guidance; any broader reconsideration requested by unresolved FHIR-53182 should proceed separately through work-group resolution.
