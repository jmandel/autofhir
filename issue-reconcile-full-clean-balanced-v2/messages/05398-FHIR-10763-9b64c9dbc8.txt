FHIR-10763: Audit Endpoint payload flexibility

Issue request:
FHIR-10763 was a Published/Persuasive with Modification Patient Administration request for the DSTU2 Endpoint resource. It reported that Endpoint.payloadFormat was 1..1 even though the field needed to support no payload and multiple MIME types, and the final disposition chose to add example payload type codes for "any" and "none" rather than simply relying on a cardinality change.

Initial application:
The Jira-tagged source commit 3e4dd26ef51c6ba90a3bcad1e3fb51e317ac05bb ("Trackers# 12343, 10763, 12048") added the Endpoint payload type code system include to source/endpoint/valueset-endpoint-payload-type.xml and updated the Endpoint spreadsheet. Published R3/R4 artifacts show the resulting any/none codes and definitions in the Endpoint payload type code system.

Additional context:
Endpoint is active in the current build through source/fhir.ini. The current R6 source has Endpoint.payload 0..*, Endpoint.payload.type 0..*, and Endpoint.payload.mimeType 0..*, with payload.mimeType text explicitly allowing unspecified MIME types including no content depending on connectionType. Later Endpoint decisions refactored but did not remove the FHIR-10763 behavior: FHIR-34261 relaxed payload type cardinality, FHIR-20530/FHIR-28467 changed the value set to import THO/IHE format-code content while retaining the endpoint payload type code system, and FHIR-39617 clarified how payload.type, payload.mimeType, and profiles advertise content.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The current authoritative Endpoint source and terminology composition already support no-payload/open-ended endpoints and the any/none payload type concepts requested by FHIR-10763.

Recommendation:
Keep this commit as a no-change audit. No core FHIR follow-up is needed for FHIR-10763; future terminology maintenance should preserve the THO endpoint-payload-type any/none codes because the core value set imports that code system.
