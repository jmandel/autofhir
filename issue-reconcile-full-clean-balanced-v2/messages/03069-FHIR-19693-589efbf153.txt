FHIR-19693: Audit MedicationDispense receiver RelatedPerson support

Issue request:
FHIR-19693 is a Published/Persuasive Pharmacy change request asking that MedicationDispense.receiver allow RelatedPerson so a dispense can record a family member or similar related person who picked up the medication. It was raised against STU3, voted 5-0-0 on 2018-12-17, and applied for R5 with the resolution "Add relatedPerson."

Initial application:
The Jira application comment cites applied commit aa42e5dcc1e780bf1fa001dc784d2801f6d3b1d4 from 18Feb2019. That merge contains implementation commit 9d4a0fe09370e2b75ede4debcff124f36c3d3d7e, which changed the then-authoritative MedicationDispense spreadsheet receiver type from Reference(Patient|Practitioner) to Reference(Patient|Practitioner | RelatedPerson | Location) and broadened the receiver short/definition text. The current StructureDefinition source introduced by later source refactoring carries RelatedPerson forward on MedicationDispense.receiver.

Additional context:
MedicationDispense is active and approved in source/fhir.ini, so source/medicationdispense/structuredefinition-MedicationDispense.xml is in current build scope. Later receiver-family decisions did not reverse RelatedPerson: FHIR-19698 added PractitionerRole, FHIR-50109 added Organization and updated the receiver definition, FHIR-42843 rejected adding Person while affirming RelatedPerson as the receiver representation for non-patient/non-practitioner pickups, and FHIR-20209 is already represented on the combined branch as a no-change audit for the duplicate RelatedPerson request. Zulip and Confluence reference searches found no conflict; the Pharmacy 2018-12-10 Confluence notes explicitly record the FHIR-19693 need to add RelatedPerson and the 5-0-0 motion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active MedicationDispense StructureDefinition already lists RelatedPerson among the MedicationDispense.receiver target profiles, and the local search parameter merely indexes the reference element without constraining target types. Adding redundant prose would not change implementer understanding.

Recommendation:
Keep this no-change audit commit as-is. No core FHIR source follow-up is needed for FHIR-19693 unless a future Pharmacy decision reopens the broader MedicationDispense.receiver target list.
