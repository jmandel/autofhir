FHIR-30383: Audit Subscription filter clarification

Issue request:
FHIR-30383 was a Published/Persuasive R5 FHIR-I clarification request asking how Subscription.filterBy behaves when a subscription topic has multiple triggering resource types. The resolution required additional text stating that all matching filters need to match, with an example showing that behavior.

Initial application:
The issue was applied by 8bfd3a8a002530fb2843e2b46e0a34ce6d560d7a, which updated the active Subscription StructureDefinition filterBy definition to say only conditions applicable to the resource are evaluated and added Subscription framework guidance explaining that filters apply only to the resources they are listed by and that all filters applying to a resource must match.

Additional context:
The January 2021 Zulip discussion that prompted the ticket distinguished AND behavior for multiple filters on one resource trigger from OR-like evaluation across separate resource triggers. The July/August 2021 block-vote trail included FHIR-30383. Later Subscription work, including the resourceType-to-resource rename, preserved the FHIR-30383 semantics and only adjusted current element names/formatting.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current active build inputs still contain the requested clarification in source/subscription/structuredefinition-Subscription.xml and source/subscriptions.html, and the narrative page is in the active hierarchy while Subscription is an active resource in source/fhir.ini.

Recommendation:
Keep this audit commit as-is. No further core source change is indicated for FHIR-30383 unless a future work-group decision changes multi-resource Subscription filter semantics.
