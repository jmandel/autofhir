FHIR-36334: Audit FHIRPath collection cardinality wording

Issue request:
FHIR-36334 was a Published/Persuasive FHIR-core change request for R5 asking that FHIR-defined FHIRPath functions define their behavior for input collections with more than one element. The request specifically called out hasValue(), getValue(), memberOf(), subsumes(), subsumedBy(), and htmlChecks as singleton/error cases and ofType() as a collection-preserving case.

Initial application:
The issue was applied by git commit b97b828202710802aebb6b743dc18ac3fba16cc1, which changed source/fhirpath.html to add explicit single-input, empty-input, and collection behavior for the functions named in the Jira request. The current source still contains that applied wording, with later editorial refinements.

Additional context:
The originating Zulip thread records the concern that singleton FHIRPath functions should say what happens for repeating input collections, and the FHIR-I May 2022 WGM minutes record a 15-0-0 Persuasive motion for FHIR-36334. The companion FHIR-36335 was moved to ITS for the separate base FHIRPath specification and is outside the FHIR-core source decision. Later R6 ballot tickets FHIR-53951 and FHIR-53960 raise broader examples, type/cardinality, and error-handling cleanup for newer FHIRPath content, but those tickets are Triaged/not final and should not be folded into this R5 reconciliation.

AutoFHIR reconciliation:
This commit intentionally makes no source change. source/fhirpath.html is in build scope via publish.ini, and its current function definitions already preserve the FHIR-36334 decision: hasValue() and getValue() require a single FHIR primitive or return empty; ofType() returns all matching items from the input collection; memberOf(), subsumes(), and subsumedBy() define singleton input/parameter behavior; htmlChecks defines single xhtml/string behavior and returns empty for collections. Editing the page now would either duplicate existing guidance or preempt later unresolved R6 cleanup work.

Recommendation:
Keep this audit commit as-is for FHIR-36334. Any remaining broad cleanup for examples, return types, cardinalities, or error-handling consistency on newer FHIRPath functions should proceed under the later R6 issues after final work-group disposition, not by reopening this already-applied R5 issue.
