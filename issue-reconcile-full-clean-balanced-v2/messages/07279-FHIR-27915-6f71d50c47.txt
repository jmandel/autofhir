FHIR-27915: Audit mapping-language metadata syntax

Issue request:
FHIR-27915 was a Published FHIR-I change request, resolved Persuasive with Modification for R5, asking to replace the mapping-language `map` metadata statement with shorthand metadata syntax. The final resolution required the mapping-language page to describe `/// elementname = fhirpathvalue` metadata declarations for Canonical/StructureMap metadata, including multiline markdown.

Initial application:
The change was applied in commit c372919350db4764cebd887053bd3bd567234faa, which replaced the old `map "..." = "..."` explanation in source/mapping-language.html with `///` metadata declarations and changed the tutorial's opening example to `/// url` and `/// name`. No prior combined-branch reconcile commit for FHIR-27915 was found.

Additional context:
FHIR-22110 proposed the older doccomments facility and was closed Not Persuasive because the FHIR-27915 approach supplied the metadata solution. The 2022 Zulip and FHIR-I minutes show the reopened discussion narrowed the syntax to metadata comments rather than full FSH, while preserving compatibility concerns; the current linked grammar supports `metadataDeclaration` and keeps `mapDeclaration` optional. Existing `.fhirmap` files that still start with `map` therefore do not contradict the final applied decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scope mapping-language page already describes `/// name{.property}* = {value}`, primitive/FHIRPath literal values, repeated and nested metadata, and triple-quoted markdown; hierarchy.xml includes the mapping-language and tutorial pages, and mapping-language.html links the ANTLR grammar that now contains matching metadata syntax.

Recommendation:
Keep this no-change audit as-is. Future work on removing or deprecating the optional legacy `map` declaration, or mass-converting existing `.fhirmap` source files, would need a separate work-group decision because FHIR-27915's final applied text and discussion support the current documented metadata syntax without forcing that broader compatibility-breaking cleanup.
