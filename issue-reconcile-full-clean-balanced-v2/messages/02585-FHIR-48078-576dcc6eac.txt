FHIR-48078: Audit Device ownership association

Issue request:
FHIR-48078 was an Applied OO change request asking for Device.owner to allow Patient, RelatedPerson, and Practitioner owners. The final Not Persuasive with Modification resolution said PHI should not be carried in Device, that ownership belongs in DeviceAssociation, and that the DeviceAssociation category/relationship wording should make ownership clear.

Initial application:
No FHIR-48078-tagged source commit was found. The same change family appears to have been applied through FHIR-44840 commits, especially 743a304f21, which removed Device.owner from the active Device definition, renamed DeviceAssociation.category to DeviceAssociation.relationship, bound it to a relationship value set with an owner code, added Organization and PractitionerRole to DeviceAssociation.subject, and preserved the existing Patient, Practitioner, and RelatedPerson subject targets.

Additional context:
FHIR-44840 and FHIR-37999 are the same ownership/DeviceAssociation family and both support using DeviceAssociation.relationship plus DeviceAssociation.subject instead of broadening Device.owner. Current source/fhir.ini has Device and DeviceAssociation active in the build, Device and module narrative explicitly state that Device.owner moved to DeviceAssociation.relationship, DeviceAssociation narrative says ownership/custodianship should use DeviceAssociation, and the relationship value set includes owner. OO Confluence minutes record the March 2025 ballot/block vote path for FHIR-48078 and the HCP discussion that separating ownership from Device avoids sensitive owner data in the Device resource.

AutoFHIR reconciliation:
This empty audit commit makes no source change because the current build already conveys the approved rule: ownership is represented as a DeviceAssociation relationship to the owning subject, not as a broadened Device.owner reference. Adding another local comment would restate guidance already present in the active resource definition, value set, and narrative and would not change implementer understanding.

Recommendation:
Keep this audit commit as-is. Future work, if any, should be handled under a separate DeviceAssociation cleanup issue rather than reopening FHIR-48078, because the seed request is satisfied by the current DeviceAssociation.relationship model.
