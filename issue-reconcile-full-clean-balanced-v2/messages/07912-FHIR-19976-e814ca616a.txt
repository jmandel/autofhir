FHIR-19976: Audit Subscription notification limitations

Issue request:
FHIR-19976 was a Published/Persuasive FHIR-core Subscription change request asking FHIR-I to clarify why subscription subscribers cannot assume every data update, delete, authorization change, or subscription/filter change will produce a notification. The approved resolution was to add clarifying examples adjusted for the R5 Subscription redesign.

Initial application:
The issue was applied before this reconciliation. The explicit implementation commit ba1ecb7480d6a0776e6bd122a489a84899b29aa1 added a Safety and Security paragraph explaining that security and privacy can prevent notification generation, with examples for Entered in Error deletion and confidential lab results, and tightened the Scoping Responsibilities delivery caveat. The broader R5 redesign tracked by FHIR-23738 also recorded FHIR-19976 as covered by server-advertised SubscriptionTopics and the new safety text.

Additional context:
The original Zulip discussion shows the exact concern: resources can stop qualifying because their content, referenced criteria, or authorization state changes, and the tracker was filed to clarify those complexities rather than require universal delta notifications. FHIR-I minutes from 2019-07-01 approved adding clarifying examples adjusted for the revamped design. Current source keeps the guidance on the active Subscriptions Framework page: authorization must be rechecked when sending notifications, security/privacy can prevent notifications from being generated, server/topic combinations may trigger workflows when notifications SHOULD NOT be sent, and clients are warned that some notifications might not be delivered or might be duplicated. Later Applied R6 work, especially FHIR-43516 and FHIR-47280, only aligned duplicate text and terminology; it did not reverse the FHIR-19976 rule.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build already conveys the implementer-facing limitation requested by FHIR-19976 through the active Subscription resource's link to the Subscriptions Framework page and the framework page's Safety and Security and Scoping Responsibilities sections. Adding the original STU3 examples verbatim would duplicate existing guidance and could conflict with the R5/R6 topic-based redesign.

Recommendation:
Keep this audit commit as-is. Future work on subscription notification reliability should proceed through new Jira issues if the work group wants stronger delivery guarantees or more prescriptive delta semantics; FHIR-19976 itself is already reflected in current source.
