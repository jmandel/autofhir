FHIR-16970: Audit Attachment contentType MIME search guidance

Issue request:
FHIR-16970 was a Published/Persuasive with Modification STU3 FHIR-I issue for the core datatypes page. It asked to clarify why Attachment.contentType is a code with a required MIME type binding even though MIME types are not enumerable, to note that MIME parameters such as charset may need parsing, and the accepted resolution was to add a MIME-type search note while relying on existing code datatype and binding documentation for the non-enumerable required binding point.

Initial application:
The Jira comment cites SVN revision 14048. In the git-svn history, commit 466c4233f3dce83b7ebe6c63305f9161dada150f corresponds to build@14048 and added a Searching MIME Types section to source/search.html with the DocumentReference.contenttype example, :below guidance, and a warning that servers are not required to sort MIME parameters or do formal subsumption logic. No separate Jira-tagged source commit was found for changing Attachment.contentType from code to Coding, matching the resolution that the code binding model was already appropriate.

Additional context:
The current source still defines Attachment.contentType as a code bound to the required MimeType binding, the datatype narrative explicitly permits charset and other MIME parameters, and the terminology page documents required code bindings for single external code systems including MIME Types. source/fhir.ini includes the mimetypes value set source and the search page is active source for the search rules. Later FHIR-17742 extended the same MIME search section to cover first-segment :below searches such as image, so the current text reflects both the original FHIR-16970 application and later compatible refinement.

AutoFHIR reconciliation:
Published an empty no-change audit commit. The current source already conveys the accepted FHIR-16970 behavior: Attachment.contentType remains a code using the MIME Types value set, MIME parameters are documented on Attachment, and search guidance explains how :below handles MIME parameters without requiring full parameter-order subsumption.

Recommendation:
Keep this audit commit as-is. No FHIR core source change is needed for FHIR-16970; future work should only revisit this area if the work group wants to change MIME-type search semantics beyond the current FHIR-17742 refinement.
