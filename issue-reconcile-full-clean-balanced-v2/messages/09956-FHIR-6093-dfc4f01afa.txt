FHIR-6093: Audit ElementDefinition choice base metadata

Issue request:
FHIR-6093 was a Published FHIR-core StructureDefinition change request, resolved Persuasive with Modification, about validation.zip StructureDefinitions expanding choice-element paths from forms such as Observation.value[x] to type-suffixed names in snapshots. The approved resolution was to add basePath, baseMin, and baseMax to ElementDefinition, using a 0..1 base component whose child values are required when base is present.

Initial application:
The Jira comment records svn revision 5924. Git history maps this change family to ddb1f8c4e0 (#6066, svn r5923), which added ElementDefinition.base and initially populated it, followed by 74950f48e2 (#6066, svn r5924), which added ElementDefinition.base invariants. Current source no longer uses the flat basePath/baseMin/baseMax names, but represents the approved concept as ElementDefinition.base.path, ElementDefinition.base.min, and ElementDefinition.base.max.

Additional context:
FHIR-6340 is the same change family: it has the same Published/Persuasive with Modification disposition, vote, and svn r5924 application for StructureDefinition [x] path handling, and it is already represented on the combined branch by audit commit 5a8263a61f08f86c7a6f8f2b8d58321a9bfbb18f. ElementDefinition is an active normative datatype in the current build, and the current ElementDefinition narrative also explains that polymorphic paths retain [x] and that type-specific elements do not by themselves constrain the allowed types. Direct Zulip and Confluence searches found no FHIR-6093-specific community record that changes the Jira/source conclusion.

AutoFHIR reconciliation:
No source change was made. Recommendation:
