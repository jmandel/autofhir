FHIR-28489: Audit SubscriptionTopic query criteria behavior

Issue request:
FHIR-28489 was Published/Persuasive for R5 after a Subscription connectathon discussion. It asked to clarify how SubscriptionTopic resource query criteria behave when the previous or current resource state does not exist, proposing a previousNotFoundPasses-style flag and clarifying how requireBoth combines with missing previous/current state.

Initial application:
The issue appears to have been applied before final Jira publication. Git commit 4f3fcec0394f15c2c0a93f377b15fd0b866b3c9f, "First pass of FHIR#28489", added prior/current not-exists behavior fields to the old SubscriptionTopic spreadsheet with a CriteriaNotExistsBehavior code list. Later source generation/refactoring moved the current authoritative definitions to source/subscriptiontopic/structuredefinition-SubscriptionTopic.xml and renamed the old resourceTrigger path to trigger with fhir.ini aliases for the former R5 names.

Additional context:
The source/subscriptiontopic folder is active in source/fhir.ini as the SubscriptionTopic resource, and fhir.ini preserves aliases from SubscriptionTopic.resourceTrigger.queryCriteria.* to SubscriptionTopic.trigger.queryCriteria.*. The 2020 Zulip thread and Subscription connectathon page match the Jira request: make missing previous/current state behavior explicit rather than infer it from search evaluation against a missing resource. FHIR-39025 later clarified the same resultForCreate/resultForDelete/requireBoth flags, and that related issue is already represented on the combined branch.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source defines resultForCreate and resultForDelete as required-code bindings to CriteriaNotExistsBehavior, with test-passes/test-fails codes for missing criteria state, and the current narrative explains create/delete/update behavior and the requireBoth combinations in detail. That covers the seed request without adding duplicate wording or changing current R6 trigger naming.

Recommendation:
Keep this audit commit as-is. No FHIR core source change is recommended for FHIR-28489 because the current authoritative source already conveys the requested behavior and later clarification work has already been audited separately.
