FHIR-6267: Audit ServiceRequest scope clarity

Issue request:
FHIR-6267 was Published with resolution Persuasive for the DSTU1 DiagnosticRequest/DiagnosticOrder artifact. It asked for the resource introduction to be clearer about what the request resource could be used for, with example uses such as lab, radiology, vitals, family or social history, and questionnaire completion.

Initial application:
No explicit source commit mentioning FHIR-6267, GF#6267, or #6267 was found. The old DiagnosticRequest introduction already stated that the resource supported diagnostic investigations on patients, groups, healthcare devices, and environmental locations. Later source history moved the issue's artifact through FHIR-11119, which merged DiagnosticRequest into ProcedureRequest, and FHIR-13867, which renamed ProcedureRequest to ServiceRequest. Commit 03c1552138694ef3b5192027ab603c20ca28b21b then updated the active ServiceRequest introduction to say it covered a procedure or diagnostic or other service, preserving a broad request scope.

Additional context:
ServiceRequest is the active OO request resource in source/fhir.ini, while DiagnosticOrder is listed only as deleted/subsumed into ServiceRequest and DiagnosticRequest is not an active current-build resource. The current ServiceRequest Scope and Usage opening says ServiceRequest is for a diagnostic or other service on or for a patient, diagnostic investigation on a group, healthcare-device maintenance, or environmental-location testing, and it lists broad example service categories. ServiceRequest.subject also permits Patient, Group, Location, and Device and describes animals, groups, devices, and environmental scans. The 2017 Zulip merge discussion confirms implementer concern that DiagnosticRequest and ProcedureRequest boundaries overlapped; a later questionnaire-related Zulip thread treated ServiceRequest as the merged successor but also identified Task as possibly a better fit for questionnaire completion, so the old questionnaire example should not be reintroduced as a current normative clarification without a fresh decision.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The current active ServiceRequest source already answers the seed's clarity concern at the current artifact level, and adding the exact old DiagnosticRequest examples would be redundant at best and potentially misleading for questionnaire/task workflows.

Recommendation:
Keep this audit as-is. Do not add more ServiceRequest examples solely for FHIR-6267; if OO wants explicit modern guidance for questionnaire completion, family/social-history requests, or similar data-collection workflows, that should be handled as a new focused ServiceRequest/Task/Questionnaire decision.
