FHIR-17728: Audit ElementDefinition choice path invariant

Issue request:
FHIR-17728 was a Published/Persuasive technical correction for FHIR-core ElementDefinition. It reported that the element-name invariant introduced by GF#/FHIR-15678 was being enforced against ElementDefinition.path, where choice elements can legitimately include [x], and asked that [x] be allowed by the path regex.

Initial application:
The Jira comment says the issue was pre-applied with SVN #14927. The git-svn history contains commit 97ec32a1d28851e0b0ca79ef125d2824e53a9c93, "Fixed issue with validation of paths containing [x] - GF#17728", which changed source/datatypes/elementdefinition.xml so eld-20 allowed an optional (\[x]) segment in path components. The precursor GF#/FHIR-15678 is represented by commit 1df3fff3b3, which first added the element path/name constraints.

Additional context:
source/fhir.ini lists ElementDefinition as an active datatype and maps its type page to elementdefinition, so source/datatypes/elementdefinition.xml is in the current build scope. Later Published FHIR-I issues refined the same invariant family without reversing the [x] allowance: FHIR-26306 fixed anchoring and Schematron namespace/escaping, FHIR-19745 enforced the 64-character component length, and FHIR-38795 clarified the human descriptions for eld-19 and eld-20. Current source still permits optional [x] in both the error-level eld-19 regex and the warning-level eld-20 regex.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current active ElementDefinition spreadsheet already implements the requested [x] allowance for ElementDefinition.path, including the later anchoring and length corrections, and a small regex check confirms representative choice paths such as Observation.value[x] match the current expressions.

Recommendation:
Keep this no-change audit commit as-is. No further core FHIR source work is needed for FHIR-17728 unless a future work group decision changes the broader eld-19/eld-20 path rules.
