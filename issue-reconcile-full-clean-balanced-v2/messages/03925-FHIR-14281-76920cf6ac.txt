FHIR-14281: Audit TriggerDefinition type requirements

Issue request:
FHIR-14281 was a Published/Persuasive with Modification CDS issue for STU3 PlanDefinition trigger restrictions. The final resolution was to define invariants requiring the elements appropriate to each TriggerDefinition.type--named-event requires a name, periodic-event requires timing, and data-event requires data--without adding new type-specific prohibitions.

Initial application:
Jira records the issue as applied at 07099b4. Git commit 07099b45f9 added the required-type-elements invariant to source/datatypes/triggerdefinition.xml. The separate data-versus-timing invariant already existed before that application and was not introduced by FHIR-14281.

Additional context:
TriggerDefinition is an active metadata type in source/fhir.ini, and PlanDefinition.action.trigger uses TriggerDefinition, so the datatype invariant is the current build-scope source for the PlanDefinition behavior. Later applied/published TriggerDefinition work changed how the original rule should be read now: FHIR-21232 added coded named events and subscription-topic trigger support, and FHIR-53414 clarified that condition can be used with any trigger type while data-change triggers populate current/previous data context. Those later changes are already represented on the combined branch, including the FHIR-53414 reconciliation commit that aligned the current XPath invariant with the FHIRPath rule.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current TriggerDefinition source retains the issue-scoped required-type-elements invariant and now requires name or code for named-event, timing for periodic, data for data-* events, and subscriptionTopic for subscription-topic. The current condition guidance no longer carries the old condition-only-with-data restriction. Relaxing the still-existing data-versus-timing invariant would be a broader constraint change than this published issue safely supports.

Recommendation:
Keep this audit commit as-is. If the work group wants data and timing to coexist in TriggerDefinition, revisit that as a separate explicit constraint decision rather than changing it under FHIR-14281.
