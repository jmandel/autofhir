FHIR-16622: Audit contained-resource metadata rule

Issue request:
FHIR-16622 was Published/Persuasive for FHIR-core DomainResource after STU3. It asked what tags and security labels mean on contained resources and resolved to disallow security labels on contained resources with an invariant, while explicitly allowing tags in general.

Initial application:
The issue was applied in git-svn commit 1e1877180a069320e60af6aaff497ec66b8a09d3 (GF#16622 / svn r13892), which added the DomainResource.contained comment allowing meta tags but not security labels and added invariant dom-5 with expression contained.meta.security.empty(). The 2021 source rework commit 33b409a4b6d544598262f2f074ebb4b6dc466157 carried the rule into the active StructureDefinition source.

Additional context:
DomainResource is active in source/fhir.ini under [resource-infrastructure]. The current DomainResource StructureDefinition has dom-5 and the contained-resource comment, and references.html repeats that contained resources SHALL NOT contain meta.security and MAY contain meta.tag. Later FHIR-50103 directly requested weakening this meta.security rule and FHIR-I resolved it Not Persuasive/No Change, with minutes explaining that contained resources inherit the containing resource's security and separate security labels require separate resources.

AutoFHIR reconciliation:
No source change was made. The current build source already enforces the security-label prohibition and documents the allowed tag behavior requested by FHIR-16622, and later work-group evidence supports preserving the current wording.

Recommendation:
Keep this no-change audit commit. Revisit only if FHIR-I reopens the normative contained-resource metadata policy; otherwise no core source follow-up is needed.
