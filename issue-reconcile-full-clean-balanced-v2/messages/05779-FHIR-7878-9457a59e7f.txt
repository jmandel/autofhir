FHIR-7878: Audit Attachment contentType documentation

Issue request:
FHIR-7878 was a Published/Persuasive DSTU1 correction asking that Attachment.contentType narrative stop saying the element SHALL always be populated and instead agree with the formal cardinality and structure rule.

Initial application:
The issue was applied by SVN-backed git commit 5ae1eebfcac2835ff22fdbbc1cdfb452b33ab838 (#7878, svn r5937), which changed source/datatypes.html so contentType is required only when an Attachment contains data and may be present for url-only attachments.

Additional context:
FHIR-3279 had previously made Attachment.contentType 0..1 with the data-only invariant, and the current source still carries that rule. source/fhir.ini keeps Attachment in the active [types] list with datatypes.html as the default datatype page and normative Attachment metadata, so the checked source is in current build scope. A later typo issue, FHIR-13128, concerned the same invariant text but did not alter the requirement and is already represented on the combined branch.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current Attachment narrative says contentType SHALL be populated when data is present and MAY be populated when url is present, while the authoritative spreadsheet has cardinality 0..1 and the invariant data.empty() or contentType.exists(). That is the consistency FHIR-7878 requested.

Recommendation:
Keep this no-change audit commit as-is. No core source follow-up is needed for FHIR-7878 unless a future work group decision changes the Attachment contentType/data/url rule itself.
