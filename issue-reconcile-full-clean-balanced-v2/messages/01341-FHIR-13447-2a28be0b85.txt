FHIR-13447: Audit DocumentReference required-element cardinalities

Issue request:
Published FHIR-13447 was a Persuasive with Modification STU3 change request for DocumentReference asking whether required fields were truly required after a Zulip discussion about lightweight attachment use. The final decision was to relax DocumentReference.type and DocumentReference.indexed, keep DocumentReference.status mandatory, and keep both DocumentReference.relatesTo.code and DocumentReference.relatesTo.target mandatory when relatesTo is present.

Initial application:
The decision appears to have been applied in git commit 94e532a611046fcdc40df2d7d28457eeb7dad3a6, whose San Diego WGM block-vote message explicitly lists GF#13447. That commit changed the then-authoritative DocumentReference spreadsheet so DocumentReference.type went from 1..1 to 0..1 and DocumentReference.indexed became DocumentReference.date with cardinality 0..1 and an indexed alias; status remained 1..1 and relatesTo.code/target remained 1..1.

Additional context:
DocumentReference is active in source/fhir.ini. The current authoritative source is source/documentreference/structuredefinition-DocumentReference.xml after later source refactoring, and it preserves the intended cardinalities: status 1..1, type 0..1, date 0..1 with alias indexed, relatesTo 0..*, relatesTo.code 1..1, and relatesTo.target 1..1. The origin Zulip thread confirms the use case and Lloyd McKenzie's concern that indexed and possibly type did not meet the bar for mandatory elements. FHIR-13281 independently requested the indexed relaxation and was handled in the same application commit.
