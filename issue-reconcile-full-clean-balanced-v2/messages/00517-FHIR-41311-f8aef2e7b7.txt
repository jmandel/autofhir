FHIR-41311: Put availability period on availableTime

Issue request:
FHIR-41311 was an Applied/Persuasive PA change request for R6 asking that the Availability datatype include a period for each availability block and guidance for how that period interacts with a containing resource period. The final Jira resolution specifically added Availability.availableTime.period 0..1 Period with display, definition, and comment text.

Initial application:
The issue was initially applied by commit 52c81fc0778c00406004a8e1b68e22af65c97988 and merged in PR #3040 by 2f6ff2fdb4d3b03836369a6e360571211c1dc5db. That application added the requested definition/comment text to source/datatypes/availability.xml, but named the element Availability.period even though the comment and Jira resolution both identify Availability.availableTime.period.

Additional context:
The current build scope includes the Availability datatype through source/fhir.ini's active availability=metadatatypes entry, and the related Location, PractitionerRole, and HealthcareService resources are active resources that consume the Availability datatype. PA minutes from 2023 record discussion about adding a period to Availability.availableTime; PA WGM minutes from 2024 record the 8-0-0 motion and the expected relationship to root-level resource periods. No directly relevant Zulip discussion was found that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This commit moves the Period row from the root Availability level to Availability.availableTime.period, keeps the approved cardinality, datatype, display, definition, and comment text, and orders it with the other availableTime children so each availableTime repetition can carry its own applicability period.

Recommendation:
Keep this source fix. It corrects the only discovered semantic mismatch in the original application and avoids creating a single root Availability.period that would not satisfy the approved per-availableTime period request.
