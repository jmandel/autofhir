FHIR-39126: Audit search paging continuity timing

Issue request:
FHIR-39126 is a Published/Not Persuasive with Modification FHIR-core change request against the Search and HTTP pages. It asked for a hard requirement that paged search results represent the result set at the time the search operation executed.

Initial application:
The issue was applied by commit f63bcf4e297263d89809e69f2ac86ddbeb935b0d, which rewrote the HTTP paging prose and added the Paging Continuity & Integrity subsection. That application rejected a single required frozen-snapshot behavior and instead described multiple valid server strategies for maintaining or repeating paged search results while resources change.

Additional context:
FHIR-I minutes for 2022-11-14 record the same decision: this was not a hard requirement, and a future CapabilityStatement2 feature/flag could describe snapshot support. Current source/http.html is an active core RESTful API page and still tells clients that paging behavior varies, that servers may or may not use stateful paging, and that clients should not assume a particular behavior. Later applied paging guidance in FHIR-51428 added best-practice link handling but did not alter the search-result timing rule.

AutoFHIR reconciliation:
This is an empty no-change audit commit. No source change is needed because the current HTTP paging section already implements the final issue resolution by making server variation explicit rather than imposing the hard snapshot requirement requested in the issue description.

Recommendation:
Keep this audit commit as-is. Revisit only if a final CapabilityStatement2 or successor mechanism is published that lets clients discover paging snapshot behavior; that would be a new follow-up clarification rather than a missed application of FHIR-39126.
