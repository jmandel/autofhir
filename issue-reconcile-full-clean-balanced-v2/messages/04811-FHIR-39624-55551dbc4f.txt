FHIR-39624: Audit DocumentReference $generate output

Issue request:
FHIR-39624 was a Published/Persuasive R5 OO change request asking that the DocumentReference $generate OUT parameter be clarified because the operation definition used docRef/DocumentReference while the example returned a Bundle. The approved resolution was to change the OUT parameter name to return.

Initial application:
The issue was applied before this reconciliation. Jira records a March 2023 implementation link, and local source history contains 23fc079ad9, "add Consent R4 maps, and FHIR-39624", which changed the output parameter from docRef 0..1 DocumentReference to return 1..1 Bundle and aligned the operation definition with the Bundle example.

Additional context:
The initiating Zulip thread confirms the intended operation-response rule: a single out parameter named return may be returned directly as the resource, and the thread narrowed the options to return: Bundle as matching the existing example. OO minutes on 2023-02-02 approved the block vote containing FHIR-39624 by 14-0-0. A later R6 source change removed DocumentReference-generate from the core DocumentReference operations list and the ballot intro says DocumentReference.$generate moved to the API Incubator, so re-adding or otherwise changing the core operation list would not be a safe seed reconciliation.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current local OperationDefinition source still has an out parameter named return with type Bundle, and the checked example response is a Bundle containing a DocumentReference. In the current build-scope wiring, DocumentReference operations list only includes $docref, consistent with the later move of $generate out of core.

Recommendation:
Keep this audit commit as-is for FHIR-39624. If the moved API Incubator copy or the broken incubator links need review, handle that as separate R6/API Incubator work rather than changing the already-correct R5 core reconciliation.
