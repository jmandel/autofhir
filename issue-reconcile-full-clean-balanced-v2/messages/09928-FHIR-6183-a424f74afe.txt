FHIR-6183: Use stable BCP-13 reference link

Issue request:
FHIR-6183 was a Published/Persuasive FHIR-core correction for DSTU1 asking that the BCP-13 link in the Attachment.contentType description stop using the broken http://www.rfc-editor.org/bcp/bcp13.txt.html URL and use the RFC Editor BCP-13 reference instead. A reporter comment then identified http://www.rfc-editor.org/bcp/bcp13.txt as the apparent correct URL at the time.

Initial application:
No current git commit was found that explicitly mentions FHIR-6183. The current Attachment source is no longer carrying the stale direct BCP-13 URL: source/datatypes/attachment.xml defines Attachment.contentType with the MimeType binding, and source/datatypes.html describes contentType without an embedded BCP-13 hyperlink. A source-wide search found no remaining bcp13.txt.html URL.

Additional context:
The current terminology narrative still had the same BCP-13 reference family in an active explanatory link for Mime Types, using http://www.rfc-editor.org/bcp/bcp13.txt. That URL now returns 404, while https://www.rfc-editor.org/info/bcp13 returns 200 and is the stable RFC Editor information page originally requested by the issue. A 2022 Zulip thread independently tied the old http://www.rfc-editor.org/bcp/bcp13.txt value set reference to Attachment.contentType-era bindings and validator confusion. Other current BCP-13 references that use http://tools.ietf.org/html/bcp13 redirect successfully, so this reconciliation did not broaden into a style-only URL sweep.

AutoFHIR reconciliation:
Updated source/terminologies.html to point the Mime Types example link at https://www.rfc-editor.org/info/bcp13. This is a source-only hyperlink correction on an active FHIR terminology narrative page and does not change datatype, terminology, or conformance semantics.

Recommendation:
Keep this commit as-is. It preserves the already-applied Attachment.contentType model state and fixes the remaining current broken BCP-13 RFC Editor narrative link with the stable target named in FHIR-6183. Separate historical maxBinding cleanup discussed in 2022 belongs to FHIR-36705 and was not re-decided here.
