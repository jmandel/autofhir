FHIR-17256: Audit conditional PATCH expectations

Issue request:
FHIR-17256 was Published/Persuasive for STU3 and asked the RESTful API PATCH section to document conditional PATCH expectations instead of implying that conditional PATCH works exactly like Conditional Update. The accepted behavior was that servers supporting both PATCH and Conditional Update should support conditional PATCH; no matches must not create a resource and should return the documented error, one match is patched, and multiple matches error.

Initial application:
The issue appears to have been applied in git-svn commit 051eb59d8749d2453417410ed7d2d55ec1f19a1a, svn revision 14206, titled "GF#16448 + GF#17256 - conditional operations status". That commit removed the incorrect "servers SHALL support Conditional PATCH, which works exactly as described for Conditional Update" wording and added a conditional patch subsection with separate no-match, one-match, and multiple-match outcomes.

Additional context:
The current combined branch still builds source/http.html as the RESTful API page through source/hierarchy.xml. Later conditional-PATCH issues FHIR-31610 and FHIR-49646 concern adjacent terminology and URL-pattern clarifications and are already represented on the combined branch; FHIR-23077 and FHIR-17806 are related but separate CapabilityStatement and transaction questions that are also already represented. FHIR-16448 was co-applied in the same historical commit but concerns conditional-operation standards status, so it requires a separate decision and is not decided here.
