FHIR-25183: Confirm legacy binding guidance

Issue request:
FHIR-25183 was a Published FHIR-core change request, resolved Not Persuasive with Modification for R5, asking for guidance on how legacy, patient-provided, third-party, international, or otherwise poorly coded data should be handled when required or extensible value set bindings make mapping difficult.

Initial application:
The issue was applied by commit 20773ceb3e13dbd52890f695c523c2b7e6cddada, "FHIR-25183 - Added additional guidance on bindings.", which added a "Bindings and legacy data" section to source/terminologies.html. That section described required/extensible binding consequences for legacy or external data, pointed specification authors to Additional Binding/current binding capabilities, and explained use of Resource.meta.profile plus _profile search for clients that need only IG-conformant instances.

Additional context:
The Jira resolution text named the Best Practices for Implementers page, but the Jira related page and URL were the core terminologies page and extensible binding section. The current source keeps the guidance on the active Using Codes/terminologies page, adjacent to binding strength and conformance expectation text. Later terminology edits preserved the section and updated the Additional Binding link to the in-build ElementDefinition binding.additional definition. Confluence minutes from 2022-05-16 record the FHIR-I motion and rationale: additional-binding can specify whether a binding applies to all data or only current data, while the group did not need to solve per-instance current/non-current signaling. The linked Zulip thread supports the same outcome and records the rejected meta.tag-style non-conformance flag discussion. Duplicate FHIR-25184 is the same request and does not need a separate commit.

AutoFHIR reconciliation:
This audit commit makes no source change. The current active source already gives implementers the material guidance required by the issue family: legacy/external data still has to respect binding conformance rules, Additional Binding/current can express stricter expectations for current data, and Resource.meta.profile can mark instances that actually conform to a supported IG. Adding duplicate prose to best-practices.html would not change implementer understanding and would risk divergence from the terminology page that owns the binding rules.

Recommendation:
Keep this no-change audit commit. Revisit only if the work group wants a new, broader non-terminology best-practice section for invalid base-FHIR data generally; that broader policy was explicitly left open in the discussions and is not necessary to reconcile this published terminology-binding issue.
