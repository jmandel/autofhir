FHIR-19597: Audit systemless quantity search clarification

Issue request:
FHIR-19597 was a Published/Persuasive FHIR-I change request from STU3 asking the core search page to clarify expected Quantity search behavior when a client supplies a unit code without a system, especially whether servers match Quantity.code, Quantity.unit, or both.

Initial application:
The issue was applied by git commit 7c9884b2adc8f3a572d8ca491f2be92f5e76a90e ("FHIR-19597 - Clarify system-less quantity search."), which changed source/search.html to add explicit Quantity search syntax forms, including the systemless form that matches by value and code or unit. A follow-up same-day commit 44a2455d847 placed that systemless form after the system/code form in the current ordering.

Additional context:
The related implementers Zulip thread shows the origin poll split and Lloyd McKenzie's interpretation: when both code and system are specified, match Quantity.code plus Quantity.system only; when only code is specified, match Quantity.code or Quantity.unit. FHIR-17790, already represented on the combined branch, is related background for optional Quantity units but did not change this systemless matching rule. Confluence searches found no work-group minutes or later records contradicting the Jira/Zulip/source conclusion.

AutoFHIR reconciliation:
This is an empty no-change audit commit. Current source/search.html is an active core search narrative page and already states that [parameter]={[prefix]}[number]||[code] matches a quantity by value and code or unit, with the example Observation?value-quantity=5.4||mg described as matching either Quantity.code or the stated human Quantity.unit. No source edit is needed to preserve implementer understanding of the Published issue decision.

Recommendation:
Keep this audit commit as-is. The current source already carries the FHIR-19597 clarification; any purely editorial cleanup of the surrounding pre-existing grammar should be handled separately rather than expanding this reconciliation beyond the issue's semantic requirement.
