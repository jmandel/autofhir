FHIR-7796: Audit Resource(Any) profile restriction support

Issue request:
FHIR-7796 was a Published/Persuasive with Modification FHIR-core DSTU1 request for a convenient way to constrain Resource(Any) in profiles. The accepted resolution was to allow a profile to reference an implementation guide as a profile on a reference type, with finer control left for later exploration.

Initial application:
The Jira comments record svn revision 6109. Git history maps that to a0b0f17cd40a206443ba821ed846ff680ed217e4, which changed source/datatypes/elementdefinition.xml so ElementDefinition.type.profile could reference an implementation guide and required the resource to conform to at least one profile defined in that guide.

Additional context:
FHIR-7795 is the same change family and explains the implementation-guide/default-profile mechanism behind the resolution. Current source/fhir.ini keeps ElementDefinition in the active datatype build, and the current ElementDefinition source preserves the implementation-guide canonical option on both ElementDefinition.type.profile and the later ElementDefinition.type.targetProfile split used for Reference, canonical, and CodeableReference targets. ImplementationGuide.global and its Default Profiles narrative also remain in active source. Searches for direct Zulip or Confluence discussion of FHIR-7796 found no conflicting community evidence.

AutoFHIR reconciliation:
This is an empty audit commit. No source edit is needed because the current active specification already lets profile and targetProfile canonicals point to StructureDefinition or ImplementationGuide and states the corresponding at-least-one-profile conformance rule.

Recommendation:
Keep this no-change audit as-is. Future work on finer-grained profile-family constraints should be handled by a new work-group decision rather than by changing the already-applied FHIR-7796 semantics.
