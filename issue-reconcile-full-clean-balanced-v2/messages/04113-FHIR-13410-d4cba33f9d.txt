FHIR-13410: Audit ServiceDefinition removal

Issue request:
FHIR-13410 was a Published/Persuasive CDS change request from STU3 asking to deprecate/remove the ServiceDefinition resource and update Clinical Reasoning decision-support service guidance to refer to CDS Hooks for user-facing remote decision support.

Initial application:
The issue was applied before this reconciliation in SVN r13261, imported as git commit 44c2ccc5d64db10ecd5df0b3220bcd20be31e318 ("GF#13410: Removed ServiceDefinitionResource"). That commit removed ServiceDefinition from active fhir.ini resource, work group, FMM, status, and abbreviation entries; added it to [removed-resources]; removed ServiceDefinition rows and links from Clinical Reasoning pages; and rewrote decision-support service guidance away from ServiceDefinition/$evaluate. The Jira comments also record "Removed ServiceDefinition at SVN Revision 13261" and a follow-up "SVN 13353" note.

Additional context:
Current source still has legacy source/servicedefinition files and a few out-of-build historical/catalog references, but source/fhir.ini is the build-scope authority and now lists ServiceDefinition only under [removed-resources], not as an active [resources] entry. Current Clinical Reasoning guidance describes CDS Hooks, PlanDefinition/$apply, a cqf-cdsHooksEndpoint extension, and the Using FHIR Clinical Reasoning with CDS Hooks IG. Later Zulip and Confluence evidence is consistent with the same interpretation: ServiceDefinition was deprecated/removed in favor of CDS Hooks-oriented guidance.

AutoFHIR reconciliation:
This empty audit commit intentionally makes no source changes. The current build-scoped specification already implements the Jira decision: ServiceDefinition is not an active resource, the release history notes its removal, and the Clinical Reasoning module directs implementers to CDS Hooks-based guidance.

Recommendation:
Keep this audit commit as-is. Do not edit the legacy source/servicedefinition folder or old catalog/history references as part of FHIR-13410 unless a separate maintainer cleanup decision says those out-of-build artifacts should be purged; no current-spec correction is needed for this issue.
