FHIR-16950: Audit primitive integer size clarification

Issue request:
FHIR-16950 was a Published/Persuasive FHIR-I change request raised against STU3 datatypes. It asked whether unsignedInt and positiveInt were specializations of the 32-bit integer type, independent unsigned widths, or otherwise size-limited, and its final resolution was to note that all integers are constrained to 32-bit numbers.

Initial application:
The issue was applied by git-svn commit 2f25071c64f0b50b23e620ac55e77e794ab692a7, which matches the Jira comment for svn 14286. That commit changed source/datatypes.html to give integer the signed 32-bit range and to give unsignedInt and positiveInt explicit upper bounds of 2,147,483,647.

Additional context:
The current build scope routes primitive type pages through datatypes.html, and source/fhir.ini marks integer, positiveInt, and unsignedInt as ranged primitive types. Later datatype-page refactors and reordering preserved the same integer, positiveInt, and unsignedInt range semantics. The active primitive spreadsheet also models unsignedInt and positiveInt as based on integer, with no current positiveInt plus-sign regex, so the inherited 32-bit interpretation is not contradicted by the primitive source.

AutoFHIR reconciliation:
This audit commit makes no source change because the current source already conveys the requested rule: integer is limited to -2,147,483,648..2,147,483,647, positiveInt is 1..2,147,483,647, and unsignedInt is 0..2,147,483,647.

Recommendation:
Keep this no-change audit as-is. No follow-up source work is needed for FHIR-16950 unless a future work group decision wants to change primitive integer range semantics.
