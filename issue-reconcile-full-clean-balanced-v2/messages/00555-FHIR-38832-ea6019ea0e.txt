FHIR-38832: Audit Measure linkId application

Issue request:
FHIR-38832 was a Published/Persuasive R5 CQI change request asking to add linkId elements to Measure and MeasureReport so MeasureReport groups and populations can be linked explicitly to the corresponding Measure groups and populations without relying on non-unique code values or internal Element.id values. The resolution also called for backwards-compatible support for code, id, and ordering fallback behavior.

Initial application:
The Jira comment points to f9f70c4bbb4606c854d3ed18e86355b9dd2bc70f, which added linkId elements to source/measure/structuredefinition-Measure.xml and source/measurereport/structuredefinition-MeasureReport.xml. The current build-scope source still has Measure.group.linkId, Measure.group.population.linkId, MeasureReport.group.linkId, and MeasureReport.group.population.linkId, and the implementation also added parallel linkIds for stratifier-related and supplementalData elements.

Additional context:
Measure and MeasureReport are active resources in source/fhir.ini. Later Applied issue FHIR-49670 clarified the same Measure-to-MeasureReport correspondence family in R6 by adding SHALL/SHOULD guidance for MeasureReport group, population, stratifier, code, description, and backwards-compatible id support; that later decision reinforces rather than reverses the FHIR-38832 application. The clinical reasoning quality reporting source also explains that the group, population, and stratifier linkIds correlate MeasureReport content back to Measure content. Community searches found no conflicting FHIR-38832 discussion, and a later Zulip implementation discussion described R5 linkId as the explicit replacement for R4 id-based correlation.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The authoritative resource definitions and current narrative already convey the concrete linkId mechanism requested by FHIR-38832, preserve backwards-compatible id handling, and include later code/correspondence clarification from FHIR-49670. Adding another fallback-priority paragraph would duplicate existing element-level guidance without correcting a current semantic defect.

Recommendation:
Keep this no-change audit. If the work group wants processor-specific warning behavior for ordering-only MeasureReports beyond the current data model and narrative, handle that as a new clarification rather than reopening the already-applied FHIR-38832 source changes.
