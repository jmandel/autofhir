FHIR-25048: Audit choice-type search parameter filtering

Issue request:
FHIR-25048 was Published with resolution Persuasive with Modification. It asked that search parameters whose expressions point at choice elements, specifically Procedure-date on Procedure.occurrence[x], not expose irrelevant datatypes; the accepted resolution said the filter should be created by tooling based on the declared search type.

Initial application:
The issue was applied in d1f2f1ca6e, which updated checked-in search parameter bundles for Procedure-date and parallel choice-type search parameters to add type filters such as dateTime, Period, and Timing. A later cleanup in 7b140eccee changed Procedure-date from the FHIRPath as() form to ofType() after FHIRPath behavior was clarified.

Additional context:
Procedure remains an active resource in source/fhir.ini, and source/procedure/bundle-Procedure-search-params.xml is the current build-scope search parameter bundle. Related Procedure occurrence datatype work, including FHIR-20627, is already represented on the combined branch and supports the current Procedure.occurrence[x] datatype set that includes Timing. ChargeItem and MedicationUsage historical files touched by the original commit are no longer active current core resource directories; MedicationStatement carries the corresponding filtered effective[x] expression in the current source.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current Procedure-date has path Procedure.occurrence[x], type date, and expression Procedure.occurrence.ofType(dateTime) | Procedure.occurrence.ofType(Period) | Procedure.occurrence.ofType(Timing). A strict scan of current search parameter bundles found no non-template choice search parameter block matching this issue's unfiltered pattern after excluding boolean existence searches and already-explicit FHIRPath type filters.

Recommendation:
Keep this audit commit as-is. The current source already implements the published FHIR-25048 decision, and adding redundant prose or re-editing generated search parameter bundles would not change implementer understanding.
