FHIR-5733: Audit versionId ordering and uniqueness wording

Issue request:
FHIR-5733 was Published/Persuasive for DSTU1 FHIR-core BaseResource metadata. It asked the specification to state explicitly that version ids have no required ordering semantics and that the same version id must never be reused for two different versions of the same resource.

Initial application:
The issue was applied by git-svn commit 7c468fa4303fbf3163e4ba56c13c3a8c375ea4d3, imported from svn revision 4486, which added the no-fixed-order sentence and the versionId reuse prohibition to source/resource/resource-notes.xml. The current source still contains those two clarifications in the active Resource metadata notes.

Additional context:
source/fhir.ini keeps Resource in the active infrastructure/resource build, so source/resource/resource-notes.xml is in current build scope. Later same-row changes for FHIR-29685 and FHIR-11259 adjusted REST operation wording and caveated versionId changes when versioning is unsupported, but they preserved the FHIR-5733 ordering and per-resource uniqueness rules. The HTTP contention text independently says servers may generate version ids however they wish as long as the ids are valid and unique across all versions of the same resource. Targeted Zulip and Confluence searches found no conflicting community decision; a 2026 implementer thread instead treated versionId as opaque/non-sortable.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active source already states that clients cannot infer chronological order from numeric or alphabetic versionId ordering and that the same versionId can never identify more than one version of the same resource.

Recommendation:
Keep this no-change audit commit. No follow-up source work is needed for FHIR-5733 unless a future work-group decision changes the opaque version-id model or adds a separate deterministic history ordering mechanism.
