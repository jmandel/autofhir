FHIR-23721: Audit NamingSystem canonical URL application

Issue request:
FHIR-23721 was Published with a Persuasive resolution for R5. It asked to resolve the inconsistency where NamingSystem was treated as having a canonical url, by adding NamingSystem.url 0..1, explaining that this url identifies the NamingSystem record/registration rather than the code or identifier system being described, advising that it SHOULD NOT be one of the preferred identifiers, and updating examples.

Initial application:
The source history contains a67c98716e17a00b4bd8fa24342349df6b2947eb, explicitly titled "FHIR-23721 NamingSystem is stated to have a .url property", which added the NamingSystem.url narrative guidance and temporarily changed the url element definition to emphasize the naming system record/definition. Current source/fhir.ini includes NamingSystem as an active resource, current source/namingsystem/structuredefinition-NamingSystem.xml defines NamingSystem.url as 0..1 on a MetadataResource-derived resource, and the NamingSystem examples all include distinct url values alongside uniqueId entries.

Additional context:
Later canonical/metadata-resource cleanup, including ab0ada522243d1ecd280228fc660c8628115a383 and 49b86f8a6978650d8f8a6d36d27dee0433e455bc, standardized the element-level canonical URL wording back toward the shared canonical-resource text. That does not undo the issue because source/namingsystem/namingsystem-notes.xml still gives the issue-specific rule: NamingSystem.url identifies the registration/description itself, is not the preferred identifier for the described system, and SHOULD NOT be the same as a URL in the preferred identifiers list. The Jira-cited Zulip Definition pattern thread supports that distinction; Confluence and issue-key community searches did not reveal a later contrary decision.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The active current source already conveys the required semantics through the 0..1 url element, the NamingSystem.url notes, and updated examples, so restoring duplicate issue-specific prose into the element definition would be redundant and could drift from the canonical-resource wording maintained by later edits.

Recommendation:
Keep this audit commit as-is. Revisit only if the work group specifically wants the conformance element definition itself to restate the record-versus-described-system distinction in addition to the existing NamingSystem notes.
