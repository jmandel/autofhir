FHIR-3001: Audit procedure order support

Issue request:
FHIR-3001 was a Published, Persuasive with Modification change request stating that Procedure could not be ordered under the then-current order guidance because Procedure did not define how it represented something requested rather than something already done. The recorded decision was to create a new resource, ProcedureOrder/ProcedureRequest, rather than make Procedure itself carry request mood.

Initial application:
No commit explicitly tagged FHIR-3001 was found in the source history. The issue comment says "ProcedureRequest is defined now," and git history shows commit 48e489b1c7 added ProcedureRequest as an active resource in source/fhir.ini with introductory text saying it represented planned, proposed, or ordered procedures.

Additional context:
Current FHIR no longer has ProcedureRequest as a standalone resource; source/fhir.ini records that ProcedureRequest was merged into ServiceRequest. Both Procedure and ServiceRequest are active current-build resources. ServiceRequest now represents orders, proposals, and plans for diagnostic or other services, including procedures and surgeries, while Procedure remains an event resource with Procedure.basedOn able to reference ServiceRequest. Negative Zulip and Confluence searches found no contrary community record for FHIR-3001 or the procedure-ordering question.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current specification already provides the requested procedure-ordering capability through ServiceRequest and links performed procedures back to the request through Procedure.basedOn, so adding new Procedure wording would be redundant and could blur the request/event boundary the original resolution preserved.

Recommendation:
Keep this audit commit as-is. Future work should only revisit this if Patient Care or Orders and Observations decide to change the ServiceRequest/Procedure request-event boundary; no FHIR core source edit is needed for FHIR-3001 now.
