FHIR-18091: Audit Device definition split

Issue request:
FHIR-18091 is a Published/Persuasive with Modification STU3 OO issue for FHIR-core-DeviceDefinition. It asked to split the old Device element definition so the conformance definition would say only that a device is a manufactured item used in healthcare without substantial change, while examples of medical and non-medical devices would be comments rather than part of the definition.

Initial application:
The Jira comment points to commit c4720c1e9558fe9b60e0d80228a62d3336c77c1c, which changed the then-current source/device/device-spreadsheet.xml by replacing the long Device definition with the concise manufactured-item wording and moving the device examples into the comment column. Current source no longer uses that spreadsheet, but the current active Device StructureDefinition keeps the concise definition requested by the issue.

Additional context:
Device and DeviceDefinition are both active resources in source/fhir.ini. Current Device narrative already carries the medical and non-medical examples as scope/use text, so implementers still see the explanatory material without putting it back into the formal root definition. DeviceDefinition has since been revised by later Applied R6 issues, including FHIR-47051, FHIR-47903, and FHIR-47908, to define a kind/model or broader category of device; that later text supersedes the STU3 Device wording and should not be overwritten with the older comments.

AutoFHIR reconciliation:
This is an empty no-change audit commit. No source edit is needed: the current Device definition has the requested concise meaning, the explanatory examples are present in active narrative source, and the current DeviceDefinition wording is governed by later R6 decisions rather than the old STU3 Device comments.

Recommendation:
Keep this audit commit as-is. Do not add the FHIR-18091 example prose back to DeviceDefinition or duplicate it in the Device root element comment unless OO explicitly reopens that modeling choice; the current source is consistent with the applied STU3 change and later R6 DeviceDefinition decisions.
