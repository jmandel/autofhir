FHIR-31859: Audit medicinal package link direction

Issue request:
FHIR-31859 was a Published FHIR-core BR&R change request resolved as Persuasive for R5. It reported that MedicinalProductDefinition could not point to PackagedProductDefinition because the product-to-package and package-to-product links were bidirectional when many products must point to fewer package definitions. The accepted resolution was to remove the bidirectional links.

Initial application:
The issue was applied in source history before this reconciliation. Git 700d56df5d removed the PackagedProductDefinition target from MedicinalProductDefinition.packagedMedicinalProduct by changing it from a CodeableReference to a CodeableConcept. Git aa2f228c82 then removed the remaining MedicinalProductDefinition.package.package Reference(PackagedProductDefinition) and updated examples so PackagedProductDefinition pointed back to the medicinal product instead.

Additional context:
MedicinalProductDefinition and PackagedProductDefinition are active current-build resources in source/fhir.ini. Later related work changed the package-side relationship name from subject to packageFor for FHIR-31776, and FHIR-31782 removed the obsolete MedicinalProductDefinition.package backbone. A previously published AutoFHIR commit for FHIR-31863 on the combined branch corrected stale productFor narrative references to packageFor, so the current source consistently describes the one-way package-to-product relationship.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current MedicinalProductDefinition.packagedMedicinalProduct is only a CodeableConcept and current MedicinalProductDefinition has no Reference targetProfile to PackagedProductDefinition. Current PackagedProductDefinition.packageFor is the active Reference to MedicinalProductDefinition, preserving the one-way relationship required by FHIR-31859.

Recommendation:
Keep this audit commit as-is. The current source already reflects the published decision, and adding or removing additional prose would be redundant rather than a necessary specification correction.
