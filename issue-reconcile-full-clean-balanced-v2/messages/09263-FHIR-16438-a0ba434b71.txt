FHIR-16438: Refer HTTP search text to general parameters

Issue request:
FHIR-16438 was Published/Persuasive with Modification for STU3. It asked for _pretty to be defined clearly and for the HTTP/search pages to distinguish general parameters that can be used on normal interactions from search-only/result-control parameters, including avoiding wording that treated _format as the only general parameter.

Initial application:
The issue was initially applied by SVN r14192, represented in git as 69bc784817a08f775619849c0e5374d09748b179, which added the HTTP General parameters table containing _format, _pretty, _summary, and _elements and adjusted search.html to mention _format and _pretty as parameters defined for all interactions. The current HTTP page retained the general parameter definitions, including the _pretty section.

Additional context:
Later search-page work rewrote and split the search summary tables. FHIR-32070 and FHIR-36879 clarified that search parameters, search result control parameters, and generic HTTP/general parameters are distinct; FHIR-36879 specifically records that _format and _pretty are HTTP parameters rather than SearchParameter resources. In the current source, the search introduction had regressed to saying only _format works like other interactions, and http.html still had two _format-only references near the general-parameter material.

AutoFHIR reconciliation:
This commit updates the active core source pages so the search introduction links to the general RESTful API parameters as a group, removes the _format-only parenthetical from the HTTP header note, and changes the history interaction note to refer to the general parameters rather than the standard _format parameter. No computable SearchParameter resources are added because later Jira/Zulip evidence says _pretty and _format are not SearchParameter resources.

Recommendation:
Keep this source fix. It restores the FHIR-16438 distinction without broadening the search result parameter table or duplicating the existing _pretty definition, and it remains consistent with the later SearchParameter-registry decisions.
