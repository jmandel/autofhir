FHIR-18296 was Published/Persuasive with Modification for STU3 as a non-substantive FHIR-I change request. It asked the specification to clarify ElementDefinition.pattern[x] behavior for arrays, primitives, and complex objects, especially whether a patternCodeableConcept with one coding allows additional codings and whether matching is recursive.

Initial application:

ElementDefinition is an active datatype/page in source/fhir.ini, so source/datatypes/elementdefinition.xml is the authoritative build input for the definition text. Later same-family issues FHIR-33316 and FHIR-36700 refined the same pattern[x] paragraph for R5, including the distinction between nested arrays and pattern[x] on a repeating element; both are already represented on the combined branch. The current source reflects those later clarifications while preserving the FHIR-18296 recursive matching semantics.

AutoFHIR reconciliation:
No source change was made. The current ElementDefinition.pattern[x] definition already says that primitive values match exactly, that elements within a pattern constraining an array recursively match at least one element from the instance array, and that complex object properties recursively match. The profiling page also summarizes that pattern values allow additional values such as extra codings, ids, or extensions, so the specification already answers the seed issue without needing duplicative prose.

Recommendation:
Keep this no-change audit commit. The current FHIR-core source is correct for FHIR-18296 after considering later FHIR-33316/FHIR-36700 clarifications; only revisit if FHIR-I reopens the substantive behavior of pattern[x] on repeating elements.
