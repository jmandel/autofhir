FHIR-16958: Audit Identifier case sensitivity wording

Issue request:
FHIR-16958 was a Published/Persuasive FHIR-core datatypes change request from the May 2018 Core Norm Infrastructure ballot asking whether Identifier.value could be made unconditionally case sensitive. The accepted resolution changed the rule to say that Identifier.system is always case sensitive, while Identifier.value is treated as case sensitive unless knowledge of the Identifier.system makes non-case-sensitive processing safe.

Initial application:
The Jira comment records application in SVN revision 14160. In the Git history, commit a5c90c3db3cc87902faf8b096c1fdc5f179853fc (2018-07-29, "GF#16131, GF#16940, GF#16958, GF#16959, GF#16966: documentation improvements on data types, + precision extension") added the requested Identifier.system and Identifier.value wording to source/datatypes.html and source/datatypes/identifier.xml. Later formatting and spreadsheet refresh commits preserve that rule in the current source.

Additional context:
source/fhir.ini lists Identifier as an active datatype, so source/datatypes.html and source/datatypes/identifier.xml are current build inputs. A bounded Jira search for identifier value case sensitivity found FHIR-16958 as the only final core issue directly matching this request; the other apparent follow-up was a Triaged US Identity Matching issue outside the current core source-edit scope. Exact-key Zulip and Confluence searches found no community record that conflicts with the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current datatype narrative says "Identifier.system is always case sensitive" and that Identifier.value is treated as case sensitive unless knowledge of the Identifier.system allows safe non-case-sensitive processing; the Identifier.system and Identifier.value spreadsheet rows also carry the same rule.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-16958 unless the work group separately wants an editorial typo cleanup of the existing word "processer", which would be outside this issue's semantic reconciliation.
