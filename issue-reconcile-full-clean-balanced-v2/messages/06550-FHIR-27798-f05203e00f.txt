FHIR-27798: Audit DeviceDefinition classification cardinality

Issue request:
FHIR-27798 was a Published/Persuasive OO change request for R5 asking to change DeviceDefinition.type from 0..1 to 0..* so hybrid devices, such as gateway/sensor devices, can carry multiple distinct types.

Initial application:
The source history does not contain a commit whose subject names FHIR-27798, but commit b1671782cb820cad536d9bcfb7747f99544cd085 has 27798 in its commit body and changes source/devicedefinition/structuredefinition-DeviceDefinition.xml so DeviceDefinition.type max changes from 1 to *. Later FHIR-29726 commits, including b04b42f1da41162494f02a7dbfb3cb64936dd81e, refactored that repeated CodeableConcept into repeated DeviceDefinition.classification with required classification.type, preserving the ability to record multiple classifications/types.

Additional context:
DeviceDefinition is active in the current build through source/fhir.ini, and fhir.ini records the R5-to-current mapping DeviceDefinition.type=@DeviceDefinition.classification.type. Published R5 already has DeviceDefinition.classification 0..* with classification.type 1..1. FHIR-20579 is the earlier duplicate DeviceDefinition.type request and explicitly says it was resolved by accepting 0..* in FHIR-27798; FHIR-27797 was the R4 version retracted by the submitter. Zulip and Confluence searches found block-vote/minutes evidence for FHIR-27798 but no conflicting later decision requiring a source change.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current authoritative source already permits multiple device classifications using DeviceDefinition.classification 0..*, with each repetition carrying one classification.type CodeableConcept, which satisfies the original DeviceDefinition.type 0..* requirement after the R5 refactor.

Recommendation:
Keep this no-change audit commit. No follow-up is needed in core unless a future work group decision changes the DeviceDefinition.classification modeling.
