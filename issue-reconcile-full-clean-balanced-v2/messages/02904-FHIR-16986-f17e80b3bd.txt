FHIR-16986: Audit Timing repeat range wording

Issue request:
FHIR-16986 was a Published/Persuasive FHIR-core datatypes request to clarify the relationship between Timing.repeat count/countMax, duration/durationMax, frequency/frequencyMax, and period/periodMax. The approved resolution required each base element to state that its corresponding Max element makes it the lower bound, and each Max element to follow the existing frequencyMax range pattern.

Initial application:
The issue was applied in SVN revision 14076, now git commit 3c90bd518312a0c35842ca968584ee9d017dba8c, which changed source/datatypes/timing.xml definitions for count, countMax, duration, durationMax, frequency, and period to add the lower-bound/range wording. The Jira comment cites the same SVN revision.

Additional context:
Timing is an active normative datatype in source/fhir.ini, so source/datatypes/timing.xml is in current build scope. The current source still contains the lower-bound language for count, duration, frequency, and period and the matching range language for the Max elements. Existing Timing.repeat invariants also require countMax, durationMax, and periodMax to have their base element, reinforcing that these Max elements are paired range upper bounds rather than standalone open ranges. A 2017 Zulip thread shows the underlying implementer confusion about count/countMax but does not conflict with the applied Jira resolution. Confluence searches found no contrary work-group record.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative Timing spreadsheet already implements the requested clarification, and adding redundant prose or polishing minor wording would not change implementer understanding of the range semantics.

Recommendation:
Keep this audit commit as-is. No follow-up core source work is needed for FHIR-16986 unless a future work-group issue reopens the broader question of open-ended Timing ranges.
