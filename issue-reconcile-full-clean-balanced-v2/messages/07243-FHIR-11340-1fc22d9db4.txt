FHIR-11340: Clarify CarePlan request intent

Issue request:
FHIR-11340 was Published with a Persuasive with Modification resolution for DSTU2 DiagnosticRequest. It asked the DiagnosticRequest/CarePlan relationship to say that CarePlan typically references DiagnosticRequest with a stage of "plan" or "proposal", though the requests may have to be initiated and authorized outside of the CarePlan.

Initial application:
The issue was initially applied in git commit ccaebaf26211addd4753b390f79e43735583f08a, which replaced the DiagnosticRequest boundaries paragraph with the approved CarePlan plan/proposal wording. Later request-resource work merged DiagnosticRequest into ProcedureRequest under FHIR-11119, and commit 2fa71284c7cb0518c0d71318cc883f828b33c1bc removed the old DiagnosticRequest-specific boundaries paragraph while rewriting the merged ProcedureRequest page.

Additional context:
DiagnosticRequest is now listed as a removed resource, while CarePlan and ServiceRequest are active current resources in source/fhir.ini. Current ServiceRequest already represents diagnostic and other services as an order, proposal, or plan and uses ServiceRequest.intent for that distinction. The active CarePlan boundaries text still described referenced request resources as having a status of "planned" or being an active order, which no longer matches the current request pattern and loses the FHIR-11340 distinction that proposal/plan requests may need separate initiation or authorization. Zulip and Confluence searches found no non-bot or work-group evidence that changes this conclusion.

AutoFHIR reconciliation:
Updated source/careplan/careplan-introduction.xml, which belongs to the active CarePlan resource, to describe CarePlan activity references to request resources in terms of request intent: proposal or plan references may still need independent initiation or authorization, while other referenced resources may already represent active orders.

Recommendation:
Keep this source fix. It carries the approved FHIR-11340 clarification forward onto the current CarePlan/ServiceRequest surface without reviving retired DiagnosticRequest wording or changing the ServiceRequest model.
