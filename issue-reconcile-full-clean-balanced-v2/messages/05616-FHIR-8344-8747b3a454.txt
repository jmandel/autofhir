FHIR-8344: Audit Timing repeat bounds duration support

Issue request:
FHIR-8344 was a Published/Persuasive with Modification FHIR-core datatypes change request asking to support Timing.repeat.bounds as a Quantity so a medication schedule such as TID for 14 days could be represented without knowing the outpatient start date. The final recorded resolution was "Done under another task," with a Jira comment explaining that Timing.repeat.bounds[x] already had a duration.

Initial application:
No independent FHIR-8344-tagged source commit was found. The issue was satisfied by the same Timing.repeat.bounds[x] source trail already represented in the combined branch for FHIR-5951: git commit fca58ccc39dd07aaf03838155eb8654a5f713d9c changed source/datatypes/timing.xml from Period-only bounds to bounds[x] with Duration support, and git commit 2fbb4392eeaedcf258c8e4f38bbe77af755cb2d6 then added Range to the same choice element for FHIR-6252.

Additional context:
The current build scope includes Timing as an active normative datatype in source/fhir.ini. The authoritative Timing spreadsheet currently defines Timing.repeat.bounds[x] as Duration | Range | Period, and the Duration datatype is a Quantity for a length of time. The datatypes examples page includes the seed issue's exact TID for 14 days pattern using boundsDuration. A later FHIR-31559 decision chose an extension path for combining explicit start dates with Duration/Range bounds rather than changing the base Timing.repeat.bounds[x] choice. Zulip and Confluence searches for FHIR-8344 and Timing repeat bounds duration found no conflicting community decision.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The current active source already supports the requested quantity-like duration semantics through boundsDuration, and adding a generic Quantity choice would be broader than the accepted modification.

Recommendation:
Keep this no-change audit as-is. Future Timing work should preserve Duration/Range/Period as the base bounds[x] choices and use later extension-path decisions when explicit start-date plus duration/range modeling is needed.
