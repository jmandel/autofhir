FHIR-15894: Audit markdown XML tag handling

Issue request:
FHIR-15894 was a Published FHIR-core change request, resolved Persuasive for STU3, reporting that HierarchicalTableGenerator choked when markdown text contained embedded XML-like tags such as `<reference value=#med"/>`. The applied resolution said XML could not be processed as tags in this context, so markdown handling should use CommonMark, turn off HTML so tags are escaped, and use CommonMark backslash escaping if needed.

Initial application:
No Jira-keyed commit was found for FHIR-15894. The issue appears to have been applied directly by commit 345c7269b29819b9c86b2b3383bde64cedb300c9, made on the same day shortly after the Jira was created, with subject `fix to use commonmark`. That commit changed the old in-repository `HierarchicalTableGenerator.Cell.addMarkdown` implementation from txtmark to `org.commonmark.parser.Parser` plus `HtmlRenderer.builder().escapeHtml(true)`, which matches the Jira resolution's CommonMark and HTML-escaping behavior. Related dependency history shows CommonMark was already present before the issue and GFM table support was later added to `ivy.xml`.

Additional context:
The Java `HierarchicalTableGenerator` source that FHIR-15894 changed was removed from the current FHIR source checkout in the 2019 old-code cleanup, so there is no current in-repository generator implementation to edit. The active datatype documentation is still in build scope through `source/fhir.ini`, and current `source/datatypes.html` already says FHIR markdown uses GFM/CommonMark with inline HTML unsupported and that processors SHALL treat embedded XML tags as string content. Later Published issue FHIR-38714 explicitly clarified the same markdown rule and is already represented on the combined branch, including the correction that processors escape less-than characters before markdown processing.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The historical tooling fix matches the FHIR-15894 request, and the current build-scope markdown datatype source already conveys the resulting rule for processors and implementers. Adding duplicate prose or editing removed tooling would not improve the current specification.

Recommendation:
Keep this no-change audit commit. No FHIR-core source follow-up is needed for FHIR-15894; any future runtime behavior concerns for markdown rendering should be handled in the current publisher/tooling repository rather than by resurrecting removed source in this checkout.
