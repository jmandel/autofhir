FHIR-18872: Audit Questionnaire answerValueSet invariant

Issue request:
FHIR-18872 was Published with a Persuasive with Modification resolution for FHIR-core Questionnaire. It reported that Questionnaire.item.answerValueSet's definition allowed choice and open-choice questions while the que-5 human description said only choice items could have answerValueSet; the final resolution was to update the rule language so it reflected the actual constraint.

Initial application:
The issue was applied in commit cbff33df9bd5be63e2896db96ebd360f26730d2d, which changed the then-authoritative source/questionnaire/questionnaire-spreadsheet.xml que-5 human text from "Only 'choice' items can have answerValueSet" to "Only 'choice' and 'open-choice' items can have answerValueSet." That historical source file has since been replaced by the generated StructureDefinition source used in the current build.

Additional context:
Questionnaire is active in the current build and approved in source/fhir.ini. Later Published FHIR-20396 removed choice/open-choice from Questionnaire.item.type, added coding and answerConstraint, and updated que-5 to describe answerOption on the current item types. Later Applied FHIR-40780 intentionally split answerValueSet out of que-5 into que-5b, limiting answerValueSet to coding, string, and uri and documenting how each type interprets the ValueSet. Both related issues already have Issue-Reconcile-Key commits on the combined branch, so this reconciliation should not duplicate those decisions.

AutoFHIR reconciliation:
Made no source change. The current source/questionnaire/structuredefinition-Questionnaire.xml already has que-5 human text aligned with its answerOption expression and separate que-5b human text aligned with its answerValueSet expression, and Questionnaire.item.answerValueSet carries condition que-5b. Restoring choice/open-choice wording would contradict the later published Questionnaire model.

Recommendation:
Keep this empty audit commit. No further core change is needed for FHIR-18872 unless a new work-group issue reopens the current coding/string/uri answerValueSet design.
