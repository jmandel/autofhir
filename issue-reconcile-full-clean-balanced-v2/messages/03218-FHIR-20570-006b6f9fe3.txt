FHIR-20570: Correct PlanDefinition action linkId narrative

Issue request:
FHIR-20570 was Published with a Persuasive with Modification resolution to stop relying on Element.id when matching PlanDefinition actions to realized request actions, adding optional string linkId elements to PlanDefinition.action and RequestGroup.action for R5.

Initial application:
Commit fc2803f516 added PlanDefinition.action.linkId and RequestGroup.action.linkId as 0..1 string elements. Later R5 work renamed RequestGroup to RequestOrchestration through FHIR-24619, preserving the action.linkId element, and FHIR-33169 updated the Applying a PlanDefinition narrative to use linkId but left the target element rendered as linkId>.

Additional context:
The current build has active PlanDefinition and RequestOrchestration resources, with RequestGroup mapped to RequestOrchestration in fhir.ini. The current StructureDefinition sources already contain PlanDefinition.action.linkId and RequestOrchestration.action.linkId, and CarePlan.activity has no linkId element, consistent with the final FHIR-20570 resolution naming only PlanDefinition.action and RequestGroup.action. The originating Zulip thread matches the Jira request, and no Confluence reference or conflicting community evidence was found.

AutoFHIR reconciliation:
Corrected the Applying a PlanDefinition narrative in source/plandefinition/plandefinition-notes.xml so the instructions say to set the RequestOrchestration action linkId element, not a non-existent linkId> element. No structural element changes were needed because the authoritative PlanDefinition and RequestOrchestration definitions already carry the requested optional linkId elements.

Recommendation:
Keep this source fix. It preserves the already-applied model change and removes a directly related narrative typo that could point implementers at a non-existent element name; no CarePlan source change should be made unless a later work-group decision explicitly adds a CarePlan activity linkId.
