FHIR-13065: Enforce modifier reason scope

Issue request:
FHIR-13065 was Published/Persuasive with Modification for DSTU2 and asked that modifier elements be documented with why they are modifiers. The approved resolution added ElementDefinition.isModifierReason (0..1 string) and required an invariant that isModifierReason must be present when isModifier=true and may only be present when isModifier=true.

Initial application:
The issue was initially applied in svn revision 13068, represented in git as 2923983143, which added ElementDefinition.isModifierReason and a one-way invariant requiring a reason when isModifier is true. That initial application did not enforce the reciprocal "may only be present" half of the Jira resolution.

Additional context:
ElementDefinition is in the current build scope through source/fhir.ini, including the active datatype page mapping, normative marker, and short code. FHIR-20331 later corrected the original FHIRPath expression from the unsafe bare isModifier form to the current `(isModifier.exists() and isModifier)` form, but it only addressed the one-way syntax issue and did not supersede FHIR-13065's reciprocal requirement. Zulip discussion after GF#13065 confirms the new element triggered a sweep for missing modifier reasons, with no discovered community or Confluence evidence changing the invariant semantics.

AutoFHIR reconciliation:
Updated source/datatypes/elementdefinition.xml invariant 18 so the human-readable text, FHIRPath, and XPath require isModifierReason exactly when isModifier is true. The edit preserves the FHIR-20331 corrected true test and adds the missing reciprocal guard that rejects a reason when isModifier is absent or false.

Recommendation:
Keep this source fix as-is. Regenerated build artifacts should pick up the stricter ElementDefinition invariant; no separate related issue should be marked resolved by this commit.
