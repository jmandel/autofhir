FHIR-8750: Audit extension cardinality reconciliation

Issue request:
FHIR-8750 was a Published/Persuasive FHIR-core change request from the DSTU1-to-DSTU2 period. It reported that generated profiles were defaulting referenced extension slices to Extension's base 0..* cardinality instead of inheriting the defined extension cardinality when the referencing spreadsheet omitted an explicit cardinality.

Initial application:
The issue was applied in historical svn revision 7174, now git commit e2fcdd2b2b6b5d3eb8728d1cb7f8717399f9bb9d. That commit explicitly says "#8750 - fix for extension cardinalities" and changed the old ProfileUtilities snapshot-generation workaround so extension templates no longer copied the base element cardinality; it also updated then-active SDC and Claim spreadsheet text artifacts.

Additional context:
The old affected QICore examples named in the Jira are not present in the current FHIR core source or the Extension Pack checkout. The specific old SDC/SDC-DE/Claim .sheet.txt artifacts touched by the 2015 application are no longer tracked in the current core checkout. Current source/fhir.ini still has active core profile spreadsheet entries for extensions, and current profiling.html already states that the minimum cardinality used for an extension slice in a profile must be a valid restriction on the extension definition's minimum cardinality.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The historical tooling defect was applied in 2015, the directly affected generated/source artifacts are no longer part of the current build, and the current profiling guidance already captures the relevant extension-cardinality rule without needing duplicative prose.

Recommendation:
Keep this audit commit as-is. No current core source edit is needed for FHIR-8750; any future concern about a particular IG's generated extension cardinalities should be handled in that IG or tooling context with a specific current artifact.
