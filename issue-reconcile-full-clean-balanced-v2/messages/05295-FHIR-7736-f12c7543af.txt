FHIR-7736: Audit MedicationPrescription status clarification

Issue request:
FHIR-7736 was Published/Persuasive with Modification for the DSTU1 MedicationPrescription.status definition. It asked why the medication prescription status value set included superceded/superseded as a status when replacement by a new order could instead be represented as a relationship and each order could retain its own lifecycle status.

Initial application:
No git commit explicitly names FHIR-7736. The status family was nevertheless applied in source history: commit 6dc7a59c9b fixed the spelling from superceded to superseded in DSTU1 medication/document statuses, commit 4bde19269737 added MedicationPrescription.priorPrescription for the replacement relationship, and commit 29f5a29869ef removed superseded from the medication prescription/order status value set while MedicationPrescription was renamed to MedicationOrder.

Additional context:
MedicationPrescription later became MedicationRequest. The current build includes MedicationRequest through source/fhir.ini, and the active MedicationRequest status value set and CodeSystem contain active, on-hold, ended/stopped/completed/cancelled, entered-in-error, draft, and unknown, with no superseded or superceded medication status. Current MedicationRequest.priorPrescription is a 0..1 Reference(MedicationRequest), and later FHIR-39142 clarified its wording as the order/prescription being replaced by this MedicationRequest. FHIR-8015, the closely related priorPrescription tracker, is already represented on the combined branch, and FHIR-9666 is the same status-removal follow-up audited separately.

AutoFHIR reconciliation:
This empty audit commit makes no source change because the current build-scope MedicationRequest source already resolves the concern behind FHIR-7736: superseded is no longer a MedicationRequest status, and replacement is represented by priorPrescription rather than by overloading status.

Recommendation:
Keep this audit commit as-is. Do not reintroduce a superseded medication status or add redundant explanatory prose for this old DSTU1 issue; any future refinement of basedOn versus priorPrescription should be handled as a separate Pharmacy decision.
