FHIR-16450: Audit HTTP delete reference handling

Issue request:
FHIR-16450 was a Published FHIR-I STU3 change request resolved Persuasive with Modification. It asked that the RESTful HTTP delete section clarify what happens to other resources that reference a deleted resource, with the final resolution requiring text that servers may or may not enforce business rules for deletion of resources referenced by other resources.

Initial application:
The request was applied in svn revision 14174, imported as git commit a1cd05b722493b8dbd36926a33a9e17ef2b98192, which added the requested reference-handling sentence to source/http.html. Later commit 7b129e2288476995a7a73ac45b0c50a18f3c257a only changed the restricted wording "MAY NOT" to "might not" while preserving the intended server-discretion meaning.

Additional context:
The current source/http.html delete interaction still states that a server refusing deletion for resource-specific reasons such as referential integrity should return 409 Conflict and that servers MAY choose to enforce business rules for deletion of referenced resources, but might not do so. Later FHIR-24888 adds background about finding references with _revinclude=* and explicitly treats referential-integrity support as bounded by what servers index and support; it does not reverse the delete-section discretion. Direct Zulip and Confluence searches for FHIR-16450 found no conflicting community record.

AutoFHIR reconciliation:
This commit intentionally makes no source change because the current RESTful API source already contains the clarification required by FHIR-16450 in the active delete section.

Recommendation:
Keep this audit commit as-is. No follow-up source change is needed for FHIR-16450 unless the work group later decides to alter the broader delete/referential-integrity policy.
