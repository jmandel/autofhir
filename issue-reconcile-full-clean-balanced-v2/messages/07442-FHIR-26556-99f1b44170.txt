FHIR-26556: Audit thumbnail guidance in Extension Pack

Issue request:
FHIR-26556 was a Published/Persuasive FHIR-core DocumentReference change request, raised for STU3 and applied for R5, asking for clear guidance on thumbnails in DocumentReference.content/Attachment. The final Jira resolution accepted that repeated DocumentReference.content entries may represent the same document in different formats or attachment metadata, but requested a standard thumbnail indicator extension with valueBoolean and recommended it over inferring thumbnail status from Attachment.size.

Initial application:
The issue was not applied by a commit whose message names FHIR-26556. Git history shows cebeac615e added source/documentreference/structuredefinition-extension-documentreference-thumbnail.xml and source/documentreference/implementationguide-DocumentReference-core.xml on 2022-03-17, defining a boolean DocumentReference Thumbnail extension with context DocumentReference.content. The extension URL was not the originally suggested iso21090-ED-thumbnail URL; Jira comments and Zulip show the implementers considered that ambiguity and the created extension is a DocumentReference.content boolean.

Additional context:
The current core build has Attachment and DocumentReference active in source/fhir.ini, and DocumentReference.content still says repeated content entries represent the same document in different formats, or attachment metadata. Commit dd468d4f17 removed the DocumentReference extension definitions from the R5 source during the later extension migration. The current HL7/fhir-extensions checkout owns the active trial-use StructureDefinition at http://hl7.org/fhir/StructureDefinition/documentreference-thumbnail, with context DocumentReference.content and valueBoolean. Current core retains only the OID mapping for that canonical.

AutoFHIR reconciliation:
This commit intentionally makes no FHIR core source change. The applied artifact now lives in the FHIR Extension Pack, which is outside this checkout, and re-adding the extension or duplicating usage prose in core would conflict with the current extension-pack ownership model.

Recommendation:
Keep this audit commit as-is for the core reconciliation. If the work group wants clearer wording, update the Extension Pack definition or its generated extension registry page rather than restoring the extension to core.
