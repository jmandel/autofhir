FHIR-33997: Audit _filter _has and composite support

Issue request:
FHIR-33997 was a Published/Persuasive FHIR-I change request for R5. It asked the _filter specification to clarify that _filter supports reverse chaining with _has and composite search parameters such as code-value-quantity, including the syntax and grammar needed to use them.

Initial application:
No Jira-keyed source commit was found for FHIR-33997. The issue appears to have been applied by cf2bd24c028dbbb0fbef1a09e6c96930a5b9394c, which changed the active source/search_filter.html page to add a composite code-value-quantity example, an _has example, explicit reverse-chaining guidance, hasSpecifier grammar, and a note limiting composite _filter comparisons to eq and ne. A later already-published reconciliation for FHIR-41013 corrected the same _filter composite example to use the normal composite value syntax.

Additional context:
The original #implementers Zulip thread shows the reporter asking whether _filter should support composites and _has and then filing FHIR-33997. The February 2023 FHIR-I Zulip thread shows Grahame drafting the hasSpecifier grammar and Gino confirming it looked right while noting dateChar needed ':' and 'Z', which are present in the current source. FHIR-I minutes record the March 2022 assignment to draft syntax and the August 2022 12-0-0 Persuasive vote. The _filter page is in build scope through source/hierarchy.xml and is linked from the active search page.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/search_filter.html already states that reverse chaining is allowed with _has:Resource:index1:index2, includes matching grammar, includes an _has example, includes a composite code-value-quantity example using the corrected $ composite value syntax, and says composite search parameters are evaluated under eq/ne only.

Recommendation:
Keep this audit commit as-is. The current specification conveys the approved FHIR-33997 behavior, and changing the page now would be redundant rather than corrective. Separate later issues about composite example correction or general chained-search clarification should remain tracked by their own Jira decisions.
