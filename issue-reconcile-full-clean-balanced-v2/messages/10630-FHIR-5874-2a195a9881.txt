FHIR-5874: Audit extension hierarchy rendering

Issue request:
FHIR-5874 was Published/Persuasive for DSTU1 and asked that the hierarchy view display an extension's data type rather than showing every inline extension as the generic Extension type. The Jira resolution says to display the data type of the extension in the hierarchy view and records svn revision 4557 as the application.

Initial application:
The recorded svn revision is present in the imported git history as commit 7996f50897b97db120319141c23e9a1070d853b4, whose git-svn-id is build@4557. That commit changed the old in-repository Java ProfileUtilities renderer so profiled extension rows resolve the extension definition, call getExtensionValueDefinition, and render the value definition's types instead of the Extension type; complex extensions intentionally render an empty/complex type cell. The commit subject cites old tracker number #5847, but the git-svn revision and diff match the FHIR-5874 Jira resolution.

Additional context:
The old Java publisher sources edited by revision 4557 are no longer present in the current FHIR specification checkout, so there is no current in-repo renderer source to patch for this historical tooling behavior. Current build-scope profile source still correctly models extension slices as type Extension with a profile URL; source/fhir.ini keeps FamilyMemberHistory active, and the current build uses those source profiles plus extension definitions to render profiled extension rows. Community searches found no Zulip or Confluence evidence that changes the Jira/history conclusion.

AutoFHIR reconciliation:
No source files were changed. The current build output for the active FamilyMemberHistory genetics profile shows inline extension slice rows such as extension:parent with the type cell rendered as "(Complex)" rather than the generic Extension type, while ordinary unsliced extension elements still show Extension as expected. This preserves the FHIR-5874 intent without redundant source changes.

Recommendation:
Keep this audit commit as-is. If a future hierarchy-rendering regression appears, the fix likely belongs in the current publisher/tooling repository rather than this core source checkout; for the current build, no source change is needed.
