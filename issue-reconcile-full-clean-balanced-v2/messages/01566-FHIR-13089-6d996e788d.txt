FHIR-13089: Audit compatibility guidance

Issue request:
FHIR-13089 was a Published/Persuasive with Modification FHIR-core M&M change request asking for stronger future/backward compatibility guidance on the timelines/version management page. The requested changes included renaming the backward compatibility section, defining forward and backward compatibility objectives, making clear that new codes/resources/operations/references may appear, specifying behavior for unrecognized modifier codes, adding invariant/business-rule guidance, revising operation-change wording, documenting additions to CapabilityStatements for FHIR services and core IGs, noting terminology exceptions for normative value sets/code systems generated from non-normative artifacts, stating scope for core and HL7 International normative IGs, preserving IG global profiles, allowing compatible conformance-resource reference retargeting, and drafting a governance process for technically breaking changes.

Initial application:
The historical application appears to be the SVN-derived git commit fccd01d1da946ae8d270f20c68e2b6407b3b6dec, "Updated forward/backward compatibility rules, a few Questionnaire/Response trackers", with git-svn-id build@14686. That commit aligns with the Jira comment noting SVN #14685 and rewrote source/versions.html to define forward/backward compatibility, add the compatibility rules table, permit new resources/artifacts/codes/operations, add the modifier-code handling bullet, add CapabilityStatement/Implementation Guide/Reference rows, update operation-change wording, and include the original rare technically breaking changes note.

Additional context:
The active source has been refined by later published issues in the same section rather than reverting the FHIR-13089 outcome. FHIR-24828 added the current FMG breaking-change policy link. FHIR-36755 clarified that warning and best-practice invariants may be added and that error invariants may be tied to newly introduced elements, codes, or existing narrative rules. FHIR-38876 added the current warning that permitted non-breaking changes can still make some implementations fail. The page is in build scope as a listed published page in publish.ini. Direct Jira-key, Zulip, and Confluence searches found no community evidence that conflicts with this source/history conclusion.
