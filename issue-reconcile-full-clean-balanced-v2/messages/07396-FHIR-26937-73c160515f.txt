FHIR-26937: Audit JSON integer primitive serialization

Issue request:
FHIR-26937 was a Published FHIR-I R5 change request, resolved Persuasive with Modification, asking the JSON primitive representation page to cover the newer integer-related primitive types. The accepted resolution was to add language for the new integer types and make clear that integer64 is not serialized as a JSON number but as a JSON string.

Initial application:
The issue was applied by acc7cdb646, which changed source/json.html to add unsignedInt and positiveInt to the JSON-number list and to identify integer64 with the other string-serialized primitive types. A later terminology-only cleanup, 8592e12072, changed "data type" to "datatype" without altering the serialization rule.

Additional context:
The current core source page source/json.html is the active FHIR JSON format narrative page, and its primitive section now says integer, unsignedInt, positiveInt, and decimal are represented as JSON numbers, boolean as JSON boolean, and all other types, including integer64, as JSON strings. The datatypes page independently agrees: integer64 is a JSON string because of precision concerns, while unsignedInt and positiveInt are JSON numbers. The FHIR-I 2020-04-27 minutes record the FHIR-26937 vote as adding a new integer type that is not a JSON number but a string. A later Zulip discussion and FHIR-28586 clarify that the submitter did not intend unsignedInt and positiveInt to become strings; they remain integer-valued/JSON-number primitives.

AutoFHIR reconciliation:
This commit makes no source change. The current source already implements the issue's final intent and later clarifications: integer64 is explicitly called out as JSON string, while unsignedInt and positiveInt are explicitly listed as JSON numbers.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-26937 unless a future work-group decision changes primitive JSON serialization rules.
