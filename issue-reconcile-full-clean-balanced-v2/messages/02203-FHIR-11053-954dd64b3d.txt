FHIR-11053: Audit Consent rule element support

Issue request:
FHIR-11053 was Published/Persuasive with Modification for the DSTU2 Consent resource. It asked to support common basic consent directives by adding Consent.actor, Consent.action, Consent.data, and Consent.securityLabel at the top level and by removing Consent.recipient.

Initial application:
The issue appears to have been applied in git commit 612068c15886b6624c44de5d656417bcfa7d76d3, which grouped STU3 Consent updates for GF#11053 and related ballots. That commit removed the active Consent.recipient element, added the requested root Consent actor/action/securityLabel/data fields, and retained matching exception fields.

Additional context:
Later Published Consent decisions changed the model after the original application. FHIR-13477 deliberately removed the root/exception duplication and moved actor, securityLabel, dataPeriod, data, and related rule details into a recursive rule/provision structure. FHIR-39597 later removed the provision-zero pattern, moved the base permit/deny choice to Consent.decision, and left Consent.provision as 0..* constraints or exceptions. The current build has Consent active in source/fhir.ini and defines Consent.provision.actor, Consent.provision.action, Consent.provision.securityLabel, and Consent.provision.data, with search parameters for those paths and no active Consent.recipient element.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Reintroducing the DSTU2 root element placement would conflict with later published Consent model decisions, while the current source still supports the actor/action/data/security-label semantics that FHIR-11053 required through the current provision model.

Recommendation:
Keep this audit commit as-is. Do not recreate Consent.recipient or the old duplicated root fields unless CBCC makes a new model decision; the current specification is correct for this issue when FHIR-13477 and FHIR-39597 are considered.
