FHIR-19455: Audit ImagingStudy UID guidance

Issue request:
FHIR-19455 was Published/Persuasive with Modification for the STU3 ImagingStudy resource. It asked for additional implementation guidance and examples for DICOM Study, Series, and SOP Instance UID encoding, including use of system "urn:dicom:uid" and value prefix "urn:oid:" when a DICOM UID is carried in an Identifier; its resolution also included an ACSN accession-number example.

Initial application:
The Jira comment says this was applied on branch moehrke_ii_uid. Git history does not show a commit subject explicitly naming FHIR-19455, but merge 5ccbf09b4f brought in commit 131af0770a from that branch, and that commit updated the active ImagingStudy notes and examples in the same UID/change family as FHIR-19455, FHIR-19456, and FHIR-18064.

Additional context:
ImagingStudy is an active current-build resource in source/fhir.ini. Later applied ImagingStudy decisions refined the accession-number part of the old guidance: FHIR-22118 moved accession numbers away from ImagingStudy.identifier to basedOn.identifier, FHIR-49675 restored that basedOn model after a brief R6 reversal, FHIR-46224 kept the UID and accession note subsections directly linkable, and FHIR-56033 removed remaining accession-number wording from ImagingStudy.identifier comments.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The current active source already states that Series Instance UID and SOP Instance UID are id values encoded directly, states that DICOM Study Instance UID is carried in ImagingStudy.identifier with system "urn:dicom:uid" and value prefix "urn:oid:", and includes examples with those encodings. The current accession text intentionally uses ImagingStudy.basedOn.identifier with ACSN under later applied issues, so restoring the original FHIR-19455 accession wording under ImagingStudy.identifier would be incorrect.

Recommendation:
Keep this audit commit as-is. No core-source follow-up is recommended for FHIR-19455; future accession-number changes should be handled through the later ImagingStudy accession issue family rather than by replaying the STU3 wording.
