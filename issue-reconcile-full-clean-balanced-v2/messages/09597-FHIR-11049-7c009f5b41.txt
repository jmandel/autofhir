FHIR-11049: Audit UDI AIDC carrier support

Issue request:
FHIR-11049 was Published/Persuasive with Modification for Device and asked to clarify AIDC support guidance for Device.udiCarrier, noting that AIDC could be supported if it could be distinguished from user-entered UDI carrier data.

Initial application:
The request appears to have been applied in the 2017 Device UDI commit series 2bd8c95642d3, 05a8652714ff, and d9163a93a7ba, whose messages explicitly cite [11049] and [11050]. That series split UDI carrier representation into HRF and AIDC forms and added entry-type examples/source support.

Additional context:
Device is an active resource in source/fhir.ini, so source/device/structuredefinition-Device.xml is current build input. Current Device.udiCarrier.carrierAIDC is a base64Binary element whose definition says AIDC representations can include non-printable characters and therefore SHALL be base64Binary encoded; Device.udiCarrier.carrierHRF separately carries the human-readable form. FHIR-11050 is the same change family because it added the entryType data element that differentiates user-entered from machine-read UDI data. Zulip and Confluence searches found no conflicting later community decision.

AutoFHIR reconciliation:
This commit makes no source change. The current source already supports AIDC carrier conveyance without relying on XML/JSON control characters and includes the related entry-type mechanism needed to distinguish capture methods.

Recommendation:
Keep this audit commit as-is. No core FHIR source follow-up is needed for FHIR-11049 unless a future work group decision changes the UDI carrier encoding or entry-type model.
