FHIR-20392: Audit no-filter search behavior

Issue request:
FHIR-20392 was Published with a Persuasive with Modification resolution. It asked the FHIR-core search/http pages to state that a search such as GET [base]/[type] with no filters returns all resources of that type, and that servers unable or unwilling to run an unconstrained search should return an error instead of silently applying a default filter.

Initial application:
The behavior was introduced into source/search.html before this tracker was named in git history by 142ad7624c (Fix FHIR-19523,22702,23809), then explicitly reconciled for this tracker by 6600a9d173 (FHIR-20392) on 2022-08-08. The FHIR-20392 commit expanded the examples from type-only searches to system and type GET/POST searches, added "in scope of the search context", and replaced the stale insufficient-parameters wording with overly-broad error guidance.

Additional context:
The Jira-linked 2019 Zulip thread records agreement that no-filter searches are allowed, that authorization can constrain visible records, and that a server can reject a request as too broad. Later edits a3766ac36c6 and 887bc2383fb only wrapped the paragraph in conformance markup and adjusted punctuation; they did not change the rule. The combined branch still contains the current paragraph in source/search.html lines 232-235. No Confluence references were found.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The authoritative search page already says that searches without filters, including GET [base], GET [base]/Patient, and POST _search forms with no body, SHOULD return all records in the search context and MAY be rejected as overly broad with an appropriate error.

Recommendation:
Keep this empty audit commit as-is. Do not duplicate the rule on the HTTP page or in search.html#all unless the work group wants a navigation-only editorial change, because the current Search Inputs section already conveys the FHIR-20392 behavior without adding maintenance drift.
