FHIR-27762: Audit CodeSystem unique-code invariant

Issue request:
FHIR-27762 was a Published/Persuasive with Modification Vocab change request for R5. It reported that CodeSystem csd-1 used `concept.code.combine($this.descendants().concept.code).isDistinct()`, where `$this.descendants()` did not correctly collect nested concept codes, and the accepted resolution was Bryn Rhodes' final expression: `concept.exists() implies concept.code.combine(%resource.concept.descendants().concept.code).isDistinct()`.

Initial application:
The issue was applied before this reconciliation. Commit ade907ca5b1bc08efb093bc524c5b00bdc7fa5ac, "2nd batch of vocab R5 tickets", explicitly listed FHIR-27762 and changed source/codesystem/structuredefinition-CodeSystem.xml from the old `$this.descendants()` expression to the final `concept.exists() implies ... %resource.concept.descendants().concept.code ... isDistinct()` expression.

Additional context:
CodeSystem is an active current-build resource in source/fhir.ini and remains owned by Vocab/normative core source. The current authoritative StructureDefinition still carries the applied csd-1 expression and attaches csd-1 to CodeSystem.concept. A repository-wide scan found the old expression only in frozen tools/history/release4 and release4b artifacts, while current source and release5 history contain the corrected expression. Confluence minutes record the 2021-07-08 Vocab motion approving the resolution 9-0-0, and the original community.fhir.org thread explains the `$this` problem that led to the Jira. Corrected Zulip searches found no direct FHIR-27762 discussion or later superseding decision.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current build-scope source already implements the final Jira-approved CodeSystem csd-1 FHIRPath expression, so editing it again would only duplicate the prior application. Historical R4/R4B snapshot files were left unchanged because they preserve prior published release surfaces rather than drive the current build.

Recommendation:
Keep this no-change audit commit. No current-core follow-up is needed for FHIR-27762; any desire to retroactively correct R4/R4B historical publication artifacts should be handled as separate release-maintenance work, not by changing current build source during this reconciliation.
