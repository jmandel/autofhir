FHIR-46399: Audit additional binding key support

Issue request:
FHIR-46399 was Applied/Persuasive for R6 and asked for a mechanism to distinguish constraining an existing additionalBinding from adding a new one. The accepted resolution required a 0..1 id key on the additional binding structure, a best-practice key.exists() constraint, and profiling guidance that additional bindings can be constrained only when the derived binding uses the same key.

Initial application:
The issue was explicitly applied by git commit 757595c1e9a3b3e452fb3651f4d3eaabf32a9c60, "FHIR-46399 Need a mechanism to constrain additional bindings." That commit added ElementDefinition.binding.additional.key to source/datatypes/elementdefinition.xml, added the best-practice invariant on ElementDefinition.binding.additional, and inserted the requested profiling prose in source/profiling.html.

Additional context:
source/fhir.ini actively includes the elementdefinition page and declares ElementDefinition normative, so source/datatypes/elementdefinition.xml and source/profiling.html are current build inputs for this issue. The originating Zulip thread in #IG creation shows the same problem statement: downstream profiles needed to tighten additional bindings, and participants identified adding a key as the mechanism. Confluence minutes and agenda records only schedule or relate FHIR-46399 with FHIR-46350 and do not narrow the Jira resolution. Later related issues were not decided here: FHIR-51073 is a follow-up to populate keys on existing additional bindings, FHIR-49977 belongs to the FHIR-tools additional-binding extension release, and FHIR-46350 is a separate policy issue about maximum/required additional bindings.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change because the active core source already contains the requested key, best-practice invariant, and profiling rule. Adding duplicate prose or touching generated/history artifacts would not improve current implementer understanding.

Recommendation:
Keep this audit commit as-is for FHIR-46399. If further work is desired, handle FHIR-51073 and FHIR-49977 as their own issues because they concern follow-up population of binding keys and FHIR-tools extension packaging rather than the core mechanism requested here.
