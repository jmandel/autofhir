Issue request:
FHIR-5678 was a Published FHIR-core List change request with resolution Not Persuasive with Modification. The submitter questioned the then-repeating List entry flag cardinality and the final decision was to change the flag to 0..1 and update the definition accordingly.

Initial application:
The issue appears to have been applied in git commit 304db837a48d21af881357a443d387d3d721848f, whose message is "#5678 - change cardinality of List.item.flag" and whose git-svn id records build@6816, matching the Jira implementation comment. That commit changed List.entry.flag from 0..* to 0..1, changed the short/definition to singular status/workflow wording, and removed a second flag from the medication list example.

Additional context:
The current List resource is in build scope through the active source/fhir.ini list=List entry. The current StructureDefinition source preserves List.entry.flag as 0..1 with singular definition text and the same example binding. Current List examples use at most one flag per entry. A later 2020 Zulip discussion asked whether multiple List.entry.flag values could be supported in future versions, but the discussion did not identify an applied/published Jira reversal; Jira and community searches found no final conflicting decision.

Recommendation:
Keep this audit commit as-is. Future work to make List.entry.flag repeating should require a new work-group decision and tracker, not a reinterpretation of FHIR-5678.
