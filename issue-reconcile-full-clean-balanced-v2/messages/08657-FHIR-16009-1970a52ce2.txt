FHIR-16009: Audit ElementDefinition value set maturity

Issue request:
FHIR-16009 was a Published/Persuasive FHIR-core request from STU3 asking that ElementDefinition's required terminology value sets, starting with resource-slicing-rules and including discriminator-type, property-representation, resource-aggregation-mode, reference-version-rules, and constraint-severity, not remain draft FMM 0 while ElementDefinition moved normative. The accepted resolution was to fix the missed FMM levels caused by tooling.

Initial application:
The Jira application comment cites svn revision 14464. In git history this is commit 44e6df5562160cf956ea56f34b6c8dcdb6655c10, whose message is "GF#16009 - fix bug setting fmm levels etc for value sets used in data types" and whose relevant code change made datatype validation carry the datatype's FMM, standards status, work group, and normative package through a fake parent resource.

Additional context:
The current source keeps ElementDefinition as an active data type in source/fhir.ini and marks ElementDefinition normative. The affected required bindings are still generated from source/datatypes/elementdefinition.xml. Current build output for all six named ValueSets and their CodeSystems is standards-status normative; R5 publication also shows FMM 5 for all six. The R4 publication surface shows the same artifacts as normative, although it retained an FMM 2 extension, so the current build has moved beyond the original draft-FMM problem.

AutoFHIR reconciliation:
No source change was made. The current FHIR source and generated build surface already satisfy the accepted request: the affected ElementDefinition terminology artifacts are not draft FMM 0 and are treated as normative in the current specification.

Recommendation:
Keep this audit commit as-is. No follow-up core source work is needed unless a future ballot explicitly wants to reintroduce a separate numeric FMM extension on normative terminology artifacts.
