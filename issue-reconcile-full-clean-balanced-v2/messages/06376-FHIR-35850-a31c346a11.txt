FHIR-35850: Audit workflow supportingInfo Encounter context

Issue request:
FHIR-35850 was a Published/Persuasive FHIR-core workflow request for R5. PA asked FHIR-I to make the workflow-supportingInfo extension usable on Encounter because PA did not plan to add a native Encounter.supportingInfo element and had chosen the extension as the right mechanism for Encounter-related supporting documents.

Initial application:
The request was applied by commit 3af6d20c390b085f5d67e4eb837d11c2ad58a2c5, which added Encounter to the supportingInfo context list in the active source/profiles/workflow-extensions-spreadsheet.xml workflow extension spreadsheet. That same spreadsheet was active in source/fhir.ini as workflow-pattern-extensions. No current source hunk from that commit remains to fix because commit dd468d4f1799dd79819315b211588ef1cf4586e0 later removed the extension definitions from the R5 core source as part of the extension extraction.

Additional context:
FHIR-28250 is the PA-side decision that led to FHIR-35850: PA rejected broadening Encounter.reason and instead said workflow-supportingInfo should be used, with FHIR-35850 created to add Encounter context. The PA WGM minutes record the same rationale. Current FHIR core still has the active workflow extension spreadsheet shell, but the supportingInfo definition is no longer a core-owned row; the current FHIR Extension Pack source defines StructureDefinition-workflow-supportingInfo with contexts for DiagnosticReport, DocumentReference, Encounter, Observation, and CommunicationRequest. A 2026 FMG Zulip thread discussed version-specific context limits for DiagnosticReport and repeated the Encounter context without contradicting it.
