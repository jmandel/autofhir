FHIR-12450: Audit repeated GET operation parameter handling

Issue request:
FHIR-12450 was a Published/Persuasive FHIR-core operations change request asking what clients should do when an idempotent operation invoked by HTTP GET has a repeating input parameter. The approved resolution was to clarify that repeated parameter values are represented by repeating the named query parameter.

Initial application:
The Jira comments record application in svn @11112. Git history maps that application to 7edc5218da58db5570524fc324f45d3bd66ae767, which added the repeated named parameter paragraph and Observation $stats example to source/operations.html.

Additional context:
The current source/operations.html Operation Request section still contains the requested rule and example, and source/documentation.html links the Operations page from the RESTful API documentation. Later edits changed nearby GET-invocation wording and query escaping but preserved the repeated-parameter semantics. Zulip and Confluence searches for FHIR-12450 and the repeated-parameter GET operation terms found no conflicting community evidence or related final issue that changes the interpretation.

AutoFHIR reconciliation:
This commit makes no source change because the current build source already states that, when using HTTP GET for an operation, values for a repeating parameter are represented by repeating the named parameter, with an example showing multiple statistic parameters.
