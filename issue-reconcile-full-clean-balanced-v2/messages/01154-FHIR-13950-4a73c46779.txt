FHIR-13950: Audit formatCode terminology handoff

Issue request:
FHIR-13950 was a Published/Persuasive STU3 DocumentReference request to stop carrying IHE and HL7 formatCode values as an undifferentiated local FHIR value set. It asked for the values to be represented by CodeSystem resources, with the existing formatCode ValueSet composed from those systems, and noted that HL7-authored codes should not appear as if they were assigned by IHE.

Initial application:
The request was applied in svn revision 13175, preserved in git commit f86337b9ba, which was explicitly labeled GF#13950 and GF#14003. That commit replaced the long local list in source/documentreference/valueset-formatcodes.xml with an external IHE include and corrected the IHE ValueSet OID, while registering the terminology source in source/fhir.ini.

Additional context:
Later formatCode work moved the remaining mixed vocabulary management out of FHIR core. FHIR-14104 and the linked terminology discussion established an HL7-managed document format CodeSystem, and commit 6f1b3314e9 removed the old core-local formatcodes ValueSet while changing DocumentReference.content.profile.value[x] to bind to the THO ValueSet http://terminology.hl7.org/ValueSet/v3-HL7FormatCodes. Current THO content composes active IHE format codes with the HL7 Document Format Codes CodeSystem, so the semantic result requested by FHIR-13950 is present outside the core source checkout. FHIR-17298 shows that later remaining formatCode expansion questions are being handled as THO/UTG work, not as a core-local value-set restoration.

AutoFHIR reconciliation:
No source files were changed. The active core build includes DocumentReference, and the current DocumentReference binding points to the THO format-code ValueSet. Recreating source/documentreference/valueset-formatcodes.xml or adding another core CodeSystem would reverse the later THO handoff and duplicate externally managed terminology.

Recommendation:
Keep this audit commit as-is. Future changes to the composition or expansion of DocumentReference format codes should be pursued in THO/IHE/UTG unless a separate Jira explicitly asks FHIR core to change which ValueSet the resource binds to.
