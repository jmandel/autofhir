FHIR-6877: Audit ProcedureRequest status overlap

Issue request:
FHIR-6877 was a Published Patient Care change request from the DSTU1 ballot cycle. It observed that Procedure and ProcedureRequest status values overlapped and asked whether ProcedureRequest should replace completed with closed, remove in-progress/accepted-style fulfillment states, or add scheduled. The final Not Persuasive with Modification resolution said the status values would be aligned with workflow patterns through GF#10293, now represented as FHIR-10293.

Initial application:
No source commit was found that directly names FHIR-6877. The linked Published workflow issue FHIR-10293 listed Procedure as an Event resource and ProcedureRequest as a Request resource, and its comments later removed FHIR-6877 from the duplicate ballot-comment list after recording that workflow changes had been applied. Source history shows the relevant application path: fd96fa1d815117d335e22713f30f6792a9c83b1d applied Procedure workflow pattern changes under #10293, e9a85998b0dbe25b03abd0045bfa30e67ce56b36 carried ProcedureRequest.status from the broad local status list into RequestStatus/request-status wording during the ProcedureRequest merge work, and 06bd9f6ffe08096694a3424721006e5fdcd82d3a later renamed ProcedureRequest to ServiceRequest.

Additional context:
ProcedureRequest is no longer active in the current build. source/fhir.ini actively lists procedure=Procedure and servicerequest=ServiceRequest, and records ProcedureRequest only as a deleted resource merged into ServiceRequest. Related audits already on the combined branch for FHIR-11120 and FHIR-6876 found the same Request-status alignment in the ProcedureRequest/ReferralRequest successor family. Later source has further refined terminology, for example using on-hold/stopped rather than the older suspended/aborted names for Event status, so the current code lists should be judged against the current workflow pattern rather than the 2015 wording literally.

AutoFHIR reconciliation:
This empty audit commit makes no source change. The current build-scope source already preserves the requested workflow separation: Procedure.status is an Event-status element bound to http://hl7.org/fhir/ValueSet/event-status, ServiceRequest.status is a Request-status element bound to http://hl7.org/fhir/ValueSet/request-status, and the Request pattern narrative says requests do not track fulfillment statuses such as requested, accepted, or in-progress; those are managed through Task or corresponding Event resources.

Recommendation:
Keep this no-change audit commit. Do not edit retired ProcedureRequest source or reintroduce fulfillment states into Request.status/ServiceRequest.status unless a later work-group decision reverses the workflow separation between requester-controlled authorization status and performer/event fulfillment status.
