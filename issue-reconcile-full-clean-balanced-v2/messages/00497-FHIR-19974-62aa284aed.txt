FHIR-19974: Clarify Composition $document bundle contents

Issue request:
FHIR-19974 was Published with a Persuasive with Modification resolution for Composition/$document. The issue asked to remove the misleading searchset wrapping note, remove the type-level [base]/Composition/$document form and id parameter, and replace the generated idempotence wording with a clearer statement that the generated Bundle entries are not modified.

Initial application:
The searchset wrapping sentence was removed in the same operation source by the adjacent FHIR-32016 implementation commit, and the explicit FHIR-19974 commit changed Composition/$document from type+instance to instance-only and removed the id input parameter. The generated operation page still renders the generic "This is an idempotent operation" sentence because it is derived from OperationDefinition.affectsState rather than from per-operation prose.

Additional context:
SD minutes for 2023-02-09 approved the exact clarification text after asking whether the operation was really idempotent if the Bundle id can change. FHIR-36699 raised the same ambiguity and was answered by the same FHIR-19974 clarification path. Zulip discussion confirms the intended behavior: $document is not a type-level search that returns a searchset of document Bundles; the multi-document/query use case would need different design.

AutoFHIR reconciliation:
Updated the active source/composition/operationdefinition-Composition-document.xml description to include the WG-approved clarification that the operation will not modify the content in the entries of the generated Bundle. This preserves the existing affectsState=false/GET behavior while making the per-operation page less misleading when the generated idempotence sentence is shown.

Recommendation:
Keep this source fix. A broader change to the generated OperationDefinition renderer's generic idempotence wording would affect all operations and should only be considered separately by the tooling/spec editors.
