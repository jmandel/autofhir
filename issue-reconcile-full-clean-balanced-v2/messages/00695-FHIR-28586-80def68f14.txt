FHIR-28586: Audit unsignedInt and positiveInt generator fix

Issue request:
FHIR-28586 is Published/Persuasive for an R4 technical correction applied for R5. It requested changing the StructureDefinition value element type for unsignedInt and positiveInt from http://hl7.org/fhirpath/System.String to http://hl7.org/fhirpath/System.Integer.

Initial application:
The primitive datatype source in source/datatypes/primitives.xml already models unsignedInt and positiveInt as integer-based primitives with JSON number representation, and the generated R5/current differentials expose positiveInt.value and unsignedInt.value with System.Integer. However, the generated snapshots still expose those same value elements as System.String. Jira also records Jean Duteau's comment that the remaining issue is a snapshot generator problem rather than a primitive source-row problem.

Additional context:
The current FHIR build depends on the external org.hl7.fhir:kindling publisher/generator artifact. HL7/kindling's ProfileGenerator currently uses type.getFHIRPathType() for the DefinedStringPattern differential but hard-codes System.String for the corresponding snapshot value element, which exactly explains the current build.fhir.org and R5 mismatch. The linked Zulip discussions confirm the intended result: the type code should be System.Integer, with the structuredefinition-fhir-type extension retaining positiveInt or unsignedInt.

AutoFHIR reconciliation:
This commit intentionally makes no FHIR source change. The remaining correction belongs in HL7/kindling, not in the HL7/fhir source checkout; changing generated history files or duplicating source metadata in this repository would not correct the authoritative current build output.

Recommendation:
Keep this external-repo audit commit as-is for the FHIR combined branch. Fix HL7/kindling ProfileGenerator so the DefinedStringPattern snapshot value type uses type.getFHIRPathType() instead of hard-coded System.String, publish/use a corrected kindling version, then rebuild FHIR to make the current snapshot match the already-correct differential.
