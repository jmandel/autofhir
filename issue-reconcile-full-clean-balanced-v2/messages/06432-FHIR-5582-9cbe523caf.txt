FHIR-5582: Document profile summary cardinality impact

Issue request:
FHIR-5582 was Published/Persuasive for DSTU1 and asked that base resource or datatype elements with minOccurs/min cardinality 1 be required to have isSummary=true. The approved resolution added build-tool enforcement for base definitions and called for notes on ElementDefinition.isSummary and in profiling about the effect when profiles make optional elements mandatory.

Initial application:
The explicit application commit was svn 3983, imported as 8997ed2d40dafcfdc82b74e5a16b4a6891679f5f, which added a publisher validation rule but did not edit source/profiling.html. Later source work added and refined ElementDefinition.isSummary guidance and search-page links, so the base-definition rule is already present in the current ElementDefinition text.

Additional context:
Current source/fhir.ini lists ElementDefinition as an active datatype and profiling.html is an active core profiling narrative page. FHIR-9201, FHIR-33148, and FHIR-35855 later clarified that _summary=true uses the base definition's isSummary markings, that isSummary cannot be overridden in profiles, and that the current rule is more nuanced than the original min=1 shorthand. Those later decisions do not remove the profiling-page warning requested by FHIR-5582.

AutoFHIR reconciliation:
Added a short note to source/profiling.html in the Changing Cardinality section explaining that _summary=true results are based on base-resource isSummary markings and that a profile making an otherwise optional non-summary element mandatory cannot assume the element will be present in summary results, so such a summary might not conform to the profile.

Recommendation:
Keep this source fix. It completes the profiling-page portion of the published FHIR-5582 decision without changing the later refined ElementDefinition.isSummary rule or adding redundant guidance outside the cardinality discussion.
