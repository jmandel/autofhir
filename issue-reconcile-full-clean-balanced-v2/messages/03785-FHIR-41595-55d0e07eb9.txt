FHIR-41595: Audit FHIRPath ofType wording

Issue request:
FHIR-41595 was an Applied/Persuasive FHIR-I change request for R6 asking that the FHIRPath polymorphism documentation say choice children can be treated as a specific type using the `ofType` operation rather than the `as` operation, matching the example `(Observation.value.ofType(Quantity)).unit`.

Initial application:
The issue was applied in source history by commit 9427f2600639dacab9a820d0000161087929320e, titled "FHIR-41595 as -> ofType in fhirpath documentation", and merged through HL7/fhir PR #3797. That commit changed `source/fhirpath.html` from `<code>as</code> operation` to `<code>ofType</code> function` in the polymorphism section while preserving the existing `ofType(Quantity)` example.

Additional context:
The current `source/fhirpath.html` page is a built top-level FHIRPath source page listed in `source/hierarchy.xml` and linked from current specification pages. It now says `using the <code>ofType</code> function` immediately before `(Observation.value.ofType(Quantity)).unit`, so the Jira-requested correction is present. A nearby cross-spec search found `source/structuredefinition/structuredefinition-notes.xml` still referring to the FHIRPath `as` operator, but that text is governed by published issue FHIR-39179, which explicitly changed that note from `is` to `as` for expression constraints, and FHIR-53208 documents that a broad `as => ofType` replacement elsewhere was accidental. The FHIR-I WGM minutes record the 22-0-0 persuasive motion for FHIR-41595, and a Zulip implementers thread cites FHIR-41595 as support for using `ofType` rather than `as` in the reported search-parameter case.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. The authoritative FHIRPath documentation source already contains the requested `ofType` wording, and changing separate intentional `as`-operator guidance would exceed FHIR-41595 and conflict with related history.

Recommendation:
Keep this no-change audit as-is for FHIR-41595. Do not perform another broad `as` to `ofType` replacement under this issue; any future concern about the StructureDefinition profiling note should be reviewed under FHIR-39179 or a new issue because that note was intentionally set to `as`.
