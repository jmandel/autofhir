FHIR-12460: Audit Timing repeat constraints

Issue request:
FHIR-12460 was Published/Persuasive with Modification for the Timing datatype after examples using dayOfWeek, timeOfDay, frequency, period, and when were blocked by overly strict invariants. The approved resolution asked to fix the Timing examples, increase Timing.repeat.when to 0..*, drop tim-3, loosen tim-10 so only when and timeOfDay are mutually exclusive, remove tim-11, and add a cautionary note about nonsensical combinations.

Initial application:
The issue was applied by historical commit aedd18d2bf63c6b72d72dca8285dd9fdbd904a4d, "#12460 relax constraints on Timing datatype", corresponding to svn revision 11172 cited in Jira. That commit changed source/datatypes.html, source/datatypes/timing.sheet.txt, and source/datatypes/timing.xml to implement the requested example, cardinality, invariant, and note updates.

Additional context:
Timing is an active normative datatype in the current build via source/fhir.ini, and datatypes.html is the active type page for Timing. Related Timing issues FHIR-12201 and FHIR-12352 introduced dayOfWeek and timeOfDay, while later FHIR-23710 and FHIR-25289 clarified that timeOfDay is exclusive with when but not with frequency or period. Current source now carries that later clarification, so the right reconciliation target is the current combined rule family rather than the exact 2017 wording.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source/datatypes.html has the corrected Timing example rows and the cautionary note; current source/datatypes/timing.xml has Timing.repeat.when at 0..*, the multi-when union comment, tim-10 as timeOfDay.empty() or when.empty(), and no remaining tim-3 or old dayOfWeek/frequency/period tim-11 constraint.

Recommendation:
Keep this audit commit as-is. The current source already implements FHIR-12460 as refined by later Timing decisions; adding more prose would be redundant and could risk drifting from the single authoritative datatype definition.
