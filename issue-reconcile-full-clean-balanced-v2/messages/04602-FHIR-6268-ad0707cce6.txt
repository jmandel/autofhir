FHIR-6268: Audit Coverage plan search parameter types

Issue request:
FHIR-6268 is a Published/Persuasive FHIR-core Coverage correction from the Financial Management work group. It asked that the Coverage plan and subplan search parameters, plus the related group search parameter noted in comments, be string rather than token because the then-current elements were insurer-assigned string codes without known code systems.

Initial application:
The request was applied in git commit e3341738311776bc6dfe4f077468782ca1e1f1d7, whose subject was "Coverage search #6268" and whose Coverage spreadsheet changes made plan, subplan, group, subgroup, class, and subclass search parameters string-valued on the then-current Coverage.group child elements. A follow-up tracker commit, 43806174288e821cb06173a72cde96317186412b, also listed tracker 6268 while updating the Coverage grouping source.

Additional context:
The old Coverage.group.plan, Coverage.group.subPlan, and Coverage.group.group elements no longer exist in the current build. FHIR-12322 introduced the explicit grouped classifier details; later FHIR-15564 accepted the current repeating Coverage.class structure and removed Grouping and Sequence; FHIR-17949 added class-type and class-value search parameters for that structure; and FHIR-24641 changed Coverage.class.value from string-like content to Identifier. Coverage is active in source/fhir.ini, current examples represent group/plan/subplan as Coverage.class entries, and the current class-value SearchParameter is token because it searches an Identifier-valued element.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Changing the current class-value SearchParameter back to string would conflict with the later, already-applied Coverage.class Identifier model, while the specific old plan/subplan/group search parameters requested by FHIR-6268 are no longer current build artifacts.

Recommendation:
Keep this no-change audit commit. No core source follow-up is needed for FHIR-6268; future changes to Coverage.class.value datatype or coded alternatives should be handled under later R6 Coverage.class issues, not this DSTU1 search-parameter correction.
