FHIR-7031: Audit CodeableConcept translation handling

Issue request:
FHIR-7031 was Published/Persuasive for DSTU1 by the Vocabulary work group. It asked the ConceptMap $translate documentation to state whether translation codings in a CodeableConcept input are allowed and whether they are evaluated, particularly for batch translation use.

Initial application:
The issue was applied in svn revision 5699, now git commit e5a7c238c6, by changing the ConceptMap translate operation's CodeableConcept input documentation from saying the server can translate any coding values to saying it can translate any coding values, including existing translations. That application landed in the old ConceptMap spreadsheet source and was later carried forward into the current OperationDefinition source.

Additional context:
ConceptMap is an active current-build resource in source/fhir.ini, and source/conceptmap/list-ConceptMap-operations.xml includes OperationDefinition/ConceptMap-translate. Later R5/R6 work, including FHIR-32129 and FHIR-41175, renamed the $translate inputs to source*/target* forms and harmonized examples without removing the FHIR-7031 clarification. Both of those later issues are already represented on the combined reconciliation branch.

AutoFHIR reconciliation:
Made no source change. The current active ConceptMap $translate OperationDefinition already documents sourceCodeableConcept and targetCodeableConcept as CodeableConcept inputs whose coding values, including existing translations, may be translated by the server. Adding duplicate prose to the batch narrative would not change the rule and would increase maintenance drift.

Recommendation:
Keep this empty audit commit as-is. No current-core source follow-up is needed for FHIR-7031 unless the work group wants a new, separate policy change from the published server-choice wording to a stricter requirement.
