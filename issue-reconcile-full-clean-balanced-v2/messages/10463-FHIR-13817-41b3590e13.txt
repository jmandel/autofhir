FHIR-13817: Audit search :not set semantics

Issue request:
FHIR-13817 was a Published/Persuasive FHIR Infrastructure request raised for STU3 to clarify how the token search modifier :not works when a searched element can have more than one matching value, and the issue description proposed documenting that behavior and defining :excludes. The final resolution narrowed the decision to clarifying that :not excludes a resource if any of the codings match.

Initial application:
The issue was applied in svn revision 13379, now git commit 331f9b3e724eda72d6e6f4b868d9b7fd51a4bb6b, which changed source/search.html to say :not returns resources that do not have a matching item and added a Composition.section:not example explaining that the negation applies to the set, not each individual entry.

Additional context:
The current build-scope search narrative still contains the same set-level rule in the detailed not modifier section and token examples, and the current Search Modifier Code code system defines not as resources that do not contain a match. Later search modifier refactoring in 2022 expanded the narrative and kept the same behavior, while the final Jira resolution did not require adding a new :excludes modifier. Searches of Zulip and Confluence found only bot/commit references for this issue and no substantive community discussion that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current specification already says [parameter]:not=[value] requests resources that do not have any matching value in the searched element(s), and its multi-valued Composition.section example explicitly says the negation applies to the set and not each individual entry.

Recommendation:
Keep this no-change audit as-is. A source edit would be redundant and could reopen a resolved STU3 wording decision; future work on additional negation operators should be handled by a new Jira issue rather than by reinterpreting FHIR-13817.
