FHIR-22485: Audit Encounter serviceType history

Issue request:
FHIR-22485 was an Applied/Persuasive with Modification Patient Administration change request raised against STU3 Encounter asking to support Encounter.serviceType history because the service can change during an Encounter and admission/discharge service may matter for care continuation metrics. The final resolution says Encounter.serviceType had already been updated in R5 to match Appointment cardinality, and that the history portion is covered by EncounterHistory.

Initial application:
No source commit explicitly tagged FHIR-22485 was found. The serviceType cardinality portion was applied through FHIR-25794 by commit 636866f7f8b827d44e9455590965ec1f68c48810, which changed Encounter.serviceType max from 1 to *. The history portion was applied through FHIR-14157 EncounterHistory work, including commit 53538c40d6fd5ba9a8dc8c07e050478d73aa9037, whose EncounterHistory draft included EncounterHistory.serviceType at 0..*. The current Encounter source still has Encounter.serviceType as 0..*.

Additional context:
source/fhir.ini actively includes Encounter in the current build. EncounterHistory was later removed from core by commit 71567db3ee039ac6977be5f96a7e013896569a36, and current core narrative now links to the admin-incubator EncounterHistory artifact instead of building it as a core resource. That referenced admin-incubator StructureDefinition currently includes EncounterHistory.serviceType as 0..* CodeableReference(HealthcareService). Confluence PA minutes from January 2022 show FHIR-14157 was amended to include serviceType in EncounterHistory, and May 2023 PA minutes record the FHIR-22485 motion with the note that R5 had already dealt with this via EncounterHistory. FHIR-25794 is already represented on the combined branch; later FHIR-53475 concerns wording alignment for Encounter.serviceType but is only Resolved - change required and is outside this default Applied/Published source-edit scope.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The build-scope core Encounter source already implements the repeatable serviceType cardinality, current core narrative points readers to EncounterHistory for history tracking, and the referenced external EncounterHistory artifact contains the repeatable serviceType element needed for the history part of the request.

Recommendation:
Keep this no-change audit as-is for FHIR-22485. If Patient Administration wants to restore EncounterHistory to core, change its maturity/source location, or apply FHIR-53475 wording alignment, those should proceed under their own trackers; FHIR-22485 itself is satisfied by current core source plus the referenced EncounterHistory artifact.
