FHIR-13498: Clarify resurrected updates return 201

Issue request:
FHIR-13498 was a Published/Persuasive FHIR-core HTTP issue asking the RESTful API page to explicitly say that a PUT to a location where a resource previously lived, after deletion, uses the same 201 Created response as other creations. The resolution also asked to describe this as bringing the resource back to life and to avoid implying that version history is lost.

Initial application:
The issue was originally applied in git commit 7b16fff931930a9054083771bbbad8bdd1b5cf06, imported from svn revision 12840, by adding "or brought back to life/re-created" to the update response sentence that required 201 Created for created resources. Current source still had the delete-section statement that deleted resources may be brought back to life and the version-history explanation, but the update status sentence no longer carried the explicit deleted-resource qualifier.

Additional context:
FHIR-26358 later refactored the same update response paragraph to split status, Location, and ETag requirements, and that refactor dropped the FHIR-13498 qualifier while pursuing a different Location-header clarification. FHIR-25038 is a later Published/Persuasive-with-Modification issue about ETag optionality whose resolution quoted the update response wording with the brought-back-to-life parenthetical, confirming that the qualifier remained intended even as ETag/Last-Modified language changed. The HTTP page is in current build scope as the REST (HTTP) entry in source/navigation.xml.

AutoFHIR reconciliation:
This commit restores the explicit qualifier in source/http.html so the update interaction says that a resource created by bringing a previously deleted resource back to life returns 201 Created. It also fixes the adjacent deleted-resource note's broken update anchor from #href to #update so readers can follow the cross-reference to the governing interaction.

Recommendation:
Keep this source change as-is. It restores the original applied clarification without changing the later Location-header or ETag semantics, and no separate work-group review appears necessary.
