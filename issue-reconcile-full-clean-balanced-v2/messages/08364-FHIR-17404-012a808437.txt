FHIR-17404: Audit ElementDefinition BackboneType lineage

Issue request:
FHIR-17404 was a Published/Persuasive FHIR-I STU3 clarification request asking which ElementDefinition inheritance statement was right: the ElementDefinition page did not show modifierExtension or a BackboneElement specialization, while the Datatypes page listed ElementDefinition as a special-purpose type that may include modifier extensions. The accepted resolution was to make it consistently clear that ElementDefinition is a backbone element.

Initial application:
The issue was applied in svn revision 14035, represented in git as cd611f6d04dcd2087501f6c40ddaf5762076a31b, which changed the ElementDefinition spreadsheet root type from Structure to BackboneElement. That matches the Jira comment and made the generated ElementDefinition definition inherit modifierExtension support through the then-current type model.

Additional context:
The current build has since split the abstract type framework. ElementDefinition is an active datatype in source/fhir.ini, BackboneType is an active normative infrastructure type, and source/datatypes/elementdefinition.xml now makes ElementDefinition derive from BackboneType. BackboneType is explicitly defined as the base for datatypes that can carry modifier extensions, and source/types.html plus source/datatypes.html list ElementDefinition among the few datatypes that may include modifier extensions. The 2019 type-framework refactor, cbdf7d1e55dc4bfa1dc30fc526edee0491e05782, changed ElementDefinition from BackboneElement to BackboneType, preserving the FHIR-17404 substance in the newer model. FHIR-13363 is background for the broader modifier-extension datatype family; FHIR-35865 was only a later modifierExtension summary issue and does not change this conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source is already internally consistent and preserves the implemented decision through BackboneType rather than the older literal BackboneElement base. Editing the ElementDefinition page to restate this would duplicate generated/inherited type information and risk maintenance drift.

Recommendation:
Keep this no-change audit commit as-is. No core source follow-up is needed for FHIR-17404 unless the work group later decides to change the modern BackboneType abstraction itself.
