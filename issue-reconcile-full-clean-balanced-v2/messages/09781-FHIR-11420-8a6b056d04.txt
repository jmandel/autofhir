FHIR-11420: Clarify workflow update limits

Issue request:
FHIR-11420 was a Published/Persuasive with Modification FHIR Infrastructure change request for DSTU2. It asked whether Request artifacts can be updated and whether a Task can be responded to with another Task. The accepted resolution says all resources can be updated in principle, business rules may prevent that, shared RESTful Task workflows typically update the same Task, messaging workflows may have independent Task instances, and request artifacts typically need limits on changes after fulfillment has been sought.

Initial application:
No explicit FHIR-11420 source commit or Jira-keyed git history was found. Before this reconciliation, the active workflow page still said definitions and requests can both replace prior versions of the same artifact without qualifying that request changes depend on resource definitions and business rules, and the Task note did not distinguish shared RESTful Task updates from independent messaging/separate task instances.

Additional context:
source/workflow.html is a current core workflow topic linked from active source pages such as canonicalresource.html, clinicalreasoning-module.html, claim-notes.xml, and fivews.html. Later workflow history and the current combined branch did not add the FHIR-11420 limitation language. Jira, Zulip, and Confluence searches found no related decision or community discussion that narrowed or reversed the Jira resolution.

AutoFHIR reconciliation:
This commit updates source/workflow.html so the request/definition replacement relationship is conditional on the resource definition and applicable business rules, adds the requested language that Request updates are often limited after fulfillment has been sought or begun, and clarifies that Task response behavior differs between shared RESTful task-management spaces and messaging or separated task-management spaces.

Recommendation:
Keep this source change. It is a narrow application of the accepted FHIR-11420 resolution to the active workflow page and does not require follow-up outside core.
