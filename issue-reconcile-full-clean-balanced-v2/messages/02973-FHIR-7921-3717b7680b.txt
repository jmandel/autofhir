FHIR-7921: Audit access denied response guidance

Issue request:
FHIR-7921 was a Published/Persuasive with Modification security change request raised against FHIR-core-http. It proposed requiring 403 responses when a client is not authorized, but the accepted motion was to add guidance that 404 should normally be the default unless there is a specific reason to return 403.

Initial application:
The 403/404 policy text was first introduced by related FHIR-3310 in git commit e99a4d5856, then FHIR-7921 was explicitly applied by git commit 6f4cc33a42 / SVN revision 6467, which added that 404 does not leak information and should be the default unless there is a specific reason to return 403.

Additional context:
Later Published/Persuasive with Modification issue FHIR-9593 found the simple advice on both http.html and security.html incomplete. Git commit 268bdbbf8b implemented that later decision by replacing duplicated REST-page text with a pointer to Security and adding a fuller Access Denied Response Handling section covering empty search bundles, 404, 403, and 401. The current source still contains that section at source/security.html#AccessDenied and current HTTP interaction text links to it for security-sensitive status-code choices.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current specification already conveys the FHIR-7921 rule as refined by FHIR-9593: response choice for access denial is controlled by policy and context, 404 protects against leakage, and 403 is appropriate only when the client or user is well enough known to receive that information.

Recommendation:
Keep this no-change audit commit as-is. Do not restore the older duplicated 403/404 paragraph to http.html; future work, if any, should update the consolidated Access Denied Response Handling section through a new Security work group decision.
