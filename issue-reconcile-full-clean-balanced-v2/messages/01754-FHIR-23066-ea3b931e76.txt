FHIR-23066: Audit AuditEvent search action rationale

Issue request:
FHIR-23066 was a Published/Persuasive Security WG change request for R5 asking FHIR-core AuditEvent to explain why query/search audit events use AuditEvent.action = Execute rather than Read, even though REST searches often use HTTP GET. The accepted resolution requested adding a sentence to the Search operation row in the AuditEvent common scenarios table: the server must execute search parameters to get results, while Read identifies a specific object.

Initial application:
No local git commit with FHIR-23066 in the subject or body was found, but the Jira comment links HL7/fhir pull request 708. Local history shows commit 8f93636e058fa1a4b9ce4240fea41076e10e6760, "Initial set of Security CR for AuditEvent", changed source/auditevent/auditevent-notes.xml on 2019-10-03 by adding exactly the requested Execute-versus-Read sentence to the Search operation row. Current blame still attributes that sentence to the same commit.

Additional context:
source/fhir.ini lists auditevent=AuditEvent as an active resource, so source/auditevent/auditevent-notes.xml is in current build scope. The current source still contains the requested table clarification and the RESTful operation action table still maps search, search-type, and search-system to Execute. Later related AuditEvent work, especially FHIR-26938, added a Recording Search Events subsection that repeats the same Execute rationale for search requests; FHIR-37820 clarified the Read action definition without changing the Execute definition for query/search operations. The cited Zulip thread records the original debate and supports keeping query/search as Execute for ATNA/DICOM consistency and because a search is parameter execution rather than retrieval of a single identified object. No Confluence reference for FHIR-23066 was found.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active AuditEvent source already implements the FHIR-23066 resolution, and adding more local prose would be redundant with both the table row and the later Recording Search Events guidance.

Recommendation:
Keep this audit commit as-is. No follow-up source work is needed for FHIR-23066 unless the Security WG later changes the underlying AuditEvent.action policy for search/query events.
