FHIR-32540: Audit ConceptMap code/valueSet constraints

Issue request:
FHIR-32540 was Published with a Persuasive with Modification resolution. It asked why ConceptMap.group.element.code and ConceptMap.group.element.target.code were 0..1 instead of mandatory, and the accepted resolution kept those cardinalities because ValueSet alternatives were being added while requiring invariants that exactly one of code or valueSet be present at both source and target mapping levels.

Initial application:
The issue was applied in pieces. Commit 44b6a9fc8f977d070ab90083f6d1004394e83ffc added ConceptMap2.group.element.valueSet and the source-side cmd-5 code/valueSet invariant. Commit fbabfc1beb0eab4422797f110bc01e2cf590b640 added the matching target-side cmd-7 invariant. Commit 67c1a318489a92c8da3a4c10cb9cd75212b19921 updated the specimen type ConceptMap example so target entries without a code/valueSet became noMap entries instead of invalid empty target entries.

Additional context:
FHIR-15687 is the linked Published/Persuasive ConceptMap issue that introduced the source and target valueSet alternatives as canonical 0..1 elements, explaining why code could not become mandatory. FHIR-34279 later reconciled the same FHIR-32540/FHIR-15687 issue family for unmapped.valueSet and cmd-2. The current ConceptMap resource is active in source/fhir.ini, and the old ConceptMap2 source was subsequently folded into the current ConceptMap structure definition.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active ConceptMap source already has ConceptMap.group.element.valueSet and ConceptMap.group.element.target.valueSet, with cmd-5 and cmd-7 error constraints whose expressions require exactly one of code or valueSet. The current specimen type example also uses noMap for source concepts with no target, so the invalid empty-target shape noted during application is no longer present.

Recommendation:
Keep this audit commit as-is. FHIR-32540 needs no further core source change unless a future ConceptMap tracker reopens the broader valueSet mapping model; such future work should be handled under that later tracker rather than by making code mandatory here.
