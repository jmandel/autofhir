FHIR-27157: Audit Location near unit clarification

Issue request:
FHIR-27157 was a Published/Persuasive with Modification PA change request, applied for R5, asking the Location near search parameter to clarify which unit strings clients and servers should use for distance, especially miles. The controlling resolution says the units should be UCUM distance units, that bare "mi" is insufficient for miles and [mi_us] is the relevant mile code, and that a server supporting near may fail invalid units with an OperationOutcome and HTTP 400 while a server not supporting near may report the parameter as unused and ignore it.

Initial application:
The issue was applied before this reconciliation in source/location/bundle-Location-search-params.xml by FHIR-27157 commits 650dd988a28c506e7f39c5086c08623f8ebfb48c, ed8eec973ee8f2eb851f30831cce8c3c66adf0d5, and d0999a3fb40cd5581118ba30af17f181f2d8ee41. Those commits added the required km support, changed the requested miles text from both mi and [mi_us] to [mi_us] only, and added invalid-unit handling. A tightly related FHIR-33976 commit, ecb4dd444f3c065bac2460eb9df26b4f66b2af4a, later corrected the transient 403 wording to 400, changed RFC conformance wording to MIGHT, and added the algorithm caveat; fede0a93513316ea3626657108ef57a9e8f1c63a later preserved the same semantics while normalizing SearchParameter source formatting.

Additional context:
Location is an active resource in source/fhir.ini, so source/location/bundle-Location-search-params.xml is in the current build scope for the Location near SearchParameter. PA Confluence minutes record the January 2022 vote for the FHIR-27157 disposition, the April 2022 agreement that the 403 wording was wrong and would be resolved, and the April 2022 refinement that coordinated this text with FHIR-33976. Zulip discussion shows the original implementer ambiguity around km, mi, and [mi_us], and a later implementer confirmation that the build text answered the question. FHIR-33976 is already represented on the combined branch by commit 3bba9f9bcd64aaa938e6d92cd21582eab7b7a30f, so this commit does not duplicate that related issue.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active Location-near SearchParameter description already says servers supporting near SHALL support 'km' for kilometers and SHOULD support '[mi_us]' for miles, leaves other unit support optional, defaults omitted units to kms, and uses HTTP 400 BadRequest handling for unrecognized units when near is supported. That matches the final Jira, PA minutes, and related FHIR-33976 refinement without retaining the ambiguous bare mi code or the mistaken 403 status.

Recommendation:
Keep this no-change audit commit as-is. No follow-up core source work is needed for FHIR-27157; if PA wants to strengthen or otherwise revise the current permissive invalid-unit handling, that should be a new tracker rather than a reconciliation edit to this applied issue.
