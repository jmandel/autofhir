FHIR-7575: Audit profile-on-profile support

Issue request:
FHIR-7575 was a Published/Persuasive FHIR-core profiling issue from the 2015 May ballot. It asked the profiling page to state that a profile can be profiled, including realm or constrainable Patient profiles reused by downstream IGs, and noted that this should work for both resource and system profiles.

Initial application:
The Jira comment records svn revision 6463. Git history contains bef18bce7b1086b415f28671b4a107a22ce2bf8c, with git-svn-id build@6463, adding to source/profiling.html that a constraint StructureDefinition may specify restrictions on a resource or datatype "or an additional set of constraints on an existing profile." Later profiling-page edits preserved and expanded the same rule.

Additional context:
Current profiling.html is the active profiling narrative page and still says constraint StructureDefinitions may constrain existing profiles. It also describes cardinality rules for a profile constraining another profile, while the current StructureDefinition resource model uses baseDefinition plus derivation=constraint to identify the constrained base StructureDefinition. Related Jira FHIR-3872 covered the lower-level tooling/spreadsheet ability to base a profile on another profile; it supports this conclusion but is broader than the FHIR-7575 narrative audit and was not separately decided here.

AutoFHIR reconciliation:
No source change was made. The current specification already conveys the requested capability in both the profiling guidance and the StructureDefinition model, and the historical Jira-tagged commit matches the Jira application note.

Recommendation:
Keep this empty audit commit. Further wording would be redundant unless a later work-group decision changes profile derivation semantics or tooling behavior.
