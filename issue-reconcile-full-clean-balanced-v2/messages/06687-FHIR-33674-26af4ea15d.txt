FHIR-33674: Audit SubscriptionTopic empty-trigger behavior

Issue request:
FHIR-33674 was a Published FHIR-core SubscriptionTopic change request, resolved Persuasive with Modification for R5. It asked what happens when the then-current resourceTrigger and eventTrigger elements were both absent, and the approved decision was to clarify that such SubscriptionTopic resources simply will not trigger while still allowing non-triggering or extension-defined topics, plus noting that servers MAY reject unsupported triggering mechanisms.

Initial application:
The issue appears to have been applied by git commit 305bddee79, which added SubscriptionTopic narrative text explaining non-computable trigger definitions and server rejection of unsupported mechanisms. The affected SubscriptionTopic resource is in current build scope through the active source/fhir.ini subscriptiontopic resource entry.

Additional context:
FHIR-46492 later collapsed resourceTrigger and eventTrigger into the current SubscriptionTopic.trigger backbone and moved trigger-related filter and shape content under it. The current source therefore no longer uses the original R4B element names, but the current SubscriptionTopic notes still state that topics without computable definitions are not expected to trigger unless a server explicitly supports them, and that servers supporting create on SubscriptionTopic MAY reject resources without computable definitions or with unsupported mechanisms. Confluence FHIR-I WGM minutes record the 26-0-0 Persuasive with Modification motion, and no relevant Zulip discussion or conflicting community record was found.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The active SubscriptionTopic source already preserves the approved behavior in current R6 terms: absence of computable trigger definitions does not make a topic inherently invalid or universally firing, and servers may reject unsupported or non-computable mechanisms.

Recommendation:
Keep this no-change audit commit as-is. Future changes should only be made if the work group adopts a new decision to require invalidity, add constraints, or further refine server create-time validation behavior.
