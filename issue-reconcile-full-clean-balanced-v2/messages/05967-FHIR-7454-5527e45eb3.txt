FHIR-7454: Audit Coding.userSelected resolution

Issue request:
FHIR-7454 was a Published FHIR-core vocabulary change request from the 2015 May datatype ballot. It asked whether Coding.primary allowed only one Coding in a CodeableConcept to be primary or whether none could be primary. The approved persuasive-with-modification resolution renamed the element to "User Selected", allowed more than one coding to be flagged, and said trading partner agreements may need to clarify use while presuming direct user selection.

Initial application:
The issue was applied in SVN revision 5518, imported as git commit b1e826a4b83ef9617115bf221f0df040c5e39951. That commit renamed Coding.primary to Coding.userSelected in the datatype narrative and spreadsheet source, and removed the CodeableConcept invariant that limited primary/user-selected codings to at most one. The current build-scoped source still has Coding.userSelected in source/datatypes/coding.xml with 0..1 cardinality on each Coding and with comments preserving the direct-selection and trading-partner-agreement semantics.

Additional context:
The datatype page is in current build scope through source/fhir.ini, with Coding and CodeableConcept marked normative. Later Published issue FHIR-17268 resolved the remaining ambiguity by changing CodeableConcept prose from "One of the codings" to "One or more of the codings" and by explicitly explaining that multiple userSelected codings mean the user explicitly chose multiple codes. FHIR-17681 and FHIR-17267 made narrower follow-up clarifications already represented on the combined branch. FHIR-9745 and FHIR-11029 rejected repurposing userSelected for richer translation/provenance semantics, supporting the current narrow direct-selection interpretation.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Current source already uses Coding.userSelected rather than Coding.primary, contains no remaining Coding.primary or primary=true datatype constraint, allows multiple user-selected codings in the CodeableConcept narrative, and explains the zero-userSelected case by preferring CodeableConcept.text when present.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-7454; future work on richer coding provenance should use separate Jira decisions or extensions rather than changing the settled userSelected semantics.
