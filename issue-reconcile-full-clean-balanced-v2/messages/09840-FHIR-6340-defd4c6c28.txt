FHIR-6340: Audit ElementDefinition base handling

Issue request:
FHIR-6340 was a Published FHIR-core StructureDefinition change request, resolved Persuasive with Modification, asking how derived StructureDefinitions should represent choice elements such as Observation.value[x] when a profile includes a type-specific path like Observation.valueQuantity. The approved resolution added ElementDefinition base information, with a 0..1 base component whose path, min, and max children are 1..1 when base is present.

Initial application:
No current git commit explicitly names FHIR-6340, but the Jira comment records svn revision 5924 and nearby git-svn history contains ddb1f8c4e0 (#6066, svn r5923), which added ElementDefinition.base and initially populated it in source/datatypes/elementdefinition.xml. The current source retains the requested base backbone and required child fields.

Additional context:
Current ElementDefinition source is active in the build and normative. The flat resolution names basePath/baseMin/baseMax are represented in the current model as ElementDefinition.base.path, ElementDefinition.base.min, and ElementDefinition.base.max. Current narrative also clarifies choice-type constraints: type restrictions belong on the original [x] element, and including a type-specific element does not by itself constrain the allowed types.

AutoFHIR reconciliation:
This audit commit makes no source change because the current source already conveys the approved behavior: the base component exists with required path/min/max children when present, and the surrounding choice-element guidance resolves the original ambiguity about type-specific [x] paths.
