FHIR-26411: Audit OperationDefinition inline resource targetProfile

Issue request:
FHIR-26411 was Published/Persuasive for R5 and asked for OperationDefinition.parameter.targetProfile to apply not only to Reference and canonical parameters, but also to inline resource parameters so returned resources can be constrained to specific profiles.

Initial application:
The issue appears to have been initially applied by git commit 2e8a7e7dd9a0580c53bb24f5fcd697270083b308, which changed the OperationDefinition.parameter.targetProfile short text to mention inline Resource use. That initial application did not update the opd-3 invariant or the full targetProfile definition, and later FHIR-39345/FHIR-44690 work completed those missing pieces.

Additional context:
OperationDefinition is an active current-build resource in source/fhir.ini, so source/operationdefinition/structuredefinition-OperationDefinition.xml is authoritative for this issue. FHIR-39345 updated opd-3 to allow resource parameters and is already represented on the combined branch by a no-change audit commit. FHIR-44690 later corrected the expression to ValueSet/all-resource-types and clarified that resource parameter types use targetProfile as profile constraints on inline resource instances; that source-fix commit is also already represented on the combined branch. The originating Zulip thread records Grahame Grieve and Lloyd McKenzie agreeing this was an R5 oversight, and FHIR-I minutes record the 2020 persuasive vote. The only old targetProfile wording still found is in source/operationdefinition/operationdefinition.svg, a generated-looking diagram tooltip rather than the authoritative XML source.

AutoFHIR reconciliation:
Made no source change. The latest combined-branch OperationDefinition StructureDefinition already says targetProfile is allowed for Reference, canonical, or resource parameter types; uses all-resource-types in opd-3; and defines the resource-type behavior as applying profiles to the resource instance passed as the parameter value, corresponding to ElementDefinition.type.profile behavior. Editing only the stale SVG tooltip would not be an authoritative source correction and is outside this workflow's generated-diagram guardrail.

Recommendation:
Keep this no-change audit commit as-is. If maintainers want the checked-in OperationDefinition SVG tooltip refreshed, handle it as generated-artifact regeneration rather than as a FHIR-26411 source correction.
