FHIR-24671: Audit pre-applied category value set

Issue request:
FHIR-24671 was Published/Persuasive for R5. It asked OO to collaborate with SDWG to refine the value set used by Composition.category and DocumentReference.category; the final resolution said the category value set had already been applied and should be considered pre-applied.

Initial application:
No historical source commit explicitly names FHIR-24671. The apparent application happened through the R5 DocumentReference category work: git commit 1e542148c2d27a0394c2798fa8a1a78014db1b4d changed DocumentReference.category from the old document-classcodes binding to the new referenced-item-category value set and created source/documentreference/valueset-referenced-item-category.xml; git commit 314c3b3a9f56c4480808c133aec77d1078f3bf6f then changed Composition.category to the same referenced-item-category value set while fixing build fallout.

Additional context:
SDWG minutes in 2020 recorded that FHIR-24671 needed follow-up on the Document Class Value Set and possible IHE guidance. OO minutes in 2022 recorded that the Referenced Item Category Value Set had been updated and should address the issue, and OO minutes in 2023 recorded the final 7-0-0 pre-applied vote. Current source/fhir.ini keeps Composition and DocumentReference active, and prior combined-branch reconciliation for FHIR-32577 has already corrected the remaining DocumentReference category display/description wording to referenced records/media rather than only documents.

AutoFHIR reconciliation:
No source change was made. The current authoritative source already has DocumentReference.category and Composition.category example-bound to http://hl7.org/fhir/ValueSet/referenced-item-category, and that value set now includes media-category codes plus all LOINC codes where SCALE_TYP = LP32888-7 with a referenced-record description. Adding another source edit for FHIR-24671 would duplicate the pre-applied and already-reconciled value-set work.

Recommendation:
Keep this no-change audit. Future changes to split, narrow, or otherwise specialize Composition.category versus DocumentReference.category should be handled as a new OO/SDWG terminology decision rather than inferred from this already-applied R5 issue.
