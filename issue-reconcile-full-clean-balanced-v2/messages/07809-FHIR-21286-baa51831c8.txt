FHIR-21286: Audit Subscription email delivery guidance

Issue request:
FHIR-21286 is a Published/Persuasive FHIR-core Subscription change request asking the specification to make email delivery more predictable, especially by clarifying that email bodies are human-readable, machine-readable FHIR content goes in attachments, MIME/content-type negotiation can distinguish body and attachment behavior, and possible body-text/template/Direct-protocol extensions may be explored. The Jira resolution also mentioned SMS "as appropriate."

Initial application:
The issue was first applied in the Subscription source by e78447afbb9b095050ad9b54c9ecab233717223d, which split email and SMS channel documentation, added text/html/text/plain and attach=application/fhir+json/xml examples, and stated that email body content should be human-readable while attachments can be machine-readable. Jira later recorded 70355f13b223012ee7f9f70eb5a999219cfe7fb1 as another Subscription documentation update; that commit refined the same channel documentation and workflows. The current active Subscription source preserves the email-specific substance, though later R5/R6 model changes renamed Subscription.channel.payload fields to top-level Subscription.contentType and Subscription.content.

Additional context:
Related historical issues FHIR-18991 and FHIR-18992 established the earlier SMS/email payload and text/plain background. The SMS-specific channel prose introduced while applying this issue was intentionally removed by fb3fe3195848fb543677d2135c68a54c6a999a4b with the stated reason "Removed SMS - not enough feedback," and current Subscription source no longer defines SMS as a core channel. FHIR-23738 later served as the R5 Subscription redesign umbrella and explicitly listed FHIR-21286's email text as part of the Argonaut Subscription branch work. The original Zulip thread confirms the same connectathon rationale: raw FHIR JSON/XML should not be placed in an email body, human-readable email body content and optional FHIR attachments were discussed, and Direct/S/MIME security considerations were part of the discussion. Confluence refs search found no directly relevant FHIR-21286 pages.

AutoFHIR reconciliation:
This is an empty audit commit. The active build includes Subscription, and the current source/subscription/subscription-notes.xml email section already says message body content SHALL be human readable, attachments SHOULD be machine readable, contentType controls the body, and MIME parameters such as text/html;attach=application/fhir+xml can request a FHIR attachment. source/subscription/structuredefinition-Subscription.xml also says channel definitions such as email can allow text/plain and text/html. Reintroducing SMS or adding speculative body-template/Direct extensions would go beyond the current core source and later history.

Recommendation:
Keep this no-change audit commit as-is. If the work group later wants standardized email body text, body templates, or Direct-protocol signaling, that should be handled as a new issue/extension proposal rather than as remaining FHIR-21286 core cleanup.
