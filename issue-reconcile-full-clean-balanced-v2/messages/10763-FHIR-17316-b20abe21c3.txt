FHIR-17316: Audit POST search paging links

Issue request:
FHIR-17316 was Published/Persuasive for STU3. It asked for guidance because POST-based searches can return self/prev/next paging links represented as GET URLs, even though clients may have used POST for URL length or logging reasons. The approved resolution was to add a note about POST-based searches returning GET links and the possibility that a client turns those GETs into form-based submits again.

Initial application:
The Jira comment records svn revision 14263. In git history this is commit 84b71cb1380f51ac3b6efafb8615b57d4d428b5a, "GF#17316 - note about post/get mixing on search", which added the Paging paragraph in source/http.html. The paragraph remains in the current source after later refactoring and states that an initial POST search may have follow-up page requests made by GET, while servers SHOULD allow clients to convert follow-up requests to POST.

Additional context:
The checked pages are in current build scope: publish.ini lists http.html and search.html, and source/hierarchy.xml places Search under the RESTful API page. Current source/search.html also gives the broader link semantics added by later search work: self links are GET-based search URLs regardless of how the search was performed, and relevant paging links are expressed as GET requests. Existing combined-branch audit work for FHIR-33220 covers that later self-link/paging-link clarification and does not replace the original FHIR-17316 audit. Direct community searches found no Zulip or Confluence record for FHIR-17316; later POST-search discussions quote or rely on the same current paging paragraph rather than contradicting it.

AutoFHIR reconciliation:
This is an empty no-change audit commit. No source change is made because the authoritative HTTP Paging source already contains the note requested by FHIR-17316, and the current Search page is consistent with it. Adding another note would duplicate existing guidance without changing implementer understanding.

Recommendation:
Keep this audit commit as-is. If the work group wants a more detailed algorithm for converting opaque paging URLs into POST body form submissions, that should be handled as a new or later linked search issue; FHIR-17316 itself is already correctly reflected in current source.
