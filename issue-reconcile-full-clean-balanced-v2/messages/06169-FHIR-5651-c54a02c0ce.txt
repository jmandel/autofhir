FHIR-5651: Audit Condition relationship element naming

Issue request:
FHIR-5651 was a Published Patient Care change request for DSTU1 Condition. It asked that Condition.dueTo and Condition.occurredFollowing not name their first CodeableConcept child "codeableConcept"; the accepted modification was to rename those children to "code" and create distinct bindings.

Initial application:
No current git commit explicitly mentions FHIR-5651, but the Jira comments record the application as "svn 4978". Current git history shows the later same-source lineage: FHIR-7620/FHIR-7621 moved Condition.dueTo and Condition.occurredFollowing out of the core Condition backbone into standard extensions, and FHIR-10102 then converted those extensions to a single choice-valued value[x] instead of separate code/detail children.

Additional context:
Condition is an active core resource in source/fhir.ini, but the current source/condition/structuredefinition-Condition.xml no longer contains Condition.dueTo or Condition.occurredFollowing elements. It directs causality/predecessor use to the condition-dueTo and condition-occurredFollowing extensions. Those extension definitions now live in the FHIR Extension Pack, not core, and each has a single Extension.value[x] with a distinct binding (ConditionCause and ConditionPredecessor), so the DSTU1 child-name inconsistency is no longer present in the current core build.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Editing current core Condition would reintroduce obsolete backbone-element concepts, and editing the Extension Pack is outside this core checkout; the read-only extension-pack evidence already matches the material intent of using distinct semantics rather than the old generic codeableConcept child name.

Recommendation:
Keep this audit commit as-is. No further core action is needed for FHIR-5651 unless a future work group decision reopens the Condition relationship extension model in the Extension Pack.
