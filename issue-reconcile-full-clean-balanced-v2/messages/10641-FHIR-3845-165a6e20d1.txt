FHIR-3845: Audit repeated invariant handling

Issue request:
FHIR-3845 was a Published/Persuasive DSTU1 FHIR-I change request reporting repeated invariants on profiles and asking whether a profile could define an invariant with the same id as its parent, redefine it more tightly, or whether that was illegal. The decisive Jira comment says that using the same id is an error.

Initial application:
No explicit FHIR-3845-tagged source commit was found. The active ElementDefinition source already contains the relevant invariant, eld-14, with human text "Constraints must be unique by key" and FHIRPath "constraint.select(key).isDistinct()". That invariant was already present when ElementDefinition was split into source/datatypes/elementdefinition.xml in ee49751f230a4a4b753e9aaa603eaab0743271ff and was later carried forward into the current FHIRPath form by e6b7e7387b566458f155dfb402fd78a8d04a0af1.

Additional context:
source/fhir.ini lists ElementDefinition as an active type with its own type page, so source/datatypes/elementdefinition.xml and source/elementdefinition.html are in current build scope. The ElementDefinition guidance says additional constraints can be defined but do not replace constraints from the base definition, while mappings are the separate case where same identity replacement is allowed. Later Zulip discussion confirms the current practical rule is more nuanced than global uniqueness: keys are not globally unique across an IG, duplicate keys in an inheritance path can be errors, and any future relaxation for identical expressions would need its own resolved specification decision.

AutoFHIR reconciliation:
This audit commit makes no source change. The target combined branch already carries the active constraint-key uniqueness invariant and related profiling guidance needed for FHIR-3845, and adding redundant prose here would risk overstating global key uniqueness or preempting later unresolved tooling-policy questions.

Recommendation:
Keep this audit commit as-is for FHIR-3845. If the work group wants to change or document cross-element reuse of the same constraint key, especially reuse with identical expressions, handle that as a separate issue because FHIR-3845 only supports the existing no-redefinition/error rule.
