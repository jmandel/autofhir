FHIR-15782: Use paused in RequestStatus on-hold definition

Issue request:
FHIR-15782 was Published/Persuasive with Modification for STU3 and asked to update valueset-request-status definitions. The final resolution rejected adding 'plan' everywhere, but specifically approved changing on-hold to say the request and any implicit authorization has been temporarily paused and is expected to resume, alongside revised revoked, completed, and entered-in-error definitions.

Initial application:
Jira records Github#6b8ca9c6. That merge applied most of the issue in source/request/request-spreadsheet.xml, replacing authorization/request wording for revoked, completed, and entered-in-error, but the on-hold definition was committed as 'temporarily withdrawn' rather than the approved 'temporarily paused'. The 2021 source rework then carried that wording into source/request/codesystem-request-status.xml, so current source still had one semantic mismatch.

Additional context:
source/fhir.ini lists request as an active logical pattern, and the request-status worksheet plus CodeSystem source feed the current Request pattern terminology. Related Published/Applied Request-status decisions renamed suspended/cancelled to on-hold/revoked, aligned Request.status usage, and later added the ended parent, but none supersede the FHIR-15782 on-hold definition. A later Resolved - change required proposal for another RequestStatus code remains outside this default Applied/Published reconciliation scope.

AutoFHIR reconciliation:
This commit changes the active RequestStatus on-hold definition in both source/request/request-spreadsheet.xml and source/request/codesystem-request-status.xml from 'temporarily withdrawn' to 'temporarily paused'. No change was needed in source/request/valueset-request-status.xml because it only composes the request-status CodeSystem.

Recommendation:
Keep this source fix as-is. It completes the approved FHIR-15782 wording without revisiting later RequestStatus hierarchy or future-code proposals; future work on FHIR-53252 should be handled separately if and when it is applied.
