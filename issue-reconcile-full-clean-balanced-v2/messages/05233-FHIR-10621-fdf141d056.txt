FHIR-10621: Update CarePlan activity kind definition

Issue request:
FHIR-10621 was Published with a Not Persuasive with Modification resolution for DSTU2 after Patient Care considered whether CarePlan.activity.detail.category should bind to an external code system. The accepted resolution removed the old category element in favor of an inline activity kind code with a required binding to a filtered resource-type value set and retained the requirement that the kind may determine permitted extensions.

Initial application:
The historical implementation commit 96ea9f40cb80fdaebe3f1e29e72447fa55a5ea8a is explicitly tagged for #10621 and added the Care Plan Activity Kind value set. Current source already has CarePlan.activity.plannedActivityDetail.kind as a code with a required binding to http://hl7.org/fhir/ValueSet/care-plan-activity-kind, and that value set contains the intended resource-type choices, updated for the later ProcedureRequest to ServiceRequest rename.

Additional context:
FHIR-14817 later confirmed that the inline activity kind was not redundant because the detail/reference alternatives are mutually exclusive. FHIR-26064 then renamed CarePlan.activity.detail to CarePlan.activity.plannedActivityDetail and CarePlan.activity.reference to CarePlan.activity.plannedActivityReference. Separate combined-branch reconciliation commits already exist for FHIR-26064 and FHIR-39101, so this commit does not re-decide those issues; it only aligns the FHIR-10621 definition text with the current element names on the active combined branch.

AutoFHIR reconciliation:
This commit updates the CarePlan.activity.plannedActivityDetail.kind definition so it names CarePlan.activity.plannedActivityDetail and CarePlan.activity.plannedActivityReference instead of the pre-R5 CarePlan.activity.detail and CarePlan.activity.reference paths. No binding, value-set membership, cardinality, or examples were changed.

Recommendation:
Keep this commit as-is. It preserves the original FHIR-10621 semantics while removing stale path names that would otherwise mislead readers of the current CarePlan StructureDefinition.
