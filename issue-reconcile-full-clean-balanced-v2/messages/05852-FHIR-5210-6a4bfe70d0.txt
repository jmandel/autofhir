FHIR-5210: Audit EpisodeOfCare referral direction

Issue request:
FHIR-5210 was a Published/Persuasive with Modification Jan 2015 ballot issue for EpisodeOfCare asking how to track and manage referral-in versus referral-out when related referrals are tracked at the episode level. Its resolution referred to FHIR-5209 and concluded that the FHIR-5209 change, together with the referral requestor and recipient fields, should differentiate inbound from outbound referrals; it also asked that EpisodeOfCare status codes be reconsidered for referral receipt handling.

Initial application:
No git commit explicitly mentions FHIR-5210. The issue appears to have been applied implicitly through the March 2015 EpisodeOfCare ballot reconciliation commit f659c3fbc16870414aac80f798d75afcb5480bf8, which renamed currentStatus to status, made EpisodeOfCare.referralRequest repeat, defined those requests as incoming referrals fulfilled by the EpisodeOfCare, and renamed the corresponding search parameter toward an incoming-referral concept. Later source refactors preserved the same semantics while ReferralRequest was folded into ServiceRequest.

Additional context:
EpisodeOfCare is active in the current build through source/fhir.ini. Current EpisodeOfCare source defines referralRequest as 0..* Reference(ServiceRequest) with the definition "Referral Request(s) that are fulfilled by this EpisodeOfCare, incoming referrals." Narrative now says an incoming referral can create a new EpisodeOfCare, while the intake example separately says the organization can create an outgoing ServiceRequest to continue care. Current ServiceRequest retains requester and performer/request-recipient semantics, supporting the Jira resolution's direction test. The EpisodeOfCare status code system includes planned and waitlist states for intake and acceptance workflow. Zulip and Confluence searches found no directly relevant or conflicting FHIR-5210 record.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The authoritative current source already carries the inbound/outbound distinction and status handling expected by FHIR-5210, and adding duplicative prose would not change implementer understanding.

Recommendation:
Keep this audit commit as-is. No FHIR core follow-up is needed for FHIR-5210 unless the Patient Administration work group later wants a broader redesign of EpisodeOfCare referral workflow or ServiceRequest directionality.
