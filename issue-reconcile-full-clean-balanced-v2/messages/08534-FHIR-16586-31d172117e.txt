FHIR-16586: Audit display language validation note

Issue request:
FHIR-16586 was a Published/Not Persuasive with Modification STU3 FHIR-I issue asking how $validate and code validation should behave when resources carry display values in a language different from the server's validation displays. The accepted resolution rejected a hard Resource.language-based rule and instead required an implementation note that validation behavior for language, especially Coding.display, was currently undefined and might receive later requirements or recommendations.

Initial application:
The issue was explicitly applied by git-svn commit 40233ff25a, titled "GF#16586 - note about display language and validation". That commit added the undefined-language-validation note to the Resource $validate operation and the ValueSet $validate-code operation in the then-authoritative spreadsheet sources. The current XML OperationDefinition sources retain that application: Resource/$validate carries the note in the footer/comment, and ValueSet/$validate-code carries the matching Coding.display language note.

Additional context:
The same Zulip thread also led to FHIR-17218 for ValueSet $validate-code display result status; that issue already has a no-change reconcile commit on the combined branch. Later final issues refined specific parts of the space: FHIR-39526 added Resource $validate control parameters including language and display-issues-are-warnings, FHIR-40770 aligned repeated displayLanguage semantics for $validate-code, and FHIR-41229 added lenient-display-validation for invalid displays. These later decisions narrow specific parameter behavior but do not revive the original proposed Resource.language rule or require removing the historical caveat.

AutoFHIR reconciliation:
This audit commit intentionally makes no source changes. The combined branch already contains the FHIR-16586 note in the active Resource and ValueSet operation sources, while the active CodeSystem $validate-code source is governed by later Vocabulary decisions and should not receive the older broad undefined-behavior note as a FHIR-16586 fix.

Recommendation:
Keep this no-change audit. Further precision about display-language fallback, Accept-Language handling, or Resource.language interactions should be handled by a new final FHIR-I/Vocabulary decision rather than by reapplying the 2018 rejected proposal.
