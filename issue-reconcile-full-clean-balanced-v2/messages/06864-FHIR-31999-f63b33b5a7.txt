FHIR-31999: Audit cross-version extension pre-adoption guidance

Issue request:
FHIR-31999 was a Published/Persuasive FHIR-core clarification request for the compatibility page. It asked whether the cross-version extension URL mechanism could be used to pre-adopt content such as R5 SupplyRequest.item from an earlier version, and the approved resolution said to clarify that the mechanism applies to net-new/backbone content and cardinality increases, but not to simple expansion of allowed reference targets for a polymorphic element.

Initial application:
No source commit was found that explicitly mentions FHIR-31999. The same compatibility section was updated by FHIR-31348, FHIR-36702, and FHIR-31721; FHIR-31721 added the relevant R5-era guidance for complex extensions, cardinality increases, targetProfile differences, alternate-reference/alternate-canonical, and a complex-extension example.

Additional context:
The current core source was later refactored by f45505e5b3a to move detailed cross-version conversion content out of versions.html and into the individual cross-version definition packages, leaving the core page with the URL pattern, scope summary, package links, and a pointer to package details. The current references page also describes alternate-reference for cases where the target resource is not allowed by the base reference element. The published R5-to-R4 cross-version package demonstrates the SupplyRequest.item case directly: it defines a complex extension for R5 SupplyRequest.item in R4, lists DeviceDefinition among the supported CodeableReference targets, and separately uses alternate-reference for target-only expansion cases.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source is correct because the core build page remains the build-scope overview while the detailed, generated cross-version package now owns the example-specific mechanics requested by FHIR-31999. Reintroducing the removed detailed prose into core would duplicate package-owned guidance and risk drift.

Recommendation:
Keep this audit as-is. Future changes to the detailed pre-adoption mechanics should be made in the cross-version package/source workflow, while core versions.html should continue to provide the stable overview and package links.
