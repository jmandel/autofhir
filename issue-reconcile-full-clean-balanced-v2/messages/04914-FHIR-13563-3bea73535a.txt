FHIR-13563: Audit Location.type cardinality

Issue request:
FHIR-13563 was a Published/Persuasive PA change request for STU3 asking why Location.type was 0..1 when a single Location can support multiple functions or services, such as OB and GYN care. The approved resolution was to update the cardinality to support multiple types.

Initial application:
The issue was applied by historical commit 3816ab7838 (GF#13563), which changed the old source/location/location-spreadsheet.xml Location.type row from 0..1 to 0..*. The current source has since been refactored into source/location/structuredefinition-Location.xml, and that file preserves Location.type with min 0 and max *.

Additional context:
Location is an active resource in source/fhir.ini, so source/location/structuredefinition-Location.xml is in the current build scope. Later Location.type issues FHIR-43181, FHIR-41510, and FHIR-50319 changed the binding, value set, short text, and definition, but they retained the 0..* cardinality and do not reverse the FHIR-13563 decision. Zulip and Confluence searches found no substantive community discussion that conflicts with the Jira/source/git conclusion; the Zulip hits were tracker/commit bot notifications for GF#13563.

AutoFHIR reconciliation:
No source change was made. The current authoritative Location StructureDefinition already allows multiple Location.type values, matching the approved FHIR-13563 resolution.

Recommendation:
Keep this audit commit as-is. No follow-up source work is needed for FHIR-13563 unless a future PA decision separately reconsiders Location.type cardinality.
