FHIR-36195: Audit Device operation rename history

Issue request:
FHIR-36195 was a Published/Persuasive with Modification R5 OO change request for FHIR-core Device. It asked to replace the prior Device.operationalStatus structure with a repeating operation/operationalState backbone containing status, statusReason, operator, mode, cycle, and duration details for device use.

Initial application:
The Jira comment points to commit 2c8d41bdffb2e2cbc27ec8bfb76ee0f9edf2d0d1 as the build application. Nearby history shows 0e4e912dedef663db1fc73bcee4b3ab79586023e and d76dc5b48270664a83bc7b51d07bfc4b7f78e6ed first changed Device.operationalStatus to Device.operationalState and added the requested children, while the Jira-linked commit refined the operator short text. FHIR-37545 later completed the naming requested by this family by renaming Device.operationalState to Device.operation and aligning operation value set names.

Additional context:
Later Published Device decisions changed the model before the current build. FHIR-38904 removed the Device operation/operationStatus backbone from Device while introducing DeviceAssociation, and FHIR-48924 later removed the remaining Device.mode, Device.cycle, and Device.duration elements in favor of Device operation extensions. Current Device and DeviceAssociation are active resources in source/fhir.ini, but current parsed source contains no active Device.operation, Device.operationalState, Device.operationalStatus, or DeviceAssociation.operation elements; the resource introduction notes explain that Device.mode/cycle/duration were removed and DeviceAssociation.operation was collapsed into other elements.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Re-applying the FHIR-36195 R5 structure would conflict with later published R5/R6 Device decisions, and the current built source is already consistent with those later decisions.

Recommendation:
Keep this audit commit as-is. No core follow-up is needed for FHIR-36195 unless the work group separately decides to reintroduce an operation backbone in a future Device or DeviceAssociation issue.
