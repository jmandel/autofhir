FHIR-25773: Remove stale DocumentReference masterIdentifier ModelInfo

Issue request:
FHIR-25773 was Published with a Persuasive OO resolution for R5. It asked to remove the confusing and misplaced DocumentReference.masterIdentifier element, move that document-identifier function into DocumentReference.content.identifier, and adjust the identifier search parameter.

Initial application:
No local commit message directly names FHIR-25773, but the July 2020 DocumentReference block-vote commit 0bf0b46a829ce94829ceef7e036dcb2043c74d18 removed masterIdentifier from a DocumentReference example and added content.identifier in the DocumentReference spreadsheet/example source. That matched the original Jira request at the resource source level.

Additional context:
FHIR-32584 later superseded the content.identifier model by removing DocumentReference.content.identifier and consolidating business identifiers on DocumentReference.identifier. The current DocumentReference StructureDefinition and identifier search parameter already reflect that later model, and source/fhir.ini maps the old R4 DocumentReference.masterIdentifier to DocumentReference.identifier. The active FHIR ModelInfo Library, however, still exposed a stale DocumentReference.masterIdentifier element even though DocumentReference and Library are both active build resources and the ModelInfo payload is published as a Library example.

AutoFHIR reconciliation:
This commit removes the stale DocumentReference.masterIdentifier element from source/library/library-fhir-model-definition-content.xml and regenerates the embedded base64 payload in source/library/library-fhir-model-definition.xml. It intentionally does not add content.identifier because the later FHIR-32584 decision made DocumentReference.identifier the correct current target.

Recommendation:
Keep this source fix. It reconciles the remaining current-build FHIR ModelInfo surface with FHIR-25773 as superseded by FHIR-32584; any broader QUICK or historical model-definition cleanup should be handled separately because this issue concerns the current FHIR DocumentReference model.
