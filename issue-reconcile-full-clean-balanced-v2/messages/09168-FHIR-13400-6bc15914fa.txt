FHIR-13400: Audit sliceName constraint application

Issue request:
FHIR-13400 was a Published/Persuasive with Modification FHIR-core StructureDefinition issue asking for sliceName constraints: no sliceName on a true snapshot or differential root element, and no snapshot sliceName unless an earlier element in the same path hierarchy declares slicing.

Initial application:
The issue was applied by git-svn commit 5dfb9237e7c6c0550099bc8feedb68b7a8c85eaf (svn revision 14484), which added StructureDefinition invariant sdf-23 to the then-authoritative StructureDefinition spreadsheet. The current generated StructureDefinition source carries that invariant forward as an error-level rule on both snapshot.element and differential.element.

Additional context:
The Jira resolution narrowed the enforceable change: a differential may start at a non-root subnode, so the root test must be path-based, and the same-path predecessor rule was accepted as correct but not expressible in FHIRPath without grouping or a previous-node axis. Current ElementDefinition slicing prose still defines slices as elements following the slicing entry with the same path until a shorter path occurs, and the current StructureDefinition resource is active in source/fhir.ini.

AutoFHIR reconciliation:
No source change was made. The current source already contains the required path-based root sliceName invariant, and adding a duplicate or approximate invariant for the accepted but non-expressible predecessor rule would exceed the Jira resolution and risk false validation behavior.

Recommendation:
Keep this no-change audit commit. If tooling later gains sequence-aware FHIRPath/grouping support, the second rule could be reconsidered as a new validator/tooling enhancement, but the current specification source matches the applied FHIR-13400 decision.
