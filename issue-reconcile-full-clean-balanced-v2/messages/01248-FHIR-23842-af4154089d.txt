FHIR-23842: Audit formal abstract type framework

Issue request:
FHIR-23842 was a Published/Persuasive MnM change request asking to formally define the abstract type "Type" because it existed in reference implementations and UML definitions but did not exist formally. The approved resolution was to define this type formally in R5.

Initial application:
No Jira-keyed implementation commit was found for FHIR-23842. The relevant source history instead shows an unkeyed December 2019 "rebuild abstract type framework" commit that introduced formal source spreadsheets and active fhir.ini entries for Base, Element, BackboneElement, DataType, PrimitiveType, and BackboneType. Later source state and R5 publication use this explicit abstract type framework rather than a separate canonical StructureDefinition/Type.

Additional context:
The current build-scope authority, source/fhir.ini, actively lists the abstract infrastructure types and maps their pages to types.html. The current narrative source defines the FHIR Type Framework as the base abstract types that provide the foundation for datatypes, resources, and logical models, and includes DataType as the base definition for usable FHIR datatypes. R5 and current build publication checks confirm Base and DataType StructureDefinitions exist and are abstract, while type.profile.json/StructureDefinition/Type is absent. A later FHIR-53296 issue proposes moving Base and DataType into an abstract display group, but it is only Resolved - change required and does not establish a separate Type definition for this reconciliation.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Adding a new canonical Type now would be a substantive model change and would conflict with the already-published R5/current source model, where the approved formalization is represented by the Base/DataType abstract framework.

Recommendation:
Keep this no-change audit. If the work group still wants a distinct canonical StructureDefinition/Type instead of the current Base/DataType framework, that should be raised as a new model-change issue rather than inferred from FHIR-23842.
