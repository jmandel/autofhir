FHIR-33169: Align PlanDefinition apply narrative with Bundle result

Issue request:
FHIR-33169 was Published/Persuasive with Modification for R5 and asked to simplify PlanDefinition/$apply semantics by removing useCarePlan, returning Bundle 0..*, and representing each per-subject result as a Bundle rather than a CarePlan wrapper.

Initial application:
Commit e54c8a3dda (J#33169) removed the useCarePlan input, changed the return parameter to multi-cardinality Bundle, and rewrote the operation and narrative toward Bundle/RequestOrchestration semantics. The current operation definition and PlanDefinition operations list are in build scope, but the PlanDefinition narrative still retained one pre-Bundle sentence saying created resources are returned as contained resources in the result.

Additional context:
RequestGroup was later renamed to RequestOrchestration in the current source, and FHIR-46313 intentionally relaxed the FHIR-33169 strict RequestOrchestration-wrapper wording so PlanDefinition/$apply can return any applicable request-resource combination in the result Bundle. FHIR-51557 later clarified that the multi-cardinality Bundle return is still conveyed through a Parameters response. Zulip and CDS Confluence evidence support the original FHIR-33169 rationale while also explaining why the later FHIR-46313 relaxation should be preserved.

AutoFHIR reconciliation:
Updated source/plandefinition/plandefinition-notes.xml so the transient-result note says created resources are returned as entries in the result Bundle(s), not as contained resources in a single result. No useCarePlan or return-signature changes were needed because those parts are already correctly applied, and the later FHIR-46313 variability was left intact.

Recommendation:
Keep this commit. It fixes the remaining semantic mismatch from the FHIR-33169 application without reverting the later work-group decision in FHIR-46313 or duplicating the FHIR-51557 response-format clarification.
