FHIR-17559: Audit Consent.scope extensibility

Issue request:
FHIR-17559 was a Published FHIR-core Consent change request with resolution Persuasive with Modification. It asked to make the then-current Consent.scope CodeableConcept binding extensible because a required four-code scope list prevented non-patient uses, and to rename the consent scope code "privacy" to "patient-privacy".

Initial application:
No git commit explicitly mentioning FHIR-17559 was found. The requested code rename was already present in history in commit f4bb6c3d6e, which changed the consent-scope code and examples from privacy to patient-privacy. The R4 published history shows Consent.scope as 1..1 with an extensible binding to ValueSet/consent-scope and the patient-privacy code in the consent-scope CodeSystem, so the STU3/R4-era request was reflected in the published source lineage.

Additional context:
Later Published Consent issues changed the model. FHIR-27776 clarified Consent.scope wording for R5, and FHIR-31903 then superseded the separate scope element by eliminating Consent.scope and changing Consent.category to 0..* with an example binding to a category value set that includes the consent-scope code system. Current fhir.ini keeps Consent active and records the old Consent.scope path as merged with Consent.category. Zulip discussion for FHIR-31903 confirms the WG rationale that scope and category were duplicative and that category should be the flexible categorization surface.

AutoFHIR reconciliation:
This commit intentionally makes no source change. In the current build, source/consent/structuredefinition-Consent.xml no longer defines Consent.scope; Consent.category is 0..* and bound with strength example, and source/consent/valueset-consent-category-example.xml includes http://terminology.hl7.org/CodeSystem/consentscope. A current-source search found no Consent.scope element and no current Consent example or Consent value set using code="privacy".

Recommendation:
Keep this empty audit commit as-is. Reintroducing a Consent.scope edit would conflict with the later FHIR-31903 model change; any future change to consent-scope codes belongs in the terminology/THO process or a new Consent.category-focused tracker, not in a revival of the removed core element.
