FHIR-15095: Audit identifier wording application

Issue request:
FHIR-15095 was a Published / Persuasive with Modification STU3 request saying resources such as Composition, DetectedIssue, DeviceComponent, DeviceMetric, ImagingManifest, QuestionnaireResponse, SupplyRequest, and datatypes should not describe identifier as the unique logical resource id. The approved resolution updated the Event, Request, and Definition pattern identifier descriptions to business-identifier wording, did not require all identifier elements to become 0..*, and asked editors to review resource-specific wording while allowing domain-specific refinements.

Initial application:
The issue was applied by git commit 70df4285c448d78f8b09c6c7a1ff02a807e99be9, imported from SVN r13441, with subject "GF#15095 - revise definitions of identifier". That commit changed the Event, Request, and Definition pattern spreadsheets to describe identifiers as business identifiers and add the note distinguishing business identifiers from resource identifiers. Current source still carries the Event and Request pattern wording, while the Definition pattern was later refined by FHIR-40406 to align with canonical-resource wording while retaining the business-identifier role.

Additional context:
The active build list includes Composition, DetectedIssue, DeviceMetric, and QuestionnaireResponse, but DeviceComponent is commented out, ImagingManifest is only in removed/legacy metadata, and SupplyRequest is absent from the active [resources] list. Current active resource definitions do not use identifier as the unique FHIR logical id: DetectedIssue and QuestionnaireResponse use the business-identifier wording; DeviceMetric gives a device-domain instance/handle identifier rather than a resource logical id; and Composition keeps CDA setId-style version-independent business identification with 0..* cardinality. The resource identity narrative separately explains logical id versus business identifier. Zulip follow-up from the applying editor confirms the workflow patterns were templates and that resource editors could refine wording.

AutoFHIR reconciliation:
This empty audit commit intentionally makes no source change. The approved pattern-level change has already been applied, later Definition-pattern maintenance does not reintroduce the original ambiguity, and the remaining active resource-specific wording is either aligned or intentionally domain-specific. Editing legacy/out-of-build DeviceComponent, ImagingManifest, or SupplyRequest source would not be a current-build correction.

Recommendation:
Keep this audit as-is. If a future work group wants stricter uniform wording across every resource-specific identifier element, that should be a new harmonization issue; FHIR-15095 itself is already satisfied in the current build.
