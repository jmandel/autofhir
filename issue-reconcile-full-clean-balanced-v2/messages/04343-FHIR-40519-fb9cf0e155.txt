FHIR-40519: Audit messaging protocol wording

Issue request:
FHIR-40519 was Published/Persuasive for R5 and asked FHIR-core messaging to clarify that the base specification provides a direct delivery mechanism while other transfer mechanisms can be abstracted and should define their exact message transfer protocol in implementation guides.

Initial application:
The requested wording was applied to source/messaging.html by the February 24, 2023 FHIR-39096/FHIR-40518/FHIR-40519 merge commit 87b1af3c094d4dd726733409d815683ceeab15c7. The same issue key also appears in the topic branch commit 5e04fe1f02dae32f3f0abc945c15dade0d13a5cd, but the source-changing application for this paragraph is in the merge commit.

Additional context:
The current source/messaging.html page is a current FHIR messaging narrative page and still contains the approved clarification in Basic Messaging Assumptions. Later Published/Persuasive FHIR-40501 added Apache Kafka to the examples of transfer mechanisms, which explains the only meaningful difference from the original FHIR-40519 replacement text. The February 2023 Zulip thread and FHIR-I minutes show the protocol wording arose from the same discussion as FHIR-40518 about response-message expectations.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current messaging source already states that this specification provides a direct delivery mechanism, other transfer mechanisms may be abstracted, those mechanisms are expected to define implementation guides for the exact message transfer protocol, and logical-to-implementation address mapping remains out of scope.

Recommendation:
Keep this audit commit as-is. No further core source change is recommended for FHIR-40519; any future adjustment should be driven by a new messaging transport decision rather than by reapplying the already-published R5 clarification.
