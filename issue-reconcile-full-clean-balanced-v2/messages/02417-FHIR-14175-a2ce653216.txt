FHIR-14175: Audit Signature MIME format split

Issue request:
FHIR-14175 was a Published/Persuasive STU3 FHIR-core issue from the Security WG. It requested that Signature stop using one contentType element ambiguously for the signature blob MIME type, rename that field to make the signature MIME type clear, and add a separate MIME-typed field for the format of the FHIR resources being signed.

Initial application:
The issue appears to have been applied in git commit f72fd6237875c6ba9d2a21e235881c7fed559700, which changed the Signature datatype source from Signature.contentType to Signature.targetFormat and Signature.sigFormat, bound both rows to MimeType, described targetFormat as the technical format of the signed resources, and updated Provenance signature examples. Later commit b96bbd292505dde0f56bdda132c7476d85b19de8 renamed Signature.blob to Signature.data, but did not undo the FHIR-14175 MIME split.

Additional context:
Signature is an active current datatype in source/fhir.ini and is marked normative. Later reconciliation for FHIR-48679 removed a stale short-form xml/json/ttl allowance from Signature.targetFormat while preserving the plain MimeType binding, and later reconciliation for FHIR-47211 fixed remaining signature-rule wording to use Signature.sigFormat and Signature.targetFormat consistently. These later decisions refine surrounding MIME/canonicalization guidance but do not supersede the FHIR-14175 element split.

AutoFHIR reconciliation:
No source change was made. The current authoritative Signature datatype source already has Signature.targetFormat for the signed resources and Signature.sigFormat for the signature itself, both bound to MimeType, and current examples/rules use targetFormat and sigFormat without stale Signature.contentType references.

Recommendation:
Keep this audit commit as-is. No FHIR-core follow-up is needed for FHIR-14175 unless the Security WG makes a new decision to rename the already-established targetFormat/sigFormat elements or change their MIME bindings.
