FHIR-42931: Audit SearchParameter multiples rendering

Issue request:
FHIR-42931 was Applied/Persuasive with Modification for R6. The issue reported that standard SearchParameter pages, such as Group search, rendered omitted multipleAnd/multipleOr values as "The parameter cannot repeat or have multiple values" even though the intended meaning was server discretion. The approved resolution was to render separate Multiple And and Multiple Or rows that explicitly convey the meaning-if-missing, and to leave core SearchParameter instances unset by default unless a work group has a specific reason to require true or false. The modifier discussion did not require a core source edit because the resource model still cannot distinguish "no modifiers allowed" from "no restrictions expressed" by absence alone.

Initial application:
No commit in this FHIR source checkout directly mentions FHIR-42931. The underlying SearchParameter definitions had already been clarified by FHIR-40328 in commit 3625f3cd1975c798b2051bf5216f946563265678, which added meaningWhenMissing text for SearchParameter.multipleOr and SearchParameter.multipleAnd. The remaining FHIR-42931 application appears to have been a publisher/rendering fix rather than a core source-data change: current CI output for Group search now renders distinct multipleAnd and multipleOr rows with server-discretion language when the source omits both elements.

Additional context:
FHIR-I minutes on 2023-10-30 record the 9-0-0 motion and the core conclusion that FHIR already defined the missing multipleAnd/multipleOr behavior. Zulip follow-up in November 2023 confirms that the definitions were correct, the rendering was oversimplified, and work groups should not mass-populate multipleAnd/multipleOr just to work around the rendering issue. The active fhir.ini entries include SearchParameter and Group, and the Group search parameter source still intentionally omits multipleAnd/multipleOr on representative standard search parameters.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current authoritative SearchParameter source already states the correct meaning when multipleAnd/multipleOr are missing, the active Group search parameter source preserves the intended unset defaults, and the current rendered build no longer displays the misleading "cannot repeat or have multiple values" sentence. Adding multipleAnd/multipleOr values to standard search parameter resources would change conformance semantics and contradict the Jira resolution.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-42931 unless the publisher rendering regresses; any such future regression should be fixed in the rendering/publisher path, not by populating default multipleAnd/multipleOr values across core SearchParameter instances.
