FHIR-14670: Audit operation subset capability guidance

Issue request:
FHIR-14670 was a Published STU3 FHIR-core change request asking to split ValueSet $expand so terminology servers could distinguish support for GET ValueSet/[id]/$expand from POST ValueSet/$expand with an arbitrary ValueSet. The final Not Persuasive with Modification resolution rejected splitting the operation and instead required CapabilityStatement guidance: referencing a base OperationDefinition means supporting the full operation, while subset support requires a custom OperationDefinition based on the original.

Initial application:
The issue appears to have been applied by git commit 73c40e6c1f2068f77c616a53ae2f37c564acb4b2, "GF#14670 - not about custom operations in capabilitystatement", which changed the CapabilityStatement spreadsheet source. Current history shows the wording was carried through later source refactors into source/capabilitystatement/structuredefinition-CapabilityStatement.xml.

Additional context:
The linked Zulip thread confirms the same intent: CapabilityStatement references must point to an OperationDefinition that describes the server's actual implementation, and a server that deviates from the base $expand definition needs its own OperationDefinition. FHIR-14960 arose from the same thread for the separate GET/POST operation execution wording and is already represented on the combined branch by d6452c245ad646a2636ed8de3e9d251d9dc05fcb, so this commit does not duplicate that decision.

AutoFHIR reconciliation:
No source change was made. CapabilityStatement is an active resource in source/fhir.ini, OperationDefinition is active, and CapabilityStatement.rest.resource.operation.definition already says that referencing the specification base OperationDefinition such as ValueSet-expand means supporting the full capabilities including GET and POST; if only a subset is supported, a custom OperationDefinition with base pointing to the original must describe that subset.

Recommendation:
Keep this no-change audit commit. The current built source satisfies FHIR-14670, and adding more prose or splitting $expand would contradict the published resolution.
