FHIR-2865: Audit compartment all-types search clarification

Issue request:
FHIR-2865 was a Published/Persuasive FHIR-core change request asking to clarify the ambiguous DSTU1 compartment search form GET [base]/[compartment]/[id]/? so readers would not confuse a compartment all-types search with reading the compartment-defining resource.

Initial application:
The issue was applied by commit 04f196672ff2f42a31650ada7f0b8bc1ced2c70d, which replaced the ambiguous GET [base]/[compartment]/[id]? form with GET [base]/[compartment]/[id]/*? and linked the all-patient-record use case to $everything. Later HTTP/search refactors preserved that applied syntax and expanded the explanation.

Additional context:
Current source/http.html is in the active HTTP page source and now shows the GET all-contained-resource-types compartment search as [base]/[Compartment]/[id]/*, explains that the literal * means all types and distinguishes the interaction from a read, lists search-compartment with /[compartment]/[id]/*? in the interaction table, and points to Patient/Encounter $everything operations. A later Applied issue, FHIR-51608, clarified related compartment-search URL behavior and is already represented on the combined branch, so it should not be republished here. Zulip discussion in 2018 confirms the same interpretation of * as resources of all types; Confluence and direct Zulip key searches found no conflicting FHIR-2865-specific record.

AutoFHIR reconciliation:
This empty audit commit makes no source change because the current built source already conveys the FHIR-2865 clarification and subsequent related work remains consistent with it.

Recommendation:
Keep this no-change audit as-is. Further edits for FHIR-2865 would be redundant; any future compartment URL work should be handled under newer compartment-search issues rather than reopening the DSTU1 ambiguity.
