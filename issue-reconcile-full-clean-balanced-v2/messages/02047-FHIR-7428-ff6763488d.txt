FHIR-7428: Audit Composition SNOMED type binding

Issue request:
FHIR-7428 was a Published/Persuasive with Modification DSTU1 Structured Documents request for Composition type codes to permit SNOMED CT use. The resolution said Composition.type and the then Composition.class binding should not force LOINC, and that the Composition.type comment should strongly endorse LOINC while noting most implementation guides would require LOINC as an extensible binding.

Initial application:
The issue was applied in SVN revision 6198, now git commit d69e59071c85aff8e7d5d104188c39f911f4d6f4, which added the LOINC endorsement note to the Composition.type spreadsheet source. A closely preceding same-family commit for FHIR-8057/SVN 5993 changed the Composition DocumentType binding to preferred and kept the then DocumentClass binding as an example binding with a LOINC document-kind value set.

Additional context:
Composition is active in the current build through source/fhir.ini. The current XML source has Composition.type bound preferred to http://hl7.org/fhir/ValueSet/doc-typecodes and includes the LOINC guidance note, so SNOMED CT remains possible without contradicting the work group's LOINC endorsement. The old Composition.class element has since become Composition.category; later category work for DocumentReference and Composition, including FHIR-17171, FHIR-32577, FHIR-24671, and FHIR-31668, keeps category as an example binding and moved it to the broader referenced-item-category value set. That later trail makes changing category back to preferred unsafe and unnecessary for this seed.

AutoFHIR reconciliation:
No source change was made. The current authoritative Composition.type source already satisfies the SNOMED CT allowance and LOINC guidance requested by FHIR-7428, while the category/class portion is governed by later category decisions rather than this DSTU1 wording.

Recommendation:
Keep this no-change audit. Do not strengthen Composition.category from example to preferred under FHIR-7428; any future change to category binding strength should be handled as a new Structured Documents/Orders and Observations decision because later Jira history deliberately treats the category value set as example guidance.
