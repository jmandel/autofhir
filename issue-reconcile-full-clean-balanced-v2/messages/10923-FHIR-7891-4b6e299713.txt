FHIR-7891: Audit search POST clarification

Issue request:
FHIR-7891 was a Published/Persuasive DSTU1 FHIR-core change request asking that the search-specific page clarify what URL POST search must be supported against, and also carry the HTTP-page guidance that resources returned inside a Bundle do not have per-resource ETag or Last-Modified headers. The recorded resolution was to update the page to make this clear.

Initial application:
The issue was initially applied in git-svn commit 4f363ad0bd1afafaa97da59cb1cee0d469fcf2ef (svn r5534), which explicitly mentioned #7891 and added a POST [base]/[type]/_search example to source/search.html. That initial application did not duplicate the Bundle ETag/versionId sentence on search.html, and later commits substantially refactored the search and HTTP pages.

Additional context:
The current build uses source/search.html and source/http.html as active top-level pages linked from source/documentation.html. A later Published/Persuasive with Modification issue, FHIR-39137, approved moving search transport protocol content from search.html to http.html and leaving search.html to reference the HTTP page for method-specific details. Commit e441170220c19e992f803667b245e63dcdd508cf implemented that structure. Current search.html describes the search contexts and POST shapes at a search-concepts level and explicitly points to http.html#search for HTTP method details. Current http.html#search lists the supported POST URLs for system, type, and compartment searches, requires form-encoded POST body parameters, describes optional query parameters, and its response summary table marks search interaction versioning headers as N/A. The general HTTP header section still states that resources returned as part of a Bundle have no ETag and use the resource versionId directly.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already gives implementers the required POST URL clarification through the active search contexts and HTTP search section, and the ETag/Last-Modified behavior is still present in the authoritative HTTP header and interaction-summary material. Adding duplicate header prose to search.html would work against the later FHIR-39137 page-structure decision and create avoidable drift.

Recommendation:
Keep this audit commit as-is. Revisit only if FHIR-I decides to reverse the FHIR-39137 structure and duplicate HTTP transport/header details on the search page again.
