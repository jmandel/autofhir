FHIR-6251: Audit Communication payload content wording

Issue request:
FHIR-6251 was a Published/Persuasive with Modification DSTU1 Patient Care change request. It said Communication.payload.content[x] was too narrow because it only described multipart messages, and it requested changing the definition to "The communicated content (or for multi-part communications, one portion of the communication)" with the same change on the equivalent CommunicationRequest element.

Initial application:
The issue appears to have been applied by commit a452682b2ad0328e1dec9b63685546719904daf2, whose subject included "#6251" and whose patch changed both Communication and CommunicationRequest spreadsheet sources from "An individual message part for multi-part messages" to the requested broader wording. Later source refactors carried that definition into the current StructureDefinition XML inputs.

Additional context:
Communication and CommunicationRequest are active resources in source/fhir.ini, so their StructureDefinition XML files are in the current core build scope. The current Communication.payload.content[x] definition says "A communicated content (or for multi-part communications, one portion of the communication)." The current CommunicationRequest.payload.content[x] definition says "The content (or for multi-part communications, one portion of the communication) to be communicated"; that later prospective wording was approved by FHIR-38783 and applied in commit fa35c0d85eb81ae4a3adc9de5c5cd75f201280f7. FHIR-20770 later added CodeableConcept payload support and explanatory comments to the same payload family, but it did not reintroduce the old multipart-only meaning. Targeted Zulip and Confluence searches found no direct FHIR-6251 community record that changes the Jira/source conclusion.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already conveys that the payload is the communicated content, or one portion of a multipart communication, and no current source location still uses the narrow "individual message part for multi-part messages" definition. Forcing the exact 2015 sentence back onto CommunicationRequest would undo the later FHIR-38783 tense clarification without changing implementer understanding of FHIR-6251.

Recommendation:
Keep this audit commit as-is. No follow-up core source work is needed for FHIR-6251 unless the work group wants a separate editorial cleanup of the article in Communication.payload.content[x], which is not necessary to satisfy this issue.
