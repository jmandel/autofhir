FHIR-19564: Audit Attachment filename extension location

Issue request:
FHIR-19564 was a Published/Persuasive with Modification MnM change request asking where to represent the original filename for a CDA carried in DocumentReference.content.attachment. The approved resolution was to add a note to Attachment.title that it may sometimes be derived from the source filename, and to create a standard Attachment extension named recommendedFilename with usage guidance allowing local paths and warning local systems to be cautious when storing files with local paths.

Initial application:
The R5 MnM application commit 732b40c16876bd7f23e75b50253824d920485f4e mentioned FHIR-19564 and added the Attachment.title comment in source/datatypes/attachment.xml. The same commit also added source/datatypes/attachment-extensions-spreadsheet.xml containing a recommendedFilename extension row on Attachment with the requested local-path usage note and security note.

Additional context:
FHIR-19601 is a duplicate of this filename question. The current build-scope authority, source/fhir.ini, has no active attachment-extensions profile entry, while Attachment itself remains part of the current datatype build. The historical recommendedFilename row was removed from the core source by dd468d4f1799dd79819315b211588ef1cf4586e0, whose subject was "remove extensions from R5 source". A current exhaustive search of the read-only FHIR Extension Pack checkout found no recommendedFilename/recommended filename/source filename/local-path extension definition and no extension-pack history containing the recommendedFilename text. Confluence minutes confirm FHIR-I reassigned the issue to MnM and MnM approved FHIR-19564 as persuasive with modification; corrected Zulip and Confluence searches found no conflicting community decision.

AutoFHIR reconciliation:
This commit makes no core source change. The current core source already carries the Attachment.title note in an active datatype source file, and the remaining missing artifact is the standard extension definition, which now belongs in the FHIR Extension Pack rather than this core checkout. Editing the out-of-build attachment-extensions spreadsheet or reintroducing a core extension definition would not be a current-build core fix.

Recommendation:
Keep this external-repo audit commit for the core reconciliation. If the work group still wants the FHIR-19564 extension, add recommendedFilename to HL7/fhir-extensions with context Attachment, type string, short/definition "The recommended filename for an attachment", and the local-path/security usage note from the original application; otherwise record a work-group decision that the extension was intentionally retired while retaining the Attachment.title note.
