FHIR-11505: Audit ActivityDefinition/DataElement boundary

Issue request:
FHIR-11505 was a Published/Persuasive CDS clarification request from the DSTU2 ballot asking ActivityDefinition to explain how it differed from DataElement, especially for order catalogs/master files where DataElement also described individual data that might be collected.

Initial application:
The issue was applied in SVN 10927, represented in git by c03a8aca84. That commit explicitly named #11505 and added ActivityDefinition boundary prose saying ActivityDefinition was a less granular reusable template for specific request resources, while DataElement described more granular elements such as a blood pressure or the answer to a question.

Additional context:
The same boundary question also appeared from the DataElement side in FHIR-11321. Later, FHIR-13094 was Published/Persuasive with Modification and collapsed DataElement into StructureDefinition/logical models; git commit d0802c9b75 removed DataElement references from ActivityDefinition while updating StructureDefinition context. In the current build, ActivityDefinition is active in source/fhir.ini, DataElement is commented out there and has no source/dataelement directory, while source/history.html records DataElement as a removed resource. Current ActivityDefinition prose still says the resource describes an activity/action and is a reusable template for request resources such as ServiceRequest and MedicationRequest.

AutoFHIR reconciliation:
This audit commit intentionally makes no source change. Reintroducing DataElement wording on the ActivityDefinition page would be stale because DataElement is no longer a current built resource, and adding a new StructureDefinition/logical-model comparison would be broader than the original applied issue and not required for implementer understanding of the current ActivityDefinition boundary.

Recommendation:
Keep this no-change audit. If a future work group wants a current comparison between ActivityDefinition order catalogs and StructureDefinition logical models, handle that as a new CDS/conformance clarification rather than reviving the retired DataElement wording.
