FHIR-3478: Audit Attachment.creation application

Issue request:
FHIR-3478 is a Published/Persuasive with Modification FHIR-core datatypes issue asking to add a 0..1 dateTime element to Attachment so an attachment's creation timestamp can be conveyed without companion elements on every resource using Attachment. The accepted recommendation also called for reviewing Attachment users, especially Media and patient/provider/related-person photos.

Initial application:
The historical implementation is explicit: git commit c1c8b179a9 (#3478, svn revision 4527) added Attachment.creation as 0..1 dateTime to source/datatypes/attachment.xml and removed the then-existing Media.created element while adding Media.content guidance. A later Media-specific commit, 6cb3689cb2 for FHIR-10212, added Media documentation pointing readers to Media.content.creation.

Additional context:
source/fhir.ini routes ordinary datatypes to the datatypes page and marks Attachment normative, so source/datatypes/attachment.xml is active build input. Current source still defines Attachment.creation 0..1 dateTime with the intended creation-date meaning. Later Media decisions refine but do not reverse this issue: FHIR-10212 resolved that the media recording date already existed at Media.content.creation and should be documented more clearly, while FHIR-14144 later aligned Media with Observation by adding Media.created[x] and Media.issued for collection/availability timing. Current Media notes explain the relationship between Media.created[x] and Media.content.creation. Community searches found no FHIR-3478-specific reversal or Confluence record.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The seed request is already represented in current active source, and the apparent Media companion work has either already been applied or later superseded by separate Media decisions.

Recommendation:
Keep this audit commit as-is. No core source follow-up is needed for FHIR-3478; any future work on Media timing should be handled under the later Media issue family rather than reopening the Attachment datatype addition.
