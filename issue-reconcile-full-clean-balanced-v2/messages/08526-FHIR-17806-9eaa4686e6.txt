FHIR-17806: Audit conditional transaction support

Issue request:
FHIR-17806 was Published with a Persuasive with Modification resolution for the FHIR-core HTTP page. It asked whether batch and transaction entries support conditional create/update/delete through Bundle.entry.request and whether conditional PATCH should be reflected in the transaction processing rules. The resolution recorded that Bundle.entry.request already carries ifNoneMatch, ifModifiedSince, ifMatch, and ifNoneExist, and that the same conditional properties used with PUT can be used with PATCH.

Initial application:
No source commit with the FHIR-17806 key was found. The PATCH-ordering portion appears to have been applied through the same October 2018 decision family as FHIR-18300: git commit 2b62df68e0 changed the transaction order from PUT-only to PUT or PATCH and from GET-only to GET or HEAD. Bundle.entry.request already contains the conditional request fields cited by the FHIR-17806 resolution.

Additional context:
FHIR-18300 covers the directly overlapping PATCH transaction-ordering clarification and is already represented on the combined branch, so this commit does not duplicate that issue. A later Published issue, FHIR-34060, refactored the transaction order list from raw HTTP verbs to linked FHIR interactions while preserving PATCH on the update line. Current http.html also defines conditional patch and lists patch-conditional in the HTTP summary tables. Exact-key Zulip and Confluence searches found no conflicting community record.

AutoFHIR reconciliation:
This is an empty no-change audit commit. The current source already permits the conditional request metadata on Bundle.entry.request and already includes PATCH in the transaction processing order, so an additional source edit would be redundant rather than corrective.

Recommendation:
Keep this audit commit as-is. No follow-up source change is needed for FHIR-17806 unless a future work group decision chooses to restate conditional PATCH in additional summary prose.
