FHIR-16534: Audit OAuth access-control guidance

Issue request:
FHIR-16534 was Published with resolution Persuasive with Modification for the Security work group. It asked the FHIR security checklist to add Authorization/Access Control guidance that when OAuth is used, an OAuth profile is needed, and that the SMART-on-FHIR App Authorization Guide should be considered where appropriate.

Initial application:
The issue was applied in the historical security narrative commit 95ee245e72e4bd1ac09824738ae7b5f7519239ef, which changed source/security.html. That commit placed the OAuth/SMART checklist text in the Authentication summary item rather than the Authorization/Access Control summary item, while leaving the access-control summary text about the FHIR Security Label infrastructure.

Additional context:
Later Security work, especially FHIR-34362, revisited the same security checklist and OAuth access-control wording. It added a separate "When using OAuth" checklist item for OAuth security best-current-practice and added token expiration/scope as access-control context. The current source has since been reorganized: the summary still recommends OAuth and the HL7 SMART App Launch IG for web-centric authentication, the access-control section recommends OAuth and SMART App Launch for authorizing interactions with a protected FHIR server, the SecPriv module recommends the OAuth-based SMART protocol for third-party app authorization, and the Safety checklist still says systems should use a risk- and use-case-appropriate OAuth profile, preferably SMART App Launch. FHIR-53717, FHIR-53923, and FHIR-56089 later made security-page editorial cleanup without changing this OAuth/SMART substance.

AutoFHIR reconciliation:
This is an empty no-change audit commit. The current built source already conveys the substantive FHIR-16534 guidance through active source/security.html, source/secpriv-module.html, and source/safety.html. Re-adding the exact older "a profile of OAuth will be needed" sentence to the security summary would duplicate nearby active guidance and risk editorial drift without changing implementer understanding.

Recommendation:
Keep this audit as-is. If the Security work group wants stricter or differently located OAuth-profile wording, handle that as a fresh editorial/security-page tracker rather than as a missed application of FHIR-16534.
