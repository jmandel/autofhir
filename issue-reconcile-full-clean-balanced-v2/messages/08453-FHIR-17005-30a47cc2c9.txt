FHIR-17005: Audit JSON comments guidance

Issue request:
FHIR-17005 was a Published/Persuasive with Modification FHIR-core JSON-page ballot issue asking to clarify that the pseudo-JSON examples use // comments, but // comments are legal in JavaScript rather than JSON files or instances. The resolution also recorded that a _comment property might or might not be ignored by processors, but would not make the instance valid.

Initial application:
The issue was applied in git commit f615f53824fcb9432db703108c72399b1c9a83c1, matching Jira's svn revision 14249 comment. That commit changed source/json.html from saying // comments cannot be in JSON instances to saying // is legal in Javascript but not JSON and comments SHALL not be in JSON instances irrespective of whether applications ignore them.

Additional context:
The current source/json.html page is in the build through publish.ini, and its current text preserves the applied rule with the later 2025 correction to uppercase SHALL NOT. Older JSON-comment issues show that earlier support for fhir_comments/comments was removed or superseded before this issue, and the 2018 FHIR-I minutes list FHIR-17005 as Persuasive with Modification. Later community search found no FHIR-17005-specific Zulip conflict; a 2020 minutes snippet separately notes no normative JSON syntax or commitment for JSON comments.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current JSON page already conveys the required rule: // may appear in the specification's illustrative format, but comments are not valid in JSON instances even if an implementation chooses to ignore them. Adding separate _comment prose would be redundant and could blur the stronger existing SHALL NOT statement.

Recommendation:
Keep this audit commit as-is. No follow-up source edit is needed for FHIR-17005 unless the work group wants a new, broader policy on non-standard comment-like properties in JSON instances.
