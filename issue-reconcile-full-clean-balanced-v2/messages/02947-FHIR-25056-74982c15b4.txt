FHIR-25056: Audit PlanDefinition apply output options

Issue request:
FHIR-25056 was Published/Persuasive for R5 and asked to fix PlanDefinition/$apply because its output only listed CarePlan even though RequestGroup could also be the result of applying a PlanDefinition.

Initial application:
The issue was directly applied by commit 95d6822227 (J#25056), which added a useCarePlan input and changed the return parameter from CarePlan to Resource with documentation naming CarePlan or RequestGroup. A 2020 Zulip follow-up showed the change was still on the editor backlog before that source commit landed.

Additional context:
RequestGroup was later renamed to RequestOrchestration by FHIR-24619. FHIR-33169 then intentionally replaced the CarePlan-or-RequestOrchestration return shape with a Bundle 0..* return and removed useCarePlan; that issue is already represented on the combined branch. FHIR-46313 later relaxed the Bundle contents so the result may be any combination of request resources, explicitly including CarePlan and RequestOrchestration, and FHIR-51557 clarified that the plural Bundle return is encoded in a Parameters response.

AutoFHIR reconciliation:
No source change was made. The current build-scoped PlanDefinition/$apply operation returns Bundle 0..* and the operation and PlanDefinition narrative both state that result Bundles can contain request resources including CarePlan and RequestOrchestration, so the current specification no longer has the CarePlan-only output problem that FHIR-25056 identified.

Recommendation:
Keep this audit commit as-is. Do not restore the older useCarePlan/Resource return shape for FHIR-25056; the current Bundle-based semantics are governed by later final PlanDefinition/$apply decisions. FHIR-46313 and FHIR-51557 can be reconciled separately if needed, but they do not require a seed source change here.
