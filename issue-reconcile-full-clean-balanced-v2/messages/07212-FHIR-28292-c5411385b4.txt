FHIR-28292: Audit operation return response wording

Issue request:
FHIR-28292 was a Published/Persuasive FHIR-I clarification for operations.html asking whether a single output parameter named "return" may be wrapped in Parameters. The approved decision was that when the single return output has maximum cardinality 1 and a resource type, the server SHALL return the resource directly with no wrapping Parameters resource.

Initial application:
The issue was applied by git commit 61cdda43d3, which changed the operations response overview from MAY to SHALL with no wrapping Parameters resource, removed a duplicate MAY paragraph, and changed the operation response section to describe a single Resource named "return" being returned directly.

Additional context:
FHIR-I minutes from 2020-12-07 record the same 11-0-0 decision: if the output parameter is a Resource named "return" with cardinality 0..1, the server SHALL return the resource directly. The current source/operations.html page is in current build scope via source/hierarchy.xml, and operation-specific notes for multi-cardinality return Bundles continue to direct those responses through Parameters, which is consistent with the approved max-cardinality-1 limit. A companion AutoFHIR commit for FHIR-24869 restored the adjacent "one or more output parameters" typo before this audit; it did not change the FHIR-28292 rule.

AutoFHIR reconciliation:
This is an empty audit commit. The current active Operations Framework source already says that a single output parameter named 'return' with maximum cardinality 1 and a resource type SHALL be returned as the resource value with no wrapping Parameters resource, and the response section already says the parameter format is not used for a single Resource named "return".

Recommendation:
Keep this audit commit as-is. No additional FHIR-28292 source change is needed unless the work group wants a future broader editorial cleanup of the operations response prose.
