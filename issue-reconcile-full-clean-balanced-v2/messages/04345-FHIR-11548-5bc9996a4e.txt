FHIR-11548: Audit ActivityDefinition binding application

Issue request:
FHIR-11548 was a Published/Persuasive CDS change request from the 2016 September CQF ballot asking that ActivityDefinition provide at least example bindings for code, timing, and product, because the then-current bindings were incomplete and it was unclear how timingTiming and productReference bindings should work.

Initial application:
The request was applied in SVN revision 10935, now git commit 21fb883470b18d1dd855f6e5d61e73259b77f73e, which changed the ActivityDefinition spreadsheet binding rows from unbound to example bindings for ActivityDefinitionType/procedure-code, ActivityTiming/timing-abbreviation, and ActivityProduct/medication-codes. Shortly afterward, FHIR-12935 was applied in SVN revision 11549, now git commit 67644277d6ccc7946f18aaaa0d1c617a8ca8ec2c, removing the CodeableConcept choice from ActivityDefinition.timing[x] and dropping the ActivityTiming binding because timing was to be expressed with Timing/dateTime/Period/Range instead.

Additional context:
ActivityDefinition is active in source/fhir.ini and the current authoritative StructureDefinition source contains example bindings for ActivityDefinition.code and ActivityDefinition.product[x]. The current ActivityDefinition.timing[x] is no longer a bindable CodeableConcept-bearing choice; later published/applied timing decisions refined the allowed types and guidance, including FHIR-12935, FHIR-14082, FHIR-25471, FHIR-43696, and FHIR-29799. Community searches found no human Zulip or Confluence discussion that conflicts with the Jira and git history.

AutoFHIR reconciliation:
This commit intentionally makes no source change. Restoring an ActivityTiming binding on the current timing[x] element would conflict with the later published model in which timing is represented by Timing, Age, Range, Duration, and RelativeTime rather than a direct CodeableConcept timing choice. The remaining seed-request bindings for code and product are already present on active current source.

Recommendation:
Keep this no-change audit. If a future work group wants timing-specific vocabulary guidance for ActivityDefinition, it should be considered as a new timing-model issue, likely on Timing or RelativeTime semantics, not as a reapplication of the obsolete 2016 ActivityTiming binding.
