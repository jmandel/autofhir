FHIR-5539: Audit transaction response HTTP semantics

Issue request:
FHIR-5539 was a Published/Persuasive FHIR-core Feed change request from DSTU1 asking to reuse RESTful HTTP status semantics in transaction results instead of relying on the older implicit mix of Bundle entry status, resource metadata, and deleted-entry modeling.

Initial application:
No git commit explicitly names FHIR-5539. The relevant 2015 history shows the Bundle transaction model was reworked shortly after the issue was filed, including explicit transaction/response-related entry structures, and the approved header follow-up appears in the March 2015 http-response-header extension commit. A later Published/Persuasive related tracker, FHIR-8878, clarified the same response status element to require at least a three-digit HTTP code.

Additional context:
Bundle is an active current-build resource in source/fhir.ini and is normative. Current source requires response elements for transaction-response and batch-response bundles, defines Bundle.entry.response as the result of processing the corresponding request, makes Bundle.entry.response.status mandatory, and defines that status as starting with a three-digit HTTP code with optional standard HTTP description text. The RESTful HTTP page also explains that batch/transaction response entries carry the HTTP status code plus Location and ETag values where applicable. The older http-response-header extension was removed from core R5 source when extensions moved out of core and now exists in the FHIR Extension Pack, so re-adding it to core would be the wrong current-build fix.

AutoFHIR reconciliation:
This commit intentionally makes no source change because current build-scope core source already conveys the FHIR-5539 decision: transaction response entries use explicit response elements with HTTP status/header semantics rather than the obsolete implicit status/resource meta/deleted model.

Recommendation:
Keep this audit commit as-is. Do not reintroduce the old core http-response-header extension into core; any future work on arbitrary response headers should be handled in the Extension Pack, while the core Bundle response status/location/etag/lastModified model is already correct.
