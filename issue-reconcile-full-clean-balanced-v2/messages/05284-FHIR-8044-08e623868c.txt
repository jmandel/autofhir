FHIR-8044: Audit CommunicationRequest occurrence range

Issue request:
FHIR-8044 was a Published/Persuasive Patient Care DSTU1 change request asking FHIR Core to rename CommunicationRequest.scheduledTime to scheduled[x], allow dateTime or Period, and explain that a Period represents the time period within which the communication should occur.

Initial application:
The request was applied in git commit a452682b2a (#8044, #8198, #8466, #6251), which changed the CommunicationRequest spreadsheet element from scheduledTime to scheduled[x] and changed its type from dateTime to dateTime|Period. The implementation kept the element definition as "The time when this communication is to occur," which already applies to either a point in time or a Period.

Additional context:
Later Published/Persuasive Patient Care issue FHIR-10293 applied workflow standardization to CommunicationRequest. Its implementation commit 999f9323ad renamed the scheduling element from scheduled[x] to CommunicationRequest.occurrence[x], preserved the dateTime|Period choice and the "When scheduled" short description, updated examples/search parameters to occurrence, and left the active conversion mapping CommunicationRequest.scheduled=CommunicationRequest.occurrence in source/fhir.ini. The current CommunicationRequest resource is active in source/fhir.ini, and the current occurrence search parameter explicitly searches both dateTime and Period. Related FHIR-8198 was part of the same original implementation commit and is already represented on the combined branch by its own no-change audit commit.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current active CommunicationRequest definition no longer contains scheduledTime; its workflow-aligned successor CommunicationRequest.occurrence[x] remains 0..1 dateTime|Period and conveys the effective timing/range requested by FHIR-8044. Adding another local sentence specifically restating Period semantics would not change implementer understanding and could create maintenance drift.

Recommendation:
Keep this no-change audit commit. No FHIR core follow-up is needed for FHIR-8044 unless Patient Care reopens the broader CommunicationRequest timing model, such as adding Timing for repeated reminders or requiring a new explicit comment beyond the existing dateTime|Period choice.
