FHIR-38872: Align x-fhir-query language code

Issue request:
FHIR-38872 was a Published FHIR-core change request, resolved Persuasive with Modification for R5, asking Expression support to cover FHIR operations by moving x-fhir-query documentation into core, ensuring x-fhir-query covers URL-invocable operations, and defining a server-style FHIRPath service surface for operations needing body parameters such as StructureMap/$transform and ActivityDefinition/$apply.

Initial application:
The issue was initially applied by commit 36365345c78a1ddcd443605a8c033a4dd757c61d, which added source/fhir-xquery.html, linked it from the documentation and hierarchy, added operation examples to x-fhir-query, and introduced the FHIRPath General Service API with %server.transform and %server.apply. The current source still had the operation support, but two build-scoped source locations retained the old application/x-fhir-query spelling even though the current ExpressionLanguage value set and surrounding Expression narrative use text/x-fhir-query.

Additional context:
Expression is active in source/fhir.ini under [types], with expression=metadatatypes in [type-pages], so source/datatypes/expression.xml and source/metadatatypes.html feed the current datatype pages. source/fhir-xquery.html is active through publish.ini and source/hierarchy.xml. FHIR-27883 and commit 450cf3e64ae3d71ae6c027d39327311afdfc1986 moved ExpressionLanguage to BCP 13 MIME codes and the current value set defines text/x-fhir-query. FHIR-46082 later fixed a separate typo in the same General Service API section and is already represented on the combined branch, so it is context only.

AutoFHIR reconciliation:
Updated source/fhir-xquery.html so the x-fhir-query page names text/x-fhir-query consistently with the current ExpressionLanguage value set, and updated the active Expression datatype source short text in source/datatypes/expression.xml from application/x-fhir-query to text/x-fhir-query. No other operation semantics were changed because the existing x-fhir-query operation example and %server.transform/%server.apply FHIRPath API already satisfy the rest of the issue.

Recommendation:
Keep this commit. It removes a build-scoped conformance inconsistency that would otherwise point implementers at a language code not present in the current ExpressionLanguage value set, while preserving the already-applied operation support from FHIR-38872 and later FHIRPath cleanup.
