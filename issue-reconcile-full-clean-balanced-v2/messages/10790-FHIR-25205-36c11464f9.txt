FHIR-25205: Audit DocumentReference content versions

Issue request:
FHIR-25205 was Published as Not Persuasive with Modification for STU3/R5. It asked where to represent distinct creation/scanning/reference dates after DocumentReference.created was removed, and the accepted resolution clarified that repeated DocumentReference.content attachments are not different versions of a document. Different versions should be represented by multiple DocumentReference resources related through DocumentReference.relatesTo, with a content-definition note and implementation-note clarification.

Initial application:
No source commit explicitly names FHIR-25205. The application appears to be part of the August 2020 DocumentReference block-vote commit 0bf0b46, after the OO 2020-07-16 block vote, which added the DocumentReference.content comment that content repetitions shall not contain different versions and that version handling uses multiple DocumentReference resources with .relatesTo. Commit 33b409a migrated that wording into the current StructureDefinition XML source, and commit 465bcbf preserved it while adding separate title guidance for FHIR-17909.

Additional context:
The referenced Zulip thread confirms the original ambiguity came from the R4 removal of DocumentReference.created and interpretation of Attachment.creation. FHIR-17453 is the earlier published decision that removed DocumentReference.created as redundant with Attachment.creation. Later DocumentReference relatesTo/related cleanup in commit 3800384 added current implementation-note language that relatesTo is for document reference lifecycle changes such as revisions and transforms. DocumentReference is active in source/fhir.ini, so the inspected source feeds the current build.

AutoFHIR reconciliation:
This audit commit makes no source change. The current source already states that multiple DocumentReference.content repetitions must all represent the same document in different formats or attachment metadata, not different versions; it directs version handling to multiple DocumentReference resources with .relatesTo; and the implementation notes now describe relatesTo as the lifecycle relationship mechanism for revisions and transforms. Adding more date-specific prose would go beyond the accepted resolution and risk duplicating or changing guidance that the work group did not approve for this issue.

Recommendation:
Keep this empty no-change audit commit. No core source follow-up is needed for FHIR-25205 unless OO chooses to open a new issue for broader date-capture guidance beyond the published resolution.
