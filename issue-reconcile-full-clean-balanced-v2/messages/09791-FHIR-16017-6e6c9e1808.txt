FHIR-16017: Audit exact string Unicode search behavior

Issue request:
FHIR-16017 is a Published/Persuasive FHIR-core search issue for STU3. It asked the string search :exact modifier to specify that exact matching includes casing and combining characters, while handling of extended grapheme clusters and canonical equivalence remains within server discretion.

Initial application:
The issue was initially applied in SVN revision 14261, represented in this git repository by commit 2f6cb4b8fee23dac83c8021e22b04f93ac8f25f1, which changed source/search.html to add the grapheme-cluster and canonically-equivalent-character discretion text for string :exact.

Additional context:
FHIR-16016 is the same change family and was applied immediately before this issue in revision 14260 to clarify default string search handling of combining characters. Later search-modifier documentation commits reorganized source/search.html and preserved the FHIR-16017 rule in the dedicated exact modifier section. The referenced Zulip discussion confirms the original intent, and Jira/Confluence searches found no later decision that reverses it. source/search.html is the current core search source page.

AutoFHIR reconciliation:
No source change was made. The current source/search.html :exact modifier section says the supplied string input is the complete exact value tested for a match, including casing and combining characters, and says the server decides whether matching uses canonically equivalent characters or the actual Unicode code points.

Recommendation:
Keep this no-change audit commit. The current dedicated modifier section conveys the required behavior; duplicating the full explanation in the later string-type summary would be editorial and could create maintenance drift.
