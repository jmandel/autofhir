FHIR-43364: Audit Element extension context clarification

Issue request:
FHIR-43364 was Applied/Persuasive with Modification for R6 and asked the FHIR-core extensibility documentation to explain the historic meaning of a StructureDefinition.context.type of element now that Resource is no longer modeled as an Element. The approved resolution chose documentation over changing the context model or tooling, and specified that element contexts can reference resource and datatype roots; DomainResource or a specific resource can express root-only use; and fhirpath is needed for all-elements-except-root use cases.

Initial application:
The upstream application commit 2865d924342d7f3870bcbaefb89ecdd67b671a2a added a Notes list to source/defining-extensions.html#context with the approved element/root clarification, the legacy Element-anywhere convention, the DomainResource/Patient root-only examples, and the fhirpath fallback for excluding roots. That source page is build-scoped as the Defining Extensions guidance linked from the active extensibility and StructureDefinition pages.

Additional context:
The originating Zulip thread matches the Jira request: participants identified that Element had historically meant anywhere extensions are actually allowed, including DomainResource roots, despite the R5 class model separating Resource from Element. Later extension-context work in FHIR-41633 and FHIR-46620 refined adjacent assigned-type and Resource-context wording; FHIR-46620 already has a reconciliation commit on the combined branch and now leaves the current source consistent with FHIR-43364.

AutoFHIR reconciliation:
This commit intentionally makes no source change. The current source already conveys every approved point from FHIR-43364 in source/defining-extensions.html#context, and the adjacent StructureDefinition and ExtensionContextType sources point readers back to that guidance.

Recommendation:
Keep this no-change audit commit. Further edits for FHIR-43364 would mostly duplicate existing guidance or perform editorial cleanup rather than change implementer understanding; handle any future Resource-context refinements under their own Jira issues.
